# Decisions

The decisions in force across Whombat, one row each. Product decisions come from the maintainer (John); the others
were taken while building and keep their reasons in the linked file under `docs/decisions/` (index:
`docs/decisions/README.md`).

When a decision changes, replace its row here and mark the old row in its decision file “Superseded by …”; don't
annotate rows in this file. A new cross-cutting decision gets a row in the section it belongs to.

## What Whombat is

| # | Decision |
|---|---|
| OP-01…OP-03 | **A Whombat is one person's device.** One person uses it and talks to its one agent; nobody else signs in. The person's own devices, support while remote help is on, and outsiders who only send something in (website feedback reporters, a report tracker's customers, whoever mails the person) remain. No invites, members, roles, admins or presence between people. (`one-person.md`) |

## Writes, keys and the audit log

| # | Decision | Reason |
|---|---|---|
| A-03 | Contract first: Zod schemas for every operation, frame and runner message in `@whombat/core`, in this repository's `packages/`; a contract change and the server, web and mobile code that use it are one commit. | Server, web and mobile build against one typed contract. |
| A-04 | One write path, the commit pipeline, for the person, the agent, Whombat's own signers and the runner. Session operations and MCP tools are thin adapters over the same commands. | The keys engine, signing and audit apply to every actor alike. |
| WL-01…WL-03 | **A write holds the burrow lock briefly**: outside calls (Google's changes) run after the commit and sign their event once done; `callGoogle` refuses to run under the lock in development and tests, except for an approval card's reads; a write's statements and its wait for the lock stop after a minute. | One slow provider must not hold up every write on the box, or leave a change made with no record of it. (`write-lock.md`) |
| A-05 | Ed25519 signatures, a per-burrow hash chain, an append-only `events` table enforced by a trigger. | Tamper evidence without Nostr's key management. |
| D-06 | Signing keys are held by the server per principal, encrypted at rest with the master key, built so user-held keys can be added later. | Maintainer, 2026-09-23. |
| C-03, C-13 | Operations are `api.<area>.<action>` contracts; a mutation resolves to `CommitResult` (`ok` / `pending_approval` / `blocked`), and MCP tools answer with the same union. | One outcome shape everywhere (`core-contracts.md`). |
| C-04 | Event ids are `evt_<hex>`, shown as `e-<hex>`; seed keypairs are derived deterministically, so fingerprints are stable. | Matches the mock; stable tests. |
| C-12 | Not signed: read markers, account state, derived projections. High-volume internals are signed with `text: null` and hidden from the log. | The log shows meaningful actions only. |
| BP-06, BP-07 | Private content stays out of signed events (ids, sizes, hashes, versions only). Retrieved data is data: memory, attachments and tool output are delimited in prompts and never authorize anything. | Privacy of the log; prompt injection (`buzz-parity.md`). |
| B-02 | Undo on an approval is possible only until its action has executed. | An executed action can't be taken back. |
| APC-01…APC-05 | An approved connection call ends its approval as the call did: succeeded, failed in plain words, or uncertain. An HTTP write, a page's button included, requires a 2xx response (a redirect is never done); it runs after its command's commit as a required continuation, and after a crash its own events settle it, never sending it twice. The yes is bound to where the call goes and as whom, and to where every other connection it acts through goes (a Servers backup place on a TrueNAS); a card's words and its yes come from one read of the connection, and the card is saved only while the connection is still stored so; every request is signed only as the connection it was checked on (a pooled session too, and every credential, checked before it is opened and again once it is in hand), and nothing is sent once any changed, not even a sign-in, a token refresh, a datagram or a line (the agent hears it and may ask again). An Undo goes only where its change went. A page's button, setting and Put it back sign only as the connection they were checked on, the assistant's yes to a page change is bound to where it goes and its action runs only bound, and a request not sent for a changed connection is never reported as “may have happened”. A yes to a call or page change the previous release saved unbound runs nothing and asks again on a fresh card bound now; page-change cards name the connection by its label. (`approved-connection-calls.md`) | A failure after the yes was logged and the approval still said it was done. |
