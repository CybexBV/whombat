# Backup options, the list of backups, the passkey-locked kit and bringing a Whombat back, on the phone (AP-6850…AP-6864)

John, 2026-11-03: see the backups it made, choose how many and how much space, keep a way back in with a passkey, and
bring a Whombat back on a new box (Whombat `docs/decisions/backup-options.md` BKO-01…14; mockups approved the same day,
their final changes in the orchestrator's `MOCKS.md`). The shared words and views are `@whombat/client/managed`'s
`backup-options.ts` and `kit-passkey.ts`, the hooks `@whombat/client/react`'s `backupOptions.ts`. This is the phone's
part (Android and iPhone): the pure decisions are `managed/backupOptions.ts` (unit tested), the screens
`WhombatBackupsScreen.tsx`, `BackupsOverview.tsx`, `BackupOptionsScreen.tsx`, `BackupDetailScreen.tsx`, `KitWays.tsx`
and `BringBack.tsx`, the demo's box `fixtures/backupOptions.ts`.

| ID | Decision | Why |
|---|---|---|
| AP-6850 | **This Whombat → Backups shows the new page when the box answers `backup.checkpoints` and `backup.policy` and has a destination**; an older box (`unknown_op`), a refusal or an unprotected box shows the page as it was (BACKUPS with Set up backups, ON YOUR NETWORK, RECOVERY KIT, BACKUP FILE). | The ops are new; a box without a place has nothing to list and needs Set up first. |
| AP-6851 | Superseded in part by backup-v2.md AP-6887, AP-6889 (no kit row; Details). **The web's page stacked**: top card (shield in an ok circle, `backupHero`'s title, line and chips; Back up now and Options side by side under them), NEEDS YOU (one bordered card per row, the kit's with the warn border; buttons under the words), BACKUPS · N with NEWEST FIRST, the day groups and the first 9 rows until Show all, the assistant line, then ON YOUR NETWORK, “Set up backups” (choosing a destination by hand stays reachable), a quiet Recovery kit row with Save again, BACKUP FILE. | The mock is the web's at 728 px; a phone's width wants the buttons under the text. |
| AP-6852 | **Words the shared text lacks stay in the phone's `BACKUP_PHONE_TEXT`** (Back, Recovery kit, Save again, printed, saved as a file, Saved 3 November, the options' field errors, the print and file failures, “Waiting for Home to answer…”). | The web agent edits the shared file at the same time; these can move there when both are merged. |
| AP-6853 | **Backup options is a pushed screen with Cancel · Backup options · Save in its header**; the numbers are kept as typed until Save (`policyDraft`/`draftInput`), which refuses a half-typed number, “Every backup for” under 1 day and a limit under 1 GB in plain words; turning the limit on starts the field at twice what the backups take now (at least 10 GB). The timeline under “Up to a year” draws the ticks of the choice being edited. | A sheet over a keyboard and four number fields is cramped; Save must never send a guess. |
| AP-6854 | Superseded in part by backup-v2.md AP-6887: only a Whombat from before the passkey reaches it. **“Keep a way back in” replaces the old save-and-confirm screen** (the rotation step with the current key stays before it): three checkboxes, Your passkey (RECOMMENDED, ticked) only where the phone can carry PRF and control is there, Print it too (ticked), Save as a file; the button is “Use my passkey” while the passkey is ticked, else “Save”. | MOCKS.md screen a. |
| AP-6855 | **PRF through the native module**: `prf()` asks for an assertion of this Whombat's passkeys (`allowCredentials`, a random challenge nobody verifies, user verification required) with `extensions.prf.eval.first` and reads `clientExtensionResults.prf.results.first`; null when absent (the kit says `kit.noPrf`). Android passes the JSON to Credential Manager unchanged; iOS sets `request.prf = .inputValues(…)` and reads `credential.prf?.first` on iOS 18 and later. `supportsPrf()` (new in both modules; an older Android build is taken as able) decides whether the passkey row shows. | One API on both; iOS before 18 has no PRF, and offering what fails is worse than not offering it. |
| AP-6856 | Superseded in part by backup-v2.md AP-6893, AP-6894. **One backup is a pushed screen**: ‹ Backups, “Today, 03:00”, why · what it added · on which place, the check badge, WHAT’S IN IT, Check this backup now (then `checkQueued`), Download it as files… which unfolds `downloadLead` under it (no download from the phone). | MOCKS.md: no “Go back to this backup…”. |
| AP-6857 | **Printing is a page shared through the share sheet**: the app has no print module, so it writes an HTML page (title, lead, QR code of `kitQrPayload` with `printScan`, the kit's text; black on white whatever the theme) to its cache and shares it; a browser or printer app prints it. The file goes with the kit's other temporary files. | No new native dependency for one page; the share sheet is how the phone already saves the kit. |
| AP-6858 | Superseded by backup-v2.md AP-6885 (one passkey rule for both apps). **A kit locked with the passkey is confirmed at once**; a printed or saved one after “I’ve saved the kit”, as before. The phone remembers, per Whombat identity, the kit generation it kept and how (`whombat-kit-kept.json`), since control can't know of a print; NEEDS YOU asks while the kit isn't confirmed, or neither an envelope at control nor this phone kept the current generation. Without control's envelopes (no control, an older control) only the confirmation counts. | The envelope proves it is kept; a share sheet doesn't. |
| AP-6859 | **After the claim the phone asks “Is this a new Whombat?”** (`claimStepKicker('protect')`, so the steps stay numbered as the claim's: it stands where the backup step was); Start fresh goes on to where backups go, Bring back follows its own screens without a kicker, as drawn. | The claim's steps are shared with the web; this adds no step to the count. |
| AP-6860 | Superseded by backup-v2.md AP-6900. **The kit comes from the account's newest envelope for another Whombat** (`kitsToBringBack`, unlocked with the passkey), **the printed kit scanned** with the app's QR scanner, **the file** through the document picker, or **pasted** (the scanner's way out, and where the camera is refused). The name shown is the envelope's, else the kit's `Whombat:` line. | The phone has a camera scanner already (the claim card); a person without a camera still gets in. |
| AP-6861 | **While it works the phone asks `backup.restoreState` every 3 s**; an unanswered ask is the runtime stopped for the restore: the steps show the copy as going (`restoreSteps(state, false, place)`), “Waiting for Home to answer…” under them, and the session is told to dial again at once. A session closed for good (the box that came back doesn't let this phone in) shows the failed screen. | BKO-12: nothing serves the app while the runtime is down. |
| AP-6862 | **The newest backup is picked first**; three are listed, Older backups… shows all. | The mock's “The newest is usually the one you want.” |
| AP-6863 | Superseded by backup-v2.md AP-6901, AP-6902. **“Almost there”'s sign-ins card answers with its button** (“Sign in” when some need it, “They’re fine” otherwise; none to check is answered already) and the devices card with “They’re all mine”: signing in and reviewing devices happen in the Whombat once it opens. After Start, the phone follows the state until it is released, then Done (the assistant's name read from the box), Open Chat. | Nothing else runs until the answers are in, so the screens before the Whombat opens can only record them. |
| AP-6864 | **The demo world answers the backup ops** on an in-memory box (`fixtures/backupOptions.ts`: BlackBox, 6.2 GB used, 1.9 TB free, 23 backups, one checked, 14 older on the box), and its This Whombat page has a Backups row opening the same screens; places, the kit and the backup file stay a Whombat's. | The screens can be looked at and screenshotted without a box. |
