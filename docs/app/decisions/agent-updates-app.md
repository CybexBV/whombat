# Server agents keep themselves up to date, on the web and the phone (AP-2980…AP-2994)

John, 2026-10-20: “I want the agents to automatically update if there is a new version.” The product decisions are
Whombat's `docs/decisions/agent-updates.md` (AU-01…AU-10); this is stream U of
`docs/implementation/agent-updates/assignment.md` there: AU-06, AU-08 and AU-09 on the web's System tab and This
Whombat → About, and on the phone's server screen and Settings. Contracts 0.99.0 (CT-510…CT-516: `HostAgentUpdate`'s
`reasonCode`, `auto`, `state` `waiting`/`halted`, `waitingFor`, `failedVersion`, `updatedAt`, `canInstall`;
`HostAgentSettings`; `hosts.agentSettings`, `hosts.updateAgentSettings`, `hosts.updateAgent`; feature
`hosts.agent_updates`). Not in the mocks (B-05): the Agent card and This Whombat as they are.

The rules and words are `@whombat/client/hosts` `agent-updates.ts` (tested); the web's parts are the Agent card in
`apps/web/src/features/things/tabs/SystemTab.tsx` and `apps/web/src/features/settings/AgentUpdatesSwitch.tsx`; the
phone's `apps/mobile/src/screens/server/AgentUpdates.tsx` and `apps/mobile/src/settings/AgentUpdatesSwitch.tsx`; the
fixtures `packages/client/src/hosts/fixtures-au.ts` and `apps/mobile/src/fixtures/hostsAgentUpdates.ts`.

| ID | Decision | Why |
|---|---|---|
| AP-2980 | **One view model for both clients**: `agentUpdatesView` picks the Updates row's words, tone, “updated 2 h ago” and its one button from the server's `agent.update`, the switch, the viewer, the connection and the runtime; `agentSettingsView` the switch's. | The web and the phone say the same thing for the same state (the brief puts shared words and state logic in `packages/client`). |
| AP-2981 | **The Updates row, in this order**: updating (“Updating to the new version…”, no button); the server's own owner turned updates off (“Updates are turned off on {server} itself.”, no button: nothing Whombat presses changes it); failed (“Couldn’t update: it went back to the version it had.” + **Try again**); no key or another key (“Needs one more install, then it updates itself.” + **Update the agent** where `canInstall`, else the install command); halted (AP-2982); waiting (AP-2983); a newer version with the switch off (“Automatic updates are off.” + **Update now**), on (“Updates to the new version soon”); else “Kept up to date” (on) or “Up to date” (off). A newer agent than the build (`newer_running`) is up to date too. All three buttons are `hosts.updateAgent`; the note says “Updating the agent on {server}.” or, for the last install, “Installing the agent on {server} once more.”. | AU-08's words. Turned off on the server outranks an old failure: it is why nothing more happens. A last install that failed offers Try again where Whombat may run it, the command where it may not. |
| AP-2982 | **Halted on a server that didn't fail**: “Stopped: the new version didn’t work on another server.” with **Update now** (amber). | AU-05 stops the rollout everywhere; “Couldn’t update: it went back …” would be untrue on servers that never tried. Update now clears the halt (the hub's rule). |
| AP-2983 | **What it waits for**: `packages` is AU-08's “Waits until {server} has finished installing updates”; `console` “Waits until the console on {server} is closed”; `task` “Waits until {server} has finished its task”. No button: it is tried again by itself. | AU-04's three reasons, in AU-08's shape. |
| AP-2984 | **The row replaces “Update the agent first”** on a Whombat with the feature: every case where the agent is too old for `allow` is now the Updates row's (Update the agent, the command, Update now, or soon by itself). Without the feature the old row stays. The install command row is the same (`useUpdateCommand`, `UpdateCommandBlock`), its note “Run it there once; after that the agent updates itself.”. | One way to a newer agent per card (AP-1752's rule); the brief asks to reuse the install-command row. |
| AP-2985 | **Live enough without a frame of its own**: while the agent updates its settings are read every 5 s; a `hosts.server` frame also refetches that server's settings; when the update ends the page and the fleet are read again (the card's head shows the new version). | The hub's `agent.update` bus event isn't a client frame; the end comes with the server's settings. |

Only with `hosts.agent_updates` and the hosts service there. | AU-06 says About → UPDATES; the DEV Whombats that run the hosts service are managed, the fixture world isn't. |

Update now still works on each server.”; stopped (on and halted, an amber dot) “Stopped for now: a new version didn’t work on one of your servers. Try again on that server, or wait for the next version.”. Notes: “Server agents are kept up to date.” / “Server agents no longer update by themselves.”. | AU-03, AU-05, AU-06 in a sentence each. |
| AP-2988 | **Members**: the row isn't shown (it reads `hosts.serverSettings`, owners only, as the rest of the Agent card's switches). | AP-2990 | **The fixture world** (`fixtures-au.ts`, web's `createHostsFixtureLayer`, the phone's demo world): pve-02 kept up to date (updated 3 h ago); blackbox without the key where Whombat may run the last install (Update the agent); pve-01 without the key, its shell blocked on itself (the PX-04 world), so the install command; thetitan with the new version waiting for its updates to be installed (2 minutes, as the updates world installs them), then updating by itself; the-falcon whose update went back (Try again).
