# A backup file to download and restore, on Android (AP-1211…AP-1220)

John, 2026-10-11, asked for a backup you choose the contents of, download, and restore by uploading it again (Whombat
`docs/decisions/backup-file.md` BF-01…; contracts 0.79.0, CT-335). The web and the shared client model are
`backup-file.md` (AP-1181…AP-1210): the hooks `useBackupMaker` and `useBackupRestorer`, `downloadBackupFile` and
`uploadBackupFile` in `@whombat/client`. This is the phone's part: the same two panels (“Download a backup”, “Restore
from a file”, the sketch `mock-dark.png`) on a screen of their own, with what only a phone needs — where the file is
saved, the file to restore, the screen staying on while a file moves. The pure part is `managed/backupFile.ts` (unit
tested); `managed/backupFileSave.ts` binds the native pieces; the screen is `managed/BackupFileScreen.tsx`.

| ID | Decision | Why |
|---|---|---|
| AP-1211 | **This Whombat gets a BACKUP FILE section** right after BACKUPS (the automatic box backups), for burrow owners (`bootstrap.me.role`, not the appliance's `owner`) on a Whombat with `backup.file` (`backupFileAvailable`): one row, “Backup file” over “Download a file of what you choose, or restore from one.”, and **Open**, which opens the new managed-only `BackupFile` stack screen (back bar “‹ This Whombat”), the way DEVICES opens Devices. The screen is restored after a killed process like Devices; one restored after the person stopped being an owner says the contracts' `owners_only` sentence, on a Whombat without the feature “This Whombat can’t make backup files yet.”. | BF-01, BF-12. The two panels are long; This Whombat is long already, and a screen of their own keeps a transfer in front while it runs. |
| AP-1212 | **Download a backup, choosing.** The panel's title (20/700) and intro (14.5, `mut`), then a card of the ten categories in the contracts' order, ticked from the burrow's defaults: each row the whole 56 dp checkbox — a 22 dp rounded tick (`btn` with a check when on, a `line2` outline when off), the label 15.5/600, its size on the right in mono 12 (none for an empty category, as the client says), the meta line 13 `mut` under it (a skeleton line while the estimate loads). Then the password (`FormField`, secret: no autofill, suggestions or autocorrect) with “You need it to restore. Whombat can’t get it back for you.”, the primary **Download · 1.8 MB**, and **Make these the default** (secondary) until it is saved, then “These are the default now.”. Download stays enabled; pressing it with something missing says why — a short password under the field, anything else under the buttons — as on the web (AP-1188). | The sketch's panel at phone width; the web's rule for reasons over greyed-out buttons. |
| AP-1213 | **Making and the ready file.** While it is made: the file card (a `.wbk` mark, the name, “Making the file · Messages · 42 %” and a 6 dp bar) and **Cancel** (`backups.remove` stops it). Ready: “Your file is ready.”, the card with “1.8 MB · expires in 23 hours”, the primary **Download · 1.8 MB** (secondary **Download again** once saved here) and **Remove** (secondary, off while it downloads). A failed download keeps its button and says why under the card, as on the web. Save as doesn't open by itself when the file becomes ready: one tap. | The web's states (AP-1189). A system dialog appearing after a wait — maybe while the person scrolled to Restore — would surprise more than one tap costs. |
| AP-1214 | **Saving: Android's “Save as”, written as it arrives.** Download asks Android's own Save as (`ACTION_CREATE_DOCUMENT`, a new local module `whombat-transfer`, one Kotlin file) with the file's name filled in; the person picks Downloads, a folder or a drive. The bytes go through the shared `downloadBackupFile` (the session's `backup-file` stream, picked up by range after a dropped connection, size and sha256 checked) into `documentSink`: each chunk is written into the document through expo-file-system's file handle on its `content://` URI (opened on the first chunk, truncating), so the file is never held whole; a failed or cancelled download closes and deletes the document, so no half file stays. The document is created as `application/octet-stream` (Android doesn't know the contracts' `application/vnd.whombat.backup`, and a provider would otherwise add its own extension to `.wbk`). The module takes a persistable grant so a recreated activity can still write. Without the module (a build before it) expo-file-system's folder picker and a new file in it do the same. | Not the folder picker first: since Android 11 it can't pick Downloads, and it asks for access to everything in a folder, now and later. Not the share sheet: it needs a whole copy in the cache first (files can be gigabytes) and never says when the receiving app has finished reading it. |
| AP-1215 | **While a file moves** (a download, or an upload to restore): the screen stays on (`FLAG_KEEP_SCREEN_ON` through `whombat-transfer`, cleared when it stops or the screen goes), “Stay on this screen until it’s done.” shows under it, and leaving asks first — “Stop the download?” / “The file isn’t saved yet.”, “Stop the upload?” / “Choose the same file later to go on from where it stopped.”, **Keep going** or **Stop** — because the hooks stop a transfer when the screen goes. | A sleeping phone pauses the app and its connection; a transfer that runs on in the background (a foreground service) isn't needed for a file people make now and then. |
| AP-1216 | **The file to restore** is picked with expo-document-picker, any type (Android has no type for `.wbk`; the client's header check says “This isn’t a Whombat backup file.” before a byte is sent), **not copied to the cache** (`copyToCacheDirectory: false`): the upload reads it by offset through expo-file-system's handle on the document (`fileChunkSource`, one chunk in memory at a time) and closes it when the upload ends. A provider that doesn't say the file's size gets “Whombat can’t tell how big that file is. Save it on this phone first, then choose it again.” (the size is staged before the first byte). An upload that stopped shows as its card (“Uploading stopped at 42 %. Choose the same file to go on.”); choosing the same file (name and size) goes on from there, as on the web. | A copy would double a multi-gigabyte file on the phone before anything happens. |
| AP-1217 | **Restore from a file, the steps**, as the web's (AP-1192…AP-1197): **Choose a file** (primary); uploading — the card with “Uploading…” until the first byte goes (a managed Whombat's upload reads the file first), then “Uploading · 42 %” and the bar, and Cancel; the password — the card with “Uploaded · 1.8 MB”, the field, **Open** (off until something is typed; “That password doesn’t open this file.” under the field), Cancel; the preview — the card with “Made 11 Oct 2026 on Cybex BV · Whombat 0.83”, a card of the file's categories (the same tick rows; chips 12/500 on `sf2` in `ink2`, the “different” one in `warn` with a `warn` outline, as the sketch's amber; the fixed line and notes under), the file's notes, “When something is different” as the settings' segmented control (Keep what’s here, Use the backup) while a ticked category differs, **Restore** (off while nothing is ticked) and Cancel; restoring — the card with “Restoring · Automations · 42 %” and the bar; the end — the card with “Made 11 Oct 2026 on Cybex BV”, “Restored” (or why it stopped, in `bad`) and what came back and needs you, **Open Connections** and **Open Automations** (the phone's Connections, where Needs you comes first, and Automations), and **Done** or **Try again**. | One flow on both clients; the phone's own screens for what needs the person. |
| AP-1218 | **Words.** Every panel word is the contracts' (`BACKUP_COPY`, the meta lines, chips, hints, notes, summary lines, error sentences) or the client's (`BACKUP_FILE_TEXT`); the phone's own few are in `COPY.backupFile` (the section row, the size and save failures, “Stay on this screen until it’s done.”, the leave question). No ids, hashes or paths. | `concise-replies.md`; one wording on web and phone. |
| AP-1219 | **Restores put away on this phone** (Done, Try again) are kept in a small JSON file in the app's documents (`whombat-backup-file.json`, ids only, the newest 20), read once like the registry's (`preloadedStorage`). | The web keeps them in local storage; in memory the last summary would come back after every restart. |
| AP-1220 | **Accessibility and checks.** Each tick row is one TalkBack checkbox named “Agents, 12 KB. 5 agents with their roles, models and keys” or “Memories. 130 new, 12 already here, 3 different”; the file card is one element (its name and line), a progress bar with its value while something moves (no live region, which would read every percent); the download's bar likewise; the password fields are labelled with their hints; panel titles are headers. Targets: rows 56 dp, buttons 44 dp, the segmented control 38 dp with its slop; the touch-target audit lists the screen (2 sites) and the reading-order audit includes it. Unit tests (`backupFile.test.ts`): every step of both panels, the row labels, the leave question, Save as and its fallback, the sink writing a download that drops and resumes into one document and deleting a damaged one, the picked file, the restores put away. `pnpm check` once (DEV fast). The Kotlin module compiled with Gradle (`:whombat-transfer:compileDebugKotlin`) in a throwaway prebuild, and Metro bundled the release JS; nothing was run on a device or the emulator. | DEV is fast; the logic is in the pure model, the native part is small and compiled. |

Open: the screen hasn't been seen on a phone — Save as with Downloads and Drive, writing a large file through a
`content://` handle, picking a file from Drive (a provider that streams rather than gives a file may not let the upload
read by offset), and the keyboard over the password fields want one look on a device before release.
