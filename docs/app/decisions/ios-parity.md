# The iPhone does what the Android app does (2026-10-30)

John, 2026-10-30, after a check that both phones were on 3.22.1: “close the iPhone gap but skip Apple push for now,
we’ll do that tomorrow.” The gaps were passkeys, the hosted UI's links opening the app, sharing into Whombat from other
apps, and the screen staying on while a backup file moves. Pushes to the iPhone (an APNs key for DEV control) come
separately. Phone and hosted-web only: no contract or runtime change.

| # | Decision | Why |
|---|---|---|
| AP-6320 | **Passkeys on iPhone through AuthenticationServices** (`modules/whombat-passkeys/ios`): the same WebAuthn JSON in and out as Android's Credential Manager, so `managed/passkeys.ts` is one `PasskeyPlatform` for both. The RP ID is the hosted UI's host, the origin `https://<host>`, which the Whombat and control already accept as the web's. The app claims `webcredentials:<host>` for each `https` UI without a port and the UI's `apple-app-site-association` grants it. Exclusions need iOS 17.4; a passkey on another device signs in through the QR code iOS offers itself. A dismissed sheet is `cancelled`, an excluded passkey `exists` (iOS 18), an app the RP doesn't vouch for `unsupported`; iOS has no “none on this phone”. | Android has had passkeys since 0.42; on iPhone “Sign in with a passkey” and Set up this device were missing. Apple ties an app to an RP only through associated domains. |
| AP-6321 | **The hosted UI's links open the iPhone app as they open Android's**: Universal Links for each `https` UI (`applinks:<host>`), and `apps/web/public/.well-known/apple-app-site-association` lists exactly the paths Android's App Links list (magic links, the computer's sign-in code, appliance and invitation links, `/claim`, `/connect/…` for a sign-in the phone started, the burrow pages in both forms; a test keeps the two lists equal). The app ID is team `4R8P9MTF9T`'s `com.whombat.mobile`. The development stack's web server serves the file as JSON (appliance harness `web-server.ts`); production's host gets it with its next hosted-web release. | A sign-in email or a QR code read by the camera opened Safari on iPhone. One list for both phones, so a path added to one can't be forgotten on the other. |
| AP-6322 | **Share to Whombat on iPhone**: expo-share-intent's share extension (named “Whombat” in the share sheet through our patch's `iosShareExtensionDisplayName`), for text, a link or a page, and up to ten photos, films or files, Android's limit. It keeps the share in the app group `group.com.whombat.mobile` and opens `whombat://dataUrl=…`, which `startShareCapture` reads and React Navigation's linking and the managed root skip (`isShareUrl`). The share screen is the same; the copies in the group's folder are deleted as Android's cache copies are. Apple signs the extension only once the group is registered on developer.apple.com (Identifiers → App Groups) and ticked on both App IDs (`com.whombat.mobile`, `com.whombat.mobile.share-extension`); no API registers one, and Xcode's automatic signing with the App Store Connect key turned on the capability but couldn't add the group. Until then the iPhone build leaves the extension out (`disableIOS`); the app's side is in place. | Sharing a photo or a page into a Chat was Android only. |
| AP-6323 | **The screen stays on while a backup file moves on iPhone too** (`modules/whombat-transfer/ios`, `isIdleTimerDisabled`); saving there picks a folder (expo-file-system), since iOS has no “Save as” that hands back a place to write (`WhombatTransfer.savesAs()` is Android's). | A phone that went to sleep paused a gigabyte transfer. |
| AP-6324 | **`publish:ios --check`** archives and signs on the Mac and uploads nothing. | A new capability or extension (the app group, associated domains, the share extension) is tried against Apple's signing without spending a version on TestFlight. |
