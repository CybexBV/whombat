# Chat on the phone opens and scrolls quickly (2026-11-02)

John found the phone app laggy on his iPhone Duo. A code read and a simulator survey found: a conversation or thread
drew its oldest rows first and then jumped to the end; every small agent avatar was about 120 native views; a thread
showed grey rows for over half a second after the tap, with no sign the tap landed; and typing, agent activity, a busy
button or the 15-second clock re-rendered the whole list or rebuilt the whole history. This stream (app-polish-b) fixes
those; layout and keyboard, decoding, and the query flow are separate streams.

Checked on an iPhone Duo simulator (iOS 27.1, Release build, fixture world, closed display): opening Chat, a thread and
PR #482's room with an HTML page and a diagram lands at the end with no jump frame by frame (10 and 20 fps recordings);
small avatars are pixel-for-pixel the same picture as before in light and dark (PSNR ≈ 40 dB, the difference being
anti-aliasing); reactions, swipes, iOS's long-press menu, the diagram and “just now” turning into the time all work.
Not checked on Android or on the open (two-page) display.

| # | Decision | Why |
|---|---|---|
| AP-6520 | **A conversation's list opens at its last rows**: `initialScrollIndex` at the eighth row from the end when it mounts (not with a link to a message, which opens at the message), 8 rows first, 4 rows per batch, a window of 7 screens. A thread that first shows only its root from the room (AP-6523) gets a new list when its replies come. The list's own failed scroll to that row is answered by going to the end, not by the anchor's search. | The list drew from its oldest row in batches of 10 with a 21-screen window, each batch moving the list to the end again, so a long conversation drew everything above and jumped. |
| AP-6521 | **One scroll to the end per frame, plus one follow-up** (`jumpToEnd`): the first call in a frame scrolls and schedules one more after the frame; later calls in that frame only update what was seen. | Each content-size change asked for two scrolls to the end. |
| AP-6522 | **Only the reader's drag or fling takes the list away from the end** (`onScrollBeginDrag` until shortly after the fling ends, and the status bar's tap to the top); reaching the end counts however it happens. The phone's counterpart of the web's AP-6451 (thread-scroll.md). | The list also moves by itself as rows take their real size; judging those moves by position stopped it following the end. |
| AP-6523 | **A finger on a Chat row or a replies row starts loading the thread** (`prefetchQuery` with the thread screen's own query; the client's 15-second staleness means a fresh thread isn't asked for again), and **until it is there the thread shows its root** as the room's cached pages have it (`placeholderData`), not grey rows; nothing is marked read or looked for in it until the real answer. **A Chat row shows its press** (the `sel` wash, after 70 ms so a scroll doesn't light it up). | The thread waited for its request after the tap, and the row gave no sign the tap landed (about 570 ms in the survey). |
| AP-6524 | **Agent faces up to 32 dp are one image view**: `expo-image` draws the bundled SVG from a `data:image/svg+xml;base64,…` address made once per file (CoreSVG on iOS, kept as a vector image; AndroidSVG on Android), kept in memory and shared by every avatar of that file. Larger faces stay with react-native-svg (AP-903). The accessible name is on the image. | Each small face was react-native-svg's ~120 native views; a Chat screen has dozens. |
| AP-6525 | **A busy button goes only to its row**: a reaction being sent to the message it is on, a report's decision to the row with that report; `RichText` is memoised on its props. | Every row got the screen's “a reaction is on its way” flag, so one reaction re-rendered every row, and each re-render parsed and laid out the words again. |
| AP-6526 | **Each row's menu, iOS's menu and its swipe are kept per message** (`createRowMenus`, a `WeakMap` by message): built again only when the message, the viewer, the menu options, its thread's settle offer or what answered it changes. A row's thread work is asked once and decides both its replies row and whether it can settle. | Every agent update rebuilt every row's menu and its JSON for iOS. |
| AP-6527 | **The chat's items change with the day, not the clock**: they are rebuilt with the messages and when the day turns (`dayOf`), and carry a message's time as it reads after its first minute plus when it was sent; the row says “just now” (`sentLabel`) and the replies row “Last reply 12 min ago” (`lastReplyText`) from the shared clock through `useNowLabel`, which re-renders only when the words change. Typing and the agents' activity are read by the list's footer (`ChatFooter`), not the screen. | The 15-second clock, each typing refresh and each activity update re-rendered the whole screen and rebuilt the whole history's items. |
| AP-6528 | **A diagram's page is built once**: the Mermaid runtime's `<script>` element is escaped once (`mermaidScriptElement`), the last four pages are kept by source and theme, and every page's last height is kept, so a row drawn again or a page let go comes back at its size. **A preview's WebView is let go after 20 s out of view** (more than two rows from the screen) and started again when it comes near. Supersedes AP-909's “then stays” (android-slim.md). | Each diagram built and escaped a ~4.8 MB page whenever its row was drawn, and every page seen stayed a live browser. |
| AP-6529 | **Looping animations run on the display thread**: the thinking dots are one native timing driving an eased there-and-back interpolation (`pulseRange`); a live run's and task's time re-render each second only while it shows seconds, then once a minute (`nextElapsedTick`). A swipe row's missing side is a constant. | React Native restarts a loop of `Animated.sequence` from JavaScript at every step, so idle dots kept the JavaScript thread busy; a two-hour run card re-rendered every second to say the same; a new `[]` each render made every swipe row hand its sides to the display thread again. |
| AP-6530 | **The list stays a `FlatList`.** FlashList or LegendList only if, after the above, a long conversation still drops frames; measure first: frames dropped while flinging a 200-message room and a 50-reply thread (Perf Monitor / Instruments' Animation Hitches), JS-thread time per batch, rows mounted, and memory after five minutes. | Recycling lists change measurement, anchors, maintained position and the swipe rows; the costs found were in what the rows did, not the list. |

Memory: the survey's ~920 MB after five minutes is the simulator process (shared libraries included), not a phone's.
What this changes for it: a window of 7 screens instead of 21, small faces as shared images, previews let go when away,
diagram pages kept to four. What else holds memory: each live WebView (a browser's worth each), the photos in the image
cache, and the query cache with every conversation opened.
