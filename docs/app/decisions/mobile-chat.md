# Mobile chat: following the end, Return, anchors, copy, dividers, syntax colours, share copies, haptics (MX-01…MX-09)

The improvement review (Whombat `docs/implementation/improvement-review/report.md` §D items 1–4 and 12–15, assignment
§6.1, 2026-10-07): the Android conversation pulled readers to the bottom, sent on Return, opened links at the bottom,
copied nothing, had no day dividers or unread line, showed PR files without colours, kept shared files in its cache and
had no haptics. Stream MC, whombat-app `ir-mchat`. MX-01…MX-08 need no contract change; MX-09 uses contracts 0.55.0.

| # | Decision | Reason |
|---|---|---|
| MX-01 | **The list follows the end only while the reader is there, or after their own send; otherwise a floating “New messages ↓” pill.** One pure rule, `followAction({atEnd, seen, last, anchored})` (`data/chatScroll.ts`), runs on every content and size change: the first messages open at the end; at the end (within 80dp, `isAtEnd`) everything is followed — a message, the thinking row, the list shrinking for the keyboard; further up nothing moves, and only a new *message* (not the thinking row, not an older page) shows the pill. Sending (the composer, a quick reply) jumps to the end first. Reaching the end by hand or tapping the pill hides it. The pill is a 44dp `btn` pill with the toast shadow, `New messages ↓`, centred 12dp above the composer (`ui/jumpPill.tsx`; it floats, so it sits outside the files the TalkBack-order audit keeps free of absolute positioning, and the audit now checks it comes after the list and before the composer in the tree). | `ChatView` scrolled to the end whenever the last item or the typing count changed, so a reply or “is thinking” yanked anyone reading older messages away (report D1). |
| MX-02 | **Return types a new line; the Send button sends.** The composer is `submitBehavior="newline"` without `returnKeyType="send"`. With the `@` list open, Enter still picks its first row (AP-710): a change that is exactly one `\n` typed at the caret (`isEnterAt`, soft or hardware keyboard — React Native doesn't report hardware keys on Android) picks instead of breaking the line. **Drafts are kept per conversation and per thread** (`data/drafts.ts`): sealed in the `SecureBox` with the outbox (same scope, `drafts` entry), saved once typing rests 800 ms, written at once when the conversation closes or the app goes to the background, at most 50 (newest) and none older than 30 days; sending clears it; a wipe (sign-out, another Whombat) takes it with the box, and a store that was left writes nothing more. A draft read from the device after the composer opened comes in only if nothing was typed meanwhile. `OutboxProvider` owns the store (`useDraft`), so no new provider. | Phones type lists, code and paragraphs; Return sending made that impossible, and anything typed was lost on leaving (report D2). Typed text is as private as the outbox, so it gets the same sealed storage. |
| MX-03 | **Links open a conversation at the message.** Routes carry `anchor` (a message id, checked with core's `MessageId`): `routeForLink` gives it for `message` links (top level → the conversation or DM, a reply → its thread; a link to a thread's root opens the thread as before), so mention pushes (`pushTarget` → the inbox item's link), inbox rows and search results land on it; `appScreenUrlForPath` keeps a web path's `#msg_…` fragment as `?anchor=` (and `?thread=root#msg_reply` as the thread at the reply), so notification URLs and tapped web links do too. `ChatView` then loads older pages until the message is there (`anchorStep`, at most `ANCHOR_MAX_PAGES` = 10 pages of 50), scrolls it to 30% from the top and highlights it on `hi` for 2 s (the web's pins jump, a little longer for the screen transition), meanwhile following nothing; a message folded into a run highlights the run. Not found: “That message isn’t here any more, or it’s too far back.” and the end. The screen drops the param once handled, so back and a restored screen don't jump again. A pinned top-level message goes back to the conversation below at the message (`pinnedMessageOpen`, `setParams` on that route), a pinned reply opens its thread at it. Param name `anchor` everywhere, because `Thread.messageId` already names the root. | A mention push opened the conversation at the bottom and pinned messages couldn't scroll to themselves (report D3, essentials Open). |
| MX-04 | **Copy text and Copy link in the long-press menu, Copy on code blocks** (`expo-clipboard` ~57.0.2). Copy text: any message with text (not a tombstone). Copy link: where the message has a web address (not the demo world): `messageLinkPath` — the burrow-less path with `?burrow=` and the `#msg_…` fragment, a reply as `?thread=<root>#<reply>` — on this Whombat's web (`useWebUrl`: the hosted UI's appliance link or the server). The phone opens that same link at the message (MX-03). Code blocks get the web's head: the language (“Code” without one) and **Copy**, which says “Copied” with a check for 2 s. Android 13+ shows its own clipboard preview, so the app's toast (“Copied the text.”, “Copied the link.”, “Copied the code.”) shows only on older Android. | Nothing on a message could be copied (report D4); Android's guidance is not to duplicate its own confirmation. |
| MX-05 | **Day dividers and the “New” line.** `chatItems` marks the first item of each calendar day in the viewer's zone with core's `formatDayDivider` (`Today · Wednesday 7 October`; the web's divider: hairlines in `line`, mono 500 11.5 `mut`; TalkBack reads it as a heading) and the first message by someone else after the read point with the “New” line (a `brand` hairline and `NEW` in mono 600). The read point is the conversation's `lastReadMessageId` at open, taken from a fresh answer only (a cached one could be from before the last visit), and marking read waits for it so the answer can't already say “read up to here”; after marking, the cached detail's `lastReadMessageId` moves too, so the next visit starts there. A read point older than the loaded pages marks the first loaded message by someone else; one that is gone (deleted) marks nothing. The author line shows again under a divider or the line. | No day dividers or unread marker in chat (report D12). |
| MX-06 | **The PR file view colours unchanged lines by language with a pure tokenizer in `@whombat/client`** (`codeTokens.ts`: `codeLanguageOf`, `tokenizeCode`, `tokenizeFileLines`). The web's highlighter is highlight.js inside `apps/web` (not DOM-bound, but not shareable without moving web code and bundling highlight.js grammars into Hermes); a small line lexer is enough for a file view and runs anywhere: C-like languages (JS/TS, Go, Rust, Java/Kotlin/Swift/C#/Dart, C/C++, PHP), Python, Ruby, shell, Dockerfile, SQL, JSON, YAML, TOML/INI, CSS/SCSS, HTML/XML/SVG/Vue, Markdown; block comments, multi-line strings, open tags and fences carry to the next line; lines over 2 000 characters and files past 20 000 lines stay plain. Kinds and colours are the web's (`codeColors.syntax*`). Only the new file's lines are read in order; changed lines stay plain green/red (AP-664). **Deep links:** a web `/pr/482?tab=files&file=<path>` opens `whombat://pr/482/file?path=…&repo=…` (the file screen), `?tab=files` alone `whombat://pr/482/files` (the pull request screen); a path is up to 4 096 characters without control characters, as on the web. | The phone showed every file in one colour and a link to a PR's files opened the branch room (report D13). |
| MX-07 | **Shared files' copies are deleted** once the share is sent or cancelled (the share screen goes), when a newer share replaces one not yet sent (except a file both share — Android copies the same name to the same place), and on the scope guard's wipe (`wipeShares`, sign-out, another Whombat, revocation). Only files directly in the app's cache directory are deleted (`cachedShareFiles`): expo-share-intent copies a `content://` share there; a file another app shared by its own path (a gallery photo) is never touched. Copies left by a killed process stay for Android's cache trimming. | Shared photos and files piled up in the cache: the share screen only forgot them in memory (report D14). |
| MX-08 | **Light haptics** (`expo-haptics` ~57.0.3, `ui/haptics.ts`): sending (composer, quick reply, Share to…) a `virtual-key` tick, approving (approval screen, inbox row, Work row) `confirm`, opening a message's menu `long-press`. On Android through `performAndroidHapticsAsync`, i.e. `View.performHapticFeedback`: the phone's “Touch feedback” setting turns them off. Neither new module needs a config plugin; both are autolinked at prebuild (expo-haptics' manifest adds `VIBRATE`, a normal permission). | The app had no haptics (report D15); system feedback constants respect the person's setting. |
| MX-09 | **Contracts 0.55 on the phone.** *Stop* (CT-295): an agent's thinking line gets a 44dp **Stop** (`TURN_STOP_LABEL`, a bordered text button at the line's end, after the words for TalkBack) when the Whombat has `dispatches.cancel`, the typing event names the turn (`typing.dispatchId`) and core's `canStopTurn` lets the viewer (a person who may wake that agent, or a burrow owner; `offersStop`); it calls `dispatches.cancel` and the line clears from the server's typing event; a refusal (a run's turn: “Pause the run instead.”) shows in the app's alert. *Deploy card* (CT-297): a settled line at once (`cardDisplay` → `line`), `Deployed api to production · 3f9c2a` in ok or `Deploy of api to production failed · 3f9c2a` in bad, opening the card in place: `DEPLOYED`/`FAILED`, `api to production`, the short sha, **Open site** (its URL, when the deployer named one) and **Deploys** (the `work` link with `DEPLOYS_SECTION`, MQ's Deploys segment); with `runId` it shows inside that run's line like a learned skill. *Thumbnails* (CT-298): image tiles show `thumbnailUrl` (HTTP, with the token) or the session download's `preview` variant (managed), falling back to the file when the thumbnail doesn't load; the full-screen viewer shows the file; a preview is cached under its own key. *Thread paging* (CT-299): with `messages.thread_paging` a thread asks for its newest 50 replies (`threadQuery`), and **Load earlier replies** under the root (44dp, `brand`, a chevron) adds the page before `more.before`; each page is its own cached `messages.thread` query, so realtime keeps them current, and `threadMessages` puts them together (each reply once, by time). The thread screen's header reads the same page. An anchor in a thread pages back like the conversation (MX-03). Older Whombats: no Stop, no line for deploys (nothing changes), the file in tiles, every reply. | The improvement review's features 4 and 5 and its thumbnail and thread items, on the owner's primary device. |
| MX-10 | **Stop asks first, on the thinking line and on Work items.** “Stop Banjo?” · “Banjo stops what it’s doing here now. You can ask again.” · Stop (destructive). Work's `stop_turn` (offered by the server on queued and running turns to the people allowed) is wired now: `workCommand` → `dispatches.cancel`, with the same question. | A mis-tap on a phone would throw away an agent's work in progress; one question is cheap, and the Work row already asks before Decline and Take over. |
| MX-11 | **Shared client pieces this needed, kept minimal for the web streams to reuse:** `TypingEntry.dispatchId` (copied from the typing event when present); `cardDisplay('deploy')` = `line`, `nestedRunId` folds a deploy with `runId` into its run, and `deploySettledLine(card)` (the line above, from core's `deployLine` wording); `resourceKey` keys a `preview` download apart from the file. The web renders nothing for a deploy card until WM's WX-12 (its `SettledCardLine` falls back to the full card, which has no deploy case yet), so a deploy folded into a run shows nothing under it there meanwhile. | The thinking line can't stop a turn it can't name; the line and the fold are the card-settle rules (AP-730…AP-732) both apps share; without its own key a thumbnail would be served as the file from the cache (or the other way round). |
