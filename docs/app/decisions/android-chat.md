# Android chat: flat full-width messages, the run card's progress, the `@` list, Take photo (AP-705, AP-706, AP-710, AP-714)

John, 2026-10-04: the Android app becomes the primary device (the Android-primary batch, stream B “chat”). The phone's
conversation still looked like the DM mock — bubbles and cards capped at 84–92% of the width, a run card without its
progress bar or a way to watch it, no `@` list while typing, and no camera under the paperclip — while the web's rows
are flat and full width. No contract change: everything below uses endpoints and features that exist (contracts stay
0.45.1). No version bump in this batch.

| ID | Decision | Why |
|---|---|---|
| AP-706 | **Messages are flat full-width rows, everyone's alike, as on the web.** No bubble background for anyone, the viewer's own messages included: the text in `ink` (mentions and links in `brand`, code on `sf2`) across the list's width, left-aligned, faded to 0.6 while it is being sent. Since nothing tells the viewer's own messages apart any more, the author line (24dp face, name, time) now heads the first of consecutive messages by the same author for the viewer too, and in agent DMs (`DmScreen` passes `authors`; `chatItems` no longer skips `mine`). Everything under a message goes the message's full width: receipts, digest, guide and failed-turn cards, card summaries, the run line, link previews, file rows and the tombstone (`alignSelf: 'stretch'`); quick replies and reaction pills wrap across the whole width; the pinned/edited marks, skill chip and “N replies” sit on the left. Pictures take the full width up to 360dp tall (`imageBox(a, width − 2 × gutter, 360)`; it was min(280, 70%) × 220). The list's side padding is `CHAT_GUTTER` 14dp (was 16), the composer pill's inset, so text lines up with the field. The “is thinking” row and the #general welcome are flat too. Colours only from the theme, so light and dark follow. | The web shows everyone the same, and a phone has no width to spare: an 84% bubble of a 360dp screen left long answers, cards and screenshots cramped, and right-aligned own bubbles made a conversation with agents read like a texting app rather than the workspace the web is. |
| AP-705 | **The phone's run card has the web's progress, Watch run, diff and pull request, and a failed run offers Try again on its line and card.** A run with changes (`runShowsAsLine` false) keeps the compact card (`RUN · LIVE`, title, “Now: …” or the attention line) and adds, as the web's `RunCard`: a 6dp progress bar under the title while live (the run line's bar, extracted as `RunProgressBar`: `sf2` track, `progress` fill of at least 8%, the sheen sweeping every 1.4s; still while it needs a person or with “Remove animations”), a mono line `+214 −12 · 6 files · PR #482` (additions `ok`, deletions `bad`), and the links **Watch run ›** (the Run screen, every state, as the web keeps “Watch run”) and **Branch room ›** when the sidebar has the PR's room (the run screen's lookup). Where the Whombat has `runs.recovery`, a failed run's card has a secondary **Try again** button and its line a **Try again** text button (13.5px 600 `brand`, 44dp, `mut` while in flight) beside the 44dp row that opens the run; both call `runs.retry` (`runLineControls(run, { retry })`, the web's rule), say “Asked Banjo to try again.” as a toast, a refusal's outcome or the error's words in the app's alert; the line goes live again from the run's own `run.updated`. Amends AP-699's “No Try again on the phone yet”. The model is `CardSummary.run` (`RunCardModel`) and `RunLineModel.retry`/`agentName` in `data/messages.ts`, unit-tested. | The run line had progress, the card it turns into didn't: a run that had just changed its first file looked frozen, there was no way to get to the run from the card, and a failed run could only be retried on its page. |
| AP-710 | **Typing `@` at the start of a word opens the `@` list above the composer** (channel messages, DMs and thread replies — they share `ChatView`'s composer). The web's rules (`MentionList`, MS-07, AP-662) in `data/mentions.ts`: agents first, then people, each in the bootstrap's order; matched on the start of the mention name or any word of the full name, any case; never the viewer, someone else's assistant, a system agent, someone who left or a retired agent; in a direct conversation its people only (agents aren't members there; `ChatView` reads the conversation with `useConversation`, the screen's cached query). Rows are 44dp: the face (26dp), the name in 600 and, after it, an agent's role (“Software Developer”) or a person's `@Joris` in `mut`; at most **5** rows (the web shows 8; a phone's keyboard leaves room for five, and typing narrows the list), “Nobody by that name here.” when nothing matches. A tap puts `@Name ` in place of the query (the rest of that word goes) with the caret after it and the keyboard kept up. The first row is highlighted and Enter (the soft keyboard's send key or a hardware keyboard) picks it, as on the web; the Send button always sends. Arrow keys aren't offered: React Native's `TextInput` doesn't report them on Android. The caret comes from `onSelectionChange`; the case correction as you type (AP-607) stays. | The web's composer has had the list since MS-07 and the thread reply box since AP-662; on the phone you had to know and spell a name, with only the case corrected afterwards. |
| AP-714 | *Superseded in part by AP-9376 (chat-inbox-phone.md): the same choices are in the message box's “+”.* **The paperclip opens an Attach sheet with Take photo, Photo from gallery and File.** The two-button alert became a bottom sheet in the message menu's style (52dp rows with an icon), since Android's alert takes at most three buttons and Cancel is the backdrop now. **Take photo** asks for the camera on first use (`requestCameraPermissionsAsync`); refused, it says “Camera is off for Whombat” and, when Android won't ask again, offers Open settings. It opens the system camera app (`launchCameraAsync`: images only, no EXIF, quality 0.85) and the photo goes up through the composer's upload path like a picked one (`fromImageAsset`, `useComposerUploads`). Both builds now declare the camera permission (`expo-image-picker`'s `cameraPermission`; the legacy build had none), with one text for the picker and the QR scanner: “Whombat uses the camera to take a photo you attach to a message, and to scan QR codes: …”. | Taking a photo of a screen, a whiteboard or a receipt to show an agent is the phone's most natural attachment, and it took a detour through the camera app and the gallery. |
