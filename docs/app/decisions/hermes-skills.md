# Hermes's skills only: Settings → Skills and Add skills on Hermes's hub (AP-5520…AP-5599)

From 2026-10-24 the agent's skills are Hermes Agent's (Whombat `docs/decisions/hermes-skills.md` HSK-01…HSK-16):
Hermes's built-in skills, what owners install from Hermes's hub (Hermes's optional skills, its trusted GitHub
repositories, skills.sh), what the agent learns with each person and the learned skills owners share. Whombat's own
skills, the archive upload and add-from-link are gone. Settings → Skills is its own tab again, after Agent. Contracts
2.0.0 (CT-1400…CT-1449, session major 3); whombat-app 2.0.0. Numbers: client AP-5520…AP-5529, web AP-5530…AP-5569,
phone AP-5570…AP-5599. Supersedes, for skills: hermes-engine-app.md AP-5200, AP-5201's chips and status words,
AP-5202's “Restore Whombat's”, AP-5204's world, AP-5205, AP-5230's chips and AP-5234; one-agent.md AP-4922's and
AP-4947's Skills in Settings → Agent; all-skills.md's Add skills (AP-2313, AP-2314, AP-2368).

## For the runtime and the contracts

- A shared skill's row can't name who shared it (`SkillLibraryItem` has no sharer), so it says “Learned and shared”
  where the old list said “Shared by Mara”. A `sharedBy` would let it.
- A hub search result doesn't say its name is taken here (only the preview's `nameTaken`), so the list can't mark it
  before it is opened.
- A refused export read should carry the application code in `details.code` (CT-21), as the fake session does; the
  client maps it back to the op's error (AP-5521).
- The library's `hub.updateAvailable` should reflect the last update check, so `can.update` is right once the client
  re-reads it after `skills.hubUpdates` (AP-5523).
