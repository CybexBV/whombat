# The passkey as the key to the backups in the apps (AP-6865…AP-6879)

John, 2026-11-04 (Whombat [backup-passkey.md](../../decisions/backup-passkey.md) BPK-01…BPK-10): every passkey touch
gives the Whombat its backup key. These are the apps' wiring for it; the screens (Backups, Bring back, the paper copy
under details) are the ui stream's. The shared logic is `@whombat/client/managed` (`passkey-backup-key.ts`:
`withBackupPrf`, `prfOutputOf`, `withoutPrfResults`, `backupKeyInput`, `holdBackupKey`, `deliverBackupKey`;
`kit-passkey.ts`: `armBackupKey`, `tapPasskeyForBackups`, `kitsToBringBackFrom`, `kitsFromNetwork`, `paperCopyText`,
`confirmPaperCopy`).

| ID | Decision | Why |
|---|---|---|
| AP-6865 | **The shared sign-in and registration ask for PRF** (`extensions.prf.eval.first` = `KIT_PRF_SALT_V2`, base64url) and read the output from the platform's answer; `canonicalAssertion` and `canonicalRegistration` drop `prf.results` from every JSON that goes to control or the Whombat. A passkey sign-in that opened a Whombat holds its key in memory (`holdBackupKey`, by device code); adding a passkey sets it at once when creation answered PRF (`backups: 'armed'`), else says the next touch will (`touch`) or that the passkey can't (`unsupported`). | One touch, and the PRF output — the secret behind every backup key — never leaves the device. |
| AP-6866 | **The web turns the PRF inputs into bytes itself** after the browser's own JSON parser (which not every browser applies to extensions) and writes the outputs into the answer's JSON as base64url, as the phones do, for the shared code to read and drop. `webPrf` also says the passkey's user handle. | The same shared code on every platform. |
| AP-6867 | **A sign-in's key reaches the Whombat once its app is open**: the web's `PasskeyNotices` (`BackupKeyDelivery`, also on Settings) and the phone's `ApplianceRoot` when its session opens call `deliverBackupKey`, once; a refusal (an older Whombat, no backup service) is quiet. | A sign-in has no app session yet; the key never touches storage. |
| AP-6868 | **The Inbox's “Use my passkey”** (`BACKUP_PASSKEY_HREF`, `isBackupPasskeyHref`) runs `tapPasskeyForBackups` where it is tapped — on the web in the click (a browser shows a passkey prompt only for a tap), on the phone in either of the sheet's button paths — and shows what it says: armed; a passkey added (that touch arms it where the platform allows, else “once more”); this passkey can't. An app that doesn't know the link opens This Whombat's backups. A passkey whose user handle names another Whombat (one this was brought back from) isn't used: a new one is added. | One tap from the ask to done. |
| AP-6869 | Superseded in part by backup-v2.md AP-6908 (the iPhone’s registration asks for PRF). **Platforms.** Web: WebAuthn's `prf` on get and create where the browser and the passkey's manager offer it (otherwise no output, and nothing is armed). Android: Credential Manager passes the JSON, `extensions.prf` included, on get and create, and the provider answers `clientExtensionResults.prf`. iPhone: AuthenticationServices answers PRF on get from iOS 18 (`whombat-passkeys` since AP-6855); its registration doesn't pass `prf` yet, so a passkey added on an iPhone arms on the next touch. | What each platform does today; the iPhone's registration PRF is a Swift change to build and test on the Mac. |
| AP-6870 | Superseded by backup-v2.md AP-6900 (Look on my network, when the person asks). **Bring back on the web** shows the account's envelopes at once and, when there are none, looks on the network meanwhile (`kitsFromNetwork`, up to two and a half minutes): what it finds is offered, and the choice moves to bring back while the person hadn't chosen. | A brand-new Whombat must not wait for a scan before it asks anything. |
