# Mobile parity screens (MQ-01…MQ-12)

Improvement review 2026-10-07, stream MQ (report feature 1 and D9–D11): what the web had and the phone didn't — an
agent's computer, schedules, notes and always-allowed commands, Spend, the audit log, hiring with a provider and packs,
channel and people administration — and, on contracts 0.55.0, a canvas to read and Work · Deploys. Everything uses
endpoints the contracts already have; nothing here changes a contract. Not mocked: the screens are built in the phone's
list language (grouped 20dp cards, mono section labels, 44dp buttons) with the web's words.

| # | Decision | Reason |
|---|---|---|
| MQ-01 | **The agent screen manages what the web's agent settings do.** COMPUTER is a section of its own after RIGHT NOW (it replaces the “Computer · Running” line): the state with its dot and “Working for you now”, or why it failed / “set up the first time it needs one”; SIZE, IMAGE, LAST USED; Start, Stop and **Reset…** (an alert with core's `resetTitle`/`resetBody`/`resetConfirm`) for whoever may manage the agent (`canManageAgent`), else the web's “Only owners and the person who hired … / Only Mara starts, stops or resets it.”; with `agents.risk_rows` PUBLISHED PORTS (each port's line, its address with **Open**, and **Stop** — the assignment's “Unpublish” is the web's verbatim “Stop”) and KEPT AWAKE with **Let it sleep**. While the computer is being set up it is read again every 2 s, as on the web. **SCHEDULES** is a row (“2 active · 1 paused”) opening the agent's Schedules screen: what, when and its state, NEXT / ENDS / RUNS / FOR, **Pause**, **Resume**, **Remove** (asks first, core's sentence split as the web splits it) by each schedule's `canChange`. MEMORY gets **Notes** (“3 notes”): the Notes screen with the usage line, who wrote each note last and when, and — `canEdit` — **Edit** in a sheet (the web's count, Save/Cancel; only a changed, non-empty text is sent) and **Remove** at once, as on the web. KEYS gets **Always-allowed commands** (“1 command”, where computers run): each command in full mono, its target and key, **Remove** at once for managers. The three rows show where the web shows those settings tabs (`configuresAgent`: no system or retired agent, someone else's assistant never; `agents.schedules`, `agents.memory`, computers available). Deep links `whombat://agents/<agent>/schedules\|notes\|commands`; the web's `/agents/<agent>/settings?tab=schedules\|notes` open them, `?tab=spend` opens Spend. | The report's first feature: agents wake themselves on schedules and run computers, and the only off switch was the web. The computer is one item with a few buttons, so it sits on the screen; lists that grow (up to 20 schedules, notes, allowances) get their own screens behind a row that already says how many. |
| MQ-02 | **Spend on the phone.** The agent's spend line is now a 44dp link (“This week: … ›”) to a Spend screen with that agent's week on top (the web's agent settings → Spend: THIS WEEK [· YOURS], the summary, Turns / Tokens in / Tokens out / Cost, its notes), then the web's Settings → AI → Spend: the intro and the estimate note, the three tiles (Today, 7 days, 30 days), the footnote, **Today · 7 days · 30 days** switching BY AGENT and BY PERSON (the web's tables are 30 days; the phone has no room for three columns per window), HANDOFF BUDGETS and TOP PLANS. A table row is the face, the name and role (an assistant as “Mara’s assistant”) and one mono line “42 turns · 2.8M tokens · $11.66” (— when no cost was reported); an agent's row opens the agent, a plan opens the plan. A member sees their own spend without BY PERSON, as on the web. Also in the settings sheet's AI group (SPEND · Spend). Read again on open and pull, nothing live. | Same numbers and words as the web; the window switch is the phone's answer to a table that doesn't fit. |
| MQ-03 | **The audit log on the phone.** Its filters are route params (`?actor=&kind=&who=&open=`, checked by `auditFilters`; a change sets the others back to undefined because `setParams` merges): Everyone / People / Agents, the kind chips with their counts in a sideways row (Vault once the log has one, AP-117), “Only Banjo ×”. Events grouped by day (core's `groupAuditByDay`), each row the time, face, name, tag, status, text, meta and pill; tapping opens the signed detail (core's `auditFields`: SIGNED BY … EVENT “e-9f18 · signature verified”, red when it doesn't verify) and the button to what it was about (`auditLinkLabel`, opened with `useOpenLink`). Load more pages back. A link's `open` event starts opened (receipts, notifications). Reached from the settings sheet's This Whombat (AUDIT LOG, as the web's SS-21), from `log` links (`routeForLink`, which opened the browser before), `/log` web paths in either form and the Android app link `/log`. **Export CSV stays on the web**: the phone has no file download, and a CSV is a desk task. | The log is where a person checks what an agent did with its keys; a receipt on the phone shouldn't send them to a signed-out browser. |
| MQ-04 | **Hiring picks the AI provider and the packs, as the web.** On a live Whombat, AI PROVIDER lists Claude Code and Codex with their state (“Ready · claude 2.1.3”, “Not installed”); only a ready one can be picked, the Whombat's default first (`hireDefaultProvider`), and the web's line says the picked one's state or where to set it up (`providerHint` without the ACP branch: hiring never offers ACP). **No model picker**: the web hires with the provider only, and the contracts have no list of models (`HireBody.runtime.model` exists, but nothing says which models a provider offers); the provider's default model it is. SKILLS is a switch per pack of the role (title · skill names, “2 skills”), ticked up to `hirePacksMax` while untouched and then as left (`editHirePacks`, `switchHirePack`); a pack only an owner adds is locked “an owner adds it” and said after the hire, never sent; past the limit “Up to 16 packs”. Another role starts its packs over (AP-629). | The phone hired with the default provider and every pack; a person who wants Codex or fewer skills had to fix it afterwards on the web. |
| MQ-05 | **A canvas reads on the phone.** `canvases.content` (contracts 0.55, CT-303) gives the canvas and its Markdown; the screen shows CANVAS, the title, “Started by Toffee · updated 2 h ago” and the text with the message renderer (`MessageBody`: headings, lists, tables, code, images, diagrams' source), then “Read-only on the phone. Edit it on the web.” and **Open on the web**. Canvas links (`routeForLink` → `Canvas`) open it where the runtime has `canvases.content`; elsewhere `useOpenLink` opens the web page straight in the browser (through `Linking`, since `useOpenUrl` would turn a Whombat link back into the canvas screen). `/canvases/<slug>` in either form opens it too; the canvas list stays on the web. `/canvases` is **not** an Android app link: the web fallback must reach the browser. A canvas that is gone (404/403) says so without Try again. | Reading the plan an agent wrote is a phone task; editing a collaborative document isn't. |
| MQ-06 | **Channels and people are administered on the phone.** CHANNELS gets **Create a channel** (the web's sidebar `+`): NAME as typed (lowercase, dashes; `typedChannelName`/`finalChannelName` copied from the web), TOPIC, **Private channel** with the web's line (with `channels.browse`), and the people and working agents to bring in (a picker without the direct conversation's cap of eight); “Create channel” opens it. The conversation menu (the header's “More”) gets the web's channel menu: **Members**, **Channel settings** (members of a live channel), **Archive channel** (asks with the web's text) / **Unarchive channel** (owners and its creator, never #general, `canArchiveChannel`), **Leave channel** (never #general; a private one asks first) — a branch room and a direct conversation get Members only. Channel settings: name, topic and, for owners, private (never #general); only what changed is sent; a 403 says “Only members of this channel can change it.”. Members: people then agents with what they are; in a channel or branch room **Add people** (the picker), **Remove** at once and **Leave** on your row; a direct conversation's and an archived channel's members say why they don't change. The settings sheet shows **Members** (the web's Settings → Members): invite by email (on a managed Whombat the owners' invite card from Devices, which also invites to the organization and shares the one-time link), each person's role, and with `members.manage` a sheet with Make owner / Make member / Remove from burrow… / Leave burrow… (removing and leaving ask with the web's text; the last owner is told to make someone else an owner first); pending invites with **Share invite link** (the web's “Copy invite link”: the share sheet copies too, and this branch has no clipboard module) and Remove; FORMER MEMBERS. **Clear all messages** stays on the web (not in MQ-06, and irreversible). | Report D10: administration was web-only (AP-515 left the phone at Browse/Join). |
| MQ-07 | **Work · Deploys.** Where the runtime records deploys (`deployments`), Work has **Work · Deploys** under its title. Deploys shows ENVIRONMENTS — a section per environment (“PRODUCTION · 2 h ago”), a row per service with the deploy live now (“DEPLOYED Banjo · 2 h ago · GitHub Actions · 7be20f”), a newer attempt that failed (LAST ATTEMPT FAILED …) and the one before (BEFORE …, where a rollback goes) — and HISTORY, newest first (`deployLine`, the pill, who · when · how · commit). A deploy opens a sheet: its facts, its summary (everyone in the burrow reads it), **Open the deployed site**, **Open where it was posted** (only for members of that conversation, as the server fills it). History grows by 30 up to the endpoint's 200 by raising `limit` (one query, so a refetch stays whole). Live: the shared client's `deployment.recorded` handler reads both again (kept as vendored with 0.55). A `deploys` work link, `/work/deploys` and `whombat://work?section=deploys` open on the segment, also on a Work already open. Words not in the mocks or core are ours (`DEPLOYS_TEXT`). | Feature 5 on the phone: “what is live where” is the question asked away from a desk. |
| MQ-08 | **Small shared parts.** `ui/facts.tsx` (mono-labelled facts, a note inside a card, a row of buttons), `screens/PeoplePicker.tsx` (64dp checkbox rows with presence), `screens/useChannelActions.ts` (the web's `useConversationActions`: call, read again what shows it, say it in a note or the server's words) and `useAgentName` (a screen opened by handle names the agent). | The new screens share them; nothing existing changed shape. |
| MQ-09 | **The demo world has the parity data** (`fixtures/parity.ts`): Dusty's two schedules (active, paused) and two notes, Banjo's always-allowed staging deploy, its published dev server and keep-awake, and the writes that change them (pause/resume/remove, edit/remove, remove, start/stop/reset/unpublish/sleep). Channel and member writes are **not** faked: `@whombat/fixtures` doesn't implement them, and the screens show the server's refusal (“That isn’t available on this Whombat yet.”). | The emulator pass and the demo should show the new agent sections with something in them. |
| MQ-10 | **Words that aren't the web's.** The rows' summaries (“2 active · 1 paused”, “3 notes”, “1 command”, “None”), the port address's **Open**, “That isn’t an email address.” under the invite field (the web only reddens it; the phone says it for TalkBack), the Spend rows' one-line numbers, the canvas and Deploys texts. Everything else is the web's or core's, verbatim. | Not mocked; kept to the fewest new sentences. |
| MQ-11 | **Leaving the burrow from the phone** reads the session and the bootstrap again and goes to the Inbox; what opens next is the app's session handling (another burrow, or the sign-in path), as on the web, which goes home. | The phone has no “home”; the session layer already decides what a person without this burrow sees. |
| MQ-12 | **The web's pure models are copied, not moved** (`data/spend.ts`, `data/members.ts`, `data/channelAdmin.ts`, `data/schedules.ts`, `data/computer.ts`'s `COMPUTER_TEXT`): `packages/client` is edited by the web streams in this same build (WA, WM). Moving them there is a follow-up once the streams are merged. Hooks the client lacks (`canvases.content`, `deployments.*`) are `queryHook`s next to their screens for the same reason. | No conflicts in shared files during a parallel build; one place to change them later. |
| MQ-13 | **A canvas reads as text on the phone** (lead, emulator pass 2026-10-07): `canvasReadingMarkdown` drops a plan block's `:::plan{…}` / `:::` fences (the step listing between them stays) and shows `==highlights==` / `==text=={author=…}` as their words, outside fenced code, before the message renderer gets the canvas Markdown. Spend on the phone says “tasks” like the web (WE-16), including the agent's week, its facts and “This week: no tasks” (the contract's `spendLine` still says “turns” for an empty week; the app answers that case itself). | The emulator showed the raw dialect (`:::plan{id=pln_invoice-pdf}`, `==…=={author=prn_pippa}`) and “turns” on the phone's Spend. |

  three agent rows and their screens in the demo world (Dusty, Banjo); Spend from the spend line and the AI group; the
  audit log from This Whombat and from a receipt (row expansion, the detail's button); hiring with AI PROVIDER (a live

  canvas link from a message and its tables/code; Work · Deploys and a deploy's sheet; TalkBack on the new rows.

  conversation's “New conversation with more people” (the New message screen takes no starting people), the agent's
  Profile, Model & provider (beyond RUNS ON), Danger zone (beyond Retire) and Access → keys detail beyond the existing
  Keys and channels screen, email and thread notification preferences, Repositories, feedback reports, burrow usage,
  the automation editor, the canvas list and canvas editing, creating schedules (agents create them).
- `data/spend.ts`, `data/members.ts`, `data/channelAdmin.ts`, `data/schedules.ts` duplicate the web's models (MQ-12).
