# Connection pages open fast (AP-2650…AP-2679)

John, 2026-10-19: “make connection pages open fast”. A connection's or device's page (`/things/connection:con_…`,
`/things/device:…`) is built by the server (`things.page`); until it answered, the web drew only grey skeletons and the
phone `SkeletonRows`. The server is made faster beside this (it answers within about a second, from the last reading
when a fresh one is slow, with `refreshS: 5` while it still reads the service); this is the clients' half. No contract
change. Ranges: AP-2650…AP-2659 the page's head while it is read (web and phone), AP-2660…AP-2669 reading it on hover
(web only: the phone has no hover).

## The head while the page is read

| ID | Decision | Why |
|---|---|---|
| AP-2650 | **Until `things.page` answers the first time, the page's head is drawn from a row the app already holds**: on the web the crumb back to Connections, the kind's icon or mark on its tint, the name and the status badge, with the same `PageHead` the loaded page uses (`headLook` gives both the crumb, icon, mark and tint); on the phone the glyph or mark, the name, the status dot and its words (`HeadTop`, shared with the loaded head). Only what is below the head stays skeletons. Errors, the 404 “Not found”, the tabs, the range picker and `keepPreviousData` are unchanged. | The person sees at once that the right page is opening; the head is where the eye goes. Drawn with the page's own pieces, nothing moves when the page comes: checked in the fixture world at 1440×900, light and dark — the crumb's, icon's, name's, badge's and head row's boxes are the same before and after, and the head's pixels (Home Assistant) are identical. |
| AP-2651 | **Where the row comes from** (`cachedThingHead`, `@whombat/client/react`): Home's things (`home.overview`, which the web's sidebar and Connections and the phone's tab bar and Connections tab read) by the thingId, else `connections.list` (Settings → Connections, an agent's LOOKS AFTER) for a `connection:` thingId, named as the page names it (the label without the host it ends with, the server's `displayName`) with its catalog entry as icon. Read with `getQueriesData` — no request, no subscription — once as the page opens (`useCachedThingHead`, per thing). Nothing cached (a link opened before anything else): as before, skeletons only. | The rows are there already: on the web the sidebar reads Home on every screen of the assistant shell; on the phone the tab bar does. A device's head isn't taken from `connections.list`: its page's icon is the device's, not the catalog entry's. Read once: the page answers within about a second anyway, and a cache subscription would run on every cache event. |
| AP-2652 | **The badge says the status in the sidebar's words** (`THING_STATUS_LABELS`: Running fine, Needs a look, Problem, Learning, Offline, Not checked yet), toned as the page tones it (`thingBadgeTone`). A page with words of its own (Hetzner's “All running”, “Needs to be connected again”) changes them in place when it comes. A row that doesn't say how it is (`connections.list`) draws no badge until then. **No buttons before the page**: Ask, Restart and Open come with it, together. | The summary has no badge words; the status's are what the sidebar's tooltip already says, and only the words can change, never the place. Ask first in the right-aligned button row would move left as Restart and Open join it. |
| AP-2653 | **On the phone the head reads the same** (`headSpoken`): “Home Assistant, Needs a look”, the name alone while no status is known. The nav title stays the fallback name when nothing is cached. Both clients still read again every `refreshS` (5 s while the server still reads the service, else 60) — unchanged, no polling of their own. | TalkBack users get the same early head. |

## Reading the page on hover (web)

| ID | Decision | Why |
|---|---|---|
| AP-2660 | **A link to a connection's or device's page reads it while the pointer rests on it, or the keyboard's focus reaches it** (`useThingLinkProps(burrow)` in `features/things/prefetch.ts`, spread on the link: `{...linkProps(href)}`): the sidebar's rows (a server's reads nothing, AP-2664), Connections' service cards, Settings → Connections' rows, an agent's LOOKS AFTER, a chat's subject pill, a server's “Also connected” and Watch's titles. | Opening the page then draws it from the cache: no skeletons at all. One helper; every site that links to a thing page uses it. |
| AP-2661 | **It waits 100 ms** (`PREFETCH_DELAY_MS`) before reading, and leaving the link stops the wait; one wait per list (a new link's replaces it). Keyboard focus waits the same; focus from a click or a tap (not `:focus-visible`) and a touch's pointer (`pointerType` `touch`, which also covers the hover a touch screen emulates) start none. | A mouse sweeping over the sidebar, or Tab run through it, reads nothing; a person resting on a row means it. A tap opens the page at once anyway. |
| AP-2662 | **A copy younger than 20 s (`PAGE_FRESH_MS`) isn't read again** (`prefetchQuery` with that `staleTime`); a read in flight is joined. No retry; a refusal stays quiet and the page, opened, reads again and shows its own error. | Resting on the same row twice asks once; the server isn't asked for nothing. |
| AP-2663 | **The page reads with the same key and the same freshness**: `thingPageInput(burrow, thing, range)` builds both reads (the range only when one is asked, so a hover's read is the default range's), and the page's query takes `staleTime: 20 s`. | Opening the page after a hover reuses that read instead of asking again as it mounts; checked in the fixture world: a sweep then a rest reads one page, a second rest none, opening it shows no skeleton and reads nothing more. `refetchInterval` still follows `refreshS`. |
| AP-2664 | **Only a connection's or a device's page at the default range** (`prefetchedThing`): a server's page (`/things/server:…`) is built from the hosts service and not read here, a link with `?range=` (a different read) isn't read, `?tab=` is (the same read). Nothing on a Whombat without `things.pages`, whose links open Settings. | What would be read must be exactly what opens. |
