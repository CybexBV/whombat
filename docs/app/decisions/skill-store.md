# Skills without packs: client and web (2026-10-21)

John, 2026-10-21 (main checkout): “I would like to move to a skill system similarly like Hermes Agent and remove packs.”,
then “Yes, implement this fully.” Product decisions: Whombat `docs/decisions/skill-store.md` (SST-01…SST-17); contracts
0.113.0 (CT-800…CT-839); assignment: Whombat `docs/implementation/skill-store/assignment.md`. The client and the web are
AP-4100…AP-4149 (stream W); the phone is AP-4150…AP-4199 (stream M). The Settings → Skills mockup
(`docs/design-handoff/all-skills/settings-skills.html`) still draws the tab: only what a row says changes.

## The shared client (`@whombat/client/skill-library`)

| # | Decision | Why |
|---|---|---|
| AP-4100 | **The library on contracts 0.113.0** (CT-819…CT-822). The client re-exports core's shapes under its names (`SkillLibraryItem`, `SkillLibrarySkill`, `SkillLibraryVersion`, `SkillChange`, `SkillOrigin`, `SkillOriginalRef` = core's `SkillPackRef`); `SkillSource` and `SkillPackRef` go. A skill is its **name** (SST-02): every request names `agentId` and `name`, never `pack` (that is for older phones, CT-822); someone else's import it could add is `name` plus `from` (its `addedBy.id`). `skillRowKey(item)` is a row's identity in a list: the name, or `<their id>/<name>` for someone else's import, which may share a name with the agent's own. A write's answer replaces the agent's row of that name in its cached library (an Add also the import it came from), a reset that leaves nothing drops it, a switch flips at once and goes back if refused. | One skill per name per agent; the legacy fields are the server's to fill for phones that still read them. |
| AP-4101 | **The model** (`skillLibraryView`, `skillPanel`, shared with the phone). Groups are the server's `group` (SST-03): “Learned by {name}” (`origin: 'learned'`), then each import group (“From Hermes · smart-home”), then the shipped categories by title. No `replaced` rows: a row a runtime before 0.113 still says was beaten isn't drawn. Status words: a shipped skill someone changed reads **“Changed today”** (“Changed on 3 Oct”), with **“· original changed”** in `warn` when Whombat's moved on since (SST-05); an imported or learned skill of a shipped name reads **“Replaces Whombat’s”**; the rest as before (“Ready · Used 4 times”, the server's `missing`, “Resting · last used …”, “Off”, “Added by Theo”). The open skill: its tag is its group, with “ · Changed” for a changed shipped skill; its lines add “Replaces the one that came with Whombat” for an import or learned skill in a shipped skill's place; “The original changed since this version was made.” shows with Compare when the original is there; `resetKind` is `original` (Reset to original: a changed shipped skill, or an import or learned skill of a shipped name), `remove` (an import or learned skill of a name Whombat doesn't ship: the reset removes it, CT-821) or null; `editMakesCopy` for a shipped skill not changed yet. Changes are counted from the versions: all of a changed shipped skill's, any other's but the first (how it came); an unchanged shipped skill has none. The Chips stay (Learned is `origin: 'learned'`), and the preview's clash words are “Replaces the one that came with Whombat”, “Replaces an earlier import”, “{name}’s own stays in use”; an archive made as a pack reads “a Whombat archive”. | The rows say what John already knows from Hermes: the skill is his once changed, and Whombat's comes back with one click. |
| AP-4102 | **Archives go through `skills.stage`** (CT-817): `importSkillArchive` hashes, stages (`skills.stage {burrow, fileName, size, sha256}`), uploads through the `skill-archive` stream and previews `{stagedArchiveId, agentId}`; `SkillStagingUnsupportedError` when a runtime answers `unknown_op`. The module is `session/skillArchive.ts`; there is no fallback to `packs.stage`, which went (the web ships with its runtime, SST-16). The world to look at (`createSkillLibraryWorld`) answers by name as the server does: one row per name, a shipped catalog for originals, Add as the agent's own copy, Edit of a shipped skill making a changed copy, Reset back to Whombat's or removing, Undo as a new version (`skv_` ids), `{added, categories}` for an import; `seeds` give another agent's library. | Contracts 0.113.0 renamed the op and the upload target; the phone and the web's tests read the same world. |

## Removed with the packs (SST-09, SST-17)

| # | Decision | Why |
|---|---|---|
| AP-4103 | **Hiring and onboarding bring no packs.** The hire modal's details have no SKILLS group of role packs, onboarding's “Meet your first agents” no “Skills for {name}” rows; neither request sends `packs`, and a hire always toasts “{name} joined the burrow. Say hi in a DM.”. The client's `hirePacks`, `editHirePacks`, `HirePackPicks` and `hirePacksMax` go. | Every agent has every shipped skill (SST-10); there is nothing to pick. |
| AP-4104 | **No Skills page of before the library.** `/skills` always redirects to Settings → Skills (anchor kept, entry replaced), and so does `?tab=packs`; Settings always has the Skills tab. `oldSkillsPageOf` / `useOldSkillsPage`, the assistant sidebar's Skills row (`skillsPage`) and its `skills` location go, and the sidebar no longer reads `packs.list`. | The page was the packs screen for a Whombat without the library (before 0.92); packs are gone (SST-09). |
| AP-4105 | **Settings → Skills in the crew shell is an agent's library too** (SST-10): “SKILLS OF” with a select of the agents the viewer configures — their own assistant first, every team agent for an owner — over that agent's `SkillsLibraryTab`. | AP-4106 | **An agent's settings page → Skills is its library** (`/agents/$agent/settings?tab=skills`, SST-10): the same `SkillsLibraryTab` as Settings, for that agent, so the assistant's “More settings” and a team agent land on the same screen. The tab shows where the Whombat has `skills.library` (was `packs`); nothing on it waits for Save, every change applies at once. | AP-4107 | **`features/packs` is gone.** What skills still need moved to `features/skills`: “Learn this” (`LearnSkill`, `learnPlace`), the proposal's decision and details (`SkillProposal`, `DecisionButtons`), the scan's tag and findings (`ScanParts`), “Let {Agent} propose skills” (`SkillProposalsToggle`), `useSkillAgents` and their words (`skillsCopy`, pack words left out), with their styles in `Proposals.module.css`. `InstalledPacks`, `ShippedPacks`, `PackModal`, `RolePackRows`, `AgentPacks`, `SkillRows`, `SkillNames`, `ProposedSkills`, `ProposeSkills`, `SkillsScreen`, `assistantCatalog`, the role-pack hooks and `PACKS_TEXT` go with their tests. | AP-4108 | **The composer's `/` reads each agent's library.** `useAgentsSkills(burrow, agentIds)` asks `skills.library` per agent (the same cache as Settings → Skills) and `enabledSkillsOf(library)` offers its own rows that are ready or need setup, in the library's order, each name once: someone else's import not added, a skill switched off, resting or hidden isn't offered. `EnabledSkill` is `{name, description, missing}`. | `packs.agent` goes with the packs; the library is what the agent has. |
| AP-4109 | **The client loses the pack calls**: `usePacks`, `usePackInspect`, `usePackDiff`, `useAgentPacks`, `useSkillUses`, `usePackWrite`, `usePackExport`, `importPackArchive`, `importBundledPack`, `exportPackArchive`, `usePreviewSkillLink`, `useAddSkillLink`; strict decoding no longer lists `packs.*` (there are no pack tool approvals to hide). A decided proposal and a removed learned skill read the library again instead of the packs. | Nothing calls them (SST-09); no dead code. |
