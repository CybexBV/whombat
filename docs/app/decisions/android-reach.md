# Android reach: links, sharing, voice, offline, editing on the phone (AP-709, AP-715…AP-718)

John, 2026-10-04: the Android app becomes the primary device. Stream D of the Android batch makes the phone reachable
from everywhere else on the phone (links, the share sheet, notifications), usable without a connection, and able to
change what so far only the web could. No contract change: everything uses endpoints contracts 0.45.1 already has.

| ID | Decision | Why |
|---|---|---|
| AP-709 | **A tapped link opens the app's screen, else the browser.** `urlTarget(href, origins)` (`navigation/routes.ts`) decides: a link to the web app — the build's hosted UI (`EXPO_PUBLIC_WHOMBAT_UI_URL`) or Whombat's own, `https://app.whombat.com` and `https://dev.whombat.com` (`appOrigins`) — in either path form (burrow-less `/c/general`, the old `/<burrow>/runs/12`), a bare `/c/general`, and a `whombat://` link open the screen `appScreenUrlForPath` names (conversation, DM, direct conversation, branch room, thread `?thread=`, plan `?plan=&step=`, approval `?approval=`, run, automation run, agent, Work, search, automations — `/automations/<id>` opens the list — and now the Vault, `/vault`); a page the phone has no screen for (settings, canvases, the audit log) and every other `http(s)`, `mailto:` or `tel:` link opens in the system's app; hosted-UI sign-in, claim, invitation and appliance links go to the system too, which hands them back to the managed root that already handles them. Any other scheme (`intent:`, `javascript:`, `file:`, `//host`) opens nothing, and a `whombat://push?…` in a message means nothing; a notification's `whombat://open?…` opens its screen without marking anything read. `useOpenUrl()` (`navigation/hooks.ts`) does it from message text (`RichText`), link previews and digest items; it navigates through the container's ref (`openAppUrl`: `getStateFromPath` → `getActionFromState`, `stripLinkedActionParams` as for every incoming link), and a link naming another of the person's burrows switches to it first, as `AppLinks` does. `useOpenLink` opens canvases, the audit log and external `LinkRef`s on the web (`webUrlForLink`: `appPath` + `?burrow=`) instead of doing nothing. **Android app links** claim the web paths the phone has a screen for, in both forms: `/c/ /dm/ /direct/ /pr/ /runs/ /agents/ /automations/ /automation-runs/` (prefixes), `/agents /work /search /automations /vault`, and the old form as `pathPattern` (`/.*/c/.*`, `/.*/vault`, …: Android's glob, `.*` standing for the burrow's slug) — an email's or another app's Whombat link opens the app. The domains are already verified (AP-291's `assetlinks.json` covers the whole host); paths are only intent-filter patterns. **Notification taps on Android** were checked, not changed: Android's notifications are native (`modules/whombat-live`) and open `whombat://open?…` / `whombat://push?…` through their own `PendingIntent`, which reaches `Linking` (and `LatestIntentListener` keeps it across a killed process); a managed push FCM showed itself reaches the app through `launchPushTap`/`onPushTap`. `push/taps.ts` being iOS-only is right: it turns iOS's tapped alert into the URL Android's notifications already carry. | A URL in a message did nothing when it pointed at the web app (or opened the web app in the browser, signed out), and canvases and audit rows didn't open at all. Whombat links are the phone's to open; the rest belongs to the browser. A scheme allowlist keeps a message from launching arbitrary intents. |
| AP-715 | **Share to Whombat.** Android's share sheet offers Whombat for text, links, images and any file, one or several (`expo-share-intent` 8.0.1 — it supports SDK 57 and its plugin can leave iOS out, `disableIOS`; the main activity stays `singleTask`). The share is caught from `index.ts` (`startShareCapture`) before anything renders, so one that starts the app or arrives on the sign-in screen waits in memory (`data/shareInbox.ts`, never in navigation params) until a navigator is up; `ShareIntentBridge` then opens **Share to…**: channels, DMs with agents and direct conversations with people, newest first, with “Find a conversation” (branch rooms left out). Picking one opens a small composer on the same screen — the shared text (a page's or mail's title on its own line above it, unless the text already has it), the files as the composer's upload chips (`useComposerUploads`: same limits, errors, Retry and Remove; at most 10, a note names any the phone couldn't hand over) — and “Send to #general” sends through `useSendMessage`, then the conversation replaces the Share screen. A newer share replaces an unsent one; Cancel drops it. A `pnpm patch` of the module's Kotlin reads `EXTRA_SUBJECT` when there is no `EXTRA_TITLE` (browsers and mail apps name a page there) and takes a `text/plain` share with a stream but no text as a file. Share intents carry no URL, so `Linking`, the linking config and the managed root's `onUrl` never see them. | The phone is where things are found — a link, a photo, a PDF — and handing one to an agent should take the share sheet, not a copy, a switch and a paste. The composer on the share screen needs nothing of the conversation screen, which another stream is rebuilding. |
| AP-716 | **Voice input stays the keyboard's.** No microphone button in the composer: Android keyboards (Gboard's voice typing, Samsung's) already dictate into any text field, offline on most phones, and an in-app button (`expo-speech-recognition`) would add the `RECORD_AUDIO` permission the app has so far refused (no camera or microphone beyond the QR scanner, `app.config.cjs`) plus another native module, for what the keyboard's mic already does in the same place. Revisit if people ask for voice notes (audio as an attachment), which the keyboard can't do. | Same result, no new permission, no audio path through the app. |
| AP-717 | **The phone opens with the last-seen burrow, and keeps what is written offline.** (1) **Persisted cache**: an allowlist of reads (`me.get`, `burrows.get`, `conversations.bootstrap`/`list`/`get`/`getChannel`, `messages.list` — the newest page only, without optimistic copies — `messages.thread`, `notifications.inbox`, `agents.list`/`get`) is saved after changes (at most every 2 s) and when the app goes to the background, and restored before the first screen (at most 1.5 s), so the inbox, sidebar, conversations and agents show at once while the session comes up; nothing from the Vault, sign-ins, tokens, devices or settings is ever written. A copy older than a week isn't shown. (2) **Outbox** (`data/outbox.ts`): a message sent while offline — or, on a managed Whombat, while the session isn't open, or while earlier messages of the conversation still wait — is kept, shown above the composer as the viewer's faded bubble with “Waiting to send” (“Sending…”), and sent in order once connected, each with the client id it was written with (the server's idempotency key, so a resend is never a second copy). A refusal shows “Not sent · {reason}” with **Retry** and **Delete** (44dp), and holds the later messages of that conversation (or thread) behind it; five sends without an answer while online show “Not sent · Couldn’t reach your Whombat.” Held for approval counts as sent. The ChatView change is one hook and one line (`useOutboxSend`, `<OutboxRows>`). **Protection** (docs/privacy-and-security.md: data on the device): both live in a `SecureBox` (`data/secureBox.ts`): ChaCha20-Poly1305 (native when it matches the pure-JS one, AP-26) under one random 256-bit key kept only in expo-secure-store (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`, not synced or backed up); files in the app's documents directory hold ciphertext only, named by a hash (no ids on disk), with the storage scope and name as associated data. **Scope**: per Whombat (`managed:<org>/<Whombat>`; `server:<url>` self-hosted), and the cache records the account scope it was saved under (`scopeKey`: org, Whombat, account, authorization generation) and is saved only once the session said whose data it is; a session that opens as another account or with other permissions drops it. **Wipe**: the scope guard's clear (sign-out, switching Whombats, revocation, a permission change — and, as for everything cached, leaving the burrow app for the recovery kit) deletes every file and the key; self-hosted sign-out does the same. | The phone is opened in passing, often on a poor connection: a blank “Loading” until the handshake is done wastes it, and a message typed in a tunnel shouldn't be lost or make the person wait to retype it. Encrypting with a keystore key keeps the copy as protected as the endpoint key, and the account check and wipes keep one person's data from another's session. |
| AP-718 | *Its Automations part is superseded by AP-6245 (automation-chat-mobile.md): plans in Chat replace publishing a draft.* **Editing on the phone** (John lifted “that stays on the web”). **Vault**: “Add to Vault” under the Vault's intro opens a sheet with the web's templates — MCP server, API token, Basic auth, Login (only where the Whombat has `vault.login`), Secret for a pack — and the web's form; validation is the contract's schema with the web's words (`data/vaultForm.ts`, a copy of the web's rules: they live under `apps/web` and `packages/client` isn't changed in this batch), refusals land under their field, and after saving it checks the connection of an MCP or HTTP entry as the web does and opens the entry. An entry's SECRET section has **Replace** (Basic auth and logins also ask for the username, sent only when changed). Secrets are typed only in a masked field (`FormField`'s secret mode: no autofill, autocorrect or suggestions), live only in the open sheet's state, are cleared on save and dropped on close, and are never logged or put in navigation params. SSH keys (servers, public key, host keys), a login's CSS selectors and Test sign-in stay on the web, and the forms say so. **Plans**: a Plans screen (Open / All; open plans first, each row with where it lives, progress, due date and the leading step) opened from a “Plans” button in the Work header — its own route, no deep link — and **Add a step** at the end of a plan's STEPS: title (160 characters) and owner (you by default); with handoffs (`delegation`), a brief turns it into “Hand over” with an optional “Done looks like” and the first teammate who isn't you as owner, as on the web; 30 steps at most; no due time (the app has no date picker). **Automations**: on/off was already there; a saved draft gets “Review and publish” (“Review the new draft” beside a live version): a sheet with what starts it, its steps and its problems, and **Publish** only for someone the server says may manage it and a valid draft, bound to the draft's hash. **Packs**: unchanged — the web's lists don't turn packs on or off or attach them either (that is the pack's own dialog), and the phone already turns each on and off. **Skill proposals**: an agent's Packs screen (the phone's skills list) shows PROPOSED · n with the proposal, its reason and scan, and Approve / Reject under the chat card's rules (a clean scan for someone who may decide; “Decide on the web” after a cautious scan; a confirmation first). | The phone is the primary device now: a key the agent asks for, a step to add to a plan, a draft to publish and a skill to approve shouldn't wait for a computer. What needs a file, a picker or a test browser the phone doesn't have stays on the web, and says so. |

## Left open

- AP-715: the module copies shared files into the app's cache and doesn't delete them after sending (app-private, but
  not cleared with the scope guard); its native file lookup can crash on a provider that returns no row. Both upstream.
  `THIRD_PARTY_NOTICES.md` needs `pnpm notices` once the batch's branches are merged (the patch's notice is in the
  script).
- AP-717: unsent messages are wiped with the cache when the person switches Whombats, signs out or opens the recovery
  kit (privacy first). Files picked while offline can't upload, so a held message carries only files uploaded before.
- AP-718: deciding a skill proposal from an inbox row isn't wired (the inbox is another stream's; `ProposedSkills`
  mounts with one line); editing or removing a Vault entry, the home network list, pack secrets and attaching packs
  stay on the web. The Vault form rules are a copy of the web's (`data/vaultForm.ts`) until they move to
  `packages/client`.
- Everything here needs the one APK and emulator pass: shares from Chrome (title + link), Photos (one, several), a PDF
  and a `.txt`; an app link from Gmail in both path forms; airplane mode with a message written, then back online;
  a cold start offline; adding a Vault entry, replacing a secret, adding a step and publishing a draft.
