# What’s new in the apps (AP-10060…AP-10065)

A customer on the web app noticed Whombat updates itself, but nothing readable said what changed. The apps showed
only a technical line under “Updated to …” (control's release summary), and the plain-language changelog
(`docs/changelog.md`, legal-texts.md LGL-05) lived only in the repository. This first step shows that changelog in
the apps and says once that an update happened. Release notes per release are a later step (below).

| Id | Decision | Why |
| --- | --- | --- |
| AP-10060 | **What’s new is a page of the web app, `/whats-new`, built from `docs/changelog.md`** (without its note for those who keep it, after the first `---`), drawn like the legal pages. Inside the app it is a screen in the shell; on the hosted app it also opens without signing in when it is the page first opened (a link, the phone), never when going back and forward inside the app. The box's web build copies the changelog for it (`appliance/nix/lib/sources.nix` and the runtime's fetched web source). | One source for the words people read, served by Whombat itself; a box shows the changelog its version came with. Back and forward must never close an open app. |
| AP-10061 | **This Whombat → About's UPDATES has “What’s new”** (“What changed in Whombat lately, in plain words.”, Read) under the update rows, on the web; the phone's About has the same row, opening the hosted page in the in-app browser. | Where people look after an update. |
| AP-10062 | **“Whombat updated · See what’s new · Dismiss” shows once per update** (`whatsNewNotice` in `@whombat/client/managed`), in the web shell's notice slot and in the phone's strip under the status bar (after the passkey nudge, one card at a time). It compares the Whombat's last update (`update.lastUpdate.release`) with the release the device saw last, kept per Whombat (web: this browser's storage; phone: the secure store). Dismiss, See what’s new and opening What’s new keep the release; showing it doesn't. | Said once, where the person already is, and never again for the same update. |
| AP-10063 | **The first look only remembers**: a device that never saw a release stores the current one (or `none` before the first update) without a notice, so the next update is the first it tells about. No notice after an update that can't go back (forward repair) or where storage can't be read. | Nothing to compare with on a first look; a notice at every start would be worse than none. |
| AP-10064 | **Both apps read the status they already read** (web: the version line's `appliance.status` query; phone: the Settings list's query, once the session is open); no new poll. | The notice needs no fresher status than the version line. |
| AP-10065 | **Later, not here**: notes per release from the release build (the changelog lines added between two releases, kept with the release and shown under “Updated to …” in place of the technical summary), and a check that a change people can notice adds its changelog line. Until then the hosted app's page is the changelog of the hosted app's build, which can be ahead of a Production Whombat. | The first step needed no contract or control change. |
