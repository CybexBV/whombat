# Live data, calmly (AP-6560…AP-6579)

John, 2026-11-02: the phone app feels laggy on his iPhone Duo. A code read found refetch storms (coming back to the
app, the assistant at work) and app-wide re-renders on every message. This file covers the live data: when reads are
fetched again and what draws again. The web shares the client parts (AP-6562, AP-6563, AP-6570).

| ID | Decision | Why |
|---|---|---|
| AP-6560 | **Coming back to the app or getting online refetches a read only when the live updates came back without resuming since it was answered, when nothing changed it for five minutes (`QUIET_READ_MS`), or when it failed** (`createFreshness(session, realtime)` in `managed/background.ts`). While the connection isn't open a resumable read waits: the subscription resumes from its cursor when it opens, or says what it lost, and `invalidateForResync` reads those topics' queries again then; a quiet one is asked at once and waits for the connection. Supersedes android-slim.md AP-926's “the connection was down, or came back after the read”. | After two minutes in the background the connection is let go (AP-925), and on return the focus event came before the connection opened, so every observed query refetched (frozen pages and visited tabs too), although the subscription resumes and replays what it missed. The quiet bound came after John's Android phone showed yesterday's Chat all morning (2026-11-07): a change the live updates lose without saying so was otherwise never read again while the screen stayed mounted. |
| AP-6561 | **Reads on a screen out of view don't refetch**: the navigators tell each screen whether it is in view (`navigation/ScreenFocus.tsx`, `ScreenFocusContext` from `@whombat/client/react`) and the client's read hooks (`queryHook`, the infinite lists) pass an `enabled` function that is off while it isn't. Realtime still patches their data; a screen coming into view reads again only what was invalidated, failed or never read meanwhile (or, drawn out of view, what it would have read on mounting). In view: the top page, and with two pages on the open Duo the tabs on the left as well as the right page's top; a tab when its bar shows it and the tabs are in view. The tab bar's badges use TanStack Query's own hook and stay live under a page (the app icon's count). | Frozen screens (freezeOnBlur) don't draw, but their observers still counted as active: every invalidation and focus refetched what nobody saw. `subscribed: false` was the obvious tool, but it detaches the observer: the cache drops the data after five minutes out of view, every return refetches anything older than 15 s, and the flag only changes with a render, which a frozen screen doesn't do. An `enabled` function is read when TanStack asks, needs no render and keeps the observer. |
| AP-6562 | **Home's overview is refetched at most once a second for realtime frames** (`query/calm.ts`, `invalidateCalmly`): the first frame at once; frames inside the second mark it out of date and one refetch follows at its end, after any fetch still on its way (not cancelling it). Web and phone. | Every turn of the assistant sends `home.changed {working}` (claimed, ended, plans, approvals, done), each refetching the whole overview (Needs you, chats, things, widgets), the next cancelling the one before. The frames carry no content, so `working` can't be patched into the cache. |
| AP-6563 | **`widget.updated` refetches the overview only when it shows that widget** (Home's pinned ones); `widgets.list` refetches as before. Web and phone. | A widget kept on a thing's page isn't in the overview; its refresh refetched the overview anyway. |
| AP-6564 | **The tab bar's badges take only their counts from the overview and the chats list** (`select`), and `useBadges` returns the same object until a badge changes. Its Settings dot reads the burrow's stable parts. | Every overview refetch and every message drew the bar again. A lighter read for the Needs you count would need the server (a follow-up); the overview is fetched once for both. |
| AP-6565 | **The navigator, its saved place, the live activities and the account theme don't follow the bootstrap**: they read `useBurrowBase()`, the sidebar from `currentBootstrap()` when a push tap or a restore needs it, and the theme through `useBootstrapSelect`. | Each new message changed the bootstrap and drew `RootNavigator` (the whole navigation tree) again, as well as the bridges around it. |
| AP-6566 | **A read on screen that failed is asked again 30 s after it failed while the app is in the foreground** (`retryFailedReads` in `managed/background.ts`: every 5 s it asks the reads in view whose failure is 30 s old, `failedReadDue`), unless the box answered no (a 4xx other than 408 and 429). Not TanStack's `refetchInterval`. | With data from before on screen a failed read looks like a good one on most screens, so a read that failed stayed failed until the next return to the app. TanStack starts a query's interval over on every change to it, a live update to what it shows too: an interval never came while a conversation or a run's log was busy. |
| AP-6567 | **A saved copy too large to keep is removed from the phone** (`queryPersist.ts`), and **a copy read back after the first screen leaves the reads answered or failed meanwhile alone** (only reads not asked yet, or still on their way, take it). | A copy over the cap was skipped but the old file stayed, so every start opened with the last one that fit, however old (up to the week's limit). A late copy over a failed read made it look answered, and nothing asked again. |
| AP-6568 | **A realtime event the app can't read is a resync of its topic** (`createSessionRealtime`: `bad_frame` is also `onResync({ reason: 'gap' })`), web and phone. | The cursor has moved past it, so its change (a settle, a new reply) was lost until the screen mounted again. |
| AP-6569 | **A read that outgrew one message gets its export stream within a deadline** (the request's, at least 60 s; `readTooLarge` in `session/secure.ts`), then fails as timed out and is asked again (AP-6566). | The stream had none: a bulk slot that never freed or an answer that stopped coming left the read waiting for ever, and its later refetches waited on it. |
| AP-6570 | **A live update changes what a read shows, not when it was read** (`patchQueryData` in `query/cache.ts`, under `patchEndpoint`, a removed search result and a mutation's rollback): the read keeps its `dataUpdatedAt`, its failure and its invalidation. Web and phone. | John's Z Fold8 showed 5 November's Chat on 10 November while Home had the threads (2026-11-10). `setQueryData` stamps a patched read as answered now and clears its failure and invalidation, so a days-old list one live event touched looked just read: the quiet rule (AP-6560), the retry of a failed read (AP-6566) and the catch-up of a screen coming into view (AP-6561) all passed it by. |
| AP-6571 | **The copy read back at start is owed a read, however recently it was read before it was saved** (each of its queries is invalidated in `queryPersist.ts`), and **the reads on screen that failed or are owed one are asked as the connection opens** (`refetchOwedReads`). A read whose last refresh failed while live updates kept it current is saved too, as an answer. | The copy is what the phone showed when it was saved; live updates kept changing it after its last read. A screen showing it now asks for it as it opens or comes into view, and a read that failed while the connection was still coming up doesn't wait for its next retry. |
| AP-6572 | **Chat and a thread say “Updating…” or “Couldn’t update · Try again” over old data** (`ui/updatingPill.tsx`, `data/readLine.ts`): a quiet pill over the top of the list when a read over data a minute old or more takes over 2 s, or when a read failed with data on screen; Try again reads it again. It floats, so nothing moves. | A list days old looked as current as one read a second ago. Most answers come within 2 s, so a routine refresh says nothing. |
| AP-6573 | **The box keeps the app build each device's last session named** (`appliance_endpoints.app_build`, from `hello.client.build`, with `last_seen_at`; migration 0066) and logs each enrolled device's session open with its build and way in. | Which build John's phone ran when Chat went stale had to be guessed from its update downloads. |
| AP-6574 | **The phone keeps a sync log** (`data/syncLog.ts`): reads asked over old, owed or failed data and their answers, slow and failed reads, the connection, the app coming and going and the copy read back at start, never what a read brought; the newest 400 notes, kept on the device between runs and cleared with the rest of a Whombat's data (leaving it, another account). **This Whombat → About shares it as a text file** (“Share this phone’s sync log…”), where the person chooses, like the diagnostic files: nothing is sent by itself. | Whether the phone asked for Chat's list that morning, and how the read ended, couldn't be found out afterwards: the box logs only answers over 64 KB, and the phone kept nothing. |
