# A faster session on the iPhone (2026-11-02)

John uses the app on an iPhone Duo and finds it laggy. A read of the phone's session path found the iPhone doing in
JavaScript what Android hands to the system, and several pieces of work done twice. Measured on the iOS 27 simulator
(Hermes, Release build, fixtures mode) with a temporary probe; numbers are per call unless said otherwise. Phone only:
no contract, runtime or protocol change, no new dependency.

| # | Decision | Why |
|---|---|---|
| AP-6500 | **`modules/whombat-crypto` has an iOS half** (`ios/WhombatCryptoModule.swift`, CryptoKit `ChaChaPoly`): the same synchronous `isSupported`, `chaCha20Poly1305Seal` and `chaCha20Poly1305Open` as the Kotlin module, ciphertext followed by the 16-byte tag, bytes copied once each way (`Data` ↔ `Uint8Array`). The existing self-test (`checkedNativeCrypto()`, AP-891) turns it on and keeps pure JS on any mismatch; Android is unchanged. Amends AP-890 (“the iPhone keeps the pure-JS cipher”). | Every frame of the Noise transport and every sealed file was pure JS on the iPhone: sealing 65 kB took 19.6 ms there against 0.14 ms in CryptoKit, opening 19.1 against 0.15 ms. The self-test passes on iOS (checked on the simulator). |
| AP-6501 | **A native running SHA-256 in the same module** (CryptoKit `SHA256` on iOS, `MessageDigest` on Android): a shared object (`Sha256Hasher`, `update`/`digest`) so a download is hashed frame by frame. It is checked once per process against the pure-JS hash, whole and in uneven pieces (`checkedNativeSha256()`), and handed to the session (`createSecureSession({ sha256 })`, `ApplianceSession.sha256()`), which hashes downloads, uploads, upload chunks and backup files with it. The web keeps the pure-JS hash. | Hashing 65 kB took 25.3 ms in JS on Hermes against 0.05 ms native, on every download frame. |
| AP-6502 | **An export read is hashed once.** `readExportFile` takes the stream's checked `stream_done` (a stream whose bytes don't hash to it already failed with `integrity`) instead of hashing the whole file again. | The same bytes were hashed in the stream and again at the end. |
| AP-6503 | **A read that came back `too_large` / `use_export_stream` goes straight to the export stream next time** in that session: the op and its exact input are remembered, at most 64 of them, oldest dropped first. | Each such read built and refused the whole answer on the box before the stream asked it again. |
| AP-6504 | **The client decodes the box's messages with a lean copy of `ApplianceMessage`** (`session/control-decode.ts`): an answer's `output`, an outcome's `result.output`, an error's `details` and a stream's `output` are taken as `JSON.parse` made them (an `output` must be present) instead of being walked as the recursive `JsonValue`; the text is decoded with the platform's `TextDecoder`. Every other member and check is the protocol's own; the published contract is unchanged. Nothing relies on the walk: the endpoint's own schema checks the answer next (`http/client.ts`), and the client copies answers through JSON anyway. | Decoding a 50 kB answer took 10 ms on Hermes (6 ms of it core's pure-JS UTF-8, 4 ms the schema) against ~1.2 ms for the platform's UTF-8 and `JSON.parse`. In Node with `--jitless`: 5.4 → 0.09 ms. |
| AP-6505 | **The saved cache (AP-717) is smaller and saved only when it changed.** A save is skipped when no kept read's data changed since the last save or restore (a refetch with the same answer keeps the same data through structural sharing); the messages of at most six conversations or threads are kept: those on screen first, then the most recently opened or changed; while the copy is too large the least important of them go first, one at a time; the limit is 400 000 characters (was 1.5 million). Opening a conversation the copy left out makes it out of date. Restore is unchanged. | Every save dehydrated, stringified and sealed every cached conversation once a minute and on each trip to the background, and the next start decrypted and parsed all of it before its first screen. |
| AP-6506 | **zod's compiled parsers are off on the phone** (`z.config({ jitless: true })` in `src/polyfills.ts`, before any schema is made: each schema reads it when it is made). | Hermes allows `new Function`, so zod compiled a parser for every object schema on its first parse: 2.0 ms each against 0.08 ms interpreted, and only 5 against 7 µs per parse afterwards. The app's JS was busy for 1064–1179 ms after a fixtures-mode start with it, 838–883 ms without (four launches each). |
