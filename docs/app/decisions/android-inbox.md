# Android inbox: one list, live NEEDS YOU, read rows leave, badges, no false update notice (AP-701…AP-704, AP-708)

John, 2026-10-04, making the Android app his main device: the phone kept saying it needed a new version when none
was there to get, the inbox's chips split one list into four, NEEDS YOU showed requests he had already dealt with, read
mentions and replies never left, and nothing on the tab bar said something was new. No contract change (contracts stay
0.45.1): `downloads.android` (CT-191), `work.overview`, `notifications.inbox`/`markRead` and `conversation.unread`
already say everything.

| ID | Decision | Why |
|---|---|---|
| AP-701 | **“Update the app” only when a newer build is out; the notice doesn't stick.** (a) The phone asks control for the APK it hands out (`androidDownload()`, `managed/appUpdate.ts`: `updateCheckFor(control)`, asked when a session opens and hourly, one request at a time, cached an hour, a failure retried after ten minutes) and offers the button only when its `versionCode` is above this build's (`newerAppPublished`; the build's own is `phoneClient().buildNumber`, the `versionCode` app.config derives from the root `package.json`, AP-259). Without a newer build the notice stays, calmly: the strip has no warning border and no button, and reads “This Whombat is newer than this app. The update will be here soon.” for a runtime the app is too old for, or the left-out text followed by “The update will be here soon.”; `NeedsNewerApp` (Devices, owners) says the same without its button. The left-out notice stays (AP-266: nothing left out silently) because with (b) and (c) it no longer sticks. The iPhone app, with no APK, keeps offering the page. The full-page gates (`client_too_old`, below the security floor) keep their button: the app can't go on there at all. (b) The inbox shows its own placeholder rows (“This needs a newer version of the app.”, one per row left out, as the Work view does, AP-255), so `notifications.inbox` joins `work.overview` in not counting towards `leftOut`. (c) A strict failure (a security view this app couldn't read) belongs to its screen: `leftOut.clearStrict()` runs whenever the focused route changes (`RootNavigator`'s `onStateChange`); a screen opened again asks again. | DEV served a 0.17.1 APK for days, so the box was far ahead and the phone kept saying “Update the app”, and the button led to the same build. An approval answer that didn't read strictly kept the notice on every screen until he switched Whombats, and an inbox row of a newer kind raised it too. |
| AP-702 | **One inbox, no chips.** The filter chips (All, Needs you, Mentions, Agents) are gone: under the title, NEEDS YOU (when something needs the viewer), the WORK card (AP-94), then MENTIONS, DIRECT, REPLIES and FROM AGENTS in the server's order, empty sections left out; “Nothing new. Agents will show up here when they need you.” when there is nothing at all. The screen still loads `filter=all` once. | The chips split a short list into four views of itself; the section headers already say what each part is, with what needs the viewer on top. |
| AP-703 | **NEEDS YOU is the live Work view's `needs_you`.** `inboxView` builds it from `work.overview` (the web Work view's list): pending approvals (now included), Vault asks, questions, plan steps and skill proposals, as `WorkRow`s with the Work screen's actions (Approve, Decline with its confirm, …; `useWorkActions('Inbox')`), opening the item's own screen from its link (approval, plan, run, conversation). The notifications' stored `needs_you` rows are dropped; they only stand in on a server without the Work view (it answers 404: `null`), with their inline Approve / Details as before, and are hidden while it loads. The WORK card no longer repeats what needs the viewer (its rows are blocked, failed, running, queued; its counts unchanged). It stays live: `approval.updated`, `plan.updated`, runs, turns and skill cards already refetch the Work view, and a new `needs_you` notification now does too. | The stored rows have no resolved state: a decided approval stayed with a “done” line and Vault asks and skill proposals never went away. The Work view is built per viewer from the objects that own the state, so what's decided leaves. |
| AP-704 | **Mentions, direct messages and replies leave once read.** The list drops a `mention`, `direct` or `reply` row whose `readAt` is set; agents' updates stay (read ones without the unread look): they are a record of what agents did, and John's ask was about mentions and replies. Reading marks them: `useMarkRead` (a conversation's top level read to the end) reads the cached inbox rows whose link is that conversation or a message in its top level, and tells the server (`notifications.markRead {ids}`) so other devices agree; opening a thread reads the rows of that thread (`useReadInboxAt(conversationId, threadRootId)` from `ChatView`; a thread's replies don't move the conversation's read marker); `conversation.unread` with 0 (read on another device) reads the top level's rows in this cache. Matching is by link (`query/inboxRead.ts`): the conversation's link from the cached sidebar or detail against the row's conversation link or `message.in` (channel by slug, DM by agent, direct by id, branch room by number and repository when both say), and the row's `threadRootId`. A reply in a thread the viewer hasn't opened stays. | `readAt` existed but nothing filtered on it, and reading the conversation never touched the inbox. |
| AP-708 | **Badges on the tabs and the app icon.** Inbox: what needs the viewer (`work.overview` `counts.needs_you`; without the Work view the unread stored NEEDS YOU rows) plus unread mentions, direct messages and replies (`inboxBadgeCount`); agents' updates don't count. Channels: the conversations that mention the viewer or are unread direct messages (an agent's DM or people's, not muted) (`channelsBadge`), else a dot when something not muted is unread. The badge is the unread pill (`btn`, a mono 11/500 `btnfg` count, “99+” above 99) over the icon's top right, ringed 2dp in the bar's `bg`; the dot 12dp. TalkBack hears it in the tab's label (“Inbox, 3 new”, “Channels, unread messages”); the badge itself is hidden from it. The app icon's badge follows the Inbox count (`expo-notifications` `setBadgeCountAsync`; Android launchers vary). The tab bar uses the Inbox screen's own queries (one fetch, kept live). | Nothing told John something was new unless he opened each tab. |

Open: there is no realtime event for notifications read elsewhere, so another phone sees a row read by this one on its
next inbox refetch (focus, pull to refresh, 15 s staleness), not at once; reading the conversation there clears it at
once (`conversation.unread`). A `notification.read` event would need a server change. — Closed by contracts 0.55
(CT-300) and MN-03 (mobile-reach.md): the event reads the rows on every device.

Checks: `pnpm check` once (DEV fast). Android not run on a device or emulator; no version bump.
