# Passkeys that open a Whombat, on web and Android (AP-785…AP-803)

John, 2026-10-05: signing in on a new device was “email link → Pick a Whombat → Open → Set up this device”; “I want to
instantly open my environment”, then “Implement this fully”. The spec is Whombat `docs/decisions/passkeys.md`
(PK-01…PK-11, server PK-D01…PK-D09); contracts 0.50.0 (CT-280…CT-285: `enroll.passkey`, `passkey.register.begin`,
`passkey.register`, `passkeys.list`, `passkey.remove`, `passkeys.policy`, the codes `passkey_invalid`,
`passkey_not_allowed`, `passkey_limit`, the feature `passkeys`, `SESSION_API_LEVEL` 33, control's Whombat-bound
options); control CL-117…CL-119. One touch signs in to the cloud account (control) and lets the device in
to the Whombat the passkey names, which verifies the assertion itself: control still never lets a device in (MA-03).
There is no mock (B-05): the screens reuse the sign-in frame, the setup card, Settings' rows, the strips and their
words' conventions. Decided by the implementer (feedback-decide-yourself).

## Shared (`@whombat/client/managed`, `passkeys.ts`)

| ID | Decision | Why |
|---|---|---|
| AP-785 | **Contracts 0.50.0, vendored like every bump.** `FEATURE_NAMES.passkeys` = “passkeys” (“Update your Whombat to use passkeys.”). API level 33 needs nothing else here: the window is 31…34, no level-30 runtime is in the field. | CT-284. |
| AP-786 | Superseded for shared credentials by [SPK-01](../../decisions/shared-passkey.md). **`PinSource` gains `passkey`.** The Whombat a passkey names in its user handle (`wb1:<PeerId>`, PK-01) is a party that already trusts it, like a link or a kit (AP-63): the authenticator returns the handle it stored at registration, which this app only ever registered after checking control's `user.id` equals the Whombat's own `passkey.register.begin` user. So `trustDecision({pinned, named: handle, directory})` decides: no pin → pinned from the passkey; equal → on; pinned and different from the directory → the existing identity-changed hard stop, nothing sent. | PK-04 step 5 without a new trust root. |
| AP-787 | **The port is `PasskeyPlatform`** (`isAvailable`, `supportsConditional`, `create(options) → RegistrationResponseJSON`, `get(options, {conditional, signal}) → AuthenticationResponseJSON`), WebAuthn JSON both ways (the `@simplewebauthn` shapes the contracts verify). A dismissed or aborted prompt is `PasskeyCancelled` and is said nowhere; everything else is a `PasskeyError` with a code (`challenge_mismatch`, `options_mismatch`, `invalid`, `not_allowed`, `limit`, `exists`, `unsupported`, `none`, `control_failed`, `rate_limited`, `unreachable`, `failed`) with its words in `PASSKEY_COPY.errors`. The Whombat's precise reason is its `details.code` (`forbidden` + `passkey_invalid`, `conflict` + `passkey_limit` / `passkey_exists` / `endpoint_enrolled`, `not_allowed` + `passkey_not_allowed`; Whombat PK-D03/PK-D04), read by `operationReason`; control's `passkey_invalid` / `passkey_limit` became `ControlErrorCode`s (a 401 `passkey_invalid` is not a sign-out). | One vocabulary for two platforms and two verifiers. |
| AP-788 | **Control client** (`ControlApi`): `passkeyAuthenticateOptions(endpoint)`, `passkeyAuthenticateVerify(challengeId, response)` (stores the token like `verifySignIn`), `passkeyRegisterOptions({appliance, applianceNonce})`, `passkeyRegisterVerify({name, response})`, `passkeys()`, `deletePasskey(id)` (control's id is the credential id, base64url, CL-117). **Session ops** in `sessionOps`: `enrollPasskey`, `passkeyRegisterBegin`, `passkeyRegister`, `passkeysList`, `passkeyRemove`, `passkeysPolicy`. `passkey.*` and `passkeys.*` answers are read strictly (AP-266: a passkey that can open the Whombat must never vanish from a list). | Contracts first. |
| AP-789 | Shared-credential sign-in and multi-appliance discovery follow [SPK-01](../../decisions/shared-passkey.md). **Sign-in (`preparePasskeySignIn`, `passkeySignIn`, PK-04).** Options are asked for this device's key (`endpoint` = its PeerId); the challenge is recomputed (`passkeyEnrollChallengeBase64url({nonce, endpoint})`) and anything else is refused **before** the authenticator is asked (`challenge_mismatch`); `allowCredentials` from control is dropped and `userVerification` is `required` (a Whombat passkey is discoverable and verified). Prepared options are reused for two minutes (the autofill's request and the button's share them; a dismissed prompt leaves them unused). After `…/authenticate/verify` every ending is an outcome carrying the cloud session (the token is stored by then): `signed_in` (a handle that names no Whombat, PK-11), `not_in_org`, `retired`, `changed` (hard stop), `open` (`enrolled: true` when let in now), or `setup` (`needs_update`: the runtime lacks `passkeys`; or the Whombat's refusal) — pinned either way, so pairing can follow. The Whombat is looked up in the directory of **every** organization of the session, first by this device's record for that PeerId, else by `contentPeerId`. Already enrolled → open without `enroll.passkey`; `endpoint_enrolled` from the Whombat → open too (PK-11, PK-D04). The registry gets the record (`pinSource: 'passkey'`, `enrolled`, `accountId`) and becomes the last used, so the app lands in the Whombat. | PK-03, PK-04, PK-11 in one tested place. |
| AP-790 | **Registering (`passkeyRegister`, PK-06).** `passkey.register.begin` on the Whombat, then control's options checked against it — `challenge` = `passkeyRegisterChallengeBase64url({controlNonce, applianceNonce, appliance})`, `user.id` = the begin's (the Whombat can't check it, PK-D03), `rp.id` = the begin's `rpId` — else `options_mismatch` before the authenticator; the Whombat's `excludeCredentialIds` are added to control's, and `residentKey`/`userVerification` `required`, attestation `none` are forced (PK-01). The Whombat stores it (`passkey.register`), then control (`…/register/verify`); control failing twice → `passkey.remove` on the Whombat and `control_failed` (“Your Whombat saved the passkey but Whombat’s servers didn’t, so it was removed again. Try again in a moment.”). The name is this device's label (“Chrome on Linux”, “Pixel 9 · Android app”), cut to 64. `passkeyRemove`: the Whombat, then control for the caller's own (control not having it is fine; not answering doesn't undo the removal: without the Whombat it opens nothing). | PK-06, PK-08. |
| AP-795 | **Telling the person (PK-09, Whombat PK-D08).** The Whombat's push is content-free; the words are the client's. `passkeyEnrolledDevices(endpoints, passkeys)`: a device (not this one, not removed) created during the last day within two minutes of a passkey's `lastUsedAt` is one that passkey let in. The web shows a line in the shell's notice slot (like the nudge, under any other notice; a warn dot) on the person's other devices, once per new device (`createSeenDevices`, local storage): “New device signed in with a passkey: Pixel 9 · Android app” with Review (a link to Settings · Devices) and OK. Only the device created closest to a passkey's last use counts (a device paired a moment earlier isn't mistaken for it); on both platforms that device's row in OTHER DEVICES says “Signed in with a passkey · Last seen …” for the day, with its Remove. | The counter to a taken-over Google/Apple account is a visible notice with one-tap removal. |

### AP-803 For the server and control

- The Whombat and control accept this app's origin `android:apk-key-hash:hcREl8…` (PK-02, both done).
- Control's `Passkey.id` must stay the credential id (base64url): the client deletes the Whombat's id at control.
- Control's sign-in options must carry `rpId` (Credential Manager needs it in the request JSON; `@simplewebauthn` sets
  it).
