# Connecting from the phone (AP-2900…AP-2959)

John, 2026-10-19 (Whombat main checkout): “In the Android app, when I go to connections and add a new connection, I get
a list of all the available connections. When I click on a new connection that I want to add, I get presented with the
connection overview page again instead of the configuration for that connection. … implement it fully.” The spec is
Whombat `docs/decisions/phone-connect.md` (PC-01…PC-11); this is stream P of
`docs/implementation/server-updates/assignment.md`. Decided by the implementer (feedback-decide-yourself). Not in the
mocks (B-05): the phone's screens follow Add a server (AP-1697) and the web's connect form (CS-50 `SetupForm`) word for
word. No contract change (contracts 0.97/0.98 have every endpoint).

The cause, confirmed: Add a connection's rows opened `connectionsWebPath` (`/settings?tab=connections&connection=<id>`,
on a managed Whombat `https://<ui>/appliances/<device>/…`); the managed app claims `/appliances/` as a verified App Link,
so Android handed the page back to the app, whose link parser (`settingsScreenUrl`) dropped `connection=` and opened
Settings → Connections. This reverses AP-767, AP-847, AP-2810 and AP-2813 (the phone connects nothing), as SI-12
reversed AP-1367 for servers.

## Left for later

- Setting up Google's and Microsoft's apps, connecting GitHub and adding a feedback website stay on the web (a computer).
- Tool tiers (Allowed · Asks · Off) are still changed on the web; the phone shows them.
- A provider that redirects without a user gesture may keep the return in the browser (Chrome hands App Links over on a
  gesture); the hosted UI then finishes it there if that browser has the Whombat, else the person connects again.
- A sign-in started in a phone browser on the hosted web now comes back to the app as well, which finishes it at the
  Whombat last used.
