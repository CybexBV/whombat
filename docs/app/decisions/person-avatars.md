# A person’s photo (PA-01…PA-08)

John, 2026-10-05: “Add the ability to change a persons avatar.” Until now a person was always their initials on a tone.
Contracts 0.47.0 (CT-265) add `Person.avatarUrl` (an attachment URL every member may read), `me.setAvatar`
(`PUT /me/avatar`, `{image: base64 | null}` → `ProfileResponse`, account-wide like `me.updateProfile`) and the feature
`people.avatars`; the runtime side is Whombat `docs/decisions/person-avatars.md` (PVA-01…). There is no mock: the Profile
controls are designed in the existing Settings style. (Numbered PA-, not AP-: AP-755 and up belong to another stream.)

| ID | Decision | Why |
|---|---|---|
| PA-01 | **Changing the photo is gated on `people.avatars`; drawing it is not.** Web Settings → Profile shows a “Photo” row on every Whombat: with the feature its buttons, without it the row's meta line is the standard “Update your Whombat to use profile photos.” (`FEATURE_NAMES['people.avatars']`) and the avatar isn't a button. Android shows nothing without it (the sheet has no room for notes; the web says it), and never in the demo world (no account). `avatarUrl` is drawn wherever it is set; an older runtime simply never sends it. | The same split as the reply chip (AP-751): a control the runtime can't serve is not offered; data it sends is always shown. |
| PA-02 | **The sizing rules are shared and pure (`packages/client/src/avatarPhoto.ts`).** `avatarSquare(w, h)`: the largest centred square, refused under `AVATAR_MIN_PIXELS` (“That image is too small. Pick one at least 32 pixels across.”) or without a size (“Couldn’t read that image.”). `AVATAR_ATTEMPTS`: `AVATAR_PIXELS` (256) at quality 0.85, 0.75, 0.6, 0.45, then 192 at 0.6/0.45, 128 at 0.5, 96 at 0.4; `fitAvatar(encode)` returns the first encoding of at most `AVATAR_MAX_BYTES` (32 KiB) or fails “Couldn’t make that image small enough. Try another one.”; an encoder that throws is the image's fault (unreadable). `base64DecodedBytes` counts a base64 result. `avatarErrorText`: the image's reason, the Whombat's own words for a 4xx in the contract's shape (a type it refused), else “Couldn’t save your photo. Try again in a moment.” Copy in `AVATAR_COPY` (“Change photo”, “Remove photo”, “Photo saved.”, “Photo removed.”). Always JPEG: every platform encodes it, it has no alpha surprises once drawn on white, and a 256px JPEG is ~5–20 KB, so the first attempt nearly always fits. | One tested place decides what leaves the device; web and Android only decode and encode. |
| PA-03 | **Web: every person avatar goes through `PersonAvatar` (`features/messaging/PersonAvatar.tsx`), which resolves `avatarUrl` with `usePhotoSrc` and hands `HumanAvatar` a `src`.** `HumanAvatar` (`@whombat/avatars/react`) gained `src`: an `<img alt="">` absolutely over the initials disc, `border-radius: 50%`, `object-fit: cover`, same box, same label on the outer span; the initials stay underneath while it loads, are hidden once it has loaded (a transparent PNG doesn't show letters through) and remain when it fails (the `<img>` is dropped on error). `usePhotoSrc`: legacy, the URL itself; managed, the session's object-URL cache (`ObjectUrlCache.get`, shared, never aborted when an avatar unmounts — the read is small and other avatars wait on it) with the new `ObjectUrlCache.peek` so a photo already held draws in the first frame (no initials flash in long lists). Routed through it: messaging and canvas `PrincipalAvatar` (messages, threads, DMs, direct faces, mention lists, pins, member panes, everything that already used it), the sidebar footer, Profile and Members (current and former; invites stay initials), audit, search, Work, usage and spend rows, cards' parts, canvases list, the new-repo modal, and the stacked heads in the conversation header (26px inside the 30px ring) and a message's thread line (20px inside 24px). | One loading path per platform; URLs change with the photo (new attachment id), so caching by URL is always fresh. |
| PA-04 | **Android: `PersonAvatar` in `avatars/Avatars.tsx` with `usePhotoSource` (`avatars/photo.ts`); `HumanAvatar` gained `src` (an `<Image>` source, `cover`, round, initials until `onLoad`, kept on `onError`).** Legacy: `authedSource` (the bearer token on every request, as attachment images). Managed: the photo streamed into the scoped resource cache (`resourceToCacheFile`, cleared with the others on sign-out, revocation or switch), one download per URL for every avatar waiting on it, and `cachedResourceFile` (new, synchronous) so a cached photo draws at once. The conversation's token/session plumbing moved into `data/fileAccess.ts` (`useFileAccess`, `FileAccess`) and is shared by attachments and photos. `PrincipalAvatar` (everywhere people are drawn) and the Inbox's avatar use it. | The same rules as the web, with the phone's file cache. |
| PA-05 | **Web Settings → Profile: the profile row's 32px avatar is a button (“Change photo”, round focus ring, a `--line2` ring on hover), and a “Photo” row under it says “Shown with your name in every burrow. Any picture works: it’s cropped to a square.” with “Remove photo” (link button, only when there is one) and “Change photo” (secondary lg).** Both open one hidden `<input type="file" accept="image/*">`. `photoFromFile`: `createImageBitmap` (EXIF orientation applied), `avatarSquare`, a canvas per attempt filled white then drawn with high-quality smoothing, `toBlob('image/jpeg', q)`, `fitAvatar`, base64 → `api.me.setAvatar`; the same queries `updateProfile` invalidates (this burrow's bootstrap and members, the account session); toast “Photo saved.” / “Photo removed.” or the reason (PA-02). Controls are disabled while it saves. Anything the browser can draw is accepted (SVG and GIF too): nothing but the re-encoded JPEG leaves. | A row of its own keeps the name/title form untouched and matches the Settings rows (Signing key, assistant); the avatar as a button is where people look for it. |
| PA-06 | **Android settings sheet: the Profile header became `settings/ProfileRow.tsx`; the 44dp avatar is a button (“Change photo”, focus ring), and under it “Change photo” (secondary) and “Remove photo” (quiet, when set), each 44dp.** `pickPhoto`: `expo-image-picker` (`allowsEditing`, `aspect: [1, 1]`, no EXIF), then `expo-image-manipulator` (~57.0.20, added; a native module, in the next APK) crops the centre square, resizes and saves JPEG with base64 per `fitAvatar` attempt. The result is said under the buttons in 13 (mut, or bad for a failure) and announced to TalkBack; bootstrap and members are invalidated. There is still no name/title editing on the phone. | The sheet has no toast; a line under the buttons is where the eye already is. |
| PA-07 | **The fixture worlds answer `me.setAvatar` and carry photos (`app/avatarFixtures.ts`).** Checked as the runtime does: base64, at most `AVATAR_MAX_BYTES`, sniffed JPEG/PNG/WebP (never SVG), `validation_failed` otherwise; a `ProfileResponse` back. Legacy fixture mode keeps Mara's photo as an object URL (`avatarUrl` is at most 300 characters; a `data:` URL only under jsdom) and its outermost layer puts it on every person in every JSON answer (`withPhotos`). The fake managed world stores the photo as an attachment its session streams (`resources`), so the managed path is exercised end to end, and decorates every answer the same way. In-memory: a reload starts without a photo. No seeded photos: the mock's screens stay as drawn. | Dev mode, tests and e2e can set, see and remove a photo without a runtime. |

### PA-08 Checks

`pnpm check` once (biome, typecheck, unit tests). Unit tests: `avatarPhoto.test.ts` (square, attempts, fit, base64
size, error text), `react.test.tsx` (photo markup), `PersonAvatar.test.tsx` (legacy URL, managed stream once then
from the cache), `avatarFixtures.test.ts`, `SettingsScreen.test.tsx` (photo drawn, Remove photo, an unreadable file).
A look at Settings → Profile at 1440×900 in both themes in fixture mode, without and with a photo (and the photo in
Members, the sidebar and #general's header). No emulator run (DEV fast); the orchestrator bumps, tags and releases. The
`settings-general` baseline in `visual/__screenshots__` was already stale before this change (it shows the old tabs) and
is not refreshed here.

Released in whombat-app 0.39.0 (`app-v0.39.0`, contracts 0.47.0), APK 0.39.0 with `expo-image-manipulator` on DEV.
