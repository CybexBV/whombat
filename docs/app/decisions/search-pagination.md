# Search pagination (2026-09-30): decisions

Whombat's search now pages a keyset over everything the viewer may open (Whombat `docs/decisions/search-pagination.md`
SRP-01…SRP-10): a page may hold fewer results than asked for — even none — and still have a `next`; only `next: null`
says the search ended; a cursor from another search or an older server is refused with a 400. The contract is unchanged
(`SearchResponse.next`, `SearchQuery.cursor`). These are the clients' side, numbered on from the Whombat's.

| # | Decision | Why |
|---|----------|-----|
| SRP-11 | **`useSearchPages` (`@whombat/client/react`) is how web and mobile page search.** The first page is `useSearch` (chip counts, the answer); further pages are their own cached `search.query` entries (realtime edits and answers reach them), merged in order, each result once (`searchWalkResults`). A walk chains a page only while its cursor is still the `next` of the page before it (`searchWalk`): a first page refetched since that now ends elsewhere drops the pages after it (they would skip or repeat rows), and the hook lets their queries go at once — observed, they would be fetched again on every focus and resync, each with the Whombat's count scan (Whombat SRP-07); “Load more” goes on from the new `next`. A previous search's page kept on screen as `placeholderData` (mobile, while typing) never lends its cursor, and the merged rows follow the search and each page's status as well as its data, so a new search that fails shows none of the last one's rows. | One implementation of the paging rules for both apps. |
| SRP-12 | **A short or empty page isn't “No results”.** The empty notes (web “No results for “…”.” / “Nothing matches these filters.”, mobile “Nothing matches “…”.”) show only when the last page has no `next`. While nothing shows yet and the search goes on, the list loads on by itself with the skeleton up, at most `SEARCH_AUTOLOAD_PAGES` (10) further pages; after that “Load more”. Under a short page with results, “Load more” (nothing loads by itself while rows are on screen). “Load more” now stays, disabled, reading “Loading…” while its page loads (it used to vanish). Mobile gets the same end of list: “Load more” (the 44 dp secondary `Button`) — mobile had no further pages before; what the tab shows is `searchListState` (`apps/mobile/src/data/lists.ts`), tested as a view model because the mobile tests run without React Native. A receipt link looks its result up in every loaded page. | The Whombat bounds the work per request (SRP-05), so emptiness of one page says nothing about the rest. |
| SRP-13 | **A refused cursor starts over.** A further page answered with a 4xx (SRP-04: out of date, another search's, an offset cursor from before the Whombat updated) shows the existing “Couldn’t load more results. Try again in a moment.”; Retry then drops the further pages and fetches the first page again (the same cursor can never succeed). Other failures retry the page. Mobile shows the same sentence with its “Try again” button. No new copy. | Retrying a refused cursor would fail forever. |
| SRP-14 | **A removed result lowers the chips once** (review round 2). On `message.deleted` or a tombstone, `removeSearchResultEverywhere` treats the pages of one search — the same query but for `cursor` — as one: they share the search's counts and the apps show the first page's. When any page of a search shows the result, it leaves that page and the counts go down by one on every page of that search; a search that didn't show it is left alone (its counts are right again on its next fetch). Before, only the page holding the result lost it and a count, so the chips didn't move when it sat on a later page. A page fetched after the Whombat had already dropped the result, cached next to one that still shows it, goes down once too many until it is fetched again. | The chips are the first page's; a removal must reach them whichever page showed it. |
