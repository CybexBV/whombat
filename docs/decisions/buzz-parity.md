# Buzz-parity: cross-cutting decisions (orchestrator)

Six workstreams (A attachments, B memory, C automations, D packs, E ACP, F distribution) build Buzz-inspired
capabilities in Whombat's architecture. Plan and ledger: `docs/implementation/buzz-parity/`. Workstream decisions
live in `bp-<workstream>.md`; these are the ones that bind more than one workstream.

| # | Decision | Reason |
|---|---|---|
| BP-01 | Work lands on the local integration branch `buzz-parity`; it is not merged into `main`, pushed, released or deployed by this work. | The assignment prepares a reviewed change set for a later, authorized release. |
| BP-02 | **Contracts first, one owner per contract file.** `contracts/attachments.ts` (A), `memory.ts` (B), `automations.ts` (C), `packs.ts` (D); `DispatchContext.attachments/memory/packs`; persona hooks `persona/{attachments,memory,packs}.ts`. | Parallel workers never edit the same shared file; registries take one-line additions only. |
| BP-03 | **Providers declare capabilities** (`ProviderCapabilities`: images, documents, sessionResume, skills, cancel, usage, guardedConfinement). The runner delivers attachments/skills by capability and says honestly when a provider cannot use them; the AI provider panel shows the matrix. `false` means unsupported. | Unsupported behavior must be explicit (native providers and ACP alike). |
| BP-04 | **Agents never get storage paths or storage credentials.** The runner fetches the bytes of attachments listed in the dispatch's `DispatchContext.attachments` through the runner protocol (runner token + live lease); the server re-authorizes against the agent's conversation access at fetch time. Images go to the model as image content; other agent-readable files are copied into a per-turn, read-only directory under the turn's cwd and described in the prompt. Agents publish artifacts through a bounded MCP upload tool and attach them to their messages; the server stores and scans them like any upload. | The keys engine and membership checks stay the only gate; guarded sandboxes keep denying `WHOMBAT_HOME`. |
| BP-05 | **Uploaded content never executes in the app origin.** Files are served with `Content-Disposition: attachment` except sniffed raster images (png, jpeg, gif, webp), always with `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, private caching; the content type is sniffed from bytes, never trusted from the client; SVG/HTML are downloads only. | Same origin as the session cookie. |
| BP-06 | **Private content stays out of the audit log.** Signed events about attachments, memory, packs and automation runs carry ids, sizes, hashes and versions, not file names, file bytes, memory bodies or secrets. Deferred commands stored with approvals never carry file bytes (they reference attachment ids). | Events are append-only and visible to the whole burrow (C-10). |
| BP-07 | **Retrieved data is data.** Memory, summaries, attachment text, pack instructions and tool output enter prompts in clearly delimited sections below Whombat's own rules and are never treated as authorization. Only keys and approvals authorize. | Prompt injection must not grant permissions. |
| BP-08 | **Pack MCP tools run behind Whombat's `/mcp`.** A pack's approved external MCP server is spawned/called by the server (never by the provider), its tools are exposed namespaced through the agent's Whombat MCP session, each call is a commit-pipeline command with a key (read tools `can`-able, write tools at least `ask` unless an owner grants `can`), audited, rate-limited, time- and size-bounded, with secrets sealed by `WHOMBAT_MASTER_KEY` and injected only into that server's process. Providers keep `strictMcpConfig` / Whombat-only MCP. Runtimes that cannot be restricted to Whombat's MCP server cannot use pack tools. | A prompt warning is not enforcement; the server is the only place keys apply. |
| BP-09 | **Automations act as themselves with bounded, delegated authority.** An automation run's actions are commits by an automation principal whose authority is the intersection of its grants and the authority of the person who published the version, re-checked at every step; a trigger from a less-privileged person or an agent never adds authority; approvals bind to a hash of the exact action + input + automation version (+ commit sha where relevant). Protected merges stay human-only. | No second, less-protected mutation path. |
| BP-10 | **Durable over in-memory.** New background work (automation timers and steps, memory summaries, upload cleanup, approval re-evaluation at boot) uses DB rows with leases and fencing, idempotency keys and bounded retries; a crash leaves an explicit `uncertain`/`needs_review` state instead of a blind retry. | Existing post-commit hooks are in-memory (C-finding). |
| BP-11 | **Migrations are ordered centrally** (see PLAN.md) and take an advisory lock when applied (F). | drizzle-kit snapshots form a chain; CLI and server both migrate. |
| BP-12 | **Storage lives under `WHOMBAT_HOME`** by default: `files/` (attachments), `packs/` (installed pack versions), next to `pgdata/`; backups cover database and these directories together (F). An S3-compatible backend stays optional behind a storage interface. | Zero extra services; consistent backup/restore. |
