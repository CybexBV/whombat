# One Whombat — consoles through the session and the 0.80.1 gaps (stream CS, 2026-10-17)

Stream CS, a follow-up of `docs/implementation/one-whombat/assignment.md` under `docs/decisions/one-whombat.md` (ONE-13:
consoles in the browser) and the servers stream's ONE-DH10 (the console WebSocket proxy). Contracts 0.80.1 and 0.80.2
(CT-344…CT-351, `docs/implementation/one-whombat/contracts-0.80.1.md`). Code: `apps/server/src/hosts/console.ts`
(both ways to a console), `managed/resources.ts` (`openConsole`), whombat-app `packages/client/src/session/console.ts`
and `secure.ts` (`openConsole`), `apps/web/src/features/things/console/`.

| # | Decision | Why |
|---|---|---|
| ONE-DC01 | **A console on a managed box is a session stream** (`open{spec: {kind: 'console', burrow, sessionId, token}}`, capability `stream.console`), shaped like the collab stream: DATA both ways, credit, END and RESET; each hosts-service WebSocket message travels unchanged, framed `[u32 len][message]` (≤ 2 MiB). Not a WebSocket tunnelled through the relay, not an HTTP upgrade. | The web app on dev.whombat.com reaches the box only through the relay, inside the Noise session; streams are how the session already carries anything that isn't a request (downloads, uploads, collab). The relay sees only ciphertext, and the session's own authentication covers the console. |
| ONE-DC02 | **Superseded in part by one-person.md OP-S07**: the caller must be the person, not an owner; the rest holds. **One rule for both ways in** (`authorizeConsole`): the burrow sees servers (the hosts service is there, ONE-DH02), the person is still an owner of it (ONE-DH05), and the ticket `hosts.createConsole` issued is redeemed — the same person, the same console session, once, within 30 seconds. On the session the person is the session account's principal in the stream's burrow; the WebSocket proxy keeps its sign-in and Origin checks in front. | The session must not be a side door around the proxy's checks; one function keeps them the same. Cookie and Origin don't apply to a session (the endpoint key authenticates it end to end). |
| ONE-DC03 | **`opened` is sent only once the service's console is connected**; until then the service's first messages wait. A refusal is `error{stream_refused}` with `details.code`: `console_refused` (the ticket was used, is old or someone else's; the service answered 401/403/409), `hosts_unavailable` (no service, no token, no answer), `forbidden` (not an owner). | The client can tell “open it again” from “try later” and never sees a stream that opened and then failed for a reason it could have been told at once. |
| ONE-DC04 | **Back-pressure is credit, bounded both ways**: toward the client at most 1 MiB of the service's messages wait for session credit before the service's socket is paused (resumed under 512 KiB); toward the service a DATA chunk is credited back only after the service's socket took its messages and holds less than 1 MiB. The client opens a 1 MiB window after `opened` and credits DATA as it reaches the console. | A slow phone or a busy console must not grow memory on the box; a VNC screen update (≤ 1 MiB) still arrives in one go. The session's 2 MiB connection-wide send budget stays in force. |
| ONE-DC05 | **Closing**: the service closing normally (1000, 1001, 1005) ENDs the stream after what was queued — its `{"type":"closed","reason"}` control arrives first, as over the WebSocket; any other close RESETs it (`internal`). The client's END or RESET closes the service's socket. The client leaves with RESET `cancelled`, and answers the appliance's END with its own, so the stream is freed on both sides. A dropped connection ends the console (close 1006): it never re-attaches, since its ticket works once; “Connect again” makes a new one. | The hub's reason is what the dialog shows (“Closed after 15 minutes without typing.”); a re-attach would need a second ticket the person didn't ask for. |
| ONE-DC06 | **Keep-alive is the client's**: the hub's 15-minute idle timer counts `{"type":"activity"}` controls, which the console transport sends while a person types or moves the mouse; Whombat relays them like every other message and adds none of its own. The session's own ping keeps the connection up. | WHOMBAT.md §5: Whombat must not keep an abandoned console alive; only a person's input should. |
| ONE-DC07 | **The client API is WebSocket-shaped**: `ApplianceSession.openConsole({burrow, sessionId, token})` returns a `ConsoleSocket` (`readyState`, `binaryType`, `bufferedAmount`, `send`, `close`, `on*` and `addEventListener`, plain event objects so it runs in browsers and Hermes), or null on the HTTP transport and on a runtime without `stream.console`. Close codes: 1000 ended, 1006 lost, 1011 broken, 4003 refused, 1013 the service isn't answering; `error` holds the appliance's words. The web's `ConsoleTransport` takes it as its socket (`socket` option), so xterm.js and noVNC run unchanged on either transport; a console stream counts as work under way (the phone app won't suspend the session under it). | The console dialog was written for a WebSocket; giving it the same surface keeps one code path and lets Android use it later. |
| ONE-DC08 | **`watch.acknowledge`** (CT-349): a server alert's acknowledgement is the hosts service's (until it resolves, `hosts.ackAlert` with 0 minutes, signed with Undo, every member may), and the person's own snooze mark on it is cleared so the shared state shows; any other item is the person's own mark (`needs_you_snoozes`, `state: acknowledged`) for at most **7 days**, then it shows again if it is still there. `acknowledged: false` takes either back. | ONE-07. A connection's Watch item keeps its id across breakdowns and its time moves with every health check, so “until it changes” can't be told from the item; a week never hides a problem for good. |
| ONE-DC09 | **The hosts service being down is a 503 `unavailable`** (CT-346) instead of a 503 `conflict`, everywhere (routes, the WebSocket proxy, the session's console), `details.code: hosts_unavailable` unchanged. Over the session it is the protocol's retryable `unavailable`, so a client may simply ask again later. | Clients branch on `details.code`, so nothing changes for them; the contract now has the right code (ONE-DH11 had none). |
| ONE-DC10 | **A Servers call's words ride on the approval's action** (`ConnectionCallAction.params.words`, CT-347), written by `call.ts` from the call's own arguments and cut at 150 characters with “…”; the copy override (`ApprovalDraft.callWords`, `NewApproval.callWords`) is gone, since core's `actionCopy` now writes the same title, question and WHAT HAPPENS. | Clients derive an approval's copy from its action; with the words on it, the stored copy and the derived one agree, on the phone too. |
| ONE-DC11 | **Links into a task chat are `ChatLink`s** (CT-348): `linkOfConversation`, conversation summaries and the work overview link a DM with a task key as `{type: 'chat', id}`; the default DM stays `{type: 'dm', agent}`. | Messages, approvals and plans in a task chat opened the default DM. |
| ONE-DC12 | **Devices** (CT-345): an action's own `unit` comes first, then the reading of the same key, register or path (ONE-DD18 stays the fallback for older profiles); a reading's own `choices` come first, then the action of the same key's (ONE-DD19); the profile check refuses a reading with the same choice value twice. | The profile can now say it; older profiles keep working. |
| ONE-DC13 | **`chats.unarchive`** (CT-349): the chat's person only (someone else's chat and the default chat are `not_found`, as for archive), signed `chat.unarchived`, a no-op when it isn't archived. | Mirrors `archive_chat`. |
| ONE-DC14 | **The web's fake world has a console** (whombat-app `apps/web/src/managed/fake/console.ts`): a tiny shell behind each `hosts.createConsole` token (prompt, echo, `hostname`, `uptime`, `exit` with the reason `ended`), and a `servers(true)` switch for the managed e2e suite (`e2e-managed/console.spec.ts`: a shell opens through the session, answers typing, ends and connects again). | The session transport is only exercised against a fake appliance in the app repo; a fixture check needs something that answers like a shell. |
