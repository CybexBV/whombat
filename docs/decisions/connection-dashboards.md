# A dashboard for every connection

John, 2026-11-23: “When I click on a connection we sometimes get a dashboard (like Hetzner), but sometimes we get a
summary (like FindMy). I want (when possible) to have all connections show dashboards when we click on them by
default.” He had the connections researched (Fable 5.2, Muse Wonder Full and Opus), read the plan and said “Go” to
its first step: everything the server can do without a contract change or an app release. Pages for accounts
(Google, Microsoft 365, Email, GitHub, Website feedback) need both and come later.

What the research found: 43 of 60 catalog entries already opened on a page in slots. The rest opened on Find My's
near-empty Summary, on the generic “How it answers” page (Notion, Airtable, Dropbox, the AI gateway, the report
tracker, Custom connections without a recipe, Proxmox and Unraid), on an empty page for the first sign-in (Todoist,
Mollie, Cloudflare with “Sign in with …”), or on Settings (the accounts).

| id | decision | why |
|---|---|---|
| CDB-01 | **A kind may name the tab its page opens on** (`KindView.lead`): that tab comes first, its other tabs after it, the Summary last, and the Summary gets no answer-time slots. Both apps open the first tab, so no app changes. An app below session minor 5 still opens on the Summary. | Find My's decision said its page opens on the map (FMC-03), but the server always put the Summary first, and that Summary only had answer times for a connection that sends nothing anywhere. |
| CDB-02 | **Find My opens on its map**, then the Timeline, then the Summary (what needs a look, Changes here, What Whombat may do). | The map and the people are the dashboard; nothing new is read. |
| CDB-03 | **The page of a connection Whombat can't see inside is “With Whombat”** (was “How it answers”): its answers and answer time as before, and when Whombat last used it (“3 h ago”, “Not yet”). A Custom connection without a page also offers “What’s inside” under Show more here, which asks the assistant to build its page. | Answer times alone said nothing a person cares about. What Whombat may do already lists the tools, so they aren't repeated. |
| CDB-04 | **No uses-per-day counter for that page.** | It needs a new counter and a migration for a page few connections reach once the kinds below exist; Last used says the same in one line. |
| CDB-05 | **A report tracker's page comes from what Whombat keeps of it**, no call to the tracker: Live “Fixes on their way” (pull request open, merged, on development; linked to the pull request), Inventory “Reports” (open with new this week, open bugs, open feature requests, fixed and out to customers in 30 days), Trend reports per day, People “Who reports most” by organization (two or more), and the installation the poller reads with when it last did. A tracker no automation listens to says so instead of showing noughts. Kept a minute. | The tracker is read only by its poller; the box's mirror already has everything a person asks first. |
| CDB-06 | **A generic AI gateway's page** (LiteLLM, a company's gateway): Inventory “Through the gateway” (Claude Code and ChatGPT on or off, turns today with how many failed and how many go now, its models from `GET /v1/models`), Trend turns per day from Whombat's own turns (each keeps the provider it went through the gateway for; a burrow has one gateway, so turns since it was connected count). Models kept 15 minutes and never read by the health pass. | A gateway has no management API Whombat knows; what Whombat sent through it is the useful part. |
| CDB-07 | **Every catalog entry opens on a dashboard or is named with where it opens instead**, checked by a test (`kinds/landing.test.ts`): Custom connections (their recipe), a device (its readings page), Whombat's servers (each server's page), and the accounts (Settings, until they get pages). | A new service can't ship with only the generic page by accident again. |
| CDB-08 | **One way to read a connection's MCP tools for a page** (`kinds/mcp-read.ts`): only tools the server marks read-only, with the kinds' deadline; recipes and kinds share it. | Kinds now read through “Sign in with …” connections too. |
| CDB-09 | **Dropbox's sign-in doesn't ask for `sharing.read`**: its page shows shared links only for a sign-in that already holds it. | One more permission for one count isn't worth asking every person for. |
| CDB-10 | **A kind's read kept longer than 15 minutes stays that long** (`cachedRead`'s keep follows its own time). | Airtable's, Cloudflare's and Tailscale's hour-long reads were dropped after 15 minutes and read again. |

## Reading through “Sign in with …”

| id | decision | why |
|---|---|---|
| CDB-20 | **Todoist, Mollie and Cloudflare connected with “Sign in with …” build their page from their own MCP server's tools that only read** (`kinds/mcp-read.ts`, helpers in `kinds/mcp-tools.ts`). The token path is unchanged. | The default sign-in gave an empty page. Whombat already knows from the server's list which tools only read. |
| CDB-21 | **Todoist reads `find-tasks-by-date`, `find-completed-tasks` and `find-projects`** (all `readOnlyHint: true`). They give today and overdue for everyone, as the API's `today \| overdue` does; the next 7 days; done today and in 14 days; and project names. Their tasks are turned into the API's shape, so the token's code builds the page. Source: https://github.com/Doist/todoist-ai (`src/tools/`, `@todoist/mcp-core` `getToolOutput`). | One page, two ways in. |
| CDB-22 | **No Done button when signed in with Todoist.** Done refuses on that sign-in. | A page never changes anything through MCP tools, and the token isn't for the API. |
| CDB-23 | **Per call: 40 tasks, 50 done tasks, 100 projects. At most 3 calls per list, then “+”.** | Whombat keeps 64 KiB of an answer, and one task with a description can take a kilobyte. |
| CDB-24 | **An answer is its structured content. Otherwise it is the first line of its text that is a JSON object.** A cut answer says “answered with more than Whombat reads”. | Todoist also sends its JSON as the first part of the text. A structured answer over 64 KiB is dropped. |
| CDB-25 | **The health pass reads only the shared main part:** Todoist's today and overdue, done today and projects (projects kept 15 minutes); Mollie's newest page of payments. Only an open page reads the week ahead, the done history, Mollie's older pages and the next payout. These are kept 5–10 minutes. | The 5-minute pass must stay cheap. |
| CDB-26 | **Mollie reads `ListPaymentsFromGivenIDOnwards` and `GetNextSettlement`.** The newest 25 payments every read, and up to 4 pages back to the month's start kept 5 minutes. Past that the month says “at least”. Tool names come from Claude's connector directory (https://claude.com/connectors/mollie) and two listings made from the live server (https://neuraltrust.ai/mcp-catalog/mollie, github.com/suverenai/suveren-gateway `content/integrations/mollie.json`). Mollie's own page (https://docs.mollie.com/docs/mollie-mcp-server) lists only what the server can do. | Mollie publishes tool names, but not their arguments or answers. |
| CDB-27 | **A Mollie tool gets only the arguments its own schema names.** That is a page size (`limit`, `pageSize`, `perPage`) and a payment to go on from (`from`, `fromId`, `startingAfter`). A tool that requires anything else is left out, with one line saying why. Answers are read as Mollie API v2's (https://docs.mollie.com/reference/list-payments, https://docs.mollie.com/reference/get-next-settlement). Any other shape leaves the part out. | The server's own schema, stored at connect, is the only sure source for arguments. Check this on a real Mollie sign-in. |
| CDB-28 | **Signed in with Mollie, there are no refunds or chargebacks, and the chargeback check counts as not seen.** | Its server has no tool for them; Mollie's page says refunds aren't supported. |
| CDB-29 | **When the server offers no read-only tool for the main part** (Todoist's tasks, Mollie's payments), the page keeps its line “This page needs … connected with an API token / key”. | The tools may not be synced yet, or the server changed. |
| CDB-30 | **Signed in with Cloudflare, the page reads nothing from Cloudflare.** Under the name it says “An API token shows its traffic and tunnels here.” The Worth a look hint stays and still starts off. Its MCP server (https://github.com/cloudflare/mcp, Code Mode at https://mcp.cloudflare.com/mcp) marks only `whoami` read-only; `search`, `execute` and `docs` aren't. | The hint starts off as advice about settings (watch-defaults), so the page said nothing before. |
| CDB-31 | **Fixture pages `con_todoist_mcp`, `con_mollie_mcp` and `con_cloudflare_mcp`** show each sign-in's page. | Fixture mode shows both sign-ins. |

## Notion, Airtable and Dropbox

| id | decision | why |
|---|---|---|
| CDB-40 | **Notion, Airtable and Dropbox get kinds in slots**, one group `kinds/workspace/` (`WORKSPACE_KINDS`), fixture pages in `servicePages/workspace.ts`. | They opened on “How it answers” only. |
| CDB-41 | **Notion with a token reads its API**: `POST /v1/search` sorted by `last_edited_time` descending, `page_size` 100, never past one page; the pages and databases counted with one filtered search each (`object` `page`, `data_source`) only when that page has more; `GET /v1/users` (names, people) and `GET /v1/users/me` (workspace name) kept 15 minutes, a refusal too; the catalog's `Notion-Version` on every read; kept 5 minutes. Sources: developers.notion.com/reference/post-search, /reference/get-users, /reference/get-self, /reference/pagination, /reference/request-limits. | One search gives Live, Trend and People; most workspaces fit one page, so the counts cost nothing extra; 3 requests a second is the average limit. |
| CDB-42 | **Notion's slots**: Live “Edited lately” (10 newest, page or database, last editor, when); Inventory “In Notion” (Pages, Databases, People; “100+” past one page; “N changed this week”); Trend “Edits this week” (pages changed per day, no bar on or before the oldest read's day when more were left, “+” on the figure); People “Who edits most” (last editor of each page read, left out under two named editors). No checks. | What changed and who changes it is the glance; nothing in Notion breaks that Whombat could act on. |
| CDB-43 | **Notion signed in with Notion reads its MCP server's read-only tools**, never the API with that token: `notion-search` with an empty query sorted by last edit (arguments from the tool's input schema; `sort: "last_edited"` as documented when it has none) and `notion-get-self` for the workspace's name. Source: developers.notion.com/guides/mcp/tools-search-reference. | The default sign-in must give the dashboard; an MCP token sent to the API is refused and renewed every read. |
| CDB-44 | **A plan that can't sort by date shows “Opened lately”**: when Notion drops the sort (it says so in `notices`, and date sorting needs Business or Enterprise), or the search fails, Live lists `notion-list-recent-pages` (limit 10) and says why in its meta; no Inventory or Trend then. No read-only tools at all: one line, “Add an access token”. | Relevance-sorted results would pretend to be “edited lately”; what the person opened is true and still useful. |
| CDB-45 | **Notion's MCP answers are read defensively**: their shape isn't published, so results come from `results` (or the first list), each by id or url, title, type and a timestamp under the names the reference uses; counts from them are “at least” (N+). The health pass doesn't read through MCP; the card keeps its facts. | A changed answer leaves a line out instead of breaking the page; people's questions, not the 5-minute pass, are what those tools are for. |
| CDB-46 | **Airtable shows its bases' metadata only**: `GET /v0/meta/bases`, then `GET /v0/meta/bases/{baseId}/tables` for at most five bases the connection may read (not interface-only); signed in with Airtable, `list_bases` and `list_tables_for_base` (the base id argument named from its schema, else `baseId`). No record counts. Sources: airtable.com/developers/web/api/list-bases, /get-base-schema, /rate-limits; airtable.com/developers/agents/mcp/tools; support.airtable.com/docs/managing-api-call-limits-in-airtable. | The Free plan has 1,000 calls a month per workspace and metadata calls count; a record count means reading records 100 at a time. |
| CDB-47 | **Airtable is read only while its page is open, kept an hour** in a cache of its own (the kinds' shared cache drops everything after 15 minutes), a failure 5 minutes; the health pass answers from the last read and never calls Airtable; with nothing read yet the card keeps its facts. | At most six calls an hour while the page is open, none otherwise. |
| CDB-48 | **Airtable's bases take Live's place**: “Your bases” (each opens at `airtable.com/<baseId>`, with its tables and the connection's access) beside Inventory “In Airtable” (Bases; Tables with “+” and “In the first 5 bases” when not all were counted). | The bases are what a person comes for; Inventory alone, widened to the whole row, read empty. |
| CDB-49 | **Dropbox is one read kept 10 minutes**: `users/get_space_usage`, `files/list_folder` of the top (`path ""`, `limit` 100, not recursive) and `sharing/list_shared_links` only when the connection holds `sharing.read`. Sources: github.com/dropbox/dropbox-api-spec (users.stone, files.stone, shared_links.stone, auth.stone). | Three cheap calls; Dropbox has no account-wide “recently changed”. |
| CDB-50 | **Dropbox's shared links wait for `sharing.read`**: the catalog's sign-in doesn't ask for it, and without it Dropbox answers 401 `missing_scope`, which renews the token every read. The line shows once a sign-in holds the scope; adding it to the catalog is a separate change (the person's own Dropbox app must allow it). | No call that is sure to be refused. |
| CDB-51 | **Dropbox's slots**: Live “Changed lately” = files at the top changed in the last 30 days, newest 8, left out when none did; Inventory “In Dropbox” = Space used of the allowance (the account's, a member's share or the team's space; amber from 85 %, red from 95 %; “0.8 of 2.0 TB”), Folders at the top with the files beside them, Shared links; Trend “Space used” = GB added per day from the health pass's own point (`nas_used_gb`, as a NAS), with “Full in about …”. | Space is what people check in Dropbox; the top level is the honest cheap view of change. |
| CDB-52 | **One Dropbox check, `dropbox.space` “Dropbox is almost full”**, from 85 % (red from 95 %), with an Ask about what takes space; it starts off. | A quota nearing its limit is information until someone asks to hear it (watch-defaults). |
| CDB-53 | **Pages read MCP tools only through `kinds/mcp-read.ts`**, and a tool's arguments come only from the input schema its server published (`kinds/workspace/common.ts`: `readTools`, `propsOf`, `choicesOf`). | A page can never change anything, and never sends an argument the tool doesn't take. |

## Proxmox VE, Unraid and small fills

| id | decision | why |
|---|---|---|
| CDB-60 | **Proxmox VE and Unraid get a kind in slots** (group `kinds/servers/`, `SERVER_KINDS`). When Whombat watches the server the connection reaches (`partOfServer`), the page is that server from what the hosts service already answers (fleet card, `/servers/{id}`, its guests, kept 30 s); no call to the service's API. Otherwise the kind reads the service's own API. | Both landed on “How it answers” plus a sentence, though Whombat knows the server; one page either way. |
| CDB-61 | **Watched server: Live “Guests now”** (id `guests`, rows): an unhealthy one first, then running guests busiest first (processor as the bar, memory under the name, “up 3 weeks”), then paused, then off (greyed); at most 6, each opening the guest on the server's page; Whombat's own helper containers left out. Unraid puts a running parity check, rebuild or the mover first. | What runs now and how busy it is, like the server page's Guests. |
| CDB-62 | **Watched server: Inventory “On <server>”** (id `inventory`): VMs and Containers (how many run), the two fullest storages or the array and the two fullest pools, Backed up (the last job's guests ok of all, red when one failed, who is in no backup job), Nodes in a cluster, Shares on Unraid. | The counts the server's page has, one line each. |
| CDB-63 | **Watched server: the machine card is the server**, linked, when the page knows it as what the connection runs on; else its figures as “The machine” and Inventory links “See <server>”. Its lines: what it runs (“Proxmox VE 9.0.10”, “Unraid 7.3.1” with “Version X is out”) and how long it has been up. | One “See” link, never two. |
| CDB-64 | **Watched server: no Worth a look of its own**; the health pass reads nothing from Proxmox and skips every kind check, Unraid's reads only its small array query (its name for matching, its used space). | CDB-65 | **Proxmox VE without a watched server reads `GET /api2/json/cluster/resources`** (nodes, VMs, containers, storages in one call; templates left out; a shared storage counted once), kept 30 s, plus `GET /api2/json/version` kept 5 min. No Trend. | What Proxmox's own summary and Homepage's widget lead with; nothing per day worth a week of it. |
| CDB-67 | **Guests in no backup job** from `GET /api2/json/cluster/backup-info/not-backed-up` (Sys.Audit on `/`, which PVEAuditor has; same source), read on the page only, kept 10 min; the health pass skips its check. | It changes rarely and a token without Sys.Audit simply leaves it out. |
| CDB-68 | **Proxmox checks**: `proxmox.node_offline` (on: part of it is down), `proxmox.storage_full` (on, 85 % amber unless a terabyte is free, 95 % red: data at risk), `proxmox.no_backup_job` (off: leaving a test VM out is often on purpose). | watch-defaults.md. |
| CDB-69 | **Unraid without a watched server reads GraphQL `POST /graphql` in three small queries**: the array (state, capacity in kB, parities, disks, caches, hostname, uptime), the guests (`docker.containers`, `vms.domains`) and the rest (shares, unread notification counts, `parityCheckStatus`, `metrics` cpu and memory, `info.versions.core.unraid`), kept 30 s; a part that fails costs only itself. Source: github.com/unraid/api `api/generated-schema.graphql` (fetched 2026-11-23) and docs.unraid.net/API/how-to-use-the-api/ (`x-api-key`, `/graphql`). | A field an older Unraid lacks refuses the whole query: split, the page keeps the rest. |
| CDB-70 | **Unraid's page**: Live “Guests now” (parity check first, containers with Docker's “Up 12 days”, VMs), Inventory “In Unraid” (Array, two fullest pools, Disks with the worst, Containers, VMs, Shares), Trend “Space used” from the array's used space kept as a point (`nas_used_gb`, the NAS way, also when watched), its own processor and memory as “The machine”, lines Unraid version and Up. | Its dashboard's first screen: array, disks, containers. |
| CDB-71 | **Unraid's health pass reads only the array query** and keeps the hostname in the glance (the special case in `home/health.ts` is gone; the kind does it). | The same one small read as before, now useful for the card and the Trend too. |
