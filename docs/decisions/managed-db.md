# Managed appliance: database safety (workstream `managed-db`)

Branch `managed/db-compat`, based on main `c39f1f2`, 2026-09-25. Implements the Whombat side of the appliance
architecture's MA-10 (managed mode's migration authority) and MA-11 (updates and database safety), and gives
MA-09 (cursors/snapshots) and MA-13 (backups) the facts they need. **Supersedes BP-F18's prefix-only schema
guard** (`bp-distribution.md`): a newer schema is no longer refused as such; what an older binary may do is
decided by what the newer migrations declared.

Code: `apps/server/src/db/compat.ts` (the model, pure), `db/migrate.ts` (validation and the migration
authority), `db/backfills.ts`, `db/startup.ts`, `db/migrations/compat.json`, `apps/cli/src/schema.ts`
(`schema-check`, `migrate`), `apps/cli/src/recovery.ts` + `upgrade.ts` (legacy upgrade recovery). Tests:
`db/compat.test.ts`, `db/compat.int.test.ts`, `db/migrate*.int.test.ts`, `apps/cli/src/recovery.test.ts`,
`schema.int.test.ts`, `upgrade.int.test.ts`, `upgrade-recovery.int.test.ts`.

**Since 2026-10-23** (one-agent.md OA-20, OA-S80…OA-S84) the journal starts again at one `0000_baseline` (class
`incompatible`, its own floors) that replaced `0000_init … 0138`; the positions below count the old history, and a
database from it is refused as `foreign` with its own reason.

| MD-01 | **Schema versions are journal positions** (`0000_init` = 1 … `0027_feedback` = 28). Every migration has an entry in `migrations/compat.json`: its **class** and its **reader** and **writer floors** — the oldest binary schema (named by tag) that can still safely read, and safely write, the schema the migration produces. A schema's floors are the maximum over its migrations. The file also declares the binary's own needs (`runtime.readsFrom`/`writesFrom`, normally its newest migration) and the PostgreSQL majors it supports (`postgres.majors`, `[17]`). `compat.json` ships in releases next to the journal. | Explicit, reviewable per migration; positions make floors comparable; tags keep the file readable. |
| MD-02 | **The migration authority records each applied migration's compatibility in the database** (`whombat_meta.schema_versions`: version, tag, hash, class, readers, writers, backfill, checkpoint, applied_by), created by the authority itself like drizzle's bookkeeping, and back-filled for migrations applied before this model. An older binary judges migrations it doesn't know from these rows; a newer migration **without** a row (applied by drizzle's migrator or a pre-model build) is `foreign` and refused. `whombat_meta` is outside `public`, so backups don't carry it; a restore rebuilds it by replaying the migrations. | The old binary can't know the future; the database must describe itself. |
| MD-03 | **Classes and the rules for authors.** `expand`: additive (new tables, nullable or defaulted columns, indexes); floors strictly before it — old binaries keep reading and writing. `backfill`: a schema change plus a registered, resumable data migration (MD-05); reader floor before it; writer floor as the author decides. `contract`: removes or tightens something older code uses; floors up to itself; always needs a checkpoint (MD-06). `incompatible`: floors are itself. `legacy`: the 28 migrations written before this model, each treated as incompatible with anything older (only binaries that know them read this metadata anyway). `pg-major` is **not** a migration class (MD-09). `resolveCompat` enforces: an entry per migration, known tags, floors not after the migration, readers ≤ writers, the class rules, `backfill` naming a registered backfill, no `legacy` after a declared migration. **How to change the schema**: (1) release N: `expand` (new column nullable/defaulted, new table); code writes both old and new shapes, reads tolerate both. (2) `backfill` in N or N+1 to fill existing rows, idempotently. (3) Release N+1 (at least one release later): code stops using the old shape. (4) Release N+2: `contract` (drop the old column, add `NOT NULL`), writer floor = the first schema whose code no longer writes the old shape (or itself); a contract first repairs rows older writers wrote since the backfill (it runs with writes quiesced), then adds the constraint. Never edit an applied migration or change its entry's class or floors after release. Generate SQL with `drizzle-kit generate`, then add the entry; `pnpm test` fails without it. | Expand → migrate → contract is the only way code rollback stays safe; the rules make the unsafe cases fail CI instead of production. |
| MD-04 | **Verdicts** (`evaluateSchema`, never throws): `current`; `migration_required` (behind this binary, or a known backfill unfinished — access by `readsFrom`/`writesFrom`, normally none); `newer_compatible` (read-write); `newer_read_only`; `newer_incompatible`; `foreign` (another file at a known position, or an unrecorded newer migration); `postgres_unsupported`. Each carries `access` (`read-write`/`read-only`/`none`), the database's floors, pending and checkpoint-needing migrations, one-sentence `reason` and the exact `action`. Machine form `whombat.schema-check/1`; exit codes (`SCHEMA_EXIT`): 0 read-write, 10 migration required, 11 read-only, 12 refused, 13 checkpoint required, 14 lock timeout, 1 error. | One answer for startup, doctor, upgrade, the CLI and the appliance manager. |
| MD-05 | **Resumable backfills** are a migration class. The migration's SQL changes the schema and the authority registers the backfill (`whombat_meta.backfills`) in the same transaction; after the schema transaction commits it runs the backfill batch by batch, **each batch in its own transaction that locks the backfill's row, runs after the stored cursor and stores the next cursor** — a crash resumes after the last committed batch, two authorities never run the same batch. Batches are bounded, idempotent, data-only (no external calls). An unfinished backfill makes its migration count as not applied for binaries that know it (`migration_required`); older binaries judge by floors. A restore defers backfills until the rows are loaded, then re-runs them over the restored data (idempotent). None exist yet (`BACKFILLS = {}`). | Large data migrations must not hold the schema transaction or be lost halfway. |
| MD-06 | **Checkpoint discipline.** Contract and incompatible migrations on a database that has data are applied only with a checkpoint reference (`runMigrations({checkpoint})`, `whombat migrate --checkpoint <backup>`); without one: `CheckpointRequired`, nothing applied. The reference is recorded on those migrations' rows. **Procedure before an incompatible (or contract) migration**: (1) quiesce affected writes and external effects — self-hosted: the service is stopped (server, runner, automations, poller); managed: the manager drains to a safe boundary (no new turns, runner idle, automation engine and outbound effects paused, accepted work persisted); (2) take a consistent checkpoint inside that quiesce (database snapshot and files together, MA-13); (3) **verify** it (the upgrade re-reads the pre-upgrade backup: authenticated under the master key, every entry, and its schema history equals the database's); (4) migrate with it; (5) accept new work only once the new binary is healthy. **After newer acknowledged writes or external effects, only compatible code rollback (within the floors) or forward repair — never a silent rewind**: restoring the checkpoint then is an explicit, owner-authorized, data-losing operation, never an automatic rollback. Development boots (NODE_ENV ≠ production) and `pnpm db:migrate` pass a development checkpoint; restores pass their backup. | A narrowing migration is the point of no return for older code; the checkpoint is what makes it recoverable, and only while nothing newer was accepted. |
| MD-07 | **Startup validation is separate from migration authority.** `checkSchema` is read-only (one `read only` transaction, no lock, no DDL). `runMigrations` is the only code that changes the schema, under the existing advisory lock (`0x57484d47`), and validates under that lock exactly like startup. **Self-hosted** (`WHOMBAT_MODE=selfhosted`, default): the server's boot, `whombat start`, `whombat migrate`, restore and upgrade stay authorities (serialized by the lock). **Managed** (`WHOMBAT_MODE=managed`): the server's boot only validates; `migration_required` stops it (exit 10) — the appliance manager is the single authority. **Read-only start**: when access is `read-only` the server opens its pool with `default_transaction_read_only` (Postgres refuses every write), answers unsafe methods, `/internal/*`, `/mcp` and `/collab` with `503 read_only` ("This Whombat is read-only for now…", new `ErrorCode`), maps Postgres' `25006` to the same answer, starts no background worker (outbox drain, personal-agent backfill, poller, sweeps, automations, feedback, memory, demo) and reports `access: 'read-only'` in health (local callers and admins). Sign-in writes, so it waits too. The runner has no database access: it needs no schema validation (server↔runner protocol compatibility is a separate concern). | Old code must never write a schema it can't write correctly; reading keeps the product useful during a rollback. |
| MD-08 | **Legacy upgrade recovery** (`whombat upgrade`, self-hosted only; managed updates are the manager's, MA-11). If the new release migrated and then doesn't come up (or a backfill failed after the schema committed), the upgrade evaluates the **previous release's own** `migrations/compat.json` against the database: read-write → `current`, the unit and config.env go back, the previous release starts and must answer healthy as itself → outcome `reverted` (exit 1) with “Reverted to X, running.” and the advice to fix forward (not to restore, which would drop new writes); read-only → the same, running read-only, with both ways forward (restoring the pre-upgrade backup loses nothing then); cannot read, or cannot judge (a release from before this model, a checkout install), or the previous release also fails → **maintenance**: stopped, recorded in `$WHOMBAT_HOME/maintenance.json` (owner-only; steps in order), printed with the restore and link commands, shown by `whombat doctor` (a failing check) and `whombat start`, cleared by a healthy `whombat start` or upgrade, excluded from backups. Never silently stopped. | The old behaviour left the service stopped after every post-migration failure, even when the old release could safely run. |
| MD-09 | **PostgreSQL major upgrades are a separate class**, never a routine migration: a binary declares its supported majors; a server outside them is `postgres_unsupported` (refused at startup and by the authority) with the way forward (back up, move the data to a supported major, start again). The existing preflight (embedded `PG_VERSION` = the release's major) stays. Supported: 17 (dev, embedded, our instances). | Crossing a major is a data-directory operation with its own checkpoint and rollback, owned by the appliance (or an operator), not by `ALTER TABLE`. |

## MD-11 in detail: how the outbox, its retention and the startup bookkeeping work today

- **Table** `outbox` (0000_init): `id bigserial`, `burrow_id` (null for account-level writes), `topic`, `event`
  (jsonb `RealtimeEvent`), `event_id` (the signed audit event, if any), `audience_conversation_id`,
  `created_at`, `published_at`; index `(published_at, id)`.
- **Write**: only commits through `Pipeline.transact` (`commit/pipeline.ts`). `Session.publish` buffers frames;
  `flushOutbox` inserts them at the end of the command's transaction, so a frame exists iff the change committed.
  Burrow-scoped transactions hold the per-burrow advisory lock (`lockBurrow`) until commit; account-level
  transactions (`transactAccount`, burrow `''`) take no lock.
- **Publish**: after commit, `afterCommit` hands each row to the **in-process** `RealtimeBus` (synchronous fan-out
  to this process's hub/collab listeners), then marks the rows `published_at` in a separate best-effort update
  (a failure is only logged), then runs post-commit hooks.
- **Frames that never enter the outbox**: `conversation.unread` (mark-read hook, `publishUnread`),
  `notification.created` (`domain/notify.ts`), `typing`, `presence` (hub) — published straight to the bus.
- **Delivery**: the hub authorizes topics at subscribe time and filters `audience_conversation_id` frames
  against **current** membership at delivery; automation frames are personalised per recipient at delivery.
  Frames carry a **per-connection** `seq` (C-09), not the outbox id; after a gap or reconnect the client refetches
  (resync) — nothing is replayed.
- **Startup bookkeeping** (`drainOutbox`, `index.ts`, before listening; skipped in a read-only start): every row
  left unpublished is **marked published without being delivered** (its sockets died with the old process), and
  published rows older than **24 h are deleted**. That is the only retention: it runs at boot, so the table grows
  between restarts; nothing reads published rows.

**Why it can't serve as a replay log**: (1) crash-left rows are marked, not delivered; (2) retention is "older
than a day at the last boot", not bounded by any consumer's position and with no recorded low-water mark;
(3) `bigserial` ids are allocated at insert time inside concurrent transactions, so id order is not commit order
across burrows or for account-level writes — a reader tailing `id > cursor` can permanently skip a row that
commits later with a smaller id (inside one burrow the lock plus the end-of-transaction insert happens to order
them); (4) it is incomplete (unread counts, notifications, typing, presence bypass it); (5) rows are stored
before authorization and filtered at delivery against current membership, so a replay must re-authorize against
the reader's current rights (and `authzGeneration`); (6) payloads are the `RealtimeEvent` shape of the binary
that wrote them; (7) there is no per-session cursor or acknowledgement.

**Input for the MA-09 cursor design**: write `session_events` in the same transaction as the change, but make the
cursor **commit-ordered** (e.g. assign it under one short global lock at the end of the transaction, or read
only below a visibility horizon such as `pg_snapshot_xmin(pg_current_snapshot())` over `xid8`); decide for each
bypassing frame whether it becomes a durable event or snapshot-only; keep a recorded low-water mark and an
epoch so `after` below the mark, a restart discontinuity or a changed `authzGeneration` answer
`snapshot_required`; bound retention by age and count in a periodic job, not only at boot; authorize on read.
