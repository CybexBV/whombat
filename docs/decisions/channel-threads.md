# Agents answer in threads in channels (CH)

John, 2026-10-08, looking at his DEV box: his chat with Banjo in #general (four jobs: a Morphe patch, its APK, a patch
repository, merging and Actions settings) was 50 top-level messages without a thread, while #reports has one thread
per report. Asked what makes more sense: threads in channels, DMs and branch rooms flat, as in Slack. “yes”. Whombat
side here; whombat-app `docs/decisions/channel-threads.md` for the phone.

| # | Decision | Why |
| --- | --- | --- |
| CH-01 | **In a channel an agent answers a person's top-level message in a thread under it.** `postMessage` queues the turns a person's top-level message in a `channel` causes (a mention, RT-01's addressee) with `threadRootId` = the message; everything that follows the turn's thread follows: the runner's final text (`finalThreadOf`), “Reply in the thread (reply_in_thread …)”, “thinking” (the web's and the phone's reply row under the root, AP-735), run and approval cards (`turnThread`, RC-14), skill and schedule notes, the run's later turns (`cardThread`, VA-02). DMs, branch rooms and direct conversations stay flat; a reply in a thread stays in it; an agent's own top-level post (a handover to another agent) and system posts keep their place (handoffs have lanes, automations BP-C40). The system prompt's “Reply where you were asked” is unchanged: the turn's own line says where. | A shared channel reads as a list of jobs, each with its home, as #reports does; a one-to-one DM is already one conversation, and a branch room is about one pull request. |
| CH-02 | **Superseded in part by HN-T04 (hermes-native.md)**: every request coalesces only into a queued turn of its own thread (the top level counting as one); each top-level message that opens a thread still gets its own turn. **Each top-level message gets its own turn; a reply joins its thread's turn.** A request whose message opens its thread (`threadRootId = messageId`) never coalesces into a queued turn, and a queued turn of such a thread takes in only messages of that thread (`queueIn`). Other turns coalesce as before. | Two asks in a row would otherwise be answered together in the first one's thread, the second left without an answer under it. |
| CH-03 | **Superseded in part by chat-channel.md CHT-12**: no turn sees an earlier thread; a channel thread's opening turn still sees the channel's recent messages first. **The opening turn sees the channel and the agent's last thread with that person.** Its context carries the thread (the root) and the recent window as before; the runner shows a thread's opening turn in a channel (root = trigger) the window first (“Recent messages”, without the root), then the thread. The window also carries the last `EARLIER_THREAD_REPLIES` (12) replies of the agent's most recent thread in this channel whose root is by the same person, while that root is still in the window; each shows “(in the thread of <root id>)”. Memory's budget treats them as window messages; they don't count toward the window's candidate limit and never go into the conversation's summary. | Answers now live in threads, so a top-level “Try again” or “Do you have the APK?” would otherwise reach an agent that can't see what it did. The same person only: another person's thread isn't what they mean. |
| CH-04 | **The opening turn may fork the agent's latest warm session in the channel.** `threadFork` (TE-03) offers, for a thread a top-level message opened, the agent's most recently used active session in the conversation, whichever thread it is (else, for other threads, the top-level session as before); every other condition of TE-03 holds (same parts, warm, provider whose fork keeps the cache, context size). | With every answer in a thread, the top-level session is never used again; the latest thread's session is the warm one. |
| CH-05 | **What changes for people.** A top-level message that names nobody in a channel with other people now rarely wakes an agent (RT-02 needs the agent's answer at the top level): reply in the thread or name the agent. In a room where you are the only person RT-01 still finds the agent you named there. Thread replies don't count toward the channel's unread badge (server-core); the person who wrote the root is notified of the agent's reply (`reply`, EP-13). No migration, no contracts change. | The documented consequences of the rule, so nobody files them as bugs. |
