# Moving a Whombat to Wi-Fi: the server (NM-S)

Decisions the server stream made building network-move.md (NM-01…NM-12) on contracts 3.13 (`host.cable.set`,
`ServerMove`, `POST /v1/network/cable`) and the hosts service's `reconnecting`, `POST /hub/agents/move` and `via`
(hosts HS-220…HS-222). Code: `apps/server/src/managed/` — `host-network.ts` (the op), `network-move.ts` (pure),
`network-move-service.ts` (the servers' move), `network-move-store.ts` (`box_network`), `network-watch.ts` (the minute
watch and the Inbox source), `fake-host.ts`; `apps/server/src/hosts/hub.ts`, `service.ts`, `sources.ts` (the hold);
words in `@whombat/core`'s `network-move.ts`.

| Id | Decision | Why |
|---|---|---|
| NM-S01 | **`host.cable.set` is `host.wifi.join`'s twin**: the person's enrolled device (the `app` scope), the manager's `POST /v1/network/cable` with `confirmTimeoutSec: 120` in 15 s, an external effect (`manager.network.cable`, not idempotent), its refusals on `CABLE_ERROR_STATUS` with the cable's own code in `details.code`, a 404 manager `unavailable` (“It needs an update.”). Each change the manager took is one signed `network.cable_set` (`{use, by: 'person', via: 'app', changeId}`, the owner's account and device as actor); the event type was missing from `APPLIANCE_EVENT_TYPES` and was added to `@whombat/protocol` (additive, TS only). The box's screen doesn't switch the cable (NM “Not now”): its routes only list the codes. | One way to change the box's network, one audit chain; the contract's payload needed its event type. |
| NM-S02 | **Wi-Fi only asks the servers to move before the manager is called**: from the state read just before, Wi-Fi's address (only while it is connected with one) at the hub's agent port (`GET /hub`'s agents URL, else 8443), `POST /hub/agents/move` as Whombat (admin). No hosts service, a 404 (an older one) or any failure is logged and the switch goes on. The move is recorded only once the manager took the change. | NM-05: no gap for current agents; HS-174 covers the rest, so the move never blocks the switch. |
| NM-S03 | **The cable again is followed in the background**: the manager's state every 2 s until the change with that id is done (or, if it left the state, until a cable is in use), at most 4 minutes on this process's clock (the manager's deadline is its clock); once committed, the agents are asked to move to the cable's address and the move is recorded. A reverted or failed change asks nothing. | The cable's address exists only after the change applied; the two clocks needn't agree. |
| NM-S04 | **The move is kept 24 hours in `box_network`** (migration 0032, one row, `state` jsonb read part by part, written through the pipeline's account-level transaction under a row lock): `{from, to, since}`, `from` the box's address before (`boxAddress`: a cable in use wins, else Wi-Fi's). No settings store fitted (the appliance's row is the claim's; no key-value table), so the box's network got its own small row, which also holds the watch's events (NM-S06…). | Survives a restart; never written from a route handler. |
| NM-S05 | **`host.network`'s `move`**: a recorded move under 24 hours, else the hosts service's agents' address change (`agent_url_previous`/`agent_url_changed_at`) under 24 hours, `from`/`to` as plain IPs (none when the address is a name; `from` left out when unknown). `total` = the fleet's servers, `found` = connected ones whose `via` is `to`. Read at most every 5 s (one hub read and one fleet read, the fleet itself cached 5 s), and without a hosts service there is no `move`. | The app polls every 2 s while the Network section shows; the hosts service mustn't feel it. |
| NM-S06 | **NM-06 on Whombat's side**: while `GET /hub` says `reconnecting` (read at most every 5 s, and only when the fleet has an offline server), an offline server seen since 30 s before the hold began (the hub's own drop window) is held: its fleet row comes to no dot (as a switched-off heartbeat), so it is no look for the assistant, no desk look and no Inbox item, and its “isn't checking in” alert, if one is open, is left out of the Inbox too. Servers offline from before aren't covered. After the hold the hub opens the alerts of those that didn't come back, which flow as before (and BF-16's item asks to point them here). | The hub doesn't list whom it covers; last seen around the hold is the same set in practice. Every per-server signal (dot, look, Inbox, desk, brief) reads the fleet's verdict, so one place holds them all. |
| NM-S07 | **A watch of its own, once a minute** (`box network` on the housekeeping tick, started with the disk alerts, never in a read-only start): nothing else polled the manager's network (the desk reads it when asked, the power and disk checks read measurements). The Inbox source reads only `box_network`, never the manager. | NM-09's “at most once a minute” without a call per Home read. |
| NM-S08 | **The cable that stopped**: a cable seen in use (a link and an address, Wi-Fi only off) and now not, while the box is online and Wi-Fi has an address, is one event with the time it was first seen. Nothing while a cable change runs; Wi-Fi only chosen clears it and forgets the cable; a cable in use again ends it. Item: kind `alert`, `nature: you`, ref `box_network`/`cable_stopped:<time>`, *Open Network* (`/settings?tab=appliance&section=overview`), Settle as any item (a new loss is a new ref). | One item per event, gone when fixed either way NM-09 names. |
| NM-S09 | **The backup**: a committed cable change `by: backup` is kept by its id (the manager keeps it only 5 minutes) and is one item (ref `cable_backup:<id>`) until Wi-Fi only is on again or three days went by; Settle settles it. | The person needs to hear it once; a stale “uses its cable again” helps nobody. |
| NM-S10 | **An address change** (NM-10) is the box's address from the manager changing between two known values (an address that went isn't one), else a hosts service's agents' address change first seen within an hour. The connections that worked in their last check before it (their glance checked before the change, else the previous pass's look in memory) are checked again with the health pass's own check at the first pass at least 45 s later (≤ 50); each refused (signed out, `conn.signin`) or not answering (no answer or an error answer) is one item (ref `address_refused:<id>:<time>`, kind `connection`, *Open it*), “… It may only allow 10.100.1.81.”, until a later check finds it working. A second change before the check compares with the first one's before; one back to where it was cancels it. | Only a before/after pair can point at allow-lists; the 45 s lets leases and routes settle. |
| NM-S11 | **The three checks start on** (`box.cable_stopped`, `box.cable_backup`, `conn.address_refused`, registered in `things/quiet/defaults.ts` with why beside each). There is no Stop watching on them: the box isn't a thing with checks, and a connection's checks come from its kind; each item is one event, and Settle is enough. | watch-defaults.md WD-01 (broken now, only the person fixes it); no new thing kind for three one-off events. |
| NM-S12 | **Words** are core's `NETWORK_MOVE_WORDS` with the Whombat's own name (`desk_display.whombat_name`), else “Your Whombat”; tests check the facts (names, addresses, refs, links), not the sentences. | concise-replies.md; the app may show the same words. |
| NM-S13 | **The move as the box is now** (`currentMove` with the network `host.network` read): a recorded move while its cable change runs is shown as recorded; after it `to` is `boxAddress` now, and none once that is the recorded `from` (NM-15). The hosts service's change between an IPv4 and an IPv6 address is no move. `progress` reuses the kept state, the hub and the fleet for 5 s and applies the network each read, which `host.network` reads beside it. Counted (`moveProgress`): connected through `to` (found) or through `from` (any address but `to` when `from` is unknown), and not connected but last seen at most 10 minutes before `since`; connected without `via` or through another address, and away longer, aren't. | Home's hub picked the cable's IPv6 address at a start and then IPv4, which showed a router tip for the cable's own address for a day; the record outlived what it described. |
| NM-S14 | **The servers aren't asked to move when the manager is sure to refuse** (Wi-Fi only on already, a Wi-Fi or cable change running, from the state read just before). | Each ask opens the hosts service's 5-minute hold, which hides real “isn't checking in” alerts. |
| NM-S15 | **The cable again is followed until the cable has its address**, not given up when the change is committed first (the 4 minutes still end it). | The manager's confirmation can come before the cable's DHCP lease; the servers were then never asked back. |
| NM-S16 | **The address-change recheck waits** while a cable change runs (`cableChange` not done) and is skipped when the box is back at the change's `from` (that pass undoes it; NM-17). | A failing Wi-Fi only was checked again inside its own 2 minutes and every connection looked refused. |
| NM-S17 | **`box_network`'s row is made before it is locked** (`insert … on conflict do nothing`, then `select … for update`). | Two first writers (the minute watch and a recorded move) both read no row and the later one dropped what the earlier wrote. |

## Assumptions about the hosts service

- `GET /hub` `reconnecting` is `{since, until, reason, waiting}` or null, absent on an older service; `via` on `/fleet`
  servers is the hub-side IP; `POST /hub/agents/move {url}` answers `{asked, already}`, 400 when the URL isn't one of
  the hub's addresses, 404 on an older service. Built against the hosts service's branch for HS-220…HS-222 as it stood.
