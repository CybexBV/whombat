# Steering: a same-person follow-up joins the agent's running turn (SX)

Improvement review 2026-10-07, report A1 item 7 (stream SX, `docs/implementation/improvement-review/assignment.md`
§4.4); contracts 0.55.0 CT-305 (`ProgressResponse.inject`, `ProgressBody.injected`, `TURN_MERGED_REASON`). Before: one
turn per (agent, conversation) at a time and mentions coalescing into the next turn, so a person who added something
while the agent worked waited for the whole turn. On John's DEV box a duplicate mention waited 166 s and a follow-up
239 s in the queue (health review §2, F4).

Transcripts and scripts of the checks below: `~/.cache/wb-tmp/ir/SX/` (`transcripts/`, `scripts/steer-real.mjs`,
`scripts/codex-steer.mjs`, `codex-schema/` = the pinned app-server's generated schema, sha256 of the v2 bundle
`2719fccd…` = the fixture's).

| # | Decision | Reason |
| --- | --- | --- |
| SX-01 | **Claude Code 2.1.283 (the pinned binary) steers: a further stream-JSON `user` message written while a turn runs joins that turn.** Checked with a tiny real turn on this machine's login (`claude-haiku`, `sleep 8` in Bash): written while the command ran, it was in the next model call and one `result` (3 model turns) answered both (`real-2.1.283-during-tool.log`); written while the model produced the next tool call, it joined at the following tool boundary (`…-between-replay.log`); written while the final answer was on its way (no boundary left), the CLI first emitted the turn's `result` without it, then started it as its next turn in the same process (`system init`, a model call with it, a second `result`; `…-final-replay.log`); two written during one command joined at the same boundary (`…-two-replay.log`). Never rejected. With a `uuid` on the message the CLI reports `command_lifecycle` `queued` → `started` (the moment it joins the conversation) → `completed`, and the `result` that answered it lists it in `user_message_uuids` — without `--replay-user-messages` (`…-uuid-noreplay.log`). The provider fixture now records both cases from the binary offline (`turn.steering`: `duringCommand` answered by result 0, `afterAnswer` by result 1; `command_lifecycle` fields). | The stream-JSON input stays open for the whole turn (Whombat closes it only when the turn is over), so the CLI's own queue is the steering mechanism; the lifecycle message gives an exact, per-message delivery signal. |
| SX-02 | **Codex 0.157.0 (the pinned app-server) steers with `turn/steer`.** Its generated schema (stable bundle) has `turn/steer {threadId, expectedTurnId, input: UserInput[], clientUserMessageId?} → {turnId}` (stable; `additionalContext`, `responsesapiClientMetadata` experimental-only) and the error info `activeTurnNotSteerable` (review/compact turns). Run offline against a fake Responses API with a made-up key (no sign-in): a steer while the model call was in flight was accepted, the next model call carried it and one `turn/completed` came after answering it; during a command the next call carried the command's output, then the steer; two steers both went into the next call; after `turn/completed` the answer is JSON-RPC −32600 “no active turn to steer”. The input joins as an `item/started` `userMessage` whose `clientId` is the `clientUserMessageId`; an `image` input with a `data:` URL reaches the model as `input_image` (`codex-0.157.0-*.log`). The fixture lists `turn/steer` as used (stable); `codex/binary-steering.test.ts` runs the real binary when `WHOMBAT_CODEX_PATH` is set (passed with 0.157.0). | Both providers can, so both are built; nothing is left on “today's behaviour” except ACP runtimes and the scripted provider, which don't declare `steering`. |
| SX-03 | **A provider-neutral seam in `@whombat/agent-runtime`.** `TurnInput.steering` (`TurnSteering {open(take), close()}`) hands a provider whose `capabilities().steering` is true the follow-ups while its turn runs; `take(TurnSteer {id, prompt, attachments})` answers false once the turn can't take one any more; a new `TurnEvent` `steered {id}` says the session took it, and the provider answers it before the turn ends. `steering` is not in the AI provider panel's matrix (the contract's `ProviderCapabilities` strips it). | The runner stays provider-agnostic; each provider owns how a message gets into its session and how it knows it did. |
| SX-04 | **The runner's part (`apps/runner/src/steering.ts`).** Per message, once: its files fetched and checked as a trigger's (`prepareTurnFiles` in a folder of its own under the workspaces root, the files cache), rendered (SX-08) and handed to the provider in the order offered; one offered before the provider opened waits for it. A queued dispatch is reported in `ProgressBody.injected` while every message the server's *latest* offer names for it was delivered (`steered`); a last beat carries it before `complete` when needed. A message the provider refused, one that came after the turn closed, one cancelled with the turn or whose preparation failed is never reported. No follow-ups for assessments, reflections (and their forks), answers, briefings, automation steps, or a provider without `steering`. | Reporting per dispatch against the latest offer is what makes the server's merge safe when a person adds a second message while the first is on its way (SX-10). |
| SX-05 | **Claude: one `uuid` per follow-up, `command_lifecycle` `started` is the delivery.** The follow-up is a further `user` message (`claudeUserContent`: images and PDFs as content blocks, like the trigger) written in order. The turn ends at a `result` only once no written follow-up waits to start; a `result` while one waits keeps reading (the CLI starts it as its next turn at once; a 30 s safety grace ends the turn and the follow-up is not delivered). Each `result` is a `final` whose usage adds up all of them (cost: the CLI's running total). `result.user_message_uuids` is a fallback for `started`. A result that failed ends the turn whatever waits. | Exactly what 2.1.283 does (SX-01); the turn must not end before the provider answered the follow-up, including when a `result` arrives right after it was written. |
| SX-06 | **An answer given before a follow-up joined is posted first.** When `steered` comes after a `final` (Claude's next-turn case; Codex's `final_answer` before the steer joined, emitted as a `final` at that moment) and the agent posted nothing since its request, the runner posts that text then (`NO_REPLY` never); then the turn counts as working on a new request: “is thinking” again (reply turns), and its own final text is posted at the end unless the agent posts. | Otherwise the first answer is lost (the runner keeps only the last final text), or the follow-up's answer is withheld because the turn had posted before. |
| SX-07 | **Which turn takes which follow-up (server, `apps/server/src/runtime/steering.ts`).** A turn for a person (`on_behalf_of`), in `reply` or `run` mode, of a person's kind (`mention`, `dm`, `retry`, `approval_granted`/`declined`, `vault_pass`, `run_control`), not a search, schedule, plan-step or handoff-result turn. A follow-up: the same agent, conversation, thread and person; trigger `mention` or `dm`; never claimed (`attempts = 0`); nothing of its own (plan step, approval, schedule, retry, usage-limit requeue, search); `reply` mode — or, for a run's turn, the same run's answer (RA-DS62). Of two such turns in flight in that place (HRS-01's pair), only the one claimed last. **Run turns: yes.** A person's correction in a run's thread reaches the run's turn, which has the checkout and is doing the work. | The rule in the assignment (same person, same conversation and thread; others unchanged), and runs are where waiting cost most (turns of minutes). The run's turn is the newer of HRS-01's pair and the one doing the work (AE-04). |
| SX-08 | **How a follow-up reads**: `Mara added this while you were working (message msg_…): <text> [file: …]` / `It is part of what you are doing now: take it into account, and answer it in this turn together with the rest.`, plus `They didn’t name you; if it isn’t meant for you, carry on without answering it.` when it doesn't name the agent outside a DM (RT-05's case), plus the trigger's attachments section for its files. | The request's own wording (“Mara is asking you: …”) and the same file delivery as a trigger's; two short lines. |
| SX-09 | **Superseded in part by HN-T05 (hermes-native.md)**: a message of the person elsewhere in the conversation no longer keeps the follow-up out, as it has its own turn there (HN-T04); the rest holds. **What a queued follow-up carries**: its trigger and the same person's later messages in the turn's place that don't name only others (deleted ones left out), at most `TURN_INJECT_MAX` (8) in one answer, in order (one that can't join keeps the later ones out). A message of that person elsewhere in the conversation since, which names the agent or nobody, keeps the follow-up out entirely; so does more than 32 messages to look through. | Coalescing (unchanged) puts every later wake of the same person into the one queued dispatch, whatever the thread; merging it must not drop one the turn never saw. |
| SX-10 | **A report means exactly what was offered.** What a follow-up is offered with is fixed at its first offer and kept in memory per running turn (forgotten when the turn ends, `finalize`); later beats repeat it unchanged. The merge runs under the burrow lock, so a message the person sends meanwhile coalesces before it or after it, never in between; a message the follow-up took on after its offer (coalesced since) becomes a follow-up of its own, queued in the merge's commit (trigger, mode and run of the merged one; its first such message as the trigger), and is offered with the next beat. After a server restart nothing was offered: the next report re-offers, the one after merges. Never fails the beat (a failed beat loses the lease): problems are logged. | The runner reports dispatch ids (CT-305), not messages, and two beats can overlap or an answer can get lost; a fixed offer makes a stale report harmless without a contract change, and nothing a person wrote is merged unseen or lost. A restart costs one beat. |
| SX-11 | **A merged follow-up**: `cancelled`, `finished_at`, `error = merged:<the turn's id>` (the server-only link to the turn that took it), `DispatchSummary.reason` `TURN_MERGED_REASON` (“Answered in the running turn”, `dispatchReason`), `dispatch.updated`; operational bookkeeping in `transactAccount` like every dispatch state, no signed event; logged. No migration. | `error` already carries such codes for cancelled queued turns (`handoff_cancelled`, `run_<status>`, `unrunnable:<cause>`); a column for one link isn't worth migration 0086. |
| SX-12 | **Stop, pause, take over**: a turn that is stopping neither offers nor merges (its beat answers `cancel`), so an undelivered or unreported follow-up runs as its own turn after it. One already merged shares the turn's fate: a Stop (or pause) after that stopped it too; a crash retry or a runner restart re-runs the turn with the window, which holds it, and offers what is still queued to the new attempt. | The assignment's rule (“if the turn ends before confirming, the queued dispatch runs as today”); after confirming, the message is part of that turn. |
| SX-13 | **Codex: images as data URLs, `clientUserMessageId` = the message id, `userMessage` with that `clientId` is the delivery.** `turn/steer` names the running turn (`expectedTurnId`); a refused steer (the turn completed, or can't be steered) is simply not delivered. | In a managed turn the app-server reads `localImage` paths inside the task sandbox, which binds only the files known when it started (`sandboxTask`); the bytes are already checked by the runner. |
| SX-14 | **`runnerFetch` needed no change**: a dispatch's readable files are computed live from its place (the top-level window and the whole thread, `dispatchMessageIds`), and a follow-up is in the turn's place by SX-07, so its files are offered (`dispatchAttachments` for that message) and fetchable (int test). | One rule for what a turn may read. |
| SX-15 | **Superseded in part by HN-T01, HN-T04 (hermes-native.md)**: one queued turn per agent, conversation, thread and person, and one in-flight turn per agent, conversation and thread (a top-level turn alone in its conversation); the contracts are still unchanged. **Unchanged**: what wakes an agent and what is queued (enqueue, coalescing — still one queued turn per agent, conversation and person —, AH-01, AH-02, RT-01…RT-06), the claim (one in-flight turn per agent and conversation, HRS-01, AC-20/TE-04, RF-01), the contracts. | Steering only acts on dispatches that already exist. |
| SX-16 | **A message with more for the agent than the chat shows gets a turn of its own.** A message Whombat posts for the person with a brief for the agent (`message.agent_brief`) or as a Feedback handoff (`provenance: feedback_handoff`) is never offered: as a follow-up's trigger, the follow-up isn't offered and runs as its own turn; later in what a follow-up carries, the follow-up is offered only up to it, and the merge queues it as a follow-up of its own (SX-10), which then runs as its own turn. | Only a turn whose request is that message reads its brief or gets the report and assessment (`buildDispatchContext`); merged into a running turn it reached the agent as its one plain line. |
| SX-17 | **…and never joins a turn already queued for an earlier message.** When the person already has a queued turn in that place, such a message queues a turn of its own instead of coalescing into it (`enqueue` checks `turnOfItsOwn` for the message being queued); it joins only a queued turn whose request it already is (the merge in SX-16 then finds that turn instead of queuing a second). Two queued turns in one thread run one after the other (HN-T01); a later message of the person's joins either. | The queued turn's request is the earlier message, so the agent got the briefed message as its one plain line again. Its own turn is simpler than carrying a second message's brief in a turn whose request is another. |
