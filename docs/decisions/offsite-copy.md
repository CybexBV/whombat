# A copy somewhere else: a second place for the backups

John, 2026-11-28, in the look-after build: “Backups you can trust”: a second copy of Whombat's own backup away from
home, so a fire, a theft or a flood that takes the box and the NAS together doesn't take the backups too.

Before this the box kept its backups in one place (a NAS through a backup place, a bucket, SFTP, a USB disk or its
own disk; the appliance's `docs/decisions/backup.md`, `backup-places.md`). A backup place on the home network is the
recommended one, and it sits in the same house as the box.

Code: the appliance's backup service (`appliance/backup/internal/offsite`, `pkg/restic/copy.go`, the unit
`whombat-backup-offsite` in `appliance/nix/modules/backup.nix`), the runtime's ops (`apps/server/src/managed/backup-offsite.ts`),
the Inbox's check (`apps/server/src/home/box-backup.ts`), the shared words and views (`packages/client/src/managed/backup-offsite.ts`),
Settings → This Whombat → Backups on the web (`apps/web/src/features/settings/BackupOffsite.tsx`) and the phone
(`apps/mobile/src/managed/BackupOffsite.tsx`). The runbook is `appliance/docs/runbooks/backup.md`, “A copy somewhere else”.

| # | Decision | Why |
|---|---|---|
| OFS-01 | **The second place is an S3-compatible bucket the person owns**: Backblaze B2, Cloudflare R2, Hetzner Object Storage, Amazon S3 or any other S3 storage (the form's choice only fills in an example address and the name people read). SFTP isn't offered. | The storages people rent for this are S3; restic's `copy` shares one SSH command between both repositories, so an SFTP main place and an SFTP copy can't have their own keys. |
| OFS-02 | **The bucket is checked before it is kept**: the backup service writes a small file, reads it back and deletes it with the key (hand-signed S3 requests, no restic involved), then opens or makes the copy's repository with the main repository's password and chunker. A failure says which step in one sentence: the address, the bucket, the key, the region, write, read, delete, a folder that holds backups this Whombat can't open, the place the backups go already, or a main bucket with another key. The place the backups go already is told by restic's repository id, so another address for the same storage, bucket and folder is refused too. The check never follows a redirect: S3 names the bucket's region with one, which is asked for again at the same address; one that names none fails as the region step. Nothing is kept until every step worked. | The person types four values from another company's page; “it didn't work” helps nobody. Delete is checked because restic needs it for its locks and Whombat to clear old copies. A copy that is the main place would count the backups as copied and clear the backups themselves; a followed redirect could take the key's signed requests to another address, over plain http too (restic's own S3 client follows none). |
| OFS-03 | **One password for both**: the copy is a restic repository with the main repository's password (`restic init --copy-chunker-params`) and the same chunker, so `restic copy` moves only what is new and the recovery details' one backup key opens both. | A second password would be a second thing to lose, and a different chunker would copy everything again. |
| OFS-04 | **Copied after each backup that worked, and retried by a timer**: a backup that worked asks for a copy (`offsite-request.json`, started by its path unit); the unit `whombat-backup-offsite` has its own lock and first checks by both repositories' ids that the copy isn't the main place, then runs `restic copy` of this Whombat's own checkpoints not in the copy yet (by their ids), so it never holds up the next backup. Its own are those its backup list trusts (signed with its key, or with the key of a Whombat it was brought back from, within that one's cut-off): another Whombat's backups in the same main place are never copied, counted or cleared. With none of its own at the main place yet, a run copies nothing, isn't called a copy that worked (“nothing to copy yet”) and doesn't clear the copy. What is in the copy is read from the bucket's own list on every run, never from what was sent there once: backups taken out of the bucket by someone else are copied again, and the status (the newest backup in the copy, how many) says only what that list showed. One the copy's own clearing took out while the main place still has it isn't copied again. A 15-minute timer starts it when a copy is due: asked for, the first one, a new backup at the main place not copied yet, or a retry. Nothing is copied while a restore is going or waits for its answer. | The copy follows the backups without slowing them; a backup made at a place used before isn't copied from there. A bucket emptied or pruned by hand must not read as a good copy. |
| OFS-05 | **A failure waits before it is tried again**: 15 minutes after the first failure, doubling to at most 6 hours; Copy now and the next backup's request try at once. | A bucket that refuses the key refuses it the next minute too; a storage that is down for an hour shouldn't be asked forty times. |
| OFS-06 | **Old backups are cleared in the copy by the same keep windows as the main place**, after a copy, at most once every 23 hours (`restic forget` with the person's windows, then prune). The space limit is the main place's alone. Only this Whombat's own backups are cleared: those of its machine and of the Whombats it was brought back from (the machines of the main place's backups it trusts, OFS-04); another Whombat copying into the same folder, or keeping its backups in the same main place, keeps its backups. | The copy is a copy: it keeps what the main place keeps. Pruning a bucket costs requests, once a day is enough; the bucket's size is the person's bill there. Clearing by the product's tag alone would let two Whombats in one folder clear each other's backups. |
| OFS-07 | **A main place in a bucket and a copy in a bucket need the same key**: restic reads the S3 key of both repositories from one environment, so a second bucket with another key is refused at setup (`pair`). REST, SFTP and disks as the main place have no such limit. **Each place's certificate authority stays on its own connection**: restic's `--cacert` is one setting for both repositories, so a REST main place over https is reached through a relay on a socket in a private folder of the copy's (`pkg/restic/relay.go`) that trusts only the main place's authority (its private CA, else the system's roots), and `--cacert` is the copy's alone; the relay goes when the copy ends. An S3 main place over https with an authority the copy doesn't share is refused at setup (`pair`). | Better a plain refusal at setup than a copy that fails every night. A NAS's private CA must not vouch for the bucket on the internet, nor the internet's roots for the NAS. |
| OFS-08 | **The key is kept like the main destination's**: staged, then sealed on the box with systemd-creds (`offsite-s3-secret`), loaded only into restic's environment, never in a state file, the status, an error, a log, an event, a receipt or the assistant's input. `backup.setOffsite` is a secret op. | The same rule as every other backup secret. |
| OFS-09 | **The recovery details name the second place**: the kit material gets an optional `offsite` part (its repository, the key, the region, its repository id); older kits still work. A new Whombat joining old backups tries the main place first and the copy when that place is gone, and says which it used (`from`); joined from the copy, the bucket becomes its main place (a second place can be set up again later). The recovery tool takes `-offsite` to read the copy. | A copy that can't bring a Whombat back alone isn't a backup; the main place being gone is the case it exists for. |
| OFS-10 | **The passkey's locked copies follow**: setting or removing the second place locks the backup details again at once (the details changed), as a new destination does. A saved paper copy is out of date only once there is a second place (its digest counts the second place only when there is one), so a paper copy saved before this change stays good. | The passkey must open what brings the box back; a feature the person didn't use mustn't ask them to print again. |
| OFS-11 | **Older apps get the recovery details without the copy**: the apps read the material strictly, so the runtime leaves `offsite` out for a session below protocol minor 22. | An older phone must still bring a Whombat back from its main place. |
| OFS-12 | **The Backups page shows both places**: the top card's line under the main place (“Copy at Backblaze B2 · copied 2 hours ago”, amber while it fails, “nothing to copy yet” while the main place holds none of this Whombat's backups) and A COPY SOMEWHERE ELSE: without one, why and *Keep a copy somewhere else*; with one, where, the last copy, the newest backup in it, how many, what went wrong and when Whombat tries again, *Copy now*, *Change* (the key typed again: it never comes back) and *Stop keeping a copy* (the copies already there stay; they are the person's). The backup summary carries it as `offsite` (null: none; absent: a box from before). | One page answers “am I safe?”, now for two places. |
| OFS-13 | **What Whombat watches**: “The copy of your backups isn’t working” is one Inbox item (`box.offsite_copy`, on from the start, only once a second place is set up) after three failed tries in a row, or when newer backups have waited two days for the copy (never while the main place holds no backups: then there is nothing to copy). It says the backups here are fine and opens Backups; an Ignore lasts the episode (everything since the last copy that worked). | A second place that silently stopped is the risk the feature removes (a backup isn't happening); a single failed try isn't news. |
| OFS-14 | **The assistant reads the copy, the person sets it**: `whombat_backup`'s status names the place by its storage's name, its state, the last copy and the problem in words, never an address or a key; the assistant may copy now and asks before removing it, and can't set one up (it needs a key). | The key is the person's to type on the page; the assistant answers “is my copy fine?” and fixes what it can. |
| OFS-15 | **The bucket's address is https**: plain `http://` is taken only for a literal address on the home network, by one rule on both sides (a private, loopback or link-local IPv4 or IPv6 address: 10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, fc00::/7, ::1, fe80::/10), where a storage at home may have no certificate. The runtime refuses any other at once, the backup service refuses it too; both test the same table of addresses. | Over plain http the key and the backups would cross the internet unprotected; the main place has the same rule. |
