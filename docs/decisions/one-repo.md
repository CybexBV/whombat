# One repository for the runtime, the apps and the contracts — 2026-10-26

John asked to merge repositories. A contract change took six steps across three repositories: change whombat-contracts,
release its tarballs and tag `contracts-vX`, vendor them into whombat-app and here (`vendor/whombat-contracts` plus
pnpm overrides), release the app's build and tag `app-vX`, vendor that here (`vendor/whombat-app/PIN`), and let the
appliance's candidate read the pins. Contracts reached 3.0.0 within a month. Now one commit carries a change across the
contracts, the server and the apps. whombat-appliance, whombat-api, whombat-relay, whombat-hosts and the website stay
separate.

Merged: whombat-contracts main `96b8d6ccf71751d5bb130eeb4faf4ba333404592` (984 commits) and whombat-app main
`e3dd1af99e08fa0588bdd399571644ef501b80f7` (3,001 commits), both equal to their origin/main on 2026-10-26.

hosts service (the hub and its agents) in `hosts/`; and one private repository for control, the relay and the
maintainer tooling. Until then whombat-appliance and whombat-hosts were repositories of their own, and a release pinned
a commit of each of the three. The move comes in steps. These decisions are in force from the first one: both are
here as copies, every check covers them, and releases are still built from the old repositories.

builds the image from the folders beside it. Before, it fetched a pinned commit of this repository and one of
whombat-hosts, and every release moved both pins.

| # | Decision | Reason |
|---|---|---|
| OR-17 | **`appliance/flake.nix` has no input for anything in this repository. Each build reads a narrow copy with a name of its own** (`appliance/nix/lib/sources.nix`): the runtime bundle's source, the web app's, the pnpm store's, the hub's, the agents', each Go program's. A copy is always made from a path, never from a string that names the repository's root. Tests, stories and browser suites are in none of them. | Nix copies the whole commit before it reads the flake, and that copy is new with every commit. A build that named it would be new with every commit too, and every box would download a "new" runtime after a change to a document. Measured with `appliance/scripts/ci/source-matrix.sh`, which makes one test commit per kind of change and compares the output path of what each evaluates to: a document, a test, the phone app or an old release record changes nothing; the web app changes the web app and the runtime; the hub changes the hub and not the agents. A Go program that doesn't run its tests in its build is built without test files. A file a build needs and a list lacks fails that build at once, so a list can't be too short unseen. |
| OR-19 | **The runtime's stamp is an argument, never "this commit".** The stamp is the commit a bundle says it is and that commit's time: its version (`<package.json>-<time>.<rev>`), `gitSha`, `SOURCE_DATE_EPOCH`. `lib.applianceRelease` takes `runtimeStamp = { rev; time; date; }` and doesn't evaluate without one; `release/build --runtime-stamp` passes it and `build.json` records it (`runtime.stamp`), and the installer build, the host comparison and the upgrade gates read it from there.
