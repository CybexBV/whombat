# Settling threads in Chat and Feedback (2026-10-28)

John, 2026-10-28 (main checkout): “Research T3 Code, they use threads and ‘Settle’ to archive a thread, I want to
implement a similar approach in Chat.” He saw the mockup (`docs/design-handoff/chat-settle/index.html`) and said
“Implement it fully and I want you to use your recommendations.” T3 Code's own behaviour, with sources, is in the
research note behind the mockup: Settle there means finished work kept close by (a Settled shelf, searchable, Undo,
a new message brings it back, settling by itself after quiet days or a merged pull request), not Archive.

Contracts **3.8.0** (`ThreadSettle`, `ChatThread.settled`/`waiting`, `Message.settled`, `ChatThreadsQuery.state`,
`ChatThreadsResponse.settledCount`, `chats.settle`, `chats.settleFinished`, frame `chat.settled`,
`Preferences.chat`), migration **0014**. The app's side is `docs/app/decisions/chat-settle.md`.

| # | Decision | Why |
|---|---|---|
| CHS-01 | *The fold and the shelf in Threads: superseded by CHS-13.* **Settling puts a finished thread away; it removes nothing.** A thread of the person's Chat or Feedback room (a top-level message and its replies, CHT-02) is open or settled. A settled thread folds into one line in the room, moves to the Settled shelf in Threads, stays in search and opens as before. Its state lives on its first message (`messages.settled_at`, `settled_how`, `kept_open_at`; migration 0014) and is sent as `Message.settled` and `ChatThread.settled` (`{at, how}`). | Like T3 Code's Settle, not its Archive: put away, close by. One row per thread already exists (the root carries `reply_count`, `last_reply_at`). |
| CHS-02 | **Four ways a thread settles** (`how`): the person settles it (`person`, `at` = now); it settles by itself after `settleQuietDays` days without a message (`quiet`, `at` = its last message's time); the pull request its work opened merges or closes after the person's last message in it (`merged`, `at` = when it merged or closed); the problem the assistant looked into by itself in it went away and the person didn't write in it (`resolved`, `at` = then; contracts 3.10, migration 0016, look-research.md LR-04, LR-S24). The apps say “Settled when the problem went away”. The agent has no tool to settle. | The person decides, and the automatic rules only tidy what is clearly done. `at` = when the work ended, so the shelf orders by that. |
| CHS-03 | **Never while it isn't done.** `chats.settle`, `chats.settleFinished` and the automatic round skip or refuse a thread the agent works on (a queued, claimed or running dispatch in it) or one that waits for the person (`ChatThread.waiting`: a pending approval, a key or Vault request, or a question card in it that isn't answered). Refusals say it plainly: “{Agent} is still working on this.” / “This thread waits for your answer.” | Settling something unanswered would hide the question. T3 Code refuses the same. |
| CHS-04 | **A new message opens it again**: any message in the thread (the person's, the agent's, an automation's, a reporter's in Feedback) clears `settled_at`, `settled_how` and `kept_open_at` in the same transaction and sends `chat.settled` with `settled: null`. | New words in a thread mean it isn't finished. |
| CHS-05 | **Open again by hand keeps it open**: `chats.settle {settled: false}` (Open again, Undo) clears the settle and sets `kept_open_at`; the automatic round leaves such a thread alone until a new message clears the mark (CHS-04). | T3 Code's “active override”: a person's choice beats the timer. |
| CHS-06 | **The automatic round** runs every 15 minutes on the server's ticker, for each person's Chat and Feedback room with their `Preferences.chat` (absent: `DEFAULT_CHAT_PREFERENCES`, 3 days and merged on). It settles open threads that pass CHS-03, aren't kept open (CHS-05), aren't pinned, and meet `quiet` or `merged`; it re-checks each thread in the transaction that settles it, so a message or a person's action in between wins. One `chat.settled` frame per room with `rootId: null` when anything settled. | Server-side, so it happens with every app closed. Pinned messages are the person's way to keep something in view. |
| CHS-07 | **Superseded in part by CHS-14** (a customer's report whose fixes are live). **`merged` reads the runs of the thread**: a run whose card is in the thread (or that the thread's dispatch started) with a pull request that the GitHub mirror has seen merge or close after the person's last message in the thread. | The pull request is the end of a code thread; a later question from the person means it isn't over. |
| CHS-08 | **Settling lets go of the thread's warm Hermes session** where the runtime can do so without deleting it (the pod frees its slot; opening the thread again resumes the same session). Where that isn't possible nothing is dropped: a settled thread must answer as before when it opens again. | The pod keeps up to four threads warm (HN-09); finished threads shouldn't hold a place. |
| CHS-09 | **Settle finished threads** (`chats.settleFinished {room}`): every open thread of the room that passes CHS-03, `how: person`, `at` now; answers how many. Clear chats (CHC-01…) stays as it is. | Starting with many old threads, one action tidies them; clearing is a different thing (it hides the room's view). |
| CHS-10 | *The Threads pane's groups: superseded by CHS-13.* **Threads lists by state** (`chats.threads` `state`): `open` newest activity first; `settled` latest settled first, paged by `settled.at`; absent: all, as before. `settledCount` comes with a first page. `ChatThread.waiting` and `settled` are on every row. | The Threads pane shows Needs you, Active and a Settled shelf with its count. |
| CHS-11 | **Signed events, ids only**: `chat.thread_settled` {conversationId, rootId, how}, `chat.thread_opened` {conversationId, rootId, by: `person` or `message`}, and for a bulk or automatic settle one `chat.threads_settled` {conversationId, room, count, how}. Kind Messages. | Same shape as `chat.cleared` (CHC-06): what happened, never words. |
| CHS-12 | **The person's choices** are `Preferences.chat` (`settleQuietDays`: 1–90 or null for never; `settleMerged`), saved with `me.updatePreferences`. The apps offer a switch for “after 3 days” (on = 3, off = null) and one for merged pull requests. | Two plain choices; the contract leaves room for other day counts without a new release. |
| CHS-13 | **Settled threads leave the room.** John, 2026-10-28, after a day with folded settled threads in his Chat: “rename Threads to Settled and move them there, so they are not visible in the chat anymore.” The apps show only open threads in Chat and Feedback, and the room's head opens **Settled**, the room's settled threads (`state: settled`), where Open again puts one back. Server and contracts are unchanged: `messages.list` still sends settled first messages with `Message.settled`, and the apps leave them out of the room. Threads that Clear chats hid (CHC-01) are found with search. | A room of open threads reads as what is still going on; the open threads are the room itself, so a second list of them adds nothing. |
| CHS-14 | **A customer's report settles once its fixes are live.** John, 2026-11-18: reports #25 and #27 stayed open the morning after their last fixes went live, because a report's pull requests are an automation's, not a thread's run. A thread whose report automation's runs (`automation_runs.thread_root_id`) made fixes (`tracker_fixes.run_id`) has ended (`merged`, under the same switch) once every one of those fixes is `live` or `confirmed` where the customer is (or `closed` unmerged, one at least live) and none of the thread's runs still goes on; its time is when the last went live (`production_at`, else `development_at`, `merged_at`, the row's last change), and it counts only after the person's last message in the thread, as CHS-07. It settles in the round, so only once the person has read it (CIB-08). | The report is done when the customer has its fixes; the “live” message is the last word, and Settled's “when its pull request merged” is true of it. No new `how`, so no contract or app change. |

## The server (CS-S…)

Built 2026-10-28 on `chats/settle.ts` (commands and the round), `chats/settle-rules.ts` (pure rules),
`chats/thread-state.ts` (what a thread is doing) and migration `0014_chat_settle`.

| # | Decision | Why |
|---|---|---|
| CHS-S01 | **Migration `0014_chat_settle`** (expand): `messages.settled_at`, `settled_how`, `kept_open_at` (nullable), a check that `settled_at` and `settled_how` are set together with a known `how`, the shelf's partial index (`conversation_id, settled_at desc, id desc` over settled first messages) and the round's (`conversation_id, coalesce(last_reply_at, created_at)` over open, not kept open, not deleted first messages). An older binary never writes them, so a reply it posts leaves a settled thread settled until the next one under a newer build. | CHS-01; the two lists the feature reads, each one index range. |
| CHS-S02 | **One place opens a thread again: `postMessage`.** Every message (the person's, the agent's tools, the runner's answer, automations, Feedback and the tracker, Whombat's own notices) is posted there; a reply clears `settled_at`, `settled_how` and `kept_open_at` in the same update that counts it on its first message. When it was settled, a `chat.thread_opened` `{by: 'message'}` (signed by the message's author, no text) and `chat.settled` `{settled: null}` follow; the first message's `message.updated` already goes. A new top-level message is a new thread. A backup file doesn't carry the settle: restored threads are open. | CHS-04 without a rule in each caller. |
| CHS-S03 | **`waiting`** is true for a thread with a pending approval whose card message is in it (any action: a yes or no, a key the agent asked for, a Vault entry it wants to use, a command, a connection call), a message of the agent's with `asks` that the room's person hasn't answered by a later message in that thread (Home's Needs you rule for threaded rooms), or a guide card still open in it that isn't standing (a standing card states a setting and keeps its buttons as controls, AG-19). **`working`** stays what `ChatThread.working` was: a turn of the room's agent queued, claimed or running with the thread as its `thread_root_id`. | CHS-03; the same bindings Needs you and Home's chats read, so the Threads pane's “Needs you” and Home agree. |
| CHS-S04 | **Refusals**: `conflict` (409) with “{Agent} is still working on this.” or “This thread waits for your answer.” (working is said first; “Your assistant” when the agent has no name); the agent gets `forbidden` “Only you settle your threads.”; another person's thread, a reply, a deleted first message or a task chat's message is `not_found` (“Thread not found.”). Settling a settled thread or opening an open one answers the thread as it is, without an event or frame, so a resend changes nothing. | CHS-03; the app shows the message as its toast. |
| CHS-S05 | **`chats.settleFinished` leaves pinned threads open** and settles kept-open ones. The single Settle still settles a pinned thread. | A pin is the person's standing “keep this in view”, as for the round (CHS-06); a kept-open mark answered one settle, and asking for all of them is a new answer. |
| CHS-S06 | **Superseded in part by CHS-14** (a report automation's fixes count). **`merged`, exactly**: a run whose card (`runs.message_id`) is in the thread, or whose starting turn (`runs.dispatch_id`) ran in it, with its pull request (`repo_id`, `pr_number`) `merged` or `closed`; its time is `merged_at`, or for a closed one the row's `updated_at` (the mirror writes a pull request only when something changed, so that is when it saw it close); it counts when later than the person's latest message in the thread (any, without one). The latest such time is `at`. When both rules apply, `merged` wins. Only `runs`: an automation's pull request isn't a thread's run. | CHS-07; `closed` has no column of its own, and adding one for this alone wasn't worth a mirror change. Merged says better why the thread is done. |
| CHS-S07 | **The round**: the housekeeping job `chats.settle` every 15 minutes (the first after one period), skipped while maintenance holds the box; one commit per room of a live agent (`settle_threads_by_themselves`), signed by that agent, which reads the person's `Preferences.chat` and the candidates inside the transaction that settles them. The commit holds the burrow's lock, so a message or the person's action committed first wins and a later one waits for it. At most 500 threads per room per round, quietest first. `settleRound(services, now)` takes the time, for tests. | CHS-06; signed by the agent because nobody acted (as an old guide card expires); the lock is the re-check. |
| CHS-S08 | **Events**: `chat.thread_settled` and `chat.thread_opened` (kind Messages, where “Chat” or “Feedback”) with the texts “Settled a thread in Chat”, “Opened a thread again in Chat”; `chat.threads_settled` “Settled 4 threads in Chat” for Settle finished threads. The round's `chat.threads_settled` (one per `how` that settled anything) and a message's reopening have no text. Payloads are ids, counts and `how`/`by` only. | CHS-11; the audit log lists what the person did, not housekeeping. |
| CHS-S09 | **Frames**: every change sends `chat.settled` on the room person's `me` topic. One thread (settle, open again, a reply) also sends its first message as `message.updated` on the room's topic. Settle finished threads and the round send one frame for the room, `rootId: null`, whose `settled` is the newest settle of the batch. | CHS-06, CHS-09; `@whombat/client` reads the room and its threads again on `chat.settled`. |
| CHS-S10 | **Reads**: `Message.settled` comes on a settled thread's first message wherever messages are built (`loadMessages`: the timeline, threads, frames) and is absent while it is open (clients replace a message whole). `ChatThread.settled` is null while open and `waiting` is on every row. `chats.threads` `state: open` lists unsettled threads by last activity; `settled` by `settled_at` then id, newest first, `before` and `next` on `settled.at`; absent lists all as before. `settledCount` comes with every page without `before`, counted with the same room and subject; a room that doesn't exist answers 0. | CHS-10. |
| CHS-S11 | **No Hermes session is let go (CHS-08's “where that isn't possible”).** A turn holds a place in the person's Hermes only while it runs (one `hermes acp` per turn, released at its end); between turns a thread's session is files in the profile's `sessions/`, and the runtime's only operation on a session is `sessions.delete`, which would make the thread forget when it opens again. Settling doesn't touch sessions; an opened thread resumes the same one. | Nothing warm is held by a finished thread, so there is nothing to free. |
| CHS-S12 | **`me.updatePreferences` stores `chat` whole** (it kept only the fields it knew). | CHS-12. |
| CHS-S13 | **`ApplianceInfo.hermes`** (hermes-updates.md HU-02) is filled per `appliance.status` from the runtime's runner reports (`setupStatus().hermes`: a ready runner wins): `{version}`, cut to 64 characters, while Hermes is ready there, else null. Not one of the manager's facts. | The runner already reports it in every heartbeat; a stopped runner shows “Not known yet”. |
