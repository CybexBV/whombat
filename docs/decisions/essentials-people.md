# Essentials: people and notifications (stream R3)

Items 10 (offboarding people, retiring agents) and 12 (notifications people control: server rules, levels, DND and
quiet hours, `@channel` / `@here`, thread replies, direct messages, email, VAPID keys in the CLI) of
`docs/implementation/essentials/assignment.md`, on contracts 0.26.0 (CT-175…CT-177, CT-182). Migration
`0053_people_notify`.

| # | Decision | Why |
|---|---|---|
| EP-01 | **Superseded in part by one-person.md OP-S02, OP-S08**: principal rows still stay for the signed history, and people have no `removed_at`. **Principal rows stay.** `principals.removed_at` (people) and `retired_at` (agents), nullable. The API shows `Person.removedAt` / `Agent.retiredAt` only when set; `isActiveRow(row)` (read/principals.ts) is the server's `isActivePrincipal`. `Bootstrap.principals` keeps everyone, so history names them (“former member”, “retired”); clients filter pickers with `isActivePrincipal`. | Signed history names its actors; a deleted principal would orphan every event and message. |
| EP-02 | **Superseded by one-person.md OP-S08**: nobody is removed. **Removal ends access at once, for that burrow only.** `burrowAccess` (REST, the `/ws` upgrade, managed `api` ops, file routes) refuses a removed person (403); the commit pipeline refuses a removed actor and a retired agent; after the commit a bus control `principal.removed` closes their sockets (4403 `removed`), canvas connections and managed session subscriptions, and the hub's heartbeat re-check closes any a removal in another process left open. Every account→person lookup that means “member” filters `removed_at` (memberships, managed events and dispatcher, push resolve, the appliance principal summary, profile updates, usage overseers, guides, AI-client managers). The account's other burrows are untouched. | “Sessions for this burrow stop working at once, sockets closed”; sessions are account-wide, so the burrow check is the cut. |
| EP-03 | **Superseded by one-person.md OP-S03, OP-S08**: nobody is removed, and `members.list` is gone. **Lists and pickers leave them out; history keeps them.** `members.list`, `agents.list` (roster), the sidebar's agent count and DMs, server mention resolution (`mentionTargets`: `@Tom` of a removed Tom stays text), the agents' “People / Agents” facts in the dispatch context. Adding a removed person or a retired agent to a conversation is refused (“Tom isn’t in this burrow any more.”, “Banjo is retired.”), and a retired agent can't be configured (keys, channels, runtime). | The same rule everywhere a principal is chosen. |
| EP-04 | **Retiring an agent** (`agents.retire`, owners and the person who hired it, never a personal assistant or a system principal): status idle, `channel_ids` emptied, live and queued turns cancelled (`error: agent_retired`, its MCP token dies with them), live or paused runs failed (“Banjo was retired.”, a signed `run.finished` by the person), grants deleted (`grants.updated []`), Vault keys and passes taken (a signed `vault.key.taken` each), its requests withdrawn (EP-08), it leaves every conversation but its DMs. Signed `agent.retired` (Keys): “Retired Banjo”; with its owner “Retired Wren with Tom”. Name and handle stay taken (`assertAgentNameFree` and `uniqueHandle` see every principal). | CT-177 and the assignment's list; one transaction, so nothing half-retired is ever visible. |
| EP-05 | **A retired agent's DM stays readable but closed.** It keeps its membership there; posting answers 403 with `retiredAgentText` (“Banjo is retired. You can still read this conversation.”); `open_dm` returns an existing DM but never starts one; `enqueueDispatches` never wakes a retired agent; the sidebar leaves the DM out (it opens by link, search and history). | Readable history, no way to talk to something that no longer works. |
| EP-06 | **Superseded by one-person.md OP-S08**: nobody is removed. **A removed person's Vault entries in that burrow go** in the removal's transaction (a signed `vault.entry.removed` each, neutral text, by whoever removed them; bridges evicted, browser sessions closed). A team agent running on their own sign-in stops finding it (`credentialOwnerOf` sees them as not present). | VT-06 / VT-D18: nothing of theirs survives them; the tables cascade only on a row delete, which never happens now. |
| EP-07 | **Superseded by one-person.md OP-S08**: nobody is removed, so no removal revokes devices. **Managed boxes revoke the account's devices** when a removal leaves the account in no burrow on the box — never an owner of the appliance (`admin_since`: they administer the box itself). Each revocation is a signed appliance `endpoint.revoked` with `reason: member_removed`, actor the remover's account, sessions closed through `endpoint.revoked` / `authz.changed`, reported to control like any revocation. Wired through `onPersonRemoved(services, hook)` (domain/offboarding.ts), which the managed runtime registers. | Revoking an account still in another burrow here would lock them out of it; the last-owner invariant (MA-19c) must hold. |
| EP-08 | **Superseded by one-person.md OP-S08**: nobody is removed, so nothing is withdrawn or stopped for them. **What stops with them.** Requests they (or their assistant, or a retired agent) asked for that haven't happened — pending, or approved but not run (`execution.state` idle, `executed_at` null) — read as declined by whoever made the change, with a signed `approval.declined` “Withdrew request #12: Dusty was retired” (the number, never the title: a personal agent's titles are private); pending Vault pass requests with them; nobody is woken. Turns working for a removed person stop: live dispatches on behalf of their account in the burrow and every turn in their DMs (`error: member_removed`), and those turns' runs. | The assignment's “approvals they asked for are cancelled”; approvals have no `cancelled` state, and `declined` is what every client already renders as “it didn't happen”. |
| EP-09 | **Superseded by one-person.md OP-S07, OP-S08**: there are no roles, and nobody is removed or leaves. **Roles** (`members.setRole`): owners only; the same role again changes nothing (no event); at least one owner always (`canSetMemberRole`); a signed `member.role_changed` (System) “Made Priya an owner” / “Made Priya a member”, payload `{principalId, from, to}`. Refusals: “Only owners change who is an owner.”, “You’re the only owner. Make someone else an owner first.”. `members.remove`: “Only owners remove people from the burrow.”, “You’re the only owner. Make someone else an owner first, then leave.”; the text of `member.removed` is “Removed Tom from Burrow HQ” or “Left Burrow HQ” (payload `scope: 'burrow'`; the conversation-level `member.removed` has a `conversationId`). Both run under the burrow lock, so two owners can't each remove the other. | Core's rules, with sentences a person can act on. |
| EP-09a | **Superseded by one-person.md OP-S03, OP-S08**: there are no invites, and nobody is removed. **Coming back.** A removed person can be invited again; accepting restores the same principal (`removed_at` cleared, the invite's role), their DMs with agents and their personal assistant (un-retired, with the default personal keys). Channels don't come back: like any new member they start in #general. | The unique `(burrow, account)` principal and the signed history are theirs; a second principal would split them. |
| EP-09b | **Direct conversations keep a removed person's membership row.** The member set of a `direct` conversation is fixed and names its title, so the others keep reading it with the former member named; the removed person reaches nothing (burrow access) and gets nothing (EP-14). Every other conversation (channels, branch rooms, their DMs with agents) drops them. | “Their direct conversations stay readable to the others.” |
| EP-10 | **Levels are per member row**: `conversation_members.notify` (`all` / `mentions` / `none`, null = `defaultNotifyLevel(kind)`). `conversations.setNotify` is a pipeline command for people who are members, private like read markers (no signed event), and publishes `conversation.notify` to the viewer's `me` topic. `ConversationSummary.notify` and `ConversationDetail.notify` always carry the level in effect. Leaving a conversation forgets the level. | The membership row is exactly “this person in this conversation”. |
| EP-11 | **One entry point decides who a message notifies**: `notifyForMessage(services, {burrow: {id, slug}, messageId, addedMentions?, notifyMentions?, notifyDmPerson?})` (domain/message-notify.ts), run after the post's commit (`postMessage` calls it). It loads the message, the people who are members and not removed, their levels and `threadReplies`, and decides with core's `notifyReason` (the pure plan in message-notify-rules.ts). Every row carries the dedup key `msg:<messageId>`: one notification per person and message, ever. **Edits (R2):** after committing an edit, call it with `addedMentions` (core `addedMentions(before, after)`): only those people, newly mentioned, get a `mention` — once, even if the edit repeats. | One rule for post and edit; the dedup key makes “notifies them once” hold across edits and processes. |
| EP-12 | **`@channel` / `@here`** are read from the text with core `parseBroadcast` (not from R2's stored `Message.broadcast`, so the rule doesn't depend on the column), and count only in a person's message: an agent's broadcast notifies nobody beyond their levels, and never wakes an agent. `@here` asks `presenceFor(services).activeAmong(ids)` (realtime/presence-tracker.ts): the last `presence` frame each principal's clients sent on the bus, `active` only. It is the boundary R2's presence work plugs into. | Agents shouldn't be able to page a whole room (prompt injection, loops); presence has one reader. |
| EP-13 | **Kinds.** A mention or broadcast is `mention`; a reply in a thread you're in (you wrote its root or a reply, or were mentioned in it) is `reply`; a direct conversation's message is `direct`. At `all` elsewhere: a thread reply is `reply`, an agent's message `agent_update` (in its DM with “Direct” as before), a person's message `direct` (“Message · #general”). Managed content-free push maps `reply` to `message` (it isn't a mention). | `NotificationKind` has five members; these read right in the inbox sections and push titles. |
| EP-14 | **Quiet time holds push back; the inbox still fills.** `notify()` looks up each recipient: nobody removed (or retired) gets a row; for someone in Do not disturb or quiet hours (their zone, else the burrow's, else UTC; `isQuietNow`) the row and its `notification.created` frame go out, push (web push, FCM, APNs and the managed control request) doesn't — needs-you items included. Nothing is pushed later when quiet ends; the email covers what stays unread. `notifications.message_id` records the message a row is about. `me.updatePreferences` stores `notifications` whole (days de-duplicated). | CT-175: “DND and quiet hours hold back push and email; they end on time.” |
| EP-15 | **Email.** A worker in the server (every 5 minutes; not in a read-only start; only when email works, EP-16) sends each account at most one plain email: unread rows 30 minutes to 24 hours old, not emailed yet, of kinds `mention`, `direct`, `reply`, `needs_you` and an agent's message in a DM; left out: a message read in its conversation (top-level, read marker), a message that is gone or in a conversation they left, a request someone decided. `hourly` (default): 60 minutes since the last; `daily`: from 08:00 in their zone, once that day; never in DND or quiet hours; `off`: never. Rows and the account's `notifications_emailed_at` are claimed under a row lock before sending, so two processes never send the same item. Up to 10 items (“…and 3 more in your inbox.”), each with its quote and an absolute link (`PUBLIC_URL` + `linkPath`), “Open Whombat”, and the way to change or stop it: **`/{burrow}/settings?tab=notifications`** (the web's Settings → Notifications must use `tab=notifications`). | Short, safe to send twice-never, and quiet by the same rules as push. |
| EP-16 | **Capabilities** (`Bootstrap.capabilities`, added by the bootstrap route): `emailNotifications` = self-hosted with `SMTP_URL` (development defaults to Mailpit, so true there); `webPush` = self-hosted with both VAPID keys. Managed boxes: both false (no mail; push goes through control and the app's own settings). | Settings → Notifications shows only what works here. |
| EP-17 | **VAPID keys in the CLI.** `whombat init` writes a P-256 pair (node:crypto, base64url, the encoding web-push and browsers use) into config.env's new “Web push” section unless the file already mentions VAPID; `whombat start` adds a pair once to a config.env that has none (appended under “# Added by whombat start on …”, mode 600) and logs one line. A file that mentions VAPID at all — keys, `VAPID_PRIVATE_KEY_FILE`, or empty values — is left alone: `VAPID_PUBLIC_KEY=` is how someone turns web push off. `whombat doctor` gains `push` (ok; warns when missing or off; fails for half or broken pairs). There is no `doctor --fix`. | Self-hosted web push out of the box, without ever replacing keys browsers subscribed with. |
| EP-18 | **Migration `0053_people_notify`** (`expand`, floors `0047_delegation` per UI-R17; after `0052_essentials_agents`, 0053 is R2's): the principal, member, notification and account columns above plus a partial index for the email scan. Old binaries ignore them: a removed person or retired agent looks active to them, a level reads as the default. | Additive only (the production box has no backup destination). |
| EP-19 | **The wake paths of essentials-agents (EA-07, EA-09) respect it.** `wakeQuietly` (a yes's `approval_granted` turn, a Vault pass) returns null for a retired agent and for a turn whose person (account) is no longer in the burrow; `dispatches.retry` answers 409 for a retired agent's turn (“Banjo is retired.”) and for one working for a former member (“The person this was for isn’t in the burrow any more.”), and the Work view doesn't offer `retry_turn` for a retired agent. A removal cancels the `approval_granted` turns already queued for the person (they are on their behalf, EP-08). | Every way to start a turn follows the same rule. |
| EP-20 | **Retired means retired everywhere (2026-10-02, John: retired agents were still offered in a Vault entry's “Give a key to…”).** An audit of every place that picks or lists agents found these gaps, now closed. **Vault:** `eligibleAgentIds` leaves retired agents out, and `vault.giveKey` refuses one through `vaultKeyHolderProblem`'s new `retired` code (contracts 0.39.1, CT-240), “That agent is retired, so it can’t hold a key.”. **Licence:** `countTeamAgents` (the hire limit and the usage the box reports) doesn't count a retired agent; its name stays taken (EP-01), its place is free. **Teammates** (DG-06) are active principals only, so no turn is offered a retired agent or a former member to hand work to. **Automations:** `dispatchableAgent` is null for a retired agent (publishing names the step, a run blocks it), and a former member can't be an approver. **GitHub:** `ciReporter` skips retired agents; the mirror signs as GitHub whatever a retired agent or a former member would sign (`canSign`: the pipeline refuses them, which broke mirroring), and a retired agent's last push is GitHub's with a commits card; recorded authors (`authorId`, commit authors) stay. **Needs you:** a retired agent's `asks` questions leave it. **Refused targets:** memory for a retired agent (403 “Banjo is retired.”), its provider sign-in source (as `agentByHandle`), a reviewer condition naming a retired agent or a former member (400), and key-request approvers / approval routing skip former members. **Feedback:** `agentProblem` treats a retired assessor as `agent_missing` (the integration's health and a blocked assessment say it is gone, not “add it to the channel”). **Computers:** `removeRetired` at boot and hourly removes what retirement's one `remove` couldn't (computerd down). | A retired agent kept a licence place, could be handed a key, a handoff, an automation step or a review, and broke CI mirroring; the actor check in the pipeline only covers who acts, not whom an action targets. |
| EP-21 | **Retiring takes what the agent still had (2026-10-02).** `retireAgent` now also: stops every handoff the agent owns that still awaits its first result (`stopRetiredOwnersHandoffs`: step `blocked`, label “Owner retired”, note “Banjo was retired. Reassign or cancel it.”, `handoff.stopped: 'retired'` — a server-only value, not in core's `HandoffStop`; the delegator woken once as for any stop; done before turns are cancelled, so the step says why); rejects its pending skill proposals (the existing `rejected` state, decided by the person retiring it, their needs-you rows settled); detaches every pack attached to it, its own pack too (`detachAgentsPacks`, a signed `pack.detached` each; tool approvals, skill switches, pack secrets and Vault bindings go with the attachment row); deletes its “Always allow” commands. `agent.retired`'s payload (no schema) counts `handoffsStopped`, `proposalsRejected`, `packsDetached`, `allowancesRemoved`. Refused for a retired agent: `decide_skill_proposal` (403), every pack configuration through `assertMayConfigure` (403), Retry of its handoff (409; Reassign works); removals (`detach_pack`, `revoke_pack_tool`, `clear_pack_secret`) still work. A restored assistant gets no packs back. **Agents retired earlier** are settled at boot (`settleRetiredAgents`, domain/retired-settle.ts): every retired agent with a pack, an allowance, a pending proposal or an open handoff gets the same steps in one `settle_retired_agent` commit, signed by whoever retired it, else the first owner still here; no new event type (each step signs its own), idempotent. | Retired agents kept packs (DEV: Pippa 10, Pepper 1), and a handoff to one stayed open forever. |

## For the other streams

- **R2 (edits):** after an edit commits, `notifyForMessage(services, {burrow, messageId, addedMentions})`. Deleting a
  message may leave its notification rows; the email already skips rows whose message is gone. When
  `messages.deleted_at` lands, add `m.deleted_at is null` to the email's message check (mail/digest.ts).
- **R2 (presence):** `presenceFor(services)` is where `@here` reads presence; make it the store behind
  `Bootstrap.presence` (or replace its internals) rather than a second one.
- **Web (W3):** Settings → Notifications at `?tab=notifications` (the email's link).
