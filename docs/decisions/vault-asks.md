# Where an agent asks to use a Vault entry (VA-01)

John on DEV (2026-10-03): “When Banjo needs approval for Vault access, then my assistant shows this … This is annoying,
because I have to exit the thread I was working in. Can we let Banjo ask for access instead in the thread?”

| ID | Decision | Why |
| --- | --- | --- |
| VA-01 | **Superseded by one-person.md OP-S62, OP-S72**: every room is the person's, so a Vault ask lands where it was asked. **In the owner's own turn, in a room nobody else reads, the agent asks right there.** When the turn is the entry owner's (`requesterIsOwner`) and no other person can read the room it runs in (a DM, a direct conversation or a private channel whose only person member is the owner; a public channel or branch room whose burrow has no other active person), the `vault_use` card goes into that room, in the turn's thread, posted by the asking agent itself: “I’d like to use a private Vault entry of yours for one turn.” (on its computer: “I’d like a private Vault entry of yours on my computer for one turn.”). Everything else stays VT-31: the owner alone decides, the approval is private, only the owner's card names the entry, the pass wakes a turn in the same place. Any other turn (someone else's, or a room others read) still asks in the owner's DM, as their personal agent. In such a room an owner without a personal agent can now be asked too (`ownerReachable`). | The person asking is right there; leaving the thread to answer was friction. VT-31's rule “the card never reaches a room others read” still holds. Someone who joins the room later sees a card they can't open (the approval is private, the entry unnamed). |
| VA-02 | **A run's turn stays in the thread it was asked in.** A run started in a turn with a thread but no message of its own (a woken `vault_pass` turn) gave its run turn no thread (`continueInCheckout` kept the thread only with a message), so that turn's Vault ask, the pass turn it woke and the next run card landed in the channel. Now the run turn takes the starting turn's thread whatever woke it; an approved run's turn takes its card's thread (it had none); Resume, a stalled run's wake-up and Try again use the starting turn's thread, else the run card's (`cardThread`). | John on DEV: “Banjo posted a card in the channel instead of in the thread, this should not happen when we are talking in a thread.” |
| VA-03 | **A run turn's yes goes to a turn of the same run.** When the turn that asked was a run turn (mode `run`) and its run is still live, the owner's yes wakes a `vault_pass` turn of that run (mode `run`, `runId`, so it gets the run's checkout), coalescing only with a queued turn of the same run; its prompt says “Carry on with your run #N (title) where it stopped; don’t start a new run.” Otherwise as before (VT-D26: a plain `vault_pass` turn where it asked). The pass still lasts one turn (VT-30). | John on DEV: “I had to give many permissions during a session.” Each yes woke a plain turn without a checkout, so Banjo started a new run there, whose turn asked again: eight runs and eight asks for one job. |
