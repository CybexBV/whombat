| MR-06 | **Durable commands** (`managed/receipts.ts`, `commit/scope.ts`). Every mutating op is a command keyed `(principal, op, requestId)` (principal = account id, or `peer:<PeerId>` unenrolled) in `command_receipts`, bound to `requestDigest(op, input)`. States `received → accepted → completed \| rejected`, or `not_executed`. The handler runs inside an `AsyncLocalStorage` command scope; **every commit-pipeline transaction of it calls the scope just before it commits, in the same transaction**: before the first commit a cancelled request or passed deadline throws (rollback, nothing executed), else the receipt becomes `accepted`; after the commit the session sends `accepted{id, at}`. The outcome (`result` or the error) is stored when the handler returns. A retry with the same id and digest replays it; one still running in this process joins it (one execution); `accepted` without an outcome (the process died after commit) answers `outcome{state: accepted}` — never re-executed; `received` without a live execution (died before any commit) runs again; another digest is `idempotency_mismatch`. Validation/permission errors are final for the id; `internal`, `unavailable`, `rate_limited`, `too_many`, `cancelled`, `deadline_exceeded` leave it `not_executed`. `status{id}` answers the newest receipt of the id (`not_found \| executing \| accepted \| completed \| rejected`, digest, outcome). Retention: finished receipts are deleted after `WHOMBAT_COMMAND_RECEIPT_HOURS` (default 7 days, swept every 5 min); `accepted` ones stay. **Cancellation after accept** is best-effort by a follow-up command, per area: `runs.*` → `runs.pause`/`runs.takeOver`; `approvals.decide` → `approvals.undo` until executed; `automations.runNow` → `automations.cancelRun`; `uploads.create` → `uploads.discard`; messages, reactions, burrow/agent/pack/memory settings → a compensating edit (no retraction of a sent message); enrollment and owner changes → the opposite op (revoke, `admins.revoke`). Limits: one server process per appliance (the in-flight map is per process); a handler that commits several transactions is accepted at the first and a crash between them leaves what REST would; a mutating op that writes nothing through the pipeline is accepted when it returns. | MA-09: `accepted` means committed; retries never duplicate; nothing claims exactly-once external effects. |
