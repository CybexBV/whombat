# Workstream: the browser (BT)

Workstream `agent-capabilities` (2026-09-28, John: “give the agents a web browser, Playwright for example, headless”;
assignment `docs/implementation/agent-capabilities/assignment.md` §3). Agents open pages, read them, click, type and
take screenshots in a headless Chromium that **Whombat** runs — never the agent's sandbox — and sign in to websites
with logins kept in the Vault without ever seeing the password.

Contracts 0.20.0 (CT-119…), runtime migration `0048_capabilities`, app 0.11.0 (AP-195…), appliance candidate 0.18.0
(IN-87…, NX-94…). Binding and unchanged: ASR-02 (the web key is the exfiltration path, off by default), BP-06 (no
private content in signed events), BP-07 (retrieved data is data), VT-01…VT-23, VT-D22, VT-D27, PA-01…PA-10, MR-44.
Related: `vault.md` VT-D28…VT-D35 (the `login` kind), `skills-library.md`, `agent-roles.md`.

## Decisions (the assignment's requirements, settled)

| # | Decision | Why |
|---|---|---|
| BT-01 | **A browser host process, not the server and not the agent sandbox.** Self-hosted: a child process of the server (`apps/server/src/browser/host/`, entry `main.ts`, bundled as `browser-host.mjs` in a release), Playwright (`playwright-core`, pinned; no browser download at install) driving headless Chromium: `WHOMBAT_BROWSER_BIN` when set, else Playwright's Chromium under `WHOMBAT_HOME/browser/` (`whombat browser install`). The server talks to it over a unix socket `WHOMBAT_HOME/run/browser.sock` (directory 0700). Appliance: a `whombat-browser` systemd unit under its own uid runs the same entry against the kiosk's `pkgs.chromium`, socket `/run/whombat-browser/host.sock` (0660, the browser's group, which the server user is in), its own cgroup with memory and pid limits, restarted on crash; the server connects to `WHOMBAT_BROWSER_SOCKET` and never spawns. A crashed page or host never takes the server down; while the host is unavailable every browser tool is refused with a plain reason (“The browser isn’t available on this Whombat right now.”). | A page is hostile input: it runs in its own process (and on the appliance its own uid and wall), and the model never touches Chromium. |
| BT-02 | **Key `browser.use`**: label “Use a web browser”, description “Open pages, click, type and take screenshots in a browser Whombat runs.”, group `research`, `agentMaxTier: can`, `implies: ['web.browse']`, off by default. A row right after “Browse the web” in the hire modal and Configure (both use core `hireKeyOptions`). Default `can` only for the Tester (AR-05). Personal agents never hold it (`personalAgentMayHold` stays without web keys, ASR-02 + PA-07). | Same reasoning as ASR-02: a browser plus read access is an exfiltration path, so an owner switches it on deliberately. |
| BT-03 | **Tools** — MCP tools behind `/mcp` (`BROWSER_MCP_TOOLS` in core `contracts/mcp-browser.ts`), each `requiredKey: 'browser.use'`, each a pipeline command that signs a hidden event `browser.used` (`kind: System`, `text: null`, payload `{tool, origin, dispatchId}` — the page's origin only, never path, query, typed text or content): `browser_open {url}`, `browser_snapshot {}`, `browser_click {ref}`, `browser_type {ref, text, submit?}`, `browser_press {key}`, `browser_select {ref, value}`, `browser_scroll {ref? , direction?}`, `browser_wait {text? , ms? ≤ 10 000}`, `browser_screenshot {attach?}`, `browser_back {}`, `browser_close {}`, `browser_sign_in {entry}` (BT-06). Actions answer the page's new state (URL stripped of query and fragment, title, origin, a short note) and, for `open`/`back`/`click`/`press` that navigate, a fresh snapshot. `browser_snapshot` answers an accessibility tree with element references `@e<n>`, ≤ 64 KB, cut with “[cut: the page is longer; scroll or snapshot a part]”. Activity rows are kind `web`: “Opened example.com” (object = the URL without query and fragment) for `open`/`back`, “Used the browser on example.com” for the rest; typed text, selected values and `sign_in` never reach evidence (sign-in rows read “Used a private Vault entry”, VT-D-rule). | One tool per action keeps each call small and auditable; refs from the accessibility tree are what models handle well (Playwright MCP's approach). |
| BT-04 | **Sessions**: one browser context per dispatch, created on the first tool, closed when the turn ends (`RunnerRuntime.finalize` and the orphan sweep `interruptOrphans` tell the host `close`), when cancelled, on `browser_close`, or after 5 minutes idle; cookies and storage discarded, no persistent profile, no service workers, downloads accepted into memory only. Caps: 40 navigations per turn (`WHOMBAT_BROWSER_MAX_NAVIGATIONS`), one context per turn, `WHOMBAT_BROWSER_MAX_CONTEXTS` per host (4 self-hosted, 2 on the appliance; a full host refuses “The browser is busy with other agents; try again in a minute.”), a 30 s deadline per call, 2 pages at most per context (popups replace the current page). **Downloads** become attachments: each download during a call is taken from the host (≤ the upload size cap), sniffed and published with `publishArtifact` as the agent into the turn's conversation (the `upload_file` path), and the answer lists `{attachmentId, name, size}` so the agent can attach it to a message. Nothing downloaded runs or opens. No file uploads into pages in this version (file choosers are dismissed with a note). | Throwaway contexts leave nothing behind between turns or agents; the upload path already enforces quotas, sniffing and membership. |
| BT-05 | **Destinations are checked at connection time by a filtering proxy inside the host.** Every context is created with its own proxy credentials (Playwright `newContext({proxy})`, the browser launched with the same proxy, `--proxy-bypass-list=<-loopback>`, QUIC off, `--host-resolver-rules` mapping everything to NOTFOUND so Chromium never resolves a name itself, WebRTC non-proxied UDP off, extensions, sync, background networking, DNS prefetch and component updates off). The proxy resolves each CONNECT and absolute-URI request, checks **every** resolved address with core `browserDestinationProblem` and pins the connection to a checked address: public addresses on ports 80 and 443 only; never loopback, link-local, private (outside the list), CGNAT, ULA, metadata, multicast, reserved or unspecified addresses (IPv4, IPv6 and v4-mapped); home-network addresses only when inside an admin-listed Vault network with that port listed (`vault_networks`, VT-12; the server sends the list with every `open`). `browser_open` accepts only `http:`/`https:` URLs without credentials; `file:`, `data:`, `javascript:`, `blob:`, `chrome:`, `about:` (but `about:blank`), `view-source:` and extension URLs are refused, top-level page navigations to them are aborted. A redirect is a new request and is checked again, so a redirect to a private address fails at the proxy. On the appliance the nftables wall also confines the browser uid to 80/443 on public addresses plus the Vault networks (NX-94…). | The server's `outbound.ts` pins DNS for Node sockets; Chromium resolves on its own, so the rule has to sit where Chromium connects. One core rule for the Vault and the browser. |
| BT-06 | **Logins live in the Vault** (`vault.md` VT-D28…): entry kind `login` — the sign-in page URL (its origin is the site), `username`, the password as the sealed secret, optional `usernameSelector`, `passwordSelector`, `submitSelector`, and a reserved `totp` slot (never settable in this version). `browser_sign_in {entry}` decides with `decideVaultUse` unchanged (VT-20…VT-32: the owner's turn follows the tier; anyone else's turn needs a pass), opens the entry's URL in the turn's context (a fresh one if the current session is on another site), and the **server** hands the host the username and password for one `signIn` op; the host fills (selectors when set, else the usual heuristics: the visible password input, the text/email input before it, the form's submit button or Enter) and waits up to 15 s; it answers `signed_in` when no visible password input remains, else `still_asks` / `no_form`. The model sees neither value; every sign-in signs `vault.used` (owner detail “Browser sign-in”). A **logged-in session is pinned to the entry's site** (registrable domain, `tldts`): a top-level navigation to another site closes the session with “That page is on another site, so Whombat closed the signed-in session.”; a plain session refuses the sites of the logins the agent holds keys to (“Sign in with browser_sign_in to use {site}.”) — only the agent's own keys, so nothing reveals other people's entries. Snapshots never carry the values of password inputs (and screenshots mask them); any snapshot, page text, answer or screenshot's page text that holds a form of the secret (`secretForms`, VT-D22) is withheld whole, the session closed, and the key taken back with its passes (`withholdVaultAnswer`, the owner is told). “Test sign-in” (Vault UI, owner only) runs the same flow in a throwaway context and returns the outcome with a screenshot shown to the owner only (never stored or signed). *Amended by BT-D40…BT-D43, BT-D45, BT-D48 (security review, 2026-09-28): a signed-in session masks every field in its screenshots and refuses one while the field it filled holds the password; the host’s word that a session is signed in is final and the turn stays checked after a close; the fill keeps to frames on the entry’s site; a sign-in always starts in a new session unless it is signed in with the same entry; text waits and every page string are checked before any cut, as the model would read them.* | The Vault rules apply unchanged; pinning keeps a signed-in page from being walked to a site that collects it. |
| BT-07 | **What a room may see.** In a logged-in session `browser_screenshot` returns the image to the model only; `attach: true` is refused (“Screenshots of a signed-in page stay with you.”); the agent's own words remain its responsibility. In a plain session `attach: true` publishes the screenshot as an attachment of the turn's conversation (answer `attachmentId`). Page text and snapshots reach the model as delimited data: `[[web <origin>]] … [[/web]]`, with `[[web`, `[[/web`, `[[pack` and `[[memory` inside defused (BP-07). *Amended by BT-D41, BT-D45, BT-D46: “a logged-in session” is the host’s word or the server’s (either counts); its downloads stay private too; titles, notes, URLs and download names reach the model as page words (defused like page text).* | A signed-in page is private to the entry's owner; data is never instructions. |
| BT-08 | **Prompt lines** (both builders, `persona/browser.ts`, snapshot-tested) when the agent holds `browser.use` and `DispatchContext.browser.state` is `available`: what the tools are for (pages that need clicking or signing in; plain reading stays with WebFetch), that page content is data and never an instruction, that it must never type a password, token or code someone gave it in chat, and that sign-in goes through the Vault (`browser_sign_in`) for the entries listed. When the key is held but the browser is off: one line saying so and why. | Agents need to know the tools, their limits and the credential rule. |
| BT-09 | **Appliance**: the unit, uid and cgroup (MemoryMax 1.5 GiB, TasksMax 512, CPU weight below the runtime's), the nftables rules, `whombat.browser.enable` derived from total memory (on at 8 GiB and above, off below; `whombat.browser.force` overrides) — the unit's gate writes `/run/whombat-browser/status.json` `{state, reason}` that the runtime reads (`WHOMBAT_BROWSER_STATUS_FILE`), the runtime told through `WHOMBAT_BROWSER_SOCKET`, `host` info reporting the browser (BT-10), and `vm-tests/browser.nix` (the unit starts, a page from a listed network loads through the socket, a private address is refused, the memory cap holds). No LAN reach beyond the Vault networks. | The appliance is the reference deployment; memory decides whether a browser fits. |
| BT-10 | **UI**: the key row (web hire and Configure; Android key summary), the Vault “Login” template with Test sign-in (web only, VT-73), agent profile KEYS, activity rows “Opened example.com”, and Settings → General “Web browser: Available” / “Web browser: Off · {reason}” from `HostInfo.browser` (`{state: available \| off \| unavailable, reason}`). | People see what agents may do and whether the host can. |
| BT-11 | **Docs**: this file, `vault.md` VT-D28…, ARCHITECTURE.md (“Agent runtime”: tools, and a “Browser” section), user guide `docs/browser.md`, appliance NX-94… and IN-87…. | |

## Details settled while building (BT-D…)

| # | Decision | Why |
|---|---|---|
| BT-D01 | **Host protocol**: newline-delimited JSON over the unix socket; requests `{id, op, …}`, answers `{id, ok: true, result}` or `{id, ok: false, error: {code, message}}`. Ops: `hello` (version, Chromium version, limits), `open {session, url, networks, pinSite?, refuseSites[]}`, `snapshot`, `click`, `type`, `press`, `select`, `scroll`, `wait`, `screenshot {mask: true}`, `back`, `pageText`, `signIn {session, url, username, password, selectors, pinSite}`, `takeDownloads {session}`, `close {session}`, `stats`. `session` is an opaque id the server derives from the dispatch (never the agent token). Codes: `busy`, `not_allowed`, `timeout`, `no_session`, `bad_ref`, `navigation_failed`, `unavailable`. The host holds no secrets beyond one `signIn` op and keeps no state across restarts. | One small protocol the self-hosted child and the appliance unit share; the VM test drives it directly. |
| BT-D02 | **Server side** (`apps/server/src/browser/`): `client.ts` (socket client with reconnect and per-call deadline), `supervisor.ts` (self-hosted: spawns the host with a minimal environment, restarts with backoff, reports `available` / `off` / `unavailable`; `WHOMBAT_BROWSER=auto\|off`, default `auto` = on when a Chromium is found; tests use a fake host), `sessions.ts` (session ids per dispatch, login pins, the navigation counter, close on finalize and in the orphan sweep), `tools.ts` (MCP handlers), `commands.ts` (`browser.use` command with the hidden event), `signin.ts` (Vault fill and Test sign-in). Feedback, search and answer dispatches never list browser tools (like `vaultless`). | Keeps browser concerns out of the Vault and MCP modules except for their seams. |
| BT-D03 | **Snapshots** use Playwright's AI snapshot (`aria-ref` locators, as Playwright MCP does) with our own `@e<n>` numbering per page; values of password inputs and inputs with `autocomplete` `current-password`/`new-password`/`one-time-code` are removed from the tree. If the pinned Playwright version lacks it, the fallback is the CDP accessibility tree with backend node ids. | Stable references without exposing a DOM or letting the model run scripts. There is no `evaluate` tool. |
| BT-D04 | **Screenshots** are PNG of the viewport (1280×800, device scale 1), returned to the model as MCP image content (`{type: 'image', mimeType: 'image/png'}`) with a text part; password inputs masked. Providers that can't take images in tool results get the text part only. | Screenshots help the model with layouts; masking keeps secrets out of pixels. |
| BT-D05 | **The host protocol as built** (amends BT-D01): schemas in the runtime (`apps/server/src/browser/protocol.ts`), not core — both ends are built from this repository (the appliance runs the same bundle); the server parses every answer strictly and drops a connection that sends a malformed one (a compromised Chromium could own the host process). `hello` answers `{version: 1, playwright, chromium, limits: {maxContexts, maxNavigations, opTimeoutMs, idleMs, maxPages, viewport}}`; the client refuses another version. Page ops answer `PageState {url (no query, no fragment), title, origin, navigated, status, notes[], downloads}`; `snapshot` adds `{snapshot, truncated, refs}` (and takes `ref?` for a part), `wait {text? , ms?}` adds `found`, `screenshot` adds `{png (base64), width, height}` (`mask` is always on), `pageText` adds `{text ≤ 256 KB, truncated}`, `signIn` adds `outcome`; `takeDownloads` → `{downloads[{name, size, bytes}], remaining, dropped[{name, reason}]}`; `close` → `{closed}`; `stats` → `{contexts, maxContexts, uptimeMs, rssBytes, proxy {open, allowed, refused}}`. Codes: BT-D01's plus `limit` (the navigation cap, core's refusal code) and `bad_request` (a malformed request; the answer names the field, never its value). The host's exit codes tell the supervisor why it stopped: 0 stopped, 1 failed / Chromium went away, 2 bad settings, 3 no Chromium, 4 Chromium didn't start. *Amended by BT-D40, BT-D41, BT-D44 (protocol version 2; the client refuses a host speaking 1): `PageState` adds `pinSite`, `signedIn` and `usage {navigations, bytes}`, its `title` is the page’s own (≤ 1000 characters) and notes are ≤ 1200; `open` and `signIn` take `budget {navigations, bytes}`; `screenshot` takes `forOwner` (Test sign-in).* | One contract the child, the unit and the VM test share; the server never trusts what the page side says. |
| BT-D06 | **Sites and pins**: a site is the registrable domain with the public suffix list's private section (`tldts` 7.4.15, `allowPrivateDomains`: `alice.github.io` ≠ `bob.github.io`), else the IP literal, else the bare host (`siteOf`, `browser/sites.ts`, shared by host and server). `signIn` (or an `open` with `pinSite`) pins a session; a pin never changes or goes. A pinned session's top-level navigation elsewhere — typed, clicked, redirected or a popup — is aborted by the context's route and caught again after commit, the session closed; the op answers `other_site`, the next op on it `other_site` once, then `no_session`. `refuseSites` (from each `open`) apply to unpinned sessions only. *Amended by BT-D41: a pinned session whose page went (the site closed it) closes itself at the next op (`no_session`), and a session whose op outlived its deadline closes; BT-D43: `refuseSites` apply to a plain session’s frames too.* | BT-06's pin, checked before the request where Playwright's route sees it and after commit where it doesn't. |
| BT-D07 | **Playwright**: `playwright-core` **1.63.0** pinned exactly in `apps/server` (no postinstall, no browser download). The AI snapshot is the public `page.ariaSnapshotJSON({mode: 'ai'})` (1.63 made it public; references are stable per element within a document; actions use `aria-ref=` locators, as Playwright MCP does) — no private `_snapshotForAI`, no CDP fallback needed. The host drives `WHOMBAT_BROWSER_BIN` when set, else Playwright's `chromium-headless-shell`, else its full `chromium`, under `PLAYWRIGHT_BROWSERS_PATH`; `whombat browser install` installs `chromium-headless-shell` (revision 1243, Chrome for Testing 153.0.8010.12, about 115 MB) with playwright-core's own registry into `$WHOMBAT_HOME/browser` (0700), and `browser status` / doctor's “Web browser” report it (with Playwright's missing-library check). playwright-core reads `browsers.json`, its injected scripts and its download helper next to its own files, so a release ships it unbundled in `node_modules/playwright-core` (types left out) and every bundle keeps it external; `tldts` is bundled. The host is `app/browser-host.mjs`, started by `bin/whombat-browser-host`. | Pinned so snapshot shape, CDP and the headless shell move together; the public API avoids private hooks that change between versions. |
| BT-D08 | **The filtering proxy as built** (`host/proxy.ts`): one HTTP proxy on 127.0.0.1 (ephemeral port); per-context Basic credentials (random, compared in constant time; unknown → 407, so a closed context's late requests go nowhere); Chromium launched with the same proxy and Playwright's forced `<-loopback>`. CONNECT (https, WebSockets) and absolute-URI requests (plain http, keep-alive per request, and their upgrades): resolve with `dns.lookup(all, verbatim)` (the system resolver — the appliance's browser uid reaches no other DNS), check every address (`checkDestination`, networks re-validated with `vaultNetworkProblem`; a name resolving to public and private addresses at once is refused like the Vault's `mixed`), dial at most three checked addresses in order (5 s each), never resolve again. Refusals: CONNECT answers 403; plain http answers a small 403 page marked `x-whombat-proxy: refused` (`unreachable` for a destination that didn't resolve or answer), each recorded per context so the op says `not_allowed` with the rule's words, or `navigation_failed`. Tunnels idle 5 min are closed; 128 connections and **256 MiB received per session**, past which the session is cut off and closed. *Amended by BT-D44: the 256 MiB and the navigation cap are the turn’s, across its sessions (each session gets what is left).* | Where Chromium connects is the only place the rule can hold for every request, redirect and WebSocket. |
| BT-D09 | **Chromium's process**: `chromiumSandbox: true` (Playwright's default is off); `WHOMBAT_BROWSER_SANDBOX=off` only when set on purpose, and with it on a sandbox that can't start fails the launch (exit 4, “Chromium didn’t start”) — never a fallback to `--no-sandbox`. The host refuses to run as root. Flags: `--disable-quic`, `--host-resolver-rules=MAP * ~NOTFOUND , EXCLUDE 127.0.0.1`, `--force-webrtc-ip-handling-policy=disable_non_proxied_udp` (and `--webrtc-ip-handling-policy`), `--disable-background-networking`, `--disable-component-update`, `--disable-sync`, `--disable-extensions`, `--dns-prefetch-disable`, `--disable-domain-reliability`, `--no-pings`, `--no-first-run`, `--no-default-browser-check`; no `--disable-features` of ours (a second one would replace Playwright's list). Contexts: viewport 1280×800 at scale 1, service workers blocked, downloads accepted, `en-US`, no permissions, 30 s default timeouts. Dialogs are dismissed (`beforeunload` accepted) with a note quoting ≤ 150 characters; file choosers answer a note; a popup replaces the current page (note), at most two pages. A renderer that crashes (killed at the unit's memory cap, say) closes only its session (`navigation_failed` “The page crashed …” once); Chromium itself going away exits the host (1) for the supervisor or the unit to restart. | The page is hostile input: its own sandbox stays, and one heavy page costs one session, not the host. |
| BT-D10 | **Snapshots as built**: lines `- role "name" [flags] [ref=@eN]: value` with `/url` and `/placeholder` child lines; `@e` numbers per page in order of first appearance, stable across snapshots of one document, restarted on a new one (a new document or a URL change beyond the fragment); an action on a reference not in the current map is `bad_ref` at once. A value is withheld (`[filled]`) when its input is a password, has `autocomplete` `current-password`, `new-password` or `one-time-code`, or is masked with `-webkit-text-security`; an input the host can't ask about keeps its value out too. The 64 KB cap counts bytes (stricter than core's characters) and cuts on a line boundary before the note. Page functions are kept as source text and compiled with `new Function` in the host (`host/page-fn.ts`): a build step (tsx, esbuild, vitest) may rewrite a function with helpers the page doesn't have. | BT-D03, with what the model sees fixed down to the line. |
| BT-D11 | **Sign-in as built** (`host/signin.ts`): the entry's selectors first (in any frame, main first); else a page function marks the fields (`data-whombat-signin`, removed afterwards): the first visible password input, the last visible text/email/tel input before it in the same form, the form's submit button — else a button worded “sign in / log in / continue / next” — else Enter. Two-step forms: a username-like field (autocomplete, `type=email`, name hints) is filled and submitted, then a password field is awaited ≤ 10 s. Outcome within 15 s: `signed_in` once no visible password input is left in any frame on two checks in a row with the document loaded; `still_asks` otherwise; `no_form` when there was nothing to fill. Playwright's errors from here are never passed on; the values are never logged, answered or kept. *Amended by BT-D42: only frames on the entry’s site are filled or counted; BT-D40: the fields filled are marked and remembered for the session’s screenshots.* | BT-06's heuristics, bounded and quiet. |
| BT-D12 | **Downloads as built**: Playwright writes them under the host's private `TMPDIR`; the host reads each finished one into memory and deletes the file. At most 4 per session waiting, each ≤ `downloadMaxBytes` (the server's upload cap from `open`/`signIn`, 25 MiB by default), else dropped with a reason; names cleaned (base name, no control characters, ≤ 200). `takeDownloads` waits ≤ 5 s for running ones and answers up to about 32 MiB of bytes per call (at least one) with what `remaining`. | BT-04's “into memory”, with bounds on memory and on answer lines. |
| BT-D13 | **The supervisor as built** (`browser/supervisor.ts`, `browserFor(services)`): modes `spawn` (self-hosted `auto`), `connect` (`WHOMBAT_BROWSER_SOCKET`), `off` (`WHOMBAT_BROWSER=off`, the default in tests unless a socket is set; a managed server without a socket: “This Whombat has no browser.”). Reasons, verbatim: “Turned off (WHOMBAT_BROWSER=off).”, “No Chromium found. Run `whombat browser install`.” (`off`; looked for again every minute, so an install needs no restart), “No Chromium at WHOMBAT_BROWSER_BIN.”, “The browser is starting.”, “The browser stopped; restarting.” (backoff 1 s doubling to 60 s, reset after a minute up), “Chromium didn’t start; restarting. The server log says why.”, “The browser host’s settings are wrong. The server log says which.”, “The browser isn’t running.”. Spawn: `process.execPath` on `app/browser-host.mjs` next to the server bundle, or `--import tsx …/host/main.ts` in a checkout, in its own process group (the group is killed on stop), environment exactly `PATH`, `HOME=$WHOMBAT_HOME/browser/home`, `TMPDIR` under it, `LANG=C.UTF-8`, `PLAYWRIGHT_BROWSERS_PATH=$WHOMBAT_HOME/browser`, `WHOMBAT_BROWSER_SOCKET=$WHOMBAT_HOME/run/browser.sock`, `WHOMBAT_BROWSER_{BIN,MAX_CONTEXTS,MAX_NAVIGATIONS,SANDBOX}` and `WHOMBAT_BROWSER_PARENT_PID` (the host stops within 2 s when its server is gone); `run/`, `browser/`, its home and tmp are 0700. A host that doesn't say hello within 60 s is killed and restarted; its JSON log lines reach the server's log at their level. Connect: the unit's status file `{state, reason}` — `off` means don't connect and report off with its reason; `available` or no file, the socket decides (hello = available, else unavailable, “The browser isn’t running.” or the file's `unavailable` reason); retried every 5 s. Started with the background work (not on a read-only boot), stopped in `onClose`; nothing about it blocks boot. | BT-01's “never takes the server down”, with words for every state. |
| BT-D14 | **Settings** (`config.ts`): `WHOMBAT_BROWSER` (`auto`\|`off`), `WHOMBAT_BROWSER_SOCKET`, `WHOMBAT_BROWSER_STATUS_FILE`, `WHOMBAT_BROWSER_BIN` (absolute paths), `WHOMBAT_BROWSER_MAX_CONTEXTS` (1–16, 4), `WHOMBAT_BROWSER_MAX_NAVIGATIONS` (1–500, 40), `WHOMBAT_BROWSER_SANDBOX` (`on`\|`off`, on). Backups leave `browser/` and `run/` out (a download to repeat, a socket). Doctor's “Web browser” warns, never fails (the browser is optional). | One place per setting, documented in docs/install.md. |
| BT-D15 | **The appliance's unit** (for NX-94…, IN-87): run `bin/whombat-browser-host` of the runtime bundle (the Nix package wraps its Node on `app/browser-host.mjs`; `node_modules/playwright-core` comes with the bundle) under its own uid with `WHOMBAT_BROWSER_SOCKET=/run/whombat-browser/host.sock` (the directory must exist: `RuntimeDirectory=whombat-browser`, group-accessible to the server user), `WHOMBAT_BROWSER_BIN=<pkgs.chromium>/bin/chromium` (a version close to 153: Playwright 1.63 speaks its CDP), `WHOMBAT_BROWSER_MAX_CONTEXTS=2`, `WHOMBAT_BROWSER_SANDBOX=on`, `HOME`/`TMPDIR` in the unit's own state or runtime directory, `Restart=on-failure`. The host creates the socket 0660 whatever the umask and removes a stale one.
