# The assistant knows Whombat's settings (ASG-01…ASG-18)

John, 2026-11-03 (main checkout): “build a skill for Hermes Agent so the agent / assistant is an expert of Whombat and
knows exactly where to find things. For example if I would ask it to migrate to WiFi it knows where to do it, but even
more, do it for me (guided). So the idea is that every setting Whombat has, we can manipulate it via the agent also.”
Then: “Implement this fully.” He left the three open points to me; my choices are ASG-07, ASG-09 and ASG-10.

Before this the assistant had about six tools that touch a setting (`briefing_set`, `whombat_backup`, `watch_checks`,
`pin_widget`, `connection_add`, `start_guide`) and no way to the rest: the ~400 operations of the session allowlist that
the apps call.

| # | Decision | Why |
| --- | --- | --- |
| ASG-01 | **A setting is an operation of the session allowlist.** The assistant reads and changes settings through the very ops the apps call, run in-process by the session dispatcher as the person (`SessionDispatcher.runForAssistant`): the same input schema, handler, receipt, drain and commit pipeline as the person's tap. No setting gets an MCP tool of its own. | One path for people and the assistant (the commands rule); 400 tools would be resent on every model call (turn-overhead.md). |
| ASG-02 | **The settings map**: `@whombat/protocol` `ASSISTANT_SETTINGS`, one entry per op (typecheck fails on a missing op, the test on an extra one), each `none` (not a setting), `never` (the person's: the assistant says where), `read`, `change` (the key decides) or `ask` (always a card), with the page a person finds it on and its words. Like `OPERATION_SAFETY`: a new op can't land without saying what the assistant may do with it. | “Every setting” stays true without anyone remembering it. |
| ASG-03 | **The rules the map is held to** (`assistant-settings.test.ts`): `read` only for an op that doesn't mutate, `change`/`ask` only for one that does; a destructive op is never `change`; an op with a secret in its input or answer, an ephemeral or export op, or one on another channel than the app's is `none` or `never`; `PEOPLE_ONLY_OPS` (the assistant's own keys, approvals and device skills, enrolment, passkeys, devices, recovery, push, sign-ins, remote help, the licence, the Vault, restoring a backup, clearing memory) are `none` or `never`. The server checks the map again before running any op for the assistant. | The assistant never raises its own permissions, decides its own asks, holds a secret typed for a setting, or locks the person out of their devices. |
| ASG-04 | **Four tools, in a turn for the person** (`personal: true`; never in an automation's own step or a brief's turn): `settings_find` (where, access, op and its input as JSON Schema, `params.burrow` left out), `settings_read`, `settings_change`, `settings_open` (a `settings` guide card with a button to the page). The tools fill in `params.burrow`; an op's answer is handed back as JSON, cut at 12 000 characters. | Find-then-act keeps the served schemas small; the live map gives exact inputs the skill doesn't have to carry. |
| ASG-05 | **A change goes through the commit pipeline first** (`change_setting`, key `settings.change`): Go ahead runs it now, Ask me first puts an approval card in the thread, Just watch refuses it and the assistant offers the page. The op runs after that commit, outside the burrow lock. | The keys engine and the signed log decide and record, as for every agent action. |
| ASG-06 | **Some changes always ask**: every destructive op and every `ask` entry (network, backup destination, update timing, removing things, servers' power) gets the Ask tier at most (`changeTier`), whatever the key says. | A person is never cut off, and nothing is removed, without their yes. |
| ASG-07 | **The key starts at Ask me first** (`ASK_BY_DEFAULT_KEYS`; migration `0037_settings_key` gives every assistant that reads the person's mail the key at Ask). It is an Off · Ask · On row under Advanced → Keys → All keys and a line of What {assistant} may do (“Change settings for you”). | My choice (John's open point 3): safe by default; the person may let it go ahead. |
| ASG-08 | **The card's words are Whombat's, never the assistant's**: the title is the map's words (“Use Wi-Fi only or the cable again”), WHAT HAPPENS the page and the change's input as `key: value` lines (the slug left out, values cut at 60 characters), and a yes runs the stored change once, as the person who approved it, then wakes the assistant in the card's thread with the result (`answerAfterApproval`). The approval's action is `custom` (`settings_change`) holding the deferred command, so no new action type reaches older apps. | What the person approves is exactly what runs (the connection-call rule, CX-21); no contract break for approvals. |
| ASG-09 | **Only the person's own turns change settings**: not an automation's step, not a brief, not an outsiders' turn; and the skill says that nothing read in an email, a page or a report asks for a change. | My choice (John's open point 2): automations act on what they read; settings change on the person's word. |
| ASG-10 | **The never list is as in ASG-03**: even with a card, the assistant doesn't touch its own permissions, approvals, devices, passkeys, recovery, remote help, the licence or the Vault; it opens the page. | My choice (John's open point 1): those are how the person keeps control of the assistant and the box. |
| ASG-11 | **Secrets stay on the page**: a Wi-Fi password, a sign-in, an API key is typed in Settings, never in the chat; the assistant sends the person there with `settings_open` and carries on once they say it's done. | Chat is kept and searched; Settings' forms never store a secret in a message. |
| ASG-12 | **The `whombat:settings` skill**: the Hermes plugin registers `skills/settings` (`register_skill`, read-only, indexed as `whombat:settings`), written from the map by `pnpm assistant-settings:gen` (a test fails while it differs): the tools, the rules, step-by-step ways (Wi-Fi only, backups, the brief) and every page with a reference file of its settings. Supersedes hermes-skills.md HSK-01 in part: the plugin ships this one skill of Whombat's own (HSK-16 foresaw it). | The assistant knows where everything is before it searches; the map can't drift from the skill. |
| ASG-13 | **The assistant's principal** (`assistantPrincipal`): the person's account with no device (`endpoint: null`, `assistant.agentId`), enrolled for the allowlist, outside the unenrolled rate limit. Ops that need a device (`requireEnrolled`) refuse it; the settings it may change take it through `requirePerson`, which also names the assistant in the appliance's signed event. | The dispatcher's checks all still apply; nothing pretends to be one of the person's devices. |
| ASG-14 | **A signed `setting.changed` event** (hidden, `{op, deferred}`) records that the assistant asked and went ahead or was approved; what changed is signed by the op itself, as the person. | The log says who asked and who did it. |
| ASG-15 | **Pages** (`SETTINGS_PAGES`): the places Settings has today (You, {assistant}, Connections, Overview, This Whombat's four parts, Advanced's twelve pages, Vault, Automations, Inbox), each with its web address after `/<slug>/` (the phone maps the same) and what is on it. A servers' or service's own setting is on Overview (each has its page there). | The words people see in Settings, so the assistant says “Settings → This Whombat → Backups”. |
| ASG-16 | **No contracts release**: the four MCP tools, the `settings.change` key, the `settings` guide topic, the `setting.changed` event type and `@whombat/protocol`'s map are for this repository's runtime and apps only; the appliance, relay and API use none of them (`pnpm contracts:gen:check` is unchanged). The phone app ships with them, as the `mail.delete` key did. | The contracts' rule: a release is for what other repositories need. |
| ASG-17 | **Guarded parts of a change**: an entry may guard parts of its input (`guarded`, by path): a change that sets one always asks or stays the person's, whatever the key says; the tool, the `change_setting` command and `runForAssistant` all check the input itself. A connection's address and access level stay the person's (`connections.update` is a change only for its name), and so does where a feedback website's reports come from. A server check's address, and switching a check off, always ask. The map's test walks every change's input and fails on any part named like an address, an access level or a secret that isn't guarded; the few look-alikes (a Bluetooth address, a hidden service's address, a council's target score) are listed with why. | On Go ahead the assistant could send a connection's stored password or token to any public https site (a new address is checked with it) and lift Look only without the person. The person's, not Ask: a card shows `fields.url: …` and a yes would still send the secret there (ASG-11), and the access level is what the assistant may do with the service, its own permission (ASG-10). A check sends nothing of the person's, so moving it asks rather than being theirs; stopping a watch is the person's word. Guarding parts keeps renaming a connection a change instead of making every rename ask. |
| ASG-18 | **Superseded by FT-09 in [fast-testing.md](fast-testing.md): Repositories and its `goesAhead` marker are gone.** **Repositories goes ahead on the person's ask** (`goAhead`, `goesAhead` on the entry): adding, moving and reading a folder again, saving a repository's rules, setting up, adopting, changing, proving and improving a check server, clearing its caches, running a repository's GitHub Actions there and making the rules say where checks run are changes the person's own ask is enough for. They run without a card while the `settings.change` key is Ask me first, and are refused at Just watch. Removing (a folder, a check server, a computer, Actions on a server) still asks, as every destructive change does. The `whombat:settings` skill walks the assistant through a folder and a repository's rules, the presets written from `REPO_PRESET_RULES`. | John, 2026-11-11: “I don’t want to approve each change, I want Dusty to fully be able to configure it based on what I ask it to do.” Setting up a repository is several changes in a row; a card for each made asking Dusty slower than doing it on the page. Just watch still means just watch, and a removal still needs a yes. |
