# Prompt efficiency (PE-01…PE-10)

John, 2026-10-03, after the resourceful-agents live checks (one Pippa DM turn: ~75 000 input tokens on Codex, Dusty
~23 000): “this should be investigated fully. I want prompts to be efficient … let a sub-agent research how Hermes agent
does this and see if we can learn from that.”

Research (read-only, 2026-10-03): Hermes Agent's techniques (`~/.cache/wb-tmp/hermes-measure`, report in this
session) and a measurement of Whombat's turns with the pinned CLIs against fake model APIs
(`~/.cache/wb-tmp/prompt-size/`, o200k token counts). What a turn costs today, per model call:

| | Pippa DM, 10 packs | Banjo run + checkout | Hazel personal | Dusty scheduled |
|---|---|---|---|---|
| Claude 2.1.283 | 51 400 (Whombat tool schemas 31 300, Claude built-ins 6 700, Whombat prompt 8 400, CLI env/skills 2 800, user turn 2 000) | 51 200 | 52 200 (tool schemas 37 000) | 48 800 |
| Codex 0.157 | 27 800 (Codex tools 9 000, base instructions 4 100, its skills list 3 300, Whombat prompt 8 400, user turn 2 000) | ~27 400 | ~22 200 | 24 800 |

A turn is the sum over its model calls (each call resends everything; 2–3 calls for a small task, dozens for a run).
What makes it worse than it needs to be:
- The system prompt changes every turn (a minute clock at ~2 % of it, “Right now”, teammates' status, knowledge, the
  checkpoint, profile/notes counters), so on Claude a resumed session rewrites the prompt and the whole history to the
  cache at 1.25× instead of reading it at 0.1×; on Codex, 0.157 ignores new `developerInstructions` on `thread/resume`,
  so resumed threads keep a stale prompt.
- Whombat's tool schemas are 31–37 k tokens per Claude call: validation-only JSON Schema (date-time regexes 4.6 k,
  `$schema` ×49, 2^53−1 bounds), personal-only action variants in team agents' `request_approval`/`perform_action`
  (6.6 k), tools the turn can't use (`post_answer` outside answers, `run_*` outside runs, run/PR tools for personal
  agents).
- Usage is miscounted: cached and uncached input are one number (spend and handoff budgets count cache reads at full
  weight; Codex records no cost), resumed Codex turns count the previous turn's usage again (~20–28 k phantom tokens),
  and session rotation and the “context filling up” nudge compare the summed turn, not the context size — sessions are
  retired after one busy turn (dev.whombat.com: 5 of 23 turns resumed in 30 days).
- Text sent twice: pack skills (Whombat's list and the CLI's own), identical AGENTS.md and CLAUDE.md, the request
  (window line and “X is asking you”).
- On Codex, Whombat's tools are discovered with `tool_search`/`exec` first: an extra ~25 k-token call per turn.

| ID | Decision | Why |
| --- | --- | --- |
| PE-01 | **Measure, then change, then measure.** A script (`pnpm prompt:size`) renders the four turn types above from fixtures and prints tokens per prompt section and the tool schemas each agent is served; the numbers before and after go into the commits. The live check (`dev/devbox ra-check`) reports tokens per scenario before and after. | Hermes pairs every prompt edit with a token A/B; we found the problem only by accident. |
| PE-02 | **One system prompt per session, byte for byte.** Nothing in the system prompt changes between turns of the same provider session: the clock, “Right now”, teammates' status and open handoffs, knowledge and the checkpoint, the profile and notes (with their counters) and every usage nudge move into the first user message of the turn (`renderPrompt`), which is new each turn anyway. A test renders two turns of one session at different times, with new messages, knowledge, profile entries and teammate states, and asserts identical system prompts. | Hermes: “prompt caching is sacred”. On Claude a resumed turn then reads its history from cache; on Codex the stale-prompt problem disappears. |
| PE-03 | **A session lives as long as its stable prompt.** The runner reports a hash of the stable system prompt with each turn; the server keeps it with the session and resumes only a session whose hash matches (a changed job, keys, packs, Vault or role starts a fresh one). Profile and note writes no longer retire sessions (they are in the user turn now). | Resume when it is cheap and correct; never with a stale prompt. |
| PE-04 | **Count tokens as they are billed.** `TurnUsage` and the runner's `CompleteBody.usage` (contracts 0.44.1, additive) carry `cacheReadTokens`, `cacheWriteTokens` and `largestCallInputTokens` next to the total `inputTokens`; Claude fills them from `cache_read_input_tokens`/`cache_creation_input_tokens`, Codex from `cached_input_tokens`; Codex usage is counted only after the turn's own id is known (no double count on resume). Session rotation and the checkpoint nudge use `largestCallInputTokens` (the context size). Spend and handoff budgets count uncached input + cache writes + output fully and cache reads at a tenth. The usage view shows cached vs uncached. | We could not see caching, and budgets and rotation acted on inflated sums. |
| PE-05 | **Lean tool schemas, only the tools a turn can use.** Whombat's MCP server serves input schemas without validation-only keywords (`$schema`, format regexes, length and safe-integer bounds) — the server still validates every call with the full zod schema and answers with the exact problem. Per agent and turn it lists only what can be used: personal action variants only to personal agents, `post_answer` only in answer turns, `run_*` only in run turns, run and pull-request tools not to personal agents. | 13–17 k tokens per Claude call, with no loss: the server's validation is unchanged. |
| PE-06 | **Pack skills listed once.** When the CLI loads the pack skills itself (Claude plugins, Codex skills), Whombat's prompt keeps the “skills first” rule and lists only skills with unmet requirements; the full list stays for runtimes that can't load skills. | The same 1–3 k tokens were sent twice per call. |
| PE-07 | **Codex sees Whombat's tools without searching.** The prompt names the core Whombat tools Codex should call directly (post_message, reply_in_thread, read_conversation, search, memory, schedule, start_run, request_approval…) with their purpose in one line each; `personality: "none"`; Codex tools Whombat can't use (user-input requests it answers empty, MCP resources it doesn't serve) are switched off where 0.157's config allows. | Saves a discovery call (~25 k tokens) on most Codex turns. |
| PE-08 | **No text twice, and short when empty.** The request appears once; identical repository instruction files are included once; the Vault section is two lines when the agent holds no entry; teammates' key lists appear only when they differ from their role's defaults. | Small, but paid on every call. |
| PE-09 | **The prompt stays honest about capability.** No line that makes agents resourceful (RA-11, RA-12, RA-16, RA-23) is cut for size; trimming is about duplicates, volatile placement and schemas. | Efficiency must not undo the build it serves. |
| PE-10 | **Not now** (measure after PE-01…PE-08 first): deferring Whombat tools behind a search on Claude (`ENABLE_TOOL_SEARCH`), ≤60-character skill descriptions across the packs, Claude's Task* tools only in run turns. The 1-hour cache came in this release for turns a person paces (PE-DR10). | Each has a trade-off worth deciding on real numbers. |

## Caching like Hermes (PE-11…PE-14)

John, after comparing with Hermes Agent's caching: “Consider if we should improve it and if we do then please implement
it.” Already in this release: the stable system prompt (PE-02), resume only on the same prompt (PE-03), cache reads and
writes counted apart (PE-04) and the 1-hour cache for person-paced Claude turns (PE-DR, Codex 0.157 has no switch).

| ID | Decision | Why |
| --- | --- | --- |
| PE-11 | **A reflection reads the conversation's warm cache.** Where the CLI can fork a session, a reflection (RA-24) continues a fork of the conversation's own live session — the same system prompt and the same tool list, with the reflection request as the new user message — so its prefix is read from cache. It may still only use `memory`, `propose_skill` and `read_conversation`: enforced when a tool is called (the server refuses other Whombat tools in a reflect turn; the runner's tool policy refuses built-in tools), never by listing fewer tools, which would break the prefix. The fork is never kept as the conversation's session. Claude: `--resume <id> --fork-session`; Codex: a thread fork only if 0.157 offers one. When the conversation has no live session (or its prompt hash differs), the reflection runs cold as today. | Hermes' cache-parity review fork. With the 1-hour cache the conversation is still warm 10 minutes after its last turn; a reflection then costs about a third, and it sees the whole session — tool results included — not only the messages. |
| PE-12 | **Every resumed turn's cache result is known.** A resumed chat turn is `hit`, `expired` (the gap since the session's last turn exceeded its cache lifetime: 1 hour for person-paced Claude turns, 5 minutes otherwise) or `miss` (neither: something changed the prefix). The class is stored with the turn's usage, logged, and counted in the usage view; repeated unexpected misses are a warning in the runtime log. | Hermes counts cache-break causes; a regression must show, not silently cost tokens. |
| PE-13 | **A prefix-stability test with the real CLIs.** Two turns of one session through the pinned Claude Code and Codex, against a fake model API and Whombat's MCP tools: the second turn's first request must extend the first turn's last request byte for byte (tools, system prompt, history). | Hermes' `test_prefix_stability`; it guards PE-02 and PE-03 against the next prompt change. |
| PE-14 | **Not ours to change:** where cache breakpoints sit and compaction inside a session — Claude Code and Codex own the model loop (Claude Code's breakpoints after the tools, after the system prompt and on the last message match Hermes' layout). | — |

### Contracts (PE-DC, contracts 0.44.1, CT-259)

| ID | Decision | Why |
| --- | --- | --- |
| PE-DC01 | **A patch: 0.44.1.** Optional fields and pure helpers only: every 0.44.0 payload parses both ways, no feature name, no `SESSION_API_LEVEL` change (contracts `docs/decisions/contracts.md` CT-259). Tag `contracts-v0.44.1`, vendored here in place of 0.44.0. | Runners and servers of either version keep working through an update. |
| PE-DC02 | **`inputTokens` stays the total.** `SpendUsage`, which `CompleteBody.usage` now is, adds `UsageCacheFields`: `cacheReadTokens` and `cacheWriteTokens` (parts of `inputTokens`) and `largestCallInputTokens` (the largest model call's input, all kinds: the context the session reached). The same optional fields ride on `MemoryContext.usage`, `MemorySession.lastUsage` and `AgentContextResponse.lastTurn.usage`; `SpendTotals` takes the cache split once a turn in the window reported one. No cross-field refinement (reads ≤ input): the helpers clamp. | A runner's slip must not cost a turn its completion; totals from older runners stay equal to 0.44.0's. |
| PE-DC03 | **One definition of billed and of context.** `billedTokens` = uncached input + cache writes + output in full, cache reads × `CACHE_READ_WEIGHT` (0.1), rounded, reads clamped to the input; `spendTokens` is it. `usageContextTokens` = `largestCallInputTokens`, else `inputTokens`. Cache writes count 1×, not Claude's 1.25×. | The server's SQL, the runtime's nudge and the clients' spend lines agree; a budget is a guard, not an invoice, and Codex has no write price. |
| PE-DC04 | **The prompt hash travels with the session id, and the runner decides.** `PromptHash` (`stablePromptHash`: sha-256 hex of the prompt's UTF-8) comes with `providerSessionId` on `ProgressBody` and `CompleteBody`, and goes back as `DispatchContext.resumePromptHash` whenever the server hands out `dispatch.providerSessionId` (a chat session, a retry's own session, a run's). Match: resume. Mismatch: a fresh session with the context given, except when `memory.session.resumed` (the window holds only what is new): then `complete` `failed` with `SESSION_PROMPT_CHANGED` and nothing runs; the server retires the session and queues the turn again at once, uncounted, with the whole window. Null never matches (an older runner recorded the session); absent means an older server: resume as before. | The server chooses the session (and trims the window) before the runner renders the prompt, so only the runner can compare, and a trimmed window is too little to start over with. |

### Server (PE-DS)

| ID | Decision | Why |
| --- | --- | --- |
| PE-DS01 | **Lean schemas: what only validates goes, what guides stays.** The MCP server serves Whombat's own tools' input schemas without `$schema`, the regex beside a `format` (date-time, date, email), zod's ±2^53−1 bounds, `minLength`/`minItems` 1, `maxLength` ≥ 1000 and `maxItems` ≥ 100 (`mcp/served.ts`). Small bounds (a 160-character title, 3 suggestions, 1–100 results, positive numbers), `default`s, `enum`s, descriptions and id patterns (`msg_…`: which id goes where) stay; a test pins that every property, requirement, type, enum, default and description of every tool survives. `callTool` still validates with the full zod schema and answers the exact problem. Pack and Vault tools keep their owners' schemas. | A bound the model writes to saves a failed call; one it never reaches only costs tokens on every call. |
| PE-DS02 | **The tools a turn is served.** `post_answer` only in search answers (`mode: answer`); the run reports (`run_step`, `run_log`, `run_tests`, `run_files`, `finish_run`) only in a turn on a run: `mode: run`, a `runId`, or a writable checkout (`dispatchCheckout`), where the agent starts its run and reports in the same turn (RC-01); `start_run` stays in every team turn. A personal agent gets no run or pull-request tool, and the personal action variants of `request_approval` / `perform_action` only for the services its owner connected (a team agent never); unused `$defs` go with them. A tool not served this turn still answers when called (tests, older runtimes). Measured (o200k, Whombat's own tools as Claude receives them): team chat turn (Pippa, Dusty) 49 → 43 tools, 31 330 → 18 316 tokens; Banjo run turn 31 330 → 19 024; search answer 31 330 → 20 837; Hazel with every connector 69 → 59 tools, 37 057 → 22 688. Lean schemas alone: 31 330 → 23 713 and 37 057 → 26 814. | Every call of every turn resends the list; a chat turn without a checkout hands its run to the run turn and can't use the reports. |
| PE-DS03 | **The prompt hash is stored with the session id, everywhere one is.** `dispatches.prompt_hash` (migration 0068) is set with `provider_session_id`: at the claim from the session handed out (the one `chooseSession` resumes, a retry's own, a run's earlier one), from the beat or completion that reports a session (null when an older runner reports a session without a hash), and `recordTurn` keeps it on `agent_sessions.prompt_hash`. The context's `resumePromptHash` is the dispatch's, null without a session. | The runner can only compare against the hash of the very session it is asked to resume. |
| PE-DS04 | **A refused resume goes again at once, uncounted.** `complete` with `SESSION_PROMPT_CHANGED` for a turn that resumed a chat session (`dispatch_memory.resumed`) retires the session as “the system prompt changed”, clears the dispatch's session and hash and queues it with no backoff and its attempt given back, as a runner shutdown does; the next claim finds no active session, starts fresh with the whole window and gives that reason (a requeued turn's dropped-session reason carries over to its next claim). The same error for anything else (a run, a fresh session) is an ordinary failure, so a runner that misbehaves can't loop, and the refused prompt's hash is never stored on a session. | Nothing ran; counting it would cost a turn its one retry. |
| PE-DS05 | **Memory writes keep the session; people's corrections retire it.** With PE-02 (runtime 4b14338a: profile and notes open the user turn), `memorySessionPart` keeps only whose profile a turn carries (`#profile:<person>` while it holds entries): one person's profile never reaches another's turn. Notes and entry versions are no longer in it, so the agent's `memory` writes, reflections and anyone's additions keep the session. A person's change or removal of a profile entry, learning switched off, and a person's change or removal of a note retire the sessions that may hold the old words (`memory/session-retire.ts`): all of the agent's for its notes; for a profile, those in conversations the person is in, where their turns run (a superset: corrections are rare). | Before, every write retired the session; a person's correction must still not live on in the history. |
| PE-DS06 | **Every token count Whombat compares or shows as used is billed.** One SQL helper (`domain/turn-usage.ts`, core's `billedTokens` over sums, reads clamped to each turn's input): handoff budgets (`stepTokens`, the plan cap), the spend overview's plans, automation limits per run and per day, and a step's reported tokens. Spend totals carry `cacheReadTokens` / `cacheWriteTokens` only once a turn in the window reported a split, so the SQL still equals core's fold, and rows sort by billed tokens. `dispatches.usage` stores the runner's `SpendUsage` whole. | Cache reads at full weight made budgets stop work that cost a tenth of what they counted. |
| PE-DS07 | **Rotation reads the context, not the sum.** `agent_sessions.last_context_tokens` (the largest call) with `last_cache_read_tokens` / `last_cache_write_tokens`; a session retires when `usageContextTokens` (largest call, else an older runner's summed input) reaches `SESSION_ROTATE_TOKENS`, still 140 000 — now meaning the context, about 70 % of a 200 k window. The context's `memory.usage` and the agent's usage view carry the same fields (cached vs uncached), for the nudge and the clients; no UI work here. | One busy turn of many calls no longer retires a session. |
| PE-DS08 | **Migration 0068 is an expand.** Five nullable columns; readers and writers keep the 0047 floors. An older binary ignores them: it resumes as before, rotates on the sum and counts every input token in full. | Mixed versions during an update keep working. |

| ID | Decision | Why |
| --- | --- | --- |
| PE-DR01 | **`pnpm prompt:size` is a workspace package** (`scripts/prompt-size`): the four turn types as dispatch contexts built from the repository's own packs and role defaults, rendered by the live builder, split into `## ` sections (a delimited block's own headings don't split; the user turn's conversation starts at `Conversation:`), plus the Whombat tool schemas the agent is served, mirrored from the server's `mcpToolList` in `tools.ts` (the server's own pure selection can replace it). Tokens are characters / 4, labelled `≈tok`: there is no JS tokenizer in the repository, and chars/4 undercounts JSON schemas by about a third. `--out DIR` writes the prompts for the CLI drivers, `--as claude\|codex` renders every turn on that provider, `--json` the numbers. | One command that shows where a prompt's tokens go, per section, before every prompt change. |
| PE-DR02 | **What moved into the turn, and what stayed.** The user turn opens with `turnStateLines`: the clock, “Right now you are: …”, “Your teammates now” (here, ready or why not, unfinished handoffs, right now), this turn's Vault passes, which Vault keys are on the computer and which aren't, that the browser isn't available, memory being unavailable or incomplete, knowledge, the checkpoint, the context nudge, the person's profile with who reads the conversation, the agent's notes. The system prompt keeps the roster (who, role, skills, working directory), the Vault entries' standing rules (“you may use it” / “asks Joris once per turn”; how a computer key reaches the computer when it is there), the browser section whenever the key is held, the approved instructions (a change already starts a fresh session), and the rules for profile, notes and what goes where — rewritten to name no person (“Prefers short replies”, not “Always reply briefly”; RA-20…RA-23's substance kept, PE-09). The scratch folder's attachments line is in every scratch turn. A reflection keeps its own prompt (it never resumes). `prompt-stable.test.ts` renders two turns of one session 47 minutes apart with everything above changed and asserts the same system prompt, byte for byte. | Nothing a turn changes may stay in a prompt a session is resumed with. |
| PE-DR03 | **Both CLIs keep a resumed session's first system prompt** (probed with the pinned binaries: a changed prompt on resume never reaches the model — Claude Code 2.1.283 ignores `initialize.systemPrompt` on `--resume`, Codex 0.157 `developerInstructions` on `thread/resume`). So before PE-02 a resumed turn ran on its session's first clock, knowledge, checkpoint, profile, notes and teammates' state, on both providers; on Claude the cache was not what broke, the facts were stale. PE-02 puts them in every turn; PE-03's hash keeps a changed stable prompt from being resumed. What caching gains: the stable prefix (tools and system prompt) is now the same for every fresh session of an agent in the same kind of turn for the same person, across conversations, so it is read from the cache instead of written. | The measured behaviour, not the assumed one, decides what PE-03 protects. |
| PE-DR04 | **The runner's resume rule is PE-DC04's** (`resumeChoice` in `apps/runner/src/prompt.ts`): with `dispatch.providerSessionId`, resume when `resumePromptHash` is this turn's `stablePromptHash` (core's) or absent (an older server); otherwise a fresh session (the resume id dropped, the new session reported with its hash), or — when `memory.session.resumed` — nothing runs and the completion is `failed` `SESSION_PROMPT_CHANGED` with the hash and no failure class (a handover, like a shutdown). The choice is made once the turn is built; the prepared working directory is released as for any end. A beat reports `providerSessionId` only together with its `promptHash`, so none before the turn is built (the server has the session from the claim). | The server records the hash it gets with each session id; a beat without one would blank it. |
| PE-DR05 | **Usage as billed, per provider.** Claude: the result's input total with `cache_read_input_tokens` and `cache_creation_input_tokens` apart; the largest call from each own call's `message_start` (or assistant) usage — a sub-agent's calls are its own context, not the turn's. Codex: per `thread/tokenUsage/updated` `last`: `inputTokens` (cached included), `cachedInputTokens` read, `cacheWriteInputTokens` written (0 on OpenAI); counted only for the turn's own id: before `turn/start` answers it waits, and `thread/resume`'s replay of the previous turn's usage (its turn id) is never counted — the 20–28 k phantom tokens of every resumed Codex turn. The completion's `usage` goes through `completionUsage`: whole, non-negative counts, unknown fields left out. The checkpoint nudge reads `usageContextTokens` (the largest call, else the sum). | Spend, budgets and rotation act on what was billed and how full the context got. |
| PE-DR06 | **Pack skills, loaded:** the runtime lists them by name and description, so “### Pack skills” says so with the skills-first rule (RA-16) and names only the skills that lack something here (`- xlsx (documents@1.0.0) — needs a scratch workspace`) and what to ask for. Not loaded, or not known: the whole list as before. | 1–3 k tokens per call were the CLI's own list again. |
| PE-DR07 | **Codex's tools by name are generated from the contract**: each tool's required arguments, then up to four optional ones marked `?` and `…` for more, with a purpose line written for it (the shape of a nested argument where it isn't obvious: `action {type: "grant_key", params: {keyId}}`, `when {kind: …}`), introduced by how exec reaches them (`tools.mcp__whombat__<name>({…})`, anything else in `ALL_TOOLS`). The list follows what the server serves that agent and turn (no runs or pull requests for a personal agent; a run's own tools in a run turn; `delegate`/`report_back` with teammates; `propose_skill` with “Propose skills”) and nothing that changes between turns. A direct exec call reached the stub MCP server's `tools/call` with no tool search (pinned binary, gpt-6-astra code mode). Cost ≈550 tokens per Codex call. | The discovery call it saves costs ~25 k; a guessed argument costs a retry call. |
| PE-DR08 | **Codex switches, verified against 0.157:** `personality: "none"` on thread/start and thread/resume (strips its “# Personality” section: base instructions 4 148 → 3 395); `-c features.goals=false` (goal tools: Whombat keeps tasks in checkpoints and plans); `-c tools.experimental_request_user_input.enabled=false` (the blocking question Whombat answers empty); `-c agents.enabled=false` in a turn that may not write (sub-agents, as Claude's `Agent` there, RA-15 — `features.multi_agent=false` doesn't override the model catalog's multi-agent version). Without a switch in 0.157, kept: the MCP resource tools, `request_user_input_async` (from the model catalog), `clock.sleep` (usable), and the permission profile's deny list that a guarded turn renders into its environment and permissions messages (~1.4 k tokens per call; for a later Codex). | Tools a turn can't use cost tokens in every call. |
| PE-DR09 | **PE-08 as built:** the request is named by its id when the window or thread shows it (“Joris is asking you in the message above (id …).”, also an automation's message and the agent's own under “More detail”), quoted when it doesn't; a repository instruction file with the same text as one shown before is one line (“web/AGENTS.md says the same as AGENTS.md.”); the Vault is two lines when the agent holds no key and the requester has no entry it lacks a key to — what the Vault is, to use what it holds first, and how a person gives it a key, SSH in short (amends VT-G01 for that case; with an entry or an unheld one the full section stays); teammates' keys only where they differ from their role's usual ones (`handoverLabels(keyRows(roleDefaultGrants))`, as the server labels them), the usual ones once. | Each was paid in every call for nothing. |
| PE-DR10 | **An hour of prompt cache for turns a person paces** (the lead's addition, after Hermes Agent: 63 % of interactive cache writes were cold re-writes after a 5–60 minute gap; an hour saves ~42 % of write cost there and costs ~49 % more on machine-paced turns). Claude turns triggered by `mention`, `dm`, `expand` or `search` set Claude Code 2.1.283's flag setting `promptCacheTtl: "1h"` (the main conversation's TTL; sub-agents keep theirs); every other trigger — schedule, reflect, notify, handoff, handoff_result, automation, run_control, retry, approval_granted/declined, vault_pass, briefing, feedback — sets nothing, so Claude Code's own choice stays (5 minutes on an API key; an hour on a subscription within its limits). An operator's `CLAUDE_CODE_PROMPT_CACHE_TTL` overrides either. Verified: a dm turn's requests carry `cache_control {ttl: "1h"}`, a schedule turn's the 5-minute default. Codex 0.157 has no TTL switch (it sends a `prompt_cache_key` per thread and no retention field): nothing there. | The next message of a person often comes after the 5-minute cache has gone; a machine's next turn doesn't wait. |
