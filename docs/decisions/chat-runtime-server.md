# Chat runtime — the server's part (stream S, 2026-10-19)

Stream S of `docs/implementation/chat-runtime/assignment.md` under `chat-runtime.md` (CR-01…CR-11): a Chat thread's
choice of provider, model, effort and fast replies, the turns that run on it, what answered each reply, and fast replies
on an agent. Contracts 0.96.0 (CT-456…CT-468) and 0.96.1 (CT-469, `messages.send` `runtime`), migration **0118**. The
runner's side is `chat-runtime-runner.md` (CR-R…).

| # | Decision | Why |
|---|---|---|
| CR-S01 | **Migration `0118_chat_runtime`** (expand): a table `chat_thread_runtimes` (the thread's first message as key, cascading with it; burrow, room, the `ChatRuntime`, who set it and when; no row: the thread follows the assistant), `dispatches.runtime` (jsonb, the turn's resolved runtime) and `messages.ran_on` (jsonb, `RanOn`) with `messages.dispatch_id` (the turn that posted it, set together, partial index). A table rather than columns on `messages`: few threads have a choice, removing the message (a deletion, the fresh start, clearing a room) removes its choice by the foreign key, and `messages` stays as wide as it was. Replies are linked to their turn by `dispatch_id` so the completion finds exactly that turn's replies (a run's turn or Whombat's cards may post in the same thread meanwhile). | CR-02, CR-07; one indexed lookup each way. |
| CR-S02 | **Only the Chat's person, only their Chat** (`chatThreadOf`): the root must be a top-level, not deleted message of the person's default DM with their own assistant, in the assistant shell. Anything else — someone else's Chat, the Feedback room, a task chat, a channel, a reply, an unknown id — is `not_found` (`Thread`), so another person's thread is never named; an agent gets `forbidden`. An assistant not on Claude Code or Codex has no choice to make: `validation_failed` “Hazel doesn’t answer with Claude or ChatGPT here.” `chats.runtime` with `?thread=` answers `not_found` the same way. | CR-01, CR-03: the choice is a conversation preference of one person. |
| CR-S03 | **`dispatches.runtime` holds the resolved choice only** (`{provider, model?, effort?, fast?}`), not a whole runtime: the turn runs on its agent's runtime as it is at the claim with those four taken from it (`turnRuntimeOf`; another provider drops `acpRuntime`; working directory, checkout, access and credential source stay the agent's). Every reader of a turn's provider reads it first — SQL `coalesce(dispatches.runtime->>'provider', principals.runtime->>'provider', 'scripted')` (`turnProviderSql`), TypeScript `turnRuntime`/`turnProvider`: the claim's provider filter, the unrunnable sweep (a thread on a provider no runner has is answered with the readiness words, never moved: CR-04), the gateway route (and so `gateway_provider` and the relay), the session parts, fork and recorded session (`memory/sessions.ts`), `DispatchContext.agent.runtime` (so the runner gets provider, model, effort and fast, and `dispatchCredential` the provider's sign-in), usage attribution (`usage.fromTurn`, `turnRunning`), the Work view's queued reason and a failed turn's sentence. | One stored fact read the same way everywhere; a host change while a turn waits still applies. |
| CR-S04 | **Resolved when a turn is queued** (`dispatchRuntimeFor`): the dispatch queue, a quiet wake (an approval's yes, a Vault pass), Try again and a turn queued again after a usage limit (by the trigger of the turn it repeats). Only turns woken in a thread of the person's Chat by something done there follow the choice: `mention`, `dm`, `expand`, `retry`, `approval_granted`, `approval_declined`, `vault_pass`, `run_control` (a run started in the thread), `notify`, `undo_requested`. Automations, schedules, briefings, Feedback assessments, reflections, search answers and handed-over work keep the assistant's own (CR-03). A choice equal to the assistant's own runtime resolves to null. A change of the thread's choice updates its turns still queued in the same commit; a running turn finishes as it started. | “From the thread's next turn” includes a turn that hasn't started yet. |
| CR-S05 | **Checks and words** (`checkChoice`, the same for `chats.setThreadRuntime`, `chats.start` and `messages.send`), `validation_failed` on `runtime`: the provider must be ready for this person (`CHAT_RUNTIME_COPY.notSetUp`: “ChatGPT isn’t set up on this Whombat.”); a model of its list when there is one (“ChatGPT has no model called “gpt-x” on this Whombat.” — Chat's provider names, ME-04's sentence); an effort the model takes (“GPT-6 Luna doesn’t take High effort.”, `chatModelLabel`); fast replies on only where the model offers them (`fastNoneText`) and never through the AI gateway (`CHAT_RUNTIME_COPY.fastGateway`); fast off where there is nothing to turn off is dropped, not refused. Without a list any model and effort pass (ME-04). Stored as nothing when equal to the assistant's own (`chatRuntimeEquals`). | ME's rules and Chat's words; a client sending the whole choice is never refused for a no-op. |
| CR-S06 | **A new thread's choice goes with its first message**: `chats.start` and (0.96.1, CT-469) `messages.send` check `runtime` before anything is posted — a refusal sends nothing — and store it in the message's commit, before the assistant's turn is queued (the queue runs after the commit), so the first answer runs on it. Only a person's top-level message in their own Chat keeps it; a reply, another room, the Feedback room and the crew shell ignore it. | CR-02; the Chat box sends with `messages.send` (files need it). |
| CR-S07 | **Stored, signed and told**: one commit `set_chat_thread_runtime` writes the row (or removes it), a signed `chat.thread_runtime_set` event (System, no text: who chose what, for the log's All) and the `chat.thread_runtime` frame on the person's `me` topic. A choice that doesn't change writes nothing. `chats.threads` lists each Chat thread's `runtime` (null: the assistant's own; the Feedback room's always null). | CR-02; every write through the pipeline, every device told. |
| CR-S08 | **What answered a reply, at post time** (`ranOnForPost`): the assistant's own message in its person's Chat while it acts in a turn of that room (its dispatch scope) whose runtime is Claude Code or Codex — the turn's provider, model (`chatModelLabel` over the runner's list; null when no model is named and no list says the default), effort (`turnEffort` with kind `chat`) and fast (`turnFast`, else the model's own default; never through the AI gateway, CR-R08). Not Whombat's cards posted for it (approval, run, plan, failed turn), not outside a turn, not in Feedback, task chats or channels. | CR-07: the reply shows what it ran on as soon as it appears. |
| CR-S09 | **Corrected at completion** (`correctRanOn`, in the completion's transaction, any outcome): the runner's `ran` (model, effort, fast, `fastSkipped`) and, when it reports `modelFallback`, `modelSkipped` = the model asked for; each changed reply gets a `message.updated` frame. An older runner without `ran` keeps the post-time values, except that a `modelFallback` it reports still says the default answered. | CR-07, CR-08; never a reply that claims a model it didn't run. |
| CR-S10 | **A thread's model refused is the reply's, not the assistant's**: a turn with a resolved runtime neither writes nor clears `principals.model_fallback` (ME-05 stays about the assistant's own model). | CR-08. |
| CR-S11 | **Superseded by HN-06 and HN-07 (hermes-native.md)**: a started thread doesn’t move to another provider; a resumed Hermes session is moved to the turn’s model with `session/set_model` and isn’t used on another provider (HN-L05…HN-L08). **Sessions**: the session parts read the turn's runtime, so a thread moving to another provider or model starts a fresh session there (Whombat's own history of the thread comes along as usual) and the session row records what ran; effort and fast stay out of the fingerprint (CR-R03). | A provider's session can't be resumed by another; speed is per turn. |
| CR-S12 | **Superseded in part by one-person.md OP-S09**: readiness checks the person's own sign-in, with no personal or team agent, requester or organisation key; the usage line's rule holds. **Readiness for Chat** (`providerReadiness`): `agentReadiness` with the provider swapped (licence, a connected runner with that provider) and, on a managed appliance, the sign-in this person's turn would run on — a personal assistant's person's own (which `agentReadiness` leaves out for personal agents), a team agent's source, each requester's: the caller's — unless the provider's turns go through the AI gateway. **Usage**: the `five_hour` window with a known share of the `subscription_usage` row of the account the turns run on (the person's for their assistant); null through the gateway, for an organization key, an API key or without a known window. | CR-04, CR-09: greyed exactly when a turn would be refused. |
| CR-S13 | **`chats.runtime`**: `default` is `chatRuntimeOf` of the assistant's runtime; `canSetDefault` is whether the caller may change that runtime with `agents.update` today — the assistant's own person (`ownerOnly`) holding `agents.manage` (every person does); `providers` both, with the runner's lists (`ProviderModel.fast` as stream R reports it), `fastBlocked: 'gateway'` while the burrow's switch for that tool is on. | CR-01, CR-03, CR-05, CR-06. |
| CR-S14 | **Fast replies on an agent** (`agents.update`, `agents.hire`): `runtime.fast` is kept for Claude Code and Codex (dropped for ACP and scripted, as ME-D07); turning it on for a model the list says has none is refused with `fastNoneText`, off there is dropped; a new provider clears model, effort and fast (ME-01). Keys line `agentFastChangeText` (“Turned on fast replies for Hazel”) for a change sent explicitly, or when going back to the model's own speed changes what runs; a new provider that only clears it says only “Moved Hazel to codex”. The profile line (`agentModelSummary` with “· Fast”) is the clients'; the server stores `fast` and serves it in `Agent.runtime`. | CR-10. |
| CR-S15 | **Feature `chat.runtime` in both shells**: Configure → Model's Fast replies is everyone's; Chat's button shows only where Chat is (`chat.channel`), and the thread choice works only in the assistant shell's Chat. | CR-11. |

## Words added in code (not yet in contracts' text)

effort.”, “{Name} doesn’t answer with Claude or ChatGPT here.”; `forbidden`: “Only the person whose Chat it is chooses
what answers there.” (agents only; no app sends it). Everything else is `CHAT_RUNTIME_COPY` / `fastNoneText` /
`agentFastChangeText`.
