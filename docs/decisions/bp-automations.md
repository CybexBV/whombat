Buzz-parity workstream C (`docs/implementation/buzz-parity/PLAN.md`), bound by BP-06, BP-07, BP-09 and BP-10
(`buzz-parity.md`). User guide: `docs/automations.md`.

## Decisions

| # | Decision | Reason |
|---|---|---|
| BP-C01 | **An automation is a row with immutable versions.** `automations` holds the name, status (`draft` · `published` · `disabled`), the current version and a mutable draft (`draft_json`, kept even when invalid, with its problems). Publishing validates the draft and inserts version n+1 (`definition`, `definition_hash` = sha256 of canonical JSON, publisher, time) and clears the draft. Editing a published automation edits its draft; the live version keeps running until the next publish. A run stores the definition it runs and its publisher, so a later publish never changes a run in flight. | Versions are what approvals and runs bind to (BP-09). |
| BP-C02 | **Definitions are strict JSON, version 1.** `{version, conversationId, triggers[1..4], steps[1..20], limits}`; every object is `.strict()` so unknown fields and unknown step kinds are rejected (no silent ignoring on import); 64 KB cap; unique step ids; templates and conditions may only read earlier steps; a condition may only skip forward, so a definition cannot loop. Keys are never part of a definition: an imported or agent-written file grants nothing. Export is `{whombat: "automation", name, description, definition}`. | Import must not be a way to carry authority or hidden behaviour. |
| BP-C03 | **Who does what.** Any person drafts. Publishing, switching on/off, setting keys, test runs and Run now need “Hire agents and change their keys” (`agents.manage`, people only: agents are Blocked and logged). The webhook (on/off, new secret) needs an owner (`burrow.manage`). Pause / Resume / Cancel: people in the run's conversation. Settling an uncertain step: `agents.manage` and in the room. Agents only draft (`draft_automation`): a new automation, or the draft of one they created or were asked to draft (“Describe it”); personal assistants never draft (a draft is readable burrow-wide, PA-09). | Publishing an automation hands it authority, like hiring an agent. |
| BP-C04 | **Execution identity (BP-09).** Each automation has its own principal: agent-shaped, `principals.system = 'automation'`, not on the roster, never dispatched, no personal keys (GitHub's system-principal pattern). It signs everything the run does. Its effective authority for every step is its own grants ∩ the publisher's current authority: the publisher must still be a person of the burrow allowed `agents.manage`, a member of every conversation the step acts in, and allowed the step's key (`keyDecision` = strictest of the two decisions). Re-checked inside the step's transaction, and again inside an approval's `StartExecution` (a guard). The trigger's author (a person, an owner, an agent, a webhook sender) adds nothing. A test run of a draft acts with the tester's authority. The keys an automation can hold are only what steps need: `pr.open` (repo-scoped) and `messages.external`. Merge into main stays people-only (no step merges). | No second, less-protected mutation path. |
| BP-C05 | **Durable engine (BP-10).** One loop per server process (`AutomationEngine`), active only while holding a session-level `pg_try_advisory_lock` on a reserved connection; a second process stays passive and retries every 5 s. Tick every second (and at once after a dispatch finishes or an approval continues a run). Runs are leased (`lease_owner`, `lease_expires_at`, 60 s) with a fencing token (`fence`) every step commit checks; the active engine clears leases of dead engines at boot. Every transition is one commit signed by the automation principal whose effect (prompt message + dispatch row, the post, the approval) and the step's new state commit together — outbox style: a crash leaves both or neither. | No in-memory hook decides what happens next. |
| BP-C06 | **External effects are never retried blindly.** `http_callback` and `open_pull_request` are marked `running` with an idempotency key (`run:step`, one per operation: the same on every retry and on a person's “Try it again”, so a receiver that acted and still answered with an error can tell) first, then done. A `running` step found by an engine that did not just mark it (a crash) is reconciled (a PR for the branch exists → done) or set `uncertain`, the run `needs_review`, and a person says “It happened” / “It didn’t” / “Try it again” (signed). Retries (`retries` 0–3, backoff 30 s × 4ⁿ) only follow failures whose outcome is known. Exactly-once is not claimed. | Unknown outcomes need a person, not a guess. |
| BP-C07 | **Triggers read the signed `events` table.** A per-burrow durable cursor (`automation_cursors`), started at the latest event when an automation is published or switched on (history never replays). Each scan reads up to 500 events in order and creates runs and moves the cursor in one transaction. Dedupe: unique (automation, version, trigger key) with keys `evt:<event>`, `sched:<instant>`, `hook:<delivery>`, `manual:<id>`. Messages: agents' and thread replies only when the trigger says so; reactions: `on` only. GitHub (mirrored by the poller): `pr.opened`, `pr.updated` with a moved head, `checks.completed` when a round finished (the event has text), `pr.approved/changes_requested/commented`, `branch.pushed` — switched-on repos only. | A durable, ordered source that survives restarts. |
| BP-C08 | **Loop limits.** An event's causal depth: an automation's own post (found through its steps' messages) or an agent's message in a conversation while one of its automation dispatches was running there is caused by that run (depth + 1, chain + automation). Depth > 2 triggers nothing; an automation never triggers itself (its principal or its id in the chain). Agent→agent mention chains keep `MAX_AGENT_CHAIN_MESSAGES`. Automation posts never dispatch anyone by @mention (only `dispatch_agent` does). Rate limits: runs per automation per day (`maxRunsPerDay`), 120 runs per burrow per hour, `maxConcurrentRuns` (queued beyond it). | Automations talking to automations must stop. |
| BP-C09 | **Approvals bind to the exact action (BP-09).** `approvals.action_hash` = sha256(canonical {action, deferred command input, binding}) with `action_binding` {automation, version, run, step#attempt, commit sha}; the hash is in the signed `approval.requested` payload (a hash reveals nothing of a private approval, BP-06). `StartExecution` recomputes it from the row, compares with the signed event and verifies that event's signature: any difference refuses (“What would run is not what was approved…”). The hash is required: an approval without one can't be approved and never runs (“Whombat can’t check that this is what was approved…”), and migration 0053 withdrew the open ones that had none. For an automation's approval a guard then re-renders the input from the definition and the run's outputs, reads the branch head now, and refuses a mismatch as stale; the run asks again with a new approval. `request_approval` steps are `custom` approvals (key label “Approve requests”) whose deferred command `automation.continue_step` continues the run; an integration step whose key asks defers the integration command itself (`open_pr`). Races are serialized by the burrow lock and compare-and-set (approve twice → one decision; approve vs cancel → the guard refuses a cancelled run). | A changed input, commit or version cannot inherit a stale approval. |
| BP-C10 | **Approval recovery (BP-10).** `ApprovalEngine.recover()` runs at boot (as the active engine) and every minute: executions left `running` by a process that is gone (started before this boot, or 15 min ago) are settled — a reconciler per deferred command says done / not done (put back to idle and run once more through the normal path) / unknown; unknown fails as uncertain (“Whombat stopped while this was running, so it may or may not have happened…”), never run twice; GitHub deploys (completed by the poller) are left alone. Then every approved-but-unexecuted approval is re-evaluated, so a decision made just before a crash still executes. | A crash no longer strands approvals. |
| BP-C11 | **`http_callback` only to destinations an owner approved.** https only (and `outboundRequest`'s SSRF rules); an owner publishing a version that calls a URL approves it (`automation_destinations`); at run time the destination must be approved, the publisher still an owner and the automation hold “Message people outside the burrow” at `can` (an `ask` blocks: put a `request_approval` step before it). The request carries `Idempotency-Key`; a 2xx = done, another answer below 500 = a refusal (failed, retried as the step says), a 5xx = uncertain (it arrived, so the receiver may have acted), refused before connecting = failed, any other error (a timeout, a dropped connection) = uncertain. | Outbound calls are the easiest exfiltration path. |
| BP-C12 | **Inbound webhooks, optional and off by default.** `POST /webhooks/automations/:id` (the `/webhooks` prefix the web server reserves): `X-Whombat-Timestamp` (±300 s), `X-Whombat-Delivery` (dedupe per automation), `X-Whombat-Signature: sha256=HMAC(secret, "<timestamp>.<raw body>")`, JSON object ≤ 64 KB. Unknown, disabled, unsigned, stale, oversize: the same 404 body. The secret is sealed with the master key (AAD `automation:<id>:webhook`), shown once. Ordinary self-hosted use needs no public endpoint. | Uniform answers tell a stranger nothing. |
| BP-C13 | **Superseded by automation-chat.md AT-01, AT-12, AT-18**: the apps have no editor; automations are made by talking to the agent. **UI.** Web: a sidebar row “Automations · N” shown once the server answers `automations.list` (the fixture world of the visual comparisons has none, so the reference sidebar is unchanged), `/:burrow/automations` (list, New: from a template · describe it · import a file · blank), `/:burrow/automations/:id` (Steps form ↔ JSON view of the same draft, validation as you type, Save draft, Publish, Switch on/off, Test run, Run now, Discard draft, Export; tabs Runs and Keys and webhook), `/:burrow/automation-runs/:number` (step timeline, links to messages, requests, agent runs and PRs, Pause / Resume / Cancel, settling uncertain steps). Settings' page language, tokens only. Android: an Automations row on the Agents tab → list with on/off and recent runs → run detail with Cancel / Pause / Resume; a step waiting for a person opens the existing approval screen. | Not mocked (B-05): nearest patterns. |
| BP-C14 | **Two templates** (`core/automations/templates.ts`, pure, filled with the burrow's own rooms, agents and repo). “Suspected bug”: a message with a keyword or 🐛 in a channel → investigator → evidence posted in the thread → a person approves → developer on `fix/bug-<run>` (*superseded by BP-C26: `feat/bug-<run>`, with checkouts and a verdict*) → reviewer → pull request through `open_pr` when the repo is switched on and the key allows (else the prepared PR is posted for a person) → report in the original thread. “Scheduled repository check”: cron (default weekdays 09:00 Europe/Amsterdam, missed: run once, overlap: skip) → an agent checks the repo (in its working directory when checked out there) → a condition on `ACTIONABLE:` → a report only then. | Working, installable, importable. |
| BP-C15 | **Superseded in part by BP-C40**: the result is only the agent's words in the prompt's own thread, never a top-level reply. **Dispatches.** `dispatch_agent` posts the automation's prompt (mentioning the agent, dispatching no one) and inserts a dispatch with the new trigger `automation` in the same transaction; the normal runner protocol applies (keys, one turn per agent and room, leases, retries). The result is the messages its agent posted after the prompt (in the prompt's thread, or top level where the runner posts a top-level turn's final text) plus the dispatch's final state and reported tokens. The runner's `finalize` nudges the engine (one additive line). Cancelling a run cancels its dispatches; the runner stops at its next beat. | The existing pipeline, not a side door. |
| BP-C16 | **`Agent.system`** (`github` \| `automation`, optional) is exposed on principals so lists of agents (web sidebar, mobile) leave system principals out. | They sign things but are nobody's colleague. |
| BP-C17 | **Templates and conditions are data.** `{{trigger.text}}`, `{{steps.<id>.text}}`, `{{run.number}}` are filled in as plain text (a value is never re-read as a template, BP-07). Conditions are a small language (`contains`, `startsWith`, `endsWith`, `lower`, `length`, `isEmpty`, comparisons, `&&`, `\|\|`, `!`) parsed by hand — no `eval`/`Function`, no regular expressions from input, ≤ 500 characters, nesting ≤ 24; only `trigger.*` and `steps.*` are readable. | Retrieved data is data; conditions cannot run code. |
| BP-C18 | **Schedules.** Five-field cron (lists, ranges, steps, names; 7 = Sunday) read in an IANA zone, or an interval ≥ 5 min counted from when it was switched on. DST policy per trigger: a local time that doesn't exist → `shift` (the same distance after the gap starts, 02:30 → 03:30) or `skip`; a repeated one → `once` (the first) or `twice`. A fire noticed more than 2 min late was missed: `skip` drops it, `run_once` runs the newest missed fire once (at most `maxCatchUp` considered). Overlap: `skip` records a skipped run, `queue` queues one, `cancel_previous` stops the running one (and its dispatch). `next_fire_at` is the durable timer. | Explicit, testable behaviour around downtime and DST. |

### Security review fixes (fix/automations)

| # | Decision | Reason |
|---|---|---|
| BP-C19 | **Run now needs a manual trigger and the caller in every room.** Run now (`test: false`) is refused unless the live version has a `manual` trigger (“This automation starts on its own. Try it with a test run instead.”); its `text` stands in for a trigger only where a person starting it by hand is the trigger. A test run (draft, or the live version when there is no draft) always acts with the tester's own authority (`publishedById` = tester). Both need the caller in every room `definitionConversations` names (“Join every room this automation uses to run it.”). | Starting a run with the publisher's authority and your own prompt must not reach rooms you can't read (SEC-AUTO-RUNNOW). |
| BP-C20 | **Content rooms per step.** `stepContentRooms(definition, runRoom)` (core, pure) gives each step the rooms whose content may be in its input or output: the room it acts in (dispatch/post: its `conversation`; approval and PR: the run's room), the run's room when it reads `trigger.*`, and transitively the rooms of the steps it reads (templates, conditions, `attachFrom`). Computed from the definition stored on the run, so it is fixed per run (no new column). The publisher must be in the run's room and all of a step's content rooms before the step (and in `automation.open_pr` and the approval guard); a trigger event in a room the publisher is no longer in (or a publisher who may no longer manage agents) creates one **skipped** run per automation, version and hour with `Blocked: …` and a signed `Blocked` event (`automation.run.skipped`, no message text), instead of a run. Viewers: a step whose content rooms they aren't all in is returned `redacted: true` with `inputSummary`, `output`, `messageIds`, `dispatchId`, `runNumbers` emptied (REST per viewer; realtime frames are stored in full and the hub calls `personalizeAutomationFrames` per recipient — fail closed: an unknown run redacts every step). | Trigger content and an agent's answer in a private room must not flow or show anywhere its readers don't reach (SEC-AUTO-TRIGGER, SEC-AUTO-RUNNOW). |
| BP-C21 | **Publishing is bound to the reviewed draft.** `automation.publish` takes `definitionHash`; the server locks the row, validates the draft and refuses a different hash (“The draft changed since you looked at it. Check it again, then publish.”). `Automation.draftHash` exposes the valid draft's hash; the web editor sends the hash of the definition on screen (after saving it when edited). | A draft swapped between review and publish must not go live with the reviewer's authority (SEC-AUTO-DRAFT). |
| BP-C22 | **Superseded in part by automation-chat.md AT-15**: the agent proposes changes to any of the person's automations, live ones too, as plans the person turns on. **Who edits drafts.** People who may publish (`agents.manage`, today every person) or the person who started an automation that was never published may save or discard its draft (`AutomationDetail.canEditDraft`; the editor is read-only otherwise). Agents write drafts only with `draft_automation`: a new automation, or one they created or were asked to draft, **and only until its first publish** (“This automation is published, so only people change it now. Draft a new automation instead.”). | An agent's drafting right must end where a person's authority begins (SEC-AUTO-DRAFT). |
| BP-C23 | **Webhook signature covers the delivery id.** `X-Whombat-Signature: sha256=HMAC(secret, "<timestamp>.<delivery id>.<raw body>")` (supersedes the string in BP-C12); dedupe by delivery id is unchanged, so a replay under its own id starts nothing and under a new id fails the signature. The string is unambiguous: a delivery id is `[A-Za-z0-9._:-]{1,200}` (no whitespace, no `{`) and the body must be a JSON object. Senders must update their signing code. | A captured delivery must not start another run (SEC-HOOK-REPLAY). |
| BP-C24 | **Superseded by one-person.md OP-S69**: every room is the person's, so summaries and frames name every room. **Room names only for their members.** `Automation.triggerSummary` names a room only for viewers in it and says “a private room” otherwise; `automation.updated` frames are stored with no room names and re-rendered per recipient by the hub. | Private room titles are not burrow-wide information. |
| BP-C25 | **A message shows only its own files; `attachFrom` copies.** `loadMessages` renders an attachment only when its `messageId` is the message (or, inside the send that claims it, it is the author's own unsent upload for that room). `attachFrom` copies each source file as a new attachment row of the new message (same blob and hash, uploaded by the automation, linked with a signed `attachments.attached`), after checking that the publisher is in the source message's room and that every member of the destination room is also in the source room; otherwise the step is Blocked (“That file was posted in a room with fewer people, so it can’t be shared where more would see it.”). Copies count toward the burrow's file quota like any row (the bytes are stored once). | Attachment ids must not carry metadata (or links) of files into rooms that can't read them (SEC-ATT-META). |

### Golden path fixes (fix/golden-path)

| # | Decision | Reason |
|---|---|---|
| BP-C26 | **Coding steps have a workspace.** `dispatch_agent` takes `workspace: {repo, branch?, base?, access: write\|read}` (strict; `branch` is a template and required for `write`; `base` defaults to the repo's default branch; a `read` without a branch reads the base). The step renders it when it runs (the repo must be switched on for agents, the names valid) and keeps it on the step row as `output.workspace`; `runtime/context.ts` gives an `automation` dispatch that checkout as `DispatchContext.workspace` (new field `access`, default `write` for runs and branch rooms). **`write`**: the agent's branch key (`branchWriteKey`, ∩ the publisher, BP-C04) is decided before the agent is asked — `can`: the prompt and the dispatch go out; `asks`: a person approves “Let Banjo work on feat/x in owner/repo” (a `custom` approval with the branch key's id, bound to run, step and attempt like BP-C09; the guard re-renders it and refuses when the key became No), after which the step asks the agent and the git credentials route runs that dispatch's push for exactly that repo and branch under the approval (`authorizeGit` with `onAsk: 'apply'`, re-checked inside the command; any other push still asks); `no`: the step is Blocked (a signed Blocked event about the agent). **`read`**: the runner fetches as usual, then exports the branch's files (GitHub's copy when fetched) without git metadata into a scratch directory outside the denied workspaces root, removed after the turn; the sandbox is read-only whatever the keys say and nothing is pushed. A read of a branch other than its base puts that branch's commits, stat and patch (24 KB, cut with a note) in the prompt as `[[changes …]]` data. The Suspected-bug template works on `feat/bug-{{run.number}}` (the `feat/*` convention the key catalog is built around: a developer holds “Read and write feat/* branches” at Can), gives the investigator a read-only checkout of the base and the reviewer one of the branch, and says which keys it needs in its description. | An automation's developer must get a real, isolated, writable worktree through the same keys, and investigators and reviewers must read the actual code without being able to change it. |
| BP-C27 | **Outcomes are checked, not assumed.** A `write` step succeeds only when its turn finished `done` **and** GitHub has at least one commit on the branch that the base doesn't (`branchExists` + `compare`; the runner pushes before it completes the dispatch); otherwise it fails with “Banjo finished without new commits on feat/x.” plus the first line the agent said. A step with `verdict: true` needs the agent's last verdict-bearing reply to start with “Approve” or “Changes needed” (case, markdown and a leading quote or bullet ignored; “Approved with…” is not a verdict) and outputs `verdict: approve \| changes_needed` for conditions; any other reply fails the step. The template reads it in a condition (“Did the review approve it?”, `steps.review.verdict == "approve"`, else stop): changes needed ends the run without a PR, the reviewer's reply being the outcome in the thread. An agent's own words go into an error only when the step read and acted in the run's room alone (BP-C20). A reviewer must be a different agent from the developer (the template refuses the same one). | M1: a step used to count as done whatever the agent said. |
| BP-C28 | **Failures are said where the report was.** When a run fails (a Blocked step included), is stopped (a decline, a person's Cancel) or needs a person, the transition's own commit posts “Automation run #4 of “Suspected bug” failed. {reason} {link}” (“stopped.”, “needs a person to check a step.”) in the run's thread — once per such change, only when the run has a thread and its publisher is still allowed and in the room (the automation may post there). The link is `{PUBLIC_URL}/{burrow}/automation-runs/{n}`. An `open_pull_request` step whose PR can't be opened (GitHub refuses, or the approved `open_pr` fails) and whose `otherwise` is `post_payload` posts the prepared pull request in the thread with “(opening it failed: …)” and succeeds with `opened: false`. | M2 and M1: the thread the person reported in is where they look. |
| BP-C29 | **An approved `start_run` wakes its agent.** When a person approves an agent's deferred `start_run` (its branch key asked), the run is created by the approvals engine and a run-mode turn is queued for that agent in the run's conversation (`run_control`, like Resume), so the work goes on in its workspace; the run prompt says it is live “a person approved it, or resumed it after a pause”. Outside automations too. | B1c: approving created a run nobody worked on. |
| BP-C30 | **Guarded read-only Claude turns can read.** Read, Grep and Glob (no LS, writes or shell) in every guarded read-only turn, confined by `canUseTool` to the working directory (real paths, so links out are refused), the turn's pack skill files and its own attachment copies (by exact path); credential paths and `WHOMBAT_HOME` stay denied, except where the working directory itself lies under a denied root (an export or worktree), where being inside it decides. Codex already reads in its read-only sandbox. The prompt says “Your working directory is a read-only checkout of … : read the code there with your own file tools” and, instead of the general “start a run” line, that it is there to read and answer, not to start a run or ask for keys to write (in the first live run the reviewer followed the general line, was Blocked and answered “Changes needed”). | B1d / M3: investigators and reviewers could not read the code. |
| BP-C31 | **Superseded by one-person.md OP-S71**: the person's turn searches every room the agent is in; an outsiders' turn searches nothing. **An agent's search keeps to its audience.** C-10 gates search by membership; for an agent that meant everything *it* can read, which it could then repeat to a room with fewer readers (the review saw evidence from another room re-posted). Search from a dispatch now also requires every other member of the dispatch's conversation to be a member of a hit's conversation (an answer keeps its asker rule) — the same audience rule knowledge sources follow (bp-memory BP-B09, BP-B10); checkpoints only hold what the agent wrote in that conversation. Burrow-wide results (PRs, canvases without a room) are unchanged. The investigator's prompt also says not to quote a room some of the thread's people aren't in — a reminder, the search rule is the enforcement. | m5: consistent rules, enforced by the server, not by a prompt. |
| BP-C32 | **Thread reports.** The Suspected-bug trigger counts thread replies (`includeReplies: true`); a run's thread is its report's thread root. While an automation has a run going (queued … needs review) for a thread, another message or reaction in that thread starts no new run of it; the automation's own posts never trigger it (BP-C08). | m6: a report posted in a thread works, and talk in the run's thread doesn't start it again. |
| BP-C33 | **Smaller fixes.** Deciding or undoing a request you can't see answers the same 404 as a missing one (m1). Step outputs on the run page go through the chat's message renderer (`MessageText`; formatted text arrives with it from main's `RichText`) (m3). Run pages and Android runs say “2 new commits on feat/bug-3.” and “Verdict: Approve.”. The agent step form has CODE (No checkout · Reads a checkout · Works on its own branch), REPOSITORY, BRANCH and REPLY (Anything · Starts with “Approve” or “Changes needed”). | Review findings m1, m3. |
| BP-C34 | **Template agents don’t hand work on by @mention.** The Suspected-bug prompts tell the investigator, developer and reviewer not to @mention other agents; the automation dispatches each step. (Final end-to-end review: the investigator's “@Banjo would need to make the change” started a separate Banjo turn before the approval; he wrote nothing — no checkout — but a mention is a normal dispatch under the mentioned agent's own standing keys, which an automation's approval does not gate.) This is guidance, not enforcement: an agent's own keys remain the boundary for what a mention can make it do. | Keeps the approval step the one place implementation starts, and avoids duplicate turns and cost. |

### Final security re-review fixes (fix/final)

| # | Decision | Reason |
|---|---|---|
| BP-C35 | **Superseded by one-person.md OP-S71**: the person's turn reads any room the agent is in (`withinTurn`); an outsiders' turn reads only its own conversation. **Every agent read keeps to its audience, not only search.** `read_conversation` (a page or a thread) and `canvas_read` of a room's canvas (`mcp/tools.ts` `withinAudience`) need the target to be the dispatch's own conversation, or every other member of the dispatch's conversation — people and agents — to be a member of the target; a canvas without a room stays the burrow's. Answer mode keeps its own rule (the asker must be a member). Otherwise `forbidden`: “Not everyone in the conversation you are working in can read that one, so you can’t read it from here.” The other agent reads were checked and already keep to the dispatch: `read_attachment` (files on messages the dispatch was given, in its conversation), `recall` (its conversation's knowledge; agent knowledge by BP-B10; burrow knowledge is everyone's), `search` (BP-C31); run tools only touch the agent's own runs. Consequence: what an agent reads from a wider room can't be carried into burrow knowledge through `remember` from there (SEC3-MEM-WIDEN-BYPASS). | SEC3-AUDIENCE: search followed BP-C31 but reading the room by id did not, so the same agent handed a private room to a wider one. |
| BP-C36 | **A branch key is classified against the repository's real default branch** everywhere: `branchDecision` (automation steps, the approval guard) and the runner's `sandboxFor`. The step's `base` (or a PR's base) says what to branch from, never what the branch is; `DispatchContext.workspace.defaultBranch` carries the repo's. `main` with `base: feat/x` is still main: merging into main stays people-only. | L3: `branchWriteKey(branch, base)` turned `main` into a shared branch when the base was something else. |

## Known limitations

- `http_callback` against a real HTTPS endpoint is covered only by review (a test HTTPS endpoint with a trusted
  certificate is not available); `safety.int.test.ts` answers the call with a stand-in receiver for success, the key
  kept across retries, refusals and the uncertain outcomes.
- A causal chain through an ordinary @mention (automation → agent A → A mentions agent B → B posts) is attributed
  to the automation only for A's messages; B is bounded by the agent chain cap instead.
- Guarded read-only Claude turns now read their working directory (BP-C30); the repository-check template still has
  no `workspace` (it reads a checkout in the agent's working directory when there is one).
- Approval cards stay top level in the run's room (as every approval card), and `open_pr` posts “Opened PR #N” in
  the pull request's branch room; everything else a run says is in its thread. The PR body (report, the developer's
  and the reviewer's replies) goes to GitHub and that branch room by the template's design (`pr.open`).
- A shared-branch push after an approved agent `start_run` still asks per push (only automation coding steps carry
  their approval to the push, BP-C26); its turn is writable now (BP-C37), so the commit is made and the push waits.
- Codex denies the runner's scratch space entry by entry when a turn's directory is inside it (BP-C38): a directory
  another turn creates there during the turn is not covered (Codex's rule compiler, as for `~/.config`).
- The web composer still offers system principals for @mentions (mentioning one wakes nobody).
- Live prompts come from `apps/runner/src/prompt.ts`, which renders an automation's dispatch like any trigger message
  (“{automation} is asking you: …”); `persona/index.ts` only gained the exhaustive `automation` case. Resumable
  checkpoints for `dispatch_agent` steps (task key `automation:<runId>:<stepId>`, reserved by Workstream B) are not
  wired yet.
