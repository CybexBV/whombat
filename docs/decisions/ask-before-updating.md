# Ask before updating

John, 2026-11-16: opening the code proves nothing about what we ship to a box, because we sign the updates. The owner
gets a switch so that no new code runs on their Whombat without their yes. Updates still install by themselves unless
they turn it on.

| ID | Decision | Why |
|---|---|---|
| ABU-01 | **“Ask before updating” is the owner's switch, off by default.** It sits in This Whombat → About, under Updates, on the web and the phone. Off, updates install by themselves as before. On, every update downloads and is checked as always, then waits until an owner presses Update now. It shows only when the box's manager reports the setting (`update.askFirst`): a manager that can't hold updates shows no switch. | Most people want updates without thinking about them. The ones who want the last word get it in one place. |
| ABU-02 | **The box's manager keeps the setting and enforces it**, in its own update journal (`/v1/update/ask`, `/v1/update/approve` on its socket, the runtime only). Neither the app nor control decides: control has no device operation that sets it or approves an update, and a release signed and assigned by us still waits. | The point is that Cybex can't push code past the owner. Only code already on the box, which the owner trusted, can enforce that. |
| ABU-03 | **An approval covers one release.** The owner approves the release shown (`appliance.update.install {release}`); a newer one assigned meanwhile waits for its own yes, and a release that no longer waits is refused (`conflict`). An approved update then installs at the next safe moment like any update: it still waits for running work, a backup it needs and the maintenance window. Turning the switch off lets one that waits go ahead the same way. | The owner says yes to what they saw, not to whatever comes next. |
| ABU-04 | **What waits and what doesn't.** Every release we offer waits, a runtime-only, host or rollback release alike, on commercial and community boxes. Going back to the release that ran before, after an update failed its checks, doesn't wait: that code was already approved. | A rollback we sign is new code for the box too; undoing a failed update isn't. |
| ABU-05 | **The owner is told once per release.** While an update waits for them, the Inbox has one item, “An update is ready”, which opens This Whombat's updates, and the Updates section shows the version with Update now. The item goes when it installs or the switch goes off. It starts on (`update.owner`): the owner asked to be asked, and an update nobody approves leaves security fixes out. | A switch that holds updates silently would leave boxes on old code forever. |
| ABU-06 | **Only the owner decides.** Both operations are `never` for the assistant: it can explain the switch and point to it, but neither turns it off nor approves an update. Each change is a signed event in the appliance's audit log (`update.ask_set`, `update.approved`) with the release. | Something acting for the person, or a prompt sneaking into a turn, must not be able to wave an update through. |
| ABU-07 | **Control hears that the box holds the update**, not why: the manager reports an owner wait to control as `hold`. | Control's contracts before 4.2 refuse an unknown reason, and the reason is the owner's business. |
| ABU-08 | **The box's own screen can turn the switch off.** In the recovery menu (hold Space at power-on), choice 7 turns *Ask before updating* off, after the disk recovery key or a typed word like the menu's other choices; the update that waited then installs by itself once the box runs again (appliance MG-160, NX-514). There is no approval at the box, only off. The journal's history records it; the appliance's audit log can't, since the runtime isn't running. | A release that breaks the apps would leave its own fix waiting for a yes nobody can give. The box has no console login, so the recovery menu is the owner's way in, and whoever stands at it can already export or erase the data. |
