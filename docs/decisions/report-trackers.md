# Report trackers through automations (TA)

John, 2026-10-10: a customer's report system that already keeps its tickets should reach Whombat through automations,
not through the feedback module. That module was built for the website widget, where Whombat itself keeps the reports;
for a tracker that keeps its own, it kept a second copy of every report and synced status both ways
(`feedback-sources.md` FBS-01…FBS-22). Automations treat GitHub issues the other way round — the issue stays on GitHub,
the automation's thread is the conversation about it (AR-08, AR-12) — and since AR-24…AR-41 they assess in plain
words, fix on an opt-in and open the pull request. A tracker's reports take that path: **the tracker is a connection, a
new report is an automation trigger, and the assessment is written back by a step**. Contracts 0.69.0 (CT-325);
whombat-app `docs/decisions/report-trackers.md`.

Everything of `bp-automations.md` (BP-C…) and `automation-recipes.md` (AR-…) holds unless a row says otherwise, and so
do the trust rules of `feedback.md`/`feedback-sources.md` that this replaces: a report is untrusted data, the reporter's
name and email never reach an agent, the customer hears only from people, Whombat never sends `available`.

## Report trackers, their drivers and the bridge (TA-72…TA-125)

John, 2026-11-15: the first tracker Whombat followed is a customer's product, so Whombat's public code and releases
name no product: a tracker's own part is a driver, owner-installed code, and the box that ran the first tracker kept
every automation through the move with no chore for him. The council agreed the design in four rounds (design v2 →
v4; 8, 7, 8, “approve once fixed in the text”). TA-72…TA-125 are that design as built in the bridge release (0.268.0)
and where the code bent it; the cut that followed (TA-126…) removed the bridge, so its rows are history. TA-01…TA-71 and
TA-D… still hold for every tracker; where they describe a tracker's own rules (its addresses, tokens, statuses,
releases and deploys) those are its driver's now (TA-76).

| # | Decision | Why |
|---|---|---|
| TA-87 | **No `manifest.json`** (design v2's, whose sha256 v4 cut): the module says what it is (`info`), and `pnpm ship` writes the file whole before renaming it. | A manifest without its hash only repeats `info`. |
| TA-88 | **Superseded by TA-126** (the cut removed the bridge). **A step still running isn't failed by the migration**: the engine's recovery after a restart takes it, as after any stop (an external step repeats with its kept request id, TA-13; an agent's turn is recovered as every turn is). | The same recovery every update already relies on; failing it would cost an attempt for nothing. |
| TA-89 | **Superseded by TA-126** (the cut removed the bridge). **Organization grants are dropped, not revoked at the tracker**: they last an hour at most and their sealed tokens named the old tables. A step claimed again asks for a new one. | No call to a tracker from a migration. |

| TA-94 | **Superseded in part by TA-131** (a made-up tracker's words). **The server's tests use a test driver over a fake tracker** (`test/tracker-driver.ts`, `test/tracker.ts`); the apps' fixtures and visual tests use a made-up tracker. | The workflow's tests keep proving what Home runs. |

### The cut (TA-126…TA-134)

John, 2026-11-15, once Home ran the bridge: the public code keeps only the generic tracker, refuses a database the
bridge didn't move, and guards against the first tracker's name coming back.
