# A write holds the burrow lock briefly (WL-01…WL-03)

Every commit-pipeline transaction takes the burrow's advisory lock, and a box has one burrow, so the lock is the box's
write lock: while one write holds it, every other write waits, and the database pool's connections wait with them. The
architecture council review of 2026-11-09 found the Google connector's allowed changes (drafting and organising mail,
trashing, calendar events, files, docs and sheets) calling Google inside the transaction, up to the provider's
20-second timeout, and no limit on how long a statement or the lock wait may take.

| ID | Decision | Reason |
|---|---|---|
| WL-01 | **An allowed Google change runs after the commit** (`connectors/commands.ts` `changeAfterCommit`): the command checks access and keys under the lock and registers a required continuation; the continuation calls Google, fills in the command's result before `commit` returns, and then signs the change's content-free event (`connector.changed`, with the key it was decided under). Google's error is the caller's, as before; an event that can't be signed after Google made the change is logged, and the agent still hears it was made. An approved re-run takes the same path. | A slow provider held up every write on the box, and a change Google made could be left with no record when the transaction then failed. Signing after Google answered records only changes that happened. |
| WL-02 | **`callGoogle` refuses to run under the lock** (`commit/lock-scope.ts` `assertOutsideLock`): it throws in development and tests and logs a warning in production. The reads an approval card shows (the emails a trash names, the draft a send shows, an event's guests, a file's name) still run while the command decides and are marked `'approval card'`. | New code can't slip a call back inside without a test failing; production keeps working if one is missed. Moving the card reads out means deciding before the transaction, a larger change left for when it is needed. |
| WL-03 | **A write's statements and its wait for the lock stop after a minute** (`WRITE_LIMIT`, `statement_timeout` and `lock_timeout` set locally in each pipeline transaction). | Nothing in a write should take that long; past it the write fails and says so instead of hanging the box. |
| WL-04 | **Starting a chat about a server names it from the last fleet read** (`hosts/sources.ts` `serverSubject`): the resolver runs inside `start_chat`'s write, so it reads the servers the last `/fleet` answer listed (every screen that shows servers made one) and asks the hosts service only when the process has none yet, for at most 2 seconds (`SUBJECT_FLEET_WAIT_MS`). A server that answer doesn't list is refused as when the service is down (“Server not found.”). | `fleetRaw` can take up to 15 seconds when the hosts service hangs, and inside the write it held the burrow lock, so every other write waited too. Resolving before the transaction would need a new hook in the commit pipeline for one resolver; the last read is as good as what the person's screen showed. |
