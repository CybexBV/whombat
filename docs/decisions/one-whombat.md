# One Whombat: a single assistant for your servers, home and services (2026-10-17)

John, 2026-10-17: Whombat stops being a Slack alternative with a crew of agents. It becomes **one Whombat** you talk
to, connected to your servers, Home Assistant, network gear, mail and services, that investigates devices it doesn't
support yet and builds a skill for them, with dashboards to see state and progress. Rackoon (John's Go homelab monitor,
`~/Code/whombat-hosts`, formerly on The Falcon) is folded in: “I don't want to use both Whombat and Rackoon, I want to
keep Whombat only.” The visual reference is `whombat-app/docs/design-handoff/one-whombat/` (`index.html` and the PNGs:
Home, a server with Whombat beside it, the heat pump skill, the phone); John: “This sounds exactly how I would like it.”
“Implement this fully.” Ship target is DEV (dev.whombat.com, the dev stack and John's DEV box); production untouched.

Stream decisions are in the stream files listed in `docs/implementation/one-whombat/assignment.md`.

## Servers (Rackoon folded in)

| # | Decision | Why |
|---|---|---|
| ONE-11 | **Rackoon becomes the hosts service, an internal part of Whombat** (a private repository of its own at first, history kept; `hosts/` here since one-repo.md). Its Go agent runs on each monitored server; its hub runs **headless** inside the box: no web UI, no own users, logins, passkeys, OIDC, kiosk or assistant. The Whombat server talks to it over a local Unix socket with one service token and passes the acting person in a header for its audit log. | John wants one product. The Go code was just tested live on his Proxmox machines; rewriting it would cost weeks and add risk. Users never see it as a separate thing. |
| ONE-12 | **Whombat owns accounts, permissions, approvals and every screen.** Server reads and changes go through Whombat's REST API (people) and the built-in **Servers** connection tools (Whombat), so keys, per-tool tiers, approvals and signed audit events apply as for any connection. Stopping, rebooting, deleting, migrating guests and running a command on a server always ask. | One permission model; the hosts service's own role checks become a second line. |
| ONE-13 | **What comes over from Rackoon**: the agent and its collectors (metrics, sensors, disks/SMART, updates, services, Docker, Incus, libvirt, Proxmox), history (24 h raw, 7 d, 90 d), alerts with snooze and maintenance windows, hints, uptime and heartbeat checks, consoles in the browser (shell via xterm.js, VM screens via noVNC), Proxmox and Incus guest editing (allowlists, digests, confirmations), backups, snapshots, firewall, tasks. **Left behind**: Rackoon's assistant, users and sign-in, its notification channels (Whombat pushes), kiosk links (later), Dutch texts (Whombat is English), the SPICE viewer (LGPL vendoring; VNC covers Proxmox). | Whombat already has its own version of what is left behind. |
| ONE-14 | **User-visible names say Whombat**: the agent installs as `whombat-agent` (`/etc/whombat-agent`, unit `whombat-agent`), the Proxmox users and roles are `whombat@pve` / `WhombatManage`; wire protocol names stay compatible and the updater accepts both binary names. A server can run the old Rackoon agent and the Whombat agent side by side. | “Whombat only”, and John's servers already run Rackoon agents. |
| ONE-15 | **Add a server** shows a one-line install command that dials the box's LAN address on the agents' port with the box's CA pinned; the box approves the enrollment from the Whombat UI. Agents reach the box only from private networks. | Same flow John knows from Rackoon, inside Whombat. |

## Devices Whombat doesn't support yet

| # | Decision | Why |
|---|---|---|
| ONE-16 | **A device skill is a description, not code**: Whombat writes a **device profile** (driver, address defaults, readings, actions with types, ranges and choices, the manual it came from). Whombat's built-in drivers do the reading and writing: **Modbus TCP** and **local HTTP/JSON** first. | The box never runs code an AI wrote against your equipment (stdio pack servers are refused on appliances, MR-44); a description is reviewable, and limits are enforced by the driver. |
| ONE-17 | **The order is fixed**: first look for what exists (a Home Assistant integration, a catalog connection, a maintained integration), then find the device on the network and its documentation, then **test read-only** against the real unit (`device_probe`), then propose the skill. | Don't build what's there; never write to equipment while learning it. |
| ONE-18 | **The skill card** (mock 3) shows what Whombat can read, with the real values from the test, and every action with **Off · Ask me · Allowed** and the owner's limits (e.g. “only between 16 and 24 °C”). Nothing changes on the device until the owner presses **Switch on**. Limits are stored with the owner's choice, not in the profile, so the skill's author can't widen them; rewriting the profile resets the choices. | Physical equipment: a wrong write can damage it. |
| ONE-19 | **Whombat says so when it can't**: cloud-only units, devices needing extra hardware (RS-485), or no documentation get a plain answer and a suggestion, not a guess. | Honesty over a half-working skill. |
