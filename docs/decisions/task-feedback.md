# Task feedback: true answers, the same choices everywhere, and work that reports back

John, 2026-10-21, on the Z13 desk Whombat: he asked Neo by voice to update the Home Assistant server. Neo said it needed
Full control first (the server had it); when told, it said its “earlier check was out of date”. The desk's popup offered
Approve · Deny · Not now, not the web card's “Don’t ask again on Home Assistant”. After “Neo is still working on it. The
answer will be in Chat.” the desk showed nothing more. Asked again on the web, the updates were installed but no message
said so. His words: “We need to massively improve this feedback.” His go: “Implement fully” (2026-10-21).

What was found (code, the Z13 is bare metal and couldn't be read):

- `server_updates` read the hub's server detail as `viewer`. The hub works the switches out for the caller
  (`model.Perms`, rank < 1 → “Requires operator access”), so `canInstall` was false and `next` said “Installing updates
  needs Full control” on every server. `server_detail` and the other detail reads showed the same. The test hub ignored
  the role. Neo's “out of date” was invented; the install itself was checked live by the hub and worked.
- The desk ask dropped `approvalView().scopeChoices` and DK-05 allowed only “approve once”.
- Talk's 90 s `slow` was final: the console stopped polling the talk, nothing kept the screen unlocked, the lock cleared
  the conversation, a follow talk's line never cleared, and the desk had no working state.
- A task's end was posted with no thread (`follow.ts`, and the approved call's “{Doing} now.” in `connections/call.ts`),
  so in threaded Chat it opened a new thread at the top. The agent wasn't woken (the pending-approval message promised
  it would be). Followed tasks lived in memory only. Done recently said “Installed …” when the install started.

## The quick release (runtime only, candidate 0.131.1)

| ID | Decision | Why |
| --- | --- | --- |
| TF-01 | **A server's switches are read with the role that acts.** Every Servers tool that reports `remoteControl`, `canInstall` or a switch's reason (`server_updates`, `server_detail`, and the Incus, Unraid and libvirt detail reads) reads the hub's server detail as `admin`, the role Whombat's own manage, console and power calls use. What the tool returns stays the mapped fields it returned before. | The hub answers per caller; a viewer always gets every switch off, which made every server look locked. |
| TF-02 | **The test hub answers per role as the real one does** (`hosts/testing/fake.ts`): a viewer's detail has every switch off with the role's reason. | The fake ignored the role, so the bug passed `proxmox.int.test.ts`. |
| TF-03 | **A reading never decides that an action is impossible.** When the switches look off, `server_updates`' `next` says Full control looks off and that `server_update install` says for sure. The agents' Servers guidance adds: don't tell a person you can't do something from an earlier result; try the action, it refuses in plain words; when a person says a setting is on, check again and say what you found, never guess why an earlier answer was wrong. | The install is checked live by the hub; an agent that trusts a reading over the action stops where it shouldn't. |
| TF-04 | **Everything said about a task goes in the thread it was asked in.** A followed task carries the thread (the turn's thread, else the approval card's), and its end, the approved call's own words and `answerAfterApproval`'s fallback line are posted there. | Chat is threaded (CHT-02): a post without a thread starts a new one at the top, where nobody looks. |
| TF-05 | **The pending-approval answer promises only what happens.** For a call that starts a followed task it says the task starts after the yes and its end is told in this chat; the wake promise stays for the others. | The agent was told it would be woken and wasn't. Superseded for followed tasks by TF-12. |

## The full release (contracts 0.116.0, app 0.119.0, candidate 0.133.0)

| ID | Decision | Why |
| --- | --- | --- |
| TF-10 | **A followed task is a live card in its thread** (card kind `task`, server-made only, the same shape stored): from its start “{Doing} on {server}” with the time it has run, then settled into one line with how it went (“Installed 23 updates on Home Assistant · 4 min”, “Backing up web on pve-02 didn’t work: the storage is full.”), opening to the full words. The card replaces the approved call's “{Doing} now.” line; a direct call (no ask) posts it too. Its words come from the existing task words (`TaskWords`, `taskOutcomeText`, `installedText`), shared by web, Android and the desk through core. | card-settle.md: active is a card, done is a line. People see that work is running and how it ended without asking. |
| TF-11 | **Followed tasks are kept in the database** (migration 0132 `followed_tasks`, one row per task: server, task, burrow, conversation, thread, agent, person, approval, words, the card's message, state `running`/`ok`/`warning`/`error`/`lost`, started, ended, result words, the turn woken). Whombat asks the hub about every running one on start, on the event stream's `resync`, and every 5 minutes for those running longer than 2 minutes (`GET /servers/{id}/tasks/{task}?platform=host`). A task the hub can't tell about 24 h after it started is `lost`: the card says Whombat lost track of it and the server's Tasks tab has it. Ended rows are deleted after 30 days. | A restart of Whombat or the hub, or a gap in the stream, lost the message for good. |
| TF-12 | **The agent that started a task is woken when it ends** (trigger `task_finished`, `DispatchContext.taskFinished`: the tasks that ended, each with server name, what, result and words) in the task's thread for the same person, and tells the person how it went in its own words, offering the next step it can take (a restart the report asks for, a retry). Tasks ending while such a turn is still queued join it (at most 10). When it can't be woken there (`wakeQuietly` refuses), the result line is posted in the thread instead. The card shows the facts; the agent's message is the conversation. | John: “we did not get feedback that it succeeded”. | TF-13 | **Done recently records a followed task when it ends**, in the past tense with its result, not when it starts. | “Installed updates” while they were still installing was untrue. |
| TF-14 | **The desk ask offers the web's choices** (amends desk-display.md DK-05): the choices `approvalView().scopeChoices` gives the paired person (“Don’t ask again on {server}” for an owner on a Servers call, “Always allow {agent} to {verb}” where the person may manage the agent, the computer's and the Vault's wider scopes), answered with that scope. Any choice wider than this once needs the PIN, as a risky approve does; approving once keeps DK-S rules. | John wants the same options on the desk as on the web; a choice that widens what agents may do from now on is the one to guard. |
| TF-15 | **The desk ask names who asks** (the approval's requester) and uses the web card's title. | The desk said “{assistant} asks” even when another agent asked. |
| TF-16 | **A slow answer isn't the end on the desk** (amends desk-display-talk.md DK-T06, DK-T16): after 90 s the talk is `working` (“{assistant} is working on it…”) and keeps waiting until the turn ends, at most 30 minutes, then it is `slow` as before. The answer replaces the line when it comes and is spoken when Talk's voice is on. A follow talk's line goes as soon as a newer message from the assistant is in the conversation. | DK-63 promised a later answer shows when it comes; the screen stopped listening instead. |
| TF-17 | **The conversation shows work in its thread**: `DeskTalkSession.working` (since, and what the assistant is doing now from its activity) while one of its turns runs there, shown as a working row at the bottom, and task cards as live rows (title, state, time, result). | The person in front of the screen sees that something happens, without opening Chat. |
| TF-18 | **The screen stays with a conversation that is working**: a talk that waits or works, and every new message or state change in the open conversation, count as use for the screen's idle and its 2-minute lock, as the talk poll's touch did. A lock (by the person, “When you leave”, or the timer) no longer drops the conversation: after unlock the screen opens it again where it was, with what came meanwhile; while locked it shows no words (DK-03). | The 2-minute lock cleared the conversation while John watched it work. |

## Full release: runtime stream decisions

| ID | Decision | Why |
| --- | --- | --- |
| TF-S10 | **An approved Servers call that starts no task wakes the agent with its result** (TF-S07's first gap, made true): a guest's power, a snapshot, a setting after a yes wake the agent that asked, as every other approved call does (HR-04), and the call's own sentence (ONE-DH21) is the line posted when it can't be woken. Only a restart or shutdown of the server this Whombat runs on keeps Whombat's own sentence and no wake (`CallWords.saysItself`), and its pending answer says Whombat tells what happened. The pending answer of a call that starts a task says a card shows it and the agent is woken when it ends. | The pending answer promised a wake that didn't come; TF-12's reason holds for every call: a plain line can't answer a follow-up or offer the next step. The agent can't carry on after its own Whombat goes down. |
| TF-S11 | **An Undo's inverse call runs in the thread the change was made in** (TF-S07's second gap): the change's thread (`changes.thread_root_id`) is given to the call, so a task it starts has its card and end there. | Undo is pressed on Home, outside any thread; the change knows where it was made. |
| TF-S12 | **The follow-up's logic runs on a store** (`TaskFollow` on a `TaskStore`: `dbTaskStore` in Whombat, a map in unit tests). The early end is remembered first (two minutes), and the call that keeps the task looks for it after its commit; an end changes only a running row, once, and one process works out an end once. | The race and the timing rules are tested without Postgres; the database rows make a double end harmless. |
| TF-S13 | **Asking the hub about a task**: as an operator, with the task's own platform (`taskPlatform`: `platform=host` only for a package task, none for a Proxmox UPID). Any refusal or no answer is “can't tell”; a task the hub still reports running after 24 hours stays followed, only one it can't tell about is lost. Checks run one at a time; the 5-minute tick also deletes rows that ended more than 30 days ago. When a task was last asked about and the deletion are bookkeeping in a plain transaction, not a signed change. | `platform=host` is the host's package tasks; a Proxmox task on that platform isn't found. A long task isn't lost while the hub knows it. |
| TF-S14 | **The card's message**: posted as the agent, waking nobody and not pushed to the DM's person (they just asked for it); its words are the card's title, which clients fold into the card (anything else would show above it). Its title is the task words' `doing` (an Install names the count Whombat last read, or the packages); `server` the server's label (else its id) and `serverId` the hosts id Home's things use. Where the agent can't post (not a member, an archived room), the task is followed without a card. | The apps fold a card's own line; a push for something the person just started is noise. |
| TF-S15 | **The wake**: a queued `task_finished` turn of the same agent, conversation, thread and person with fewer than 10 tasks takes the next one, else a turn of its own is queued (never another kind of turn). Its context lists that turn's ended tasks in the order they ended. The line when it can't be woken is the card's outcome words, in the thread, waking nobody. A `task_finished` turn is a follow-up for its person (whose sign-in it uses), follows a Chat thread's runtime choice, and, like `notify`, calls for no reflection or long-turn review. | One turn per thread tells a batch; a person's reply turn keeps its own meaning. |
| TF-S16 | **Done recently at the end**: the call's change is sealed with the task (`followed_task:<id>:change`, with whom it was for and the Undo it answers) and recorded when the task ends well or with warnings — its title in the past tense (“Started a backup of web” → “Backed up web”, “Installed 23 updates on shale”, “…, with warnings”), the outcome's first sentence before the call's own detail, in the task's thread. A failed or lost task records nothing, and an Undo whose inverse task failed leaves the change it undoes as it was. A call whose task isn't followed records at once, as before. | Nothing is said to be done before it is; Undo keeps its recipe and what it answers. |
| TF-S17 | **The woken turn's lines** (`taskFinishedTurnLines`): the tasks as delimited data (the server's words, defused), then one or two plain sentences in the agent's own words without ids, logs or the card word for word; the restart offered when the report asks for one (`server_power` reboot, only after a yes), another try or the fix for one that failed, the server's Tasks tab for one Whombat lost track of. | CLAUDE.md: agents talk like people; the card already shows the facts. |
