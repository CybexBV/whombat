# Feedback: the navigation trail and reporter sign-in (workstream `feedback-reporters`)

John asked on 2026-09-30 (proposal reviewed, then “Implement this fully”) for two changes to Whombat Feedback: the
widget sends the visitor's last 10 page views on the site with a report (“Steps to reproduce” leaves the form), and a
visitor may sign in with their email address and a 6-digit emailed code to follow the reports they sent on that site
(“Email verified”, “Your reports”). Reporting without signing in stays. Spec:
[`docs/implementation/feedback-reporters/assignment.md`](../implementation/feedback-reporters/assignment.md);
contracts 0.25.0 (CT-160 … CT-165). This file is the runtime's side (stream R); control's is control CL-98…, the
widget's whombat-app AP-427…, the manager's appliance MG-58….

Code: `apps/server/src/feedback/switches.ts`, `reporters.ts` (self-hosted sign-in, `reportChanged`), `public.ts`
(routes), `intake.ts` (`normalizeTrail`, reporter fields), `file.ts`, `read.ts` (`splitTrail`), `drop/receive.ts`
(`attestedReporter`), `drop/reporters.ts` (publisher), `drop/index.ts`, `drop/cards.ts`, `managed/ports.ts`,
`manager-client.ts`, `testing.ts`; `packages/agent-runtime/src/persona/feedback.ts`. Migration
`0051_feedback_reporters`. Tests: `feedback/reporters.test.ts`, `feedback/reporters.int.test.ts`,
`feedback/drop/reporters.int.test.ts`, `persona/feedback.test.ts`, `db/compat.test.ts`.

## Supersedes (for these two features only)

- **The non-goals of [`feedback.md`](feedback.md)**: “no customer login”, “My reports”, “status/detail endpoint”,
  “no customer emails, verification”. A visitor may now sign in to one site's widget with an emailed code, receives
  that code by email, sees a list of the reports they sent there with a visitor-facing status, and their reports are
  marked “Email verified”. Still true: visitors are never principals, accounts or members; nothing they send selects a
  burrow, channel, repo or agent; the reference opens nothing; there is no conversation, board or voting; no status
  emails are sent (the list is pulled, never pushed).
- **FB-07's “never … storage … history”**: the loader keeps the visitor's last 10 page views on the site (sanitized
  like the page URL) in the host tab's `sessionStorage` and sends them as `context.trail`, unless the integration or
  the snippet (`data-trail="off"`) switches it off. Cookies, headers, form contents, the DOM, console, network and
  replays are still never collected.
- **FB-B06's “Closed, nothing is watched”**: the loader now follows navigation while closed too (`popstate`,
  `hashchange`, a 1 s comparison of the sanitized URL) to record the trail.
- **feedback-drop FD-28 (7)** (no storage in the frame): the frame keeps exactly one `localStorage` key,
  `whombat-feedback:<site>`, for the reporter session; every other storage stays banned.

Why: John's request of 2026-09-30. The trail answers “how did the visitor get there” without asking them to write
steps; sign-in lets a visitor see that their report is being handled without the team emailing them.

## Decisions

| # | Decision | Reason |
|---|---|---|
| FR-01 | **Runtime feature `feedback.reporters`** (contracts `SINCE_0_25`) is advertised in `managed/runtime-features.ts` `IMPLEMENTED_FEATURES`; it gates the web's new settings, the trail display and “Email verified” on managed Whombats. Self-hosted advertises nothing: the HTTP client treats the server it is built with as `FULL_RUNTIME` (whombat-app `packages/client/src/session/runtime.ts`), so there is no other place to list it. | One list, checked by the feature test against the contracts. |
| FR-02 | **Migration `0051_feedback_reporters`** (`expand`, floors `0047_delegation`, UI-R17): `feedback_reports` + `reporter_id text null`, `reporter_verified boolean not null default false`, `reporter_published_at timestamptz null`, `reporter_dirty boolean not null default false` (a managed outbox flag), indexes `(integration_id, reporter_id, created_at)` and a partial one on `id where reporter_dirty`; self-hosted tables `feedback_reporters` (`fbr_…` id, integration, normalized email, unique per integration), `feedback_reporter_codes` (keyed MAC, attempts, expiry, `consumed_at`) and `feedback_reporter_sessions` (sha256 of the token, reporter, expiry; cascade with the reporter). A binary on 0047…0050 still reads and writes the result (`compat.test.ts`: target `{52, readers 48, writers 48}` from 48, 49 and 51): it inserts reports with the defaults and ignores the tables; a report such a binary changes isn't republished to control until a newer one changes it again. | Additive migrations never need a checkpoint (MD-12, UI-R17). The trail needs no column: it lives in `context` (CT-161), so redaction, hashing and storage already cover it. |
| FR-03 | **The integration's switches** `trail` and `reporterSignIn` (`on`/`off`, default `on`) are accepted and stored with the settings like every other field, signed through the config hash, and emitted by `toIntegration`; settings stored before 0.25 lack them and read as `on` (`switches.ts`, the contract's default). `publicConfigOf(settings, {mail})` answers `trail: trail === 'on'` and `reporters: reporterSignIn === 'on' && mail`: self-hosted `mail` is `mailConfigured()` (`SMTP_URL`), a managed card always `true` (control sends the codes). Changing either switch changes the card (a sync follows, FD-11). A card with `trail`/`reporters` is refused by a control older than 0.25: deploy control before boxes (assignment §4). | The widget learns from the config what it may do; an older runtime's config lacks both keys, which a newer widget reads as off. |
| FR-04 | **The trail is kept sanitized in `context.trail`** and answered as `submitted.trail`. Structure: `context.trail` is a known array capped at 10 before the schema (400 `invalid`, `fields: ['context.trail']`). `normalizeTrail` keeps the last 10 steps, re-sanitizes each URL with `sanitizePageUrl` and the integration's `redactPaths`, leaves out a step whose URL isn't an http(s) page or is over 1024 characters, makes titles printable text of at most 160 and keeps `at` (the visitor's clock) as sent; nothing left → no `trail` key. With the integration's `trail` off the trail is **dropped, not refused** (a cached or older widget may still send it). It is part of the normalized payload and so of the idempotency hash. `read.ts` (`splitTrail`) moves it out of `context` into `submitted.trail` (`[]` without one), because a 0.24 client parses `FeedbackContext` strictly and would refuse the whole report. The dispatch context keeps it in `context.trail` (runner and server are built together). | Same rules as the page URL: the server never trusts the widget's sanitizing. |
| FR-05 | **The assessor sees the trail** inside the report block, after “Sent at”: `Pages visited before reporting (oldest first; reported by the visitor’s browser, unverified):` and one line per step, `- <url> (“<title>”) · N min before sending` (whole minutes counted from `sentAt`, else from the last step; under one minute “less than a minute before sending”; an unreadable time names the visitor's clock). URLs and titles are defused like the rest of the report. The development handoff's prompt shows the same block. | The assessor gets the path to the problem with the same untrusted-data framing as all visitor context. |
| FR-06 | **Self-hosted reporter routes** under `/embed/v1/sites/:site/reporter/…`, in the public scope (no cookies, `no-store`, the fixed error bodies): the same guards as reports, in this order — module on (the scope exists), site known and intake on (404), `Origin` = the public origin (404), body ≤ 4 KiB JSON parsed strictly (400 `invalid`), `parent` allowed and sign-in on — plus mail for `code` — (404 `unavailable`), the per-network bucket (429), the work. `POST code` → 202 `{ok: true}` whether or not a code went out; `POST session` → 200 `FeedbackReporterSession` or 400 `code_refused`; `DELETE session` → 204 for any token or none; `GET reports` → 200 `FeedbackReporterReports` or 401 `signed_out`. `GET reports` and `DELETE session` carry no `parent` (the contract has none): a session is bound to its integration, so a token of another site is `signed_out` there. With sign-in switched off, `code`, `session` and `reports` answer 404, sign-out still 204, and a Bearer on a report is ignored. | The surface stays the one public scope with one set of guards; nothing tells an unknown site, a disabled one and an unoffered feature apart. |
| FR-07 | **Limits and the list.** Codes: 5 an hour (and 10 a day, FR-13) per integration and address, counted from stored code rows (429 `retryAfter` 3600, the same for every address, known or not), 30 an hour per network (`FEEDBACK_REPORTER_CODES_PER_NETWORK_PER_HOUR`; IPv4 address or IPv6 /64, FR-14) and 300 an hour per process across all sites, so a spread of addresses can't make the server a mailer. Sessions: 60 attempts an hour per network. `GET reports` and sign-out: 240 an hour per network. Buckets answer the fixed `retryAfter` 60 (FB-F07). “Your reports”: the reporter's reports of that integration, newest first, at most 200, **leaving out reports whose content was removed**; status `reporterStatusOf(status, assessment state, recorded outcome)`; `updatedAt` the later of the report's and its assessment's change; `summary` `reporterSummaryOf(description)` (null when empty). | Mail is the costly, abusable part; reads are cheap but bounded. A removed report has nothing left to show and its visitor shouldn't see it linger. |
| FR-08 | **Codes, sessions and verified reports (self-hosted).** A code is 6 random digits, stored only as `reporterCodeMac(key, site, email, code)` under a key derived from the master key (`custody.mac('feedback-reporter-code/v1', …)`, never stored), 10 minutes, one use, the fifth wrong try ends it. Only the newest live code of an address counts: a new code ends the older ones, so five codes an hour don't multiply the odds of guessing. Every failure — no code, wrong, expired, used, ended, never asked for — is the same 400 `code_refused`. The mail (`reporterCodeEmail`, the product label and the embedding origin) is sent without being awaited, so timing says nothing. A session is `fbrs_` + 256 random bits, stored as its sha256, 30 days, not renewed by use; the reporter row (id + normalized address per integration) is made at the first sign-in. A report sent with a valid session's Bearer gets `reporter_id`, `reporter_verified` and **the session's address as its email, whatever the form sent and even with the email field off** — the reporter proved it and chose to sign in; an owner who doesn't want addresses switches sign-in off. An invalid or expired Bearer is ignored and never refuses the report. The signed `feedback.report_received` gains `reporterVerified: true` for a verified report only (never the address or the reporter id); other reports' payloads are unchanged. Idempotency is unchanged: a retry with a Bearer of a report first stored without one gets the first receipt and stays unverified. | Keyed, never a plain hash of a 6-digit code (a table dump must not reveal live codes); one answer for every failure (no address enumeration, auth AH-06). |
| FR-09 | **Managed: control's attestation** (`FeedbackDrop.reporter {id, emailDigest}`, CT-164) is honoured in `receiveDrop` only when `reporterEmailDigest(site, sealed reporter.email)` equals it (constant-time) and the integration's sign-in is on when the drop is filed; then the report gets `reporter_id` = control's id, `reporter_verified`, the normalized address as its email (as FR-08). Anything else files the report unverified; an attestation never refuses a drop. A managed Whombat stores no codes, sessions or reporters (control keeps a keyed hash of the address, CL-98…). | The runtime verifies what it can (the sealed address) and trusts control only for “a valid session posted it”. |
| FR-10 | **Managed: publishing statuses.** `reportChanged(ctx, rootMessageIds, eventId)` replaces `republishRootMessages` at every call site (status change, content removal, every assessment state and result, handoff, pause/resume): it republishes the root messages and, on a managed Whombat, marks `reporter_dirty` on those reports that have a reporter in the same transaction, then nudges the publisher after the commit; the intake marks a verified report at once. The publisher (`FeedbackDropService`, `drop/reporters.ts`) sends marked reports oldest id first in batches of at most `FEEDBACK_REPORTERS_PUBLISH_MAX` (100) through `ManagerPort.feedbackReporters` (`/v1/runtime/feedback/reporters`, op `feedback.reporters.publish`): `{site, reporterId, reference, type, status, receivedAt, updatedAt}` in epoch seconds, never text; a report whose content was removed is a **removal**. After an accepted batch each flag is cleared only if the row's `xmin` is unchanged (changed meanwhile → sent again next time). Debounced 1 s; at most 10 batches a run, then another run. 501 or 404 (older manager, or control's drop off) → `reportersSupport: 'unsupported'` (logged once at info); 503, 409 `device_unclaimed` or anything else → a warning; both back off 1 min → 1 h like the cards; the hourly check sends what is still marked. Nothing before the claim, paused while quarantined or drained, nothing with `WHOMBAT_FEEDBACK=off` (control's entries go with the withdrawn cards). **Republish rule** (control, 2026-09-30): control deletes a site's reporter entries when the site leaves the card set (not when a card merely expires), so when a sync's `accepted` contains a site that had no published row before — intake switched back on, a fresh claim, a restored replacement — every report with a reporter of that integration is marked again (`SyncOutcome.reportersMarked`). | An outbox flag written with the change can't be lost by a crash; `xmin` needs no extra column; control applies only newer `updatedAt`, so repeats are harmless. |
| FR-11 | **Sweep**: the hourly retention pass (which runs even with the module off, FB-F05) deletes reporter codes older than a day (kept that long because the per-address counts are taken from them, FR-13) and expired sessions, and idle reporters (FR-17). Removing a report's content doesn't remove its reporter link (the report is left out of the list, FR-07). | The same timer as retention; nothing else holds these rows. |

## Security review fixes (2026-09-30, lead's independent review of this branch)

| # | Decision | Reason |
|---|---|---|
| FR-12 | **No status is lost after a long outage** (extends FR-10). Control unbinds a site whose card **expired** and deletes its reporter entries, and answers `{ok: true}` to publishes for sites it doesn't consider this device's — the runtime would then clear the flags of statuses nobody kept. So (a) nothing is published before control accepted a card sync **since this process started** (that first sync asks for a run), and (b) a sync accepted for a site whose last recorded card had already expired at the time of the sync counts as re-published, like a site with no card: every report with a reporter of that integration is marked again (`cards.ts`: “held” means published and `expiresAt` after now). | Across an outage longer than a card's 14 days the runtime can't know what control still holds; re-sending everything is cheap and idempotent (control keeps the newest `updatedAt`). |
| FR-13 | **At most 10 codes in 24 hours per integration and address**, on top of 5 an hour, counted durably from the code rows (one query, both windows; 429 `retryAfter` 3600). Code rows are therefore kept a day (FR-11's sweep: older than 24 h). | Five codes an hour, each with five tries, allowed 600 guesses a day at a 6-digit code; now at most 50. |
| FR-14 | **Per-network buckets are keyed by network**: the IPv4 address (also IPv4-mapped) or the IPv6 /64 (`lib/network.ts` `networkOf`, the same rule as control's `networkPrefix`, CL-31). And `TokenBuckets` (`mcp/rate-limit.ts`) prunes **before** a new key is inserted, dropping buckets that have refilled to capacity by now: pruning after the insert (the map over 10 000) dropped the full bucket just made, so what the caller took from it was lost and every new source was unlimited. This affects every user of `TokenBuckets` (MCP calls, the report buckets) for the better. | An IPv6 client can use 2^64 addresses; a map full of busy keys must not turn into no limit at all. |
| FR-15 | **A failed code email is logged without its text**: a fixed message with the error's `code` and SMTP `responseCode` only (SMTP answers quote the recipient address). | Visitors' addresses stay out of logs. |
| FR-16 | **A sign-in without an open code still compares a MAC** (against a fixed value), so an attempt costs about the same whether or not a code is open for the address. | Timing shouldn't tell which addresses asked for a code. |
| FR-17 | **Idle reporters are removed**: the hourly sweep deletes `feedback_reporters` rows made more than 30 days ago that have no live session and no report (their expired sessions go with them). A reporter who sent a report stays linked to it. | Self-hosted retention of visitors' addresses: an address that only ever signed in isn't kept for ever. |
| FR-18 | **Trail steps on another origin are dropped** (extends FR-04): after sanitizing, a step whose origin isn't one of the integration's allowed origins is left out. | The trail is about the visitor's way through this site; a crafted submission can't smuggle other sites' URLs into the assessor's prompt. |
| FR-19 | **A failed publishing run keeps its backoff**: a change requested during the run (a timer or the “again” flag) no longer starts the next run at once; the backoff timer replaces it and the report stays marked. | A down manager or control would otherwise be retried at every change instead of 1 min → 1 h. |

## Contract notes (0.25.0, no change asked)

- `GET …/reporter/reports` and `DELETE …/reporter/session` carry no `parent`; the runtime binds sessions to the
  integration instead (FR-06).
- `FeedbackDispatchContext` has no “verified” flag, so the assessor still reads “left contact details (kept from
  you)”; nothing it does depends on it.
