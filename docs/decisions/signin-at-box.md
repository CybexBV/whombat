# Sign in at the box (2026-10-20) — decisions BX-nn

John, 2026-10-20 (main checkout): “I want to loosen up the security a bit, when we enroll a device we have to download a
recovery kit, I don't want this anymore. If we have physical access to the appliance we should be able to auth /
re-enroll again.” Agreed the same day after the proposal (“yes”).

**What changes.** Claiming no longer ends with the recovery kit. A device that isn't let in yet can instead use a code
the box shows on its own screen (the console on tty1, the desk display, or the virtual machine's console): whoever can
see that screen can let a device in, as any person on the box. This supersedes MA-04 §5c (“a lost owner endpoint is
recoverable only with the customer's kit”) and MR-11/MR-25's place for the kit as the only way back; the kit itself,
pairing, invites, re-enrollment links, passkeys and revocation stay as they are. MA-03/MA-24 hold: control and the relay
still can't let a device in, because the letters never leave the box's screen and the check is bound to both Noise keys
exactly like the claim (CC-06, CC-07).

Ids: BX-01… here (product and runtime), BX-S01… (server details, below); contracts CT-620…; app AP-3500…AP-3524 (web,
`docs/decisions/signin-at-box-web.md`), AP-3525…AP-3549 (Android, `signin-at-box-android.md`); appliance console
CG-150… (`console-gui.md`). Build brief: `docs/implementation/signin-at-box/assignment.md`.

| BX-03 | **The same exchange as the claim** (CC-06): CPace `CPACE-RISTR255-SHA512`, password = the six letters, `CI = lv_cat("whombat-screen-signin/1", deviceId, appliancePeerId, clientPeerId)` with both PeerIds as each side sees them in Noise, `sid` = the sign-in id, confirmation tags from `HKDF-SHA512(ISK, "whombat-screen-signin-confirm/1")`. The device checks the box's tag before it trusts the result, and only then pins the PeerId (`pinSource: 'screen'`), like the claim. A device without a pin connects with the directory's PeerId for this exchange only and sends nothing secret before the tags match. | A lying control or relay can't relay the code (the tags bind both keys) and gets one online guess per exchange like anyone else; the code also proves to the new device it reached the real box. |
| BX-04 | **Six letters from the claim alphabet** (`ABCDEFGHJKMNPQRTVWXY`, 20⁶ = 64 million), drawn from a CSPRNG the claim's way (CT-58's byte rule, six letters), kept in memory only, never logged or reported; shown grouped `KXQ MTR` (the space isn't typed). A wrong guess rotates the letters at once (the screen shows new ones; the sign-in stays open until it expires). | Unlike the claim this stays possible for the box's whole life: with the claim's backoff (BX-05) a patient guesser gets about 24 tries a day, which four letters wouldn't survive and six do. |
| BX-05 | **Limits.** Requests: at most 5 per device key and 30 per box per hour. Wrong guesses: the claim's policy (`claimBackoffSeconds`: three free in a rolling 24 h, then 1, 2, 4 … minutes, at most an hour) on their own counter, kept in the database across restarts; a success clears it. Unenrolled request budget as for every enroll op. | Bounded guessing and griefing, the same trade the claim accepted (CC threats). |
| BX-06 | **What the box's screen shows.** Over whatever is on screen in the claimed state — the plain claimed screen, the desk glance locked or unlocked, quiet hours, dimmed or dark — a panel: “NEW DEVICE”, “{name} wants to sign in”, the device's label, the letters large, “Type these letters on that device.” and “Didn’t ask for this? Ignore it: the code goes away in {m} min.” It wakes the screen. Gone when used, replaced, expired or the runtime stops. The text console shows the same words. | It must be visible wherever the person looks, and say whose device so a stray request is obvious. |

The account's other devices are left alone. | The notice John was promised, through the channel that already exists. |

## Threats and residual risks

- **Anyone who can see the screen** (in the room, or with access to the hypervisor's console) and can open this Whombat
  from a device (control admits org members) can let a device in as any person on the box. That is the point (BX-02);
  the screen names the person and device, and owners get the push (BX-07).
- **Guessing**: one guess per exchange, letters rotate, BX-05's backoff; ≈ 24 guesses a day at most, about 1 in 7,000
  over a year of constant trying, and owners are told when it starts.
- **Griefing**: a stranger with access can replace the code showing or push the box into backoff (≤ 60 min at a time);
  the owner can still pair from another device, use a passkey or a kit, or wait.
- **Misleading labels**: the device's label is the requester's text; it's shown as plain text (`ConsoleDisplayText`),
  one line, no control or format characters.

## Server (BX-S nn)

| # | Decision | Reason |
|---|---|---|
| BX-S01 | **Where it lives.** `managed/screen-signin.ts` `ScreenSignInService`, owned by the trust service (`trust.screen`) and dispatched next to `enroll.claim.*`. What it needs from the database (claimed device id, whether a key is an endpoint, the account, the failure counter, the enrolling transaction, the pushes) is a `ScreenSignInStore` port (`DbScreenSignInStore`), so the rules are unit-tested with a fake and the real store over sessions (`claim-code.int.test.ts`). One live sign-in per box in memory: id (18 random bytes, base64url), requesting PeerId, account, device id, the endpoint as asked, what the screen shows, letters, expiry, generation. A new request from any key replaces it; a restart drops it (the console file loses it at `close()`). | One place for the rules, testable without Postgres; memory is where the claim's letters live too (CC-01). |
| BX-S02 | **Wrong codes are counted in `appliance_claim_failures` with `method = 'screen'`: no migration (no 0126).** The claim's backoff and its success-clearing skip `screen` rows; the screen's backoff counts only them (the rolling 24 h window and `claimBackoffSeconds`, as the claim); a successful screen sign-in clears only them. | The table already keys rows by a free-text method, and screen failures only happen once claimed, when the claim no longer reads the table. An older binary after a rollback is claimed too, so it never reads them; the rows go by themselves after 24 h. A table of its own would add a migration and floors for the same columns. |
| BX-S03 | **Superseded in part by one-person.md OP-S11**: the limits hold; a request names no email. **Request limits in memory** (5 per key and 30 per box in a rolling hour), counting every request that gets past “no screen”, “already an endpoint” and the backoff — an email without an account included, so the limits also bound probing for emails. | They bound griefing and probing, not guessing: guessing is bounded by the persisted backoff (BX-S02). A restart that resets them also ends the sign-in showing, and nobody can restart the runtime from a session. |
| BX-S04 | **Superseded in part by one-person.md OP-S11**: the order holds without the account check (a request names no email; before the claim it is `screen_unavailable`). **Order of checks.** Request: no screen (`WHOMBAT_CONSOLE_FILE` unset or no `WHOMBAT_APP_URL`, so no console file) or not claimed → `screen_unavailable`; the key is an endpoint → `endpoint_enrolled` (revoked: `forbidden`, as `insertEndpoint` says); backoff → `screen_backoff` (before letters show that can't be used); limits; account → `screen_no_account`. Begin: no live sign-in with this id for this key → `screen_signin_missing`; backoff; the letters and their generation taken together after the last wait; an invalid share → `screen_share_invalid` (costs nothing); kept in `SessionScope.screenBegin` for `ENROLL_CLAIM_BEGIN_TTL_S`, cleared when the session closes. `enroll.screen`: the begin is used up whatever happens; `screen_signin_missing`, then `screen_begin_missing` (none on this session, another id, expired, or the generation moved), then the constant-time tag compare. A match takes the sign-in off the screen before the transaction (used once even if it fails), inserts the endpoint (`via: 'screen'`, `by: null`, signed `endpoint.enrolled`), clears the counter and answers `EnrolledOutput + {confirm: tags.appliance}`. | The claim's shape (CC-07, MR-51) for the same exchange; refusing early keeps a code off the screen that can't let anyone in. |
| BX-S05 | **Pushes.** A success: one content-free `security` push to every owner and the account (`screen-enrolled:<endpointId>`), as re-enrollment does. The backoff: one `security` push to the owners on the wrong code that starts it (the fourth in the rolling window), not on each later one. Through the backoff the sign-in stays open with its rotated letters (BX-04) and begins are refused until `retryAt`. | Owners hear that someone is guessing without a push per guess (at most about 24 a day). |
| BX-S06 | **Superseded by one-person.md OP-S06, OP-S11**: a request names no email, and the device is let in only to the person's account. **Which accounts.** By email, trimmed and lower-cased as accounts are stored; only an account that may still sign in — an owner, or a person in at least one burrow (the passkeys' `accountActive`, offboarding's EP-07 rule) — re-checked inside the enrolling transaction. Any other answers `screen_no_account`, like an unknown email. | A person removed from every burrow has had their devices revoked (EP-07); the screen must not undo that. |
| BX-S07 | **What the screen shows.** `name`: the account's name, else its email; `device`: the label as asked, else the platform in words (`Web browser`, `Android`, `iPhone or iPad`, `Desktop app`, `Command line`); both through the burrow names' `consoleDisplayName` (separators to one space, invisible characters dropped, trimmed, over 64 code points cut to 63 + “…”). The ceremony writes `signIn` only in `claimed` and until `expiresAt`, rewrites the file at expiry by its own timer (like the backoff), drops a `signIn` the file can't carry rather than skip the whole write, and removes it at `close()`. The letters are only in that file: logs carry the peer's last 8 characters and whether a sign-in was replaced. | Never empty, never refused for a label the screen can't draw; the screen is the only place the letters exist. |
| BX-S08 | **Dispatch.** `enroll.screen.request` and `enroll.screen.begin` take `enroll.claim.begin`'s path (ephemeral: no receipt; the unenrolled budget; refused while the runtime drains); `enroll.screen` is a durable command like `enroll.claim` (receipt under `peer:<PeerId>`, never resent). `enroll.claim` answers `recoveryKitRequired: false` (BX-01). `EnrolledVia` gains `screen` as a type only: `enrolled_via` has no check constraint, so no migration. | The same budget and drain rule as the claim; nothing new in the schema. |
| BX-S09 | **A device that is in already may sign in at the screen.** `enroll.screen.request` refuses only a revoked key (`forbidden`) or another account's endpoint (`endpoint_enrolled`); one of the person's devices that is in already gets letters like a new one, and a match keeps its endpoint (`DbScreenSignInStore.enroll` returns it: no second row, no `endpoint.enrolled`) and answers the box's tag, so the device pins this box. The push and the log are as for a new device. | A box restored from a backup onto a reinstalled or new machine has a new identity, while its database knows the person's devices: they know only the old box's identity, passkeys name it too, and every way in refused a key that is in already. The letters on the box's screen still prove this box to the device, and nothing new is let in. |
