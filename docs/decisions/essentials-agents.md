# Essentials · agents (stream R1, 2026-09-30)

Items 1, 2, 3, 4 (runtime), 6 (runtime) and 7 of `docs/implementation/essentials/assignment.md`: approvals that never
claim work that didn't happen, a yes to an agent's push that lets it push, long turns that keep their tools, failed turns
that say why and can be tried again, managed GitHub sign-in, and Codex updates that flow again. Contracts 0.26.0
(CT-166…CT-184) carry the new shapes. Decisions are `EA-nn`.

| # | Decision | Reason |
|---|---|---|
| EA-01 | **Codex error infos of newer versions are mapped next to the pinned ones.** `CODEX_ERROR_STATES` lists every `codexErrorInfo` of the pinned Codex (0.157.0) and of the versions the “latest tested” job moves a scratch clone to: `flexUnavailable` (0.158.0, “Flex capacity unavailable.” → `outage`, retryable) and `tooManyDenials` (0.159.0, “Automatic approval review rejected too many approval requests for this turn” → no credential state, not retryable). `CODEX_ERROR_INFO_SINCE` names the version that added each; `bundles.test.ts` requires every info of the pinned fixture to be mapped and allows a mapped info missing from it only when it is listed there with a version newer than the pin. So the same code passes at the committed pin and after `bump-pins.mjs` (reproduced: scratch clone → 0.159.2 → fixture regenerated from the binary → 489 agent-runtime tests pass). | The job has failed for every Codex 0.158/0.159 since 2026-09-29 on exactly this test; the pin itself moves only by a person (provider-bundles.md), so the map must be ahead of it. |
| EA-02 | *Amended 2026-10-01 (runs-approvals.md MDS-03, MDS-D02): `merge.main` is the agent's Merge row now; a yes still merges as the person who approved.* **What a yes does, per action type — nothing is simulated.** `ApprovalEngine` installs no executor by default (`simulatedExecutor` exists only for the demo storyline's staging deploy and tests that ask for it, `test/approvals.ts`). Built in (`approvals/executors.ts`): `merge_pr` merges through GitHub **as the person who approved** (`merge_pr` command, its rules and `merge.main` kept; a refusal fails the approval with the reason); `create_channel` runs the real command as the agent that asked, with the people it named (agents in the list are refused: adding them is a person's call); `custom` succeeds as the yes itself, signed “{Person} approved: {title}”, never “done”, and wakes the agent (EA-07); `push_shared_branch` see EA-05/EA-06. `deploy` has an executor only with `GITHUB_DEPLOY_WORKFLOW`; `grant_key`, `vault_use` and the connector actions keep theirs. An executor that ran a signed command itself (the merge, the channel) returns `logged`, so the requester signs no second text. `perform_action`'s ask now makes an approval of the action (`KeyRequirement.approvalRunsAction`), so a yes runs the action's executor (a merge as the approver, a deploy completing from its workflow) instead of re-running `perform_action` as the agent. | Assignment item 1: no production path signs success for something Whombat didn't do; a merge is people's; re-running `perform_action` as the agent could never merge (agents are always refused) and marked a started deploy “done”. |
| EA-03 | **What can't be carried out is refused up front, and an old approval of it fails honestly.** `request_approval` and `perform_action` refuse (400, the agent reads it) a `refund` (“Whombat can’t issue refunds here: no payment system is connected. Ask a person to do it, and say what exactly.”), a `message_external` (“Whombat can’t send messages outside this burrow here: nothing is connected to send them. …”) and a `deploy` without a workflow (“Whombat can’t deploy here: no deploy workflow is set up on this Whombat. …”) — whatever has no executor. `perform_action` also refuses a `push_shared_branch` (“Pushes aren’t actions: commit your work and Whombat pushes it when your turn ends, asking a person first when the branch needs it.”) and a `custom` action (“Whombat has nothing to run for “{name}”. If you hold its key, do it yourself; if it needs a person’s yes, ask with request_approval.”). An approval of a type without an executor that gets approved fails: `approval.failed` “Couldn’t refund €24,00 on account 3310: no payment system is connected to Whombat, so no refund was issued.” (deploy: “… no deploy workflow is set up on this Whombat, so nothing was deployed.”). | The agent learns what to do instead before a person is asked for something nobody can do; a yes to an old request never reads as done. |
| EA-04 | **Agent tokens slide while their turn is alive.** Every lease-renewing beat (`progress`, `heartbeat`) and every authenticated MCP call moves the token's expiry to now + 30 minutes, never earlier than it was and never past the claim + `WHOMBAT_SANDBOX_WALL_MINUTES` (server config, default 120, the runner's own setting) + 15 minutes. An MCP call writes only when that gains a minute or more. A lapsed token is never revived; a finished or cancelled dispatch's token stops at once (state check, unchanged). | A sandbox turn may run two hours while the token lasted 30 minutes, so long turns lost their tools and the runner's final post. The margin covers the final post, the push and `complete`; the cap keeps a stuck turn from holding a token forever. |
| EA-05 | **A push whose key asks is a `push_shared_branch` approval of exactly that commit, where the turn was asked.** `runtime.authorize_git` handles its own `ask` (`onAsk: apply`): with a person's yes for this agent, repo, branch and commit (EA-06) it issues the credential; otherwise it creates one approval — the action from the runner's request (repo, branch, sha), the card in the dispatch's conversation and thread, for the dispatch's person — and the route answers 202 as before. Asking again for the same agent, repo and branch while one waits answers with it (the runner pushes before a PR and after the turn). A request without a commit (older runners) is refused. | Before, the ask was a `custom` “push to …” card in the burrow's first channel whose yes re-ran `authorize_git` and only signed `git.credentials_issued`: nothing pushed. |
| EA-06 | **A yes lets that push through; the credential handed out completes it.** The `push_shared_branch` executor wakes the agent (EA-07) and defers: the approval shows APPROVED · PUSHING. While it runs, the credentials route lets exactly that agent push exactly that repo, branch and commit (another commit asks again); the push credential handed out under it completes the approval, signed by the agent: “Allowed Banjo to push release/2.1”. The push itself is the mirror's “Pushed … to …”. Used once: the next push of the branch asks again. Unused 24 hours after the yes, recovery fails it: “Couldn’t push c0ffee to release/2.1: Banjo didn’t push c0ffee to release/2.1 within a day of the yes, so nothing was pushed. Ask Banjo again.” | “When the credential was used” is what Whombat itself does and can see at once; the mirror sees the push only when it polls. Binding to the commit keeps “what runs is what was approved”; the day bounds an allowance nobody used. |
| EA-07 | **A yes wakes the agent that asked (`approval_granted`, CT-168).** The executors of `custom` and `push_shared_branch` (at the yes) and of `merge_pr` and `create_channel` (once Whombat did it) queue a turn for the requesting agent in the approval's conversation, in the card's thread (the thread it was posted in, else a new one under it), for the person the asking turn was for (`approvals.on_behalf_of_account_id`), signed by the person who said yes (`dispatch.created`, hidden). The turn carries the approval (`dispatches.approval_id`, migration `0052`; `DispatchContext.grantedApproval`) and both prompt builders say what the agent may now do (`grantedApprovalLine`: push exactly that commit and end the turn / carry on with the custom ask / don't merge again / the channel exists). **Deduplication:** a live (queued, claimed, running) turn of that agent already carrying the same approval answers instead of a second one; a queued reply turn of the agent there for the same person takes the wake over (its `approval_id` is set, it keeps its trigger); a retry of a woken turn keeps the approval. No wake for deploys (their workflow reports itself), key grants (their own “Go ahead.” reply) or Vault passes (VT-32). The Vault's quiet wake moved to `domain/wake.ts`, shared. A push's woken turn gets the branch's workspace from the approval, `writeApproved: false`: under a key that asks its sandbox stays read-only, so the runner's push after the turn is the approved commit. | Assignment items 1 and 2: the agent's turn ended on `pending_approval`, so without a wake a yes did nothing until someone spoke to it again. |
| EA-08 | **Every final failure says why, in public words, with a `turn_failed` card (CT-167).** The runner classifies in both modes (`classifyTurnFailure`, agent-runtime `failures.ts`: the managed outcome, then the refusal's own code, then the provider's credential signal, then text rules) and sends `CompleteBody.failure {code, resetsAt}`; `error` stays the technical text. The server falls back to the same rules (a lost lease or no runner → `runner`, a context that couldn't be built → `internal`, an older runner's text or refusal). Mapping: sign-in and policy refusals (`provider.*`, `managed.provider_gated`, a lapsed or revoked credential) → `signin`; a usage limit (credential signal, “usage limit”, `managed:quota_exhausted`) → `usage_limit` with the reset from the provider or its limited window; 5xx, overload, network, `flexUnavailable`, a missing client → `provider`; the sandbox, its limits and “fs sandbox helper failed … Read-only file system” (the dev monolith, 2026-09-24) → `sandbox`; wall time → `timeout`; the working directory, clone, checkout, git → `workspace`; anything else → `internal`. The agent's message is `turnFailureText` (naming Claude or Codex, the reset in the burrow's zone), or the runner's refusal when it is safe for the room (no host path, secret or stack trace: “Joris hasn’t signed in to Claude …” stays, “~/code/billing has uncommitted changes” doesn't); no mentions, no follow-up work. The card carries the classified sentence. `dispatches.failure` keeps code, sentence, reset, the message, the retry and the technical detail (`turnFailureDetail` of the error and refusal: redacted, the last 2000 characters), which only burrow owners and admins read (`WorkItem.failure.detail`). Feedback assessments, automation steps and search answers get no card (their owners retry them; a Feedback retry would run outside the assessment's confinement): they keep their plain text or answer state. `DispatchSummary.failure` carries code and sentence. | Assignment item 4: “Something went wrong on my side” hid the cause in the log; the classification needs what only the runner knows, the sentence what only the server knows (the burrow's zone). |
| EA-09 | **Try again: once per failed turn, as it was asked (`dispatches.retry`, trigger `retry`).** People who may wake the agent there — a person in the conversation (anyone else gets 404, as for no turn); a personal agent's owner only — press Try again on the card or in the Work view (`retry_turn` on FAILED turn and run items). The retry is a new dispatch with the same agent, conversation, thread, trigger message, person, plan step and approval, `mode` reply for a run's turn (the run stopped with the failure), `retry_of_id` the failed one; its context says what failed (`DispatchContext.retry`) and both prompts open with it. The failed turn records the retry, the card's stored fields are patched (`retriedAt`, `retryDispatchId`; `message.updated`) and a hidden `dispatch.retried` is signed by the person. A second press (from anyone) answers with the first retry; a turn that didn't fail is a 409. The runtime advertises `dispatches.retry`. | One retry per failure keeps a flaky provider from being hammered by several people at once; the first retry's own failure has its own card. |
| EA-10 | **Superseded in part by one-person.md OP-S15**: the status still talks about the person's own GitHub sign-in; its words speak to the person and name no other member. **A managed box's GitHub status talks about the person's own GitHub sign-in (CT-181).** Managed `github.status` is read per caller from the burrow's connection and the sign-ins, never from the adapter's process-wide cached `whoami` (which in managed mode answered for whichever account or burrow asked last): `via: 'signin'`; `signInNeeded` for an owner without a GitHub sign-in of their own when the burrow isn't connected or its connection is broken; `canConnect` for an owner who has one (no Whombat-admin requirement, PV-06); the connector named in `note` (“GitHub runs as Mara’s own GitHub sign-in.”) or, broken, in `error` with its `fix` (“… no longer a member …” → `connect GitHub`; “Mara’s GitHub sign-in is gone, so GitHub work has stopped. …” → `sign in to GitHub`). `github.connect` refuses an owner without a sign-in with “Sign in to GitHub with your own GitHub account first (Settings → AI accounts), then connect it for this burrow.” (409, `details.fix`), else connects as that person's own sign-in (`github.connected` payload `via: 'signin'`). Self-hosted answers `via: 'gh'`, `signInNeeded: false`, unchanged otherwise. The sign-in itself is the existing `providers.login.*` flow (device code or token, the unmodified `gh`); verified with the fake `gh` device flow — GitHub's real one needs a person's account. The runtime advertises `github.signin`. | Assignment item 6: Settings told a managed owner to run `gh auth login` on a box they have no shell on, and only admins (a host role) could connect. |
| EA-11 | **Features advertised with this work:** `dispatches.retry` (EA-08, EA-09) and `github.signin` (EA-10) move from `NOT_IMPLEMENTED` to `IMPLEMENTED_FEATURES` (`managed/runtime-features.ts`), so the session welcome and the release manifest (`runtimeServes`) carry them. Items 1–3 and 7 change no shape a client gates on. | MD-15: clients offer a feature only on runtimes that say they have it. |
| EA-12 | **A content/safety refusal is its own failure code `refused`, which Try again doesn't offer (amends EA-08, EA-09).** When the provider (or the AI gateway's safety filter) declines a request on its content rather than erroring — “safety filter refused this request”, “safeguards flagged this message”, a content policy — `classifyTurnFailure` returns `refused` (a new `TurnFailureCode`, checked before the error-text rules in `failures.ts`, shared predicate `providerDeclinedContent`). The turn is final: the server doesn't auto-retry it (the same request would be declined again, like a workspace refusal or a usage limit past the backoff). The card reads **MODEL DECLINED** with “The model wouldn’t answer this one. Try rewording your request, or switch models for this chat, then send it again.”, and no Try again — on the card, the phone, and the Work view (`turnFailureRetryable(code)` gates `canRetryTurn`/`mayRetry`; `dispatches.retry` of a `refused` turn is a 409). | A jailbroken-console research question on Home kept failing with “Something went wrong on my side, so I stopped. Press Try again.” and auto-retried once — Try again re-sends the same flagged text, so it could only fail again; the person needs to reword or switch models, and the card now says so. |
