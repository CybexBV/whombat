# Key requests: agents ask for a key, a person gives it with one button

An agent blocked on a key it doesn't hold (“Browse the web”) asks for it with an approval; the person who may
change its keys gives it with one button, **Give Tinker “Browse the web”**. Before this an agent could only say
it was blocked, and a quick-reply chip “Give Tinker web.browse” sent text back and granted nothing. Built on the
approval machinery (`ApprovalAction`, `approvalView`, the approvals engine and its executors).

## Maintainer decisions (2026-09-25)

| # | Decision | Why |
|---|---|---|
| KR-01 | **New approval action `grant_key`**, `params: { keyId: KeyId }` (`@whombat/core` `GrantKeyAction`). The key is always for the requesting agent itself: no agent asks for keys on another's behalf. | One small action on the existing approval rails; no way to route keys to someone else. |
| KR-02 | *Amended 2026-10-01 (runs-approvals.md MDS-04): “Merge into main” may be asked for; “Push to main” is the people-only example now.* **Any agent may ask; asking needs no key and is always an approval, never direct.** `request_approval` with `grant_key` has no key requirement (`mcpRequiredKey` → null); `perform_action` refuses `grant_key` (“Ask for a key with request_approval: only a person can give you one.”). Refused with a clear message (`keyRequestProblem`) when the key is people-only (`agentMaxTier: 'never'`: ““Merge into main” is for people. Agents never hold this key.”), the agent already holds it at `can` or at its cap (“Tinker already holds “Browse the web”.”, counting umbrellas, other wordings and bundles), or it breaks the personal-agent rules (PA-07, the same `grantFitProblem` check Configure, hiring and personal agents use). | A person always decides; nobody is asked for something that can't or needn't be given. |
| KR-03 | **Superseded in part by one-person.md OP-S62**: the person decides a key request where it was asked, and the grant still runs as them through `grant_requested_key`. **Who decides: the people who may change that agent's keys.** The approval's approvers are the burrow's owners; a personal agent's request goes to its owner only, in their DM, private (PA-09, as every personal agent's ask). Others see the card and can't approve (`canDecide`). The grant itself runs as the person who approved, through `grant_requested_key`, under Configure's rules (`agents.manage`, `ownerOnly` for personal agents). | The task's “owners”; see KR-D01 for how that relates to Configure. |
| KR-04 | *Amended 2026-10-01 (runs-approvals.md MDS-04): a Merge or Deploy key is given at `ask`, the whole row with it.* **Approving gives the key at `can`, clamped to its cap** (`requestedTier`: an ask-capped key such as “Deploy” goes in at `ask`), replacing the agent's `ask` / `cannot` grant for that key and keeping every other grant (`grantsWithRequestedKey`). Through the commit pipeline, with the signed `Keys` event Configure writes (`keysEventFields`: “Gave Tinker a new key: Browse the web”, signed by the person who approved; payload adds `approvalId`). | Same audit trail as a change in Configure. |
| KR-05 | **Copy.** Title and desktop primary button `Give Tinker “Browse the web”`; question `Give Tinker “Browse the web”?`; target `keys · Tinker`; WHAT HAPPENS 01 `Give Tinker “Browse the web”, to use without asking` (ask-capped: `…, still asking a person each time`). Verbs `give the key` / `gives the key` / `giving the key` / `given` (labels `APPROVED · GIVING THE KEY`, `GIVEN`). Mobile primary button: the whole title when it is at most `MOBILE_CTA_MAX_CHARS` (22) characters, otherwise `Give “Browse the web”`. | The key's catalog label in curly quotes, never its id. |
| KR-06 | **The requester is woken the way a declined request wakes it**: once the key is given, the person who approved replies under the card (`@Tinker, I gave you “Browse the web”. Go ahead.`), a mention that dispatches the agent; a decline says `@Tinker, I didn’t give you “Browse the web”.` (instead of quoting a title that already quotes the key). Executed approvals otherwise don't wake their requester, so the grant does it itself. | The agent carries on without someone having to mention it again. |
| KR-07 | **Agents' instructions** (`apps/runner/src/prompt.ts`): a `blocked` answer names the key (`keyNeeded`, and the message already names its label); unless only people may hold it the agent asks with `request_approval` `{type: 'grant_key', params: {keyId}}` in the same conversation, says so in one short line and stops. Keys are named by label in curly quotes, never by id; no quick replies that pretend to grant a key. An agent without “Browse the web” is told its own tools have no network and which key (`web.browse`) to ask for, since no tool answers blocked for it (not personal agents, which never hold it). The `request_approval` tool description and the MCP server instructions mention asking for a key. | The web case is the one that matters most and has no blocked answer to react to. |
| KR-08 | **The next turn holds the key.** Grants are read when a dispatch is claimed, and a key change starts a fresh provider session (bp-memory), so the woken turn's persona lists the key; `networkFor` reads `can` grants (tested in `apps/runner/src/turn.test.ts` and `apps/server/src/approvals/key-requests.int.test.ts`). | “Browse the web” must actually open the network. |

## Decisions made while implementing

| # | Decision | Why |
|---|---|---|
| KR-D01 | **Superseded by one-person.md OP-S07, OP-S62**: the person is the only approver; there are no members or owners to tell apart. **Approvers are the burrow's owners, although `set_agent_keys` itself lets any person** (`agents.manage` is people-only but not owner-only in the catalog, so members pass Configure's key check). A member in the channel sees the card and can't approve. If Configure is ever narrowed to owners the two agree; if members should decide key requests too, change the approver list in `askForKey` (`apps/server/src/commands/approvals.ts`). | The task names owners and wants a member refused; an agent widening its own keys is a privilege change, so the narrower set is the safe side. |
| KR-D02 | **Asking again while a request for the same key waits answers with that request** (same approval id, number and card), instead of a second card. | Agents retry; one card per key keeps the channel readable. |
| KR-D03 | **The approval's `keyId` is the key asked for**, and the Asks event reads `Asked to get the key “Browse the web”` with KEY USED `Browse the web · asks a person for it`. The approvals engine doesn't re-check the requester's keys before a `grant_key` runs (asking needs no key); `grant_requested_key` re-checks the rules instead, and succeeds without a change when the agent meanwhile holds the key (the reply then says `you hold “…” already`). The executed event, signed by the agent, reads `Got “Browse the web”`. | The log names the key the request is about; a request never fails for lacking the key it asks for. |
| KR-D04 | **The agent's own words stay as detail**: its `whatHappens` lines follow WHAT HAPPENS 01, its `explainer` is shown when given, else `Tinker asked for “Browse the web”, a key it doesn’t hold. If you approve, Tinker gets it right away.`; its `conditions` and `approverIds` are ignored for key requests. The card message is `I need “Browse the web” to go on. Only a person can give me a key.` | What runs and who decides come from the action, never from the requester. |
| KR-D05 | **Mobile**: the approval screen's footer gives a key request's primary button more of the row (flex 2.4 instead of 1.4, about 192dp of text on a 360dp screen), which holds `Give “Browse the web”` (measured 175dp in Bricolage 600 16px) and the whole title up to 22 characters; longer labels ellipsize (the question above shows them in full). The inbox row's inline button (about 108dp) keeps `Approve` for key requests: the row text right above it already reads `Give Tinker “Browse the web”.` | Fits the 360dp screen without a new layout. |
