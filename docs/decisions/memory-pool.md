# One memory pool for the agents' computers (MP-*)

Every row below is superseded by one-person.md (OP-04, OP-16, OP-S108): there are no computers; each row says what still holds.

John, 2026-10-05, after Pippa couldn't read a 136 MB SketchUp model (3.1 GB needed, 1.7 GB free in her 2 GiB computer)
and FS-D12's larger default never reached a box (the appliance's host module writes `WHOMBAT_COMPUTERS_MEMORY_MB` at boot,
min(4096, a quarter)): he considered dropping the computer per agent and asked for alternatives. Findings: an idle
computer costs about 50 MB (systemd, dockerd, containerd and a few small services, from the OOM dump on his box); the
3.2 GB is the job itself and costs the same on the appliance; what hurt is the fixed slice per computer. Proposal “A”
(keep the computers, one shared pool, Whombat protected, Docker started on demand) — John: “Increase the size of the
Whombat appliance VM (Incus) to 16GB. Then implement option A fully.” His box now has 16 GiB.

Appliance side: `appliance/docs/decisions/nixos.md` NX-141… (host module). Release: IN-208.

| # | Decision | Why |
|---|---|---|
| MP-01 | **Superseded by one-person.md OP-04, OP-S108**: there are no computers; each command gets a cgroup of its own inside the task's, with memory up to all but a reserve. **Each computer may use the whole pool**: `limits.memory` = pool = the machine's memory (MemTotal rounded up to whole GiB, as today) less a reserve for Whombat, reserve = a quarter of it but at least 3 GiB and at most 8 GiB; pool at least 512 MiB. 8 GiB → 5 GiB, 16 GiB → 12 GiB, 32 GiB → 24 GiB, 64 GiB → 56 GiB. One rule, written twice and tested against the same table: the appliance's `whombat-computers-memory` script (it writes `WHOMBAT_COMPUTERS_MEMORY_MB`) and `computerMemoryMb` in `@whombat/computer` (computerd without that variable, the server's fallback view). Supersedes RA-45 and FS-D12. `WHOMBAT_COMPUTERS_MEMORY_MB` / the module's `memoryMB` option still override it. | One busy agent gets what's free instead of a quarter; the reserve keeps Whombat itself (database, server, runner, the provider CLIs of running turns, the browser) out of the agents' way. |
| MP-02 | **Superseded in part by one-person.md OP-04, OP-S108**: Whombat's own services still come first and the task sandbox stays at −500; the computers are gone and each command runs at 500. **Whombat comes first when memory runs out.** The appliance gives its own services memory protection and a low OOM score: Postgres, whombat-server/runtime, the runner, the manager and the other core units get systemd `MemoryMin=` (sized per unit, together within the reserve) and `OOMScoreAdjust=-900` (the runner's children — the provider CLIs — inherit a less negative score, e.g. `-500`, via the runner unit's setting or by the runner itself, so a turn's CLI goes before Whombat but after the computers). Every process in a computer runs with `oom_score_adj` 500 (computerd sets `raw.lxc` `lxc.proc.oom_score_adj = 500` at create and on the stopped computer before it starts, next to `limits.*`, RA-DK14). | Computers together may ask for more than the box has (MP-01 is a cap per computer, not a reservation): the kernel then reclaims and, if it must, kills the largest agent job — never the database. |
| MP-03 | **Superseded by one-person.md OP-16**: Docker is rootless Podman with Docker's API, run as its own user on the appliance. **Docker starts on demand.** Base image 8 enables `docker.socket` and leaves `docker.service` and `containerd.service` disabled, so dockerd/containerd start at the first `docker` command. An existing computer is switched the same way at its next start (computerd, once, recorded in the computer) only when it holds no Docker containers (`docker ps -aq` empty): a computer whose containers should come back at boot keeps Docker as it was. | The ~40 MB of an idle dockerd and containerd in every computer go to work instead; most agents never run Docker. |

The skill and script messages about memory (FS-D11) say how much is free now and that other agents' work shares it. *Amended by one-assistant-computer.md OC-02: no “other agents” in the words.* | “4 GB” on every agent would read as reserved; it isn't. |
| MP-05 | **Superseded by one-person.md OP-04, OP-14**: the computer surface leaves contracts 3.0.0. **Contracts.** `computerMemoryMiB` in `@whombat/core` (RA-DC18, the old quarter rule) is unused since FS-D12; the next contracts release replaces it with the MP-01 rule or removes it. No contracts change now. | Nothing reads it; a contracts release for a dead function isn't worth a release on its own. |

## Whombat side as built (MP-D01…MP-D09)

| # | Decision | Why |
|---|---|---|
| MP-D01 | **Superseded by one-person.md OP-04, OP-S116**: `@whombat/computer` is deleted. **The rule in code**: `computerMemoryMb(totalMiB)` = `max(512, gib × 1024 − min(8192, max(3072, gib × 256)))` with `gib = ceil(totalMiB / 1024)`; it takes the machine's memory as the kernel reports it (MemTotal, `os.totalmem()`, fractions allowed) and does the whole-GiB rounding itself, as the appliance's script does with `(kib + 1048575) / 1048576`. Tested against MP-01's table (8 → 5120, 16 → 12288, 32 → 24576, 64 → 57344 MiB) and 7.6 GiB → 5120. The server's fallback view passes `totalmem()` unrounded (was floored to MiB first). | One rule, the same answer as the appliance on every machine, including MemTotal a few MB above a whole GiB. |
| MP-D02 | **Superseded by one-person.md OP-04.** **`raw.lxc` is merged, not replaced**: `rawLxcWithOomScore` keeps every line already there, drops any earlier `lxc.proc.oom_score_adj` line (any case, any spacing) and appends `lxc.proc.oom_score_adj = 500`; it is set at create (computers and the base image's builder) and, next to `limits.*`, on a stopped computer before it starts (RA-DK14) — only when the text differs. Incus 6.0 takes `lxc.proc.*` in `raw.lxc` (it refuses only log, syslog, ephemeral, `lxc.prlimit.*` and most `lxc.net.*` keys). | A person's own `raw.lxc` lines survive; nothing is written to a running computer. |
| MP-D03 | **Superseded by one-person.md OP-04, OP-S108**: a command's OOM score is raised to 500 by its launcher. **What 500 reaches**: LXC writes `lxc.proc.*` as root on the host for the computer's init and for every attached process (`incus exec`, so every turn's command), which also sets the kernel's `oom_score_adj_min`: nothing in a computer can go below 500. systemd there ignores units' lower `OOMScoreAdjust=` (docker.service's −500, containerd's −999) as a container would, and Docker 26 raises its containers' score to its own (moby's “rootful in rootless” rule, since systemd v250), so `docker run` keeps working. | Checked against LXC's `start.c`/`attach.c`, the kernel's `__set_oom_adj`, runc's nsexec and moby 26.1.5. |
| MP-D04 | **Superseded in part by one-person.md OP-S108**: the task sandbox still runs at −500 and the runner unit at −900; commands are raised to 500. **The provider CLIs at −500, set by the runner**: the managed sandbox's cgroup wrapper (`taskWrapperScript`, the `sh -c` that joins the task's cgroup before it execs bubblewrap) raises its own `oom_score_adj` to `TASK_OOM_SCORE_ADJ` = −500 when it is lower, then execs: the CLI, its tools and its MCP servers inherit it. Raising needs no privilege; a score already higher (a development host, a runner unit still at 500) is left alone, and a failed write is silent. **The appliance's runner unit sets `OOMScoreAdjust=-900`** (systemd sets it as root, so the runner's own processes stay at −900 and the floor is −900) and nothing else for this. | Not the unit alone: `OOMScoreAdjust=` is inherited, which would put the CLIs at Whombat's −900; not the runner raising itself: it is Whombat. One place in Whombat, covering every turn, usage probe and assessment that runs in a sandbox. |
| MP-D05 | **Superseded by one-person.md OP-16.** **Image 8, Docker on demand**: the image enables `docker.socket` and `whombat-docker-resume.service` and disables `docker.service` and `containerd.service` (Debian 13's docker.io 26.1.5 ships `docker.service` — `Requires=docker.socket`, `Wants=containerd.service` — and `docker.socket` on `/run/docker.sock`, group docker; containerd 1.7.24's `containerd.service`). The first `docker` command starts dockerd, which starts containerd. | MP-03. |
| MP-D06 | **Superseded by one-person.md OP-16, OP-19**: the agent's services are containers of the engine that come back after a restart when started to. **Containers still come back at boot**: `whombat-docker-resume.service` (`ConditionDirectoryNotEmpty=/var/lib/docker/containers`, a oneshot running `systemctl start --no-block docker.service`) starts Docker at boot only on a computer that holds containers; otherwise its condition fails and nothing runs. In image 8 and written by the switch. | A computer publishing a site from a container with a restart policy (RA-43, started with the appliance) would otherwise wait for someone's `docker` command. |
| MP-D07 | **Superseded by one-person.md OP-16.** **The switch of an older computer** (`DOCKER_SWITCH`, computerd, as root right after the start and before the turn's preparation, image < 8 only): exits early and changes nothing when there is no Docker (3), `docker.service` isn't enabled (4, someone chose), `timeout 30 docker ps -aq` fails (1) or lists containers (2); otherwise writes the resume unit, reloads, disables `docker.service`/`containerd.service`, enables `docker.socket` and the resume unit, and stops dockerd and containerd at once (0). Recorded in the computer as `user.whombat.docker` = `on-demand` (0) or `as-is` (3, 4), so it never runs again; a computer with containers gets no mark and is looked at again at its next start (it switches once they are gone, safe with MP-D06); a failure is logged as a warning, gets no mark, and the start goes on. | The spec's “once, only without containers”; a `docker ps` on a computer whose dockerd runs anyway costs little. |
| MP-D08 | **Superseded by one-person.md OP-04.** **The status line** says `Computer: 2 CPUs, up to N GB memory shared with the other agents, <image>.` — N is the pool in GB with at most one decimal (`memoryGb`: 5120 → 5, 3891 → 3.8, unknown → ?). *Amended by one-assistant-computer.md OC-02: no “other agents” in the words.* | MP-04. |
| MP-D09 | **Superseded by one-person.md OP-04.** **documents 1.3.2**: `model3d.py`'s refusal says the computer “has N GB free now (its memory is shared with the other agents’ work)” and the skill says the computer “shares its memory with the other agents' work” where it explains exit 137; nothing else changes (FS-D11's check is as it was: the computer's cgroup room, which is all a computer can see). Rolled out like FS-D11: migration 0079 queues documents 1.0.0…1.3.1 pins (compat `expand`, runtime reads and writes from 0079). *Amended by one-assistant-computer.md OC-02: no “other agents” in the words.* | The refusal's text lives in the script; a pack bump never moves pins without a queue migration. |
