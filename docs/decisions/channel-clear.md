# Clearing a channel

John, 2026-10-02 (on dev.whombat.com): “When I right click on a channel I want to be able to remove all messages in
that channel so the channel is empty again.” Contracts CT-216 (0.35.0, `conversations.clear`, feature
`channels.clear`); the web side is whombat-app `docs/decisions/channel-clear.md`.

| ID | Decision | Why |
|---|---|---|
| CC-01 | **Owners of the burrow clear channels they are in.** `clear_conversation` refuses agents (“Agents don’t clear channels.”), members (`canClearConversation`, 403 “Only owners of the burrow clear a channel.”), people outside the channel (403) and anything that isn't a channel — DMs, direct conversations, branch rooms (400 “Only channels can be cleared.”). Archived channels can be cleared (deleting still works there, EC-16). `#general` too: clearing empties it, it doesn't remove it. | Removing other people's words is moderation, which is the owners' (EC-03); DMs and branch rooms weren't asked for and have their own lifecycles. |
| CC-02 | **Everything goes except threads that still hold work in progress** (`threadsWithWork`): a run card whose run is live or paused, an approval card waiting for its decision, a plan card with a step not done or cancelled, a skill proposal waiting, a guide still open (EC-04c), a report or assessment card while its report holds work (`reportHoldsWork`, EC-04a), the start of an open handoff's lane, and a thread where an agent's turn is queued, claimed or running (its reply would have no thread to land in). A thread is kept or removed whole. Finished work's cards go — unlike a single delete, which keeps every plan, run, approval, guide and skill card (EC-04): a cleared channel should be empty, and the finished run, the decided approval and the report itself stay in Work, Approvals and Feedback. | “So the channel is empty again”, without taking the place of work that someone still has to act on. |
| CC-03 | **One commit, the same clean-up as a delete**: files (bytes once unused), reactions, search documents, inbox rows, pins (they are on the rows); agents' summaries and sessions that saw the words are forgotten (`forgetStaleContext` for the channel and each removed thread). The channel's `lastMessageAt` becomes its newest remaining top-level message, or null. | Same guarantees as EC-04 (nothing of the removed words lingers), done once for the whole channel. |
| CC-04 | **One signed event, a frame per message.** `channel.cleared` (Messages, “Cleared #name”, payload `{conversationId, removed, kept}` — ids and counts, never words); clients get `message.deleted` per removed message on the conversation topic, as for single deletes, then the unread counts. | No new realtime frame for older clients to learn; the audit log says once what happened. |
| CC-05 | **The answer counts both**: `{removed, kept}`, so the app can say that some messages stayed and why. An empty channel answers `{removed: 0, kept: 0}` without an event. | The person sees a channel that isn't empty and should know it's on purpose. |
