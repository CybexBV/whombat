# AI gateway: Claude Code and Codex through Fusebox

John, 2026-10-10: “add a new connection: Fusebox (https://github.com/DigitalPals/Fusebox). When we set this up and
configure this, we should be able to route all our traffic from Codex and Claude for example through Fusebox. We
should be able to turn this on / off. I also would like to see the remaining usage of the subscriptions.” After the
proposal he answered: his Fusebox is `https://10.100.0.235:8317`; a generic AI gateway for every customer plus the
Fusebox kind; no fallback when Fusebox can't help; the management key is fine; and “I want the connection to
automatically add a new client key when connecting via the management key.” Then: “Implement this fully”.

Fusebox (John's fork of CLIProxyAPI-Rust, ~/Code/Fusebox) exposes Anthropic Messages and OpenAI Responses endpoints
backed by a pool of Claude and ChatGPT subscriptions; its management API (`/api/*`, `Authorization: Bearer
<management key>`) lists every account's 5-hour and weekly limits (`GET /api/accounts`), faults (`GET /api/faults`)
and edits its config (`GET`/`PATCH /api/config/settings`, `named-clients`).

Contracts 0.76.0 (CT-332), migration 0100, whombat-app 0.69.0, appliance candidate 0.80.0.

| AIG-02 | **Fusebox connects with its URL and its management key; Whombat makes its own client key.** Field `url` (placeholder `https://fusebox.example.com:8317`); sign-in `token`, label “Management key”, `auth` Bearer, help “Whombat uses it to add its own client key to Fusebox and to read the accounts’ limits. Then `GET {url}/v1/fusebox/status` with the new key must answer 200 (Fusebox 0.14+; it checks only the key, its expiry and addresses, so user agents or a used-up budget set on the client don't refuse it); a 404 there (an older Fusebox) asks `GET {url}/v1/models` instead. | AIG-09 | **The relay:** the caller's `Authorization: Bearer` or `x-api-key` is the dispatch's agent token (`wat_…`; `verifyAgentToken`) — it is per dispatch, slides with the turn and is already hidden from shell commands (MCP). | AIG-D01 | **`Burrow.aiGateway` is read, not stored whole:** the burrow's gateway connection gives `connectionId`, `name` (its label) and `kind`; `burrows.ai_gateway` gives the switches only while its `connectionId` is that connection's, so a new connection starts with both off and nothing is written at connect. `burrows.setAiGateway` is the only writer; removing the connection clears it (where it names that connection). `burrow.updated` and `usage.gateway_updated` go out when a gateway connection is added, renamed or removed, and when a switch changes. | One source for the name (a rename shows at once) and no stale switches from an earlier connection. |
| AIG-D02 | **One gateway per burrow is checked twice:** before anything is called (`gateway_exists`, `AI_GATEWAY_COPY.exists(<its name>)`), and again inside the `catalog_connection.add` commit under a per-burrow advisory lock (`hashtext('ai_gateway:<burrow>')`), so two connects at once can't both get in. | The first check spares Fusebox a key that would be thrown away; the second is the guarantee. |
| AIG-D03 | **Provisioning's edges:** `GET /api/config/settings` answering 404 is “too old” as well (a Fusebox without the settings API is older still than one without named clients); 401/403 → `check_failed` “Fusebox didn’t accept the management key for its settings.”; a third 409 → `check_failed` “Fusebox’s settings kept changing while Whombat saved its key. Try again.”; a key the check doesn't take is taken out again (on a reconnect: the entry put back as it was) before the refusal “Whombat added its key to Fusebox, but Fusebox didn’t take it. Try again.”; a key made for a connection that then isn't saved is taken out again (best effort). Absent `api-keys` / `named-clients` count as empty. An open Fusebox is stored as no `clientId` and no client key (the relay sends none); a `clientId` without a key is `gateway.missing`. | The settings answer is never logged or stored; only our own words reach the form. |
| AIG-D04 | **Reconnecting is “Replace token”** (`connections.setSecret`, retry class NEVER): the check, then the client key made again in place (same id, a new key) and sealed. `connections.update` can't move a Fusebox to another address (retry class RECEIPT: no write to Fusebox may happen before its commit): “Connect it again to use another address.” Its fingerprint may change. `clientId` lives in `fields` but is left out of the entry's field checks (the catalog has no such field). | The key lives in that one Fusebox; nothing is written there by an op a client may resend. |
| AIG-D05 | **Removing:** the connection is removed first (its commit), then Whombat's client is taken out with the management key it had; when Fusebox doesn't answer or refuses, `connections.disconnect` answers `notice: AI_GATEWAY_COPY.removeByHand(<name>, gatewayClientLabel(<burrow name now>))`. | AIG-03: the connection goes either way. |
| AIG-D06 | **At claim:** the route is decided right after the claim transaction (`gateway/claim.ts`), at every claim — a retried attempt is decided again. A refusal finalizes the dispatch `failed` with `error` = the code, `refusal` = `gatewayRefusalText` (posted like `unrunnable:*` by `recordTurnFailure`, with Try again) and failure code `provider` (as the runner classifies a gateway it can't use, AIG-D22; no usage-limit requeue). A gone connection is named “The AI gateway” in the line. | No sign-in is used, so none can have moved; one classification on both sides. |
| AIG-D07 | **Used up** = every enabled (not `off`) account of the provider `used_up`, with `until` still ahead (or unknown); the line names the earliest. No enabled account is not “used up” (Fusebox answers for itself), and the generic kind is never used up. **Unreachable** = `failures ≥ 2`; before the first poll it counts as reachable. | AIG-11, AIG-12 without guessing. |
| AIG-D08 | **The heartbeat's `gateway`** is the switches of every burrow with a gateway connection on this Whombat, OR-ed: a runner serves every burrow. It is absent while both are off (the contract's “absent: no gateway”), so an older beat's answer is unchanged. | A runner has no burrow of its own. |
| AIG-D09 | **Sessions follow the route (AIG-10):** core's `SessionParts` has no gateway part, so while a switch is on the `provider` part reads `<provider>:gateway:<connectionId>` — a switch change (or another gateway connection) makes the next turn's session fresh, like a change of sign-in. | AIG-D10 | **Readiness** (teammates, `delegate`): on a managed appliance an agent whose tool's switch is on needs no sign-in to be ready. | AIG-07. |
| AIG-D11 | **The relay** (`gateway/relay.ts`): `ALL /ai-gateway/:provider/*`, its own Fastify scope without body parsers, logged at `warn`. `api/hello` (GET or HEAD) answers 200 before any key is read (Claude Code pings without one). The key: `Authorization: Bearer`, else `x-api-key`, looked up by `agentTokenDispatch` (new): unknown or expired → 401; its dispatch not `claimed`/`running` → 409 (a queued dispatch's old token too); no or another `gateway_provider` → 403; a path off the list → 404; `Content-Length` over 64 MiB → 413 up front, a chunked body past it is cut with 413. The connection is the burrow's gateway connection now (gone or keyless → 502). Every refusal is in the provider's error shape. A relayed call slides the token like an MCP call (EA-04); `gateway_account` is written when it changes. | Least privilege per turn; nothing about the box or the caller reaches the gateway. |
| AIG-D12 | **The poller** (`gateway/service.ts`): housekeeping job `ai gateway` every 60 s (first at the next tick), connections one after another, single flight each, paused with maintenance.
