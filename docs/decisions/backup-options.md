# Backup options, the list of backups and bringing a Whombat back

John, 2026-11-03: “I would like to see the backups it made (a list) and set additional options, like how many backups
are made, disk usage on the remote server, and use best practices for the backup settings (but we should be able to
configure them). … What if we have a crash and we have to restore on a new appliance?” → mockups → “At keep a way back
in, can we use a configured passkey for it as well?” → “Implement this fully, use the defaults you suggested”.

Related: [backup-places.md](backup-places.md) (where backups go), [backup-file.md](backup-file.md) (the person's own
file), [passkeys.md](passkeys.md), `appliance/docs/decisions/backup.md` (the backup service, BK-37…),
`hosts/docs/decisions/hosts.md` (the cleanup, HS-251…), control `docs/decisions/control.md` (CL-150…), the
app's [backup-options.md](../app/decisions/backup-options.md).

| ID | Decision | Why |
|---|---|---|
| BKO-01 | **The defaults are the recommended options**: a backup every 6 hours (03, 09, 15, 21 in the person's time zone), kept “up to a year” (every backup of the last 2 days, one a day for 2 weeks, one a week for 8 weeks, one a month for 12 months), no space limit, a restore check every week. A box without a policy file uses them. | A backup takes about 15 s and pauses writes for under 0.1 s on Home, so four a day cost nothing and lose at most 6 hours; restic stores a block once, so a year of monthly backups adds little. |
| BKO-02 | **The backup service owns the policy** (`/persist/backup/policy.json`, `GET`/`PUT /v1/policy`): how often, the time zone, what to keep, the space limit and the weekly check. A 15-minute timer runs `run -if-due`: due when nothing was backed up since the newest slot, or the destination changed; a failure retries after 15 minutes. The drill runs `-if-due` daily: due when the weekly check is on and the last is 6½ days old. Staleness follows the frequency (1.5× its interval plus 2 h). | One place decides when; systemd's start limit and fixed `OnCalendar` can't follow a person's choice. |
| BKO-03 | **What to keep is always time windows** (`--keep-within`, `--keep-within-daily/-weekly/-monthly`), never counts. Restic measures the windows from the newest backup that isn't in the future: tested, a 2099 snapshot doesn't push real ones out. | BK-09's reason holds for the new rules too. |
| BKO-04 | **Who clears old backups**: a backup place's cleanup (the NAS, with the full-access password it holds, BPL-02) applies the policy's windows and the space limit; a destination the box's own key may delete from (disk, SFTP, S3, the box's own disk) is cleared by the backup service after a backup, at most once a day; an append-only destination without a cleanup is cleared by nobody (`clearedBy: 'none'`, said in the dialog). | Deleting stays where the credential may delete. |
| BKO-05 | **The space limit thins oldest first and never the last 7 days**: when the repository is over it, the cleanup forgets with ever shorter windows, the oldest first (months to 6, to 3, to none; weeks to 4, to none; then days to 7; a window already shorter is skipped) and prunes, until it fits or only the last 7 days are left; the status file says `over_limit`. Off at the start. | A cap that silently stops backups is worse than none; the newest week is what a restore needs. |
| BKO-06 | **The list is the repository's**: `GET /v1/checkpoints` lists every snapshot tagged `whombat-checkpoint` whose signed manifest verifies (with this box's key or the adopted one), newest first, with why it was made, its size and what it added, and its last restore check (`drills.jsonl`). Manifests are cached by their sha256, so a list costs one `restic snapshots`. Unauthentic ones are only counted. | People see backups, not snapshot ids; a forged one never looks like theirs. |
| BKO-07 | **“Check this backup now”** queues a drill of that backup (`POST /v1/drills`, a request file the drill's path unit picks up); its result lands on the backup in the list. | The drill already proves a backup restores; the person picks which. |
| BKO-08 | Extended by BKO-30. **Backups left on the box's own disk** (the `local` repository of a box that backed up there before a place) show as one “Needs you” row: Move copies them to the place in use (`restic copy`, same password; the signatures still verify) and removes them from the box; Remove deletes them after a confirm. | Home kept 14 backups on its only disk that nothing listed or cleared. |
| BKO-09 | **Superseded by backup-passkey.md BPK-01**: **The recovery kit can be locked with the person's passkey**: the kit's text is sealed (XChaCha20-Poly1305, key = HKDF-SHA256 of the passkey's WebAuthn PRF output for a random 32-byte salt, bound to the Whombat) on the device, and control keeps only the envelope per (Whombat, passkey) (`/auth/kit-envelopes`), which it can't open. “Your passkey” is recommended and “Print it too” is ticked with it; “Save as a file” stays. A passkey without PRF isn't offered. | One touch on any device that has the passkey; the printed kit keeps recovery working without Whombat's servers (BK-16). |
| BKO-10 | **Superseded by backup-passkey.md BPK-06**: **A kit's passkey outlives its retired Whombat** until the account saves a kit for a Whombat that isn't retired; meanwhile it doesn't sign in (`passkey_kept_for_kit`), and apps don't tell the platform to forget it. | Retiring the old box is exactly what a restore does; the key to the kit must not go with it. |
| BKO-11 | Superseded by BKO-21 (one question), and in part by backup-passkey.md BPK-05 (the kit: the passkey's envelope from the account or the network, a place found by its repository; the rest held until BKO-21): **Bringing a Whombat back is an app flow** on a freshly claimed box: “Is this a new Whombat?” → the kit (passkey envelope, scanned printed kit, or the file) → `backup.adopt` joins the old repository → pick a backup (newest checked first) → `backup.restore` → the manager starts the root restore (the backup service's `restore` command: stop the runtime, set the fresh install aside, check and restore, make the database writable, start the runtime) → the runtime comes back quarantined (no automations, no outbound work) → the person answers three cards (old Whombat gone or lost, sign-ins, devices) → `backup.finishRestore` resolves the checklist (the rest Whombat's: revocations none after the backup, outcomes left to the assistant, identity re-pinned by the device that answered, destination adopted) and releases → runtime and servers restart. | The console runbook, without a console. |
| BKO-12 | **While the runtime is down** the app shows the steps it can know (checking, copying, putting back, servers) and polls until the box answers again. | Nothing on the box serves the app then. |
| BKO-13 | **After a restore the assistant says what came back** in the person's Chat: one plain message, posted as the assistant without starting a turn (back as it was at that time; anything after it isn't there; it offers to look in GitHub and the person's accounts). The person asks; nothing after the backup is replayed. | External outcomes after the checkpoint are never replayed (BK-13); the person decides what to look for. |
| BKO-14 | **What Whombat watches** gains nothing that starts on: a failed weekly check and a repository over its limit are the place's and the backup's existing hints (BPL-11), off at the start. | watch-defaults.md. |
| BKO-15 | **The list comes a page at a time** (John, 2026-11-04, after the review): `backup.checkpoints` answers the newest 50 and a cursor, `backup.adopt` the newest page of the backups it joined; the runtime takes the backup service's whole list (up to 16 MiB) and pages it. Each backup carries what it covers (`covered`, from its signed manifest) for “What’s in it”. | A place nobody clears reached the socket's 256 KiB after about 730 backups, and the list and bring back failed; a phone shouldn't be sent megabytes. |
| BKO-16 | **One job keeps the place right**: every five minutes (and right after the person's options or yes) one job, inside the place lock, puts the schedule in the person's time zone, follows the NAS's address, hands the cleanup the person's keep, gives the place a new password after a “lost or stolen” restore, moves the backups left on the box's own disk, carries out the claim's yes, tells the first backup and refreshes the places' hints. A step with nothing to do reads nothing; the network is read only for a place Whombat set up. It waits during a restore (quarantine) and a drain. Other parts of the server add their own step to it. | The follow and the policy sync each read the whole network every five minutes, missed changes, and ran during a restore. |
| BKO-17 | **Never the defaults over the person's options**: a policy that doesn't parse whole is never written back (not even its time zone), and the cleanup is handed only windows that parsed. | One new field from a newer backup service made the sync PUT the recommended options over the person's. |
| BKO-18 | **Every cleanup change is tried again until the place took it**: the place's record keeps what its cleanup was last handed, written only once the place took it, and it is handed again when that differs in any window or the limit from the person's, when the place says it has none, or when its helper reports keeping something else. | Only the days were compared, and only with a cleanup that was on: changed windows or a limit that failed once, and a cleanup never handed over, stayed wrong. |
| BKO-19 | **An older helper can't clear too much**: a helper that doesn't report what its cleanup keeps (from before the windows) gets the longest window as its days (a year by default, at most 3,650), never the 2 days of every backup; it is handed the keep again once a day, and as soon as it reports the windows (it was updated) it gets them. | An older Unraid or Linux helper ignores the windows and would have cleared everything older than 2 days. |
| BKO-20 | **Nothing is deleted or replaced while the backup service doesn't answer**: forgetting a place (with or without its backups) and the assistant setting where backups go wait until the service says where they go now; the person reads that in plain words. | Without the service's status no place counted as in use, so forgetting deleted the live backups and the assistant's “already set” check was skipped. |
| BKO-21 | **After a bring back the person answers one question: is the old Whombat gone, or lost or stolen?** Sign-ins that need it ask again on their own, devices are on the Devices page. Finishing can be done again: what was answered stays, the assistant says what came back once, and a restart that didn't happen is asked for again. | Three cards asked what Whombat can see itself; a restart that failed left the box released but not restarted, and trying again was refused. |
| BKO-22 | Amended by BKO-50 (a place Whombat can't change: the person is asked). **Lost or stolen really rotates**: once the box runs normally again, the place in use gets a new REST password (the same repository, so its history stays) and the box's destination takes it, so the old box can no longer add backups there; the recovery material changes with it, so the kit is locked again. The backup service is told the answer and the restored backup, for trusting the earlier Whombat's key only up to it. | The REST password was reused: an old box back on the network kept write access, and its new backups listed as the earlier Whombat's. |
| BKO-23 | **Saving options never waits behind a move**: the options are saved at once and the place's cleanup follows from the job; setting a destination by hand waits for the place flows like they wait for each other. | An Unraid location move holds the place lock for up to an hour. |
| BKO-24 | **Who clears is what happens**: a place set up by hand has no cleanup, so its backups are cleared by nobody (`clearedBy: none`), as an append-only destination of the person's own. | It said the place cleared them. |
| BKO-25 | **When the backup service is down people read it plainly** (“Your Whombat’s backup service isn’t answering right now…”); a status read gives up after 10 seconds, not an hour, and reads at the same time share one answer. | People saw “Something went wrong on the appliance”, and a stuck service held every page. |
| BKO-26 | **“I’ll tell you when the first backup is done” is kept**: when the assistant set a place up on the person's yes, Whombat says in that thread, as the assistant, when the first backup is done, or plainly that it didn't work and is tried again. | It was promised and never said; a failed first backup was only logged. |
| BKO-27 | **Backups failing or late are one Inbox item**, with *Ask {assistant} to fix it*: failing for 45 minutes (the service tries again after 15, so one blip never shows) or late by the service's own rule. It starts on (a backup not happening is very important, watch-defaults.md), settles by itself once a backup works again, and a new episode is a new item. | Nothing told the person when backups stopped. |
| BKO-28 | **A finished bring back tells the person**: when the restored box comes back waiting for the answer, one push (“Your Whombat is back. Open it to finish.”), the only one a box sends before that answer, and an Inbox item while it waits, for an app that was closed meanwhile. | “We’ll tell you when it’s ready” had no push behind it; an app killed mid-restore reopened as if nothing waited. |
| BKO-29 | **Bring back stays possible later**: `backup.adopt` with `replace` (the person confirmed it) may join an earlier Whombat's backups on a box that already has its own; the backup service decides what that allows. | A mistaken “Start fresh” shouldn't be final. |
| BKO-30 | **“Let {assistant} set it up” at the claim is the yes**: Whombat keeps it, and once the AI is connected the assistant sets up the place the person saw (else the best one ready) and says so in one sentence; the Inbox proposal stays away meanwhile and asks only if that didn't work (no place ready within half an hour, no AI within a day, or it failed). Backups left on the box's own disk move to the place as part of a place's yes; the Backups page's row is for what couldn't move. | The person said yes twice, once at the claim and again in the Inbox. |
| BKO-31 | **The Backups page loads in one request** (`backup.overview`: status, places, the newest page of backups with the space, the options); a box from before is read part by part. A backup file's upload starts without hashing the whole file first, on a box that takes it. | Opening Backups read the network three times and the service's status four. |
| BKO-32 | **Plain words about when**: nothing says “every night” or “tonight” (backups run every 6 hours unless the person chose otherwise, and the first starts at once); the backup service's reasons keep their curly quotes and accents. | The words were from before the options. |
| BKO-33 | **One backup item in the Inbox at a time** (2026-11-04, integrating backups v2 and the passkey), the first that applies of: a restore waiting for its answer (while quarantined, nothing else), backups failing or late, a bring back a restart stopped, the proposal of a place, then the passkey's ask (BPK-09), which shows only while the backups themselves work. | Three parts each added their own item; at once they crowded the Inbox and could contradict each other (“use your passkey” on backups that fail). |
| BKO-34 | **A bring back a restart stopped says so and can be tried again**: the backup service's restore result `interrupted` (the box restarted mid-restore and was put back as it was) is a failed restore whose reason is `interrupted`; `backup.restore` takes the same backup again, and for a day the Inbox holds “Bringing your Whombat back stopped” with the service's own plain sentence and *Try again*. People read the service's `error`, never its technical `detail`, which stays on the box. A refusal up front has no item: the person saw it where they asked. | A power cut leads to “Try again”, never to a factory reset, and the person may not have been looking when it happened. |
| BKO-35 | **Who clears and what a backup left out are the backup service's word**: `clearedBy` follows the status's `clearing.by` (`box` → the box; `destination` → the place's cleanup when Whombat set the place up, else nobody; a service without it as before), and what the last backup left out (`lastSuccess.incomplete`: attachments that weren't on the box, the servers) reaches the summary in the service's plain words and each backup in the list. Nothing in these new members is ever a reason to refuse the status. | The space limit and “who clears” match reality, and a backup with a gap says so instead of looking whole. |
| BKO-36 | **The Backups page says where older backups are** (2026-11-04, merging backups v2): `backup.overview` names the places that kept this Whombat's backups before the one in use (their records hold another repository, newest change first), and the page says in one quiet line under the list that the older backups stay there and show again if backups go back. Nothing is said while the backup service hasn't said where backups go, or about a NAS location changed in place (its record holds the new repository only). | Moving to another place left the old backups behind without a word; the records already know which places held a repository. |
| BKO-50 | **Lost or stolen on a place Whombat can't give a new password** (2026-11-04, after the rehearsal): a place set up by hand, or a REST server, disk or bucket typed in. The rotate step keeps a note (`changePassword`, with the place's name) instead of dropping it, and one calm Inbox item asks: “Change the backup password on BlackBox”, saying what to do (set it up by hand again, which gives it a new password; or change it there and give Whombat the new one) with Open Backups; it goes once the person sets a destination again. Its check (`box.backup_password`) starts on: the old box could keep adding backups, and only the person can close that. The restore state says who can (`newPassword {by: whombat \| you, place}`), so the question's words promise a new password only where Whombat gives one, and the done screen gets one line. Amends BKO-22. | The rotate step skipped such a place silently, and the question promised what couldn't be done. |
| BKO-51 | **An old Whombat's backups made after it was replaced aren't picked**: in a list of backups to bring back, a Whombat counts as replaced from the first backup there of a Whombat that came later (one brought back from it, backing up to the same backups); its backups after that are marked “Made by the old Whombat after you replaced it” and the newest other one is picked first (`madeAfterReplaced`, `backupToBringBack`). Control's account data doesn't say when a Whombat was retired, so the backups' own order is the record; a list without the later Whombat's backups can't tell. | A stolen box's later backups were offered as the newest, steering the person to the thief's state. |
| BKO-52 | **“First backup” is each Whombat's first** in a list read to its start (none in a page that goes on), so a Whombat brought back still calls the earlier one's first backup that; and **a Whombat brought back says when the newest backup in its list was** rather than “No backup yet” before it made one of its own. | The rehearsal: “First backup” became “Scheduled”, and “No backup yet” sat above a list of two. |
| BKO-53 | **What a backup left out is always a sentence for people**: the app shows the backup service's reason only when it reads as one (no path, error code or tool prefix; straight apostrophes made curly), else a sentence from what is known (the servers, how many files), else a general one (`plainLeftOut`). | An older backup service's raw error (`whombat-hosts: stat /persist/hosts/hub.db…`) showed on every backup of a fresh box. |

Getting one thing back from a backup (a chat, a file, an automation) is [backup-look.md](backup-look.md) (BKO-40…BKO-49).

## Server (BKO-S)

| ID | Decision | Why |
|---|---|---|
| BKO-S01 | Superseded by BKO-S08. `managed/backup-options.ts` holds the ten ops. | BKO-S10 | **The cleanup record** (`backup_places.cleanup_keep`: the keep, whether it went as windows, when): written by `handCleanup` only after the place took it. `cleanupDue` decides from it, the person's keep and the helper's report (`cleanupReport`: a server's `cleanup.set` and `cleanup.keep`; a NAS says only whether one is set and always takes windows).
