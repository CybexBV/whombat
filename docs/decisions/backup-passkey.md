# The passkey is the key to the backups (BPK-*)

John, 2026-11-04, after a review of backup and restore: “The passkey is the key.” One touch, once per Whombat, gives
it a backup key; it locks its backup details again after every backup and every move and keeps the locked copy at
Whombat's servers and next to the backups; bringing it back is touching the passkey and picking a backup; paper is
optional and never goes out of date with a new address; nothing nudges a second passkey; the last step of a bring back
adds a passkey for the new Whombat, and that touch arms it. The shared spec is the orchestrator's
(`~/.cache/wb-tmp/backup-v2/spec.md`, section 1, interfaces I1, I2, I3, I6, I7).

Related: [backup-options.md](backup-options.md) (whose BKO-09, BKO-10 and BKO-11 this replaces in part),
[backup-places.md](backup-places.md) (the places), [passkeys.md](passkeys.md) (PK-*), managed-runtime.md MR-25 (the
recovery key, unchanged), the app's [backup-passkey.md](../app/decisions/backup-passkey.md) (AP-6865…), contracts
CT-1670… (`docs/contracts/decisions/contracts.md`), control (the device route, the kit drop rule, CL-151…),
the appliance (the manager's route, MG-147…), the hosts service (the kit user on Unraid and Linux, HS-252…).

| ID | Decision | Why |
|---|---|---|
| BPK-01 | **The Whombat locks its own backup details with a key from the person's passkey.** A device that touched the passkey derives it: the WebAuthn PRF output for the constant salt `KIT_PRF_SALT_V2` = SHA-256(`whombat backup key 1`), through HKDF-SHA256 with info = the Whombat's PeerId (`kitKeyFromPrf`), so every Whombat has a key of its own. The device hands the Whombat only that symmetric key (`backup.passkeyKey.set {credentialId, salt, key}`), never the PRF output; the Whombat seals its backup details with it (`sealKitWithKey`, the same `wbkit1.<nonce>.<ciphertext>`), and `openKit` on any device that has the passkey opens it. Envelopes keep their salt, so the ones devices locked with a random salt still open. Replaces BKO-09. | One touch on any device; control keeps envelopes it can neither open nor forge, because it never holds anything the key comes from — a public key would let it forge. |
| BPK-02 | **Arming is one touch, once.** Every passkey touch asks for the PRF output: a passkey sign-in in the same touch (the salt is constant because a sign-in doesn't know the Whombat before the passkey names it), adding a passkey where the platform answers PRF at creation (else the next touch), and the Inbox's “Use my passkey”. The output never leaves the device: it is read out of the platform's answer and dropped from the WebAuthn JSON before anything goes to control or the Whombat. A sign-in's key waits in memory until the app opens that Whombat. Only the person on an enrolled device may set a key (the assistant's settings map says `never`; no outsiders' tool), and only for one of their own live passkeys of this Whombat (`backup_passkey_unknown`). | The person never does anything for it but touch the passkey they already use. |
| BPK-03 | Superseded in part by BPK-17 (what makes it try again). **The details are locked again** when they change (a new destination, password, manifest key or generation), after every successful backup (the head is current) and when a key is armed. The envelopes go to control through the manager (`kit-envelopes`) and next to the backups (BPK-04); what didn't go is tried again (a minute after the backup service's report changes, else every five minutes). | A bring back always finds the newest details and the newest backup's head. |
| BPK-04 | **The copy next to the backups.** Every backup app Whombat installs has a second user, `kit` with the well-known password `whombat-kit` (`PLACE_KIT_USER`, `PLACE_KIT_PASSWORD`), whose own repository path is `/kit/`. The Whombat writes one file per passkey, named by the SHA-256 of its bytes (`{kind: 'whombat.kit-envelope/1', appliance, applianceName, credentialId, salt, envelope, generation, createdAt}`), when the details change and at most once a day otherwise. The place's cleanup keeps the newest 10 files of each Whombat. A Synology, TrueNAS or QNAP gets it in the compose Whombat writes; an Unraid or Linux server from the hosts service's `ensure`. | Safe to publish: an envelope opens only with the person's passkey (the PRF output is 32 random bytes) and the app never deletes or overwrites. A new Whombat on the same network then needs neither account nor servers. |
| BPK-05 | **Bringing a Whombat back is touching the passkey and picking a backup.** The envelopes come from the account at control; when it has none, from the backup apps on this network (the hosts the network scan found, the servers and connections, ports 8747–8766; `backup.findKits`). A kit — an envelope or the paper copy — whose address no longer answers finds its place by the repository: the backup app on the network whose same path's `config` answers to the kit's REST user and password. Replaces BKO-11's kit step; the rest of BKO-11 holds. | A DHCP lease or a move must not make a kit useless. |
| BPK-06 | **After a bring back** the Whombat names the one it came from (`adoptedFrom`, its device id) with its first envelopes, and control forgets that retired Whombat's envelopes, and the passkeys it kept for them, only once a live Whombat of the same account reported it and has an envelope of its own (the kit drop rule; an app's own save never forgets another Whombat's). The passkeys that came with the backup are removed on the new Whombat (they name the old one, so they can never open it). The last step adds a passkey for the new Whombat, and that touch arms it. Replaces BKO-10. | The way back must outlive the old box exactly as long as nothing else holds it. |
| BPK-07 | **Paper is optional and holds only the backup part** (what its QR code held), never the recovery key, so the owner prints it whenever they like without the old kit, and saving it again asks nothing (`paperCopyText`, `backup.paperCopy.confirm`). It stays good when the place gets a new address (BPK-05), not when a password or the manifest key changes. The recovery key, and that rotating it needs the old one (MR-25), are unchanged. | The passkey is the way back; paper is for those who want one without any device. |
| BPK-08 | **Where bringing it back stands** is part of the backup summary (`bringBack`): `ready` (a passkey's key locked the current generation and control kept it), `needs_passkey`, `paper_only` (no passkey, a paper copy of the current details), `none` (no backups a new Whombat could open), with how many passkeys hold the key and when the locked copy, the copy next to the backups and the paper copy were made. “Can be brought back” is `ready` or `paper_only`. | One answer for every screen. |
| BPK-09 | Superseded in part by BPK-21 (its words). **One calm Inbox item asks for the touch** while the Whombat has backups and no passkey holds its key: “Use your passkey as the key to your backups?” with Use my passkey, which runs the touch where it is tapped (no passkey for this Whombat yet: one is added, and that touch arms it where the platform allows). It goes once a passkey holds the key. Its check (`backup.passkey`) starts on; a current paper copy is a way back, so it doesn't ask then. Nothing asks for a second passkey. | Data at risk if the box breaks, and only the person can give the touch (watch-defaults.md). |
| BPK-10 | **A key goes with its passkey**: removing a passkey (or the passkeys of an account) removes the backup key it gave; `backup.passkeyKey.remove` does it by hand. | A passkey that no longer opens the Whombat shouldn't keep a way into its backups. |
| BPK-11 | **The envelope push is control's signed device op `kit.envelopes.put`** (2026-11-04, as control and the manager built it): a normal device request signed like `status.report` (`POST /v1/device/kit.envelopes.put`; control takes `PUT /v1/device/kit-envelopes` too), body `{envelopes: [{credentialId, salt, envelope, generation}] (0…64, each ≤ 65,536), adoptedFrom?}`, answer `{stored, skipped}`; the runtime's call is the manager's `POST /v1/backup/kit-envelopes`, the same body and answer, or 503 `control_unreachable`. `adoptedFrom` stays the old device id (`wb-…`); control takes that or the content PeerId. A skipped envelope (a passkey control doesn't hold for this Whombat) is logged, not sent again. Supersedes BPK-S05, and BPK-S04's per-envelope bound. | The contracts follow what the other repositories built; one device route for every op. |
| BPK-12 | **The kit user is given by the keep-the-place-right job**, inside the place lock where every change to a place is made: the copy next to the backups that finds no kit user leaves a note (`box_backup.placeKit`) and runs the job soon; its `placeKit` step runs `keepPlaceKit` (lock-free now, the step its only caller), and the note goes whatever came of it but an error (the next copy that finds none leaves it again, at most hourly; the app is set up again at most once a day). An Unraid or Linux server's kit user is read per client (`backup_place.clients[].kit`), as the hosts service reports it. Supersedes BPK-S07's own lock. | `keepPlaceKit` called from inside the job would wait for itself; called from outside, it raced the job's own changes. One job, one lock. |
| BPK-13 | **A new destination is locked again at once**: every destination the box sets (`setBackupDestination`: a new place, its new address, the new password after a “lost or stolen” bring back, which also bumps the generation) runs the re-lock right away (`whenDestinationSet`), not when the manager next reports. | The rotation after a lost box must not leave control and the NAS with envelopes of the old password. |
| BPK-14 | **Locking waits like every background effect**: during a restore, in quarantine and while drained for an update, nothing is pushed or written (`later`); the job tries again once the box runs normally. | A quarantined box sends nothing but its one push. |
| BPK-15 | **A Whombat brought back names the old one at once** (2026-11-04, after the rehearsal on throwaway VMs): after either answer (broken or wiped, lost or stolen), its first push names the Whombat it came from (`adoptedFrom`), with no envelope when it has none yet (`envelopes: []`), so control switches the old one off without waiting for a passkey of the new one; tried again until it went (`somethingWaits`). The done screen says so. Supersedes BPK-S04's “`adoptedFrom` goes with every envelope until one push carried it” and BPK-06's timing. | Nothing retired the old Whombat in the rehearsal, even when it was stolen; a person who skips Add my passkey would leave it reaching the account. |
| BPK-16 | **The Whombat's name goes with its envelopes and next to its backups**: the push carries `applianceName` and the place's kit file its `applianceName`, the name the person's app gave the box (control's), else the name it got at onboarding (its burrow's); one line, at most 80 characters, nothing invisible (`ownNameOf`). Every start sends all envelopes once with it, and a new name again; a manager or control from before that refuses the member (400, `control_refused`) gets the push without it until the runtime restarts. | Control's list, the kit file and the bring back said a device id or “Whombat”. |
| BPK-17 | **Locking again follows the backup service's own status**: the job asks the service every minute (`boxBackupStatus` fresh: the newer of its answer and the manager's report) and locks again when a backup, a move or a generation changed it; a service that doesn't answer is no change; the pause during a restore reads the same status. Replaces BPK-03's “a minute after the backup service's report changes”. | The manager's facts never carried the backup status, so nothing locked again after a backup and control's head lagged up to a day. |
| BPK-18 | **Right after the claim the network look scans as the box**: with no burrow or person yet (before onboarding), `backup.findKits` scans the box's own networks (its interfaces and the home network list, no connections; `scanAsBox`, kept 10 minutes like a burrow's) and waits up to 75 s, then reads what was found so far; a box with a person scans as them, as before. Extends BPK-S08. | The look found nothing at exactly the moment a new box needs it: no scan had run and none could start. |
| BPK-19 | **A removed passkey's kit isn't offered**: the account's kits are offered only for passkeys the account still has at control (`auth.passkeys`); on the network one of another passkey is offered only for a Whombat no live passkey's kit opens (it may be another account's). Removing a passkey removes its key on the box (BPK-10) and, through the app, the passkey at control (PK-08), where control drops its envelopes; the copy next to the backups can't be deleted (the app only adds), so new copies of it simply stop. | A passkey removed because a phone was lost still opened the backups' details from control. |
| BPK-20 | **Names up to 80 characters everywhere a kit carries one** (`KitEnvelope.whombatName`, `PlaceKitRecord.applianceName`, `BackupFoundKit.applianceName`, the push's `applianceName`), as control's names are; the device op's note says an unclaimed device keeps nothing and is answered `{stored: 0, skipped: n}`, as control does. | The vendor stream found both gaps (R-07, R-08). |
| BPK-21 | **The ask is the last step, not a choice** (John, 2026-11-04: “it should be the default that the passkey is used for backups”). The passkey already is the backups' key by default: every touch arms it (BPK-02). What can't be skipped is the one touch, because the key comes from the passkey on the person's device. So the Inbox item says “Touch your passkey once to finish setting up backups” with *Touch my passkey*, never a question. The app's Backups line and This Whombat say the same. | “Use your passkey as the key to your backups?” read like an option to turn down. |

## Server (BPK-S)

| ID | Decision | Why |
|---|---|---|
| BPK-S01 | **Storage** (migration 0039, expand): `backup_passkey_keys` (one row per (PeerId, credential id): the account, the salt, the key sealed with key custody under AAD `backup_passkey_key:<appliance>:<credentialId>`, and the envelope last locked with it with its generation, digest, when, and when control kept it) and `backup_key_state` (per PeerId: the old Whombat until control was told, the paper copy's repository, generation and digest, the current details' digest, the copy next to the backups' place, digest and times, and when the place was last given the kit user). Rows of another PeerId came with a backup of an earlier Whombat and are never used. Every set and remove is a signed appliance event (`backup.passkey_key_set`, `backup.passkey_key_removed`, `{credentialId, accountId}`). | The vault's pattern; a restored database can't make a new box use an old box's keys. |
| BPK-S02 | **rest-server 0.14.0's rules, checked** against the pinned image in throwaway containers (agent-resource, 2026-11-04): uploads are `POST /<repo>/<type>/<name>` (PUT answers 405, so I3's `PUT /kit/keys/…` is a `POST`); the name must be 64 lowercase hex characters (else 404) and, checked for `keys`, the SHA-256 of the body (else 400; `config` has no name); the same name again answers 403 (append-only), DELETE 403; `POST /kit/?create=true` answers 200 every time; `GET /kit/keys/` lists `[{name, size}]` with `Accept: application/vnd.x.restic.rest.v2`; with `--private-repos` the kit user gets 401 everywhere but `/kit/` and every other user 401 on `/kit/`; `config` answers 200 to its own user only once it exists (404 before, 401 with a wrong password). The generated NAS compose was run the same way: both users, private repositories, and the cleanup's pruning on busybox. | The naming rule fits content-addressed files exactly; a HEAD first spares the 403. |
| BPK-S03 | **What “changed” means.** Control's envelopes are sealed again when the details' digest without the time they were read changes (a new head after every backup, a generation, a destination); the copy next to the backups when the digest without the head changes, or the place does, else after a day (after a failure an hour later); the paper copy is current while the digest of the secrets and the repository id (not its address, generation or head) is the one at the last lock. `ready` needs an envelope of the backup service's current `kitGeneration` that control kept. | Every backup re-locks for control, cheaply; the NAS isn't written four times a day; a moved place keeps the paper good. |
| BPK-S04 | Superseded in part by BPK-11 (control's bounds and answer) and BPK-15 (`adoptedFrom` goes in the first push, with or without an envelope). **Pushes** are split to stay within a device request (about 40,000 characters of envelopes, at most 20, each envelope at most 32,768); control keeping fewer than were sent is logged, not retried; the manager or control unreachable (503 `control_unreachable`, or no answer) or an older manager (404) is tried again by the job. `adoptedFrom` goes with every envelope of the Whombat until one push carried it. The dev stand-in manager answers as control would. | One push per change; a box with an older manager still locks for the NAS. |
| BPK-S05 | Superseded by BPK-11. **The device op is `kit-envelopes`** (`DEVICE_OPS`; `POST /v1/device/kit-envelopes` through the device API's one route, signed like `status.report`; control may take the spec's `PUT` on the same path too), body `{envelopes: [{credentialId, salt, envelope, generation}], adoptedFrom?}`, answer `{stored}`; the runtime's call is the manager's `POST /v1/backup/kit-envelopes`, the same body. `adoptedFrom` is the old Whombat's device id (`wb-…`): the backup names its appliance by device id, and control's devices are keyed by it. | One device route for every op; I2's `adoptedFrom?: string` made precise. |
| BPK-S06 | **The NAS compose** gives the server the kit user's bcrypt line (fixed, hashed once: a redeploy changes nothing) beside the client's, mounts `<backups folder>.kit` on `/data/kit` (beside the backups, never inside the repository) and on the cleanup's `/kit`, whose daily or weekly run keeps the newest `KIT_KEEP` (10) files of each Whombat by time. No client is called `kit`, and reading a compose back never takes the kit folder for the backups'. | The same app, one user more; the cleanup has the disk anyway. |
| BPK-S07 | Superseded in part by BPK-12 (the job gives it, inside its lock). **Places from before the kit user** (`keepPlaceKit`): when writing the copy finds no kit user, a NAS's app is set up again (its compose has it now), an Unraid or Linux server's through `ensure` only once its agent reports `backup_place.kit: false` (an agent that doesn't say is older and can't), at most once a day, always where the backups are now (no location: a NAS given another would start a new repository); a place set up by hand is left alone. It takes the place lock itself, so the keep-the-place-right job calls it outside the lock. | Existing places get the user without a person doing anything. |
| BPK-S08 | **The network.** Plain http only to private IPv4 addresses; at most 64 hosts, 20 ports each, 64 at a time, 1.5 s per look; files up to 64 KiB, each checked against its name. A new Whombat that never scanned its network scans first and waits up to 75 s. In tests nothing on the network is reached unless the test hands in its own (`useKitNet`). | A minute at worst, once; a test never touches the home network. |
| BPK-S09 | **A finished bring back** (`finishRestore`) records the old device id and removes the passkeys created up to the restored backup's time (signed `passkey.removed`, by nobody); one made since stays, so finishing again is harmless. | Listed, they would sit in `excludeCredentials` and keep a phone that has them from making a passkey for the new Whombat. |
