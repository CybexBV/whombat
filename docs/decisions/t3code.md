# T3 Code (T3)

John, 2026-10-30 (main checkout): “I want to add FULL support for the T3 Code api: https://github.com/pingdotgg/t3code
as a connection. Can you research this and build this?”

T3 Code is a control surface for coding agents (Claude Code, Codex, Cursor and others) that runs as a server on a
person's computer (`t3`, its background service or its desktop app). Its server has two APIs: the WebSocket RPC its own
apps speak, which refuses every outside agent's sign-in, and an MCP server at `/mcp` that it documents for agents it
didn't start (`docs/user/outside-agents.md` in T3 Code). Facts below were read from T3 Code's source (0.1.5, 2026-10-30)
and checked against a real T3 Code 0.1.3 server.

## The connection

| # | Decision | Why |
|---|---|---|
| T3-01 | **T3 Code is a connection** (`t3code`, Developer, handle `t3`): one computer's T3 Code by its address (`http://<computer>:3773`), through its MCP server for outside agents. The agent gets T3 Code's own tools, so everything an outside agent may do there it may do: read projects, threads, AI programs and scheduled tasks; start, message and stop threads; answer their questions; schedule work. | T3 Code's MCP server is its only API for agents it didn't start; its WebSocket RPC refuses MCP sign-ins and is its apps' private protocol. Its own tools keep up with T3 Code without Whombat changing. |
| T3-02 | **Signing in is a pairing code**: the person makes one in T3 Code (Settings → Sharing & access → Create link → Copy code, or `t3 auth pairing create`; it works once, for 5 minutes) and gives it with the address. Whombat's server signs in as T3 Code links two of its own computers: it registers itself (`client_name` “Whombat”, or “Whombat (name)”), approves the sign-in with the code and exchanges it for a token, with no browser and no redirect (a loopback redirect nothing listens on, read from the answer). It is the catalog's sign in once with no account (`password`, `account: null`, the secret's own words); the token is kept as the entry's token sign-in, which the form doesn't offer (`storedOnly`). | The person's browser may not reach the computer, and T3 Code's page for a browser asks for the same code anyway. One field is the least there is to do. |
| T3-03 | **Look only is T3 Code's Read only, Manage its Full access.** T3 Code refuses an outside agent any change to a thread that runs with more access than its own, and threads run with full access unless the person chose less, so anything less couldn't answer, message or stop the person's threads. | The level that makes Manage mean something; Read only is enforced by T3 Code itself. |
| T3-04 | **The tools as served**: all of T3 Code's MCP tools except those that only work inside a T3 Code thread (previews, devices, HTML renders, delegated tasks, `create_threads`, `request_secret`, a thread's own worktree) and attachment uploads, which need a second request Whombat can't make (`mcpTools.hidden`). T3 Code marks some reads as changes; the entry names them reads (`mcpTools.reads`): reading a thread, and listing or reading a thread's questions, its queue or a transfer's status, so Look only can use them. What asks first: T3-14. | Tools that always fail only cost the agent turns. |
| T3-05 | **Thirty days, then a new code.** T3 Code ends an outside agent's sign-in after 30 days and has no refresh. Whombat keeps when it ends (the connection's `access_expires_at`, as an OAuth token's end) and the page says it (“Signed in until 29 Nov”). Signing in again is the connection's Sign in again with a new pairing code: `connections.setSecret` runs the sign-in once more when the entry's sign-in has no account, and the connection, its tools' tiers and its page stay. | There is nothing Whombat can renew by itself; a T3 Code sign-in that may make pairing codes is not one an outside agent can get. |
| T3-06 | **Found on your network**: port 3773 over http, `GET /.well-known/t3/environment` (200, with `orchestrationProtocolVersion`, version from `serverVersion`). T3 Code answers on the network only as a background service (it then closes every connection from a non-private address) or started with `--host`; on its own it listens on the computer itself. | T3 Code's own unauthenticated descriptor, the one its apps check a route with. |

## A job that keeps moving (2026-11-09)

A council reviewed tracker bug-report flow, after a look at Acme production report #22: its fix's job view stayed
on “Reading 35m” for the whole fix (12:13 to 12:50) and only caught up once the run ended, and it never showed the pull
request the automation opened, its checks or its merge.

| # | Decision | Why |
|---|---|---|
| T3-44 | **The job keeps moving while a turn waits for it.** The watcher reads a thread and keeps its state, steps and progress whether or not a turn of the agent is at work where it is told (an automation's step waits for its thread in its own turn, for hours). While one is, it tells, wakes, settles and hands on nothing (that turn may read the thread itself), and only the question the job waits on is still read, for the person to answer (T3-38). Once the turn is over the next pass decides as before, by the keys, so what the agent didn't see is told once. A thread T3 Code no longer has is read again after the turn, as before. | The watcher skipped every thread whose turn was busy, so an automation's job showed nothing new until its step ended. Reading is the person's view; only telling would get in the agent's way. |
| T3-45 | **Every item is read once.** Each pass reads the thread's items after the last position it read (`afterPosition` = `nextPosition`, 50 at a time, at most 4 pages a pass), starting a few items before the end it last saw, so an item that was still running and a request that still waits are read again. What a pass can't reach is read on the next, and the thread's state then comes from one more read of its latest items. A job's first read that finds more history than a pass reads starts at the latest items: what came before was other work. The position read to is kept with the job's progress (`readTo`). A pass that left items unread doesn't end the job: its end (telling, settling) waits until the track is whole. | The latest four items every 15 seconds missed what happened in between, so a fix's editing or tests could be missing from the track. Usually it is still one call per thread a pass. |
| T3-46 | **A file written from the shell is editing**: a heredoc, `cat`, `echo`, `printf` or `tee` into a file, `sed -i`, `perl -i`, `git apply` and `patch` move the track to *editing* and show as “Changing <file>” (“Changing the code” when no file is named), unless what they write goes to `/dev`, `/tmp` or another temporary place. | T3-47 | **The pull request an automation opens is its job's.** When an automation's `open_pull_request` step opens a pull request, or finds one open, it becomes the pull request of each job its run handed to T3 Code on that branch: in the run's places, handed over since the run began, on the branch T3 Code says the thread works on (kept with the progress as `branch`), at most five, and never one with a pull request of its own or a council's or a checklist's.
