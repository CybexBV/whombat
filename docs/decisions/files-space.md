# Files: a shared file space per conversation (FS-*)

John, 2026-10-05, after Pippa answered on DEV that she couldn't open a 136 MB SketchUp file (`1904Technischmodel.skp`)
he had attached in #private: “why not create a shared Files space where people in the same channel can see the files …
Files / General, Files / Private … when I share a file with an agent, Files / <agent name>”, then “I also want Files in
the sidebar, but only when there are actually files saved. Restrictions apply, so I can only see files that I actually
have access to”, and “Implement this fully”.

Root cause of the original answer: a computer turn doesn't copy attachments that aren't model input into the agent's
work folder (agent-computer.md AC-DP14), so the prompt said “you can’t open this type” and the file never reached the
computer. ChatGPT reads such files because its uploads land in its Python sandbox. OpenClaw and Hermes Agent save every
upload to disk and tell the model “read it yourself” (research 2026-10-05, `~/.cache/wb-tmp/research/attach/`); neither
separates files between users. `.skp` is readable on Linux: SketchUp 2021+ is a short VFF header plus a ZIP, and
OpenSKP (`pip install openskp`, MIT, 1.3.0) parses geometry, named groups/components and positions for 2013+ files
(tested on its fixtures, 2026-10-05).

Contracts: whombat-contracts 0.49.0 (CT-274…). Clients: whombat-app (AP-772…). Release: appliance IN-206.

| # | Decision | Why |
|---|---|---|
| FS-01 | **Files belong to a conversation.** Every conversation (channel, DM with a person, DM with an agent, group DM) has one Files space. It holds (a) every ready attachment sent on a message there that still exists and wasn't removed from Files, and (b) files saved straight into Files without a message. No new permission system: who may see a file is who may read the conversation now (bp-attachments.md BP-A05). “Files / Pippa” is the viewer's own DM with Pippa; another person's DM with Pippa is a different space they can't see. | Attachments already carry `conversation_id` and the membership rule; a shared per-agent folder would leak between people. |
| FS-02 | **Schema (expand-only migration 0076).** `attachments` gains `folder text not null default ''` (FS-03), `filed_at timestamptz` (set when saved straight into Files; null for message files), `files_removed_at timestamptz` and `files_removed_by text` (removed from Files, FS-06). A file is in Files when `state = 'ready'` and `files_removed_at is null` and (`message_id` is a live message of the conversation, or `message_id is null and filed_at is not null`). Index on `(conversation_id, state)` covering the listing. | One table: a file in Files and on a message is the same bytes and the same access. |
| FS-03 | **Folders are a path on the file**, `''` (top) or `A/B` — at most 4 segments, each 1–64 characters, `safeDisplayName` rules per segment, no `.`/`..`, no `/` at the ends, case kept, compared case-insensitively. A folder exists while a file is in it; “New folder” in a client is a place to upload or move into, not a row. | Simple, no empty-folder bookkeeping, enough to keep drawings apart from photos. |
| FS-04 | **Operations** (session + REST, contracts CT-274): `files.summary` → per conversation the viewer is a member of now with at least one file: `{conversationId, count, bytes, lastAddedAt}`; `files.list {conversationId, cursor?, limit≤200}` → `FileEntry[]` newest first, all folders (clients group); `files.save {attachmentId, folder?}` puts a ready, unsent upload of the caller (`uploads.create` for that conversation) into Files without a message; `files.update {attachmentId, name?, folder?}`; `files.remove {attachmentId}`. All writes go through the commit pipeline and emit `files.changed {conversationId}` to the conversation's members (realtime, like `conversation.updated`). Feature `files.space`. Every other conversation or file is “not found”. | Clients show Files only on runtimes that have it; one event keeps sidebar and lists live. |
| FS-05 | **Superseded in part by one-person.md OP-S07**: the person tidies any file in Files; agents still never rename, move or remove them. **Who may change what.** Rename: only files saved straight into Files (a message's file keeps the name it was sent with), by its uploader, a burrow owner/admin, or — in a DM — any person in it. Move (folder) and remove: the uploader, a burrow owner/admin, or any person in a DM. Agents never rename/move/remove through tools (they save; people tidy). | History stays as sent; people keep control of shared space. |
| FS-06 | **Removing.** A file saved straight into Files is deleted (state `deleted`; the bytes go with the orphan sweep when nothing else references the blob). A message's file is only taken out of Files (`files_removed_at`): the message keeps it. Deleting a message or clearing a channel (CT-216) removes its files from Files as before; files saved straight into Files survive a channel clear. | Removing from Files never silently edits a conversation. |
| FS-07 | **Superseded by final-shell-web.md FSW-04 (Files is always a place; no Files button in Chat’s head).** **Sidebar.** “Files” appears in the sidebar only when `files.summary` has at least one conversation — i.e. the viewer can see at least one file — and disappears when that drops to none (live on `files.changed`, membership changes). `/files` lists those conversations (channels as `# name`, DMs as the other party's name and avatar), newest activity first; `/files/:conversation` is one space with folder breadcrumbs, Upload (button and drag and drop), New folder, and per file Download, Open message (message files), Rename (FS-05), Move to folder…, Remove from Files. A “Files” button sits in the conversation header next to “Plans” on runtimes with `files.space`. Android: the same from the drawer and the conversation menu. No mock exists: the screens reuse the existing list, chip and dialog patterns (app decisions AP-772…). | John asked for it in the sidebar only when there are files he may see. |
| FS-08 | **Agents see the turn's conversation only.** A dispatch's `DispatchContext.files` lists the Files of the dispatch's conversation (newest first, at most 500 entries, `truncated` beyond); never another conversation's, even where the agent is a member, so a file from #private can't surface in #general. The runner may fetch any of them (`runnerFetch` accepts them, re-checked per request); `read_attachment` reads text ones. | The agent answers where the turn is; membership elsewhere isn't consent to share there. |
| FS-09 | **Superseded in part by one-person.md OP-S109**: the conversation's Files are still at `~/files`, read-only, now in each command's wrapper. **On the computer: `~/files`, read-only.** A computer turn gets the conversation's Files as a read-only share linked at `~/files` (`<folder>/<name>`, names as `scratchFileName`, de-duplicated per folder). The runner fetches the bytes into a runner-owned cache by sha256 (0700, `WHOMBAT_FILES_CACHE_BYTES`, default 10 GiB, least recently used out), materialises the tree for the turn (hardlink, copy across file systems), shares it read-only through computerd (`share`, `readonly: true`, `homeLink: 'files'`) and removes it when the turn ends. Per turn at most 250 MiB per file and 2 GiB in total, newest first; the rest stays listed with why. A scratch turn gets the same tree as `files/` in its folder (copies, same bounds). | The file reaches the tools that can open it; read-only so nothing writes behind the commit pipeline. |
| FS-10 | **Superseded in part by one-person.md OP-S87, OP-S109**: the turn's lines still say how many Files there are and that they are at `~/files` for its commands; no line names a computer. **Prompt.** The stable prompt of a computer turn says once that `~/files` holds the conversation's Files, read-only, and that results go back with `upload_file` (optionally `saveToFiles`). The turn prompt carries the count and size and, in the attachments section, the path of each attachment that is on the computer (`… not shown to you here; it is at ~/files/1904Technischmodel.skp. Open it with your tools.`) instead of “you can’t open this type”. A turn without a computer or scratch folder is told to use `list_files` and `read_attachment`. | Pippa's answer came from that “can’t open” line. Turn-specific facts stay out of the cached prefix. |
| FS-11 | **Agent tools.** `list_files {folder?}` (the turn's conversation; name, folder, size, type, who, when, attachment id; at most 200, `truncated`), and `upload_file` gains `saveToFiles?: boolean` and `folder?: string`: the artifact goes straight into that conversation's Files (still attachable to a post). Activity labels: “Listing files” / “Listed files”. | Agents can find and keep work products where people find them. |
| FS-12 | **Superseded by one-person.md OP-04, OP-13**: there is no computer base image; the agent's tools come with the appliance's image. **3D and CAD on the computer.** Computer base image 7 adds `openskp` (with numpy, trimesh, shapely) and `ezdxf` to the system Python. The `documents` pack gains a `3d-models` skill: SketchUp with OpenSKP (find groups/components by name, bounding boxes in mm, positions, dimension and text entities, export to OBJ/STL/GLB/IFC), STL/OBJ/GLB with trimesh, DXF with ezdxf; what it can't read it says so. The pack bump moves pins with its queue migration (Banjo run #6 lesson). | “Find the pool and give its size” becomes a script, not a guess. |

## Server decisions (FS-D*)

Server side in `apps/server/src/files/space.ts` (rules, queries), `space-commands.ts` (writes, `files.changed`),
`space-routes.ts` (the five endpoints); migration `0076_files_space`.

| # | Decision | Why |
|---|---|---|
| FS-D01 | **A file saved into Files and then sent stays in Files on its own account.** In Files = `ready`, not removed, and `filed_at` set *or* on a live message of the conversation (a little wider than FS-02's “message_id is null and filed_at”). While it is on a message it shows “Open message”, keeps the name it was sent with (no rename) and Remove only takes it out of Files; deleting its message or clearing the channel detaches it (`message_id` null) and it stays in Files as a saved file. | `upload_file` with `saveToFiles` promises “still attachable to a post”; deleting the post must not delete what was saved. |
| FS-D02 | **A website visitor's screenshots never reach agents through Files.** Files on a Whombat Feedback report's root message are in people's Files, but `DispatchContext.files`, `list_files` and the runner fetch through Files leave them out (FB-F3-12); the assessment and an approved handoff still get them as the dispatch's attachments. | The visitor's content is untrusted data only its assessor and handoff developer see. |
| FS-D03 | **`DispatchContext.files` is null where the agent gets no Files** (search answers, feedback assessments, a conversation it is no longer in) and an object otherwise, empty included. Reflection and every other turn get their conversation's Files. Totals are counted only when there are more than 500. | “None” and “not allowed” stay distinct for the runner; the common case is one query. |
| FS-D04 | **Who hears `files.changed`.** The people who are members now (agents have no `me` subscriptions) on save, rename/move, remove, a message with files sent, and a message delete or channel clear that changed Files. Joining, being added, leaving or being taken out tells only those people, and only when the conversation holds files. Joining a burrow (#general) and offboarding publish nothing: the client reads `files.summary` at start. | The summary changes only for the person whose membership changed. |
| FS-D05 | **Folder spelling.** Folders compare case-insensitively; a file saved or moved takes the spelling already used in that conversation, part by part (`drawings/pool` → `Drawings/Pool`). The file being moved doesn't count, so moving the only file of a folder can change its case. | One folder never shows twice in two spellings. |
| FS-D06 | **Saving and removing in detail.** `files.save` of a file already saved answers it unchanged (a retry); of a removed one “not found”; of a message's file 409 “That file is on a message already.” Removing a saved file sets `deleted`, clears `blob_key` and records who; it no longer counts toward the burrow quota, the next sweep deletes the row and the bytes go when nothing else uses them. `uploads.discard` refuses a saved file (409 “That file is in Files. Remove it from Files instead.”). The orphan sweep never takes a saved file. | Retries are safe; a removed file frees its space at once. |
| FS-D07 | **Order and pages.** `addedAt` = when it was saved into Files, else its message's time; lists are newest first by (`addedAt`, id). The cursor is that pair, opaque (base64url); a cursor this server didn't write is 400 “That page of files doesn’t exist. Start from the top.” | Stable pages while files arrive. |
| FS-D08 | **Superseded in part by one-person.md OP-S06, OP-S07**: there are no owners or admins: the person tidies any file, and agents still get 403. **People only tidy; “owner or admin” is a burrow owner** (the only role above member). Agents' REST tokens get 403 on `files.update` / `files.remove`; an agent may `files.save` its own upload (as `upload_file` with `saveToFiles` does). Copy: “Only the person who uploaded it or an owner can rename it.” / “… move it.” / “… remove it.”, “A file sent on a message keeps the name it was sent with.” | FS-05. |
| FS-D09 | **`list_files`.** A folder narrows it to that folder and the ones in it, any letter case; `uploadedBy` is the uploader's name; in a search answer or an assessment it answers an empty list. At most 200, `truncated` beyond. | Same reach as `DispatchContext.files`. |
| FS-D10 | **A runner's reports are made storable before they're written.** `recordActivity` runs every report through `wellFormed` (now `lib/well-formed.ts`, shared with the Feedback intake): NUL removed, lone surrogates replaced. | 2026-10-05 on John's box Pippa printed the first bytes of a `.skp` (UTF-16 with NUL); Postgres refuses `\u0000` in `jsonb`, so every progress beat failed, the heartbeat with it, and after a lease period the runner stopped the turn (“lease lost”) without a word in the conversation. |
| FS-D11 | **`model3d.py` reads large SketchUp files in less memory and says when it can't.** OpenSKP's `build_scene` parses the file again, so the script keeps only the small parts of `parse` (texts, dimensions, units, tags) and lets the rest go first (3.5 → 3.2 GB peak for a 136 MB file with a 223 MB `model.dat`). Before reading it compares about 15 bytes of memory per byte of `model.dat` with the cgroup's free memory and refuses with both numbers rather than be killed; the skill says to report that (or exit 137) instead of retrying, to start with `find`, and never to print a model's bytes. documents 1.3.1, rolled out by migration 0078 (queues 1.0.0…1.3.0 pins). | The same turn: the deep `tree` peaked at 3.5 GB in a 2 GiB computer and was OOM-killed. |
| FS-D12 | **Superseded by one-person.md OP-04**: there are no computers (MP-01 had already replaced the rule). **Computers may use min(8 GiB, half the host), at least 512 MiB** (amends RA-45: was min(4 GiB, a quarter)) — 4 GiB on an 8 GiB box, 8 GiB from 16 GiB. One rule, `computerMemoryMb` in `@whombat/computer`, for computerd and the server's fallback view (contracts' `computerMemoryMiB` is no longer used and changes with the next contracts release). It is a cap, not a reservation; computerd applies it at a computer's next start (RA-DK14). Superseded by memory-pool.md MP-01. | Real files (a 136 MB SketchUp model) need 3–4 GB; idle computers use little, so a quarter of the box left the one busy computer short while the rest sat empty. |

## Runner side as built (FS-R01…FS-R11)

Runner, computer, prompt and pack side of FS-08…FS-12 (branch `files-space-runner`, 2026-10-05).

| # | Decision | Why |
|---|---|---|
| FS-R01 | **Superseded in part by one-person.md OP-S109**: the turn's tree is still the conversation's Files, bound read-only at `~/files` in each command's wrapper instead of shared by computerd. **The tree and who reads it.** A computer turn's tree is `<workspaces>/.scratch/turn-tree-<dispatch>-<attempt>` (0700, the runner's), under computerd's roots (AC-04) and swept with the other `.scratch` turn directories after a crash. computerd shares it read-only with `homeLink: 'files'` at the turn's first command (AC-61), next to the other shares; the session's teardown unshares it before `end`, then the runner removes it. The agent's uid on the computer is the runner's (`shift=true`, AC-DR10), so the runner's 0700/0400 files are readable there without opening them to anyone else on the host. Nothing when the conversation has no Files (no share, no line). A share that fails is logged and the turn goes on. | The runner's own permissions stay private; the read-only mount is what keeps the agent from writing. |
| FS-R02 | **The cache.** `<workspaces>/.files-cache` (0700, files 0400 at `<2 hex>/<sha256>`), on the same disk as the tree so a tree is hardlinks (a copy across file systems); never shared itself. Bounded by `WHOMBAT_FILES_CACHE_BYTES` (default 10 GiB): after each new file the least recently used go (mtime = last use), never one a turn holds while it links or copies it; concurrent turns share one fetch; a fetch of the wrong size or sha256 leaves nothing; stray temporary files go at start. `WorkspaceManager.cleanup` skips the directory. Not in the runner's temp dir: that may be memory (tmpfs) and the appliance's is not on the workspaces' disk. | A hardlink costs no copy and no space; the read-only share means the agent can't write the cached inode through it. |
| FS-R03 | **Fetching.** Through the attachments' runner fetch (`fetchAttachment`, lease and the server's re-check, FS-08) with the same size and sha256 check, three at a time. A file that can't be fetched or placed is left out and named in the turn (“it couldn’t be fetched”); only a stopped turn fails. | A missing file never costs the turn. |
| FS-R04 | **Names.** `<folder>/<name>`: folder segments cleaned like `scratchFileName` (no `.`/`..`, no leading dot, no separators or control characters), compared case-insensitively with the first spelling kept, more than four joined into the last; names by `scratchFileName`, de-duplicated per folder (the newest keeps the plain name, an older one gets its id in front), never the name of a folder beside them. | Two people's `Q3.csv` and `q3.csv` both stay reachable, also on a case-insensitive file system. |
| FS-R05 | **Scratch turns.** The same plan as copies in `files/` of the folder (never hardlinks: the agent writes there). An attachment that is there isn't copied again into `attachments/`; its line names `files/…`. `attachments/` keeps its own bounds (SL-D05) for files that are not in Files (removed from Files, FS-06). | One copy per file, and Files' folders kept. |
| FS-R06 | **Superseded in part by one-person.md OP-S87, OP-S109**: the turn's lines still say how many Files there are and which are at `~/files` for its commands; no line names a computer. **Prompt lines.** System prompt, static: computer turn “- The conversation’s Files (what people shared or saved here) are on your computer at ~/files, read-only, in their folders: open them there with commands (your file tools don’t see them) and write what you make elsewhere (~/work). Share a result with upload_file; saveToFiles: true also keeps it in the conversation’s Files.”; scratch turn “- The conversation’s Files (what people shared or saved here) are copied into files/ in the folder, in their folders.” User turn: “This conversation’s Files: 2 files, 302 MB; 1 file (2 MB) is at ~/files.” (“…, all at ~/files.” when all are), then “Not there in this turn: <path> (<size>, larger than the 250 MB a turn copies \| past the 2 GB a turn copies in all, newest first \| it couldn’t be fetched); …; and N more. list_files lists every file; say so when one you need isn’t there, and don’t guess what it contains.” Other turns with Files: “This conversation’s Files hold N files, <size>: list_files lists them and read_attachment reads text ones. Other types can’t be opened in this turn; say so if one matters.” Attachments: “… not shown to you here; it is at ~/files/<path> on your computer. Open it with commands there.” (FS-10's example said “Open it with your tools”: the agent's file tools don't see the computer's home.) A reflection gets none of these. | Counts and names change every turn; the cached prefix doesn't (PE-02). |
| FS-R07 | **Every agent's prompt changes once.** The files line of “## Working in Whombat” names list_files and saveToFiles, and Codex gets `list_files` by name: the stable prompt's hash changes for every agent, so each conversation's next turn starts a fresh session (PE-03 `fresh` / `requeue`) once after the update. | Agents without a computer must learn that Files exist too. |
| FS-R08 | **Superseded by one-person.md OP-04, OP-13**: there are no computers or images; the tools come with the appliance's image. **Image 7, older computers.** `PYPI_PACKAGES` = uv, openskp, ezdxf in the system Python, checked by an import in the build; the build ahead (AC-60) picks the new alias up by itself. Computers made from image 6 or older are not changed in the background (unlike RA-DS58): the `3d-models` skill installs the two packages with `pip install --user` when the import fails. | Only agents that work with 3D files pay for it, and nothing races the agent's own installs. |
| FS-R09 | **Rollout.** `documents` 1.3.0 (the `3d-models` skill; the other skills name `~/files` next to `attachments/`); migration **0077** queues agents' bundled 1.0.0…1.2.0 pins for the startup upgrade (0076 is the Files schema). | A bundled bump alone never moves a pin (Banjo run #6). |
| FS-R10 | **The 3d-models script** (`scripts/model3d.py`, JSON out): bounding boxes in mm on SketchUp's axes (OpenSKP's glTF positions `x, −z, y` × 1000) per scene path, from the meshes at and under a part; matching ignores case and accents, short words (< 5 letters) match whole words, longer ones also inside names (“king stud” finds `KingStud`), plus English/Dutch synonym groups unless `--exact`. | FS-R11 | **Bounds come from the contract.** `FILES_TURN_FILE_MAX_BYTES` (250 MiB) and `FILES_TURN_TOTAL_MAX_BYTES` (2 GiB) per turn, newest first; a file that doesn't fit leaves room for older smaller ones; files beyond the dispatch's 500 are counted as “older ones”. | One number for server, runner and prompt. |

## Save to Files (FS-14…FS-19)

John, 2026-10-08: “When an agent creates an images or any other file, it shouldn't automatically store this in /files
unless we click on "Save to Files" and we should also create a "Download" button. Consider how we can make this look
nice in the chat, the UI / UX for this should be subtle.” On his box (2026-10-08) agents had posted 16 files and put 11
into Files themselves with `upload_file`'s `saveToFiles` (8 of those on no message), and every file on a message counted
as in Files (FS-01). Amends FS-01 (a), FS-05, FS-06 and FS-11. Contracts 0.59.0 (CT-312, feature
`files.save_from_messages`); the chat's buttons are the app's (whombat-app files-space.md AP-834…).

| # | Decision | Why |
|---|---|---|
| FS-14 | **An agent's file is in people's Files only once a person saved it.** In Files (people's view) = `ready`, not removed, and `filed_at` set (saved straight, or a message's file someone saved) *or* on a live message and uploaded by a person (`inFiles()`: an `exists` on the uploader's principal kind, no new column). A message's file carries `Attachment.inFiles` (`messageFileInFiles`, the same rule on the row; `loadMessages` reads the uploader's kind with the attachments). A website visitor's screenshots (the Feedback principal's) and automation copies follow the same rule: in Files once saved. | John's request. The uploader is the author of a message's file, so “who made it” needs no extra state. |
| FS-15 | **Agents still reach what agents posted.** `DispatchContext.files`, `list_files` and `~/files` keep FS-08's reach: every file on a live message of the turn's conversation plus the saved ones (minus a visitor's screenshots), saved or not; the agents' lines call them the conversation's files (“what was shared, posted or saved here”). | An agent revising its own render, or Banjo using Pippa's export, keeps working without anyone saving first; people's Files stays what people chose. |
| FS-16 | **Save to Files.** `files.save` takes a file on a live message of a conversation the caller is in now, people only (agents 403 “Agents don’t save files into Files; people do.”): it sets `filed_at` (kept if set) and `filed_by`, clears a removal (a person's file removed from Files comes back), and puts it in the given folder (the top from the chat). A file already in Files is answered as it is, no event. Signs `file.saved` with the message id; sends `files.changed` and the message's `message.updated` (its `inFiles`). The file keeps its message and the name it was sent with (no rename); the person who saved it may move and remove it (FS-05 gains “or saved it”); deleting the message leaves it in Files as a saved file (FS-D01). | Any member may already read and download it, so keeping it in the room's Files gives nobody new access; whoever chose to keep it can undo that. |
| FS-17 | **Removing.** An agent's file on a message is un-saved (`filed_at` and `filed_by` cleared; not `files_removed_at`), so it shows Save to Files again and agents still reach it (FS-15); a person's file on a message is taken out of Files as before (FS-06); a file saved on no message is deleted as before. Removing a message's file also sends its `message.updated`. Sending a message tells members `files.changed` only when a person sent it or a file was saved before it was sent. | Removing undoes a save without hiding the file from the agents' work. |
| FS-18 | **Agents don't save into Files.** `upload_file` loses `saveToFiles` and `folder` (contracts 0.59; an older runner's are dropped by the schema, `publishArtifact` no longer files anything); its description says to attach the file and that people keep it with “Save to Files”. The persona's files line, the computer and scratch lines and Codex's `list_files` purpose say the same; that changes every agent's stable prompt once, so each conversation's next turn starts a fresh session once (as FS-R07). `documents` 1.3.3: the `3d-models` skill no longer offers `saveToFiles`; migration **0089** queues agents' bundled 1.0.0…1.3.2 pins (Banjo run #6). | “Unless we click on Save to Files” leaves no case where an agent saves; a file it uploads but never attaches is swept as any orphan upload. |
| FS-19 | **Migration 0088 (expand).** `attachments.filed_by text` (nullable). Agents' files on a message that the agent itself had saved (`filed_at` set) leave Files (`filed_at` null; their message keeps them) — on John's box 3 such files; files agents saved on no message (8 there) stay in Files, the only place they are, and Remove deletes them as any saved file. `runtime.readsFrom/writesFrom` 0088 (the binary reads `filed_by`). | Un-saving what is also on a message loses nothing; deleting files that exist only in Files would, so people decide about those. |
