| TE-02 | **Retire on narrowing, not on every change** (amends BP-B16, VT-40, VT-G05, AE-DR05). Server (`memory/sessions.ts` `partsChange`, beside core's `sessionChange`): the raw grants and member ids are kept next to the part hashes (`keys:grants`, `members:ids` in `parts`; not secret, no migration: jsonb). **Keys**: one key given or raised (`oneKeyWidened`: a person's yes to a key request, one key switched on) keeps the session; a key removed, lowered or rescoped, or several at once (a Merge/Deploy row), starts fresh as before. Runner (`planResume`, `promptBeforeOneKey`): both CLIs keep a resumed session's first system prompt (PE-DR03), so on a hash mismatch it re-renders the prompt with each held key one step lower or not held; when one hashes to `resumePromptHash` it resumes and opens the user turn with `KEYS_CHANGED_LINE` and the system prompt's lines the session doesn't have (the new key list, a `## Web browser` section…), and the session goes on under the new hash; otherwise fresh/requeue as before. A grant the runner can't reproduce (two keys between turns) costs one requeue, then a fresh session. **Members**: someone leaving keeps the session; someone joining starts fresh. This reverses the assignment's “removals only”: what a session gathered (search results, other rooms, knowledge) is bounded by its conversation's audience (BP-B11, BP-C31) — fewer readers can read all of it, a new one may not. **Vault** part: held entries with their tiers (and a computer key's variable) plus the requester's unheld entries by id; no `updatedAt`, tool hashes or host-key readiness. Readiness moved from the system prompt to the turn (`vaultTurnLines`: “Not confirmed yet: the host key of staging (“Deploy key”); ssh to it fails until Joris trusts the server in the Vault.”). Unheld entries stay in the stable prompt (their ids in the part): moving their blocks into every owner turn costs ~250 tokens per entry per turn, more than the rare cold turn after a Vault edit; an edit the prompt shows (a name, a server added) still starts fresh through the runner's hash. **Facts**: “People:”/“Agents:” duplicated the roster (`teammates`, every turn but an assessment, ≤ 40): the server sends “Owners: …” instead and keeps the two lists only for a burrow larger than `TEAMMATES_MAX`. A hire or a join still changes the roster in the system prompt; moving the roster itself into the turn costs ~70 characters per teammate per turn (~85 tokens for five, ~700 for forty), more than the occasional cold turn after a hire. | A yes to a key request made the continuation turn cold exactly when its context mattered; a rotated secret, a trusted host key, someone leaving the room and a teammate's new key or skill made every session cold for nothing. |

| TE-10 | **No fetch when the copy is already on the head Whombat knows.** The server puts the branch's pull request head into `DispatchContext.workspace.headSha` (contracts 0.55 CT-306) for a run on a pull request, a yes to a push on a branch with an open pull request and a branch room — only a full sha, lowercased (`knownHead`); an automation step and a run without a pull request send none.
