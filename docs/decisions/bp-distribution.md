# Workstream F (buzz parity): packaged installation, upgrades, backup/restore, diagnostics

A release anyone can install without a checkout, pnpm or a build step; upgrades that check before they
change anything and say plainly what state they left; one backup archive that restores and verifies itself;
a support bundle without secrets. Binds with `buzz-parity.md` BP-11 (migration lock) and BP-12 (storage in
`WHOMBAT_HOME`, backed up together). Checkout-based development (`pnpm whombat …`, `pnpm dev`) is unchanged.
User docs: `docs/install.md`, `docs/upgrade.md`, `docs/backup.md`, `docs/troubleshooting.md`.

## Layout

```
scripts/package (@whombat/package)
  src/build.ts        pnpm package: esbuild bundles, web build, node_modules, manifest, archive, SHA256SUMS
  src/npm.ts          another arch's platform package: registry tarball checked against pnpm-lock.yaml
  src/notices.ts      THIRD-PARTY-NOTICES.txt from esbuild's metafile
  src/launcher.ts     bin/whombat and README.txt of a release
  src/acceptance.ts   pnpm package:acceptance: the packaged install end to end (disposable homes)
apps/cli/src
  layout.ts           checkout or release; prefix, current, the service launcher
  release/            tar (write reproducibly, read safely), manifest + SHA256SUMS, version order
  lock.ts             $WHOMBAT_HOME/maintenance.lock
  upgrade.ts          upgrade / install
  backup/             backup.ts, restore.ts, db-snapshot.ts (the database part)
  diagnostics.ts      the support bundle
apps/server/src
  db/migrate.ts       migrations under the advisory lock; applied list; prefix compatibility
  version.ts          version, git commit, schema (compiled into a release, read from the checkout otherwise)
packages/core/src/contracts/distribution.ts   ReleaseManifest
```

## Decisions

| # | Decision | Why |
|---|---|---|
| BP-F01 | **One tarball per arch, reproducible.** `pnpm package [--arch x64\|arm64]` → `dist/whombat-<version>-linux-<arch>.tar.gz`, `…manifest.json` (a copy of the one inside), `SHA256SUMS` (merged per arch). Inside `whombat-<version>-linux-<arch>/`: `bin/whombat` (POSIX sh launcher: `readlink -f`, `$WHOMBAT_NODE` or `node`), `app/{cli,server,runner}.mjs` (esbuild 0.28.2 pinned, platform node, target node24, ESM, a `createRequire` banner for the CommonJS inside, not minified so stack traces stay readable), `web/` (Vite production build), `migrations/` (SQL + journal; no snapshots), `packs/` when the repo has it, `node_modules/` with only what can't be bundled, `docs/`, `README.txt`, `THIRD-PARTY-NOTICES.txt`, `LICENSE` when the repo has one, `manifest.json` (version, git sha + dirty flag, build time, node range, arch, Postgres package/major, Claude bundled or not, every migration's tag/when/hash, every file's sha256/size/mode and every symlink). Same commit → same bytes: SOURCE_DATE_EPOCH (default the commit time) for every mtime and the build time, entries sorted, owner 0, modes 0644/0755, gzip from Node's zlib (so the Node major is part of the toolchain), and the build fails if a text file names the build machine's checkout or home. `pnpm package --verify-reproducible` builds twice and compares. The repo has no LICENSE file yet; the owner has to add one (the builder copies it when it exists). | An install must not need the workspace, pnpm or dev dependencies; reproducibility lets anyone check a published archive against its commit. |
| BP-F02 | **Checkout or release is decided at build time.** Bundles are compiled with `__WHOMBAT_BUILD__` (version, sha, time); their first lines set `WHOMBAT_APP_DIR` to their own release. The CLI's layout (`layout.ts`) is `package` only when compiled in; the server and runner read migrations (`$WHOMBAT_APP_DIR/migrations`), the web app (`$WHOMBAT_APP_DIR/web`, `WHOMBAT_WEB_DIST` still wins) and never a repository `.env` when `WHOMBAT_APP_DIR` is set. Without it everything is as before. A release's `start` never builds anything (a missing `web/index.html` is an error naming the fix); children run `node app/<name>.mjs` with the home as working directory; leftovers of any release (`…/app/<name>.mjs` with this home's `WHOMBAT_ENV_FILE`) are recognized after an upgrade. Messages say `whombat …` in a release and `pnpm whombat …` in a checkout (`CMD`). | Nothing in the environment can make a checkout act like a release or the other way round; development keeps its tsx and web rebuilds. |
| BP-F03 | **Version everywhere.** Root `package.json` `version` (now `0.1.0`) is the product version. `whombat version` / `--version` (`--json`), `GET /api/v1/health` (`version`, `gitSha`, `schema` = newest migration tag; optional in the contract so older servers still parse) and `doctor`'s `version` line (which warns when the running server is another version) show it. A checkout reports its package.json version and `git rev-parse HEAD`. Health says the version only to local callers and admins (BP-F19, superseding “unauthenticated and says the version”). | Upgrades check health against the version they installed; support needs to know what runs. |
| BP-F04 | **Releases live apart from data.** `<prefix>/releases/<version>/` + `<prefix>/current -> releases/<version>`; prefix default `$XDG_DATA_HOME/whombat` else `~/.local/share/whombat` (`--prefix`); `~/.local/bin/whombat -> <prefix>/current/bin/whombat` (only replaced when it is a link to a whombat launcher, e.g. a checkout's shim). `WHOMBAT_HOME` keeps config.env, pgdata, files, packs, logs, workspaces, backups. `whombat install` (from an unpacked release) and `whombat upgrade <archive\|dir>` do the same thing: stage (a signed SHA256SUMS next to it, BP-F20 — `--skip-checksums` is gone; safe unpacking; every file against the manifest, nothing extra; linux + this arch; Node range), put it in `releases/<version>` (copied then renamed; an identical build is reused, another build of the same version needs `--force`), then **hand over to the staged release's own CLI** (`upgrade --staged`), which takes the home's lock and does the rest: refuse an older version (going back = the pre-upgrade backup), no-op for the same build, same Postgres major, database migrations a prefix of the target's (else refuse: newer database or another history), refuse a `whombat start` outside the service; stop the service, `pre-upgrade` backup (last 3 kept), switch `current`, rewrite a unit that isn't the current launcher (a checkout's) and `daemon-reload`, add `WHOMBAT_CLAUDE_PATH` when needed (BP-F09), migrate (one transaction), start (service → `systemctl --user start` + health with the new version; no service → a checking `start` that is stopped again, unless `--no-verify`), prune releases (keep 3, never current or previous). Failure before or during the migration → `current`, the unit and config.env back, the old service started again, "Nothing changed". Failure after it → Whombat left stopped, the old release kept, and the report prints the exact way back (`<old>/bin/whombat restore <pre-upgrade backup> --home … --force` and `ln -sfn releases/<old> …/current`). A checkout-based home (`pnpm whombat init`) upgrades the same way: nothing moves, its unit is retargeted. | The target's logic knows its own layout and migrations; an upgrade must never leave an ambiguous state or pretend a binary rollback is safe after a schema change. |
| BP-F05 | **Locks.** Migrations: our own runner over drizzle's files and bookkeeping (`drizzle.__drizzle_migrations`, same hash and `created_at`, so drizzle's migrator and ours take over from each other) that holds `pg_try_advisory_xact_lock(0x57484d47)` ("WHMG") from before it reads what is applied until commit; a second migrator polls, says every 10 s who holds it (backend pid, application, since), gives up after 5 min with that in the message (server boot, `start`, `migrate`, upgrade, restore all use it). Other Whombat advisory locks: `0x57484d42` burrow chain, `0x57484246` blobs, `0x57484e52` runner claims, `0x57484155` automations engine. Home: `$WHOMBAT_HOME/maintenance.lock` (O_EXCL; pid + start time + boot id like whombat.pid, so a dead holder's lock is taken over) for upgrade, restore and backup; `start` refuses while an upgrade or restore holds it (an upgrade switches it to `starting` before it starts Whombat itself). | Server and CLI both migrate (BP-11); two upgrades or an upgrade and a start at once would fight over the embedded Postgres. |
| BP-F06 | **Backups are logical snapshots plus the home.** `whombat backup` writes `whombat-backup-<label>-<UTC>.tar.gz` (mode 600, default `$WHOMBAT_HOME/backups`, `--out`, `--keep n`): `db/<table>.copy` from Postgres' own `COPY` inside one `REPEATABLE READ READ ONLY` transaction (pg_dump's consistency without pg_dump, online, the same for the embedded and an external database; generated columns left out), sequences, the applied migrations, the attachment blobs the snapshot references; then everything in `WHOMBAT_HOME` except `pgdata`, `workspaces`, `codex-home`, `logs`, `backups`, `locks`, `guarded`, `diagnostics`, pid/lock/temporary files and `files/.staging` (so packs and whatever later workstreams keep there are covered); files from `WHOMBAT_FILES_DIR` wherever it is; `backup.json` last with every entry's sha256. Files are archived after the snapshot and every referenced blob must be there with its own hash, else the backup fails. config.env and secret files it names inside the home only with `--include-secrets` (warned); otherwise `masterKeyCheck` = HMAC-SHA256 under the master key of a fixed text proves a later restore has the right key. No schema in the dump: a restore runs exactly the backup's migrations (they must be a prefix of the restoring build's), loads the rows in foreign-key order (as a superuser with `session_replication_role = replica`), sets the sequences, then runs the newer migrations. Rejected: physical `pg_backup_start/stop` (needs WAL handling and the same major), a brief stop for a cold copy (downtime for every daily backup), bundling pg_dump (not in the embedded packages; per-arch binaries to keep in step); requiring a host `pg_dump` for an external database (the snapshot needs none, and covers exactly Whombat's schema). | One archive, consistent across database and files, restorable by the same or a newer version, without host tools. |
| BP-F07 | **Restore checks first, then verifies.** `whombat restore <archive>` into a new or empty home (config.env, logs and backups alone don't count as data); `--force` over an existing Whombat takes a `pre-restore` backup, sets the old home aside and puts it back if anything fails. Before anything is written: every entry against backup.json, the config.env to use (`--config`, else the home's, else the archive's) and its master key against `masterKeyCheck` — a wrong key is refused with what to do. Then `WHOMBAT_HOME` (and `--port`/`--pg-port`) in config.env, a new cluster (the config's password), the database, the files, and verification: every table's row count, every burrow's audit chain (`verifyBurrowChain`), every referenced blob's sha256. Unpacking (releases and backups) is our own tar reader: no absolute paths, no `..`, symlinks only inside, never through a link it made, no hard links or devices, a size ceiling, a truncated archive is an error. | A restore with the wrong key would give a database whose keys and tokens can't be opened; a restore that isn't verified is a hope. |
| BP-F08 | **Doctor and diagnostics.** New `doctor` checks (after the built-in ones, `STATE_CHECKS`): `version`, `schema` (compatibility and pending migrations), `storage` (home, pgdata, files, packs, backups owned by this user and not readable by others; free space: warn < 1 GB, fail < 200 MB), `backup` (none yet or older than 7 days: warning; from `last-backup.json`), `locks` (maintenance lock, a migration holding the advisory lock). Postgres, schema and locks share one database session per run. `doctor --json` gives the checks with their ids. `whombat diagnostics [--out f] [--lines n]` writes a mode-600 `.tar.gz` with `diagnostics.json` (versions, platform, doctor report, settings, health, whombat.pid processes, service state, maintenance lock, last backup) and the last 200 log lines. Settings are an allowlist of plain settings (URLs without user, password or credential query values); everything else shows `[redacted]`. Log lines: pino JSON keeps level, time, msg, request method and redacted URL, status, error message only; config secret values, `Bearer …`/`token …` and long token-like strings are replaced. | Support needs the facts, never the secrets or what people wrote. |
| BP-F09 | **Claude Code's binary is not in the release by default.** The SDK (2.4 MB of JavaScript) is; its per-platform `claude` (about 230 MB, more than the rest of the release eight times over) only with `pnpm package --with-claude`. A release without it runs the host's `claude`, which docs/install.md already requires installed and logged in: `init` and `upgrade` set `WHOMBAT_CLAUDE_PATH` to the `claude` found on PATH (and say so when there is none); `doctor`'s Claude check is unchanged. | The host has Claude Code anyway (its login is the operator's); a 230 MB copy of it in every release would dwarf the product. |
| BP-F10 | **Tests.** Unit: tar (round trip, pax long paths, reproducible bytes, unsafe paths, links out, writing through links, truncation, damaged headers), manifest verification (changed, missing, extra, links, modes), SHA256SUMS, version order, Node range, layout, the release unit, locks (exclusive, stale takeover, purposes), upgrade helpers (current switch, bin link, pruning), backup exclusions and secret files, master-key check, redaction, doctor storage/backup. Server integration: two concurrent migrators, a held lock (wait, message, timeout, then proceed), a failing migration changes nothing, drizzle's migrator and ours interchangeable, compatibility. `pnpm package:acceptance`: the whole packaged install in disposable homes (see `scripts/package/src/acceptance.ts`). | The brief's acceptance list, runnable again. |
| BP-F11 | **CI.** `ci.yml` gets a `package` job (x64, `--verify-reproducible`, uploads the archive, manifest and SHA256SUMS as an artifact). `release.yml` is `workflow_dispatch` only: build on `ubuntu-24.04` (x64) and `ubuntu-24.04-arm` (arm64), each with the unit tests of its arch and a smoke of the built release (`--version`, init, start, health), a checksums job merging SHA256SUMS, and a `publish` job behind the protected `release` environment (manual approval) that creates the GitHub release as a draft. Nothing here pushes, tags or triggers it. | Releases are deliberate; the PR build proves packaging keeps working. |

### Independent security review of E and F (SEC2, 2026-09-24)

Proof-of-concept tests on `review/security2` (1730d54) became regression tests next to the code they cover:
`apps/cli/src/release/tar.security.test.ts`, `apps/cli/src/lock.test.ts`, `apps/cli/src/diagnostics.test.ts`,
`apps/cli/src/backup/restore.security.int.test.ts` (+ `restore.test.ts`), `apps/cli/src/upgrade.test.ts`,
`apps/cli/src/release/signature.test.ts`, `apps/server/src/db/migrate.security.int.test.ts`,
`apps/server/src/routes/health.int.test.ts`; the ACP part is bp-acp.md BP-E14.

| # | Decision | Why |
|---|---|---|
| BP-F12 | **Links in archives** (SEC2-F1). `extractTarGz` unpacks no symlink unless the caller's `allowLink(path, target)` accepts it: backups, support bundles and npm tarballs allow none; a release allows exactly the embedded Postgres' library version links — `<top>/node_modules/@embedded-postgres/linux-{x64,arm64}/native/lib/<name>` naming a plain file name in the same directory (`releaseArchiveLink`; the 14 links of `pg-symlinks.json`). Any link whose target passes through another link — resolved component by component as the kernel does, so `e -> l/..` with `l -> .` is caught although it normalizes to `.` — is refused, including a target that is itself a link and a link made later on an earlier one's way (a pass after unpacking). After unpacking, every link must `realpathSync.native` to something inside the destination (not the destination itself). `verifyRelease` refuses a listed link outside that rule or onto another link, so an unpacked directory can't bring one either. | Lexical checks per link can't see chains; releases only need these links, backups none. |
| BP-F13 | **Backups are authenticated** (SEC2-F3). backup.json gets `mac` = HMAC-SHA256 of its RFC 8785 canonical JSON (`canonicalJson` of core, every field but `mac`, unknown fields included) under `HKDF-SHA256(WHOMBAT_MASTER_KEY, no salt, "whombat-backup-manifest/1", 32)`. `entries` holds every file's sha256, so it covers the archive. A restore unpacks (nothing else), reads backup.json, picks the config.env, checks `masterKeyCheck` (“wrong key” stays its own message), then the MAC — before any entry's hash, table file or attachment key is used: a changed archive is refused (“… doesn’t authenticate: it was changed after it was made, or not made by the Whombat with this master key. Nothing was restored.”). `format` stays 1 and `mac` is optional in the contract, so an older release (the upgrade's way back) still restores a backup the new one made. **Backups without `mac`** (made before this) are refused unless `--unauthenticated`, which restores them with a printed warning — chosen over refusing outright because the pre-upgrade backup of the first upgrade to this version is exactly such a backup. A backup restored with the config.env inside it (`--include-secrets`) authenticates only against its own key: the restore says so (“the master key comes from the backup itself, which proves the archive is intact, not who made it”). Not encrypted: whoever can read an archive reads its contents (docs/backup.md says so). | Before, the only integrity data was backup.json itself plus a constant `masterKeyCheck` anyone could copy: a writer of the archive could rewrite rows (an owner's email) and add files. |
| BP-F14 | **Tar numbers must parse** (SEC2-F2). Header fields (checksum, size, mode, mtime) are NUL/space-padded octal digits only (no base-256), a safe integer ≥ 0; a pax `size` is `^[0-9]+$` and a safe integer; a pax record must be `<len> <key>=<value>\n` with `len` exact and inside the header (trailing NUL padding tolerated); a pax header over 1 MiB is refused. Anything else: “corrupt archive (…)”. | A non-octal size parsed to NaN and spun forever; a negative pax size wrote past `maxBytes`. |
| BP-F15 | **What a restore takes from an archive** (SEC2-F6, SEC2-F3). Files only under `db/` (`db/<table>.copy`, table names `[A-Za-z_][A-Za-z0-9_]{0,62}`) and `home/`; each table's `file` must be exactly its own `db/<name>.copy` and a listed, unpacked entry (checked in the restore, and again when loading); attachment keys must equal `sha256/<2>/<2>/<sha256>` of their own hash. **Host configuration** in the archive — `acp-runtimes.json`, whatever a config.env setting (the backup's or this home's, absolute or `~/`) names inside the old or new home except the data settings (`WHOMBAT_HOME`, `WHOMBAT_FILES_DIR`, `WHOMBAT_PACKS_DIR`, `WHOMBAT_WORKDIR_ROOTS`), and every file that was executable — is left out and listed (“left out host configuration from the backup: …”) unless `--with-host-config`, which the CLI announces on stderr and the log lists (executables back at 700). | Even an authentic backup should not silently decide what runs on the host it is restored to; an unauthenticated one must not at all. |
| BP-F16 | **The maintenance lock is created whole** (SEC2-F4). Written to `maintenance.lock.tmp-<digits>` (backups skip the name), then `link()`ed into place (EEXIST = held); filesystems without hard links fall back to O_EXCL. A lock that is empty or doesn't parse counts as held for 30 s after its mtime (“Another Whombat command is taking … right now.”), then as stale. A stale lock is `rename()`d aside and dropped only if it is the same inode that was judged stale; otherwise it is linked back and looked at again. `setPurpose` replaces the file by rename. | O_EXCL then write left a window in which a second taker saw an empty file and took it over. |
| BP-F17 | **Runner lines in a support bundle** (SEC2-F9). `[runner] [runner] <msg> <json>` lines keep only the runner's known messages (signals, claim/heartbeat/turn/cleanup/progress/push failures, cleanup, sandbox and provider states, refusals, “could not post its reply”) with names, titles, paths, reasons and details replaced (`[agent]`, `[conversation]`, `[path]`, `[reason]`, `[detail]`), and of the JSON extras only `dispatchId`, the error class (`err: "Error"`, else `[redacted]`) and an HTTP status. Any other runner message is `[message redacted]`; runner output that isn't its log (provider stderr, stack traces) `[output redacted]`. | The runner logs plain text, not pino JSON, so the JSON allowlist never applied; its messages name conversations and carry error text. |
| BP-F18 | *Refined by `managed-db.md` MD-01…MD-04: a newer schema within this build's declared reader/writer floors is accepted (read-write or read-only); foreign histories and schemas past the reader floor are still refused.* **Migrations refuse a history they don't know** (SEC2-F7). `runMigrations` — server boot, `whombat start`, `whombat migrate`, restores, upgrades — checks `schemaCompatibility(applied, this build's migrations)` inside its transaction, under the advisory lock, before applying anything; a newer or foreign history throws `SchemaMismatch`: “This version of Whombat (schema <tag>, n migrations) can’t run on this database: <reason>. Run the Whombat that last migrated it (whombat version there), or restore a backup made for this version (docs/upgrade.md).” The server prints it and exits 1. Pending migrations are then exactly the ones after the applied prefix. | An older release relinked as `current` ran on a schema it doesn't know; only upgrade/doctor/restore checked. |
| BP-F19 | **Health tells strangers only that it is up** (SEC2-F10). Unauthenticated `GET /api/v1/health` answers `{ok, service, db}` (`service` stays: the mobile app recognizes a Whombat server by it). `version`, `gitSha`, `schema` and `time` (now optional in the contract) only for a local caller — socket from loopback or the server's own address, Host naming that address or `localhost`, and none of the headers a proxy adds (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`, `CF-Connecting-IP`, `Tailscale-User-Login`, `Via`) — or a signed-in admin. The CLI (doctor, upgrade, diagnostics, start) calls `127.0.0.1` directly and keeps getting them. A proxy that adds none of those headers and rewrites Host to loopback would make its callers local: the ones in docs/install.md don't. | Version and commit tell an attacker which advisories apply; support and upgrades only need them locally. Supersedes BP-F03's “unauthenticated says the version”. |
| BP-F20 | **Signed releases** (SEC2-F5). `SHA256SUMS.sig` = raw 64-byte Ed25519 signature of the exact bytes of SHA256SUMS (Node's crypto; no new tooling; checkable with `openssl pkeyutl -verify -rawin`). Trusted keys are pinned in `apps/cli/src/release/keys.ts` (raw public keys, base64) — **empty until the project's release key is generated** (a local or test key is never pinned; a test asserts no pinned key's note says test/dev/placeholder/local). `whombat upgrade <archive>`: SHA256SUMS + .sig next to it, signed by a pinned key or a `--release-key <file>` (PEM public/private or pinned base64; printed as a warning), then the archive — copied privately first, so the bytes hashed are the bytes unpacked — against the *signed* bytes; only then unpacking. `upgrade <dir>` / `install`: the signed SHA256SUMS next to the directory must list `whombat-<v>-linux-<arch>.manifest.json` with the hash of the directory's `manifest.json` (the dist copy is byte-identical), then every file against it; a directory already in `<prefix>/releases` (the handover) was checked when staged. `--unsigned` skips the signature with a printed warning (a SHA256SUMS next to it still has to match); `--skip-checksums` is gone (it says so). `pnpm package --sign-key <file>` signs (a build without it drops a stale .sig); `pnpm --filter @whombat/package sign` makes key pairs (`--keygen`, private key 600), signs a directory (`--require-pinned` refuses an unpinned key) and checks one. release.yml signs in the `publish` job of the protected `release` environment with OpenSSL from the secret `WHOMBAT_RELEASE_SIGNING_KEY`, refusing a key whose public half isn't in keys.ts, and nothing is installed from the repository in that job. The acceptance run signs with a key made for the run, passes it with `--release-key`, and proves another key's signature, a changed SHA256SUMS, an unpinned key and a missing signature are refused before unpacking. A first install is only as good as the person's own check (docs/install.md: the OpenSSL command with the key from the repository); `install` re-checks, but it is the code being checked. | Checksums next to a download prove nothing about who made it. |
| BP-F21 | **Workflows** (SEC2-F11). `ci.yml`: top-level `permissions: contents: read`. `release.yml`: a first job refuses refs other than `main` or `refs/tags/v<version>`; `publish` repeats the condition; every action pinned by commit (resolved read-only from the v4 tags: checkout `11d5960a…`, pnpm/action-setup `b906affc…` (annotated tag dereferenced), setup-node `49933ea5…`, upload-artifact `ea165f8d…`, download-artifact `d3f86a10…`); no `cache: pnpm` in the release build; `persist-credentials: false`. | Least privilege and a build nobody can steer through a branch or a cache. |

## Copy

- Upgrade outcomes: “Whombat 0.2.0 is running (0.1.0 kept in …/releases).” · “Upgrade to 0.2.0 failed: …” + “Nothing changed: the database is as it was, 0.1.0 is current again and running.” · “Upgrade to 0.2.0 failed after the database was migrated: …” + “The database has 0.2.0’s schema now, which 0.1.0 can’t be trusted with, so Whombat is left stopped.” + “To go back to the state before the upgrade:” and the commands.
- Refusals: “… doesn’t match SHA256SUMS … the download is damaged or not the release it claims to be.” · “There’s no SHA256SUMS next to … that lists it, so it can’t be checked.” · “The release in … doesn’t match its manifest (n problems)” · “0.1.0 is older than the 0.2.0 this home runs. Going back needs the backup made before the upgrade (docs/upgrade.md), not a downgrade.” · “Whombat 0.2.0 can’t run on this database: …” · “An upgrade of this Whombat is running (pid n).”
- Restore: “This backup was made without secrets (no --include-secrets), so it has no config.env.” · “The master key in … isn’t the one this backup was made with. The signing keys and connector tokens in the backup are sealed with that key: it can’t be restored with another one.” · “… already has a Whombat in it.”
- Migration lock: “The database migrations are locked by another migration (Postgres backend pid n, …); waited 300 s. Another Whombat (or an upgrade) is migrating this database: let it finish, or stop it, then try again.”
- Signatures (BP-F20): “There’s no signed SHA256SUMS next to … (SHA256SUMS and SHA256SUMS.sig in …), so it can’t be checked.” · “… isn’t signed by a Whombat release key: the download may not come from the Whombat project.” (+ “ (this whombat has no release key pinned yet)”) · “… isn’t the manifest the signed SHA256SUMS lists: this isn’t the release it claims to be.” · “warning: --unsigned: not checking who made this release (no SHA256SUMS.sig). Only install builds you made or trust.” · “warning: trusting the release key in … (…) for this run” · “--skip-checksums is gone: releases are signed now (docs/upgrade.md).”
- Backups (BP-F13, BP-F15): “… doesn’t authenticate: it was changed after it was made, or not made by the Whombat with this master key. Nothing was restored.” · “… can’t be authenticated: it was made before Whombat authenticated its backups (or its authentication was removed), so nothing proves it wasn’t changed since.” · “warning: --unauthenticated: this backup has no authentication, so its contents are restored as they are. Only do this with a backup you know nobody changed.” · “left out host configuration from the backup: … (after checking the backup, whombat restore … --with-host-config brings it back; or set it up again)”.
- Lock (BP-F16): “Another Whombat command is taking … right now.” Schema (BP-F18): “This version of Whombat (schema …, n migrations) can’t run on this database: …”.

## Follow-ups

- **Before the first release: the release key.** The owner runs `pnpm --filter @whombat/package sign --keygen
