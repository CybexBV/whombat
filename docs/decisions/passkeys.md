# Passkeys: one touch opens your Whombat on a new device (PK-*)

John, 2026-10-05, main checkout: signing in on a new device is “email link → Pick a Whombat → Open → Set up this
device (pair with another device or the recovery kit)”; “I want to instantly open my environment”. Agreed after
discussion: keep the rule that control can never let a device into a Whombat (MA-03, MA-24, threat model T2/T3), and make
the gate one touch with a passkey that **the Whombat itself verifies**. A passkey replaces the email link (it signs in to
the cloud account) and the pairing (it enrolls the device) in one WebAuthn ceremony. “Implement this fully.”

Contracts: whombat-contracts 0.50.0 (CT-280…). Control: control (CL-117…). Clients: whombat-app (AP-785…). Server:
this file (PK-D*). Release: appliance IN-208.

| # | Decision | Why |
|---|---|---|
| PK-01 | Superseded by [SPK-01](shared-passkey.md). **One passkey per (person, Whombat).** Registered from a device already enrolled on that Whombat, for the signed-in person's Whombat account. WebAuthn `user.id` = UTF-8 of `wb1:` + the Whombat's content PeerId (56 bytes), `user.name` = the cloud account email, `user.displayName` = the Whombat's name as the directory shows it. Discoverable credential, user verification required, attestation `none`. | The authenticator syncs `user.id` with the passkey and returns it as `userHandle` at every sign-in: the passkey itself names the Whombat, so a new device can pin the Whombat's identity from a party that already trusts it (MA-24, AP-63), never from the directory. Two Whombats = two passkeys, the browser picker shows both by name. |
| PK-02 | **RP ID and origins.** RP ID = the hosted UI host (`app.whombat.com`, `dev.whombat.com`; control's `WEBAUTHN_RP_ID`, the Whombat derives it from `WHOMBAT_APP_URL`). Allowed origins = the UI origin plus the Android app's `android:apk-key-hash:hcREl8X1DtHfXqk1yeVFTAZ7nhsYeSGr8uoly49gZtM` (release key, SHA-256 `85:C4:44:97…66:D3`), exported by contracts as `PASSKEY_ANDROID_ORIGINS`. Control adds them through `WEBAUTHN_EXTRA_ORIGINS` (dev harness and prod infra); the Whombat accepts `managedAppOrigin` + `PASSKEY_ANDROID_ORIGINS` + `WHOMBAT_PASSKEY_EXTRA_ORIGINS` (csv, tests and local stacks). | Both verifiers check the same RP and origins; the Android app shares passkeys with the website through Digital Asset Links. |
| PK-03 | **The challenge binds the new device's key.** Sign-in challenge = `SHA-256(utf8(canonicalJson({purpose:'whombat-passkey-enroll/1', nonce, endpoint})))` where `nonce` is control's 32-byte hex nonce and `endpoint` the new device's PeerId (its Noise identity). Registration challenge = `SHA-256(utf8(canonicalJson({purpose:'whombat-passkey-register/1', controlNonce, applianceNonce, appliance})))`. Helpers `passkeyEnrollChallenge` / `passkeyRegisterChallenge` in `@whombat/protocol`; the client recomputes the challenge it is handed and refuses a different one. | One touch serves both verifiers. A signature made for device A can't enroll device B, so control (or anyone who sees the assertion) can't reuse it for its own key; the Whombat needs no nonce of its own before the connection. |
| PK-04 | **Sign-in on a new device** (web and Android): (1) load or create the endpoint key; (2) `POST /v1/auth/passkeys/authenticate/options {endpoint}` → `{challengeId, nonce, options}` with the PK-03 challenge; (3) `navigator.credentials.get` (button “Sign in with a passkey”, and conditional mediation in the email field); (4) `…/authenticate/verify` → cloud session (replaces the email link); (5) read the Whombat PeerId from `userHandle`, find it in the directory of the session's orgs; `trustDecision` with the passkey as the naming party: no pin → pin (source `'passkey'`), equal → fine, different → the existing identity-changed hard stop; (6) already enrolled → open; else an `enroll` ticket, session op `enroll.passkey {nonce, response, endpoint}` → `EnrolledOutput`, the session is promoted, the app opens. One user gesture end to end. | “email link → Open → gate” becomes “Sign in with a passkey → touch → in”. |
| PK-05 | **The Whombat verifies `enroll.passkey` itself** (channel `enroll`): credential known and not removed; its account still exists and isn't disabled; signature by the stored public key; `rpIdHash`, origin, type `webauthn.get`, UV flag; challenge = `passkeyEnrollChallenge({nonce, endpoint: session PeerId})`; `userHandle` = its own `wb1:<PeerId>`; signature counter not going backwards when non-zero; PK-07 policy. Then `insertEndpoint(via:'passkey', accountId: the passkey's account)`, counter and `lastUsedAt` updated, event `endpoint.enrolled` (via passkey, credential id). Every failure is one error `passkey_invalid` (no oracle); `passkey_not_allowed` for the PK-07 policy. The generic unenrolled rate limit applies, plus at most 10 failed passkey enrolls per peer per hour. | Control stays untrusted for authorization (threat model boundary 3): control's own check only signs in to the cloud account (MA-03 unchanged). |
| PK-06 | **Registering** (app channel, from an enrolled device, for the caller's own account): `passkey.register.begin {}` → `{applianceNonce, rpId, user:{id,name?,displayName?}, excludeCredentialIds}` (nonce kept in the session scope, 5 minutes); `POST /v1/auth/passkeys/register/options {appliance, applianceNonce}` → `{controlNonce, options}` (control sets the PK-01 user and the PK-03 challenge); `navigator.credentials.create`; `passkey.register {controlNonce, response, name}` on the Whombat (verifies attestation `none`, rpId, origin, UV, challenge with its own nonce; stores credential id, COSE public key, counter, transports, backed-up flag, name, account) and then `…/register/verify {response, name}` on control. Whombat first; if control then fails the client retries once, then removes it on the Whombat and says so. Name defaults to the device label (“Chrome on Linux”). At most 20 passkeys per account per Whombat. | The Whombat is the source of truth for entry; control only needs the credential to sign the account in. |
| PK-07 | **Synced passkeys are allowed by default.** Owner setting “Only passkeys that stay on one device” (`passkeys.policy {deviceBoundOnly}`), enforced at registration and at every enroll from the backup-eligible/backed-up flags in authenticator data. | John agreed the recommendation: Google/Apple synced passkeys are what makes it instant; owners who want more lock it down. |
| PK-08 | **Superseded in part by one-person.md OP-S06, OP-S08**: `passkeys.list` lists the person's passkeys and the person removes them, in Settings · Devices and on the Devices screen. **Seeing and removing passkeys.** `passkeys.list {}` → the caller's passkeys (an owner also sees everyone's, with the person), plus the policy; `passkey.remove {id}` by its person or an owner; the client also removes it from control (`DELETE /v1/auth/passkeys/:id`) for the caller's own. Removing a person/account on the Whombat removes their passkeys. Web: a “Passkeys” section in Settings · Devices; Android: the Devices screen. | One place to see what can open the Whombat. |
| PK-09 | **Telling the person.** When a device is enrolled with a passkey, the person's other enrolled devices get a notice (push where available, and the device shows as new in Settings · Devices with Remove): “New device signed in with a passkey: <label>”. | The one new risk is a taken-over Google/Apple account; a visible notice with one-tap removal is the counter. |
| PK-10 | **The nudge.** After a device is enrolled any other way (pairing, link, recovery) and the browser/phone supports passkeys, the app offers once per device and Whombat: “Open faster next time — Add a passkey” (Add / Not now). Settings · Devices always has “Add a passkey”. | Passkeys only help once one exists. |
| PK-11 | **Superseded in part by one-person.md OP-S04**: pairing, device links and the recovery kit stay; invite links are gone. **Fallbacks stay**: email link, pairing, invite/add-device links, recovery kit. A device that is already enrolled and signs in with a passkey just opens (no enroll). Account-level passkeys without `wb1:` user handle (control CL-11, unused by clients so far) still sign in to the cloud account only. | Nothing that works today stops working. |
| PK-12 | **A passkey goes with its Whombat.** When a Whombat is retired or released, control deletes the passkeys made for it (and a migration deletes the ones kept from before); a sign-in with one is 401 with reason `passkey_unknown`, as for any credential control doesn't hold. Every other refusal stays `passkey_invalid`. Account-level passkeys are untouched. Control: control CL-148; contract: `CONTROL_REASONS.passkey_unknown`. | John, 2026-11-02: his only passkey was for the old DEV box, retired 23 Oct. It still signed him in to the account but couldn't open any Whombat, so a passkey sign-in left him signed in and not connected. A passkey that opens nothing shouldn't seem to work. |
| PK-13 | **The browser and phone stop offering a dead passkey** (WebAuthn's Signal API). `PasskeyPlatform.forget(credentialId)` after `passkey_unknown` (`signalUnknownCredential`; the sign-in then says `gone`); `keepOnly(userId, ids)` with no ids after a sign-in that names a retired Whombat (and the passkey is removed at control too); and Settings · Devices tells the platform which of the person's passkeys the Whombat still takes each time it loads the list (`keepOnlyLivePasskeys`, `signalAllAcceptedCredentials`), so one removed elsewhere disappears here too. Web: `PublicKeyCredential.signal…` (Chrome 132+, Safari 26), RP ID = the page's host. Android: Credential Manager 1.6.0's `SignalUnknownCredentialRequest` / `SignalAllAcceptedCredentialIdsRequest`. iPhone: `ASCredentialDataManager` (iOS 26.2+). Every signal is silent and never fails a flow; where the platform can't, nothing changes. Only `passkey_unknown` triggers `forget`, never an expired challenge. | The passkey picker kept offering “Cybex BV” for a box that no longer exists. |
| PK-14 | **A dead passkey makes the passkey offer owed.** After `gone` or a retired Whombat's passkey, the nudge (PK-10) is owed: the next Whombat this device opens offers “Add a passkey”, even where “Not now” was tapped before for that Whombat; adding, “Not now” again, or finding the person already has a passkey there settles it. The retired note and the `gone` error say a new passkey can be added once the Whombat opens. | After a box is replaced nothing asked for a passkey for the new one, so the person stayed on email sign-in without knowing why. |

## Server decisions (PK-D*)

Server stream, 2026-10-05: contracts 0.50.0 vendored, `@simplewebauthn/server` ^14 (control's major), migration
`0080_appliance_passkeys`, `apps/server/src/managed/passkeys.ts`, tests `managed/passkeys.int.test.ts` with a software
authenticator (`src/test/webauthn.ts`).

| # | Decision | Why |
|---|---|---|
| PK-D01 | **Storage.** Table `appliance_passkeys` (credential id base64url as the key, account → `accounts` on delete cascade, name, COSE public key `bytea`, counter, transports, `backup_eligible`/`backed_up` from registration, `created_by_endpoint_id`, `last_used_at`/`last_endpoint_id`, `removed_at`/`removed_by_account_id`). Removal is a soft delete: the row stays for the audit trail and for `current`. The PK-07 setting is `appliance_state.passkeys_device_bound_only` (the single-row appliance state already holds the appliance-wide trust settings: claim window, recovery key, client floor). Which passkey enrolled a device is `appliance_endpoints.enrolled_passkey_id`. Migration 0080 is `expand`, floors 0047 (old binaries ignore all three). | One place per fact, readable by an old binary after a rollback. |
| PK-D02 | **Relying party** (`managedPasskeyRelyingParty`, config.ts): RP ID = host of `WHOMBAT_APP_URL`; origins = its origin, `PASSKEY_ANDROID_ORIGINS`, and `WHOMBAT_PASSKEY_EXTRA_ORIGINS` (comma-separated, trimmed, a trailing `/` dropped, de-duplicated). Both ceremonies require user verification and check the client data type (`webauthn.create` / `webauthn.get`); algorithms are the library's defaults (EdDSA, ES256, RS256). | PK-02, with no second setting to keep in step with control. |
| PK-D03 | **Registration.** `passkey.register.begin` is dispatched like `enroll.claim.begin`: ephemeral (no receipt), the ephemeral rate budget, enrolled sessions only. Its 32-byte nonce lives in the session scope (`passkeyBegin`) bound to the account and endpoint, 5 minutes; a new begin replaces it, closing the session drops it, and `passkey.register` uses it up whatever happens (no live begin, an expired one or another session's = `passkey_invalid`). `user.name` = the account's email (always known here), `user.displayName` = the oldest live burrow's name as the console shows it (left out when there is none) — control's options carry the cloud account's values anyway. `user.id` can't be checked at registration (it isn't in the signed data): the client checks control's options carry ours, and every enroll checks the `userHandle`. Any attestation format that verifies is accepted (we ask for `none`; nothing is decided from attestation). The limit is counted under a per-account advisory lock in the inserting transaction; the policy is checked there too. The same credential id again, even a removed one, is `conflict` (`details.code: passkey_exists`). | A stored credential always comes from this session's begin; one begin, one passkey. |
| PK-D04 | **Enroll, exactly PK-05.** Checks in order: `id` = `rawId`; `userHandle` present and naming this Whombat; credential known and not removed; account active (PK-D05); then the assertion (signature with the stored key, RP ID hash, origin, type, UV, challenge `passkeyEnrollChallenge({nonce, endpoint: session PeerId})`, counter). Counter rule = `@simplewebauthn`'s: when the stored or the new counter is non-zero the new one must be **greater** (an equal non-zero counter is refused too); passkeys that keep no counter (0/0) pass. The row is re-read `FOR UPDATE` in the enrolling transaction (removed meanwhile, counter moved by a racing replay, account no longer active = `passkey_invalid`), then `insertEndpoint(via 'passkey', the passkey's account)` with `endpoint.enrolled` carrying `credentialId` (`PasskeyEnrolledAuditDetail`), counter, `last_used_at`, `last_endpoint_id`. Every failure above is the one `ApiError('forbidden', …, {code: 'passkey_invalid'})` with the same message; the reason goes to the log only. `passkey_not_allowed` comes only **after** the signature verified (no oracle for whether an id is synced); synced = BE stored at registration, or BE/BS in this assertion. Refusals that aren't about the passkey keep their codes: `endpoint_enrolled` (this key is enrolled already — clients treat it as “just open”, PK-11), the revoked-key `forbidden`, `rate_limited`, `unavailable` while draining. Control's nonce isn't checked here: a replayed assertion can only enroll the key it names, which then is enrolled (or revoked) already. | No oracle, and one assertion enrolls one key once. |
| PK-D05 | **Superseded by one-person.md OP-S06, OP-S08**: a passkey enrols only into the person's account (the claimer's), and nobody is offboarded. **“Account exists and isn't disabled”** = an owner of this Whombat, or a person in at least one burrow — offboarding's rule (EP-07). Offboarding an account from its last burrow (`revokeRemovedAccount`) removes its passkeys in the same transaction as its devices: `passkey.removed` with `byAccountId: null` (the passkey went with its account; the event's actor is whoever removed the person). Owners keep their passkeys as they keep their devices. Deleting an account row cascades. | Removing a person removes every way back in (PK-08). |
| PK-D06 | **Failure budget in memory**, per peer: at most `PASSKEY_ENROLL_FAILURES_PER_HOUR` (10) `passkey_invalid` answers in a rolling hour; then `rate_limited` (“Too many passkey attempts from this device. Wait an hour and try again.”) before anything is verified. Only `passkey_invalid` counts. A restart forgets it; the unenrolled budget (20/min per peer) applies as before. | Like pairing tries (MR-32): one server per appliance, and guessing a signature is hopeless anyway — the budget bounds the work a stranger can make the box do. |
| PK-D07 | **Superseded in part by one-person.md OP-S06**: the person lists and removes their passkeys and sets the policy (no owners or members); `current` holds. **List, remove, policy.** `passkeys.list`: live passkeys only, newest first, at most 1000; members their own, owners everyone's; `personName` = the account's name, else its email. **`current` = this session's endpoint was enrolled with that passkey** (`enrolled_passkey_id`); a passkey merely registered from this device is not `current`. `passkey.remove`: the person or an owner; anything else, an unknown or an already removed id is `not_found`; devices it enrolled stay. `passkeys.policy`: owners (`not_owner`), signed `passkeys.policy_changed` only when the value changes, `{ok: true}` either way. With the policy on, synced passkeys stay stored but enroll nothing (`passkey_not_allowed`); they work again when it is turned off. | The contract's wording (CT-281), made precise. |
| PK-D08 | **The PK-09 notice** is a content-free `security` push (MR-13: no label leaves the box) to every live endpoint of the person with a push handle — the new device has none yet, so it reaches the other ones; ref = the keyed hash of `passkey-enrolled:<endpointId>`. Phones show the generic security line (“A security change on your Whombat”) and a tap opens the Whombat; the words “New device signed in with a passkey: <label>” are the client's, read through the session (`endpoints.list`, newest device; `passkeys.list` `lastUsedAt`). Owners aren't told (it is the person's own account). | Push stays content-free; no contract change. |
| PK-D09 | The runtime advertises the feature **`passkeys`** (`IMPLEMENTED_FEATURES`) and serves session API level 33. | CT-284. |
| PK-D10 | **Every refused `enroll.passkey` is logged** (info, `passkey: an enroll was refused`): the answer's code, its `details.code`, the names of invalid fields, the message (200 characters) and the last 8 characters of the session's PeerId; never the input. Logged by the dispatcher, so input refusals, rate limits, deadlines and refusals inside the enrolling transaction show as well as the `passkey_invalid` reasons (`passkey: an enroll did not verify`). | John's Firefox sign-in, 2026-10-05: the page said “That didn’t work” and the box had nothing to say. That time the client refused before sending (app AP-805); a refusal on the box would now be visible too. |
