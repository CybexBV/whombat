# A 1Password vault kept in step with the Vault, both ways (OPW)

John, 2026-11-24 (main checkout): “We have a Vault in Whombat. Can I link it to 1Password, so I give it a vault from
1Password and it syncs with the Vault in Whombat?” After the research he chose a copy kept in step inside the Vault
(not a lookup at every use, not Hermes's own 1Password backend, which VLT-01 and VLT-20 keep off), and asked for it to
work **both ways**. The plan went to the council first (GPT 6.2 Sol, Claude Opus 5.5, Muse Wonder Full 1.0, Gemini 4
Neon; all 6/10 on round 1); what they agreed on is below, and John chose where they differed (marked “John,
2026-11-24”).

What 1Password offers (checked 2026-11-24): a **service account** is a token scoped to the vaults chosen when it is
made, with read and/or write per vault, unchangeable afterwards; it can't reach the built-in Personal, Private,
Employee or default Shared vault; every plan has them. Limits per token per hour: Business 10,000 reads / 1,000
writes, the others 1,000 / 100; **per account per day, all its service accounts together**: Business 50,000, Teams
5,000, Individual and Families 1,000. The JS SDK (`@1password/sdk`, a WASM core) reads a vault's `contentVersion`
(`vaults.getOverview`), lists item overviews with `updatedAt`, gets up to 50 items at once, creates, updates (`put`,
the whole item, with its `version`), archives and deletes. There are no webhooks.

Code: `packages/core/src/vault/onepassword.ts` (mapping, comparison, merge, guard), the catalog entry
`packages/core/src/domain/connections-catalog/onepassword.ts`, `apps/server/src/vault/onepassword/` (the worker, the
pass, the commands), the Vault and connection screens on web and phone.

Checked against a real account (2026-11-24, `apps/server/src/scripts/onepassword-smoke.ts`, SDK 0.5.0): a Login's built-in fields come back with `sectionId`, `details` and the item's `document` as `null` (the item shape first refused them, so no new Login could be made); a new Login, API Credential, marker field and one-time password round-trip and read back as the same entry; a custom field put without a section is kept (its section then reads as empty); a `put` with an old version is refused with “The submitted item is not up to date. Refetch the item and retry the request.”; every create and put moves the vault's `contentVersion`; the SDK shows no limit counters. Each call took 0.2 to 0.7 s.

## Linking

| # | Decision | Why |
|---|---|---|
| OPW-01 | **1Password is a connection** (`onepassword`, “1Password”) with a new catalog use `vault`: never one of the agent's connections, never listed or callable through `connection_tools` / `connection_call`, not in Home's five-minute health pass, at most one per Whombat. It signs in with a **service account token** (sealed as every connection's secret) and has one field, the vault, filled from the token's answer (`fromService`: the only one is taken, several are offered). Its check (new check kind `onepassword`) runs in the worker (OPW-30): the token signs in and lists the vaults it can see. The base URL is `onepassword:`, never requested. | The person already knows Connections; a connection's secret is sealed and shown only as set. The agent has no business with the token: only the sync uses it. |
| OPW-02 | **One question when linking**: the form's second field, “Your Vault entries”, “Also put them in this 1Password vault” (default) or “Keep them only in Whombat”. Entries that sync (OPW-10) and are in the Vault when the connection is made go to 1Password with the first choice and stay Whombat-only with the second (a link in state `local_only`). Every eligible entry made afterwards syncs. | John, 2026-11-24 (one question at linking). He asked for both ways, so putting them in is the default. |
| OPW-03 | **The form says what happens**, in plain words (its guide and the field's help): make a vault for Whombat and a service account that can read and write only that vault; logins and API tokens go both ways; Whombat's own settings stay in Whombat; the passwords you give Whombat go into that vault too. | The person consents to a new place their secrets go (OPW-60), knowingly. |
| OPW-04 | **A token that can't write** is found at the first push: the item stays as it is in 1Password, the connection page says “This token can only read. Make one that can read and write the vault.”, and pulling goes on. | The SDK doesn't say a token's rights up front; probing by writing a test item would leave traces in the person's vault. |

## What syncs

| # | Decision | Why |
|---|---|---|
| OPW-10 | **Two kinds sync.** A Login ↔ a `login` entry: title ↔ name, the first website ↔ the sign-in page's URL, the username ↔ the form's username, the password ↔ the secret, the first one-time password field ↔ the authenticator key. An API Credential ↔ an `http` entry signing in with `bearer` or `basic`: title ↔ name, the credential ↔ the secret, the hostname ↔ the URL (a bare host gets `https://`), the username ↔ basic's username (none: bearer). | Website logins and API tokens are what people keep in 1Password and what the assistant uses most (Home: an API key in daily use). |
| OPW-11 | **Not synced**: notes and the entry's description (the description reaches every turn's context, and notes often hold recovery codes); SSH keys, both ways (the assistant's generated key never leaves the box, VT-S03; 1Password has no ECDSA keys; servers, host keys and kept passwords have no place there); `http` entries signing in with a header or a query (1Password has no place for the header's name); legacy `secret` and `mcp` entries; every other item category. Those entries stay Whombat-only and those items stay 1Password-only. | Council, unanimous. A smaller first version that is still truly two-way. |
| OPW-12 | **What only one side has stays its own.** Whombat never sends the assistant's switch, the variable's name, checks or uses. A push changes only the mapped fields of the item it has just read (get, change, `put` with its version), so 1Password's other websites, fields, sections, tags, files and history stay. | `put` replaces the whole item; building a fresh one would wipe what Whombat can't hold. |
| OPW-13 | **Values are compared by meaning**, through one canonical form per field: the name trimmed, a URL in `parseVaultUrl`'s form, a username as it is, a secret as it is, an authenticator key as `vaultTotpCanonical`'s secret, algorithm, digits and period (its label ignored). A pushed authenticator key keeps the item's own issuer and account when only the secret changed. | Compared as text, Whombat's own normal forms would look like a change on every pass and rewrite the person's items for ever. |
| OPW-14 | **What doesn't fit isn't put in.** An item without a website, a password or a credential, an address Whombat may not reach (VT-10…VT-13, checked with its DNS before the commit), a value past the Vault's limits, or one past the Vault's 50 entries, doesn't become an entry: the connection page lists it under “Not in your Vault” with the reason. A title longer than 60 characters is shortened in Whombat and never pushed back unless it is renamed in Whombat. | An entry that can't be used must not exist where the assistant's delivery would hand it out (the delivery doesn't check these again). A shortened value pushed back would destroy the original. |

## Keeping them in step

| # | Decision | Why |
|---|---|---|
| OPW-20 | **One pass at a time**: when the server starts read-write, every 10 minutes, 10 seconds after a change to a synced entry (or a new one that will sync), and on Sync now; several reasons coming together make one pass. No pass in read-only mode, during a maintenance pause, drain or quarantine. Home's health and the connection page read the pass's stored state and never call 1Password. | The cost: about 144 reads a day while nothing changes, inside Individual and Families' 1,000 a day shared with every other service account. |
| OPW-21 | **A pass reads first, then commits.** It asks for the vault's `contentVersion`; unchanged, and nothing waiting in Whombat: done. Otherwise it lists the items, gets (50 at a time) those whose `updatedAt` differs from what the link saw, decides each pair in core (OPW-23), checks the destinations of what will come in, and applies the result in small commits (at most ten entries each) through one Vault command run as the person, which uses the Vault's own helpers (insert, replace the secret, set the authenticator key, switch on, remove), so the scrubbing of held secrets, the events and the screens behave as for the person's own change. A commit skips an entry whose `updated_at` moved since the pass read it, and a pull or removal whose pair isn't the one it read any more (kept only in Whombat meanwhile, or paired with another item); the next pass takes it. No 1Password call and no DNS under the write lock. | The write-lock rule (write-lock.md); one path for every Vault change. |
| OPW-22 | **What goes to 1Password is worked out from the state**, not queued: a synced entry whose canonical fields differ from the link's base, an eligible entry without a link (made after linking, or there when linking with the first choice of OPW-02), and a link whose entry was removed. A new item gets the Whombat entry's id in a field “Whombat entry” in a section “Whombat”; before creating, the link is written as `creating` with Whombat's side as it is sent as its base, and a pass that finds a `creating` link first looks for an item carrying that id and takes it instead of making another (what changed in it since counts as 1Password's change). An entry removed before its item was found leaves the link remembering the marker's entry id: the item carrying it is archived, never brought in. After a create or a put, the item's new `version` and `updatedAt` and the new base are stored in the same commit, so Whombat's own push never looks like a change in 1Password. A put that fails gets the item again, decides again and tries once more in that pass. | The Vault changes in about a dozen places; a queue row each place must remember is a drift waiting to happen, and a restored queue would replay old values. `create` can't be retried safely without a marker. |
| OPW-23 | **Deciding a pair**: each side's canonical fields are compared with the base the link keeps (an HMAC per field with a key of the box's, separated by entry and field, so no second copy of a secret is stored). Neither changed: nothing. One side changed: that side's fields are taken, all of them. Both changed to the same: the base is renewed. **Both changed differently: Whombat's version wins** and goes to 1Password, which keeps the replaced one in the item's history (John, 2026-11-24). **No base** (only a restore leaves one: an entry relinked after it, or a whole-box restore, after which every pair a pass makes or finds again has none until a pass reads everything and finishes): 1Password's version wins, because the restored Vault is the older side. | Whombat keeps no history and 1Password does, so Whombat winning loses nothing. Taking a side whole never mixes one side's username with the other's password. |
| OPW-24 | **Removing.** An entry removed in Whombat: its link stays as a marker until the pass archives the item in 1Password (never deletes it), then goes. An item gone from the vault (archived, deleted or moved out; only items the list calls active are in it): **its entry is removed in Whombat** (John, 2026-11-24), unless the entry holds what 1Password never got (changed here since the pair last agreed, or a change 1Password refused): then the pair goes, the entry stays and is put in again as a new item. **The guard**: a pass that would remove more than 3 entries, or more than a quarter of the linked ones, or all of them, or that met any error while listing, removes nothing and pauses; the connection page and a card in the Inbox say “1Password says 4 items are gone” with “Remove them here too” and “Keep them here”. Keeping makes them Whombat-only (`local_only`), never pushed back. | An error or an emptied vault must never empty the Vault. Pushing kept entries back would revive items the person removed on purpose. |
| OPW-25 | **What comes in from 1Password is switched on for the assistant at once**, as an entry the person saves is (an API token's variable named as usual). | John, 2026-11-24: the vault is made for Whombat; what is put in it is meant for the assistant. |
| OPW-26 | **1Password's limit**: on “too many requests” the passes wait, from 15 minutes doubling up to 2 hours with some jitter, kept with the pass's state so a restart doesn't start over; the page says “Waiting for 1Password’s limit. Next try at 14:20.” | The SDK's error says no reset time. |
| OPW-27 | **An entry that stops fitting** (switched to a header or query sign-in, say) stops following: its link becomes `local_only`, the item stays in 1Password as it was, and the entry's page says “No longer kept in step: 1Password has no place for this sign-in.” | Archiving the item would remove something the person still has; pushing half of it would be wrong. |
| OPW-28 | **An item that stops fitting** (its website or password removed in 1Password) leaves its entry as it was: the link keeps its base, the entry's page and the connection page say why (“1Password’s item has no website now”), and the pair follows again once the item fits. Never a removal. | Only an item gone from the vault removes an entry (OPW-24); a half-edited item must not take a working sign-in away. |

## The worker

| # | Decision | Why |
|---|---|---|
| OPW-30 | **The SDK runs in its own process**, `onepassword-worker` (a bundle entry beside `image-worker`), started by the server when a pass or a check needs it and stopped after 15 minutes without work. It speaks JSON lines on stdin and stdout with a small set of calls (check, vault overview, list, get, create, put, archive), keeps one SDK client per token while it runs, logs no value and no token, and its stderr is scrubbed. A crashed worker ends that pass with “1Password sync stopped unexpectedly”; the next pass starts a new one. `@1password/sdk` is pinned exactly (0.5.0, 2026-07-31); its WASM file ships beside the bundle like `node-pty` does, and the runtime's fixed hash is refreshed with the lockfile. | A 0.x WASM library that may change between minors can't take the whole server down. Loaded only when 1Password is linked. |
| OPW-31 | **The worker's network** goes only to 1Password: the worker wraps the global `fetch`, which the SDK's core uses for every request, so it reaches only 1password.com, 1password.eu, 1password.ca and their subdomains, over https on the default port, and follows no redirect. It doesn't go through the server's outbound guard (`lib/outbound.ts`), which can't wrap the SDK's own client. | Written down so nobody takes it for a gap. The token's sign-in address is always one of these. |

## Data, contracts, backups

| # | Decision | Why |
|---|---|---|
| OPW-40 | **`vault_onepassword_links`**: one row per pair: the connection (cascade), the entry (`on delete set null`: the marker of OPW-24), the item and vault, the state (`creating`, `synced`, `local_only`), the item's last `version` and `updatedAt`, the base (jsonb of HMACs, null: none), whether the name was shortened, a problem in words, when it last synced, the one-time password field it follows, the entry id a `creating` link's marker carries, and the digests of a change 1Password kept refusing. One link per entry and one per item. **`vault_onepassword_state`**: one row per connection: the vault's title, the `contentVersion` last seen, the last pass and its outcome (`ok`, `paused`, `waiting`, `failing`), counts, every item kept out of the Vault and why (the page shows 200), the removals waiting for the person, the wait of OPW-26, the passes in a row that couldn't finish, and whether a whole-box restore's “1Password first” still holds. | Everything a pass needs to decide is in the database; the worker holds nothing that matters. |
| OPW-41 | **Contracts** (`@whombat/core`, additive): the catalog use `vault`, the check kind `onepassword`; `VaultEntry.source` (optional: `{ kind: 'onepassword', state: 'synced' \| 'pending' \| 'problem', syncedAt, problem?, paired? }`); the connection page's 1Password part; the operations Sync now and the answer to the guard's card; the session protocol's minor. Older apps ignore what they don't know. | Contracts first, one commit with server and apps. |
| OPW-42 | **Backups.** A backup file's Vault entry carries `onepasswordItemId` (optional). Restoring a file or bringing one entry back relinks it to that item when the connection is there and the item in its vault, with no base, so 1Password's version wins at the next pass; otherwise it is a Whombat entry like any other. A whole-box restore clears every link's base the same way, and until a pass reads everything and finishes every pair a pass makes or finds again has none either. Nothing is pushed before that pass has pulled. | A restored Vault is older than 1Password; it must never write old passwords over newer ones. |

## Security

| # | Decision | Why |
|---|---|---|

## Server (stream S)

Shapes the rows above left open, decided while building the worker, the pass and the server's parts
(`apps/server/src/vault/onepassword/`, `things/kinds/onepassword.ts`, migrations `0020_onepassword_sync`,
`0021_onepassword_pair_fields` and `0022_onepassword_pull_first`).

| # | Decision | Why |
|---|---|---|
| OPW-S01 | **The worker is a child process** (`node <worker> --whombat-onepassword-worker`) with none of the server's environment (no master key, no database address; only the CA and time-zone variables) and a 256 MB heap. Every request carries an `id` and the token; the worker keys its SDK clients by the token's SHA-256 and drops one the SDK says expired. A call waits at most 60 s; a worker that dies or hangs fails what it had as `stopped` and the next call starts another. Its own console output goes nowhere; what reaches stderr is logged with every token it was sent taken out, and nothing of a worker already replaced is logged (its tokens are forgotten). A throw or a rejection nothing caught ends the worker (exit 70), said by its name only. A `probe` call only loads the SDK. | A process can be killed when it hangs inside the WASM, and a leaked variable can't reach it. The token in each call keeps the worker holding nothing that matters (OPW-40). |
| OPW-S02 | **A failure has a kind**: `limit`, `auth`, `forbidden` (a read-only token writing), `not_found`, `network`, `invalid`, `failed`, read from the SDK's error classes and else from its words (a timeout is `network`; `auth` only for a token's own failure, expired, revoked, invalid, rejected or not accepted, never a message that merely names a token); its message has the token and every value of the request taken out and is at most 300 characters. A single `put` on an older version is `failed`: the SDK gives only words for it. An item a batch read's answer says nothing about is `failed`. | The pass decides by kind; the words are for the log and the smoke script, never for the person. |
| OPW-S03 | **The SDK ships beside the bundles**: `@1password/sdk` and `@1password/sdk-core` (pinned 0.5.0) are kept out of every bundle and copied flat into the runtime's `node_modules`, the same for every arch; the package test loads the WASM from that layout through the bundled worker and the Nix install check imports the SDK. | The core reads its WASM from beside itself; bundled, it can't find it. |
| OPW-S04 | **The base's key** is the key custody's own per-purpose sub-key (`mac('vault/onepassword/base', …)`) over the entry's id, the field and the canonical text; a stored base missing a field counts as none (1Password wins). | One sub-key for this purpose only, and a digest of one entry's password says nothing about another's. |
| OPW-S05 | **What the tables keep**: a link's id is `opl_…`; the item's `updatedAt` is kept as 1Password's own text and compared as text; the page's counts are counted from the links when read, not stored; each item kept out keeps the time it was read at and how many reads in a row failed (neither shown), every one of them, not only the 200 the page shows, so an unchanged item isn't read again, except for the server's own reasons (“Your Vault is full”, “Whombat may not reach this address”), read again whenever the vault changed (the second also when the home networks change), and one whose read failed once. The state row is made in the commit that adds the connection, and the answer to “Your Vault entries” stays in the connection's fields (absent: put them in). | Stored counts drift; 1Password's times have more digits than Postgres keeps. |
| OPW-S06 | **One Vault command applies a pass's decisions** (`vault.onePasswordApply`: pull, add, relink, mark, creating, created, local, remove, drop), at most ten that change an entry per commit; it runs as the person through the Vault's helpers (the removal and the authenticator key's setter are shared helpers now) and adds `source: onepassword` to every event it signs. A pair it makes or finds again that one already holds (the entry or the item) answers `gone`, never a duplicate key that would undo the rest of its batch, and the pass writes nothing into that item.
