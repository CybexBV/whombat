# Notifications

Workstream: TODO 9.4 (server + desktop web push) and the server side of mobile push / live activities.
Builds on the pre-existing `NotificationService` fan-out, inbox endpoints and realtime `notification.created`
publish (REST/DB scaffolding already in `main` before this workstream started); this workstream added push
delivery, live activities, and the contract pieces (`PushPayload`, `PushDevice`/`PushProvider`,
`LiveActivity`/`RunLiveActivity`/`ApprovalLiveActivity`/`LiveActivityPush`, `liveActivityRef()`) that carry
them. See `docs/push-setup.md` for how to configure each transport.

| # | Decision | Why |
|---|---|---|
| NT-01 | Web push is sent by building the request with `web-push`'s `generateRequestDetails()` (VAPID header + AES-GCM encryption) and sending it ourselves with `fetch()`, rather than calling the library's own `sendNotification()`. | `sendNotification()` hardcodes `https.request()` regardless of the endpoint's scheme, which makes it impossible to test against a local plain-HTTP mock push server. Building-then-fetching keeps the real crypto (so tests exercise genuine VAPID auth + encryption) while staying testable offline. |
| NT-02 | FCM uses a hand-rolled OAuth2 JWT-bearer flow (`node:crypto`'s `createSign('RSA-SHA256')`) against `oauth2.googleapis.com`, and APNs uses a hand-rolled ES256 provider-token JWT (`ieee-p1363` signature encoding) over `node:http2`, instead of the Firebase Admin SDK or an APNs client library. | Both protocols are small enough to implement directly with `node:crypto`/`node:http2`, and avoiding the SDKs keeps `apps/server`'s dependency surface (and the server's cold-start/bundle size) smaller. Access tokens (FCM) and provider tokens (APNs) are cached in a module-level variable and reused until they're close to expiry. |
| NT-03 | All three transports share one `PushTransport` interface (`(config, log, device, payload) => Promise<PushOutcome>`, `PushOutcome = 'sent'\|'skipped'\|'failed'\|'prune'`) and one dispatcher, `PushSender` (`apps/server/src/push/sender.ts`), which retries `'failed'` twice (250ms/1000ms backoff, both injectable) and deletes the device row on `'prune'`. | A single retry/prune policy, applied uniformly regardless of provider, means notify() and the live-activity broadcaster don't each need their own retry logic, and a device that goes stale on any provider gets cleaned up the same way. |
| NT-04 | Push delivery hooks into the existing `notify()` pattern via `ctx.after()` — never inside the transaction itself. `NotificationDraft` grew an optional `burrowSlug`; when present, `notify()` looks up the recipient's devices and calls `push.sendAll()` after the realtime `notification.created` publish. | Matches how every other post-commit side effect in the commit pipeline is structured (`ctx.after()` hooks run after the outbox is flushed), and means a push failure can never roll back or block a write — the notification row and realtime event are already durable by the time a push is attempted. |
| NT-05 | `LiveActivityBroadcaster` is the single place that turns a run or approval into a `start`/`update`/`end` event. It keeps two in-memory maps (`active: Set<ref>`, `lastSent: Map<ref, ms>`) scoped to the server process — not persisted to Postgres or Redis. | Simplicity: a process restart just means the next non-ended change looks like a fresh `start` (harmless — the activity gets re-announced, which is the same "catch up" behavior a client reconnecting would need anyway). A persisted throttle store would add a table and a migration for a guarantee (throttle survives restart) nothing in the product spec asks for. If Whombat ever runs multiple server instances behind a load balancer, this becomes a real gap — noted as a follow-up, not solved here. |
| NT-06 | Throttling (`THROTTLE_MS = 2000`) applies only to `update` events. `start` and `end` always go through immediately, even mid-window. | An activity must never miss its beginning (nothing to show otherwise) or its dismissal (a stuck "still running" notification is worse than an extra push). Only the noisy, high-frequency middle (progress ticks) needs throttling. |
| NT-07 | Recipients: a run's live activity goes to `[run.askedById]` (the person who asked for it); an approval's goes to the `person_approves` condition's `approverIds` (via `approverIdsOf()`), the same population `approvals/create.ts` already uses for "needs_you" notification fan-out. | Reuses an existing, already-reviewed population rule instead of inventing a second one — whoever needs to act on (or is watching) the approval is exactly who should see its live activity. |
| NT-08 | Lifecycle: a run's activity ends when `status` is `'done'` or `'failed'`. An approval's activity stays alive through `pending` **and** `approved`-but-not-yet-executed, ending only when `executedAt !== null` (the action actually ran) or `state === 'declined'`. | Matches the demo storyline "approval → approved → deployed": "approved" only means a person said yes, not that the deploy finished. Ending the activity at `approved` would make the live activity vanish while the deploy is still running, which is the opposite of what a live activity is for. `ApprovalLiveActivity.state` itself only carries `pending`/`approved`/`declined` (execution completion is a separate `executedAt` check, `isApprovalEnded()` in `apps/server/src/domain/live-activity.ts`), so a client rendering the activity still needs to look at `execution.state`/`executedAt` for "is it actually done" — same as the approval detail screen already does. |
| NT-09 | Live-activity and notification push payloads carry the burrow's URL **slug** (`ctx.burrow.slug` / `burrow.slug`), never its `id`, and deep links are built with the shared `linkPath(burrowSlug, ref)` helper from `@whombat/core` rather than hand-rolled path strings. | `burrow.id` (e.g. `burrow_1`) is a database id, not a URL segment — a push whose `path`/`burrow` used the id would produce a 404 deep link. Caught during development (see below) before it shipped; routing all path-building through `linkPath()` means any future change to the URL scheme only has one place to update. |
| NT-10 | iOS live-activity device selection prefers a token already registered for the exact activity (an "update" token from `devices.registerLiveActivity`); if none exists, falls back to the account's push-to-start token so the activity can be started remotely; a device with neither is skipped for that activity. | Matches ActivityKit's own model: `push-to-start` tokens exist precisely so the server can begin an activity the device hasn't seen yet, while an already-running activity should be updated via its own token, not restarted. `devicesForActivity()` (`apps/server/src/push/devices.ts`) implements this preference order. |
| NT-11 | `LiveActivityBroadcaster` takes an injectable `lookupDevices` constructor parameter (defaulting to the real `devicesForActivity`), and `PushSender` an injectable `delay` parameter (defaulting to real `sleep`). | Both let the throttling algorithm, lifecycle rules, and retry/backoff be unit-tested deterministically and fast (no real Postgres, no real timers) while defaulting to the real implementation everywhere else. |
| NT-12 | Registering the web `sw.js` and subscribing via `devices.vapidKey` is **not** implemented as part of this workstream — described in `docs/push-setup.md` instead. | apps/web is owned by the parallel desktop-screens workstreams; this workstream's instructions permit touching only `apps/web/public/sw.js` (a new, standalone file no other workstream owns) and not the shell/app code that would register it. |
| NT-13 | **On a managed Whombat, live activities don't wake the phone** (2026-10-06). `LiveActivityBroadcaster` no longer calls `push.control`; device transports (self-hosted web push / FCM / APNs) are unchanged. | John's Android phone buzzed “Whombat · A run has news” on every start and throttled update of Banjo's runs (DEV control's `push_deliveries`: only kind `run`, pairs 2 s apart). A content-free wake (MR-13) can't show progress, the generic notification alerted each time, and its tap couldn't resolve (`push.resolve` matches inbox rows, not runs), so it opened the inbox with “not found”. What needs the person (an approval, a mention, an agent's message to them) is an inbox notification with its own push. |
| NT-14 | **Push previews** (2026-10-06, contracts 0.51 CT-286). A managed Whombat's push carries `preview {title, body}`: who and where, and the start of the text. Titles (actor = short name, `where` = the row's): `mention` “Banjo mentioned you in #general”, `reply` “Banjo replied in #general”, `direct` “Banjo · <where>”, `agent_update` “Banjo” in its DM (`where` “Direct”) else “Banjo · <where>”, `needs_you` “Needs you · <where>”. Body = the row's text; for a message its plain text with fenced code blocks as “(code)” (`previewText` on the draft; the inbox row keeps its text). `previewLine` (`domain/push-preview.ts`, pure) maps whitespace, separators and controls to one space, drops format characters and lone surrogates, collapses and trims, and cuts at a grapheme boundary to 80 / 160 code points with “…” last; an empty title reads “Whombat”. `Preferences.notifications.previews` false (“Show message text in notifications”) = no preview, the phone's generic text; the self-hosted transports then send “Whombat” and the same generic line (`GENERIC_PUSH_TEXT`, defined once). Feature `notifications.previews`. | John, 2026-10-06: “we should embrace privacy, but this is ridiculous if we even encrypt notification messages” — “An agent has an update for you” told nothing. The content-free rule (MA-03/MA-10, MR-13) narrows to two short plain lines that control passes through and never stores; the Privacy Policy (whombat-app `apps/web/src/legal/privacy-policy.md`, “Notifications”) says what a preview shows and how to turn it off. Code is never useful in two lines and is where secrets sit. |
| NT-15 | **One notification per thread or approval.** `NotificationDraft.group`: a message's `thread:<conversationId>:<threadRootId or main>`, an approval's “needs you” `approval:<approvalId>`, others none. `ControlPush` sends `collapseKey = opaqueRef('collapse', group ?? subject)`; the `ref` stays per notification, so a tap opens the newest. `services.push.control` takes an options object (`group`, `preview`, `clear`); `PushPayload` (core) is unchanged. | Since 0.51 the phone replaces a notification with the same key (silently while it shows): a busy thread is one line that keeps up, not a stack. The key is a keyed hash like the ref, so it says nothing about the thread. |
| NT-16 | **A decided approval leaves the phone.** When an approval leaves `pending` (approved, declined, expired — both `onApprovalChanged` call sites, `approvals/engine.ts` `publishApproval` and `approvals/create.ts`), `clearDecidedApproval` sends a `clear` for group `approval:<id>` to the approvers' accounts (`approvalLiveActivityAudience`, who got its “needs you”), content-free, kind `approval`; once per approval per process (an in-memory set, capped at 10 000, like NT-05). Managed only. | Someone approving on the web shouldn't leave “Needs you” on their phone (or the other approvers'). A second clear after a restart is harmless (nothing left to remove). |
| NT-17 | **Superseded in part by one-person.md OP-S14**: a push is still held while the person is at a screen (`needs_you` always pushes), read from the box's own record of their connections, not presence or typing frames. **No push while active.** `notify()` skips the push (control and device transports) when the recipient's presence is `active` (`presenceFor(services).stateOf`); `needs_you` always pushes. The inbox row and the realtime event still happen. Active here = a connection (web `/ws` or the phone app's managed session) that opened, typed or said `active` in the last minute (`PresenceTracker.activeWithin`, `PUSH_HOLD_ACTIVE_MS` 60 s), not presence's 10-minute `active`: the phone app's own open session counts, and it shows the notification in-app. | A person reading the conversation on their laptop doesn't need their phone buzzing for the same message. Clients don't report `idle` on blur, so presence's `active` lasts up to 10 minutes after the last typing: asking Banjo something and putting the phone away would have swallowed his answer three minutes later. One minute covers a quick answer while they're still looking. An approval is too important to risk. |
| NT-18 | **An older manager.** A manager (or control) on contracts 0.50 refuses `preview` / `clear` (strict schema: 400 `bad_request`, or 502 `control_refused` from control). `ControlPush` then sends that batch once more without `preview` and drops a `clear`, and logs a warning once per process. | The candidate moves runtime and manager together, but a box mid-update (or a hand-built one) must still get its notifications, the old generic way. |

Later changes (mobile-live workstream, `docs/decisions/mobile-live.md`): pushes carry the display built by
`@whombat/core` (ML-01); an agent-asked run goes to the people in its conversation (ML-03, extends NT-07);
taken-over runs and failed executions end their activity (ML-04, extends NT-08); the last throttled update
goes out when the window closes (ML-05, extends NT-06); APNs live-activity topic and attributes type (ML-13).

## A bug caught before it shipped

An early draft of `live-activity.ts` used `activity.burrowId` (the database id) both as `PushPayload.burrow`
and to hand-build paths like `` `/${activity.burrowId}/runs/${activity.number}` ``. That's wrong — burrow
paths are keyed by slug, not id — and would have produced dead deep links. Fixed by threading a
`burrowSlug: string` parameter through `onRunChanged()`/`onApprovalChanged()`/`dispatch()`/`buildPayload()`
and switching to `linkPath()` (NT-09). Caught in self-review before any test ran against it.
