# Automations that act without AI (DAU-01…DAU-19)

John's look-after build, 2026-11-28: “When the UPS has been on battery for 10 minutes, shut down the NAS” (MON-11)
must run on the box by itself, with no AI turn and with the internet down. This file is how automations act directly,
what starts them from Home Assistant and UniFi Protect, and what keeps them from looping or making noise. People still
make them only by talking to their assistant (`automation-chat.md`); the plan card says what each part does.

| ID | Decision | Reason |
|---|---|---|
| DAU-01 | **A `run_action` step does one thing from a short list, without AI.** A server: restart, shut down. One of its machines (a VM or container): start, stop, shut down, restart. Home Assistant itself: restart. A Home Assistant entity: a `light`, `switch`, `fan` or `input_boolean` on or off. The step names the thing (`server:<id>` or `connection:<id>`), an optional target (the machine or the entity) and their names as the person saw them. | The promise is a power cut handled while the internet and the AI are gone. A short list keeps what runs unseen small and easy to read on the card. |
| DAU-02 | **It runs the way the assistant would call it, from the box.** The call goes through the person's own connection (`executeConnectionCall`: the Servers connection's `server_power` and `guest_power`, Home Assistant's `request` tool posting to `/api/services/<domain>/<service>`), as the burrow's assistant, with the same limits, settings, signed lines and Done recently. The limits the person set on the tool (`limitsProblem`) are checked when the step is planned and again just before the call: an action outside them isn't sent, and the step says why. No model and no outside service is asked; it works with the internet down. | One path for every change to a connected thing: the person's limits and Off still hold, and the history reads the same. |
| DAU-03 | **Anything destructive or about safety is refused.** Locks, alarms, sirens, valves, garages, gates and doors (Home Assistant's sensitive domains and words), Home Assistant scenes and scripts, deleting, unlocking, and any action not on the list are refused while drafting, in plain words that say what it can do instead. A scene or script step an automation saved before they were refused still runs, but asks on the approval card each time (`directActionAsksEachTime`) and its line on the automation's page says so, and the sensitive words still refuse it. Starting a server that is off isn't offered (no Wake-on-LAN yet). | Doing these without a person's fresh yes is never wanted; a refusal while drafting is clearer than a run that fails later. A scene or a script runs whatever is inside it (it can disarm an alarm or open a door), which no check here can see; the saved ones keep working without ever acting unattended. |
| DAU-04 | **Turning it on is the yes; the person's own rules still ask.** The plan card shows each step in plain words (“Shut down nas-01 — runs on this Whombat right away, without AI”) and turning the plan on is the yes for exactly those actions. Those words name what the step really acts on: when the plan is made and when a version is published, Whombat replaces the names the assistant wrote with the ones it reads itself (the server's name, the machine's from the hosts service, Home Assistant's label and the entity's friendly name, `withRealNames`), says the id where it can't read one, and refuses a machine or an entity that isn't there; each run, approval card and line uses the names known then (`withNames`), so an automation saved under another name says the real one. What the person's settings ask about still asks, on the usual approval card, for that try only: a server set to “Ask me first”, a power action on the server this Whombat runs on, a tool set to Ask. A test run (“Try it”) asks on the same card before every action, and goes on after the answer. The card's proposal carries where the call goes and as whom (`callTarget`); before the yes runs, Whombat checks again that the same action, under the same names and to the same destination, can still run (`approval-guard.ts`), and the step sends nothing when the connection went elsewhere since the yes. | The plan card already shows the action; a second card each time would make a safety automation useless at night. The person's standing rules aren't overruled by an automation. A try is to see what happens, not to switch a server off by surprise; asking keeps it the real run, with the person's yes. A yes is for the thing and the place the card named: the assistant's own words, or a connection moved after the card, must never stand in for them. |
| DAU-05 | **Already so is a quiet no-op.** Just before acting Whombat reads the thing: a light already in the state asked, a machine the hosts service finds already stopped or running. Then nothing is sent and the step says so (“Porch light was already off at 21:14, so nothing was done.”). A server the hosts service can't reach is left alone and isn't counted as done: the step says it couldn't be reached (“Couldn’t reach nas-01 at 21:14, so nothing was sent to it.”) and is skipped or fails, as `otherwise` says. The one exception is a shutdown Whombat was in the middle of when it stopped: done again after the restart, a server that is off now is that shutdown, and the step is done. Where Whombat can't tell, it acts: doing it twice does no harm. | A power cut that lasts long, or a sensor that flaps, mustn't send the same command again and again. A server that can't be reached may be off or only cut off; saying it was off would claim what Whombat doesn't know. |
| DAU-06 | **One line says what happened.** A step's result is one sentence with the time (“Shut down nas-01 at 21:14 — it’s switching off.”, “Couldn’t shut down nas-01: …”), on the run page, the automation's page and in `{{steps.<id>.text}}` for a message. An automation whose steps only act posts nothing in Chat, and its card says so: its runs are on its page. | People read what their automation did without opening details. |
| DAU-07 | **Failures and crashes.** A server's or a machine's power counts only once the hosts service says how the action ended (`action.finished`, listened for from before the call, for up to two minutes, `listenForPowerFinish`): the agent saying no (switched off on that server, or it couldn't) fails the step in plain words, and no word in time says it may not have happened. `otherwise: skip` lets the next steps go on when one thing can't be reached or refused; `fail` stops the run. After an uncertain end (Whombat stopped mid-action, or the call didn't answer in time) only an action that comes out the same done twice is done again (`directActionRepeatable`): switching off, stopping and shutting down, a light or switch on, a machine started, as Whombat finds them already so first. A restart, a scene or a script isn't: the step is `uncertain` and a person is told in one sentence that it may not have happened. | A power cut must shut down every server it can, and a server must never restart twice, or a script run twice, by accident. The hub accepting an action isn't the server doing it: an agent switched off for power, or a shutdown that failed, mustn't read as done. |
| DAU-08 | **A power cut is critical.** The hosts service raises “Running on battery” as critical once a UPS has been on battery for 30 seconds, so the server's dot turns red and Whombat opens a problem automations can start on. An almost empty battery is a critical alert of its own (“{name}’s battery is almost empty”), so it comes through even after the power cut was ignored. Both start on: power is out now and data is at risk. This is a change in the hub's rules only; the agents don't change. **Supersedes MON-96.** | Before, being on battery was amber and made no incident, so “on battery for 10 minutes” could never start an automation. |
| DAU-09 | **“When the UPS is on battery for 10 minutes”** is the existing thing trigger on the server's `host.ups.on_battery` check, `problem` with `forMinutes`; “when the power is back” is `back` on the same check. Its plan card and run page say it in those words. | No second trigger for what incidents already carry. |
| DAU-10 | **A ready-made power cut automation.** “When the power goes out, shut down my servers safely” (`powerCutDefinition`): after the minutes the person chooses (10 unless they say otherwise), it shuts down the other servers first, the one with the UPS last, each skipped when it can't be reached, then tells the person in one message. `automation_read` gives it, with the servers that report a UPS (`upsServers`), and the assistant offers it where a UPS is seen; it is never made unasked. The server this Whombat runs on isn't in it. | The most common wish behind MON-11, ready to say yes to; shutting the box's own server down would stop the rest. |
| DAU-11 | **Home Assistant starts automations** (`home_state`): an entity changes to a state, optionally only from a state, optionally only once it has stayed so for some minutes. Whombat follows only the entities live automations name, over Home Assistant's own socket (`subscribe_entities` with those entity ids, one per connection), and signs only changes into or out of a named state (`home.state_changed`, by the Smart home signer, with Home Assistant's `last_changed`). A sensor that flaps signs at most 20 changes in 10 minutes. A change Whombat only hears of when it follows again (Home Assistant was away) is signed only when its own `last_changed` is under two minutes old by Home Assistant's own clock (the time its answer to the socket says, `clockAheadMs`; none said: no such change is signed), as Protect's sightings; what Whombat knew of an entity it stops following, or that Home Assistant removed or no longer lists when the socket starts, is forgotten. | Data stays on the box and nothing is followed for nobody. Signing keeps triggers on the one event path every trigger uses. A door opened during a two-hour outage is no news at reconnect, also when Home Assistant's clock runs ahead of the box's, and an entity followed again starts from what it is now, not from a state long gone. |
| DAU-12 | **A state that must hold waits durably.** A change that matches a trigger with minutes keeps a wait (`automation_waits`, one per automation and entity) until its time; any later change of that entity ends it. At its time the state must still be the trigger's, and Home Assistant's `last_changed` must still be the change's that started the wait (both Home Assistant's own times, so no two clocks are compared); while Whombat can't tell (Home Assistant away), it asks again each minute for an hour. An entity Home Assistant removed ends the wait without a start. Each stretch of a state starts at most one run. | Survives restarts, and a leak sensor that dried in between starts nothing, also when that went unseen (Home Assistant away, or a flapping sensor's unsigned changes). |
| DAU-13 | **UniFi Protect starts automations** (`protect`): the doorbell rings, a camera sees a person, vehicle, animal or package, or hears smoke, CO, glass breaking or a siren, from any camera or one. Taken from the event stream Whombat already follows, signed once per sighting (`protect.detected`) only for connections a live automation listens to, and only while fresh (two minutes). | A ring an hour late is no ring. |
| DAU-14 | **A cooldown.** `limits.cooldownMinutes` (0 to 1440): while an automation's last run is younger than that, a new start makes no run. Automations started by Home Assistant or Protect have 10 minutes unless they say otherwise; others have none. The plan card's limits say it. | A doorbell pressed five times, or a sensor that flaps, starts one run. |
| DAU-15 | **Once per incident.** A thing trigger still starts once per incident per automation, however long the power cut lasts. | No loop while the UPS stays on battery. |
| DAU-16 | **Quiet hushes news, not safety.** An automation that acts on a UPS power cut runs even while its server is kept quiet. In any run that acts without AI, a message is left out (“Kept quiet: …”) while the thing that started it is kept quiet and no step did anything yet; what it did is always said. Other automations started by a thing that is kept quiet still don't start. | Keeping the NAS quiet while working on it mustn't stop the shutdown that saves it, but news about it can wait. |
| DAU-17 | **The assistant knows all of it.** `automation_read` lists the Home Assistant and Protect connections a trigger can name (`homeConnections`) and the UPS servers with a ready power cut definition (`upsServers`); the authoring guide teaches `run_action`, `home_state`, `protect`, cooldowns and the power cut, and what is refused. | Automations are made only by talking (AT-01). |
| DAU-18 | **Older apps and older releases.** Session protocol minor 22: an app below it gets such an automation without its definition and without the `act` tag, a Home Assistant or Protect run's trigger as a message and a `run_action` step as an earlier step (`unknown` for an app from before mail automations, which has no fallback of its own). Migration `0047_direct_automations` (`automation_waits`) marks the first release that runs them: until the release the box would go back to knows it, they aren't made, turned on or run (“Automations that act by themselves or start on Home Assistant or UniFi Protect come with the next update.”) and nothing in Home Assistant or Protect is followed for them. | The release before can't read these definitions and would run what it can't show. |
| DAU-19 | **Left out:** installing app updates as an action, Windows servers, starting a server that is off, locks, alarms and doors, and acting on things other than servers, their machines and Home Assistant. | Not in this part of the build, or never without a fresh yes (DAU-03). |
