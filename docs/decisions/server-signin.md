# Add a server by signing in once (2026-10-18)

John, 2026-10-18 (main checkout): “We need an easy way to install a whombat agent to a server, for example by logging in
once via ssh or a very simple command (one liner). … What do you recommend.” Recommendation given (Whombat installs
the agent over SSH after one sign-in, every command pre-approved with its control level, the assistant can ask for it
in chat, the command stays as the fallback), then “Yes”. Before this, **Add a server** (ONE-15) showed a `curl … | sudo
sh` command: you needed a terminal on the server, pressed “Add it” afterwards, and went back over SSH for `whombat-agent
allow …` to give Whombat any control (The Titan and BlackBox both needed that second trip). The build brief is
`docs/implementation/server-signin/assignment.md`.

| # | Decision | Why |
|---|---|---|
| SI-01 | **Add a server has two ways in: “Sign in once” (the default) and “Run a command”**, under one choice of what Whombat may do. Owners only (ONE-DH05), on the web and on the phone. | Most people have the server's password, not a terminal on it; the command stays for servers Whombat can't sign in to. |
| SI-02 | **Sign in once**: address (host name or IP, `:port` optional, 22 by default), user name (`root` by default) and the password — or a key from the owner's own Vault, with the password only if `sudo` asks for one. Whombat's server signs in over SSH from the box, installs the agent as root (directly as root, else through `sudo`), waits for the agent's first report and says so step by step: Signing in · Installing Whombat’s agent · Waiting for its first report · Ready. | One sign-in, no terminal; the same installer as the command, so both paths behave the same. |
| SI-03 | **The password is used once and forgotten.** It lives in the server's memory only while the SSH steps run, goes to `sudo` on stdin (never on a command line), and is never stored, logged, put in a receipt (`secret` op), an audit line, a change record or anything a model sees. The enrollment token goes on stdin too. | “Used once, then forgotten” is what the dialog promises. |
| SI-04 | **First contact trusts the server's key and shows it** (OpenSSH's `accept-new`): “First time on this server: it showed key SHA256:…”. When the owner's Vault already knows that address with a trusted key, the key must match, else nothing is sent (“pve-03 showed a different key than the one your Vault trusts …”). | Nobody can check a fingerprint on first contact in this flow; refusing would just add a click. A known key is still enforced. |
| SI-05 | **Where Whombat may sign in**: the Vault's SSH destination rules (VT-S06, LN-01/02): any private address while the local network is open, public addresses only on the SSH ports, never this Whombat, loopback, link-local or metadata. | The same rules as every other SSH Whombat makes. |
| SI-06 | **What Whombat may do is chosen up front, and set on both sides at once**: **Watch only** (the agent's defaults: read-only checks on), **Restart and consoles** (consoles, guest power, read-only checks), **Full control** (also guest editing and creating, a shell on the server, restarting the server: every switch). The installer sets the agent's own lock (`install.sh --control <level>`, visible in the command) and the hosts service sets its switches when it approves. **Full control is the default**: Whombat's own changes still go through keys, tiers and approvals, and the owner can lower it any time. | One trip instead of two; the second lock stays on the server and is written by the installer the owner ran. |
| SI-07 | **Every enrollment Whombat makes is pre-approved** (both ways in): the hosts service adds the server the moment the agent asks, named after its host name (or the name given), with the chosen level. A name that is taken gets `-2`, `-3`, … (“Added as pve-03-2. An older pve-03 isn’t reporting; remove it if it’s the same server.”), never a takeover of the existing server. “Waiting for you” stays for commands made before this change. | The owner made the token for one server, minutes ago; approving it again was a formality, and waiting would leave the installer hanging. A one-use, one-hour token used by a stranger only adds a server that reports data, visibly; taking over an existing server's identity on a self-reported machine id would be worse. |
| SI-08 | **A server that already runs Whombat's agent is updated in place**: the installer keeps its identity, sets the chosen level, and Whombat sets the switches on its side (“pve-03 was already added. Updated its agent and set Full control.”). A server whose agent reports to another Whombat is left alone (“This server reports to another Whombat. Remove its agent there first.”). The same CA means the same Whombat, so a changed box address re-points the agent. | Re-running is the natural fix for an old agent; taking a server from another Whombat must be deliberate. |
| SI-09 | **Leaving a Vault key on the server is opt-in** (off by default): “Leave a Vault key on it, so Whombat can sign in later without a password”, with the owner's SSH key to use or “Make a new key” (an ed25519 key named “Servers”). Whombat adds the public key to the user's `~/.ssh/authorized_keys` once and adds the server to that Vault entry with the key it showed, trusted. | A lasting credential on a server is a choice; with the agent installed Whombat doesn't need SSH for its own work. |
| SI-10 | **Superseded in part by one-person.md OP-S07**: the card and the person typing the password stand; there is no member to refuse. **The assistant can start it in chat but never signs in itself.** The Servers tool `server_add` (address, optional user, level and name) puts a card in the conversation, “Add 10.100.0.40 as a server”, whose button opens Add a server filled in; the owner types the password there and the model never sees it. A member who isn't an owner is told only owners add servers. | Installing as root on a new machine is a person's step; the card makes it one tap on the phone. |
| SI-11 | *Amended by connect-in-chat.md CIC-30…CIC-32: a failure ends in one plain card with the one step that helps (the one line to run, Trust the new one, Try again).* **Failures in plain words with a way on**: wrong password or key, `sudo` wants a password, the user may not use `sudo`, the server can't reach this Whombat (“pve-03 can’t reach this Whombat at 10.100.1.160:8443. Is it on another network?”), neither curl nor wget, not Linux / an unknown init system, timed out. The installer's last lines sit under “More detail”, with the password and token removed. | The person can act on each without reading a log. |
| SI-12 | **The phone gets Add a server** (reverses AP-1367): the same two ways in and Waiting for you, opened from Servers and from the assistant's card. | Sign in once makes adding a server something you can do from the phone. |
| SI-13 | *Superseded in part by macos-servers.md MAC-01, MAC-17: Macs are added (macOS 13 and later).* **Not now**: servers that can't reach the box (the box's own Incus host on macvlan, off-site servers) — a later change lets agents dial in through the relay; Windows and macOS (the agent is Linux only); installing through a jump host. | Same reach as the command today; the relay route is a bigger change of its own. |
