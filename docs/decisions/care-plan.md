# A care plan when a server is added, and quiet hours for changes (CPL)

Part of the “effortless” work of 2026-10-30 for John (stream care-plan; the review's flows.md Journey 4.1–4.3 and 5.1,
Direction rule 4, Top 10 #7). Protection and upkeep were opt-in, server by server and machine by machine, through
dialogs; the hints saying so filled John's Worth a look. Now Whombat proposes them once, as one yes, when a server is
added, with the dialogs' own defaults, and older servers' hints get the same plan. Decided for the stream, and recorded
here: a new server's updates are **proposed** in its care plan, never installed unasked; the server this Whombat runs on
keeps asking for its own changes; temporary machines (server-pages.md SPG-04) are never in a plan.

Contracts (additive): `ChangeWindow`, `careSteps` and its helpers in `@whombat/core` (`domain/care-plan.ts`,
`automations/care.ts`), `LookDispatchContext.care`, `DispatchContext.changeWindow`, `LookReportInput.care`,
`LookPlanView.care`, `changeWindow.get` and `changeWindow.set` (`ChangeWindowView`). Migration `0018_care_plan`. It
changes ONE-10, HDL-11, HDL-13 and SWU-15 (marked there).

## What happens

| # | Decision | Why |
|---|---|---|
| CPL-01 | **A new server gets one care plan, once.** When a server Whombat didn't know first reports (it is Ready), the assistant gets one turn in the server's thread of the person's Chat (a new thread titled by the server the first time): it reads what the server is and proposes Whombat's defaults that fit as one `look_plan` card, “Here’s how I’ll look after pve-01:”, with Go ahead and Change something. One server per minute's pass, and only while a turn of the person's could run, so a plan waits for the AI rather than failing. Once per server (`server_cares`). | flows.md 4.1: the decision becomes one yes, at the moment the person is thinking about the server. |
| CPL-02 | **It is handle-it's plan card, not a sibling.** The mechanics are the same — steps with defaults chosen, one Go ahead for exactly those steps, Change something as a reply, the turn's report to Done today — so the plan rides on a research row of its own (`care:server:<id>`, `care.new`) beside the server's looks. Only the card's head differs. | One card a person learns once; a key of its own keeps it from colliding with a problem on the same server. |
| CPL-03 | **The defaults are the dialogs' own** (`careSteps`): Proxmox, every machine in a nightly backup plan an hour before the quiet hours (02:00), to the Backup Server or else the first storage that takes backups, keeping the newest 7; Incus, a daily snapshot of every long-lived machine (the `default` project's) kept 7 days; QEMU/KVM machines, a backup every Sunday at 02:00; every Linux server but Unraid, system updates on Sundays at the quiet hours' start, restarting only before they end; Docker Compose apps, “Update your apps on Sunday night” (an automation; changed by app-updates.md APU-07), and where no app was started with Compose, “Tell you when apps have updates” (Whombat's helper does that already). At most six steps. | Backups run before anything changes; the person reads plain lines (“Back up all 6 machines every night at 02:00 to pbs-01, keeping a week”), never a form. |
| CPL-04 | **Temporary machines are never in a plan**, and a temporary server (a CI job's or a leased sandbox with Whombat's helper on it) gets no plan. A Proxmox server with temporary machines on it gets a backup plan of the person's own machines rather than every guest. Core owns the rule now (`isTemporaryGuest`, `isTemporaryServer`); the pages use it from there. | SPG-04's machines come and go by themselves; a plan for them would back up throwaway builds. |
| CPL-05 | **Updates are proposed, never installed unasked.** A new server's updates are a step of its plan; nothing installs before the person's Go ahead. The server this Whombat runs on keeps asking: its line reads “Ask you on Sundays at 03:00 before installing its updates”, its install asks as always (SA-10) and its automation never restarts it. It gets its plan once, whatever id it comes back with. | The decision John was to be asked (flows.md “Decisions to ask John for”), taken the careful way: a yes once, in the plan, rather than a default. |
| CPL-06 | **Whombat writes the automations, never the assistant.** Weekly updates and weekly QEMU/KVM backups are automations (a schedule trigger and one agent step) that Whombat writes from the step with the quiet hours of that moment. Go ahead turns them on as the person, in the same commit as the go-ahead, and the `look_fix` turn reads that they are on; the rest of the steps the assistant takes with its tools. A server's care automations are written down, so a later plan doesn't offer them again (one deleted is offered again). | The card's line and what runs are the same thing, so one press can publish it; the agent can never publish (AT-*). |
| CPL-07 | **Older servers get the same plan, through the same research.** A server look whose lines include missing backups, snapshots or waiting updates (`guest.no_backup_job`, `incus.no_snapshots`, `libvirt.no_backup`, `system.updates`, `docker.image_updates`) is offered the care plan's steps when its research begins (by itself or *Ask {assistant} to handle these*); the turn names the ones that answer those lines in `look_report`'s `care` and Whombat writes them in its words. While a server's care plan waits or is carried out, a look made only of such lines is the plan's: nothing new starts on it and *Ask {assistant} to handle these* returns that plan. | flows.md 4.2: no second path; the research turn is taught, the card is the same. |
| CPL-08 | **A care plan isn't a look.** It stays while it waits though nothing needs a look, ends 15 minutes after it is done (its card stays done), when its turns gave up, or when its server left; it never counts against the day's researches; a real problem on the server is looked into as before, in the same thread. A waiting plan pushes once: “Here’s how I’d look after pve-01: 3 steps, ready for your OK.” | The plan is the person's to answer when they like; problems still come first. |
| CPL-09 | **Servers from before are known, not planned.** A Whombat from before care plans writes its servers down as known on its first read (`care_baseline_due`, set by the migration); they keep their hints, which CPL-07 answers. A new Whombat starts with none, so every server it gets is new. | Twenty uninvited plan cards on John's Home would be noise. |
| CPL-10 | **One change window: “Quiet hours for changes”**, per Whombat, 03:00–05:00 in its time zone until the person moves it (start and end differ, and may cross midnight; the control offers half hours). Read by anyone here, moved by the person, signed (`care.window_set`, with the times). The care plan's schedules use it, an approval's *Tonight* runs at its start (Needs you's `at` and the chat card), and the agent is told it in every turn of the person's: changes that can wait go in it, and it says when. | flows.md 4.3: one setting instead of a fixed 03:00 in several places. |
| CPL-11 | **The control is a small section of its own** (`apps/web/src/features/care/QuietHoursSection.tsx`, “CHANGES · Quiet hours for changes”, From · To, saved at once); the settings work places it in This Whombat. A Whombat without the ops shows nothing and keeps 03:00. | Settings is regrouped by another stream at the same time. |
| CPL-12 | **The Automations page suggests from what is connected** (`automationIdeas`): mail (“Each morning, sum up my new mail”), a server by name, Home Assistant, storage, photos, media, the network and code, then everyday ideas; three at most, each something a schedule can do. The phone has no examples (only “Tell {assistant}…”), so nothing changes there. | flows.md 5.1: the fixed chips were a developer's. |
| CPL-13 | **Not now:** the box's own updates in the window (the appliance's, outside this repository), a phone control for the quiet hours and phone ideas, keeping a weekly automation silent when there was nothing to install, proposing an automation after repeated snoozes (5.1's second half) and a backup destination for the box (4.4). | Smallest useful first. |

## Server details

| # | Detail | Why |
|---|---|---|
| CPL-S01 | Migration `0018_care_plan` (expand): `server_cares` (one row per server: `known` or `offered`, whether it is this Whombat's own, the research, the care automations by step), `look_researches.care` (the steps a research may offer, `new` for a new server's plan), `burrows.change_window_start`/`_end` (null: the default) and `care_baseline_due` (true on Whombats from before). | No hosts-service change: Whombat keeps what it offered. |
| CPL-S02 | The watcher is a home job of its own (`home.care`, every minute; `care/watch.ts`). It reads the fleet and, for the chosen server, its page (guests, the storages whose `content_types` say `backup`) outside any commit, then commits `care.start` as the agent (`licence: agentTurn`). `care.baseline` and `care.known` write servers down. Events carry ids and counts only. | All writes through the pipeline; reading the hosts service never holds the lock. |
| CPL-S03 | A care step's row keeps the card's line, what it means for the turn, its care id and, for an automation, its recipe (kind, server, guests); `look.report` keeps only the ids the turn was offered, in the order it named them, ahead of its own steps. `look.fix` builds and publishes each recipe's automation (`insertAutomation`, `publishVersion`; no keys needed) before waking the `look_fix` turn, and replaces the recipe with “Whombat turned this on…”, so a step offered again never makes a second automation. | HDL-05's one press, with the automations Whombat's. |
| CPL-S04 | The turn's context carries the care offer (`LookDispatchContext.care`) in `look` turns and the person's replies while the plan waits, never in `look_fix`; every person's turn carries the quiet hours (`DispatchContext.changeWindow`). | The prompt can name the defaults and the window without guessing. |
