# Automations by talking to the agent (AT-01…AT-20)

John, 2026-10-28 (main checkout): “make automations only be configurable by talking to the agent. So instead of
configuring a trigger for example, we should let the agent decide what the trigger should be. The agent should ask for
more information if needed … and when I talk about an automation it should give its thoughts on how to build the
automation and we can simply accept, deny or change it by talking to the agent.” He saw the mockup (a plan card in
Chat, a change card that lists what changes, an Automations page without an editor) and said “Yes, implement this
fully.”

The engine, definitions, keys, approvals and runs stay as they are (`bp-automations.md`, `automation-recipes.md`,
`report-trackers.md`). What changes is who writes an automation and how the person agrees to it. App side:
`docs/app/decisions/automation-chat.md`.

Supersedes `bp-automations.md` BP-C13 (the editor UI) and BP-C22's agent half (an agent drafted only until the first
publish), and the simple form, templates, step editor, JSON view, import and export in the apps (`automation-recipes.md`
AR-01's form, AP-966…AP-985). The server's old endpoints stay until the next contracts major so older apps keep working.

| # | Decision | Why |
|---|---|---|
| AT-01 | **Automations are made and changed only by talking to the agent.** The apps have no form, template picker, step editor, JSON view, import or export. “New automation” and the field on the Automations page start a Chat thread with the person's words. | John: configure by talking; the agent decides the trigger. |
| AT-02 | **A plan is a row of its own** (`automation_plans`, migration 0015, expand): the definition and its hash, the keys turning it on gives, the live version it changes and the keys the automation held then, the agent's “How I thought about it” (≤ 4 points of ≤ 300 characters), the card's conversation, thread and message, and its status: `waiting`, `accepted`, `declined`, `replaced`. At most one waits per automation (a partial unique index). | What the person agrees to must stay exactly what the card showed, whatever the draft becomes later; the diff of a change needs the version it was made from. |
| AT-03 | **The agent proposes with `draft_automation`** (contracts 3.9; the name stays): a `recipe` (one agent step; Whombat adds the tested steps, `recipeFile`) or a `definition`, never both; `name`, a one-sentence `description`, `thinking`, `asks` (keys that should wait for a yes each time) and an optional `message` above the card. A proposal with problems gets them back and posts nothing, so the person only ever sees a plan that can run. | A recipe keeps the well-tested chains (assess → fix → review → pull request → merge) out of the agent's hands; a definition covers the rest. |
| AT-04 | **The plan is posted as an `automation_plan` card in the turn's thread**, by the agent, server-made and stored by reference (`{kind, planId}`), resolved on read for every reader alike (one person). Its text is the agent's `message`, else “Here’s how I’d set it up…” / “Here’s the change…”. It wakes nobody. | The schedule card's pattern; an older app shows the text. |
| AT-05 | **A newer plan for the same automation replaces the waiting one**: the old row becomes `replaced` and its card folds to “Replaced by a newer plan”. “Change it by talking” is just this. | One card to decide on at a time. |
| AT-06 | **The card's sections are written by Whombat from the definition** (`planSections` in core), never by the agent: WHEN (each trigger), the agent's name (each agent step's name or first line, with what it reads, changes or reports), ASKS YOU (approval steps and keys at Asks; else “Nothing: it only reads and tells you” or “Nothing: it does all of this on its own”), POSTS (the Chat thread, then everything that leaves Whombat: comments, pull requests, merges, the tracker, calls) and LIMIT. Templates read as stand-ins (`#N`, `…`). The name, the description and “How I thought about it” are the agent's words, and what the agent is asked in each step shows word for word, folded. | The card must say what will run even when the agent is wrong or prompt-injected. |
| AT-07 | **A change to a live automation lists what changes** (`planChanges`): the lines it adds and removes, and each agent step whose words changed. The live version keeps running until the person turns the change on. | John's “change it by talking”; nothing changes behind a running automation's back. |
| AT-08 | **Turn it on** (`automations.acceptPlan`, the person, “Change the agent and its keys”): only the waiting plan, and only while the automation is still at the version the plan was made from; the definition is checked again and must hash to the plan's; then the automation takes the plan's name and description, its keys are replaced by the plan's, and the definition is published as the next version and switched on (the usual `publishVersion`). Turning on always switches on. | Publishing binds to what was reviewed (BP-C21); the card's changes must still be true. |
| AT-09 | **Not now** (`automations.declinePlan`, the person): the plan is set aside; a never-published automation is deleted with it (as Delete); a live one keeps running and its draft is cleared. The agent isn't woken: the person replies when they want something else. | Nothing lingers from a plan nobody wanted. |
| AT-10 | **The keys a plan gives are what its steps need** (`definitionGrants`): Comment for `github_comment`, Open pull requests for `open_pull_request`, both merge keys for `merge_pull_request`, Update and Reply for the tracker steps, Message outside for a call, each limited to the repositories and connections those steps name, at Can — Asks for the keys in `asks`. A call never asks (an approval step before it does, BP-C11). The card lists the asking ones; the rest it does on its own, as POSTS says. | The person agrees to the keys with the card; there is no Keys tab any more. |
| AT-11 | **The agent asks only what changes what runs**: which repository or connection, how often, and whether it may act outside Chat; one question at a time, with quick replies; sensible defaults for the rest, named in “How I thought about it”. Fixing, merging and replying to customers only when the person asked for them (the served description of `draft_automation`). | John: “ask for more information if needed”. |
| AT-12 | **`Automation.talk` and `Automation.waitingPlanId`** (contracts 3.9): the thread of the latest plan (“Talk about it”) and the plan waiting for a yes (“Waiting for you”). | The list and the detail open the conversation the automation lives in. |
| AT-13 | **Try it runs the plan once** as the existing test run of the draft (`automations.runNow {test: true}`), on the newest issue, pull request or report when something like that starts it (`tryIt: 'sample'`), else at once. The draft is always the waiting plan's definition. | A plan the person can see working before it is on. |
| AT-14 | **Only the person's own turns propose or read automations.** `draft_automation` and `automation_read` refuse, and aren't served in, an automation's own step (trigger `automation`), a Feedback assessment and any turn for nobody. | What an issue, a report or a stranger writes must never change an automation. |
| AT-15 | **The agent may propose changes to any of the person's automations** (one person), including live ones; turning on stays the person's. | The rule that an agent's drafting ended at the first publish (BP-C22) made “change it by talking” impossible; the plan card is now the gate. |
| AT-16 | **`automation_read`** lists the person's automations (id, name, on/off/waiting, description, Whombat's summary, last run) with the writing guide (`AUTOMATION_AUTHORING_GUIDE`), or one in full (its live definition, the waiting plan's and its keys). | The guide reaches the agent only when it builds one, so the tools served on every turn stay short (prompt-efficiency.md). |
| AT-17 | **The agent's own schedules show on the Automations page too**, as “only tells you” rows (Pause, Resume, Remove), and stay what they are: made with `schedule`, on at once. Something that only tells the person in Chat starts at once; anything triggered by events or acting outside Chat waits for a yes on a plan. | One list of what happens on its own, without making a reminder ask for permission. |
| AT-18 | **On/Off, Run now and Delete never need the agent**, on the web and the phone. | An automation must stop even when the AI is signed out or out of credit. |
| AT-19 | **Contracts 3.9.0**, session protocol minor 3: the `automation_plan` card, `AutomationPlanView`, `Automation.talk` and `waitingPlanId`, `automations.acceptPlan` / `declinePlan`, `draft_automation`'s new input and `automation_read`. Additive: an older app shows the card's text and keeps its old screens. | A box sends the card only as a new kind; older apps ignore unknown cards. |
| AT-20 | **Events**: `automation.plan_proposed`, `automation.plan_accepted`, `automation.plan_declined` (System), with the automation and plan ids. | Every decision is signed, as publishing is. |
| AT-21 | **`automation_read` lists the Whombat's tracker connections** (`trackerConnections`: id, label, address, working) and the guide says a tracker trigger names one of them, none meaning the person connects the tracker first in Settings → Connections. Additive output; no contracts release (only this repository's runtime reads it). | An agent's own connections leave the tracker out (report-trackers.md TA-02), so once automations were made only by talking nobody could name a tracker connection: Dusty answered “This Whombat has no tracker connection” with one connected (John, 2026-10-30). |
| AT-22 | **How a tracker automation reads code, in the guide**: a tracker report's steps reach no connection but T3 Code (outsiders-turns.md OT-11); where code work goes to T3 Code (t3code.md T3-15) the assessing step hands looking into the code to a T3 Code thread, and without T3 Code `repo` gives it a read-only copy. | Dusty writes the plan from the guide: it must not promise a step what the step can't do, as its first tracker plan did. |
| AT-23 | **An automation's step finishes its work in its own turn.** It isn't served `schedule`, and where code work goes to T3 Code its preface says to wait for the thread however long it takes and reply once it is done (`persona/code.ts`), as a customer's report does (outsiders-turns.md OT-11). | The step's reply is what the automation goes on with. Run #5 of John's “Keep Whombat in step with Fusebox” (2026-10-31) scheduled a check-back and replied “T3 Code is reading them”: the step ended on that, and the check-back then opened and merged the pull request outside the run. |
| AT-24 | **The guide says what `verdict` does**: only for a step that reviews work, whose reply must start with “Approve” or “Changes needed”; any other reply fails the step. | Dusty marked the Fusebox automation's working step as a review (the card's “Says whether it’s ready”), so its report failed the run. |
| AT-25 | **The guide says how long a step may take**: an agent step stops as failed after 60 minutes unless it gives `timeoutMinutes` (at most 1,440), so a step that waits for long work in T3 Code gives enough. | John's “The tracker nightly test and fix” (2026-11-02) waited in one step for four T3 Code threads that test and fix for up to 90 minutes, and was stopped at 60 with all four done, before its report; the guide never named the limit. |
