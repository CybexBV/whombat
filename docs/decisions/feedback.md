# Whombat Feedback — embeddable bug-report and feature-request widget

Workstream `feedback` (2026-09-25). A website owner configures a **feedback integration** in Whombat and pastes
one `<script>` into their site. Visitors report bugs and request features without leaving it; Whombat keeps
each report durably, posts it as one thread in the configured channel and queues a bounded, read-only
assessment by the configured agent. Development is only ever started by a person's approval.

Checklist and status: `docs/implementation/feedback/CHECKLIST.md`. Operator guide: `docs/feedback.md`.

## Non-goals (firm)

No customer accounts, principals, guests or channel members; no customer-facing archive, “My reports”,
status/detail endpoint, conversation, board, voting, roadmap, customer login/SSO; no customer emails,
verification or subscriptions. The reference number is an acknowledgement only: it grants nothing and links
nowhere. Reports and their history are kept **internally** (retention is an explicit internal policy).

> **Superseded in part (2026-09-30, John's request):** visitors may sign in to one site's widget with an emailed code
> and see their reports there with a visitor-facing status, marked “Email verified”
> ([`feedback-reporters.md`](feedback-reporters.md) FR-06 … FR-10). Everything else here still holds.

## Decisions

| # | Decision | Why |
|---|---|---|
| FB-01 | **Module.** `WHOMBAT_FEEDBACK=on\|off` (default `on`). `on` with no integration is inert: every public route answers the same 404 as an unknown site. `off` unregisters `/embed/*` entirely (the public surface only): the internal assessment worker keeps starting queued assessments and settling, timing out and blocking running ones exactly as when `on` (review-2 F8), and reports, Retry and handoffs keep working. Nothing else in Whombat changes behaviour. |
| FB-02 | **One public prefix: `/embed/v1/`.** Loader `widget.js`, iframe document `frame.html`, frame assets `assets/*`, and two JSON endpoints `sites/:site/config` (GET) and `sites/:site/reports` (POST). Nothing else is public; a reverse proxy may expose only `/embed/` to the internet (docs/feedback.md). No chat, login, MCP, runner, admin or automation-webhook route is reachable through it. |
| FB-03 | **Loader + lazily mounted cross-origin iframe.** The loader (plain TS, no framework, IIFE, one global `WhombatFeedback`) renders an optional floating launcher in a closed shadow root styled only through CSSOM/constructable stylesheets (no `unsafe-inline`, no global CSS) and mounts the iframe on first open. The reporting UI (plain TS DOM, no framework) runs inside the iframe on Whombat's origin. |
| FB-04 | **Requests come from the iframe, same-origin.** The iframe calls `/embed/v1/sites/:site/*` on its own origin with `credentials: 'omit'`, so no CORS is needed, the host page needs no `connect-src`, third-party cookies are irrelevant and the operator's Whombat session is never used. Public handlers never call `authenticate()`. A browser `Origin` other than Whombat's own public origin is refused (a site calling the API directly from its page is not the widget). Non-browser callers can forge anything: they are handled by abuse limits, not trusted. |
| FB-05 | **Embedding origin.** The loader passes `parent=<location.origin>` in the frame URL. `frame.html` is served only when `parent` is one of the integration's exact allowed origins, with `Content-Security-Policy: frame-ancestors <that origin>` so the **browser** enforces it; otherwise it is served as an unavailable page with `frame-ancestors 'none'`. The frame cross-checks `location.ancestorOrigins` where the browser has it. `parent` is re-checked against the allowlist on submit. None of this is identity: origin allowlisting is a browser control. Whombat's app shell keeps `X-Frame-Options: DENY` / `frame-ancestors 'none'`; only `frame.html` differs. |
| FB-06 | **Bridge.** `postMessage` with exact target origins in both directions; each side checks `event.origin`, `event.source` (the iframe's `contentWindow` / `window.parent`), the message schema (`wb: 'whombat-feedback/1'`, a type from a closed list) and a per-instance random `instance` nonce passed to the frame in the URL fragment (never sent to the server). Unknown or malformed messages are ignored. |
| FB-07 | **Context is limited and sanitized** (`@whombat/core/feedback/sanitize`, shared by loader, frame and server, which re-sanitizes). Page URL = origin + path only (query and fragment always dropped), id-like path segments (UUIDs, long numbers, long hex/base64-ish tokens, emails) replaced by `:id`, plus the integration's `redactPaths` templates (`/customers/*/invoices/*`). Browser: coarse browser name, language, viewport, time zone. App: `version`, `environment`, `build` if the site sets them. Custom: a flat map of at most 20 scalar values whose keys the integration allowlists (`contextKeys`; none by default). References: at most 5 short diagnostic ids. Never cookies, storage, headers, form contents, DOM, console, network or replay. All of it is **unverified evidence**; nothing in it selects a burrow, channel, repo or agent. *Superseded in part (2026-09-30): the last 10 page views on the site, sanitized like the page URL, are sent as `context.trail` unless switched off ([`feedback-reporters.md`](feedback-reporters.md) FR-04).* |
| FB-08 | **Screenshots** are chosen by the visitor (file input, previewed), never captured. PNG/JPEG only, at most 3 (integration default 3, max 3), each ≤ `maxAttachmentBytes` (default 3 MB, max 8 MB), ≤ 16 megapixels and ≤ 8192 px a side. The server sniffs the bytes, checks the header dimensions **before** decoding, fully decodes (pure JS `pngjs` / `jpeg-js` with memory caps, one at a time in a worker thread, FB-F02) and **re-encodes** (PNG → PNG, JPEG → JPEG q 90), which drops all metadata and any trailing/polyglot payload. SVG, GIF, WebP, HTML, anything else, malformed or decompression-abusive images are refused. Stored through the existing `FileStore` as ordinary attachments on the report's root message, so the existing per-request, membership-checked download route authorizes them. There is no public read route. |
| FB-09 | **Submission** is one JSON POST (screenshots base64) so acceptance is atomic: no public upload slots, no orphans. Strict Zod (`z.strictObject`): unknown fields — `channelId`, `agentId`, `burrow`, `repo`, `approved`… — are a 400. Body ceiling per integration (derived from its attachment limits, hard cap 32 MiB), checked from `Content-Length` before the body is read. |
| FB-10 | **Idempotency.** The widget generates `submissionId` (128-bit random, base64url) once per draft and keeps it across retries. Unique `(integration_id, submission_id)`; `payload_hash` = sha256 of the canonical normalized payload (screenshots by their sha256). Same id + same hash → the same minimal receipt (200). Same id + different hash → 409 `conflict` with no detail. No lookup ever returns more than the receipt. |
| FB-11 | **Receipt**: `{reference, receivedAt}` only, after the transaction commits. Reference `FB-XXXX-XXXX` (Crockford base32, 40 random bits, unique). It is not an id anywhere and opens nothing. |
| FB-12 | **Abuse limits before expensive work**, in this order: module/site lookup (cached 15 s) → Origin check → `Content-Length` vs body cap → an in-flight slot (FB-F03) → in-memory token buckets (global 120/min, per integration `reportsPerHour`, per integration+client IP `perSourcePerHour`; client IP only through `TRUST_PROXY` rules) → structural bounds (FB-F01) → the daily cap, counted before image work (FB-F03) → the image worker (FB-F02) → in the transaction, the durable per-integration `reportsPerDay` count. Bounded assessment queue: per-integration `assessmentsPerDay` and `maxConcurrentAssessments`. |
| FB-13 | **Persistence** (migration `0027_feedback`): `feedback_integrations`, `feedback_reports`, `feedback_assessments` (one row per assessment attempt). A report stores its type, visitor text, optional reporter name/email (unverified metadata), sanitized context, screenshot attachment ids, lifecycle `status`, assessment state/result (kept apart from the visitor's data), and the **intake routing snapshot** `{revision, configHash, channelId, agentId, repoId, projectContext}`. |
| FB-14 | **Signer.** One system principal per burrow, `system: 'feedback'` (name “Feedback”, handle `feedback`), created lazily like GitHub's. It signs report receipt, the root message and assessment queueing. Its signature attests that Whombat received the report and what it did, not who the visitor is. Visitors are never principals, accounts or members; no principal is created per submission. |
| FB-15 | **Atomic intake** (one `pipeline.transact`, burrow lock): report row, root message (author: feedback principal, text `Bug report FB-… · <product>` / `Feature request FB-… · <product>`, card `{kind:'report', reportId}`, `mentions: []`, `dispatch: false`), screenshots attached to it, signed `feedback.report_received` (ids, type, sizes, hashes — never text or contact details, BP-06), and `assessment.state = queued` (or `paused` / `not_configured`). The visitor's words live only in the report row and the card, never in message text, so they cannot mention, trigger keyword automations or be parsed as commands. Automations additionally ignore messages by the feedback principal. |
| FB-16 | **Report card** `kind: 'report'` (stored by reference, resolved on read like plan/run/approval, so status, assessment and redaction are always current). Old clients that don't know the kind still show the root message text. Web renders a card with details on demand (`feedback.reports.get`, membership-checked); Android renders the summary card. |
| FB-17 | **Channel-centred.** One configured channel per integration (a shared `#bugreport` is fine), one thread per report; discussion and the assessment happen in that thread. No helpdesk dashboard. Report detail, status changes, retry and handoff require membership of the report's channel; the integration settings require a burrow owner. |
| FB-18 | **Configuration authority.** Only burrow owners create/edit integrations, and only with a channel they are a member of, an agent that is **already** a member of that channel (never added silently), a repo already switched on in the burrow. The assessment agent must be a hireable, non-personal, non-system agent with `access: guarded` on the Claude or Codex provider (ACP and trusted agents are refused: Whombat can't confine them read-only). Every change is a signed `Keys`-kind event with the revision and config hash; the config is private and server-authoritative. |
| FB-19 | **Disable vs pause.** `intake: disabled` makes the site unknown to the public (same 404); already accepted reports keep their state and queued assessments still run. `assessment: paused` keeps intake open and leaves new and queued reports `paused`; resuming requeues them. |
| FB-20 | **Assessment worker** (`apps/server/src/feedback/assessor.ts`), in the server, restart-safe with `FOR UPDATE SKIP LOCKED` leases like `memory_jobs`. For a queued report within budget it commits, in one transaction: the prompt message in the report thread (feedback principal, `mentions: [agent]`, `dispatch: false`), a `dispatches` row with trigger **`feedback`**, a `feedback_assessments` row and `assessment.state = running`. Before that it **revalidates** against the intake snapshot (never the current config): integration exists, assessment not paused, the configuring owner is still an owner and member of the channel, the agent still exists, is guarded, on Claude/Codex, and a member of the channel, the repo still switched on. Anything revoked → `blocked` with the reason; a person fixes it and presses Retry. |
| FB-21 | **Restricted assessor turn.** For trigger `feedback`: the context carries only the report thread (no channel window, no other reports), the report as delimited untrusted data, the approved project context, and the root message's screenshots; knowledge memory and provider session resume are off. The runner forces a read-only export of the repo's default branch (or no workspace), network off and read-only tools, and refuses trusted/ACP turns. MCP for that dispatch allows only `submit_assessment`, `feedback_similar_reports` (same integration, references + summaries), `read_attachment` (the report's screenshots) and `reply_in_thread` (the report thread only, mentions stripped, never dispatches). Everything else answers “not available while assessing a report”. The agent cannot push, write, open PRs, approve, request approvals, change keys/automations/memory or wake other agents. Code execution only inside the provider's read-only OS sandbox with the scrubbed environment and no network (Codex: reads limited to the turn's directory and the toolchains, FB-F3-01); where that sandbox isn't available the turn is inspect-only and the assessment must say so (`reproduction.status = not_attempted`). |
| FB-22 | **Assessment result** is `submit_assessment` (Zod `FeedbackAssessment`), recorded by `feedback.record_assessment` only for the report's current dispatch. Outcomes: `confirmed_bug`, `likely_bug`, `needs_information`, `duplicate`, `configuration_or_support`, `feature_request`, `insufficient_evidence`, with confidence, uncertainty, reproduction status (`not_attempted`, `attempted_not_reproduced`, `reproduced`, `unknown`), evidence refs (each marked observed vs hypothesis), revision inspected vs reported, severity with rationale, missing information, next action, optional duplicate (must be a report of the same integration) and a feature assessment. `confirmed_bug` needs at least one non-hypothesis evidence item (file/test/observation). The server renders the summary message in the thread from the validated fields; all agent text is displayed as plain text. |
| FB-23 | **Honest failure.** A dispatch that ends without a submitted assessment, fails, is refused (no runner, provider missing) or exceeds `assessmentTimeoutMinutes` sets `failed` with the reason; nothing is fabricated. Retry (channel members; at most 5 attempts per report) requeues. Findings, retries and agent replies never start assessments; only intake and Retry do. |
| FB-24 | **Handoff** (optional): a channel member asks for development on an assessed report; this creates an ordinary Approval (`custom` action `feedback_handoff`, deferred command `feedback.start_handoff`, approvers = burrow owners, binding `{reportId, repoId, commitSha, commitVerified, assessmentHash}` (the exported commit, FB-F2-09)). Only on execution — which the approvals engine re-verifies (action hash, signature) and our guard revalidates (report not redacted, assessment unchanged, repo still on, developer agent still in the channel) — does Whombat post in the thread as the person who asked (the approval's requester) **Whombat's fixed handoff text** (FB-F2-01), mentioning the integration's configured developer agent, whose own keys then govern branches and pushes; the report and the assessment reach that agent only as delimited untrusted data in its dispatch context. Report text never counts as approval. |
| FB-25 | **Retention.** Owners can remove a report's content (`feedback.redact_report`): text, contact details, context and screenshots are cleared and the files unlinked; the row, reference, timestamps, states and the signed history remain (events never held content). Optional `retentionDays` per integration applies the same removal automatically (hourly sweep). |
| FB-26 | **Distribution.** `apps/widget` (`@whombat/widget`) builds with esbuild into `apps/widget/dist/v1/` (`widget.js`, `assets/frame.<hash>.js`, `assets/frame.<hash>.css`, `manifest.json`). The server serves it from `WHOMBAT_WIDGET_DIST`, else `$WHOMBAT_APP_DIR/widget`, else `apps/widget/dist`; `pnpm package` builds and ships it; `whombat start` builds it with the web app. `widget.js` is cached 5 minutes, hashed assets immutable. Public URLs derive from `PUBLIC_URL` (origin only, like the rest of Whombat); the loader derives its base from its own `src`. |

## Endpoint contracts (`@whombat/core/contracts/feedback`)

Public (`/embed/v1`, never authenticated, `FeedbackPublic*` schemas):

- `GET  /embed/v1/widget.js` — the loader.
- `GET  /embed/v1/frame.html?site=<siteId>&parent=<origin>` — iframe document (CSP per FB-05).
- `GET  /embed/v1/assets/<file>` — frame assets.
- `GET  /embed/v1/sites/:site/config?parent=<origin>` → `FeedbackPublicConfig` | 404 `unavailable`.
- `POST /embed/v1/sites/:site/reports` body `FeedbackSubmission` → 201 `FeedbackReceipt` (200 on replay) |
  400 `invalid` | 404 `unavailable` | 409 `conflict` | 413 `too_large` | 415/422 `unsupported_attachment` |
  429 `rate_limited` (+ `retryAfter`). Error body `FeedbackPublicError` `{error: {code, message, fields?, retryAfter?}}`
  with fixed, non-revealing messages.

Internal (`/api/v1`, session; `api.feedback.*`):

- `integrations.list|get|create|update|setIntake|setAssessment` — owners (list/get return `can.manage`).
- `reports.get|setStatus|retryAssessment|requestHandoff|redact` — members of the report's channel (`redact`: owners).

MCP (assessor dispatch only): `submit_assessment`, `feedback_similar_reports`.

## Failure behaviour

| Failure | Behaviour |
|---|---|
| Whombat unreachable from the visitor | Loader never blocks the page; the launcher opens a panel that says it can't reach the service; nothing thrown into the host page. |
| Network error/timeout on submit | The form keeps its content and `submissionId`; Retry resends; the server replays the receipt if it had committed. |
| Crash before commit | Nothing stored; staged files are discarded or swept; the widget's retry creates the report once. |
| Crash after commit, before response | The retry gets the same receipt (FB-10). |
| Runner or provider down | Report stays `queued` → dispatch refused by the runtime's unrunnable sweep → `failed` with the reason; Retry once fixed. |
| Crash between queued and dispatch | Worker lease expires; the next pass starts it (the start transaction is atomic, so no second dispatch). |
| Crash during the turn | The runtime's lease sweep retries the dispatch once, then fails; the assessment becomes `failed`. |
| Config changed after intake | The report keeps its intake snapshot; revalidation fails closed (`blocked`) if the snapshot is no longer authorized. |
| Assessment result invalid | `submit_assessment` returns the validation errors to the agent; if the turn ends without a valid one, `failed`. |

## Security review 1 fixes (`docs/implementation/feedback/review-1.md`)

| # | Decision |
|---|---|
| FB-F01 | **Structural bounds before the schema** (R1-1). A submission body is checked twice before Zod sees it, and refused with 400 `invalid` (`fields: ['body']`, or the known array's name: `attachments`, `context.references`): the raw bytes before `JSON.parse` (nesting ≤ 6, ≤ 2000 structural tokens `[` `{` `,` outside strings; strings skipped with a native `indexOf`), then the parsed value (≤ 6 levels, ≤ 2000 values, ≤ 40 keys an object, arrays ≤ 20 except `attachments` ≤ `FEEDBACK_MAX_ATTACHMENTS` and `context.references` ≤ 5, strings ≤ 10 000 characters except `attachments.<i>.data` ≤ the schema's base64 maximum). Only the first 20 schema issues are mapped to field names. `JSON.parse` itself is bounded by the body cap and the raw scan. The authenticated `/api` JSON parser (1 MiB) is a separate follow-up. |
| FB-F02 | **Screenshots are decoded in a worker thread** (R1-3). One long-lived `worker_threads` worker (`apps/server/src/feedback/image-pool.ts`, module `image-worker.ts`) takes one job at a time with its own heap (`maxOldGenerationSizeMb` 256, `maxYoungGenerationSizeMb` 32); the JPEG decoder's typed arrays sit outside that heap and are bounded by its own cap (512 MB, FB-F04). A job gets 10 s from when the worker starts on it. A job that fails to decode, times out or kills the worker (out of memory, crash) is the image's fault: 422 `unsupported_attachment`, and a stuck or dead worker is replaced for the next job. A worker that can't load is the server's fault: 500 `internal`, logged. Idle, the worker doesn't keep the process alive. The worker's module is found next to the code that starts it: `image-worker.ts` from source (Node's type stripping or tsx), `app/image-worker.mjs` in a release, where it is its own esbuild entry (`scripts/package`, tested by bundling the pool with the release's options and running it with nothing but the two bundles). |
| FB-F03 | **Submissions in flight are bounded, and the daily cap comes before image work** (R1-3). A public submission takes a slot after the `Content-Length` check and before its body is read (and before the token buckets, so a refused one costs no tokens): at most 4 in the process and 2 per integration, else 429 `rate_limited` with `retryAfter: 5`. The slot is released when the response is sent or the connection closes (a client that disconnects mid-body), whichever comes first. A client that trickles its body holds a slot until the connection closes; that is no worse than using up the integration's hourly bucket, which a sender can do anyway, and it affects the intake only, never chat. A submission with screenshots counts the integration's reports of the last 24 hours (indexed) before any image work and gets 429 (`retryAfter: 3600`) at the cap; the count under the burrow lock in the intake transaction stays the authoritative one. |
| FB-F04 | **JPEGs decode up to the advertised 16 MP** (R1-5). `jpeg-js`'s `maxMemoryUsageInMB` is 512 (a 16 MP baseline JPEG with three full-resolution components needs about 340 MB of its accounting, four components about 450 MB), `maxResolutionInMP` stays 16. Its typed arrays live outside the worker's V8 heap (`resourceLimits` doesn't count them), so this cap, not the heap limit, is their bound; the header check refuses anything over `FEEDBACK_IMAGE_MAX_PIXELS` or 8192 px a side before a job reaches the worker. |
| FB-F05 | **`WHOMBAT_FEEDBACK=off` turns off the public surface only** (R1-4): `/embed` isn't registered, but the hourly retention sweep still starts (and the assessment worker keeps running, FB-F2-08), so content stored while the module was on is removed on schedule (FB-25). The `module_off` health warning says so. |
| FB-F06 | **The configuration's authority is whoever saved the settings** (R1-6). `feedback.set_intake` and `feedback.set_assessment` bump `revision` and are signed by the owner who flipped them, but leave `updatedById` and `updatedAt` alone: those name the owner who last saved the settings (create or update, after `validateSettings`), which is what a report's intake snapshot records as `configuredById` and what the `owner_not_member` health check looks at. So pausing and resuming neither takes over nor drops another owner's authority. “Last changed … by …” in the integration's details is therefore the settings' last save; the switches are in the audit log. |
| FB-F07 | **Public `retryAfter` values are fixed** (R1-7): 60 s whenever a token bucket is empty (global, the integration's hourly bucket or per source), 3600 s at the daily cap (counted before image work or in the transaction), 5 s when every in-flight slot is taken (FB-F03). An exact refill time would reveal `reportsPerHour` / `perSourcePerHour` (`3600 / n`), and the time until the daily window frees up would reveal when the integration's oldest report of the day arrived. The widget words these as “in a minute” / “in 60 minutes”. |
| FB-F08 | **A report's project context is for owners** (R1-8). `projectContext` is operator-written guidance for the assessor and, like the integration's settings (FB-17), owner-only: `getReport` (and the report `setReportStatus` / `redactReport` answer with) carries the intake snapshot's `projectContext` for burrow owners and `''` for every other member of the report's channel. The contract doesn't change. The rest of the snapshot (revision, config hash, channel, agent, repository, configuring owner) stays visible to members: it names things they can already see in the channel and the report's history. |
| FB-F09 | **Page-URL redaction catches shorter tokens** (R1-9). Besides UUIDs, numbers of 5+ digits, hex of 16+, anything with `@` or outside `[A-Za-z0-9._~-]` and segments over 64 characters, `looksLikeId` redacts a segment of 12+ characters that mixes letters with at least two digits, and a base64url segment of 16+ characters with a digit or a capital, unless the segment is a slug of words: parts joined by `-` `_` `.` `~`, each lowercase, capitalized or CamelCase, all-caps up to 5 letters, a number up to 4 digits or a short letters-and-digits word (`v2`, `ipv6`, `2fa`). So `/magic-login/Xk9fQ2mZpL7tR4wB`, nanoids and JWT parts become `:id`; `settings`, `billing-v2`, `invoices-2026`, `page-3`, `MyAccountSettings` stay. A token that happens to look like a slug of words is kept: `redactPaths` covers known routes. |
| FB-F10 | **Removing a report's content removes the assessor's words, not people's replies** (review 1 note; corrected by review 3, FB-F3-11). `feedback.redact_report` (by an owner or the retention sweep, FB-25) clears what the visitor sent (the report row, its screenshots and the root message's card) and what the assessor wrote from it: the assessment's free text and the text of every message the assessor posted in the report's thread (`provenance: feedback_assessment`), which becomes “Removed with the report’s content.”. People's replies in the thread stay as they are: Whombat has no message editing or deletion, so a person who quoted the visitor there can't remove it either; owners who need it gone must remove it in the database. |
| FB-F11 | **The card summary reaches channel members by design** (review 1, note). The report card's `summary` (up to 280 characters of the visitor's description) is part of the root message, so it travels in `message.created` / `message.updated` realtime frames and `read_conversation` output to everyone who can read the channel, people and agents, like any message there.
