# Page sets: a folder of pages shown in the thread

John, 2026-11-06: on DEV, Dusty needed to show him something several times and each time started a web server. In three
days it did so at least four times (a comic reader, a site preview, a test run's screenshots, the council's UI
mockups): copy the files, run a container on a free port of 20000–20099, post `http://<the box's LAN address>:<port>`.
Those links opened only at home, without signing in, and died or showed the wrong thing when the port was reused (the
test run's screenshots were stopped an hour later and their port then served the mockups). John: give Dusty a better
way to share such things. Decisions PG-01…PG-12.

| # | Decision | Why |
|---|---|---|
| PG-01 | **A folder of pages is a page set: one file on an ordinary message**, which the person opens and clicks through in Whombat wherever the app works (dev.whombat.com, the box's own page, Android, iPhone, at home or away). It is for things to look at: mockups, a report, screenshots with captions, a small static site. What has to keep running (a dev server, a live dashboard) stays a service (one-person.md OP-19). | The files reach the person's devices through the encrypted session like any attachment, live as long as the message, and need no port, container or home network. |
| PG-02 | **One tool, `show_pages {folder, open?, title, replaces?}`**, listed with the browser's tools (a turn with commands, never an outsiders' turn), no key of its own (it shows the agent's own files in its own conversation, like `upload_file`). It answers with the set's file for `post_message` `attachmentIds`, what is in it and the problems its check found, with the cover as image content. A single page stays a block or an attachment (visual-replies.md VR-01). | Only the turn's runner reads the turn's folder, so this can't be a block or an `upload_file`; one call does what the four container steps did. |
| PG-03 | **The file is a ZIP of stored entries** with Whombat's two entries at its end: `.whombat/cover.png` and, last, `.whombat/pages.json` (`PageSetManifest`: title, the page it opens on, counts, problems). Its type is `application/vnd.whombat.pages+zip`, its kind `file`, its name `<title>.zip`; no new attachment kind. Format, paths and readers are core's (`text/pages.ts`). | Stored entries are read one by one by their byte range, so a viewer fetches only what a page uses; pictures and fonts are compressed already. `AttachmentKind` is a strict enum, so a new value would break older apps; with a type of its own they show a ZIP to download. |
| PG-04 | **The runner reads the folder like `browser_preview`'s** (inside the turn's own folder, no links, no `.git`; `readFolderFiles`), up to 2000 files and 240 MB, leaves the folder's own `.whombat/` out, and draws the page it opens on offline at 1280×800 in the agent's Chromium for the cover. A turn without a browser makes a set without a cover. | 240 MB keeps the whole file, with its headers, cover and manifest, within the 250 MB file limit (bp-attachments.md BP-A22). |
| PG-05 | **The check tells the agent what won't work**: files a page loads that aren't in the folder, point outside it or would come from the internet, then links to click that lead nowhere, then frames (PG-11); the same problem in several files is told once with where it is, script bodies and template placeholders aren't read. At most 20 problems, in the answer and the manifest, never shown to the person; the description asks the agent to fix them and show the set again before posting. | The mockups that started this linked fonts and sources four folders up; Dusty checked that by hand with `grep`. |
| PG-06 | **The set's bytes are a raw PUT** (`PAGES_TRANSFER`) streamed into the file store's staging area, accepted only while a `show_pages` of that dispatch waits and from the runner holding its lease; the server keeps the last bytes and checks the set there (its directory, the manifest last and valid, the page it opens on present, the cover as the manifest says) before the tool gets it. The tool waits up to three minutes. | Never base64 JSON or the whole file in memory (a build's preview is 50 MB as JSON); a set nobody waits for is never stored. |
| PG-07 | **The set is kept as the agent's file** (`publish_artifact` with the page set's limit, the file limit instead of `ARTIFACT_MAX_BYTES`; rate, quota and conversation checks unchanged), and its thumbnail is made from the cover the way an image's is, kept under the set's own sha256: `Attachment.thumbnailUrl` and the session's `preview` variant serve it. | Clients load a set's picture exactly as they load any thumbnail. |
| PG-08 | **`replaces` puts the new set in the earlier one's place** on its message (`replace_page_set`, `message.updated`): only a set the agent posted on a live message of its own in this conversation, checked before the runner is asked and again in the command. The old set leaves the message: still in Files if the person saved it, removed otherwise. | A set that changes in rounds (a council's mockups) keeps one card instead of a new link per round. |
| PG-09 | **The viewer runs the set in the confined preview under the unchanged page policy**: the web's sandboxed `/sandbox/html-frame.html` (an opaque origin) or the phone's WebView, with `pages-runtime.js` (`@whombat/client/pages`) loaded there: the web's built asset (`/assets/pages-runtime-<hash>.js`, which the box's own page lets into the frame like the Mermaid runtime), the phone's data URL. The script asks the app for each file of the page by its path and writes the page with pictures and media as `blob:` URLs made there, styles and scripts inline and fonts as `data:` URLs. After that it keeps the page working as on a web server: what the page's scripts add or change (pictures, scripts, stylesheets, styles) gets its files from the set too, `fetch()` of the set's own files is answered from it, and the page reads its `?…` from its own address (the frame's, set with `history.replaceState`). The app answers only for files of this set (`PageSetHost`) and adds no theme: a set shows as it was made. | No new origin, service worker or policy: the frame and the WebView keep what visual-replies.md and preview-security.md decided, and the page reaches nothing but its own files. |
| PG-10 | **One frame per page, and the page asks, the app decides**: a link to another page or a picture of the set opens it in a new frame (Back returns); a link to another file shows a Download bar; a link to the internet shows “This link goes to {host}.” with Open; a missing page says so. A page that sends you on (`meta refresh`) inside the set is followed. Nothing downloads or opens by itself. | The page inside can post any message it likes, so its messages are wishes, never actions. |
| PG-11 | **What a set can't do**: a frame inside a page shows as a link that opens its page in the viewer (`frame-src 'none'`; the check tells the agent), and ES module imports between files, `XMLHttpRequest` and requests anywhere else don't work. Apps that need those are a service. | Kept within the page policy rather than widened. The council's mockups that started this (script-built galleries reading `?card=…`) work with what PG-09 answers. |
| PG-12 | **The agent learns it from the tool and the Docker lines**: the tool's description says when to use it (“rather than a web server for anything to look at”) and the prompt's Docker lines say a service is for what has to keep running, pages to look at go in `show_pages`. No line in `whombat.md`: its 4000 characters are full. | The container recipe was where Dusty learned to serve pages; that is where it now hears otherwise. |
| PG-13 | **The web card is a 360 px tile** with the HTML preview card's border, radius and surface: the 16:10 cover (a quiet icon on a plain surface without one), the title, `Pages · {size}`, **Open**, and Save to Files and Download as on every message file. The cover and Open both open the viewer; the cover is out of the tab order (one stop for the keyboard). A plain ZIP stays a file. | `min(100%, 360px)` let the tile run into the next message. |
| PG-14 | **The web viewer is the HTML preview's full screen**: Back left of the title once you clicked into another page, the set's title with the page's own under it, Download (the whole set) and Close on the right. Focus goes into the viewer and back to what opened it; a page that sends you on before it showed replaces itself in Back's history; Try again reloads the page that failed, or the whole set when it couldn't be read. The frame is white in both themes. | Sets don't get the app's theme (PG-09), so their own colours sit on the page they were made on. |
| PG-15 | **The box's own page lets the viewer's script into the frame**: `/assets/pages-runtime-<hash>.js` gets `Cross-Origin-Resource-Policy: cross-origin` like the Mermaid runtime (visual-replies.md VR-02); the hosted app sets no resource policy. Files opens a page set in the same viewer. | The frame is an opaque origin: its request for the script is cross-origin. |
| PG-16 | **The phone card** has the cover from the thumbnail only (never the set's file; without one, or when it fails, a quiet placeholder with the Layers mark), at most 576 wide so its 16:10 cover is never taller than a picture in a message, the title, `Pages · {size}` and **Open** (44pt); Download and Save to Files sit over the cover's corner as on picture tiles. Files opens a page set in the viewer too. | The phone's tiles keep their actions on the picture; a set's file can be 250 MB, so it is never read for a picture. |
| PG-17 | **The phone viewer**: Close, Back (once you opened another page; Android's back button goes back first), the title (the file's) with the page's own under it when it differs, Download. One WebView per page with the preview's props and its own `PageSetHost` (closed when the page goes, so a late answer can't reach the next one); one reader per viewer keeps its files across pages. A page that sends you on before it showed replaces itself in Back's history, five in a row is a failure. A file of the set is streamed from its range to `cache/shared/<attachment>/<name>` and shared (bp-attachments.md BP-A19, BP-A21); a copy of the wrong length is deleted. | The web's rules (PG-10, PG-14) on the phone's own parts. |
| PG-18 | **On the phone a page can't read its `?…` from its address**: the WebView's page is `about:blank`, whose address can't change. The query still travels with each page, so a link that only changes it opens the page again. | Giving the WebView a base address would change its origin and what it may load; not without trying it on an iPhone first. |
| PG-19 | **No hourly upload limit by default** (`WHOMBAT_UPLOAD_RATE_PER_HOUR` 0; a number set there still applies), for the person and the agent alike. Supersedes the default of bp-attachments.md BP-A04. | John, 2026-11-06, after Dusty's page set was refused: a council's before-and-after pictures had used up the 200 uploads an hour (481 in two hours on Home). “I don’t want to be restricted like this.” The limit was for several people sharing a Whombat; a Whombat is one person's (one-person.md OP-01). |
| PG-20 | **The disk is the files' limit**: without `WHOMBAT_BURROW_QUOTA_BYTES` (now unset by default) a file is kept while the disk keeps 5 % free, at least 5 GiB, for the database, backups and the agent's work (`files/room.ts`); a quota set there still applies. Website feedback screenshots are checked the same way. Supersedes BP-A04's 10 GiB default. | Home used 160 MB of its 10 GiB on a 913 GB disk: a fixed 10 GiB would have been the next wall for page sets and pictures. |
