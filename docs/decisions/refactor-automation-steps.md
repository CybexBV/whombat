# Automation step execution modules

Runtime-only refactor, 2026-10-20. The existing automation contracts and BP-C, AR, RN-S and TA decisions still apply.

| # | Decision | Reason |
|---|---|---|
| RAF-AS01 | Keep `automations/steps.ts` as the command facade: operation schemas, fenced command registration, settlement and deferred commands remain together. It re-exports every existing public helper from `steps/`. | The engine and existing tests keep their import paths, and the commit-pipeline entry points remain easy to find. |
| RAF-AS02 | Move the step-kind bodies into typed handlers for agent dispatch, posting, control steps, pull requests, comments, the tracker, merging and callbacks. Shared state transitions, scope, approval binding, approval creation, words and thread placement live in cohesive support modules. `StepExecution<K>` narrows the step to its exact kind and carries the existing transaction, publisher and attempt data, with no service locator or `any`. | Each handler owns one effect while the facade still checks the publisher and content rooms immediately before dispatching it. SQL, event order, after-commit hooks, timeouts, retries and the external-effect markers are preserved. |
| RAF-AS03 | Keep PR announcement wiring in the facade and pass a typed `PrAnnouncer` callback to PR execution/support. Put `postInRunThread` in a dependency-neutral thread module and re-export it from the facade. | Existing `trackers/fixes.ts` imports that public thread helper. Having a new PR handler import fix tracking would add a runtime cycle back through the facade; the narrow callback preserves the existing integration without changing files owned by another workstream. |
| RAF-AS04 | Reuse the existing behavior tests and throwaway-Postgres harness for verification. Do not add new contract schemas, package dependencies, database migrations or visible words. | This work changes module boundaries only; permission, approval, cancellation, fencing and recovery behavior are already exercised by the automation suites. |
