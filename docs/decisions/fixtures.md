# Fixtures workstream decisions

Scope: `packages/fixtures` (TODO 3.2, data half — the server seed script that loads this into Postgres
is the server workstream's job). Ports the mock world from `Whombat Desktop.dc.html`'s
`<script data-dc-script>` block (and `Whombat Mobile.dc.html` where it adds detail) into fixtures typed
with `@whombat/core` schemas, plus `createFixtureFetch()` — a fetch-compatible function serving the
mock world over the real REST contract, for web/mobile UI work that needs a server before the server
workstream lands.

| # | Decision | Reason |
|---|---|---|
| FX-01 | Mock agent `status:'running'` maps to the domain's `AgentStatus` value `'working'` (Banjo and Clover). Every other mock status name (`idle`, `waiting`) matches the domain enum verbatim. | `AgentStatus` doesn't have a `'running'` member; `'working'` is what the mock's own copy describes ("Rounding VAT before formatting…"). |
| FX-02 | Only one DM thread is fixtured: Mara ↔ Pippa (`cnv_dm-pippa`, from the mock's `DMS.pippa`, the only DM the mock script defines). Desktop's copy for it is authoritative over anything implied elsewhere. | It's the only DM the source material actually specifies; inventing others risks copy that doesn't match either `.dc.html`. |
| FX-03 | The mobile mock (`Whombat Mobile.dc.html`) shows the storyline further along (checks 41/41, Hazel approved at 11:38, PR head `7be20f7`) than desktop's initial 11:22 state (checks 38/41 fixing, changes requested). Both are modeled as data: `work.ts` exports `run`/`pr`/`approval` (desktop's 11:22 state, served by default) and `runFinished`/`prApproved` (mobile's later state), and `fetch.ts`'s `approve()` does a one-shot fast-forward from the former to the latter when the approval is decided. | Keeps both mocks' literal copy intact instead of inventing an interpolated state, and gives `createFixtureFetch()` a working approve → deploy flow without a real scheduler. |
| FX-04 | Channel-to-id resolution: mock channel names (`'general'`, `'billing-v2'`, `'incidents'`, `'pr482'`) become `cnv_general`, `cnv_billing-v2`, `cnv_incidents`, `cnv_pr482`; the DM becomes `cnv_dm-pippa`. Agent/person handles become `prn_<handle>` (`prn_banjo`, `prn_mara`, …). Audit events keep the mock's `e-<suffix>` refs as `evt_<suffix>` (`e-9f31` → `evt_9f31`). | Matches `ARCHITECTURE.md` / `@whombat/core/ids`' `ID_PREFIXES` convention and keeps mock cross-references (like `LOG`'s `where` links) traceable by inspection. |
| FX-05 | Grants are never hand-authored: `principals.ts#GRANTS` is `AGENTS.flatMap(a => roleDefaultGrants(a.id, a.role))`, reusing `@whombat/core/keys`' `ROLE_DEFAULT_KEYS`/`roleDefaultGrants()`. Hiring reuses `HIRE_KEY_OPTIONS`/`hireGrants()`/`describeHire()`; key display reuses `keyLabel()`; the roster footer reuses `keysSummary()`/`formatKeysSummary()`; PR/merge state reuses `prStatus()`/`PR_STATUS_TONES`/`mergeBlock()`/`checksState()`; canvas comment grouping reuses `groupCommentThreads()`. | Contracts-first: the engine that computes these values already exists in `@whombat/core` and is tested there. Hand-duplicating the logic in fixtures would drift and wouldn't exercise the real engine. |
| FX-06 | `Agent.channels` (`AGENTS[x].channels` in `principals.ts`) is the mock's `AG0[x].chans` verbatim — the "channels the agent works in" list used for the `channels.read` key's scope and the roster's channel count — **not** the same thing as a conversation's `memberIds`. Conversation `memberIds` (who's in `cnv_pr482`, say) is modeled independently in `conversations.ts` and can include agents that aren't in their own `channels` list (Banjo and Hazel are members of the `pr482` branch room but their `channels` array doesn't include it, matching the mock). | `domain/principal.ts`'s own doc comment on `Agent.channels` draws this line ("CHANNELS chips, 'Can read: …' in its DM header"); conflating the two initially gave Pippa 2 channels instead of the mock's 3 (`#billing-v2`, `#incidents`, `#general`) and Hazel 2 instead of 1 (`#billing-v2`) — caught by the KEYS-summary test below. |
| FX-07 | `AUDIT_CHAIN` (`audit.ts`) prepends one event not in the mock's `LOG`: `evt_burrow` (`burrow.created`, kind `System`, actor Mara, dated at the burrow's own `createdAt`). Every other row is `LOG` verbatim, oldest first (`LOG` itself is newest-first in the mock UI). | Every `AuditKind` (`System`, `Keys`, `Code`, `Blocked`, `Asks`, `Messages`) needs at least one row so kind-filter tests and UI aren't exercising an empty bucket, and the mock's `LOG` happens to have no `System` row. |
| FX-08 | `AUDIT_CHAIN` is a **real** signed chain: each row is appended with `appendEvent()` (Ed25519 signature via `deriveSeedKeypair(principalId)`, real `hashEnvelope()`/chain-of-hashes), not the mock's fake `fp()` string hash. One event (`evt_9f18`, Dusty's deploy ask) carries a timestamp pinned to the approval's own `createdAt` (`at('11:25')`) rather than the mock's separately-stated "11:30", so the event and the approval it created agree. | `verifyEvent()`/`verifyLink()` in `@whombat/core/audit` are the real verification path the audit log UI and server both use; a fixture with a fake hash couldn't exercise them. The mock itself doesn't guarantee its two literal timestamps for the same fact agree — the fixture picks the approval's own `createdAt` as authoritative. |
| FX-09 | The audit chain includes events timestamped 11:35 and 11:36 (tests passed, branch pushed) even though the *default* served run/channel state (`run`, not `runFinished`) still shows 11:22. This is deliberate, not a bug: the audit log is a complete historical record (it's meant to show what *will have* happened by the time the storyline finishes), while the live views show the starting tick. Approving the deploy (`fetch.ts#approve()`) transitions the live views to match; it doesn't touch the audit chain, which was already "ahead." | Matches the mock's own `LOG` array, which is static and includes the same later timestamps regardless of where the live simulation's tick is. |
| FX-10 | Where the mock's copy doesn't specify a value a schema requires (Yjs `relativePosition` opaque strings for canvas comments, agent public keys for newly hired agents, etc.), the fixture author supplies a plausible literal rather than leaving it undefined or `''`. | Zod schemas are strict (`min(1)` etc. in several places) — every fixture must parse, and inventing a placeholder is preferable to weakening a contract just for fixture convenience. |
| FX-11 | `store.ts#enrichAuditEvent(signed, approvalByEventId)` turns a `SignedEvent` into the wire `AuditEvent` shape (`fingerprint`, `verified: true`, `approval` looked up from a caller-supplied map). `fetch.ts` builds that map fresh from the live `Approval` on every call (`approvalByEventId()`), since only one audit event (`evt_9f18`) is ever approval-linked in this fixture set. | Keeps `store.ts` a pure, stateless view over fixtures (per its own header comment) while `fetch.ts` owns the one piece of mutable state (the approval's current decision) that the enrichment needs. |
| FX-12 | `notifications.inbox` (and every other endpoint not in `fetch.ts`'s `IMPLEMENTED` set — `search.ask`/`getAnswer`/`postAnswer`, `runs.log`, `prs.merge`, `agents.update`/`setKeys`/`setChannels`, `conversations.createChannel`/`update`/`addMembers`/`openDm`/`markRead`, `messages.react`, `uploads.create`, `plans.*`, `canvases.list`/`create`/`collabToken`/`addComment`/`resolveComment`, all of `burrows`/`repos`/`members`/`auth`/`devices`) is intentionally **not** implemented; `createFixtureFetch()` 404s them with a message naming the endpoint id. | The workstream's explicit scope is the read surface plus send-message / approve-decline-undo / hire; every other write needs real server-side state machines (schedules, collab docs, upload storage) that don't belong in a pure-data fixtures package. Server/web/mobile workstreams that need one of these can add a case to `fetch.ts`'s `handle()` switch — the router (`API_ENDPOINTS` + `matchPath()`) doesn't need to change. |
| FX-13 | `packages/fixtures/tsconfig.json` adds `"lib": ["ES2023", "DOM", "DOM.Iterable"]` on top of `tsconfig.base.json`'s bare `ES2023`. | `fetch.ts` implements a real `Request`/`Response`/`URL`/`fetch` signature (`createFixtureFetch(): typeof fetch`) and needs the Fetch API global types; this mirrors `packages/client/tsconfig.json`'s existing pattern exactly rather than inventing a new one. |
| FX-14 | Approve is a one-shot fast-forward (`fetch.ts#approve()`) to the storyline's known finished state, not a literal simulation of the approval's three conditions resolving asynchronously over the run's live ticks. Decline sets `state:'declined'` without touching `run`/`pr`. Undo is only allowed while `executedAt === null` (blocked once `approve()` has run `execution.state:'succeeded'`), per `ApprovalExecution`'s own doc comment ("Only until the action has executed"); undo after decline puts the approval straight back to `pending`. | A full async simulation (checks finishing, Hazel's review landing, the deploy executing) needs a scheduler this package doesn't own. Fast-forwarding gets UI work a correct "before" and "after" without inventing intermediate states the mock never shows; the undo restriction is a contract rule, not a fixtures-specific choice. |
| FX-15 | Pure-UI mock state that has no `@whombat/core` schema counterpart is *not* ported 1:1. Example: the mock sidebar literally shows "Canvases · 4" but only one canvas (`invoice-pdf-export-plan`) has real content in the source material; `store.ts#sidebar()` reports `counts.canvases: 1` (the true count of fixtured canvases) rather than replicating the mock's arbitrary badge number. | `Count` in `Bootstrap.sidebar.counts` is meant to be the real count backing the badge; hard-coding "4" would be a lie the moment anything reads `canvases.list` (also out of scope, FX-12) to cross-check it. |
| FX-16 | Sidebar unread/mention badges (`store.ts#SIDEBAR_BADGE`) are only non-zero for `#incidents` (2 unread, from the mock's own badge markup near `channels.map(...)`) and the Pippa DM (1 unread, her last reply). Every other channel reads as caught up. | The mock only marks those two; inventing badges elsewhere isn't supported by the source material. |
| FX-17 | `createFixtureFetch()` (and everything else in `fetch.ts`) is exported from a dedicated `@whombat/fixtures/fetch` subpath (`package.json#exports`), not from the package's main barrel (`index.ts`). | `apps/server` imports `@whombat/fixtures` (for `SEED_NOW` in its seed-script stub) with no `DOM` lib in its `tsconfig`. Barrel-exporting `fetch.ts` pulled its `Request`/`Response`/`RequestInfo` usage into every consumer's compile graph, breaking `apps/server`'s `typecheck` the moment it resolved the barrel — TypeScript type-checks a source-file re-export's whole module graph, not just the symbols actually imported. Splitting the Fetch-API surface into its own subpath (mirroring `@whombat/core`'s existing `./domain`, `./contracts`, etc. subpaths) keeps Node-only consumers on the DOM-free barrel while web/mobile can `import { createFixtureFetch } from '@whombat/fixtures/fetch'`. |

## Testing

- `src/fixtures.test.ts` — every fixture (burrow, repos, people, agents, principals, conversations,
  messages, plan/run/runFinished/pr/prApproved/approval, run log lines, the signed audit chain and its
  `AuditEvent` enrichment, the canvas and its comment threads, search results and answer, onboarding
  state, notifications, and the full `bootstrap()` payload) parses against its `@whombat/core` Zod
  schema, plus a per-agent assertion that `formatKeysSummary(keysSummary(...))` matches the mock's
  `AG0`-derived string exactly (`"3 keys · 1 ask first · 2 channels"` for Sketch, etc. — see FX-06 for
  the bug this caught).
- `src/fetch.test.ts` — every implemented read endpoint's JSON response validates against its contract's
  `.response` schema (looked up from `API_ENDPOINTS` by id, so the test breaks if the contract changes
  shape); an unimplemented endpoint (`runs.log`) 404s; send-message produces the canned agent reply in a
  DM; approve/decline/undo drive the approval state machine including the terminal-state fast-forward
  and the undo-after-execution block; hire adds a new agent with grants and shows up in the roster.
