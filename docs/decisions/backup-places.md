# Backup places: a NAS keeps this Whombat's backups

John, 2026-11-03: “When we attach a NAS (for example Unraid) we should be able to use that as a backup service, how
can we build this? What do you recommend?” After the recommendation: “Implement this fully, including support for
Synology, TrueNAS and QNAP”.

The box already backed itself up with restic to a REST server, a bucket, SFTP or a USB disk (the appliance
`docs/decisions/backup.md` BK-09, BK-18…BK-20), and the Inbox proposed an Unraid server it could reach
(`first-day.md` FDY-21), which the assistant set up over SFTP. On Unraid that path didn't hold: Unraid lets only `root`
in over SSH (`AllowUsers root`; other users have `/bin/false`, checked on BlackBox, Unraid 7.3.1) and a user made by hand
is gone after a reboot; SFTP can't refuse deletes either, so a broken-into box could wipe its own backups. John's Home
backed up to its own disk (`local`), which a reinstall or a dead disk takes with it.

A **backup place** is a NAS or server that keeps this Whombat's backups: Whombat installs a small backup app on it (a
restic REST server that only adds) and points the box's backups at it. Code: core `domain/backup-places.ts`, server
`apps/server/src/backup-places/`, hosts `backup-place` routes (`hosts/docs/decisions/` HS-203…), web Settings →
This Whombat → Backups and the server and connection pages, the phone's Backups screen.

| # | Decision | Why |
|---|---|---|
| BPL-01 | **The backup app is a restic REST server that only adds**: `restic/rest-server` (pinned by digest) with `--append-only --private-repos`, one user per Whombat, its own container per Whombat (`whombat-backup-<client>`) on its own host port (the first free from 8747), its data in `<root>/<client>/`, the password file outside the data (`<root>/.whombat/<client>.htpasswd`, bcrypt). The box's repository is `rest:http://<numeric LAN address>:<port>/<client>/` with that user and password. | BK-09's first qualified destination: the box's credential can add and read, never delete. Plain http to a numeric address on the home network is allowed (BK-29) and restic encrypts the data. A container per Whombat means one Whombat never rewrites another's. |
| BPL-02 | **Old backups are cleared on the NAS, not by the box**: a second container (`whombat-backup-<client>-cleanup`, `restic/restic` pinned by digest) runs `restic forget --keep-within 90d --prune --retry-lock 2h` on the data folder directly once a week, and writes how it went to `<root>/.whombat/<client>.cleanup.json`. It holds the repository password, which Whombat reads from the box's recovery material after the destination is set and hands to the NAS once (`<root>/.whombat/<client>.pass`, 0600, or the app's environment on a NAS Whombat reaches through its API). | BK-09: deleting needs a credential the box never holds. Pruning needs the repository password whoever runs it; the NAS is the person's own, and the recovery kit already carries the password. `--keep-within` only, never `--keep-last` (BK-09: a future-dated snapshot can't push real ones out). |
| BPL-03 | **Where a place can be**: (a) a server with Whombat's agent, Docker and Manage on — Unraid (a share `whombat-backups` made through Unraid's own `emcmd`, not exported over SMB or NFS, `<root>` = `/mnt/user/whombat-backups`, the containers as Unraid templates so they show in its Docker tab and start with it) or any other Linux server (`<root>` = `/srv/whombat-backups`); (b) a Synology, TrueNAS or QNAP connected with Manage, through its own API: a Container Manager project, a TrueNAS custom app or a Container Station application named `whombat-backup-<client>` with both services. Never the server this Whombat runs on. | The agent is how Whombat changes an Unraid box; the three NAS have no agent and are connections already, signed in as an account of their own. Unraid's emcmd is what its web page uses, so the share has Unraid's own settings and survives a reboot. |
| BPL-04 | **A place has one of five states** for the person: *Keeps your backups* (in use), *Ready* (Whombat can set it up now), *Connect it first* (a NAS the scan found, not connected), *Turn on Manage first* (connected or added with Look only), *Can't keep backups* with one plain reason (no Docker, Container Manager missing, TrueNAS without an apps pool, too old). | One line each says what is possible and the one thing that makes it possible. |
| BPL-05 | **Setting a place up is one step for the person** (`backup.usePlace`): Whombat makes the user and password (32 random bytes), installs or updates the backup app, waits until it answers, sets the destination (`allowInit`), checks that deleting is refused (the service's own probe: `appendOnly: verified`), hands the repository password to the cleanup, records the place and starts the first backup. A step that fails says which in one sentence and leaves what worked; doing it again carries on. | The person's yes is the request; the rest is Whombat's. |
| BPL-06 | **Moving backups that go somewhere already stays the person's** (Settings → This Whombat → Backups, “Back up here”, with a confirm that says the old backups stay where they are), **except from this Whombat's own disk**: the assistant's `whombat_backup` may set a place while nothing backs the box up (FDY-23) or while it backs up only to its own disk (`local`). | A backup on the box's own disk is no protection against losing the box; moving it to the NAS only adds. Any other move is a choice about where data lives. |
| BPL-07 | **The Inbox's one proposal names the best place**: a place that is *Ready* (a NAS or storage server first, then the server with most free space), then a NAS the scan found (*Connect it first*), then a USB disk. It shows while nothing backs the box up (FDY-21) and also while backups go only to its own disk: “Your backups are on this Whombat’s own disk. Keep them on BlackBox instead?” | The same single proposal, now also for the weak case John's Home is in. |
| BPL-08 | **The place follows its NAS's address**: every few minutes Whombat compares the address in the box's repository with the NAS's addresses (the agent's report, the connection's address); when the NAS moved, it sets the same repository at the new address (`adoptPassword` from the recovery material, the same REST user), so history and the repository stay. | Plain http needs a numeric address (BK-29); a DHCP change must not stop backups. |
| BPL-09 | **By hand when Whombat can't install it**: a place whose API refused or whose kind isn't supported automatically shows “Set it up by hand”: the compose file to paste (Container Manager → Project, Container Station → Create, TrueNAS → Apps → Install via YAML, Docker anywhere) with the user's bcrypt line, then “Check it”, which sets the destination. A place set up by hand has no cleanup until the NAS is connected with Manage; its line says so. | A fallback for NAS versions Whombat's calls don't fit, without inventing a second way of keeping backups. |
| BPL-10 | **What it shows**: Settings → Backups names the place (“BlackBox · Unraid”), that deleting is blocked, and that backups older than 90 days are cleared; the server's or connection's page gets “Backups kept here” (which Whombat, space used, the last cleanup, free space). | One place to see it, where people look. |
| BPL-11 | **What Whombat watches**: the box's own backup state stays the check that starts on (a backup isn't happening). New: “Old backups aren’t being cleared on <place>” and “<place> is running out of space for backups”, both off at the start. | Watch defaults (`watch-defaults.md`): a failed cleanup and a near limit aren't urgent. |
| BPL-12 | **Servers' backups go to the NAS too**: the care plan's nightly Proxmox backups go to a Backup Server when there is one, otherwise to a backup place that can share a folder over NFS (Unraid through the agent: a share `whombat-<server>` exported to that server's addresses only; TrueNAS through its API: a dataset and an NFS share), added to Proxmox as backup storage, rather than to the server's own disks. Incus snapshots and QEMU/KVM backups stay on their server for now. | Backups on the same disks as the machines don't survive the disks. Incus and libvirt would need a mount on the host the agent doesn't make yet. |
| BPL-13 | **The person chooses where on the place** (John, 2026-11-03: “What share is being used on Unraid, I think we should see an option where to store the backup?”): a place lists its locations — Unraid's shares, a TrueNAS's pools, a Synology's or QNAP's shared folders — with free space; the recommended one is a share or folder only Whombat uses (Unraid's new `whombat-backups`, not shared on the network); a share that is shared on the network says so (“anyone who can open it could delete the backups”). Backups in an existing share go in a folder `whombat` in it. Settings names the location in use and offers Change. A Linux server has one location (its `/srv/whombat-backups`), so it asks nothing. | Where data lives is the person's choice; the default stays the safe one. |
| BPL-14 | **Changing the location moves the backups when Whombat can**: on Unraid and Linux the agent moves the Whombat's folder to the new location and starts the backup app there with the same address, user and repository, so the box's destination, history and recovery kit don't change. Through a NAS's API (Synology, TrueNAS, QNAP) Whombat can't move folders, so the new location starts a new repository and the old backups stay where they were (the confirm says so). | Keeping history matters more than the shortcut; the APIs have no safe move. |
| BPL-15 | **Every action that hands work to the assistant opens the thread where it happens**, on the web and the phone (John, 2026-11-03: “this should move me to the chat automatically, so I can see what’s going on. I think this is a global thing”): the Inbox's yes to a proposal, *Ask {assistant} to handle it*, *Go ahead* on an offered step, *Talk to {assistant} about it*, a page's Ask links and a card's buttons that start a turn. The item's own page doesn't close itself over the thread it opened. One shared rule in `@whombat/client` says which buttons go to a thread. | The person sees the work start and can follow or stop it; a toast is easy to miss. |
| BPL-16 | **What the assistant says after setting a place up is Whombat's sentence**: `whombat_backup` answers `say` (“This Whombat now backs up to BlackBox, in the share whombat-backups. The first backup is running now.”) and the agent passes it on, without addresses, ports or paths. | Its own reply named the URL and a path and said the first backup would run tonight, though it had already started. |
| BPL-17 | **A place's yes moves the backups on the box's own disk too** (John, 2026-11-04): when a place takes over from this Whombat's own disk, the backups made there are copied to the place and removed from the box as part of the same yes (backup-options.md BKO-30), shortly after the first backup; the Backups page's row stays only for what couldn't move. | One yes, not two; Home kept 14 backups on its only disk. |

## Server details

Stream S, `apps/server/src/backup-places/` (2026-11-03).

| # | Decision | Why |
|---|---|---|
| BPL-S01 | **What the backup service does with a second destination** (`appliance/backup/internal/dest/dest.go` `Configure`, read 2026-11-03): `PUT /v1/destination` replaces the destination at any time (generation + 1) after verifying the new one with staged secrets, so a failed attempt leaves the old one working. The repository password is `adoptPassword` when given, else the one the box has. With `adoptPassword` a missing repository is an error (“nothing to adopt”), never a new one, even with `allowInit`; without it `allowInit` makes a new repository with the box's own password. The REST password is kept only when the new destination is REST with a user, so every set carries `restUser`/`restPassword` again; the recovery material carries both and the repository. So: **moving to a new place** sets the destination without `adoptPassword`, with `allowInit` (a new repository there, the same password; the old backups stay where they were); **following an address** sets the same repository at the new address with the material's REST user and password and `adoptPassword`, without `allowInit`. | BPL-06, BPL-08 need to know which input keeps history and which makes a repository. |
| BPL-S02 | **The place in use is the record whose `repository_id` the backup service reports** (`status.destination.repositoryId`), not a flag: a destination the person sets elsewhere ends it by itself. A place in use that left the network still shows, from its record. | One source of truth: the backup service. |
| BPL-S03 | **The client name** is `whombat-<Whombat's name>-<short id>` (`backupPlaceClient`): the name the person gave (the desk's), else the burrow's; the second group of the device id (`wb-4hxx-…` → `4hxx`), else the end of the burrow's id; made once and reused from the first record, so a rename doesn't move the backups. | Readable on the NAS, unique per box, stable. |
| BPL-S04 | **Which servers are places**: those whose `backup_place` says supported (ready, or Turn on Manage first); an Unraid box always (with its reason, “helper needs an update” from an agent without the report); any other server only with a reason the person can fix (Docker stopped, array stopped). A Linux server without Docker and the server this Whombat runs on (unless it is Unraid) aren't listed. | A Proxmox host listed as “Can't keep backups” is noise. |
| BPL-S05 | **`kept` carries the free space of any place that reports it**, `usedBytes` null while it doesn't keep this Whombat's backups yet. | `bestBackupPlace` orders ready places by `kept.freeBytes` (core's test). |
| BPL-S06 | **The repository's address** is the hosts service's own address for the server when the agent lists it, else the first address the agent reports (the default route's); only private IPv4 addresses count (BK-29). | The address the hub reaches the server at is the one the box most likely reaches too. |
| BPL-S07 | **The steps and doing it again**: install (ensure) → record → destination (`allowInit`) → first backup started, not waited for → cleanup handed the repository password (every time; idempotent) → record. | BPL-S08 | **A move the person hasn't confirmed** is `conflict` with `details: {code: 'move_needed', from}` (`from`: the place in use's name, else the service's display), also when the backup service's status is unknown; the app asks and calls again with `move: true`. `whombat_backup` answers it as `already_set`. From nothing or from `local` no `move` is needed. | The app stream's shape; BPL-06. |
| BPL-S09 | **Records go through the pipeline as box-level writes** (`transactAccount`, no burrow): the box's backups are the box's. No appliance event of their own: `backup.destination_set` (the person or the assistant) and `backup.run_requested` (`reason: backup_place`) say it; Whombat's own reads of the recovery material (to hand the cleanup its password, to follow an address) write no `recovery_material_viewed`, which says a person saw it. | Nothing new in the signed log's vocabulary; no password anywhere but the place and the backup service. |
| BPL-S10 | Superseded by BPL-S23. **One place flow at a time per box** (set up, remove, follow), in memory; the servers' details are kept 30 s for the Inbox and read fresh by `backup.places` and the flows. | Each reads where backups go before changing it; Home reads often. |
| BPL-S11 | **The two watch lines are Whombat's own hints on the server** (`host.hint.backup_place.cleanup`, `you`; `host.hint.backup_place.space`, `fyi`; both `startsOn: false`): cleanup when it isn't set any more, its last run failed, or no run came in 9 days since the hand-off; space when less than 10 % is free. Worked out on every places read (the follow's included) and given to the hosts service (`addHintSource`) for the fleet and the server's page. A NAS connection's lines are its kind's checks (stream N), with the same words (`BACKUP_PLACE_TEXT.watch`). | BPL-11; the hosts service's hints already have Watch, Ignore and Stop watching. |
| BPL-S12 | Superseded by BPL-S24. **The address follow** runs every 5 minutes on a box with a backup service, only for the place in use, only when the material's repository is the one Whombat set there, and takes the first private address the driver reports (`addresses()`; a NAS driver without it: the connection's address). The event names no account (Whombat did it). | BPL-08 without ever pointing the box somewhere it didn't choose. |
| BPL-S13 | Extended by BPL-N12 (a TrueNAS when no Unraid can). **The care plan's NAS**: a Proxmox server without a Backup Server or a network storage (`nfs`, `cifs`, `cephfs`, `glusterfs`) and with known addresses keeps its backups on an Unraid backup place with Manage and NFS on (most free space first): share `whombat-<server>`, storage `<place>-backup`, one step naming `backup_place_nfs`, `proxmox_storage_add` and `backup_job_set`. The job step leaves out `mode snapshot` (the tool's default) to stay within a step's 300 characters. A TrueNAS place joins when stream N's driver shares over NFS. | BPL-12. |
| BPL-S14 | Superseded by BPL-N10. **By hand is stream N's**: `backup.placeByHand` and `backup.placeCheck` answer `not_implemented` until N replaces them; the record has the sealed pending password (`pending_password_enc`, AAD `backup_place:<id>:pending`) and `pending_until`, with `sealPending`/`openPending` in `store.ts`. | BPL-S15 | **The record**: `backup_places`, migration `0031_backup_places` (expand). | BPL-05's “records the place”. |
| BPL-S16 | **An Unraid server's locations come from the hosts service** (`backup_place.locations`, read in `hub.ts` `toLocation` and nowhere else; ids are share names): recommended is `whombat-backups` (made when chosen, `is_new`); a share is *shared* when its `smb` or `nfs` export is set (anything but empty, `no`, `-`); its `primary` other than the array is the pool it lives on first; `appdata`, `domains`, `isos` and `system` hold Unraid's own things. Order: recommended, then by free space, Unraid's own last. One location or none is no choice: `locations` is empty and nothing is asked (a Linux server, `locations.ts`). The place in use says the share its agent reports for the client. | BPL-13; the hub's JSON is one file to change when stream H2's differs. |

Confidence: `list_share` and `get_tree` are in Synology's and QNAP's File Station guides (high), `pool.query` in TrueNAS's middleware source (high); no real NAS has run them. | BPL-13 without a second visit to the NAS; the research notes (`nas-apis.md`) name these calls. |
| BPL-S18 | **Which location** `ensure` uses: the one asked for (checked against the place's list first, else `not_found` `backup_location_gone`, “That place on it isn’t there any more.”), else where the app keeps them now, else the recommended one. The record keeps it (`backup_places.location`, migration `0034_backup_place_location`, expand); the place in use shows the agent's report for a server (it is the one that moves them), else the record's, else `wasIn`. `backup.usePlace` answers `locationName` (“the share whombat-backups”, “the pool tank”, “the shared folder docker”; `BACKUP_PLACE_TEXT.location.said`), null when the place has no choice. | BPL-13, BPL-14; one rule for a new place, the place in use and doing it again. |
| BPL-S19 | **Another location on the place in use**: Unraid and Linux — `ensure` with `location`, the agent moves the folder (up to an hour; the hub call waits 61 minutes, only when the location differs from the agent's report), the address, port, user and repository stay, so the destination isn't set again and no first backup starts; no `move` is needed beyond the app's own confirm. ## NAS drivers

Stream N, `apps/server/src/backup-places/nas/` (2026-11-03). No real Synology, TrueNAS or QNAP has run these calls:
the drivers follow the API research (`~/.cache/wb-tmp/nas-backup/nas-apis.md`) and are tested against fakes built from
it; the compose itself ran under Docker on The Titan (REST server only adding, a delete refused with 403, restic `init`
and `backup` over REST, the cleanup's run and its failure written to the status file).

| # | Decision | Why |
|---|---|---|
| BPL-N01 | **One compose for every NAS and for by hand** (`nas/compose.ts`): service `server` (`restic/rest-server:0.14.0`, digest-pinned; `entrypoint: ["/bin/sh","-c"]` and a script that writes the htpasswd from `HTPASSWD` into `/tmp/.htpasswd` inside the container, then `rest-server --path /data --append-only --private-repos --listen :8000`; host port → 8000; only `<root>/<client>` mounted, at `/data/<client>`) and, with the repository password, `cleanup` (`restic/restic:0.18.1`, digest-pinned, `/bin/sh -c`). Every `$` of every value is written `$$`; `readPlaceCompose` reads a deployed app back (port, folder, user line, cleanup). Container Station's variant has `version: "3.8"`. | The image has no ENTRYPOINT (only `CMD /entrypoint.sh`); compose substitutes `$` everywhere. The password file stays out of the backups and is made again on every start. One text means a by-hand place and a driver's place are the same app. |
| BPL-N02 | **Only the bcrypt line goes to the NAS** (`bcryptjs`, `$2y$`, cost 10), never the REST password; the repository password goes only to the cleanup's environment (the NAS's own config, 0600 on TrueNAS). The image's declared `/data` volume stays an empty anonymous volume (compose reuses it on recreate; TrueNAS's delete and Synology's clean remove it). | The NAS's admins are the person; the box's credential still can't delete. A tmpfs over `/data` avoids the volume but wasn't proven under Docker here. |
| BPL-N03 | **The cleanup's week** counts from its last run (the status file's time) or, before the first, from `<client>.cleanup.since` written at its first start; it runs `forget --keep-within <n>d --prune --retry-lock 2h` on `/data/<client>`, writes `<client>.cleanup.json` (`last_run_at`, `last_ok`, `last_error` cut to 300 characters without quotes, `keep_within_days`) and a `<client>.cleanup.failed` marker while the last run failed; `trap` stops it at once. | A NAS that restarts weekly would otherwise never clear. TrueNAS's API lists files but doesn't read them: the file's time and the marker say how it went there. |
