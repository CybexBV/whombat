# Hermes Agent updates (2026-10-28)

John, 2026-10-28 (main checkout): “I would like a way for updating Hermes Agent as an option in Settings, can you
research what the best way is to implement this?”, then, after the research: “Implement it fully and I want you to use
your recommendations.” The research (sources as file:line) found that Hermes is pinned and built into the host image
(HE-10, NX-430…435), refuses its own `hermes update` there (read-only Nix store), that the runtime accepts only the
exact pin (`checkHermes` → `outdated`), and that Hermes's `state.db` migrations are one-way. Hermes published 8 stable
releases in 16 days in October; 0.22.0 broke 16 of the plugin's tests.

| # | Decision | Why |
|---|---|---|
| HU-01 | **No update button and no “latest” track** (how production gets it: HU-10). Hermes stays pinned and tested by Whombat (HE-10 holds); a person never updates Hermes by hand and never gets a release Whombat hasn't tested. | A self-update can't run on the read-only appliance, would bring unsigned, untested code next to the person's sign-ins, and has no way back. |
| HU-02 | **Settings shows the version**: This Whombat → About → VERSION, “Hermes Agent” · “What your assistant runs on” · `0.22.5`, from `ApplianceInfo.hermes` (contracts 3.8), which the server fills from its ready runner's `RunnerStatus.hermes`. HE-04 is amended: nobody sets anything about Hermes, but its name and version are shown. | People see what their assistant runs on and that it moves. Hermes is MIT and the notices credit it already. |
| HU-03 | **Tested Hermes releases reach DEV by themselves** (its test and timing: superseded in part by HU-07; one pin commit on one `main`: superseded in part by one-repo.md OR-66): the appliance's latest-tested Hermes job (modelled on the Claude Code one) notices a new stable Hermes release, moves the pin in scratch clones of Whombat and the appliance, runs the plugin, runtime and Hermes checks and a live turn, and on a pass commits the pin to both `main`s and runs `dev/candidate`. On a failure nothing ships and its log says why (one failed marker per version, no retry loop). PROD only through `release/ship`, as now. | New Hermes versions within a day, without anyone pressing anything, and never untested. |
| HU-04 | **Hermes ships with the runtime, not the host**: its closure (and Whombat's plugin) is part of what a runtime release activates, so a Hermes or plugin change restarts the runner instead of rebooting the box, and the manager's automatic go-back covers it. | A Hermes bump becomes a small, quick update with the existing way back (appliance decisions). |
| HU-05 | **A runtime activation is healthy only when the real Hermes works**: it answers ACP `initialize` and loads Whombat's plugin and providers in a scratch home (and runs one scripted turn where the appliance can). Otherwise the manager goes back to the known-good release. | A broken Hermes goes back by itself before anyone notices. |
| HU-06 | **The release says it**: a candidate that moves Hermes names it in its `--what` (“hermes agent 0.23.0”), so the box's “Updated to …” summary tells the person. | No new contract for one sentence. |
| HU-07 | **DEV takes a new Hermes once a day, after a simple test** (John, 2026-11-02: “update Hermes agent daily … a test that simply installs the latest version … and do some basic checks … Keep it simple”). The job runs daily at 04:47 and tests by installing and using: the build with the activation check (its version, our plugin and providers, an ACP session), the pin agreement and one turn on a box in a VM (appliance NX-490). The plugin's own tests are no gate: they follow Hermes's internals, run in CI against Hermes's newest release (HN-10), and take their example skills from what Hermes ships rather than naming them. | Hermes 0.22.6 was held back only because two tests named skills Hermes had moved. A box still goes back by itself when a new Hermes fails its activation check (HU-05). |
| HU-08 | **Superseded by HU-10** (`one-environment.md` ENV-03, ENV-19; `whombat-link.md` LNK-23). **Production takes a new Hermes once a week, by itself** (John, 2026-11-02: weekly, automated; built when production boxes take updates). A weekly job picks the newest Hermes that has run on DEV for some days with Home healthy and no go-back, builds a runtime-only release from what production runs with only Hermes moved, validates it and promotes it in the usual waves without waiting for anyone. Not built yet: no production box takes updates. | Hermes isn't expected to break; DEV, validation, waves that pause on any failure and the box's go-back are enough safety without a person pressing go. |
| HU-09 | **An agent reviews each new Hermes before DEV gets it** (John, 2026-11-02: “involve Opus 5.5 with high effort to take a look at it and see if it needs to adjust something … before deployment”; “Yes build it”). The appliance's job asks a T3 Code task on The Titan once per new release; its agent reads the release against the parts of Hermes Whombat uses, makes what must change on branches in both repositories and has the job test and ship them, or stops and asks John when the change touches where code runs or what it can reach, takes something away, needs a contract release or migration, or reopens a decision (appliance NX-492, `docs/runbooks/hermes-review.md` there). Not reviewed within two days: the job tests it as it is. | Hermes 0.22.6 replaced its browser tools; a test only held it back, a reader would have seen why and either adapted Whombat or asked. The job stays the one gate to DEV. |
| HU-10 | **A new Hermes reaches Beta through the latest-tested job; Production gets it only inside a promoted release.** There is no weekly automated promotion of Hermes to Production and no rollout waves: Production updates move only by `promote`, on the owner's word (`one-environment.md` ENV-03, ENV-19; `whombat-link.md` LNK-23). Supersedes HU-08. | Production has one promotion gate — the owner's word — with no separate automated path or wave machinery. |
