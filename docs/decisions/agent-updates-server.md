# Server agents keep themselves up to date: the server side

Decisions the server stream made building agent-updates.md (AU-01…AU-10) on contracts 0.99.0 (CT-510…CT-516). No
migration. Code: `apps/server/src/hosts/agent-updates.ts` (the pure parts and the words), `agent-signing.ts` (Done
recently), `principal.ts` (the Servers signer), `routes.ts` (the three endpoints), `testing/fake-agents.ts`.

| Id | Decision | Why |
|---|---|---|
| AU-S01 | **The `update` object of `/agents` maps field by field** (`toAgentUpdate`): `reason_code`, `auto`, `state` (four values), `waiting_for` (only with `waiting`), `failed_version`, `updated_at`, `can_install`; an unknown code, state or wait is left out, not guessed, and an older hub's object maps as before. The setting maps `auto_update` (on unless `false`) and `halted` (while `halted_version` names one). | The contract's fields are optional for older hubs; leaving an unknown value out keeps a newer hub from breaking an older Whombat. |
| AU-S02 | **The three endpoints are owners' and go through `act` and the commit pipeline** like every hosts change: `hosts.updateAgentSettings` PATCHes `/agents/settings` `{auto_update}` and signs “Turned on/off Keep server agents up to date” (`op: agent_settings`, `serverId: whombat`, no Done recently row: a setting of the whole Whombat, like checks and maintenance); `hosts.updateAgent` POSTs `/agents/update` `{servers: [id]}` as the person (admin) and signs “Asked the agent on {server} to update” or “Started the agent’s last install on {server}” (`op: agent_update`, the build's version in the payload), also without a Done recently row: AU-S04 records the finished update. A server `/agents` doesn't list is 404 “There’s no server called {id}.” before the hub is asked. | The press isn't the update; Done recently says what happened once it did. |
| AU-S03 | **`updating` or `installing`** (`HostAgentUpdateAccepted`): the hub's own word when its answer has one (`state`, or the server in `installing`), else from the update Whombat read just before the press — `no_key`/`other_key` means the last install (AU-07), anything else a signed update. **Refusals in words** (`op: agent.update`, with the server's reason code as read before): `update_running` “Another update is already running. Try again in a few minutes.”; `needs_install` “{server}’s agent needs one more install, and Whombat can’t run commands there. Run its install command on it once; the System tab has it.”; `nothing_to_update` by the reason — “The agent on {server} is already up to date.”, “{server} isn’t connected right now, so its agent can’t be updated.”, “Updates are turned off on {server} itself.”, “{server} already runs a newer agent.”; `no_build` “There’s no new agent version to install yet.”. All `conflict` (409); the shared codes (`agent_offline` …) keep their words. | The hub's `nothing_to_update` covers five reasons; the reason code Whombat already read names the right one. |
| AU-S04 | **A finished update is one line in Done recently, “Updated the agent on {server}”** (`hosts.change`, kind `hosts.agent_updated`, from/to in the payload, no Undo, no message anywhere), when the hub's `agent.update` says `updated`. Signed by the person who pressed Update now on that server within 30 minutes (remembered in memory; a person who left meanwhile falls back), else by the burrow's **Servers signer**: a system principal named “Whombat” (`principals.system = 'servers'`, made on first use like GitHub's, Feedback's and the tracker's; clients see it as `system: 'automation'`, a closed enum). Each server and version is signed once (a repeated event within an hour isn't), one after another in the order heard (the first makes the signer). The person's own press is on the server's page, not on Home (HR-05); Whombat's automatic one is on both. | “Signed by Whombat for the automatic ones” needs an agent-shaped signer for Home's Done recently (it lists only what an agent did); signing as the person's assistant would claim it did something it didn't. A restart forgets a press: that update is then Whombat's. |
| AU-S05 | **Worth a look: a failed update and a needed last install**, as hints of the server's detail (kinds `agent.update_failed` and `agent.needs_install`, warning, section `system`, the way out as the detail) and as Watch items linking to `?tab=system`. Failed: “The agent on {server} couldn’t be updated, so it went back to the version it had.” · “Try again on the System tab.” Last install: “{server}’s agent needs one more install, then it updates itself.” · “Update the agent on the System tab.” where `canInstall`, else “Run its install command on it once; the System tab has it.” **The hub's `agent.outdated` (“Agent … differs from the hub”) is left out** where one of these says it, or where the agent updates itself (`auto`, `updating`, `waiting`, up to date); it stays where nothing will update it (its own switch, the setting off, no build, a newer agent), and as the hub gave it from an older hub. | The brief's words; one thing said once. The buttons are the System tab's (the app); Watch items carry a link, not actions. |
| AU-S06 | **`halted` alone is not a failure of that server**: Worth a look shows the failure on the server where the new version didn't come back (`failed`, or its `failedVersion` still the build's), not on every server the halt stopped; Try again there clears the halt (the hub's rule). | Saying “couldn’t be updated, went back” about servers that were never tried would be wrong, and N copies of one problem is noise. |
| AU-S07 | **`agent.update` events keep their data** on the hosts change (`kind: 'fleet'`, `data`), so the follow-up hears `updated`; realtime still sends `hosts.resync` for them as before. | The smallest change to the change notices; the clients reread the server's settings on a resync. |
| AU-S08 | **`hosts.agent_updates` is listed as implemented** (code-level like every runtime feature, SWU-S11); without the hosts service `hosts.status` already says there are no servers. | `runtime-features.ts`' rule: the same list on every box. |
| AU-S09 | **The fake hosts service updates agents** (`testing/fake-agents.ts`): a signed build, every agent one version older with the key, shale and quartz without one (shale lets Whombat run commands as root, quartz doesn't), the offline server not connected; `/agents/settings`; `POST /agents/update` with the hub's refusals, clearing the failed mark and the halt; the agent back on the build at once or when a test says (`finish`), and `wait` / `fail` for the round's states, each emitting `agent.update`. `GET /agents` answers only with `serve` on, so the fleet's switches in the other tests stay the cards'. | Tests show the whole flow without a real hub; the app's dev world has its own fixtures. |

## Left for others

- The buttons (Try again, Update the agent, Update now) and the Updates row are the app's (AP-2980…); they can tell
  Whombat's hints by their kinds.
- Whether the hub's `POST /agents/update` answer names the last install (`installing: [id]` or `state`) is the hosts
  stream's; Whombat works either way (AU-S03).
