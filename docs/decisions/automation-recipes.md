# Automations from a simple form, GitHub issues, and Delete (AR)

John, 2026-10-09: building an automation where Banjo assesses a repository's new issues and pull requests was “way too
complicated” — the step editor with step ids, templates, conditions and limits was the only way to make one —, issues
weren't supported, and an automation couldn't be removed. He asked for a flow led by the trigger: *when* something
happens, *who* does *what*, and *where* the answer goes. Contracts CT-322 (0.66.0: `AutomationRecipe`,
`automations/recipes.ts`, the `github_comment` step, `StepWorkspace.pullRequest`, `automations.delete`,
`automations.samples`, `Automation.summary` and `deletedAt`, features `automations.recipes` and `automations.delete`);
whombat-app `docs/decisions/automation-recipes.md` for the form. Everything of `bp-automations.md` (BP-C01…C41) still
holds: a recipe is an ordinary definition, validated, signed, published and run like any other. (The `AR` prefix is this
file's; `agent-roles.md` and `agent-repos.md` number their own.) User guide: `docs/automations.md`.

## GitHub issues and pull requests

| # | Decision | Why |
|---|---|---|
| AR-06 | **Issues are read only for repos a live automation listens to** (published, not deleted, an `issue_opened` trigger in its current version): one conditional read of the newest 50 open issues per poll, at the repo's cadence and under the poller's rate-limit rules (PL-01). Pull requests in the list are left out (they come with the pull requests). | Nothing else uses issues; a 304 is free, but no read at all is cheaper. |
| AR-07 | **The first read is a baseline**: `github_poll_cursors.issues_since` (now) and `issues_after` (the highest open issue number, or the highest pull request number the burrow knows — they share one sequence). After it an issue is new when its number is higher and GitHub says it was opened no earlier than an hour before the baseline. When nothing listens any more the watch ends (both cleared), and the next starts with a new baseline. | History never replays (BP-C07): issues open before an automation listened, an older issue reopened, and issues opened while nobody listened start nothing. The hour covers clocks that differ. |
| AR-08 | **A new issue is mirrored once** (`github_issues`, unique per burrow, repo and number; body cut to 8 KB) with a signed `issue.opened` by its author when their login is linked, else by GitHub — the mirror command pattern of pull requests. No room post. At most 20 per poll; the rest next time (no ETag kept). | Polling again changes nothing; the issue lives on GitHub, the automation's thread is the conversation about it. |
| AR-09 | **Drafts and bots.** `pull_requests.draft`, `author_login`, `author_bot`, `body` (8 KB). Bots: `user.type` Bot or a `…[bot]` login, for issues and pull requests. A draft marked ready makes the mirror sign `pr.ready`; the engine maps it to `pr_opened` with `readied: true, draft: false`, so only triggers that leave drafts out fire on it. `pr.opened` carries `draft` and `bot` as they were when it opened, and the engine reads those over the row (a draft readied before the scan must not fire twice). Every pull request event's facts carry `draft` and `bot`. | Contract `TriggerFacts`; a draft is work in progress, a bot's is noise for an assessing agent. |
| AR-10 | **`pr.updated` after a push the poller mirrored first counts as new commits** (`action: synchronize`): the push moves the head before the update, so its `headMoved` was false and `pr_updated` never fired. | Found writing “New commits on a pull request”; the event was there, the engine's reading of it was wrong. |
| AR-11 | **`{{trigger.*}}` of an issue or pull request**: `kind: github`, `event`, `item` (`issue` · `pull_request`), `repo`, `number`, `prNumber` (pull requests only), `title`, `body`, `author`, `bot`, `url`, `labels`, `draft`, `fork`, `branch` (a fork's is `owner:ref`), `base`, `sha`, `checksState`, and `text`: “New issue #142 on acme/web by @jdoe: “Login button does nothing””, the link, labels, “It is still a draft.”, for a fork “This pull request comes from a fork: read its code, don’t run it.”, then the description cut to 2000 characters. Pull requests: “New pull request #57 … (feat/login → main)”, “Pull request #57 … is ready for review: …”, “New commits on pull request #57 …”, “Checks failed on pull request #57 …”. The run's trigger summary is that first line. | A recipe's prompt embeds `trigger.text` and is rendered to at most 3900 characters; `prNumber` only for pull requests makes an issue's checkout the default branch. |
| AR-12 | **One thread per issue or pull request.** A GitHub run with a number has `automation_runs.item_key` (`github:acme/web#57`, lowercase repo); its `threadRootId` is the thread of the latest earlier run of the same automation about the same item in the same room, while that root message is there. The first step then posts in it (`thread: run`). Test runs have no item key and start their own thread. `activeRunInThread` (BP-C32) only applies to message triggers, so these runs are never dropped. | Everything about one issue in one place in the channel. |

## Comment on GitHub

| # | Decision | Why |
|---|---|---|
| AR-13 | **`github_comment` decides with the automation's `pr.comment` ∩ the publisher (`keyDecision`, repo scope), as `open_pull_request` with `pr.open`.** Can: the step is marked `running` (its comment rendered and kept) and the engine posts it in its own pass, as the burrow's GitHub connection (`githubScope`, `externalEffect`). Asks: an approval bound to the step and attempt (`automation.continue_step`, the comment as its details, re-rendered by the guard); a yes puts the step back to pending with `commentApprovalId` — the `dispatch_agent` pattern — so the GitHub call never runs inside the approvals engine. No, a repo not switched on (or kept on the Whombat): `otherwise` (`skip` the step and go on, or `fail` the run as Blocked); a person's no follows `otherwise` too. | The same authority rules as every external step; network inside a transaction is avoided. |
| AR-14 | **Outcomes**: GitHub refusing (4xx) fails the step (a known outcome; retries as the step says); anything else (no answer, a 5xx, a crash between marking and answering) is `uncertain` for a person (BP-C06) — no reconciling by reading comments back, as `http_callback`. The comment ends with “\n\n— Banjo via Whombat” (the agent of the nearest agent step before it; none: “— via Whombat”), as agents' own GitHub writes (agent-gh.md AGH-13). A number that renders to nothing skips the step: “Nothing to comment on: this run didn’t start from an issue or pull request.”; an empty text skips it too. Output `{number, commentUrl}`, input summary “Comment on acme/web#142”. | A duplicate comment is worse than a person checking once; readers on GitHub see who wrote it. |

## Pull request checkouts

| # | Decision | Why |
|---|---|---|
| AR-15 | **`workspace.pullRequest` (read only) renders to a number → that pull request's head.** Found in `pull_requests`, else on GitHub. An open pull request from a branch of the repo: that branch, its base the pull request's base. A fork's (its branch keyed `owner:ref`) or a closed one (its branch may be gone): the branch **`pull/<n>/head`** — the server↔runner convention, no contract change: the runner fetches GitHub's `refs/pull/<n>/head` to `refs/remotes/origin/pull/<n>/head` (`pullRequestRef`, after the mirror's prune; into an owner's clone too), so preparing, exporting and diffing work as for any branch. A missing ref fails the checkout (the turn works without one and says so) instead of silently reading the base. Renders to nothing: the base, as without it. Whombat's own pull requests (a repo kept on the Whombat, local-only ones) use their branch. The step's input summary says “reads pull request #57” (AR-39; was “reads PR #57”). | A fork's code is on no branch of the repo; `refs/pull` is where GitHub keeps every pull request's head. Read-only exports never push. |

| AR-20 | **Features `automations.recipes` and `automations.delete`** are advertised (`IMPLEMENTED_FEATURES`); `automations.delete` (`DESTRUCTIVE`) and `automations.samples` (`READ`) run over a session through the same REST handlers as every `api` op. | Clients show the form and Delete only on runtimes that have them (CT-322). |

## Fixing the bugs it finds (AR-24…)

John, 2026-10-09, on the recipes above: when Banjo's assessment finds a real, important bug, Banjo fixes it — “When
banjo is sure that this is a good possibility to fix, then I think it should automatically fix” —, with certainty that
it is a bug and that it matters, and fixing on its own an explicit opt-in, never on by itself. Contracts CT-323 (0.67.0:
`AutomationAssessment`, `DispatchAgentStep.assessment`, `RecipeFix`, `fixSteps` — `worth_fixing`, `needs_yes`,
`approve`, `fix`, `review`, `approved`, `pr`, `pr_open`, `linked` —, `report_assessment`, `run.*` in conditions,
feature `automations.fixes`). The form offers *Only assess* (the default), *Ask me before fixing* and *Fix it when
sure*.

| # | Decision | Why |
|---|---|---|
| AR-24 | **`report_assessment` is an assessment turn's only**: listed (`ServedSelection.assesses`) and run only for the agent of a dispatch with trigger `automation` whose step has `assessment: true` and still waits for that very dispatch (a retry's new turn replaces it), while the turn is claimed or running. Anywhere else: “report_assessment only works in a turn where an automation asks you to assess an issue or pull request. Answer in the conversation instead.”; after the turn: “This turn has ended, so its assessment can’t change any more.” Feedback assessments and reflections keep their own lists. The handler lives in `mcp/tools.ts` (the engine loads `automations/assessment.ts`, never the MCP tools). | What the agent reports decides whether code gets written: only the turn that was asked may say it. |
| AR-25 | **The report is kept on the step**: `automation.report_assessment` (signed by the agent, `automation.assessment_reported` with the line, under the run's lock) puts it with its `line` in the waiting step's `output.assessment`; the last report counts and returns `{line}`. When the step succeeds, the settle reads it under the run's lock — none (or one that doesn't parse) is `unassessed()`, “Not assessed” — so `steps.<id>.assessment.*` always exists. A missing report never fails the step. The run page shows it as soon as it is reported, redacted like any output. | A report that lands as the turn ends isn't lost, and nothing follows from a missing answer (`unclear`: `worth_fixing` stops the run). |
| AR-26 | **Fixing on its own is opt-in and narrow**: only `Fix it when sure`, and only when every gate of `needs_yes` passes — the agent is sure (high confidence) and the fix small, `trigger.trusted`, nobody `trigger.assigned`, no `trigger.linkedPr`, not `run.test`, `run.today.fix` under `maxPerDay` (default 5). Anything else asks a person in the issue's thread, as *Ask me before fixing* always does. Merging is never the automation's, unless its person turned on merging (AR-44). | John's words: sure, important, opt-in. Each gate is a reason a person should look first. |
| AR-27 | **`trigger.trusted`: the author's `author_association` is OWNER, MEMBER or COLLABORATOR** (any case); anything else, or unknown, is not trusted. The adapter reads `author_association` and `assignees` for issues and pull requests, the mirror stores them (`github_issues`, `pull_requests`, 0096) and `fetchGitHubItem` fills them for samples. | Someone outside the repo can write anything in an issue; it must never make an agent write code on its own. |
| AR-28 | **The gate reads GitHub now, and asks when it can't**: before the engine evaluates a condition that reads `trigger.trusted`, `assigned` or `linkedPr` in a run about an issue or pull request, it reads them from GitHub (the issue's association and assignees; the repo's open pull requests), outside the transaction, and hands them to `execute`; they apply to that condition only and are kept in its output (`checked`). GitHub not connected or not answering: not trusted, assigned and linked (`unreadable` says why, also in the step's summary), so it asks. `linkedPr`: an open pull request whose title or description has a closing keyword (close/closes/closed, fix/fixes/fixed, resolve/resolves/resolved, any case, an optional colon) before `#n`, `owner/repo#n` or the issue's link — `#1420`, `hotfixes #n` and a mention don't count — or whose head branch is `feat/issue-<n>` (a fork's too). A pull request's own `linkedPr` is false. At trigger time the values come from the mirror. | An issue gets assigned, or someone opens a fix, while the agent assesses; a gate that can't see must not act. |
| AR-29 | **`run.test` and `run.today.<step>`**: `run.today` counts the other runs of the automation created in the 24 hours before now that started the step (`started_at` set; test runs too), with a number for every step of the definition — `null < 5` is true in a condition, so a missing count must never read as zero. Computed when a step executes and in the approval guard (the same scope, so an approved card renders the same), and only for definitions that read `run.today`. | The daily cap; a fix started from a test run is still a fix. |
| AR-30 | **The fix runs on the existing machinery**: `fix` is a write checkout of `feat/issue-<n>` (the developer's branch key ∩ the publisher: Can goes, Asks waits for a person's yes and lets that push through, No is Blocked); a turn without new commits fails the step with what the agent said — how “I couldn’t reproduce it with a failing test” ends —; `review` gives a verdict; `pr` opens “Fixes #n” under the automation's `pr.open` (or posts it for a person); `linked` tells the issue; the merge stays with a person, unless its person turned on merging (AR-44). A run that stops at `worth_fixing` or `approved` ends succeeded; a no at `approve` stops it (“Mara declined, so it stopped.”) and says so in the thread. | Nothing new to trust: every step is one that already exists, with its keys and audit. |
| AR-31 | **An automation's approval card is in the run's thread** (top level while the run has none yet), not at the top of the channel. It replaces “in the channel, as every approval card is” (the golden path's Suspected bug now asks in the report's thread too). | One issue, one thread (AR-12): the yes for a fix sits under the assessment it approves. |
| AR-32 | **A recipe that fixes bugs**: `recipeProblem`'s words as a 400 (a reviewer who also fixes, fixing without new issues); the developer (`fix.developerId`, else the recipe's agent) and the reviewer must be agents an automation can ask (“Pick an agent of this burrow to fix the bugs.” / “… to review the fixes.”); both join the recipe's channel through `add_members` as the person, as the agent does (AR-02), when it is made and published; the automation gets “Open pull requests” at Can for the repo, beside “Comment on pull requests” for *Also answer on GitHub*; the sentence names the developer when it isn't the recipe's agent (`buildRecipe`'s `names.developer`; `describeAutomation` passes it from 0.67's 8e3efe5). | The form's few clicks, as AR-02 and AR-03. |
| AR-33 | **Published again, a recipe gets the keys it needs that it holds no row of** (turned to fixing in the form: “Open pull requests”); a key a person set on the Keys tab — Asks, No, other repos — stays as they set it. | Turning fixing on must work without a keys step, but a person's explicit choice wins. |
| AR-34 | **WHAT HAPPENS of an automation's approval is its details' paragraphs** (split on blank lines), each at most 280 characters cut at a word with “…”. Was: the first 280 characters as one item, which cut the fix's “If you say yes, …” mid-sentence (found by the web agent). | The card says what a yes does, whole. |

| # | Decision | Why |
|---|---|---|

| # | Decision | Why |
|---|---|---|
