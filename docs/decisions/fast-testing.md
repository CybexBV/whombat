# Fast testing (FT)

John, 2026-11-12: remove Repositories (the repository manager) and the build servers (check servers, runners) from
Whombat. They caused many issues, and development must be fast. In their place is `fast-test`, a tool of its own
outside Whombat: it tests only what changed, quick tests on the machine the work is on and heavy ones on The Titan
by itself.

| # | Decision | Why |
|---|---|---|
| FT-01 | **Repositories is gone.** The builtin connection and its page, each repository's rules and presets, the rules block Whombat wrote into AGENTS.md and CLAUDE.md, setting a repository up with the assistant (the look, the plan, the practice run), night runs, a repository's production setup and the `production_release` tool, and DEV delivery driven by repository rules (named destinations, signed permission for one job, firm limits, merge waits for rules, `delegations.authorize` and `delegations.resume`). Rows superseded: all of `archive/repo-manager.md`, `archive/repository-delivery.md` and `archive/repo-setup.md`. | Rules saved in two places (Whombat and the files) drifted, a rule that couldn't be read stopped merges, and every hand-over waited on a policy read. A repository's own AGENTS.md or CLAUDE.md already says how to work in it. |
| FT-02 | **The build servers are gone.** `checkServers.*`, setting a server up with `whombat-check`, its runner and its updates, jobs and VM jobs, GitHub Actions run on a server over an SSH link (and the GitHub calls that registered runners and read recent jobs), other computers that sent checks, server reviews and the questions to the assistant about a server. Rows superseded: all of `archive/check-server.md`. | A runner Whombat installed and kept up to date on the person's servers was the largest source of trouble; `fast-test` sends heavy tests to The Titan without Whombat in between. |
| FT-03 | **Testing is `fast-test`.** A separate tool (`~/.local/bin/fast-test`, its recipe `.fast-test.json` at a repository's root) tests only what changed since the default branch: quick tests here, heavy ones (VMs, Nix, databases, wide changes) on The Titan by itself. Exit 0 passed, 1 failed, 2 couldn't run. `fast-test --full` runs everything on The Titan, only when someone asks; The Titan runs the full suite of `main` every night. Whombat doesn't install, configure or watch it. | One way to test, the same for people, agents and checklists, and fast by default. |
| FT-04 | **A checklist's threads test with `fast-test`** when the repository has a `.fast-test.json`, otherwise with the quick checks its AGENTS.md or CLAUDE.md names for what changed (the linter, the type check, the tests of the parts touched), plus its own checks before a push. Never the full suite. When `fast-test` couldn't run (2), the thread says so and doesn't run the full suite instead. Supersedes the “focused checks” of delegate.md DLG-45 and DLG-64. | The full suite is what made checklists slow; it runs at night. |
| FT-05 | **The final check of a combined candidate** is that same `fast-test` run (or the quick checks) on its exact revision when the default branch requires no checks on GitHub, reported as `local: fast-test`; CI isn't waited for, and a CI result that already failed on the revision still stops the merge. When branch protection requires checks, they are waited for as before (`ciGate`). Supersedes delegate.md DLG-62's “the project's own full check”. | Waiting for CI is the person's choice on GitHub, not Whombat's. |
| FT-06 | **A checklist merges into the default branch by default, then goes to DEV.** `merge` is on unless the person or the assistant turns it off. Once Whombat merged the checked candidate, the final row's thread does one more step: it puts the work on DEV the way the repository's AGENTS.md or CLAUDE.md says, unless the checklist's rules say not to; when they say nothing about DEV, it skips that and says so. Never production. The thread's answer is the report: Whombat doesn't read a live revision itself. However that step ends, the work stays merged; a retry of the final row puts it on DEV again (`DEPLOY_AFTER_MERGE`, `deployBrief` in `delegate/briefs.ts`). Supersedes delegate.md's “Named DEV deployment” line and DLG-68's rule read. | The person tests on DEV right after the work lands, as with their own changes, and the repository already says how its DEV works. |
| FT-07 | **Production only when the person asks.** A checklist, its threads and the threads the assistant starts never deploy to production. When the person asks in their own message to release a repository to production, the assistant hands exactly that request to T3 Code in that repository, whose own instructions say how, and tells them how it went. | No card or production setup to keep in step; the person's own words are the go-ahead. |
| FT-08 | **The data stays until a later migration drops it.** The tables `repo_places`, `repo_rules`, `repo_setups`, `repo_night_runs`, `check_servers`, `check_server_clients`, `check_server_computers`, `server_runner_facts`, `check_server_asks`, `check_server_actions` and the column `delegations.delivery` stay in the schema; nothing reads them. Removing a Vault server, or a Vault key with servers, deletes the check-server rows that still point at it instead of refusing. | No data goes in the same release that removes the feature, and a leftover row must not hold a Vault server hostage. |
| FT-09 | **No contracts release.** None of the removed shapes (the `repoManager`, `repoSetup` and `checkServers` endpoints, `delegations.authorize` and `resume`, `RepoDelivery` on the card and the dispatch context, `production_release`, the `repositories` catalog entry, the `chk`/`rpl`/`rrl`/`chc`/`cka`/`chx`/`cmp` id kinds) was in a contracts release (contracts-v3.21.0 predates them), so the session protocol keeps its version. The settings map loses those ops and the `goesAhead` marker only they used (assistant-settings.md ASG-18). | Nothing outside this repository ever saw them. |
| FT-10 | **What a box notices.** Home and Connections no longer show Repositories; the Inbox items for build servers and night runs go with their sources; a `production_release` approval still pending says nothing happened on a yes; T3 Code threads the assistant starts no longer get saved rules appended; a council's members no longer get them either. | The person sees the feature gone, nothing broken. |
| FT-11 | **This repository's own CLAUDE.md** loses the rules block Whombat wrote and every instruction to run `pnpm check` on TheTitan with `whombat-check`; its “Testing (fast testing)” section says to run `fast-test`, never the full suite or a wait for CI, and that the full suite runs every night. | The repository follows the same way of testing as the checklists. |
| FT-12 | **A failing test runs once more by itself, not the step around it** (John, 2026-11-13: “I want tests to finish quickly”). Under `fast-test` (`FAST_TEST=1`) every Vitest config retries a failed test once (`scripts/vitest-project.ts`), and the recipe's Vitest steps, the full check, Biome and the type check say `"retry": false` (`"fullRetry": false`), so `fast-test` doesn't run them a second time. A file that can't load is not retried: that is a failure. | `fast-test` ran a failing step whole again before it said so: a failing full check took 249 s instead of 131 s, and one flaky test in 2,378 doubled the server's integration suite (271 s instead of 134 s). |
| FT-13 | **`pnpm check` runs its four parts side by side** (Biome, the notices check, the type check, the unit tests; `concurrently --group --kill-others-on-fail`): the first to fail stops the others, and each part's output is printed whole. | Lint and types took about 17 s in front of the tests on The Titan, and a lint error is known in seconds instead of after the whole run. |
| FT-14 | **`fast-test`'s runs on The Titan keep Vitest's transformed modules** between runs, in the folder the runner gives them (`FAST_TEST_CACHE_DIR`; the recipe asks for it with `"caches": ["build"]`, one folder per run at a time). A run with `CI=true` and no such folder (ci-platform's check) still transforms everything afresh. | A Beast run's checkout is new every time, and transforming was 31–41% of the suite's time there. The cache's key is the one every developer machine already relies on (a module's path and content, the configs, the lockfile, where imports resolve to); ci-platform's check stays the run that depends on nothing earlier. |
| FT-15 | **A change to a shared package's source is not a wide change.** `packages/*/src/**` (`wideUnless`) runs the step `dependents` on The Titan instead of the full check: the type check of the package and of every workspace that depends on it (`pnpm --filter "...<package>"`), and every unit test in any workspace that imports the changed files (`vitest related`, all projects). Everything else in `packages/` (a `package.json`, a config, a deleted file) is still wide. | More than half the runs (13 of 23 on the first day) ran the whole suite. A small package's change now runs the tests that can see it. `vitest related` follows imports only: a test that reads a package's files without importing them is left to the nightly full run, which is what that run is for. |
| FT-16 | **The integration steps bring their own Postgres when they need one** (`fast-test with-postgres`, leased through `agent-resource` and removed with the run). `server-int` and `cli-int` use the shared development Postgres on :55432 when it answers and a throwaway one otherwise; `server-int-all` always runs in a throwaway one, with the 16 workers of its config. | The shared Postgres allows 100 connections, and tests failed with “too many connections” when two suites overlapped; and it was stopped on 12 and 13 November, which failed every run with database tests. More workers were tried and left out: 32 on a busy machine took 151 s against 134 s and failed two timing-sensitive tests that pass alone. |
