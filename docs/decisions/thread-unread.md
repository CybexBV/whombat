# Which threads have something new (TU)

John, 2026-11-02 (main checkout): “In Whombat chat we can have several chat threads open and I need an easy way to see
which thread has unread messages.” After the proposal (a read marker per thread, a dot on threads with something new,
the badge counting such threads): “Implement this fully, apply on dev after you are done.”

Until now a room had one read marker (`read_states`) and its badge counted only top-level messages (channel-threads.md
CH-05). In Chat every answer is a reply in a thread, so the assistant's answers never showed as unread anywhere but the
inbox and push.

| # | Decision | Why |
|---|---|---|
| TU-01 | **A read marker per thread** (`thread_reads`: thread, viewer, the `ord` read up to; migration 0025). A message in a thread of the person's Chat or Feedback room is new to them when someone else wrote it, it isn't deleted and it comes after their marker. A thread's first message is also passed once they read the room past it (`read_states`), since the room shows it. No marker: everything from others in it is new. | The room's marker can't say which threads were read; the first message is read where it is seen, in the room. |
| TU-02 | **Writing in a thread reads it** up to the person's message (`postMessage`, same commit), and **settling by hand reads it** to its end (`chats.settle`, `chats.settleFinished`). Settled threads count for nothing; a new message opens one again (CHS-04) and then counts. | Someone who answers or puts a thread away is done reading it; nothing hidden under Settled keeps a badge up. |
| TU-03 | **Chat's and Feedback's badge counts threads with something new**, not messages (`unreadCounts` in those two rooms; `mentions` as before). Channels, task chats and other rooms keep counting top-level messages (CH-05). A reply there publishes the person's badge (`conversation.unread`), and so does the person's own message there (it may have read a thread), so their other devices agree. | “Which thread has unread messages” is a number of threads; the person's two rooms are where every answer is a reply. |
| TU-04 | **`chats.unread`** lists the room's open threads with something new and how much (newest activity first, at most 200); **`chats.readThread`** reads a thread up to a message, never backwards, and answers what is left in it and the room's badge. Both through the session (`READ`, `RECEIPT`); the read is a private marker, not signed (C-12). | One small list the apps hold beside the room, asked again whenever the room's badge moves, instead of a per-viewer field on every message, which realtime frames (built for nobody) couldn't carry. |
| TU-05 | *Superseded by chat-inbox.md CIB-04: the inbox row's dot, bold title and count.* **The apps show a dot** on a thread's reply row in Chat and Feedback, “New replies” to screen readers: on the web an 8px brand dot in the gutter under the face, on the row's line; on the phone an 8dp one first in the row. Never on the thread open on screen (beside the room, or in the phone's right page). The sidebar's and the phone's Chat badge show the room's count. | A dot says “something here” without a second number on every row; between “3 replies” and “Last reply” it read as a separator, and in the gutter nothing in the row moves. The open thread is being read. |
| TU-06 | **The open thread reads itself** while it shows (the tab visible, the app in front) and something in it is new: up to its newest message, once per newest message. It also reads the thread's inbox rows (AP-704). An older Whombat without `chats.unread` shows no dots. | Reading happens where the person reads; a background tab or app shouldn't clear what nobody saw. |
| TU-07 | **No contracts release.** The endpoints and the table are additions nothing outside this repository uses; the session minor stays. Existing threads with replies start read up to their newest message, so nothing lights up on upgrade. | Additions matter to other repositories only when they use them. |
