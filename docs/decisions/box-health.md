## A. Old images (BH-01, BH-02)

| ID | Decision | Why |
| --- | --- | --- |
| BH-01 | **Superseded by one-person.md OP-04, OP-13**: there are no computer images to remove. **computerd removes old images itself**, once per process, as soon as the current base image is known: found at start (`prepareImage`, when computers become available) or just published by a build (a turn's or the one ahead of time). Kept: the current base image of this agent uid/gid, the newest older one (not necessarily version − 1), any newer one (a rolled-back computerd's newer image comes back with the next release), base images of another uid/gid (another install on the same Incus), any image with an alias of someone else's, and the newest cached copy of the builder's source (`images:debian/13/cloud` → cached, unaliased images whose `update_source.alias` is `debian/13/cloud`, newest by upload). Removed: the other base images and the other cached copies, by fingerprint (`incus image delete`), one info line per image (“removed an old base image: whombat-computer-base/5-u952g952 (970 MiB)”). Nothing is removed when the current image isn't in the listing. A delete or a listing that fails is a warning; the start, the build and the turn go on (`imagesToPrune` is pure and tested against the box's store). | Only the current image makes new computers; the one before it is what a computerd rolled back one release would use, so a rollback doesn't rebuild for minutes. A build runs only while no image is known (`#baseImage` holds one build at a time per process), so “after the image is known” is never during a build. Incus' own `images.remote_cache_expiry` (10 days unused) would flush the cached copies eventually, never the published base images. |
| BH-02 | **Superseded by one-person.md OP-04.** **Computers from a removed image keep working.** On the box's `dir` pool every computer is a full copy of its image's files; on `zfs`/`lvm` Incus keeps a deleted image's volume while instances still depend on it (it renames it out of the way), and on `btrfs` (the next stream's pool) a computer is its own subvolume snapshot, which doesn't depend on the image's after it is deleted. `user.whombat.image` stays what it was (the computer's view, `DOCKER_SWITCH` and `ENSURE_TOOLS` read the version from it, not from the store); a reset makes the computer again from the current image. ## B. Session events that don't fit (BH-03…BH-05)

| ID | Decision | Why |
| --- | --- | --- |
| BH-03 | **A lasting event that doesn't fit in a session message drops its subscription with `snapshot_required`**, for any event type: the session closes the subscription as an `unsubscribe` would (its registration in the event log closes, so events already queued for it are skipped by `deliver`'s `closed` check, and anything still in flight for it is dropped by the session), logs a warning with the event's `type`, topic and size (“session event too large for a session message; the client reloads that view”; an event invalid for another reason is an error with the same fields) and sends `snapshot_required{sub, reason: 'overflow', cursor: <that event's cursor>}`. The client refetches its snapshots for those topics and subscribes again `after` that cursor, as `SnapshotRequired.cursor` says (whombat-app AP-1097 makes the client do it): it gets everything after the big event and the big event's effect through the snapshot. During a replay (`subscribe` with `after`) the same holds: nothing after the big event is sent and the subscribe is answered with that `snapshot_required` instead of `subscribed`. `pr.updated` itself isn't made smaller here. | 38 `pr.updated` events of ≈85 KB (a pull request of 500 files and 218 commits) were logged as `session message did not encode` and dropped, and the app's view stayed stale until a reload. The snapshot is the one path every client already has for “you missed something”. |
| BH-04 | **The reason stays `overflow`**: `SnapshotReason` is a closed enum (`cursor_expired`, `restart`, `authz_changed`, `overflow`) that installed clients validate; a new value would be a bad frame for every one of them. The client's action is the same for each reason. **An ephemeral event that doesn't fit** (typing, presence) is dropped with a warning naming its type and topic; the subscription goes on (the next one replaces it). **Anything else that doesn't encode** keeps its error log (`session message did not encode`), now with the message kind (`t`), the size and, for an event, its type; a result or outcome that doesn't fit is answered `too_large` as before. | No protocol change; the logs say which event type grew, so the next fix (a smaller `pr.updated`) has its evidence. |
| BH-05 | **Subscribes of one subscription id are answered in order**, the newest one winning: each id has a slot whose generation every `subscribe` and `unsubscribe` of it bumps; a subscribe checks it after each await, and one that was superseded meanwhile (a resubscribe racing a topic change, or an `unsubscribe`) closes what it registered in the event log and sends nothing — no `subscribed`, no events, no `snapshot_required`. An `unsubscribe` closes the live registration and supersedes a subscribe still being answered. Different ids stay concurrent (one id's replay doesn't hold up another). The subscription cap counts answered subscriptions, as before. | Found by the app stream (whombat-app AP-1097 resubscribes after every `snapshot_required`): two subscribes of one id in flight both registered while only the later close was kept, so events arrived twice until the session ended, and an `unsubscribe` during a subscribe didn't close it. The generation check is local to the session; a per-id promise chain would also order them but make a resubscribe wait for an outdated replay. |

## D. Log hygiene (BH-09, BH-10)

| ID | Decision | Why |
| --- | --- | --- |
| BH-09 | **An outage of the control plane is one story in the log, not a line per retry.** One small helper (`lib/outage.ts`, `Outage`) for the three retry loops that met the dev control plane restarting: the relay's control connection (its WebSocket upgrade answered `Unexpected server response: 502`, or no connection at all), the relay's admission ticket from the manager (`/v1/runtime/ticket`) and the feedback drop's pull (`/v1/runtime/feedback/pull`), both `control unavailable: control HTTP 5xx` from the manager. The first failure is info (“relay: the control plane isn’t reachable; retrying”), the retries are debug, an outage still on after 5 minutes gets one warning (“… still isn’t reachable after 5 min; retrying”), and the next success one info line (“… is reachable again after 2 min 10 s”, with `downForMs`). While the relay is in such an outage its `relay control connection closed` lines (one per retry, 94 in two days) are debug too. What counts as an outage: a manager call that failed `unreachable` (its socket missing or silent — the manager restarting with an update) or with a 5xx (`managerUnreachable`), a relay upgrade answered 5xx or a connection refused, reset, timed out or not resolved (`relayUnreachable`). Everything else — a refused ticket, a 4xx, a bad frame — keeps its warning as before. The manager's own “control poll failed” warnings are the appliance's (the manager), not changed here. | Every burst on the box lined up with a restart of the dev control plane on the host (55 relay errors and 50 manager-call warnings in two days); a restart that lasts minutes is expected, one that lasts longer is worth one warning, and how long it was down is what someone reading the journal wants to know. |
| BH-10 | **Superseded by one-person.md OP-S42**: the server's computer-events loop is gone. **computerd not answering right after the server starts is info**: the server's computer-events loop logs “computer events: computerd isn’t reachable; retrying” at info during the first 2 minutes after the server started (`COMPUTERD_START_GRACE_MS`) and a warning after that — once for an outage that began inside the 2 minutes and outlasts them, at once for one that begins later — and “computer events: computerd is reachable again after 4 s” when it answers. Same helper, its grace counted from the server's start instead of the outage's. | `connect ENOENT /run/whombat-computerd/computerd.sock` six times on the box, each at a runtime restart: computerd restarts with the server during an update, so its socket is briefly missing. Later, computerd going away is news. |
