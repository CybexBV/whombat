# Visual replies: pages, charts and diagrams in a message

John, 2026-11-01: T3 Code lets a model draw a mockup or a chart and shows it in the chat; Whombat should do the same.
Whombat already showed an agent's HTML page (a ```` ```html ```` block, a raw page, an `.html` attachment) and a Mermaid
diagram live in a sandboxed frame (web AP-320…AP-323, mobile AP-328, contracts CT-149…CT-152). This workstream makes
that work everywhere, look like the app, and get used: decisions VR-01…VR-12.

| # | Decision | Why |
|---|---|---|
| VR-01 | **No new message type or tool for showing a page.** A page or diagram stays a fenced block or an attachment of an ordinary message; `post_message`'s text description says how to style one (`PAGE_GUIDE`). | The block and the attachment already do what T3 Code's `html_render` does, and every client already parses them; a new card kind would have to reach old clients too. A folder of several pages is a page set, shown with `show_pages` (page-sets.md PG-02). |
| VR-02 | **The box's own page frames the preview frame.** On the direct listener `/sandbox/*` answers with `X-Frame-Options: SAMEORIGIN`, the frame's policy with `frame-ancestors 'self'` and `Cross-Origin-Resource-Policy: cross-origin`; the Mermaid runtime (`/assets/mermaid.min-<hash>.js`) gets the same resource policy. Every other answer stays `DENY` / `frame-ancestors 'none'` / `same-origin`. | `frame-ancestors 'none'` on every answer refused the frame, so pages and diagrams were blank on the local network and Tailscale page; the opaque-origin page inside the frame is cross-origin to the box, so `same-origin` refused its script. |
| VR-03 | **Every agent's page gets the app's theme as its first style** (`<style id="whombat-page">`, `withPageStyle` / `framedPage` in core, values from `@whombat/tokens` `pageThemeCss`): `color-scheme`, the variables agents know from other tools (`--background`, `--foreground`, `--muted-foreground`, `--card`, `--border`, `--accent`, `--success`, `--warning`, `--destructive`, `--chart-1…4`, `--chart-wash`, `--radius`, `--font-sans`, `--font-mono`, … `PAGE_THEME_VARIABLES`) and a base sheet (background, text, font, 14 px margin). The page's own rules come later and win. The background is the preview card's surface (`sf`); charts use the app's chart series. | A chart that matches the app and follows light and dark, without the agent knowing Whombat's token names. |
| VR-04 | **The web frame follows a theme change live**: after writing the page it takes `{type: 'whombat.theme', css}` from the app and replaces the theme style's text (never markup). The phone draws the page again. Diagrams are drawn again in both. | No reload or flash on the web; the phone's WebView has no message channel into the page. |
| VR-05 | **The fonts aren't loaded into the frame**: `--font-sans` names Bricolage Grotesque first and falls back to the system's sans. | The frame is an opaque origin and the app's own fonts would need CORS headers; Google Fonts would be a request per page view. A page may embed fonts as data URLs. |
| VR-06 | **A page in a message grows to fit, 80 to 2000 px** (`PAGE_MIN_HEIGHT`, `PAGE_MAX_HEIGHT`), on web and phone; full screen shows the rest. | The 720 px cap cut most mockups in half. |
| VR-07 | **The phone's preview card reads the page's height through the WebView's one message**: an injected script (outside the page's policy) posts `{type: 'whombat.height', height}`, the app reads only a clamped number (`pageHeight`). Full screen has no message channel. Supersedes AP-328's “no `onMessage`” for the card. | The page can post too, but a number within the limits is all it can change. |
| VR-08 | **Superseded by PRS-02** (`preview-security.md`). **Mermaid draws on the phone**, in the same confined WebView, from jsDelivr pinned to the web's exact file (`MERMAID_CDN`: version and `sha384` integrity, a web unit test checks both against the installed package). Without the internet the page shows the source under “Couldn’t draw this diagram here, so this is what it says.” Supersedes AP-323's and AP-328's “Mobile shows the source”. | Bundling the 3.5 MB runtime would grow the APK by about 1 MB; https scripts are allowed in previews (UI-01), and the hash pins the file. |
| VR-09 | **`page_preview` (“Check a page”)**: the agent sends a page (and a width 240–1600, default 720, and a theme); the server frames it as a message would (`framedPage` with the theme), the turn's runner draws it in the agent's Chromium like `browser_preview`'s folder (a context of its own, served from memory, always offline (PRS-01, `preview-security.md`)) and sends back a screenshot of what a message shows, the height, up to 20 console lines (errors first) and how many requests were refused offline. Nothing is posted or recorded (read-only, no event). Served with the browser, beside `browser_preview`. | The agent sees what the person will see and fixes it first, as T3 Code's `html_preview` lets a model do. |
| VR-10 | **The prompt asks for visuals**: numbers with a trend or a comparison as a chart, any mockup, chart or diagram asked for as a page or a Mermaid diagram with one sentence on what it shows, checked with `page_preview` when the turn has it. Chat's Markdown includes tables (they render on both clients). The full styling rules are in the message tools' text description, not the prompt. | Agents never drew a chart unasked; the description reaches every turn that posts, the prompt stays short (turn overhead). |
| VR-11 | **Files opens an HTML page or a diagram in the viewer**, live in the same sandbox and theme, instead of downloading it. | A page saved to Files was only a download. |
| VR-12 | **The page policy has one source**: `PAGE_POLICY` in core; the phone's `HTML_PREVIEW_CSP` is it, the box's frame answer is it plus `frame-ancestors 'self'`, and tests check the web frame page's own meta says the same. | Four copies had to be kept equal by hand. |
