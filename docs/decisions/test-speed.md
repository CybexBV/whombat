# Test speed — 2026-10-18

John asked why tests and CI kept getting slower and whether the testing makes sense. Measured on main `2dfa80b8`:
`pnpm check` about 30 s (3,129 unit tests in 22 s), `pnpm test:server` about 4 min (2,400 tests in 318 files), and the
runtime CI check red since 2026-09-30 (fixed in `local-ci-tests.md` CI-T06…CI-T09).

| # | Decision | Reason |
|---|---|---|
| TS-01 | Integration test files hold 3 Postgres connections each (was 5) and 16 files run at once (was 8): 48 of the shared dev Postgres's 100, so a second suite still fits. Postgres connections, not CPUs, limited the suite: `pnpm test:server` went from about 4 min to about 2 min 15 s. Two connections starve files whose server works on several at once; those files ask for `BUSY_POOL_SIZE` (5): the automations engine's lock (engine-lock, golden-path), the runner (runner, approved-write), the demo clock and the Google guide. CI keeps `VITEST_MAX_WORKERS=4`, which overrides the config. |
| TS-02 | Tests that read “the last” rows of a table order them (`passkeys.int.test.ts` events by `seq`): without `order by` Postgres returns rows in any order, which showed up as a flake once more files ran at once. Likewise a test of racing commits counts every event they add (`audit.int.test.ts`): what 24 parallel messages set off depends on their order (a person replying right after an agent wakes it), so counting only status events was off by one now and then. And a test waits for what the code concluded, not for the request a fake received (`feedback/drop/cycle.int.test.ts`: the sync reached the fake before the service had read its answer, on CI's 4 CPUs). |
| TS-03 | Tests make ssh2 key pairs through `test/ssh-keys.ts` `sshKeyPair`, which makes another when the key doesn't read back: ssh2's `generateKeyPairSync('ed25519')` makes a key neither ssh2 nor OpenSSH can read about once in 300, so a fake SSH server with it failed to start (the Vault canary flake). Production makes keys with `node:crypto` (0 unreadable in 5,000). |
| TS-04 | Tests check the facts a prompt or message must carry (names, ids, paths, tool names, a short key phrase, order), not its sentences. On 2026-10-18, 127 assertions in 60 files matched literal text of 120 characters or more, so every rewording meant editing tests while the match rarely caught a bug. Exact text stays only where the wording is the contract: existing snapshots, prompt-cache prefix stability and short labels. The rule is in CLAUDE.md/AGENTS.md; the three worst files were converted at once (`prompt-turns`, `step-folder`, `handoffs`), the others when they are next touched. The same rule line asks for event waits or injected short timeouts instead of sleeps (80 files slept, 5 used fake timers) and for a reason before a new integration file pays its own database, seed and server. |
| TS-05 | An encrypted PEM key that a given passphrase doesn't open had the wrong passphrase (`vault/ssh-keys.ts` `openPem`). About one wrong passphrase in 200 decrypts to bytes Node reads as an unsupported key (`ERR_OSSL_UNSUPPORTED`): people were told their key type isn't supported instead of “wrong passphrase”, and the unit test flaked. Found while chasing flakes (reported by another session); the regression test uses a fixed key and a known wrong passphrase. |
| TS-06 | **A change reaches DEV in one command, and the tests were not what made it slow** (2026-10-19). John: “when I make a change it takes forever and I think it's because of the test suite.” Measured on the chat-delete thread: 15 min, of which about 2½ waiting on tests (`pnpm test:server` 2,447 tests in about 2 min, run in the background), and then 8 to 27 min per change before it was on his box, an agent working out the appliance candidate steps again each time. Step 4 of “Direct instructions” is now appliance `dev/candidate` (IN-296, about 6 min, dev.whombat.com and John's box). Two small test savings in step 2: `pnpm format` before `pnpm check`, and one repository's check at a time. |
| TS-07 | **Words alone don't need `pnpm test:server`** (2026-10-19). John agreed after the “your things” rename took 15 minutes, 2¼ of them the server suite for one label (`things/actions.ts`, an activity's `where`). A server change that only changes words people read (a label, copy, a comment) is verified by `pnpm check`, once `grep` shows no integration test (`*.int.test.ts`) has the old words; a change to what the server does still runs `pnpm test:server`. The same rename lost 3 minutes waiting on another `dev/candidate` run; appliance IN-299 makes `--help` answer at once, restarts the dev stack beside the box build and has the box ask for its update at once (candidate 0.102.4 took 3 min 32 s, 0.102.3 4 min 23 s); with the manager restarted twice 0.102.5 took 2 min 30 s, and the box's manager now checks on demand (appliance IN-302). |
| TS-08 | **A web test file that renders the whole app loads every screen, pane and modal before its tests start** (`apps/web/src/test/renderApp.tsx`, a `beforeAll` with a 120 s limit, 2026-11-07). The router's screens and the shell's panes are lazy chunks, and in a test run the first load of one transforms its whole module graph, shared with every other worker. On a cold module cache (CI, which never keeps one, and every fresh worktree) with the machine busy, that took longer than three tests' 5 s `findBy` waits: a cold full run on main `4a3f6cbb7` at load 50 had 79 web tests failing, the first one to three tests of 44 files, each on a page with only the toast region. With the screens loaded first, cold runs pass and the web project is faster (31 s against 54 s); a warm run costs about 3 s more for evaluating every screen in each file. The 5 s `findBy` limit stays: it is for what the app does, not for the bundler. | The waits were right for the app and wrong for the bundler; raising them would hide slow app behaviour too. |
| TS-09 | **The Nix evaluations and the whole server suite run on the build server, not the development machine** (2026-11-26). `appliance-nix-eval` and `appliance-source-matrix` run in fast-test's Nix container (`"where": "beast-nix"`: a pinned Nix image with a Nix store of the repository's own; `appliance/scripts/ci/nix-tools.sh` brings sed, awk, jq and diff from the pinned nixpkgs). `server-int-all` runs in the repository's container there with a Postgres 17 of its own (`scripts/ci/fast-test-postgres.sh`). The scripts accept the container's one-commit-deep copy (`shallow=1`; the flake reads its commit's date, never a count of commits). | In the week to 2026-11-26 these took about 13 hours on the development machine, which every agent and T3 Code share. |

## Slow tests (TS-S…)

The slowest Postgres integration tests of `apps/server` (and two unit suites) waited on production timeouts, poll
intervals and fixed sleeps. Each is now driven by an injectable value, a condition or a shorter test-only setting.
Production defaults are unchanged, and no assertion was removed.

| # | Decision | Why |
|---|---|---|
| TS-S01 | **`GitHubService.branchWaitMs`** (default 20 s) is the wait `awaitBranch` gives a branch that isn't pushed yet; `github/local-prs.int.test.ts` sets 300 ms. | Its “a branch that isn't there yet” check waited the full 20 s for the conflict it asserts. |
| TS-S02 | **TCP_NODELAY for the Vault's SSH sockets under the test seam**: `VaultNet.noDelay` (tests only, on by default in `useVaultNetForTests`) makes `dial` set it, and both in-process SSH fakes (`vault/testing/ssh-fake.ts`, `hosts/testing/fake-install-ssh.ts`) set it on their side. Production sockets are unchanged. | Every SSH round trip on loopback waited ~40 ms on Nagle plus delayed ACKs: a channel open took ~150 ms, an SFTP read ~600 ms. `hosts/install.int.test.ts` went from ~30 s to ~4 s, `vault/ssh.int.test.ts` from ~37 s to ~13 s. Whether production should set TCP_NODELAY on Vault SSH (interactive, latency-bound calls) is left open; that is a product change, not a test one. |
| TS-S03 | **`VaultNet.closeGraceMs`** (tests only) replaces `SSH_CLOSE_GRACE_MS` (5 s) through `sshCloseGraceMs(services)`; `sshExec` takes `graceMs`. The VT-D56 test uses 300 ms and keeps its elapsed-time bound, scaled to it, and gives the never-opened channel a 0.5 s connect deadline for that one call. | The test waited the real 1 s timeout + 5 s grace + 3 s open deadline. |
| TS-S04 | **The canary's slow Vault call runs out on a 300 ms deadline** (the seam swapped for that call and put back). | It only has to time out; the canary checks what leaks, not how long. |
| TS-S05 | **Test apps end their open connections before `app.close()`**: `useTestServer`'s teardown, `approved-write` and `golden-path` call `app.server.closeAllConnections()` first. | A request still running when a suite closes its app (a stopped runner's last claim long-poll) becomes an idle keep-alive connection after `close()` began, and holds the close for Fastify's 72 s keep-alive. Every suite with a runner spent ~70 s in `afterAll`. The same can delay a production shutdown while a runner long-polls; not changed here. |
| TS-S06 | **The ACP suite sets `unrunnableMs: 0` in `beforeAll`**, before any dispatch. | The engine keeps one unrunnable timer, armed by the first queued dispatch with the value of that moment (5 s): setting it inside the last test left that test waiting for the earlier timer. |
| TS-S07 | **Suites that start the automations engine pass `automations: { lockCheckMs: 50 }`** (`approved-write`, `golden-path`). Golden path's restart check waits until the new engine is active, runs two passes and gives the runner 1 s of claims, instead of a fixed 3 s. | The engine's handover holds the lock two `lockCheckMs` (2 × 5 s) before acting, so the first test (and the test after a restart) waited 10 s. Before, the 3 s restart check ran before the new engine was even active; now it covers its recovery and passes. |
| TS-S08 | **`startHosts(services, { serverFlushMs })`** (default `SERVER_FLUSH_MS`, 5 s); `hosts/hosts.int.test.ts` uses 200 ms. | The `hosts.server` frame test waited for the 5 s batch. |
| TS-S09 | **`GitHubPoller` takes `firstTickMs`** (default 2 s) for the first tick after `start`. The timer test uses 100 ms and steps the poller's clock past `WAKE_GAP_MS` before the wake instead of waiting 2 s. | The wake gap is the poller's rule (two polls of a repo at least 2 s apart); the test checks the wake makes the next poll soon, which it still does. |
| TS-S10 | **`VaultNet.deviceTimeoutMs`** (tests only) replaces `DEVICE_TIMEOUT_MS` (3 s) for Modbus devices; the silent-device test uses 300 ms for that one read. | It waited the full 3 s for a device that never answers. |
| TS-S11 | **The sandbox probes run their checks at once** (`probe.mjs`: 2 s per unanswered network check, 500 ms in `sandbox.test.ts`, which passes `timeoutMs`), and the fork-bomb test polls `violations()` for `pids_limit` instead of sleeping 2.5 s. | The probe waited out each unanswered TCP/DNS check one after another, three times (hook, npm, MCP server). Production keeps 2 s so “no answer” still means no answer; only the two direct DNS checks wait at all (TCP fails at once), and on the host a real answer came within 500 ms every time, so the test's shorter wait still tells an answer from none. |
| TS-S12 | **Superseded by one-person.md OP-S114**: computerd and its tests are gone. **The runner's computer tests wait until the command reached the computer** (`computerd.execs`) before the client kills it, instead of 300–400 ms. The 200 ms after the kill stays. | The kill only has to come after the command runs; the wait after it is what lets the computer end it. |

Left as they are:

- `automations/merge`, `automations/fixes`: no sleeps; the time is Postgres round trips over many engine passes
  (`settle` runs six), which is what they test.
- `smoke.int.test.ts`: it boots a production server with `tsx` and migrates a fresh database (~3 s alone, more under
  load); that is the test.
- `poll-cadence` “11 requests each with five PRs”: simulates three hours of polls against the database.
- The first personal agent with role packs in a file costs ~1.2 s (validating and scanning the shipped packs, cached per
  `Services`). Each test file has its own module graph, so a process-wide cache wouldn't help.
- `sandbox.test.ts` “blocking stdio”: its 1 s pause of the reader is what the test checks.
- `canary`'s remaining ~5 s is real work through every door (HTTP, MCP, SSH, packs, every read).
