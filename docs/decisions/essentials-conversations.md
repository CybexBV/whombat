## Channels

| # | Decision | Reason |
|---|---|---|
| EC-01 | **Visibility** is `conversations.visibility` (`public`/`private`, null = private). Migration 0054 sets every existing channel `private` except `#general` (`public`); a new burrow's `#general` is public; the mock world's seeded channels are public (the mocks show no locks). `create_channel` defaults to public (contract), and so does a channel an agent asked for and a person approved (R1's `approval.create_channel` and `perform_action`: the approval's action names no visibility). Changing it is `conversations.update` with `visibility`: burrow owners who are members of the channel, never `#general` to private; signed `conversation.updated` “Made #x public / private”. | The assignment's migration rule; owners decide who can find a room; members-only update keeps the existing rule that you change rooms you are in. |
| EC-09 | **Browse** (`GET …/channel-directory`) lists every public channel and the private ones the viewer is in, with `joined`, member count, topic and creator, sorted by name; `q` matches name, title or topic (case-insensitive, `%`/`_` escaped); active channels by default, only archived ones with `archived=true`. **Join** (`join_channel`): people only, public channels only (a private one answers 404 to outsiders), idempotent, refused while archived (409); signed `channel.joined` “Joined #x”. Leaving stays `remove_member` of yourself. | A private channel doesn't exist for people outside it; joining twice is harmless. |
| EC-10 | **Private channels in search**: people's search stays membership-only (a public channel you haven't joined isn't searched: Browse and join it first; C-10 keeps reads members-only). An agent holding “Search messages, canvases and runs” also sees public channels and branch rooms it isn't in — no longer private channels, DMs or direct conversations. | Private means members only, for agents too; before 0.26 the key reached every channel. |
| EC-11 | **Archived channels are read-only everywhere**: `postMessage` refuses them (409 `conflict`, `ARCHIVED_CHANNEL_TEXT`), which covers REST sends, the MCP post and reply tools, automations' posts, quiet replies and every other post; edits, pins, reactions, “More detail”, topic/name/visibility changes, adding members and joining are refused too. Reading, leaving, marking read, deleting your own messages (and owners' moderation) and unarchiving still work. No dispatch is queued there (`queueIn`; R1's `approval_granted` wake-up (`wakeQuietly`) wakes nobody there and its Try again answers 409), and archiving cancels the turns queued, claimed or running there (`error: channel_archived`; a runner hears it on its next beat). Automations: an event from a channel that is archived when the engine reads it starts nothing, a schedule whose room is archived is skipped (“Its channel is archived.”), a step that would post there fails. The sidebar leaves archived channels out; `conversations.list` keeps them (with `archivedAt`). | “Read-only” as the assignment defines it; deleting stays possible so a leaked secret can go without unarchiving. |
| EC-12 | **Archive** (`archive_channel {archived}`): burrow owners and the channel's creator (`canArchiveChannel`), never `#general` (400); an owner outside a public channel may archive it, a private one is 404 to outsiders. `conversations.created_by_id` is new; migration 0054 fills it from each channel's signed `channel.created` event. Signed `channel.archived` / `channel.unarchived` “Archived #x”. | The creator of an older channel keeps the right; the chain already says who created it. |

## Messages

| # | Decision | Reason |
|---|---|---|
| EC-02 | **Delete**: a message without replies is removed (row, reactions, search document) and its room hears `message.deleted`; a thread root with replies becomes a tombstone (`deletedAt`; text, mentions, card, suggestions, “More detail”, skill hint, files, previews, `@channel`, pin and reactions cleared; replies stay; `message.updated`). A reply removed recounts its root (`replyCount`, `lastReplyAt`, the three heads); a tombstone left without replies is removed with it. Deleting a tombstone again answers the tombstone (a retry); a removed message is 404. Unread counts skip tombstones. | CT-173; a tombstone exists only for its replies. |
| EC-04 | **Cards**: never edited (400 “Cards can’t be edited.”). A message whose card stands for live work — `plan`, `run`, `approval`, `report`, `guide`, `skill`, `turn_failed` — isn't deleted (409 “This message holds work in progress, so it stays.”); content cards (`research`, `review`, `commits`, `pill`, `answer`, `digest`) are. The first message of an open handoff's lane stays while the lane has no replies (409 “This message starts a handoff that is still open, so it stays.”); with replies it becomes a tombstone and the lane goes on. | Deleting a plan's or an approval's message, or a lane's start, would orphan the work (and R1's retry card). |
| EC-04a | **A feedback report's message is deleted once nothing is under way on it** (2026-09-30, John: deleting the thread of an assessed feature request FB-2P7K-8T73 said “This message holds work in progress, so it stays.”). Amends EC-04: `report` leaves the always-kept cards. Its message stays (409, same text) only while the report's assessment is queued, running or paused, its status is “In progress”, or a request for development is pending; otherwise it is deleted like any message (a tombstone while it has replies). The report itself stays in Feedback; with its message deleted, Retry and asking for development are refused (409 “This report’s message was deleted, so it isn’t assessed again.” / “… so it isn’t handed to development.”), so nothing is posted under a deleted root. | A finished report is conversation, not live work; the work it can still start is refused instead of kept alive by the message. |
| EC-04b | **Deleting a thread's first message removes the whole thread** (2026-09-30, John: “The whole thread should be removed when I remove the first message. It currently keeps the replies.”). Amends EC-04 (and CT-173's tombstone): the root and every reply are removed (reactions, files, search documents, inbox rows; one `message.deleted` frame per message, one signed `message.deleted` event with `replies: n`); nothing is kept as “This message was deleted.”. Refused while work still lives in the thread: a reply's card that stands for live work (`plan`, `run`, `approval`, `guide`, `skill`; a failed turn's retry card goes with the thread) → 409 “This thread holds work in progress, so it stays.”; an agent's turn queued or running there → 409 “An agent is still working in this thread, so it stays.”; an open handoff lane → 409 as before, now with replies too. A member removes their own thread only when no other person replied (agents' replies go with it) → 403 “Someone else replied in this thread, so only an owner can remove it.”; owners remove any. A root kept as a tombstone before this is removed with its replies when deleted again (the API accepts it; the apps show no Delete on a tombstone, so it goes with its last reply or by an owner through the API). Apps: whombat-app 0.17.3 (AP-553). | Slack keeps replies; John wants the thread gone. Other people's words are removed only by an owner (EC-03's moderation). |
| EC-04c | **A card keeps its message only while its work is going on** (2026-10-19, John: deleting in Chat “is not working, if you refresh the messages return” — the server had refused his three old setup suggestions, an expired and a done guide card, with 409 “This message holds work in progress, so it stays.”). Amends EC-04 and EC-04b: a single delete uses the same test as Clear all messages (CC-02, `cardsWithWork`): a message (or a thread, by any of its replies) stays only for a run live or paused, an approval waiting for its decision, a plan with steps to go, a skill proposal waiting, a guide still `open`, or a report being worked on (EC-04a). A failed turn's retry card still keeps its message (R1) and still goes with its thread. Clear and the fresh start now let answered and expired guides go too. Same 409 texts. | In Chat almost every thread holds Dusty's finished approvals and runs, so the fixed list made Delete fail for nearly everything; finished work stays in Work, Approvals and Feedback. |
| EC-08 | **Edit** (people, own, not a card or tombstone; empty text only when the message has files): mentions and `@channel`/`@here` are read again; the same text changes nothing (no event). A newly mentioned agent is woken **once** — never when a dispatch for that agent and message exists already (a mention removed and added back wakes nobody). A newly mentioned person is told once through the notification service (`notifyForMessage` with `addedMentions`, R3's EP-11: members only, its dedup key `msg:<message>`); inbox rows about the message show the new words. Search is reindexed, previews of links no longer there drop at once and new links are fetched. A lapsed licence refuses an edit that would wake an agent, as it refuses such a send. | CT-173's “nothing else is re-sent”, made idempotent. |
| EC-03 | **Agents read the current state**: their context loads messages at claim (edited words, tombstones); both prompt builders show a tombstone as `[This message was deleted.]` and an edited message with `(edited)`. An edit or deletion drops the context summaries of its conversation (and thread) that cover it (rebuilt from the messages as they are) and retires the conversation's active provider sessions that saw it (“a message it saw was edited or deleted”), so old words don't live on in a resumed session. A queued turn whose triggering message was deleted still runs (later mentions may have coalesced into it); its context has no trigger or the tombstone. | No stale text from the messages table, memory or a provider's history. |
| EC-13 | **What a deletion takes with it**: the message's attachment rows at once and their bytes after the commit when no other row uses them (`removeIfUnused`); its search documents in the same transaction (a reply's root is reindexed); inbox rows of kinds `mention`, `agent_update`, `direct`, `reply` that link to it; unread badges are republished. Signed `message.deleted` (kind `Messages`, `text: null`, `aboutId` = the author) carries `{messageId, conversationId, threadRootId, removed, moderation}` — ids only, like `message.edited` (`{…, addedMentions}`). | CT-173: no words in any signed payload; the words leave every place they were copied to. |
| EC-05 | **`@channel` / `@here`** are parsed on send and edit (`parseBroadcast`) into `messages.broadcast`, never into mentions, and wake no agent. Who is told is the notification service's (R3's EP-11); `@here` reads `presenceFor(services).activeAmong(…)`, the one presence store (EC-27). | CT-176; one owner for notification rules. |
| EC-14 | **Pins**: any person in the conversation pins or unpins (agents 403), not a tombstone (409), not in an archived channel (409); at most `PINS_MAX` (50) per conversation — the 51st is refused (409 “This conversation has 50 pinned messages. Unpin one first.”), never an automatic unpin; counted under the burrow lock. `conversations.pins` lists members only, newest pin first. Signed `message.pinned` / `message.unpinned` are hidden (`text: null`, like reactions): the audit log is the whole burrow's and a pin in a private room isn't its business. | People choose what to unpin; chat-level events stay out of the log. |
| EC-15 | The message read model adds `deletedAt`, `pinnedAt`/`pinnedById`, `previews` and `broadcast` only when set, so every answer about an ordinary message is exactly what it was before 0.26. | Older clients and tests see no change. |
| EC-16 | **Agents don't edit, delete or pin** through any surface: there is no MCP tool for it and the commands refuse an agent actor (403), whatever its keys — also through an agent's REST token. | CT-173: agents correct themselves with a new message; moderation is people's. |

## Link previews

| # | Decision | Reason |
|---|---|---|
| EC-17 | Fetched after the commit of a send or an edit, off the request's path: an in-process queue (four at a time, at most 500 waiting; beyond that new ones are dropped). The result is written like the search index — a derived projection (C-12): in the burrow's transaction with its `message.updated` frame, no signed event. The previews kept are those of links still in the message's current text, from this fetch or what it had (an older fetch finishing after an edit never brings a removed link back); deleted messages and archived channels get none. | A 5-second fetch must not hold a send; previews are derived from the text like search. |
| EC-18 | **Cache** `link_previews` per burrow and URL: a preview or a page without one for 24 hours, a failure for an hour; pruned hourly. Per burrow, so one burrow can't tell from timing what another posted. | The assignment's 24 h; failures retried sooner. |
| EC-19 | **The guard is `lib/outbound.ts`** with a destination rule: `http:`/`https:` on their default ports only (any explicit other port refused), no credentials, every resolved address `isPublicAddress` (the blocklist and core's `addressIsPublic`: loopback, private, link-local, CGNAT, ULA, metadata, reserved, IPv4-mapped — refused), DNS pinned to a checked address, no redirects followed by the helper: at most three, each target checked from scratch. 5 s for the whole request, the first 512 KB read (a longer page is cut, not refused), `text/html` or XHTML only. `WHOMBAT_OUTBOUND_ALLOW_PRIVATE` (tests only, refused in production) lifts the address and port rules as for every outbound caller. | Reuse the one audited SSRF guard; no naive fetch. |
| EC-20 | **Which links**: those core's Markdown parser makes links (so never inside code blocks or code spans, never an image), `http(s)` only, the first three distinct in order of appearance, in every kind of conversation, whoever wrote the message. This Whombat's own links (`PUBLIC_URL`, `WHOMBAT_APP_URL`, a managed box's hosted-UI base) get none. A preview's `url` is the link as written, even after redirects. Page parsing: `og:title` › `twitter:title` › `<title>`; `og:description` › `description` › `twitter:description`; `og:site_name`; numeric and common named entities decoded; the charset from the header, else the document, else UTF-8; `normalizeLinkPreview` cuts and drops a page without a title. No images. | CT-174. |
| EC-21 | **Off switches**: `Burrow.linkPreviews` (`burrows.link_previews`, null = on), changed by owners through `burrows.update` (key `burrow.manage`, signed `burrow.updated` “Turned link previews off”); `WHOMBAT_LINK_PREVIEWS=on\|off` for the whole server (default on, off in tests). Switching off stops new previews; existing ones stay. | Owners decide for their burrow; operators for their host. |
| EC-22 | **Failures are quiet**: no preview, the cache row records `status: failed` and a reason (`refused: …`, `timeout`, `network`, `answered 404`), a debug log line; nothing is shown to anyone. On a managed appliance whose egress is restricted, previews simply don't appear. | The assignment's “fail quietly and record it”. |
| EC-23 | **Per channel** (John, 2026-10-10, on automation posts whose GitHub card repeats the line above it: “switch off the previews of the URLs in a message”, then “Make it configurable per channel”): `conversations.link_previews` (migration 0098, null = on), `Conversation.linkPreviews` always sent as a boolean, changed with `conversations.update` by people who are members (an agent is refused: “Only people turn link previews on or off.”), signed `conversation.updated` “Turned link previews off in #name”. Off: the server fetches none for the conversation's messages (`linksOf` reads it with the burrow's switch) and clients don't show the ones already stored (`conversationLinkPreviewsOn`), so turning it back on shows them again without refetching. Any kind of conversation may have it; the apps offer the switch in a channel's details (feature `conversations.link_previews`, CT-330). The burrow switch (EC-21) still wins. | One noisy channel (automations, bots) shouldn't cost everyone their previews; hiding rather than deleting keeps it reversible. |

## Seams with the other streams (after merging R1 and R3)

- **Notifications (R3)**: a send notifies through `notifyForMessage` (R3, `domain/message-notify.ts`), an edit through
  the same with `addedMentions`; inbox rows about an edited or deleted message are rewritten or dropped by
  `refreshMessageNotifications` / `dropMessageNotifications` (by `notifications.message_id`, and by link for older
  rows); the email digest leaves deleted messages out (`m.deleted_at is null`).
- **Presence**: R3's frame-fed tracker and this stream's connection tracking are one class (`presenceFor`); the hub,
  managed sessions (`presence.set`, following a burrow) and `Bootstrap.presence` use it.
- **Offboarding (R3)**: `open_direct` refuses a removed person (“{Name} isn’t in this burrow any more.”); their direct
  conversations stay readable to the others (R3 keeps them as members).
- **Failed turns and wake-ups (R1)**: `turn_failed` cards can't be deleted (EC-04); an archived channel takes no
  `approval_granted` wake-up and no Try again (EC-11); an approved `create_channel` is public (EC-01).
