# One Whombat — the assistant, chats, Home, changes, widgets (stream SW, 2026-10-17)

Stream SW of `docs/implementation/one-whombat/assignment.md` §6.1, under `docs/decisions/one-whombat.md` (ONE-01…ONE-22).

| # | Decision | Why |
|---|---|---|
| ONE-DW01 | **Everything SW stores is in one migration, `0104_one_whombat`**: `changes`, `widgets` + `widget_points`, `needs_you_snoozes`, the task chat columns on `conversations` (`task_key`, `chat_title`, `chat_retitled_at`, `chat_subject_kind/id/name`, `chat_archived_at`), `approvals.execute_at`, `catalog_connections.glance/glance_at`, and the assistant rename. Expand only. | SH and SD take 0105 and 0106 on top of it; a later SW migration would collide with their numbers. |
| ONE-DW02 | **A task chat is a `dm` row with a `task_key`**; the person's default DM keeps `task_key` null. `conversations_dm_idx` and `conversations_slug_idx` now cover only rows without a key; `conversations_task_idx` keeps (agent, person, key) unique. No code relied on those indexes for `ON CONFLICT`. | Every DM code path (members, read state, waking, approvals) works for task chats unchanged, and `personalDmId` keeps finding the one default DM once it filters on `task_key IS NULL`. |
| ONE-DW03 | **The chat subject's name is stored with the chat** (`chat_subject_name`), besides kind and id. | The turn context (“This chat is about the server pve-02.”) and the chat list need the name without asking the hosts service, which may be down; a renamed server shows its new name on its page anyway. |
| ONE-DW04 | **The rename (ONE-01) covers Hazel and every name from core's `PERSONAL_AGENT_NAMES` pool**, compared trimmed and case-insensitively, for active personal assistants only. A name the person chose outside the pool stays. DM titles and their search documents follow, as 0062 did; handles (`<person>-assistant`) stay. | People whose Hazel was taken got a pool name automatically (PA-04); all of them are “Whombat” now. A test pins the list to core's. |
| ONE-DW05 | **`recordChange` takes any writer with a transaction and the key custody** (`ApplyContext`, any `TxSession`): it inserts the row in the caller's commit, seals the undo payload with AAD `change:<id>:undo`, and with `undoes` marks the change it reverses. Change ids are `chg_…` until contracts have an id kind. | Changes are written by commands already in the pipeline (connection calls, hosts and device commands); the payload can hold old values read from a service, so it is sealed like call arguments (CX-21). |
| ONE-DW06 | **An undoer runs inside the `undo_change` command with the person who pressed Undo as actor**; one that needs a tool call schedules the inverse as a new pipeline call (`ctx.after`), so keys, tiers and approvals apply again. Undo is offered only while the recipe's undoer is registered on this server and before `undo_until`. | ONE-08: Undo must not bypass the permission model, and an old recipe whose undoer is gone must not show a button that can't work. |
| ONE-DW07 | **`SourceCtx` also carries `services` (optional)**; sources run in parallel, each with a 4 s budget; one that throws or is late is left out of that read and logged. | SH needs its hosts client; a slow hosts service must not hold Home up or empty it. |
| ONE-DW08 | **Snoozes and acknowledgements share `needs_you_snoozes`** (`state` `snoozed` or `acknowledged`, `until` null for “until it changes”). | Needs you and Watch items are snoozed the same way; one table, one read. |
| ONE-DW09 | **`WHOMBAT_SHELL` defaults to `assistant`, and to `crew` under `NODE_ENV=test`**; a suite asks for the assistant with `env: { WHOMBAT_SHELL: 'assistant' }`. In assistant mode `complete_onboarding` makes no crew (whatever roles an older client sends) and sends the owner to Home (`/<burrow>`), `hire_agent` is refused (`not_allowed`, “Everyone here has their own Whombat, so there’s nobody to hire.”) before any key is decided, and a join queues no #general welcome. | The existing suite describes the crew; the assistant shell is opt-in there and the default everywhere people run it. |
| ONE-DW10 | **New assistants are called “Whombat” in the assistant shell** unless the account's assistant elsewhere has a name its person chose (a plain assistant name nobody else here holds). Assistants may share the name: the free-name check ignores other people's assistants there (people and team agents still hold theirs). An empty rename is “Whombat”. **The crew shell keeps PA-04** (Hazel, then the pool, unique names). | Everyone talks to their own Whombat, in their own chats; in the crew shell assistants meet in channels, where @mentions need unique names. |
| ONE-DW11 | **An automation may ask a personal assistant only for its own person** (`dispatchableAgent(…, forPersonId)`: the publisher at run time, the person saving or the Whombat drafting for its person when checked); team agents as before. In the assistant shell **Whombat may draft automations** (`draft_automation`); its prompt keeps private mail and calendar details out of a draft. | ONE-01: Whombat runs its person's automations; nobody else's automation can wake someone's assistant. Drafts stay visible to the burrow as before, so the guard is the prompt. |
| ONE-DW12 | **Whombat's working directory** (assistant shell): its person (an owner who is an admin, as for any agent) may set one with `agents.setRuntime`; the turn gets that directory, never the burrow's default, which other people's work shares, and Whombat stays guarded. With computers on it works in its computer's own folder (AC-24), as it already could; without either it builds and tests in a scratch folder (`workspace.scratch`). | Building and testing needs a place to work; one person's Whombat must not land in a directory other people's work uses. |
| ONE-DW13 | **A Whombat may look after a shared connection** in the assistant shell: the person who connects it gets their Whombat as its caretaker, and a manager may pick any person's Whombat (`requireCaretaker(…, { assistants: true })`). The crew shell keeps it to team agents. | There is no crew to give a connection to; questions about it go to a Whombat. |
| ONE-DW14 | **A chat starts with its first message** (`start_chat {text, subject?}`, one commit): the chat row (title = the message's first line, markdown marks dropped, ≤ 60 characters cut at a word with “…”), both members, a signed `chat.started` (no text, ids only), then the message as any DM message, which wakes Whombat (`dm`). It makes sure the default DM exists. The subject is checked for the person: a connection must be the burrow's or theirs and takes the connection's label; a server or device goes through its registered resolver (`registerSubjectResolver`, SH and SD), else the client's name is kept. | One call, no empty chats; the subject is never a name the client made up for something the person can't see. |
| ONE-DW15 | **Whombat improves a title once** (`set_chat_title`; `chat_retitled_at` marks it) **and never after the person renamed it** (a rename sets the mark too). Only the person renames or archives their chat; someone else's chat is `not_found`; the default DM is neither renamed nor archived. The turn's `conversation.topic` says “Task chat “<title>”. This chat is about the server pve-02.” | ONE-06: the person's own words win; the subject reaches the model without a contract change for the runner. |
| ONE-DW16 | **Task chats are listed by `chats.list` only**: the sidebar's conversation lists and the bootstrap leave them out, and the default DM is in `chats.list` as `default: true`, titled with Whombat's name. “The DM” lookups (`personalDmId`, `open_dm`, a search's report-back DM, a restore's DM map) mean the default DM (`task_key IS NULL`). | Older crew clients would otherwise show every task chat as another DM with the same agent. |
| ONE-DW17 | **On contracts 0.80.0**: `home/types.ts` re-exports the contract's Home shapes; change ids are `newId('change')`; `changes.link` stores the `HomeHref` string; chat titles use core's `chatTitleFrom` (a rename or Whombat's title is run through it too, so it stays one line of ≤ 60); `Conversation.chat` is filled by `toConversation` from `chats/view.ts` (no import cycle with the read models); `chats.list` takes `subjectKind`/`subjectId` (a thing's chats). `shell.assistant` is implemented and advertised only while `WHOMBAT_SHELL=assistant` (`runtimeFeatures({ shell })`; the release manifest lists it, as code-level support). `set_chat_title` is served (personal agents only, the turn's own chat). | The contract is the source of the shapes; the feature tells clients which shell the box runs. |
| ONE-DW18 | **Every connection write that worked is a change** (`finish_connection_tool` records it in its own commit): a plain title from what the call did — Home Assistant on/off by name or entity (“Turned off Hallway light”, the entity's friendly name read first), a climate set point (“Set Living room to 21 °C”, “It was 19 °C.”), Todoist tasks — else “Used <tool in words> in <connection>”; the subject is the connection, the link its page, the chat it was made in kept. Its person is the Whombat's owner; a shared connection's change is everyone's in the burrow, a personal one only its person's (and not recorded without one). Undo is offered for `CHANGE_UNDO_WINDOW_S` (24 h). A read is never a change. | ONE-08 with PA-09: people see outcomes in their words; private changes stay private. |
| ONE-DW19 | **Known inverses**: HA MCP `…HassTurnOn` ↔ `…HassTurnOff` (same arguments, when the connection has the other tool); HA REST `turn_on`/`turn_off`/`toggle` undo to the state read before (none when it didn't change); `climate/set_temperature` undoes to the old set point; Todoist `tasks_update` undoes to the task's old fields (read from `tasks_list`). Reading the old state never fails the call. **The connection undo is a direct undoer** (`registerDirectUndoer`): a new `call_connection_tool` by the Whombat that made the change for the person who pressed Undo, with call id `undo.<change>.<person>.<n>`; it answers `undone` (the inverse's own change marks the original), `asked` with the approval's number, or a plain refusal. In-commit undoers (`registerUndoer`, SH/SD) run in `undo_change`, which marks the change in the same commit. | Undo must go through keys, tiers and approvals again (ONE-08); the call id carries the link to the original through an approval without a new column. |
| ONE-DW20 | **Who may undo**: any person who sees the change (a shared one: everyone in the burrow; a personal one: its person); someone else's personal change is `not_found`. An undone change, an expired one or one whose undoer this server doesn't know is `conflict` with a plain reason. `undo_change` signs `change.undone` (a shared change's title in the text, a personal one's nothing). `home.changed {parts: [doneRecently]}` goes to each person who sees it. | Undo is as visible as the change; the log never names a personal change's content. |
| ONE-DW21 | **Home's periodic jobs run on the housekeeping tick** (`homeJobsFor(services)`, outside the `Services` interface): Approve later every 30 s (approved, idle, `execute_at` due → `approvals.reevaluate`; the engine skips a yes whose time hasn't come), widgets every 30 s, connection health every 5 minutes. **Approve later** (`approvals.decide` `executeAt`): a yes only, in the future, at most 7 days ahead (`validation_failed` otherwise); undoing the decision clears it; `Approval.executeAt` shows it. A push of a shared branch is let through by the runner at once (approvals/push.ts) — Approve later doesn't hold it. | ONE-10, the contract's rules (CT-338); the engine stays the one place that runs approved actions. |
| ONE-DW22 | **Widgets**: `pin_widget` is a person's Whombat's only (onto its own person's Home), at most `WIDGETS_MAX` (12); a `connection_tool` source must be a tool that only reads (`callAccess`) of a connection the person may see; `server_metric` needs the hosts stream's reader (`registerWidgetReader('server_metric', …)` in `home/widgets.ts`). Series are coloured 1–3 in order; known metrics get words (CPU %, Memory %, Hottest °C, Network Mbit/s). Refresh 60 s – 1 day, default 300 s; the first read right after pinning. | ONE-09: declarative, cheap, never a write. |
| ONE-DW23 | **A widget's read is its person's own** (`runConnectionRead`: one of the connection's call slots, no agent, no tool events), recorded by `record_widget_read` as that person (points inserted, older than 24 h pruned, `refreshed_at`, the problem in plain words: “Home Assistant needs to be connected again.”, “The answer had none of the numbers this widget plots.”); `widget.updated` to its owner. Numbers: JSON numbers, numeric strings, booleans and on/off as 1/0; anything else a gap (null). | The person sees only what they may see anyway; a refresh every minute must not flood the burrow's log. |
| ONE-DW24 | **Widgets list in their person's order** (`position`); moving one closes the others up around it; removing deletes its points. Only the owner moves or removes. | Simple, and other people's Homes never change. |
| ONE-DW25 | **Needs you** (built in): the approvals the person may decide (the `decidablePendingCount` rule) with **Approve** · **Tonight at 03:00** (the next 03:00 in the burrow's zone) · **Not now** (a snooze until tomorrow 09:00); Whombat's messages that ask something in the person's chats until the person writes there again (**Answer** opens the chat); connections that need connecting again (an owner for a shared one, the person for theirs; **Reconnect** opens the connection). Then the registry's items; snoozed ones left out; worst first, then newest. **Working on**: Whombat's newest plan with steps left in the person's chats (done → done, active → active, queued → to do, gate/blocked → waiting, cancelled left out). **Automations today**: automations the person made or whose runs post where they are — the newest run today (ran/failed) or the next run still today. `summary.problems` = open Watch items. | The mock's buttons and sections; nothing someone else may not see. |
| ONE-DW26 | **Connection health** (every 5 minutes, connections looked at more than 4 minutes ago, 50 per pass): the entry's own check with the stored credential; refused → the connect side's confirmation (`needs_reauth`) and “Needs to be connected again”; no answer → offline, “Couldn’t reach it”, the last facts kept; an error answer → warn. Written in the pipeline's transaction (nobody acted; nothing signed); `home.changed {things, watch}` only when what shows changed. | Keeps `status` current without the agents, and Home honest. |
| ONE-DW27 | **Glances**: Home Assistant from `GET /api/states` (the first climate with a current temperature and its action, the alarm, one lock by name or “n of m locked”, lights on with two names, “<n> devices”); UniFi Network (internet rate from the gateway's latest statistics, access points online, clients); Hetzner (servers running). Others show their state and “Last checked HH:MM” (the burrow's zone). Your things leave out the Servers connection and devices (SH and SD show them) and connections only automations use. | Cheap reads Whombat has words for; one look per 5 minutes. |
| ONE-DW28 | **Whombat's prompt section “## Being Whombat”** (personal agents, both shells, the same lines every turn): one assistant for servers, home, network, mail and services, talking like a colleague (one to three short sentences, no ids or logs); one task per chat, `set_chat_title` once; `plan_create` / `plan_start_step` / `plan_update` for multi-step work (Home's Working on); offer `pin_widget` when someone wants to keep an eye on something, reading it once first; say what it changed in one line (Done recently has Undo); restarts and updates at night (Approve later); `draft_automation` without private content. Its own heading, because “## How you work” (RA-11) exists already. | ONE-05, ONE-06, ONE-08…ONE-10 and concise-replies.md; a stable prompt (PE-02). |
| ONE-DW29 | **Google mail on Home**: a person's Google account with mail shows as a thing “Mail” with its unread inbox count (`is:unread in:inbox`, “50+” above 50) and the address, counted by the health job every 5 minutes with the person's own token and kept in memory (connector rows have no glance column; after a restart it's one poll away). Only its person sees it; its link is Settings → Connections. | The mock's “Google mail (unread)” without a migration on a table another part owns. |
| ONE-DW30 | **Home and servers stay live on the client side**: a client showing Home listens on `hosts:<burrowId>` and refetches Home's Needs you and Watch on `hosts.alert`, `hosts.enrollment` and `hosts.resync` (the Servers card follows `hosts.server` itself); the server doesn't fan `home.changed` out per person from the hosts bridge. Changes, widgets, snoozes, health and chats publish `home.changed` / `widget.updated` on `me`. An in-commit undoer may answer `{ ok: true, state: 'asked' }` (SH's Whombat inverse that asks): the change keeps its Undo until the inverse runs. | Server reports come every 10 s; one topic per burrow is cheaper than a frame per person per alert, and the client already holds it. |
