John on DEV (2026-10-03), after a day in which “deploy the website” failed one obstacle after another (Vault keys,
cards in the wrong place, one-turn passes, review rules, no way to copy a build) and Banjo finally stopped at
“Ask a person to deploy it”: “I think we need to re-think this completely and see if we can learn from Hermes Agent …
it's capable of researching how to achieve a goal.” Then: computers must run inside the appliance, never on the host;
“Implement it fully … clean up the dev appliance as if it was reset to the point after enrollment.”

What Hermes does (research `~/.cache/wb-tmp/research/2026-10-01-hermes-deploy/hermes.md`, repo checked 2026-10-03): one
shell on a real machine with the user's own logins; a prompt built to finish the job (“Keep working until the task is
actually complete … try an alternative … ask only when the information can't be retrieved … verify”); approvals by
risk, not by tool; procedures saved as skills. Whombat's computer turns (agent-computer.md AC-24…AC-52) already work
that way inside the appliance; the turns without a computer (the dev stack, an appliance with computers off, small
hardware) told the agent to stop at the first refusal in 27 places.

| GF-08 | **Shared origins under the appliance's sandbox.** Creating a repository failed on the DEV box (`EPERM: chmod '/persist/whombat/workspaces/.origins'`, found by the deploy check): the server and the runner run with `RestrictSUIDSGID` and `UMask 0077`, so a `chmod` with the setgid bit is refused even to the owner, and git's `--shared=group` hits the same wall (“Could not make … writable by group”). Shared folders are now made synchronously under umask 007 with mode 0770 (the setgid workspaces folder gives them its group and setgid bit), an empty owner-only one an older runtime left is made again, and git that writes into an origin (create, merge, the runner's push to a local remote) runs under umask 007 (`sharedGitCommand`), so git never needs to chmod. Reproduced and checked in a `systemd-run --user -p RestrictSUIDSGID=yes -p UMask=0077` sandbox. | “Create a repository” and pushes to it had never worked on an appliance. |
| GF-09 | **The runner's git reaches an origin the server owns.** On the DEV box every push of an agent's work failed (“does not appear to be a git repository … make sure you have the correct access rights”): `receive-pack` and `upload-pack` run in processes of their own that get none of the command's `-c`, so the origin, owned by the server's user, is “dubious ownership” to the runner's git. A push, fetch, clone or ls-remote of a local origin now names its pack program with its own `safe.directory` (`--receive-pack` / `--upload-pack`). Reproduced with a bare repository of another user. | Found by the deploy check: Banjo's committed page never reached the origin. |
