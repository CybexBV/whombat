# What automation run #9 taught us (RN)

John, 2026-10-10, after automation run #9 on his DEV box (“Assess new reports in the tracker Dev”, a Try it on the tracker Dev
report #16 that went assess → approve → fix → review → PR #52 in 17½ minutes): “analyze this run and find efficiency
and optimization improvements … check if there were issues … if the automation cleaned up afterwards”. The review
(trace, journals and disk of the box in `~/.cache/wb-tmp/run9/`) found the fix step spending most of its 12 minutes on
copies of its checkout, a second Chromium download and the target repository's whole verification gate; a server bug
that rolled back the trigger scan after every manual command; previews that couldn't read the step's own folder; the
agent's GIT_DIR leaking into the repository's own tests; the agent opening the pull request the automation was meant
to open. John: “Implement all you suggestions fully”.

## Decisions

| # | Decision | Why |
|---|---|---|
| RN-01 | **Test runs keep their own thread** (AR-12, AR-17 unchanged). Triggered the tracker runs already carry an item key (`trackerItemKey`) and continue one thread per report; runs 6 and 9 were “Try it” runs, which start their own on purpose. The waste was the repeated assessment, which RN-S2 removes. | The review's first reading (“The tracker runs have no item key”) was wrong; a real report's thread stays free of test runs. |
| RN-02 | **Superseded in part by one-person.md OP-04, OP-13**: a step still leaves a check it can't run to the pull request's CI; there is no computer and no system software to install. **An automation's step leaves the computer as it found it.** It doesn't install system software (apt, dpkg) to make a check run: it leaves that check to the pull request's CI and says so (RN-R3). The prompt says it; the command guard doesn't refuse it — the computer is the agent's own (agent-computer.md AC-40: destructive commands on its own computer aren't asked about) and a build may really need a package. | Run #9's fix ran `sudo apt-get install prometheus` for one check of the repository's gate, which left Prometheus and its node exporter enabled in Banjo's computer (47 packages, removed by hand on John's box the same day). |
| RN-03 | **The tracker hears nothing from an automation after the assessment**: no status, no reply, no link. the tracker's `UpdateFeedbackRequest` has no private field for a pull request (only `message`, a public reply, `status`, `priority`, `assessment`, `release`), and a team status change is published to the reporter. So the thread says it instead, and a person decides (RN-S4, RN-S5; TA-15, TA-N unchanged). | The approval promises “nothing is sent to the customer: that stays with a person”. |
| RN-04 | **Superseded in part by one-person.md OP-04**: the cleanups it lists hold; there is no computer, so nothing installed system-wide stays behind. **What cleans up after a fix, as run #9 showed** (no change): the step folders go when their turn ends (AR-43; only the empty `.automation` folders stay); the GitHub branch goes when the pull request merges (AR-42: recorded “already deleted” 51 s after John merged PR #52); the branch's checkout and workspace repo go with the daily cleanup once merged and a day idle (RSF-11). What an agent installs on its computer is not undone (RN-02). | Measured on John's box, 2026-10-10. |

## Runner (RN-R)

| # | Decision | Why |
|---|---|---|
| RN-R1 | **A worktree agent's environment has no `GIT_DIR` / `GIT_WORK_TREE`.** Its git finds the checkout's read-only `.git` file, which names the same admin dir in the workspace repo (`gitdir: …/.repos/<repo>/<branch>.git/worktrees/<branch>`), so a test fixture that runs `git init` / `git commit` in a temporary folder gets an ordinary repository there. Direct mode keeps both (RSF-03: the owner's clone's own `.git` must not be used). The runner's own git still pins `GIT_DIR` and `GIT_COMMON_DIR` (RSF-05). On a computer the shares are idmapped and `agent` has the runner's uid, so git's ownership check passes. Amends RSF-04's last sentence. | In run #9 the repository's migration-safety fixtures committed their “baseline” onto `feat/tracker-16` through the inherited `GIT_DIR`; Banjo had to `git reset --soft` it away and wrap every gate run in `env -u GIT_DIR -u GIT_WORK_TREE`. |
| RN-R2 | **Superseded in part by one-person.md OP-S109**: previews still read the step's own folder (`~/work/.automation/<id>`), reached without following links; the work folder is in the agent's home on the appliance, and nobody has sudo. **`browser_preview` and `ssh_upload` read the step's own folder too**, named by its full path (or `~/work/.automation/<id>` on the computer); a relative folder still means the checkout. The step folder is reached from the work folder one directory at a time without following links (the agent has sudo on its computer and could put a link there). The refusal names both places. | The fix built its preview in the step folder, `browser_preview` refused it (“Only your checkout is read”), and Banjo made the screenshot by hand with Playwright and base64. |
| RN-R3 | **An automation's step checks what it changed and leaves the gate to CI.** With a writable checkout: build and test in the checkout; the step folder is for downloads and logs only; run the checks for what changed, not the repository's whole gate, and install no system software for a check (RN-02). A reviewer (read-only checkout of a branch other than its base, `reviewsChange`): read the change and its tests first, run a focused test only when reading isn't enough. Tool caches (`~/.cache`: npm, pnpm, Playwright's browsers) stay in the home so later steps reuse them. | The fix copied its writable checkout into the step folder three times, ran the gate five times (~2.5 min) and downloaded Chromium (177 MB) although `~/.cache/ms-playwright` held 658 MB; the reviewer rebuilt and re-downloaded the same; CI ran the gate minutes later. |
| RN-R4 | **Codex's missing-folder error reads “The folder it ran in doesn’t exist.”** in the activity list (server-side, `runtime/activity-copy.ts`: the runner's activity report has no detail field); the evidence keeps Codex's text, and the agent still gets Codex's own answer. | Two commands failed with “Failed to create unified exec process: No such file or directory (os error 2)”, which says nothing to a person. |
| RN-R5 | **An automation's step starts no run and opens no pull request of its own unless its request asks.** The runner's run line and RC-07's pull request line say so in an automation's turn; a person's request keeps them as before. | Run #9's fix started a run and opened PR #52 itself (both lines told it to), so the automation's own pull request step found it open and its title and review went unused. |

## Server (RN-S)

| # | Decision | Why |
|---|---|---|
| RN-S1 | **Background work nudged by a command runs outside that command's scope** (`outsideCommandScope`): the automation engine's timers, `tick` and `start`, the feedback assessor's passes, the feedback source's timers, the tracker service's background work, the GitHub poller's `arm` and run_command's delayed wake. | The engine's tick inherited the finished command's AsyncLocalStorage scope, so the trigger scan's `pipeline.transact` called that command's `beforeCommit`, hit `ReceiptSettled` (“the command receipt was settled elsewhere”) and rolled back — after every `automations.runNow` and `approvals.decide` (4× on John's box that day). |
| RN-S2 | **A Try it run reuses a fresh, identical assessment.** A test run's `dispatch_agent` step with `assessment: true`, about a tracker report or a GitHub issue (never a pull request; never a real run), takes the latest earlier run of the same automation (test or real, last 24 h) about the same item whose same step succeeded with an assessment from the same agent, the same workspace and identical rendered instructions. No dispatch: the step succeeds with that output and `reusedFrom: {runId, runNumber, finishedAt}`, and the automation says so in the run's thread with the earlier answer quoted (“Ask Banjo here if you want a fresh look.”). A step that reported nothing, or was itself reused, is never a source. | Run 9 re-assessed #16 (2 min, 538k input tokens) 90 minutes after runs 6 and 7 had, with the same instructions and the same report. Changed instructions or a changed report change the rendered instructions, so they assess afresh. |
| RN-S3 | **The automation owns its pull request.** A write step followed by an `open_pull_request` step for the same repo and branch gets one line at run time (“This automation opens the pull request itself after the review, so commit your work and don’t open a pull request or start a run for it.”); the MCP `open_pull_request` tool refuses in that turn; RC-08's automatic pull request skips runs started in it; and when the step still finds one open (a person opened it), it comments its rendered body on it once (`commented`, `commentUrl`; needs “Comment on pull requests” or “Open pull requests” at Can). Replaces AR-41's last sentence (“The fix prompt keeps its words”): the definition's words don't change, the line is added when the step runs. | PR #52 was titled and written by the agent, and the review never reached GitHub. |
| RN-S4 | **The pull request step says where the pull request is**, one line in the run's thread: “Opened [PR #52](…).” / “[PR #52](…) was already open.”; a run from a tracker report adds “The tracker isn’t told about it; you can set #16’s status on the run page.” | With RN-S3 the agent no longer names the pull request, and the thread had no link to it. |
| RN-S5 | **A merged fix for a tracker report gets one closing line** in the run's thread when AR-42's cleanup sees the merge (`mergedNotice`): “[PR #52](…) was merged. If the customer should hear, set the tracker #16 to “Fixed, waiting for a release” on the run page.” No tracker write (RN-03). | Closes the loop for the person who answers the customer. |
| RN-S6 | **A run's id counts as a run source** in `remember`, `propose_instruction` and `save_checkpoint`: `run_…` of this burrow and `#14` become the run's number before the input is checked; anything else is refused with “A run source is the run’s number, like 14.” Server only (core's `MemorySource` unchanged). | `save_checkpoint` refused the id `start_run` had just returned. |
| RN-S7 | **A skill learned in an automation's turn is told to its person**: the card goes to the DM between the agent and the person the run is for (“I wrote down how I did this while working on Acme dev #16, so next time goes quicker.”), with Remove; the proposal records that DM as its origin. With nobody to tell, it stays in the thread. | The card sat between the fix request and its answer in the automation's thread. |

## Not now

A private link field in the tracker for the pull request (a tracker change, RN-03); the guard refusing package installs in an
automation's step (RN-02); the empty `.automation` folders.
