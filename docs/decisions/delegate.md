# Handing tasks to T3 Code from a checklist card (DLG)

John, 2026-11-05 (main checkout), after the council shipped: “I want Whombat to have a delegate tool/skill and card
also, for example when the council responds with a list of tasks it would be nice to have Dusty show a list and if it
should implement this via this delegate feature. The delegate feature will then spawn new threads in T3 Code and the
card will show progress.” Asked how it would be built, then: “Yes implement this fully, make sure that we can always
chat with Dusty about the checklist card and it’s able to update the card after the chat (if needed).”

## What it is

| # | Decision | Why |
|---|---|---|
| DLG-01 | **A list of tasks becomes one checklist card**, the `delegation` card on a message of the agent's: its intro above, each task with a number, a title, a line why and a tick, and **Hand over N**, **Change something** (the reply box) and **Not now**. Nothing starts until the person hands it over, unless they already said to do them (`start`). One task alone stays an ordinary hand-over (T3-15). | The person decides what gets built; one card reads better than a long list and can be ticked. |
| DLG-02 | **Superseded in part by DLG-51: one thread leads every compatible task.** **Superseded in part by DLG-45, DLG-48: the combined candidate and compatible groups.** **Superseded in part by DLG-42: a task after one that waits to start too is done in that one’s thread.** **Superseded in part by DLG-20, DLG-23: tasks start from the default branch and get their checks passing.** **Each task runs in a T3 Code thread, worktree and branch of its own** (`delegate/<title>-<id>`, `-2` on a retry), from the project's checkout as it is now; a task that comes after another (`after`) starts once that one is done, from its branch (from the default branch once that one is merged, DLG-11). Each pushes its branch and opens a pull request when it is done and its checks pass (unless the person says not to), never merges in that turn and doesn't wait for its checks. Without a project, tasks run in scratch folders. | Independent tasks side by side can't overwrite each other, and each is a pull request someone can review on its own; merging is DLG-10's. |
| DLG-03 | **Superseded in part by DLG-54: “at once” counts threads and caps a lead’s subagents.** **Superseded in part by DLG-21: a task waiting for its checks holds no place.** **Three at a time** unless the person says otherwise (1–6, per card); the rest wait their turn and start by themselves as places free up. A task's AI is T3 Code's own default unless the person named one for it. | A few threads at once keep the person's computer and subscriptions usable; the server starts the next, so the agent isn't woken for bookkeeping. |
| DLG-04 | **Superseded in part by DLG-28 (finished tasks fold, a menu per row).** **The same card shows the progress**: each task's state in words, what it does now, how long it has worked, its AI, a question it asks or the OK it waits for in T3 Code, links to its thread and its pull request, the agent's line about it, and Stop per task and for all (both ask first). Tasks not handed over are left off once it is handed over. | John: “the card will show progress.” |
| DLG-05 | **The person can always talk about the card in its thread**: every turn of theirs there (the card live, or ended in the last week) carries the card with its tasks and briefs (`DispatchContext.delegation`, event `reply`), and the agent changes it in that turn with `delegate_update` — add, remove, reword, tick, reorder, what comes after what, start, stop, retry, more work for a task's thread, how many at once, pull requests or not, its words under the card — by the numbers the card shows, then says what it changed in a line. An ended card opens again when a task is added, retried or sent more work. | John: “make sure that we can always chat with Dusty about the checklist card and it’s able to update the card after the chat.” |
| DLG-06 | **Ticks are the server's**: a tick on the card is a press (`delegations.pick`), so the card on every device and the agent's next turn see the same list. | The agent and the person talk about one list. |
| DLG-07 | **Superseded by DLG-26 (woken only when a task needs judgment, and at the end).** **Whombat wakes the agent as tasks end** (trigger `delegation`): the tasks that ended with their last answers, joined while the turn is queued; it writes a line under the card and on their rows and posts nothing else. Once every task handed over is over (or waits for one that didn't finish), the turn has every answer and the agent finishes with a summary under the card (`delegate_finish`); the person gets one inbox row and one push for each end. A task's question or permission request wakes the agent as any T3 Code thread's does (T3-17). | As the council (CNL-41, CNL-42): one message carries it all, and the end is the news. |
| DLG-08 | **After a council, its list is offered as a card**: when what the council came up with is things to do in a project, the agent offers them with `delegate_offer` right after `council_finish`, one task per item. | John's example. |
| DLG-09 | **Only in the person's own turns, while T3 Code manages** (the council's rule, CNL-05): never from an automation's step or a brief. One live card per thread. | It starts work on the person's computer. |

## Merging the pull requests

John, 2026-11-06, after ten tracker exam tasks ended as ten open pull requests, four with failing checks, that he had to
ask Dusty to fix and merge: “I want this to be done automatically next time.” Asked whether to merge every pull request
as soon as it is done: yes, one at a time.

| # | Decision | Why |
|---|---|---|
| DLG-10 | **Superseded by DLG-45, DLG-47 for automatic lists.** **Superseded in part by DLG-40: a pull request whose checks passed merges as it is.** **Superseded in part by DLG-20, DLG-22: checks are got passing before the merge’s turn.** **Whombat merges each task's pull request by itself once its work is done, one at a time, in the card's order** (`merge`, on by default with pull requests; the person can say to leave them for review, for the card or one task). The task's own thread is told it is its turn (`mergeBrief`): bring the branch up to date with the default branch, resolve conflicts so both changes keep working (a migration number taken gets the next free one), get its checks to pass without weakening any, check the default branch didn't move, merge it the way the repository merges, and end with `Merged: yes` or `Merged: no` and why. It doesn't merge what needs a person (a review, a decision, checks still failing after three rounds of fixes). | Ten pull requests from the same main, merged at the end, collided (25 files in conflict in one, three migrations with one number) and the combining took a new thread hours; merged as each is done, every later one starts from or updates onto what is merged, and the thread that wrote a change resolves its own conflicts. One at a time so two that each pass alone can't land together and break the default branch. |
| DLG-11 | **Superseded by DLG-45, DLG-48 for automatic lists.** **A task waiting its turn to be merged needs nothing**: its thread stays unsettled for the merge, the agent isn't woken for it (the merge's end is the news, with both answers), the card shows “Waiting to merge”, then “Merging”, “Merged” or “Not merged”. A task after another starts once that one is merged, from the checkout brought up to date with the default branch; after one not merged it waits, as after one that didn't finish. Every task's brief tells it to start from the default branch as it is on origin. The delegation is over only once no pull request waits, and the summary says what got merged. | The person hears once, when it is all in; what comes after builds on what is merged. |
| DLG-12 | **Superseded in part by DLG-61: a merge has no time limit.** **Superseded in part by DLG-46, DLG-47: a combined candidate gets a separate guarded merge and independent confirmation.** **A merge isn't over while T3 Code watches its pull request** (its checks or reviews): T3 Code runs the thread again when they move. It is merged when T3 Code says so or the last answer's `Merged:` line does; a merge runs three hours at most, then it is stopped and left open. Stop on a merging task, or on the card, leaves its pull request open (not merged); the agent has one merged again with `change` `merge: true`. | T3 Code's agents wait for checks by watching the pull request and ending their turn; Whombat follows the same rule as for hand-overs (T3-23). |

## Checking the combined candidate before merging

John, 2026-11-07: review of the faster implementation found that merging each change before the combined check could
break the default branch, that an absent check could look successful, and that a full card or later work could skip
its final check. The speed improvement keeps focused checks during coding and checks the combined change before it
reaches the default branch.

| # | Decision | Why |
|---|---|---|
| DLG-45 | **Superseded in part by FT-04 in [fast-testing.md](fast-testing.md): ordinary tasks test with `fast-test`, or the quick checks the repository names.** **Superseded in part by DLG-64: focused checks include the repository’s own pre-push checks, and a fix also runs what the failed run never reached.** **Superseded in part by DLG-56: work all in one pull request is checked as that pull request.** **Automatic lists prepare one combined candidate before touching the default branch.** Ordinary tasks run focused checks for the code they change, push and open source pull requests; they do not wait for redundant whole-project CI or merge individually. A dependent task may start from its finished predecessor's branch once its focused checks pass. Once ordinary work is over, the final task starts from the latest default branch and merges the eligible source heads in dependency order, retaining their ancestry, into one integration pull request. Kept-open work and work that depends on it stay out. Required checks for the change run once on that exact combined revision, including critical database, browser or VM boundary checks when relevant; unrelated nightly and release matrices stay out. Exact-revision results can be reused. Sources stay open until the combined merge. No diff means checking the exact default-branch revision without an empty pull request. | Full checks on every source and again at each merge repeat the same work; checking the combined candidate first protects the default branch from changes that fail together. |
| DLG-46 | **Superseded in part by DLG-62: without required checks on the default branch, the final thread’s own full check is the evidence.** **Expected checks without a branch policy: superseded in part by DLG-59.** **Completion text is evidence to verify, never permission to merge.** The final answer carries a structured `Verification:` line: full checked revision and base, the input fingerprint and generation supplied by Whombat, the expected check names, and each result's exact revision and state. Whombat independently reads GitHub's candidate and base heads, required checks, check runs and commit statuses, and confirms each source head is in the candidate's ancestry. Expected checks include jobs that have not reported yet; absent, queued or running results mean waiting. Every expected and observed check must pass on the checked revision. A failing baseline is reported honestly and blocks certification. An explicit no-checks report cannot replace independent evidence; when GitHub cannot establish the expected checks, automatic merging stays blocked. | One early green job, a missing status or a confident answer cannot certify an untested combined change. |
| DLG-47 | **Superseded in part by DLG-68: Whombat merges the checked candidate itself.** **Checking and merging are separate runs, tied to the same inputs.** Adding, retrying, sending more work or changing what will be included invalidates the final check, advances its generation and stops an obsolete final run. Its answer must match both the current generation and a fingerprint of the ordinary tasks. After independent verification, Whombat authorizes a merge of only the checked head and base. The merge uses an exact head guard and strict up-to-date protection, a merge queue, or a safe atomic fast-forward guarded by the checked base. It retains source ancestry and the checked tree: no squash, rebase, conflict resolution or extra commits during this run. A changed head or base needs a fresh combined check; if the repository offers no safe merge method, leave the candidate open. Whombat independently confirms the delivered tree and ancestry before completing the list. | Late work or a moving default branch can make a previously green candidate stale; the merge must deliver what was tested. |
| DLG-48 | **Superseded in part by DLG-51: every compatible task shares the group, dependent or not.** **Only compatible dependent tasks share a durable group.** Resolve each task's own AI choice, then the card's defaults, before grouping: provider, model and options must agree, as must keeping the pull request open versus automatic integration. Run grouped work in dependency order even when the card is reordered. One stored group id joins its rows before a thread id exists; Stop, retry, more work and keep-open controls apply to the shared branch, including a launch still in progress. A dependent task with a different choice starts separately from its predecessor's finished branch. | Grouping saves repeated setup and checks without silently replacing a person's model choice, mixing review preferences or losing a stop during launch. |
| DLG-49 | **Every automatic list has its final row: up to twelve ordinary tasks plus a thirteenth reserved row.** The final row cannot be removed or unticked while automatic merging is enabled. It starts only after the ordinary tasks are over and there is eligible work to combine or already-merged work to verify. Active lists missing it are backfilled on upgrade and on the normal sweep; an individual merge already in flight may finish, then the list still needs a fresh combined check. Queued, working or waiting-to-merge final work keeps the list open. A failed final ends honestly as incomplete with source pull requests open. | A full card, rollout or a late retry must not bypass the check that makes automatic merging safe. |
| DLG-50 | **One combined candidate and merge at a time per T3 Code connection and project.** Cards for that same repository coordinate the whole final phase, including the gap between checking and the authorized merge; ordinary independent tasks can still run in parallel. Other connections and projects proceed independently. | Two cards must not each certify against the same base and then race to change it; unrelated repositories need not wait. |

## One thread leads the list

John, 2026-11-07, about a council's Exam UI list on Home split into twelve tasks: “Should we do this or should we just
hand over the full task to the agent in T3 Code and it will manage the subagents instead?” The research found that
Dusty splits the work before anyone reads the code: all eight of that list's pull requests changed the same
translation files and help page (seven the same stylesheet, five the same screen), which the same-files guard missed
because the parts were named differently, and the lists on Home took 2 to 6½ hours for tasks written in minutes. Then:
“When we hand-over should we give the instructions to the agent to be the orchestrator and implement the job with
subagents if possible? Research this”: Dusty's threads started no subagents unasked (only reviews their briefs asked
for), T3 Code tells a thread another agent started that it starts none unless its task says so, Codex starts them only
when asked, and Claude Opus 5 delegates readily, small work too (Anthropic's prompting guidance: only for large,
genuinely independent work; OpenAI: be careful with parallel write-heavy work; Cognition: parallel writers make
inconsistent changes). Then: “Okay, implement this.”

| # | Decision | Why |
|---|---|---|
| DLG-51 | **One T3 Code thread leads the list.** The first ticked task to start takes into its thread, branch and pull request every other task waiting with the same AI choice and keep-open preference, and every task that builds on one of them; what a task builds on comes first, card order otherwise. A task with another AI (the person's, or the agent's for it), and what builds on it, runs in a thread of its own. The parts a task changes (DLG-24) only order such a task. The thread is named for the job (“Simplify the Exams page (3 items)”). A list handed over before the combined candidate (DLG-45) keeps doing only the tasks after the first in its thread. | The thread reads the code before it splits the work; one branch takes conflicts and repeated checks out of the list, and one pull request goes to the combined check. |
| DLG-52 | **Every thread Whombat or the agent hands work to is told when to use subagents**: it leads and owns the result, reads the code and plans first, and may start subagents only for sizeable, independent parts (another screen, package or app, or wide reading), at most the card's “at once” (three for a hand-over of the agent's own), each with its goal, the files it may change and what done means. Code-writing subagents get a worktree of their own or files nobody else touches, and the lead brings their work onto its branch. Small, sequential or same-file work it does itself, the shared files (translations, help pages, migrations) too, and it runs the quick checks once on the combined work; it doesn't use subagents to re-check its own work (a review by another model it was asked for still runs). Whombat appends these lines to the agent's own `t3_thread_launch` messages, once. | Without the words a thread another agent started does all the work alone, and Codex never delegates; with “use subagents if possible” Claude splits small work too. A rule for when, with a cap, gets parallel work where it pays. |
| DLG-53 | **Superseded in part by DLG-63: while the lead works, its tasks show as one row.** **The lead ends with a line per task, by its number on the card** (`Item 3: …`): each row gets its line unless the agent wrote one, and one that says “not done:” shows “Ran into a problem” with why, stays out of what is combined and merged, and wakes the agent.
