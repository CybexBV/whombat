# Bluetooth: the server

Decisions the server stream (S) made building bluetooth.md (BT-01…BT-11) from the build brief
(`docs/implementation/bluetooth/assignment.md` §2, §3 “S”). Code: `apps/server/src/managed/` — `bluetooth-client.ts`
(the Bluetooth service's socket), `host-bluetooth.ts` (the service, the audit record, the session ops),
`fake-bluetooth.ts` (the fake service); `apps/server/src/desk/bluetooth.ts` (the screen's routes).

| Id | Decision | Why |
|---|---|---|
| BT-S01 | **Built against §2's shapes first, with a local stand-in, then contracts 0.109.0** (merged from `bt`): the stand-in is gone; the shapes and session ops from `@whombat/protocol/session`, the Bluetooth socket's and the desk socket's bodies from `@whombat/control-contracts/local`, the audit types from `APPLIANCE_EVENT_TYPES`. `host.bluetooth` is in `IMPLEMENTED_FEATURES`. | The brief's order of work; the contracts were made at the same time. |
| BT-S02 | **The Bluetooth service's client** mirrors the presence client: `WHOMBAT_BLUETOOTH_SOCKET` (unset: no Bluetooth), `WHOMBAT_BLUETOOTH=fake\|off` (the fake is refused in production as presence's is), one port per `Services`. It uses the runtime's shared unix HTTP transport with a deadline on the **whole call**: 2 s for state, scan, pair, confirm and cancel (the service answers them from memory; a pair answers 202 once it started); **16 s for connect** (`BLUETOOTH_CONNECT_S`, plus a second for the service's answer); **5 s for disconnect and forget** (BlueZ waits for the link to drop). Answers up to 64 KiB, parsed with the contract (else `invalid_answer`). A refusal keeps its status and `LocalError` code only, never the service's words (they may name an address, BT-10). | The brief's numbers, with the two calls that wait on the radio given time for it: a disconnect that is refused as `unavailable` after 2 s while it worked would look broken. |
| BT-S03 | **The session ops are owners' only** (`forbidden`). Without a Bluetooth service the reads say `not_managed` and every change is refused `no_bluetooth` (not Wi-Fi's `not_implemented`): the app shows the same words as for a box whose adapter is off. Reads never throw: a service that doesn't answer, answers 5xx or outside the contract is `unavailable`, logged at most once a minute per kind (state, scan, change) with status and code only; a scan's `no_bluetooth` is a `reason`, not a warning, and a scan while a pairing runs is refused `busy` (`conflict`; the contract's scan reasons are only for “no scan”), on the desk 409 `busy`. A change's refusal rides on `BLUETOOTH_ERROR_STATUS`'s generic code with Bluetooth's own in `details.code` (as `host.wifi.*`); `unavailable` has no details. Each change is an external effect (`bluetooth.pair`, `.confirm`, `.cancel`, `.connect`, `.disconnect`, `.forget`; not idempotent): a 4xx or a socket nobody listens on did nothing, a timeout may have acted. | As HD-S04/HD-S05: the app polls every second while looking or pairing, so the journal must not fill; the effects are `never` in `OPERATION_SAFETY`, which is what an effect before the commit needs (CS-08). |
| BT-S04 | **A pairing is recorded once, when it reaches `done`.** The runtime keeps the pairings it started (id → who started it, until the deadline + 60 s). Every answer that carries the pairing settles them — a state read by the app, the screen or the runtime itself, and the answers to pair, confirm and cancel: one of ours that ended is let go *at once* (before the record is written, so a second read can't write it again) and recorded as `bluetooth.device_paired` when it is `done`; a failure is not recorded; one the service no longer shows is let go unrecorded; an answer to a read sent before a pairing started can't tell about it. While one of ours runs, the runtime reads the state every `BLUETOOTH_POLL_MS` itself, so a pairing nobody watches is recorded too, and a new pairing first settles the one before it. The record of a pairing a request merely saw is written outside that request's command (`outsideCommandScope`, as the licence's transitions, MR-57), so it never becomes part of its receipt; the watcher runs outside it too. A pairing that ends while the runtime restarts, or one whose start was answered too late (an unknown outcome), isn't recorded. | The brief's “pick the simplest that never writes the same pairing twice”: one map and one rule for every read, and a watcher only while something of ours runs. |
| BT-S05 | **A removal is one `bluetooth.device_removed`** once the service answered, with the name and kind the paired list had just before (the forget answer has no device; a list that couldn't be read gives “Bluetooth device”, `other`). A refusal writes nothing. Both records: payload `{name, kind, via}`, in their own transaction; the actor is the owner's account and device, or none from the screen; an entry that can't be written is logged as an error and the change is still answered. Connecting and disconnecting aren't recorded. | BT-08 names pairing and removing; HD-S06's way. |
| BT-S06 | **The screen's routes live in `desk/bluetooth.ts`** and join the desk socket through `DeskRoutes` beside the network's. The rule is `deskMayChangeBluetooth`: unlocked (`DeskLock`) or not claimed (`TrustService.isClaimed`), asked again on every request; otherwise `why: 'locked'`. Unlike Wi-Fi, being offline doesn't open it, and **every POST, scans too, is 409 `locked`** on a locked claimed screen, before the service is asked. Without a Bluetooth service the GET answers `adapter: null, missing: 'no_adapter'` and every allowed POST is 409 `no_bluetooth`. The service's refusals pass through (`no_bluetooth`, `busy`, `not_paired` 409, `not_found` 404, `unavailable` 503); a state that can't be read is 503. Every change that worked keeps an unlocked screen unlocked. | BT-02 and §2.4; the network's shape keeps the two route sets alike. |
| BT-S07 | **Logs carry kinds, `via` and pairing ids**, never an address, and never the service's error words. | BT-10; the name is in the audit record already. |
| BT-S08 | **`host.bluetooth` is advertised only while the runtime has a Bluetooth service** (the socket or the fake), as `desk` is only with the desk socket: a box without one doesn't show the section. | BT-02's section is hidden where there is nothing to pair; the brief's “the feature advertised only when the socket is configured”. |
| BT-S09 | **The fake** (`managed/fake-bluetooth.ts`, `WHOMBAT_BLUETOOTH=fake`): adapter `whombat`; paired “Keychron K3” (keyboard, connected, battery 80) and “WH-1000XM5” (headphones, not connected); looking finds, one a second, “MX Master 3S” (mouse, no code), “Magic Keyboard” (keyboard: code `480516`, `typed` one digit a step, then connecting), “JBL Flip 6” (speaker, no code), **“Xbox Wireless Controller”** (game controller: asks to confirm `480516`; No ends it `rejected`, as the contracts say) and “Old Speaker” (refuses: `rejected`); a “Pixel 9” phone is never listed (BT-01). Steps of 1.5 s on the clock it is given; a pairing stops looking; an ended one stays 60 s; the deadline ends one that is still waiting `timeout`. Knobs: `missing` (`no_adapter`, `no_driver`, `disabled`) and `down`. | Tests and the dev world show every phase and refusal without BlueZ or a radio; the controller is added to the brief's list so the Yes/No question can be seen too. |
