# The Vault for one person, and asking for sign-ins (VLT)

John, 2026-11-03 (main checkout): with Whombat used by one person, is the Vault still worth having, or should Hermes
keep secrets its own way? After the research: keep the Vault as Whombat's one sealed store, drop what was there for
several people, use Hermes's official plugin doors, fold the Vault's MCP entries into Connections, and — John's
addition — let Dusty ask for any sign-in (a website login, a server's password, a private key, a one-time code) with a
special input that saves it in the Vault and never reaches the chat.

What Home showed that day: two entries (a server key, an API key), both on for Dusty, 336 uses in seven days, all of
them handed to Dusty's commands; no `.env`, no Hermes vault in any Hermes home; only Hermes's own `auth.json` (the
ChatGPT sign-in).

Code: `apps/server/src/vault/`, `packages/core/src/vault/`, `packages/core/src/domain/guides.ts` (`GuideVaultAsk`),
`packages/core/src/contracts/mcp-setup.ts` (`vault_ask`), `apps/runner/src/logins.ts`,
`packages/hermes-whombat/whombat_hermes/logins.py`, `packages/commands` (the commands' SSH), the Vault and guide-card
screens on web and phone. Implementation brief: `docs/implementation/vault-simplify/assignment.md`.

## The Vault stays

| # | Decision | Why |
|---|---|---|
| VLT-01 | **The Vault stays Whombat's one sealed store for what the agent signs in with.** Hermes's own `.env`, its local credential vault and its password-manager sources (1Password, Bitwarden) stay unused; the runner keeps wiping Hermes's local store after every turn. | Hermes keeps API keys in plain text in `.env` and its vault's key beside the vault (its own docs: a copy of `~/.hermes` decrypts it); it has no phone or web screens, can't ask for a secret over ACP (`prompt_unavailable`) and has nothing for SSH. The Vault is sealed with the box's master key, backups carry sealed values only, the cloud never sees one, and connections and accounts are sealed the same way: one story. |
| VLT-02 | **Delivery stays as it is**: an API key's value in each command's environment and a server key with its config and pinned host keys on the command's tmpfs, in the person's turns only; a login through Hermes's credential vault; never in an outsiders' turn. Hermes's secret sources (`register_secret_source`) are not used for keys. | Hermes reads secret sources once when it starts, and one Hermes stays warm across turns: a key switched off would keep reaching commands until a restart. Today it stops at the next command. |
| VLT-03 | **The home-network list and the wall stay unchanged.** | They are the box's, not the Vault's alone: connections add networks to them (`connections.allowNetwork`), the server's own LAN calls and SSH go through them, and the agent's network uses them when the local network is closed. Nothing would get simpler. |

## Asking for a sign-in

`vault_ask` (connect-in-chat.md CIC-10…CIC-15) already asks for a website password, an API token or a username and
password with a write-only card. It couldn't ask for what a server needs, a private key, an authenticator key or a code
a site sends, and only in the Chat room; a server's password came only from a chat message (VS-11).

| # | Decision | Why |
|---|---|---|
| VLT-40 | **One card asks for every sign-in**: `vault_ask` with the kinds `login` (a website: username, password and an optional authenticator key), `token`, `basic`, `server` (new: VLT-42) and `code` (new: VLT-44). What the person types goes from the card to the Vault as them; the agent gets the entry's id and how it went, never the value. | One place, one habit: whenever Dusty needs something only the person knows, a card asks. |
| VLT-41 | **Asked in the thread the work is in**, in any room of the person's (Chat, a server's thread, an automation's thread), on web and phone. Never in an outsiders' turn (they get no Vault, OP-17). The desk screen shows such a card as “Answer on your phone or computer” and never takes a secret. | The person answers where they are reading; a shared screen is no place to type a password. |
| VLT-42 | **`server`**: for a new server or when Dusty's key was refused. The agent gives the address (`host[:port]`), the username and, for a refused key, the reason; the card offers three ways, the first chosen: **Use the password once to put Dusty's key on it** (Whombat signs in once, adds the key's `authorized_keys` line, signs in with the key and forgets the password, as VS-11), **Keep the password** (for servers that don't take keys: Whombat checks it signs in, keeps it sealed with that server, and the commands sign in with it through an askpass helper reading the turn's tmpfs, never an argument or a variable), **Use my own private key** (pasted or picked as a file, with its passphrase if it has one: imported as a Server key entry covering this server, the passphrase used once to open it and not kept). The server is added with first-contact host-key trust (VS-10) and checked before the card locks. A wrong password or a key the server refuses shows on the card in plain words and the card stays open (three tries, then it closes and the agent hears `refused`). | John's example: the key didn't work, Dusty asks, the person types it once, it is in the Vault and never in the chat. Putting the key on is safer than keeping a password, so it is the default; some servers only take passwords. |
| VLT-43 | **`vault_add_server` no longer takes a password**: its `password` input is ignored (kept in the contract until its next major) and a refused key answers `key_refused` with the hint to ask with a `server` card. A password pasted into the chat anyway is still blanked and used (`vault_save`, VS-07) as the safety net. | A password in a message passes the chat and the model before it is blanked; the card never does. |
| VLT-44 | **`code`**: a one-time code a site or server sent by text, mail or an app (“Type the code {site} sent you”). Used once for the sign-in under way, held in the server's memory for that turn only, never stored or logged; the card says “Used once, not kept.” | Two-step sign-ins are common; the code is as private as the password while it is valid. |
| VLT-45 | **Hermes's own asks go through the card.** Whombat's plugin serves Hermes's save-login prompt (`set_save_login_prompt_callback`) and code prompt (`set_code_prompt_callback`) in the person's turns: the plugin asks the runner over the logins socket, the runner asks the server, the server posts the `login` or `code` card in the turn's thread and waits (a login up to 10 minutes, a code up to 5). A login is saved in the Vault by the person and handed back for Hermes to fill (Hermes's local copy goes with the turn, VLT-20); a code goes back once. When the wait runs out the card stays: Hermes hears it was declined for this turn, the agent is told the person was asked, and the answer wakes it in that thread later (CIC-14). | The browser reaching a sign-in page is exactly when to ask, and Hermes already knows how to fill once it has the login; the turn waiting a few minutes keeps the page where it was. |
| VLT-46 | **A website login may carry its authenticator key** (the setup key or `otpauth://` link): sealed beside the password (`totp`, settable from this version on the card and on the entry's page), and the runner's logins service gives Hermes the current code (RFC 6238; the link's algorithm, digits and period, default SHA-1, 6, 30 s) only for that login's own site. | Hermes fills two-step codes itself when it has the key (its `has_otp`); the slot was reserved since VT-D28. |
| VLT-47 | **Nowhere but the Vault**: for every kind, the value is in no message, signed event, realtime frame, push, log line, activity row, `DispatchContext` or model context, tested as CIC-15 is; the card's stored answer holds the entry's id and the outcome only. | The brief's bar, unchanged. |
| VLT-48 | **The agent never asks for a secret in a message**: its Vault lines and `vault_ask`'s description say to ask with the card and end the turn (or, inside Hermes's browser, to let Hermes ask), and to say in one sentence what it needs and why. | Habits come from the prompt; the card is the only way that keeps the value from the model. |
| VLT-49 | **The card's words** (visible, plain): titles “Dusty needs the password for github.com”, “Dusty couldn’t sign in to prod-1 with its key”, “Dusty needs to sign in to 192.168.1.20”, “Type the code github.com sent you”; under the field “It goes straight to your Vault. Dusty never sees it.” (a code: “Used once, not kept.”); buttons Save (a server: Sign in) and Not now; a locked card “Saved to your Vault · prod-1” or “Signed in to prod-1 · key added”. The assistant's own name, never “the agent”. | Concise replies: what happened and what to do, nothing technical. |
