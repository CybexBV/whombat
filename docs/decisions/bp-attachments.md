# Workstream A (buzz-parity): attachments and agent artifacts

Files in conversations for people and agents: pick / paste / drop → upload with progress → stored bytes +
metadata → attached to a message (files alone are a message) → authorized preview and download → real input
to agents → agents publish artifacts back. Binds: `buzz-parity.md` BP-03…07, BP-10, BP-12. Supersedes
`messaging.md` MS-08 (the disabled `+ file` chip and `VITE_UPLOADS`).

## Decisions

| # | Decision | Why |
|---|---|---|
| BP-A01 | **Contracts.** `uploads.create` (reserve for one conversation: name, declared type, size) and `uploads.discard` are JSON endpoints in `api`. The byte transfers are described in `ATTACHMENT_TRANSFER` (PUT `/burrows/:burrow/uploads/:id/content`, GET/HEAD `/burrows/:burrow/attachments/:id`, runner GET `/internal/runner/dispatches/:dispatch/attachments/:id?runnerId&attempt`) and registered as raw routes (`files/routes.ts`), because they are not JSON. `Attachment` gains `kind`, `width`, `height` (defaults, so older payloads parse). New error code `too_large` (413) with `details: {reason: 'file'\|'quota', limit}`. | Contract-first without forcing bytes through the JSON adapter. |
| BP-A02 | **Storage.** `FileStore` (`stage` → `commit` / `discard`, `open` with a range, `size`, `delete`, `list`, `sweepStaging`); the shipped `LocalFileStore` keeps `$WHOMBAT_HOME/files` (`WHOMBAT_FILES_DIR` overrides), 0700 dirs / 0600 files, content-addressed keys `sha256/ab/cd/<sha256>` (never file names), exclusive temp file + fsync + rename + directory fsync, `O_NOFOLLOW` opens and realpath checks of parent directories. The same bytes share a blob; every upload keeps its own row, name, conversation and uploader. **No S3 backend and no S3 config**: a second implementation of `FileStore` is the extension point. | BP-12; no dead config. |
| BP-A03 | **Sniffing** (`files/sniff.ts`), from the bytes only: PNG / JPEG / GIF / WebP with a readable header (size from IHDR, SOFn, the logical screen, VP8/VP8L/VP8X) and at most 20 000 px a side and 60 MP (decompression bombs) → `image`; a damaged header → refused (400). `%PDF-` → `document`. Valid UTF-8 without NULs and with under 1 % C0 control bytes (tabs, line breaks, ANSI escapes allowed) → `text`, typed from a small allowlist by extension (`text/markdown`, `application/json`, `text/csv`, `text/tab-separated-values`, `text/yaml`, else `text/plain`) — never `text/html` or `image/svg+xml`, so HTML and SVG are text downloads. Else `file` (`application/zip`, `application/gzip`, `application/octet-stream`). Display names: last path segment, no control / bidi / zero-width characters, whitespace collapsed, no leading dots, ≤ 255 characters keeping the extension (`safeDisplayName`, core). | BP-05: the client's type is never trusted. |
| BP-A04 | **Superseded in part by page-sets.md PG-19, PG-20** (no hourly limit by default; the disk is the files' limit unless a quota is set). **Limits.** `WHOMBAT_UPLOAD_MAX_BYTES` (default 25 MiB, ceiling 1 GiB) checked at reserve and while the body streams (it must equal the reserved size: more → 413, less → 400). `WHOMBAT_UPLOAD_RATE_PER_HOUR` (default 200) per account — every principal of the account, any device — or per agent, counted from the rows (durable, restart-proof) → 429. `WHOMBAT_BURROW_QUOTA_BYTES` (default 10 GiB) over the logical size of all the burrow's rows, reservations included → 413 `quota`. | Clear failures; no in-memory counters to lose. |
| BP-A05 | **Serving.** Authorized on every request: the viewer is a member of the conversation of the message the file is on (removed later → gone), or the uploader while it is unsent. Anything else — other conversations, other burrows, unknown ids — is **404**; not signed in is 401. Headers: `Content-Disposition: attachment` except sniffed images (inline; `?download=1` forces attachment), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`, `Cache-Control: private, max-age=3600` (a browser may keep what its own user already saw for an hour; the server re-checks every request), exact `Content-Length`, `ETag` = sha256 (304 on `If-None-Match`), one `Range` (206 / 416), HEAD. `Attachment.url` is the stable relative path; no signed or expiring URLs. | BP-05; no probing. |
| BP-A06 | **Writes.** Reserve, complete, discard, publish and attach are commit-pipeline commands. The PUT streams into the store's staging area *outside* the transaction (no lock held while bytes arrive), then `complete_upload` moves the blob under a per-blob advisory lock and marks the row `ready`. Signed events, hidden from the log like chat: `attachment.uploaded` {attachmentId, conversationId, size, sha256, kind} and `attachments.attached` {messageId, [{id, size, sha256, kind}]}. Reserving and discarding are drafts and sign nothing. One PUT per upload at a time (409); a body cut off leaves nothing ready and the reservation open, so a retry works. | BP-06: ids, sizes, hashes — never names or bytes. |
| BP-A07 | **Attaching.** `messages.send` / `reply_in_thread` / `post_message` take `attachmentIds` (≤ 10) of the sender's own `ready` uploads for *this* conversation that are on no message; each other case is refused with what is wrong (“Unknown attachment.”, “That file was uploaded for another conversation.”, “That file hasn’t finished uploading.”, “That file is on a message already.”). Text may be empty only with files (contract refine; the server's “Say something first.” otherwise). A `clientId` retry of a send that went through returns that message. | Files alone are a message; no attaching someone else's upload. |
| BP-A08 | **Retention and the sweep.** A file lives as long as its message. Unsent uploads (reserved or ready) older than `WHOMBAT_UPLOAD_ORPHAN_HOURS` (default 24) and rows whose message no longer exists (today only the demo rewind deletes messages) are deleted; then every blob no row references is removed under its lock (the lock an upload takes to commit the same bytes), and staging files a crash left. At start and hourly; idempotent; state is the database. Direct maintenance like the runner lease sweep, not signed events. The audit log keeps only ids, sizes and hashes. | BP-10. |
| BP-A09 | **Agents: which files.** `DispatchContext.attachments` = the ready files on the messages the dispatch shows the agent (trigger, the 20-message window, the thread) while it is a member of that conversation; answer-mode (search) dispatches get none (their answer goes to someone else). The runner fetch and `read_attachment` recompute that set at call time (lease + set + membership). | BP-04; the existing membership gate. |
| BP-A10 | **Agents: how.** `planAttachments(context, capabilities)`: images as model input where `images` (≤ 8, ≤ 3.75 MB, ≤ 8000 px a side), PDFs where `documents` (≤ 2, ≤ 10 MiB), ≤ 20 MiB together; text files ≤ 2 MiB fetched for an 8 KiB excerpt each (32 KiB in all), fenced as data, the rest through `read_attachment`; everything else, or over a bound, an honest line (“report.pdf is attached; you can’t open PDFs here. Say so if it matters, and don’t guess what it contains.”). The trigger's and the thread's files come first. Claude: `images`, `documents` true (base64 `image` / `document` blocks after the prompt, each labelled with its id). Codex: `images` true (`localImage` items), `documents` false. `attachmentNote` names a message's files and ids next to its text, and `ATTACHMENT_TOOLS_LINE` the file tools, in both the persona and the runner's own prompt (`apps/runner/src/prompt.ts`, which live turns use). | BP-03, BP-07. |
| BP-A11 | **The per-turn copy lives under the workspaces root**, `<WHOMBAT_WORKSPACES>/.scratch/turn-files-<dispatch>-<attempt>/` (0700 / 0600, removed after the turn; the workspace cleanup removes leftovers of a crash like other `.scratch` dirs) — **not under the turn's cwd** as BP-04 sketched: the cwd is the owner's working directory or a checkout, where copies would dirty it and could be committed. Guarded sandboxes already deny the workspaces root, so no agent shell or file tool reads them; the model gets images and PDFs as input and text as excerpts plus `read_attachment`. Codex's app-server (not sandboxed itself) reads `localImage` paths there: verified live on a guarded turn. | BP-04 (agents never get storage paths) without touching the owner's files. |
| BP-A12 | **`read_attachment {attachmentId, offset?, maxBytes? ≤ 64 KiB}`** returns whole UTF-8 characters and `nextOffset`; non-text kinds return `text: null` and a note. **`upload_file {conversationId, name, text \| contentBase64, contentType?}`**: ≤ 10 MiB decoded (and the upload limit), sniffed like any upload, stored as uploaded by the agent for that conversation, which it must be able to post in — the rule `post_message` has (there is no key for posting) — plus the rate limit and quota; then `post_message` / `reply_in_thread` with `attachmentIds`. `/mcp` accepts bodies up to the base64 of 10 MiB + 1 MiB. The persona's “How you act” names both tools. | BP-04 artifacts through a bounded tool. |
| BP-A13 | **Web.** `+ file`, paste (files and screenshots; pasted text stays text) and drop on the room (“Drop files to attach them”). Chips upload at once: name, “Uploading 42%” with a 2px bar (`progressbar`), Cancel ×; failed chips say why (`role="alert"`) with Retry; ready chips show the size and Remove ×; a polite live region counts them. Send waits while anything uploads (`aria-disabled`, “Wait for the upload to finish”) and works with files alone; a refused send keeps the draft and the chips. Chips belong to their conversation (kept outside the component, like drafts). Messages: images as thumbnails in a 360 × 240 box (shrinking in the thread pane) opening a lightbox (name, “640 × 360 · 11 KB”, Download, Close); text as a preview of the first 10 lines (a 4 KB range fetched and rendered as text in a `<pre>`, never HTML) above its chip; PDFs and files as chips (icon, name, “PDF · 2.4 MB”, download). The thread pane shows files too; its reply box stays text-only. | Everyday flows; same look for artifacts. |
| BP-A14 | **Android.** A paperclip in the pill composer (server mode only; the demo world has no uploads) offers “Photo” (the system photo picker via expo-image-picker: no EXIF, no library permission; camera and microphone permissions blocked) or “File” (expo-document-picker). Chips with progress, Cancel, Retry, Remove (44dp). Images load with the bearer token and open full screen with Share; files download to the cache (expo-file-system) and open the share sheet (expo-sharing). Config plugins cover iOS (`NSPhotoLibraryUsageDescription`: “Whombat opens your photos only when you attach one to a message.”). Receiving shares from other apps is not done. New native modules: a native rebuild is required. | Android first, iOS stays buildable. |
| BP-A15 | **Holds when a limit is set** (page-sets.md PG-19, PG-20). **The hourly rate counts reservations, not rows; the quota is checked under the burrow lock** (security review). Every reserve and artifact publish writes an `upload_reservations` record (attachment id, burrow, rate key `account:<id>` for people or `principal:<id>` for agents, time) that discarding the upload does not remove, so reserve → discard loops still count; the attachment sweep prunes records older than two hours, and the migration seeds them from the last two hours of uploads. The uploader's count is checked and recorded under an advisory lock on its rate key (class “WHUR”: one account reserving in two burrows at once). The quota sum and the reservation run under the burrow's advisory lock that the commit pipeline holds for every command (`lockBurrow`), so concurrent reserves in one burrow are serialized and cannot pass the quota together (tested with five concurrent reserves). | A rate that deleting rows resets is no rate; a quota checked without a lock can be overshot by racing requests. |
| BP-A16 | **`/mcp` authenticates before it reads a body** (security review SEC-MCP-BODY). Its body limit is raised for `upload_file` (`MCP_BODY_LIMIT`, ~14.3 MiB), so the route verifies the bearer agent token in an `onRequest` hook, before Fastify reads or parses anything: a request without a live token gets 401 (and anything but POST 405) with `Connection: close`, whatever its body — oversized or malformed; only an authenticated agent's body is read up to the limit. | Every other route refuses a body over 1 MB before parsing; the large limit must not be available to anyone who can reach the server. |
| BP-A17 | **Android streams a picked file natively** (Android verification, `fix/mobile`). `useComposerUploads` no longer reads `fetch(uri).blob()` (the whole file copied into the JS heap, base64 across the bridge); `uploadFile` gets an injected `xhr` — `FileUploadRequest` (`apps/mobile/src/data/fileUpload.ts`), an `XMLHttpRequest` look-alike over expo-file-system's `File.upload` (OkHttp reads the file or `content://` URI itself; binary PUT, progress events, cancel through an `AbortSignal`). Reservation, headers, the bearer token, the server's answers and discard on cancel stay in the shared client; the body `uploadFile` passes is an empty placeholder the request never reads. No new dependency (expo-file-system was already linked). | Big files on small phones; one transfer path for web and mobile. |
| BP-A18 | **A failed chip says why in full and offers Retry only when trying again can work** (mobile; `uploadRetryable`). No Retry for answers about the file or the place — 4xx other than 408 / 409 / 429: too big, the burrow's storage full, a damaged or unshowable image, a conversation one cannot post in; Remove only. Retry for no answer (connection), 5xx, 408, 409 and 429. The error line wraps; a failed chip may take the composer's width. Chips are 44dp tall with a 44 × 44 Remove / Cancel and a ≥ 44dp Retry (hitSlop cannot reach past the chip, which clips touches); `touch-targets.test.ts` now also refuses `hitSlopFor(n)` on a control that is not n dp. | A Retry that can never succeed is a dead control; a cut-off error does not say what to do. |
| BP-A19 | **Names on the phone.** A downloaded file keeps its original name: it goes to `cache/shared/<attachment id>/<name>` (name made safe: no directories, no leading dots, 120 characters), so other apps and “Save” see “Q3 report.pdf”, not `att_…-Q3 report.pdf`. A picked photo whose name is only digits (Android's photo picker uses the media id, “19.png”) or empty is named after the moment it was picked, in the device's time: “Photo 2026-09-24 21.04.png”, then “Photo 2026-09-24 21.04 (2).png” within one pick. | People see these names in the chat and in other apps. |
| BP-A20 | **Authenticated images on Android use an array source and wait for the token.** React Native 0.86's Android `<Image>` passes `headers` to the native loader only for an array source (`[{ uri, headers }]`); a plain object loaded without the bearer token and got 401. `ChatView` requests no file before the session token is read (images and file chips show a quiet `sf2` placeholder until then). | Pictures never loaded (Android verification, major). |
| BP-A21 | **Android removes the copies it downloaded to share or open** (final security re-review, fix/final). `cache/shared/<attachment>/<name>` holds private conversation files outside the app's authorization: signing out removes the whole directory after the session has ended (capped like the other sign-out steps, a failure never blocks signing out), and every app start removes entries a day old or of unknown age (`staleSharedEntries`, `lib/sharedCache.ts`). | Another person signing in on the same phone, or anything reading the app's cache later, must not find the previous session's files. |
| BP-A22 | **Files up to 250 MB** (John, 2026-10-05: “can we up this to 250MB?”). `WHOMBAT_UPLOAD_MAX_BYTES` defaults to 250 MiB (the ceiling stays 1 GiB; rate and quota unchanged, so a 10 GiB burrow holds about 40 such files). The default is now the server's own value in `config.ts`, next to the rate and quota defaults; core's `DEFAULT_UPLOAD_MAX_BYTES` (25 MiB) is no longer read and goes when contracts next change attachments. The managed path already allows it (session uploads are 4 MiB chunks streamed to the staging file, `UPLOAD_MAX_FILE_BYTES` 10 GiB), and REST PUTs stream too; image previews stay capped at 32 MiB sources. A scratch turn's copies follow (`scratchFileBytes` 250 MiB, `scratchTotalBytes` 500 MiB) so an agent can open the file it was given. The “too big” copy takes the number from the limit. A REST upload through a Cloudflare proxy still hits Cloudflare's 100 MB request limit; managed boxes go through the relay, which has no such limit. | People attach videos, archives and data exports bigger than 25 MB. |

## Follow-ups

- The thread pane's reply box has no `+ file` yet (the server takes files on replies).
- Mobile: receiving shares from other Android apps; image downscaling before upload.
- No thumbnails are generated: clients scale images (a pure-JS resizer or an optional native one later).
- An S3-compatible `FileStore`; backups of `files/` are manual until Workstream F's backup covers them.
- Codex gets PDFs only as a note: a bounded PDF→text extraction would let it read them.
