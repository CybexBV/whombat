# Dashboards: one Summary for every server, connection and device

John, 2026-10-18 (main checkout): “I want to improve the dashboards of the servers, check the Rackoon project … I want to
have a dashboard (summary) that shows nice graphs of CPU, memory usage, etc. … We should also improve the dashboards of
the Things, for example Hetzner Cloud Whombat should show stats of the servers and Home Assistant should be improved …
Same for Unraid … Since we want this for all servers, but also for all connections, I suggest we rebuild this entirely
(maybe a template?)”. His screenshot: Home Assistant's page with a chart card stretched beside a nine-item “Worth a look”,
a large empty area under the chart. My answer with mockups (whombat-app `docs/design-handoff/dashboards/`: `server.png`,
`ha.png`, `hetzner.png`, `unraid.png`, `anatomy.png`, source `index.html`) and three steps; John: “All three steps”.

Builds on connection-pages.md (CP-01…CP-20); its CP-02 (how a service runs, not what is inside it), CP-04 (the server
builds a connection's page), CP-08 (runs on) and CP-12 (actions) stay. Contracts 0.89.0 (CT-394…CT-398), app 0.86.0,
candidate 0.97.0 (IN-285), migrations from 0111.

| Id | Decision | Why |
|---|---|---|
| DS-01 | **One Summary layout for every server, connection and device**, top to bottom: the head (name, one status badge, a few chips, the fact line, at most Ask plus one or two kind actions), the tabs with the **range picker** on their right (Summary only), a banner only while something is wrong right now, a row of **3–6 figures** each with a small line of the range or a meter, **one or two rows of chart cards** (1–3 per row), then a **main column (≈ 65 %) and a side column (≈ 35 %) that stack their own panels**, then whole-width panels. *Superseded in part by SPG-01, SPG-03 and SPG-07 (`server-pages.md`): a server's and a machine's head is the name, one badge, the verdict and Ask · Open · ⋯; its chips and fact line are Technical details.* | John asked for a template; one layout means one look and no per-kind page work. |
| DS-02 | **Same panels, two builders.** A connection's or device's Summary is built by the Whombat server (`things.page`, CP-04). A **server's Summary is built in `@whombat/client`** from the hosts data the app already reads (`hosts.getServer`, `hosts.serverMetrics`, the live `hosts:` events), as the same `ThingPagePanel`s, and drawn by the same renderer on the web and the phone. | The hosts data is already typed and live in the client (10-second updates), every hosts kind's model and words already live in `packages/client/src/hosts/*`; building it on the server would port thousands of lines and lose the live push. Both builders speak one contract, so the look is one. |
| DS-03 | **One range per page**, picked above the charts: servers 1 h · 6 h · 24 h · 7 d · 30 d · 90 d (the hosts service keeps 90 days), connections and devices 1 h · 6 h · 24 h · 7 d · 30 d (their points, DS-11). The range is in the address (`?range=7d`, default 24 h), applies to every chart and small line on the page, and the page reads again when it changes. A connection's page reads its range through `things.page?range=` (CT-397); `ThingPage.ranges` says what the picker offers. | One picker drives everything (John's “nice graphs”), shareable links, no per-chart state. Page-level instead of per-chart fetching: one request, one cache, the server already reads everything a page needs. |
| DS-04 | **Panels say where they sit** (`place` `top` · `chart` · `main` · `side` · `bottom`, `span` 1–3; CT-394). The renderer fills chart rows of three columns in order, then stacks main and side independently (`align-items: start`; nothing stretches), then the bottom. A 0.88 page without places is laid out from `width` (`thingPanelPlace`). Phones stack all panels in the order given. | Ends the pairing that stretched the chart card beside a long list (John's screenshot). |
| DS-05 | **“Worth a look” shows five and folds the rest** behind “Show N more” (open in place), on every page and both clients; nothing there means the panel says “Nothing needs a look.” and sits in the side column. | Nine repairs made the side column taller than the whole page. |
| DS-06 | **Chart cards** (CT-395): title, the figure now (“18 %” · “of 16 threads”), on the right “Avg **14.2 %**” and “Peak **63 %** Sun 03:10” over the range, the chart (area under CPU and memory, plain lines otherwise, a dashed limit line where it gets serious, bars for counts), and up to four small facts under it (User · System · I/O wait · Load; Used · Cache · Free · Swap). Hover shows the time and every series' value. Colours: CPU blue, memory violet, network in green and out orange, disk read blue and write violet, temperatures amber for the hottest then blue/green/violet, the serious colour only past a limit. | Rackoon's server Summary, which John pointed at; the figure, the average and the peak answer “is this normal?” without reading the chart. |
| DS-07 | **Figures** (CT-395): label, value, what it is out of, a line under it, and a small line of the range (`spark`) or a meter (`meter`, for counts out of a total: guests running, integrations loading, a disk's space). Amber or red only near or past a limit. *Superseded in part by SPG-02 (`server-pages.md`): a server's figures are at most four tiles in words.* | The top row is read first; the small line shows the trend at a glance. |
| DS-08 | **Bar lists** (`bars`, CT-396) for anything with a size: storages and volumes (with “Full in about 5 months” when the last 30 days point there within a year), array disks, pools, a Home Assistant disk. **Tables** may carry a small bar (CPU), a small line (the guest's day) and a button (Console, Open) per row. | Storage is the most common problem; a bar and a date beat a percentage. |
| DS-09 | **A server's Summary** (every kind: Linux, Proxmox, Unraid, Incus, QEMU/KVM, Docker hosts): figures CPU · Memory · Hottest (or Network without sensors) · Network · Guests (or containers); chart cards CPU · Memory · Temperatures (or Network) in the first row, Network (span 2) · Disk I/O in the second; main: busiest guests or containers (5, with CPU bar, memory, the day's line, Console/Open), the kind's own (Unraid: Array as a bar list; Proxmox: —); side: Worth a look (alerts and hints), Storage (bars) or Pools, Backups (Proxmox: last night, next run), Virtual machines (Unraid/QEMU), cluster (Proxmox). Everything the old Summary showed stays reachable: actions (start an array, update a container, acknowledge) live in their tabs and the Summary links there. *Superseded in part by SPG-02…SPG-05 and SPG-08 (`server-pages.md`): tiles in words, temporary machines left out, storage, pools, the platform's card and the cluster in Technical details, no button column.* | The mock John approved (`server.png`, `unraid.png`); the Summary shows, the tabs do. |
| DS-10 | **Connections get their machine** wherever Whombat knows what they run on (CP-08), not only Home Assistant: figures CPU · Memory · Disk of the machine and its CPU and memory charts, before the kind's own. Home Assistant (`ha.png`): figures CPU · Memory · Disk · Database · Integrations; charts CPU · Memory · Disk space (with its forecast) · Errors in the log per hour (bars: the noisiest source and everything else, span 2) · Database size; main: Integrations not loading, Backups; side: Worth a look. | “Same for all connections”: a UniFi controller in a container or Grafana on a VM gets its machine without code per kind. |
| DS-11 | **Points kept 30 days** (`connection_points`): 5-minute points for 48 hours, then one per hour (the average; kept until 30 days). New series: Home Assistant `log_err` (errors since restart, all sources) and `log_err_top` (the noisiest source's) with that source's name kept with the glance, `db_mb` (recorder database), `disk_pct` and `disk_gb` (the machine's disk it runs on); UniFi `gw_cpu`, `gw_mem`, `clients`; devices their readings as before. | Trends need more than a day; an hour is detail enough after two days and keeps the table small. |
| DS-12 | *Superseded by service-slots.md SLT-44…SLT-46.* **Hetzner Cloud** (`hetzner.png`): figures Servers running · CPU (average of running servers, small line) · Traffic this month (out of included, meter) · Cost a month; chart cards CPU, Network, Disk I/O from **Hetzner's metrics API** for the page's range (one server: its own lines; several: one line per server, up to six); main: Servers table (state, type with cores, memory and disk, location, address, CPU now with its small line, Open when the server is also a Whombat server, matched by address); a note when Hetzner can't show memory and disk space (“Add <name> as a server to see them here.” with Add a server); side: Worth a look (not running, no backups, delete protection off, traffic over 80 % of what is included). Reads cached 60 s per server and range. | John: “Hetzner Cloud Whombat should show stats of the servers”; Hetzner has CPU, disk and network but not memory or disk space, the agent has those. |
| DS-13 | *Superseded by service-slots.md SLT-40…SLT-43.* **UniFi**: figures Devices online · Clients (small line) · Internet now (down/up) · Gateway CPU; charts Internet down and up (span 2), Gateway CPU and memory; main: Devices table; side: Worth a look. No client lists (CP-09). | Same template, network equipment only. |
| DS-14 | **Every other connection** (no kind of its own): figures Status · Response time (small line) · Last used · Problems, plus its machine (DS-10); chart Response time; main: Whombat did here, What Whombat may do; side: Worth a look; bottom: Show more here. **Devices**: figures and a chart card for up to three numeric readings, a table of all readings, Worth a look. A Proxmox or Unraid connection that is part of a server keeps its one sentence (CP-10). | Every connection gets a real Summary today. |
| DS-15 | **Words**: “Summary” for the first tab everywhere (key stays `overview` for old links); averages and peaks with one decimal under 10 and none above (“2.4 %”, “63 %”); times in the person's time zone (“Sun 03:10”, “Now”); sizes in GB/TB with one decimal under 10; “Full in about 5 months”, “Full about 18 Dec” (within 60 days), nothing when it isn't filling up. | Plain, short, the same on every page (concise-replies rule for visible words). |
| DS-16 | **Live**: a server's Summary follows the live hosts events (at most once per 10 s) and reads its metrics again every 60 s; a connection's page reads again every `refreshS` (60 s default, the server's 30 s cache under it). The range picker shows “Live · every 10 s” for servers only. *Superseded in part by SPG-03 (`server-pages.md`): “Live, every 10 s” is a Technical detail, not words in the tab row.* | What Rackoon did; no extra polling for connections. |
| DS-17 | **Older runtimes** (no `things.dashboards`): a connection's page is laid out from `width` (DS-04) with one range; a server's Summary is built in the client either way (DS-02), so it needs nothing from the runtime. The old server Summary components (`SummaryTab`, which QEMU/KVM and Incus servers used too, `UnraidSummary`, the phone's server dashboard) and the old pairing layout are **removed**; Unraid's notifications and updates cards move to its System tab. (`LibvirtSummary` is a VM's own page and stays.) | DS-02 makes the server Summary runtime-independent, so the old pages can go now. |
| DS-18 | **Tokens**: a fourth chart colour (violet) joins `chartColors` (light and dark) for memory and second series; no hex in components. | John's current memory line is violet; colours only through tokens. |
| DS-19 | **Built in four streams** from integration branches `dash` after contracts 0.89.0: server S (`~/Code/.wt/whombat-dash-server`), client K (`~/Code/.wt/app-dash-client`, owns `packages/client` and `packages/tokens`), web W (`~/Code/.wt/app-dash-web`, `apps/web`), phone M (`~/Code/.wt/app-dash-mobile`, `apps/mobile`). DEV fast: one quick check per repo. | Parallel with clear file ownership. |
