# Share Home reads within one request — 2026-10-20

Runtime-only refactoring of `apps/server/src/home/overview.ts`; no contract or UI changes.

| # | Decision | Reason |
|---|---|---|
| RHR-01 | Each `homeOverview` creates a private set of lazy promises for visible catalog connections, the viewer's active marks at the overview's existing `now`, and their active assistant's name. Needs you, Things and Watch share these promises alongside the already-shared viewer chats. | Connections previously executed three identical reads, marks two, and the assistant's name two when a connection needed reconnecting. One overview now executes each once. There is no cache across requests, viewers or service containers, and no transaction or changed permission predicate. |
| RHR-02 | Keep the standalone `needsYou`, `things`, `watchList` and `workingTask` signatures. Each standalone section starts fresh, and reads only its existing dependencies. Share the assistant-name query itself, without deriving its name from viewer chats. | Needs you still reads no assistant name when it has no reconnect item; Things reads neither names nor marks. `assistantNameOf` checks kind and active status in its own query; the personal-agent lookup for chats has different predicates. Those rules stay separate. |
| RHR-03 | Required-read rejections still reject the overview; registry sources still isolate failures and the parent-server map retains its existing fallback. Keep section filtering, ordering, clipping and limits in place. | Sharing reads must not turn database failures into empty sections or change optional-source behavior. No writes, cancellation, events, signing, leases or fencing are involved. |
| RHR-04 | Add `overview-reads.int.test.ts` using the existing throwaway database harness with a small people-only seed and no HTTP listener. Assert complete Home and Watch output, standalone parity, owner/member/account/burrow scopes, private approvals, mark expiry, fresh subsequent requests and required/optional failure boundaries. Count executed SQL through Drizzle's logger. | The regression depends on real SQL visibility predicates, joins and timestamps; mocked DB chains would miss these. SQL counts verify eliminated database reads rather than the shape or number of calls to internal helpers (TS-04). |
