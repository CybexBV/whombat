# Add a server by signing in once — the Whombat server (stream S, 2026-10-18)

Stream S of `docs/implementation/server-signin/assignment.md` §2.4, under `docs/decisions/server-signin.md` (SI-01…SI-13),
contracts 0.85.0 (CT-373…CT-379) and hosts HS-93… (the pre-approved enrollments, `GET /agent-install.sh`,
`install.sh --control` and its result lines). Code: `apps/server/src/hosts/install.ts`, `install-words.ts`, the routes in
`routes.ts`, `server_add` in `tools.ts`, and the SSH sign-in next to the Vault's in `apps/server/src/vault/ssh-signin.ts`.

| # | Decision | Why |
|---|---|---|
| SI-S01 | **The install job lives in the server's memory** (`installsFor(services)`, like console tickets, ONE-DH19): `hosts.startInstall` checks, starts the job and answers 202 `connecting`; the job runs outside the request's command scope (`outsideCommandScope`), so the secret op's receipt keeps nothing of it (CT-44) and a cancel can't stop it halfway. A finished job stays readable 30 minutes; a restart forgets running ones (the person tries again). | Nothing in a job is worth a table: it holds a password while it runs and a result for the dialog afterwards. |
| SI-S02 | **Signing in is `vault/ssh-signin.ts`**: the Vault's destination check, dialling and SHA-1-free algorithms (`ssh.ts`, which now exports `clientKey` and `dial`), with ssh2's `password` then `keyboard-interactive` (every prompt answered with the password), or the person's Vault key (custody-opened by the route, as `ssh-check.ts` does). Host keys are `accept-new`: without a trusted key for that host and port in any of the person's Vault SSH servers the key is taken and reported (`hostKeyNew: true`); with one, the shown key must be one of them, else the verifier refuses before anything — not even the user name's sign-in — is sent (`host_key_changed`, the shown key reported). 30 s for connect and sign-in. | SI-02, SI-04; the same rules as every other SSH connection Whombat makes. |
| SI-S03 | **The address is checked twice**: in the route with `sshDestination(…, 'save')` (refused 403 `not_allowed` with the rule's reason on `fields.address`, so the form shows it on the field and no job starts), and again when the job dials (a name that resolves elsewhere by then fails the job `not_allowed`). The `save` wording is used both times: `call`'s “isn’t allowed any more” is wrong for a first contact. | SI-05; the dialog can't act on a job id for an address it may never reach. |
| SI-S04 | **Root, in this order**: `id -u && uname -s` (not Linux → `unsupported` before any token exists); uid 0 → as is; `sudo -n true` → passwordless sudo; exit 127 or “not in the sudoers” → `sudo_refused`; no password (a Vault key alone) → `sudo_password_needed`; `sudo -k -S -p '' true` with the password on stdin → `sudo -S`. When sudo doesn't take the sign-in's own password the user may not use it (`sudo_refused`, rootpw/targetpw/not listed); a wrong “Password for sudo” next to a Vault key says “Signed in, but sudo on … didn’t take that password.” | SI-02; each outcome is a step the person can take. |
| SI-S05 | **The installer runs from a `mktemp` file with everything secret on stdin**: `mktemp`, `cat > <file>` (the hub's `GET /agent-install.sh`, streamed), then `sh <file> --token - --control <level>` as root, `sudo -n sh …`, or `sudo -k -S -p '' sh …` with stdin `password\ntoken\n` (`-k`: sudo always reads its own line, so the password can never be taken for the token nor the token for the password), 150 s; `rm -f <file>` after, also on failure. The temp path is checked (`/[A-Za-z0-9._/-]+`) before it goes on a command line; the token and password never do. | SI-03; the same installer as the command (SI-02). |
| SI-S06 | **Error words are the contract's** (`hostInstallErrorText`, SI-11), with the address as typed; the server words only what it knows better: `not_allowed` (the rule's own reason), a wrong sudo password, a connection that broke after sign-in, a hub that isn't answering (`HOSTS_TEXT.down`), and `waiting` (“Whombat’s agent is on …, but it waits to be let in. You find it under Servers.”). The installer's stable `install.sh: …` words map to codes (`curl or wget is required`, `unsupported architecture/init system`, `cannot reach`, exit 3 / `other-whombat`, a timeout); anything else is `failed`. | One set of words on the web, the phone and the server. |
| SI-S07 | **“More detail”** (`detail`, failures of the installer only) is its last 40 non-empty lines, stdout then stderr, colours and control characters out, the password, the token and anything after `--token` replaced with `•••`, at most 4 KiB from the end. Output that held the signing Vault key (`holdsSshKey`) gives no detail at all. | SI-11: the person sees what the installer said, never a secret. |
| SI-S08 | **Limits**: one running job per person and server (host and port, case-insensitive), two per person, four per box — `rate_limited` with “Whombat is adding … already. Wait for it to finish.”, “You’re adding two servers already. …”, “Whombat is adding four servers already. Try again in a minute.” | Each job holds an SSH connection and a token; nobody adds more than a couple at once. |
| SI-S09 | **`hosts.getInstall` answers only the person who started the job** (owners only, `manage`); anyone else's job id is a 404, like another person's Vault entry. | The job is the record of their sign-in; another owner has nothing to do with it. |
| SI-S10 | **SI-09 never fails an install**: the key line goes on stdin to one `sh -c` (`mkdir -p ~/.ssh`, 700, `authorized_keys` 600, appended once with a newline before it if the file lacks one), then — as the person through the commit pipeline — a new ed25519 entry “Servers” (made only once the server took its key), the server added to the entry (the entry's server with the same host, port and user is reused; a taken name gets `-2`), and the key it showed trusted. Anything failing leaves `keptKey: false` (the dialog then says “It showed key …”, not “remembers”). The route refuses up front what the Vault would refuse later: not the person's SSH key, 20 servers on the key, the entries limit, user names over 32 characters. | The agent is installed by then; a lasting key is a convenience on top. |
| SI-S11 | **Tests use an in-process ssh2 server** (`hosts/testing/fake-install-ssh.ts`) reached through the Vault's test network seam, faking `id`, `sudo`, `mktemp`, `cat`, the installer (the test answers its lines, usually by claiming the token at the fake hosts service) and the SI-09 command; the fake hosts service pre-approves (`claim`, `-2` names, the level's switches, `enrollment.approved`), serves the installer and turns tokens away. | The job's every branch runs without a real server; the real run covers the rest. |
| SI-S12 | **`server_add` posts as the agent through `hosts.ask_add_server`**: a link-only guide card (topic `add_server`, state `done` like every card with links only), title “Add 10.100.0.40 as a server”, body “Sign in to it once and Whombat installs its agent.”, one primary “Sign in…” to `/things/servers?add=1&address=…` with `user`, `control`, `name` only when given; no text, waking nobody; the model gets `{asked: true}`. The address must read as one (`parseHostInstallAddress`), the level be one of the three. Not an owner (the agent's person, else the turn's): “Only owners add servers. Ask Mara.” (owners by short name, “A or B”). Words for an approval if an owner sets it to ask: “add 10.100.0.40 as a server” / “Here’s the card to add 10.100.0.40 as a server.” | SI-10; the card is the whole answer, so nothing else goes in the chat. |
| SI-S13 | **A pre-approved token no agent took is turned away at once** (`POST /enrollments/{id}/reject`, which the hub allows for issued ones): after `kept`, `other-whombat` or any failure once the token exists. `added` and `waiting` keep theirs. | The token was only ever on that server's stdin, but nothing should stay able to add a server for an hour without a reason (seen in the real run: every `kept` left one). |
| SI-S14 | **The change is signed before the first-report wait**: `hosts.change` as the owner, `op: install`, “Added pve-03 with full control” / “Added pve-03 to watch only” / “Updated pve-03’s agent and set restart and consoles”, ids `installId` and `enrollmentId`, Done recently's title the same; no address, password or token. Then `waiting` until the fleet's `last_seen` for that server is at or after the installer's start (read again on its events, else every 2 s), 60 s; late → `timed_out` with the contract's “It’s installed, but …” and the server id kept. `serverName` is then the host name when it is the id with its own capitals. | The server is added either way; a restart during the wait must not lose the record. |
| SI-S15 | **Every enrollment Whombat makes is pre-approved** (`hosts.createEnrollment` sends `{approve: true, control: body.control ?? 'full', name?}`), `HostEnrollment` maps `control` and `preApproved` (the hub's `approve`), `HostPendingEnrollment` maps `control` and `name` (null for older ones); `approveEnrollment` is unchanged (the hub applies a stored level). `enrollment.approved` drops the fleet and agents caches and wakes a job waiting for that server, with no frame of its own (the server events follow). `hosts.install` moved to `IMPLEMENTED_FEATURES`. | SI-07; the command tab and Sign in once add servers the same way. |
| SI-S16 | **A server reached over the tailnet calls home on the box's tailnet address**: when the SSH connection's own end on the box is in Tailscale's ranges (100.64.0.0/10, `fd7a:115c:a1e0::/48`), the job asks for `GET /agent-install.sh?hub=wss://<that address>:<the agents' port>`, so the download and the agent's hub address are the tailnet's; “can't reach this Whombat at …” names it. Any other way in keeps the hub's own agents' address. Preferring the tailnet for servers that reach both is not decided here. | A customer's servers at other sites were reachable only over the tailnet: SSH worked, the installer then tried the box's LAN address and never finished. The connection Whombat just made is the best evidence of a way back. |
