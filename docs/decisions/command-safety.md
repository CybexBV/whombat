# Command safety (workstream `command-safety`)

What a session command's receipt says after a lost answer, on the runtime side of contracts CT-194/CT-195 (retry safety
per operation, `outcome.redacted`). Decisions are `CS-nn`; they refine `managed-runtime.md` MR-06 (durable commands) and
MR-27 (secret ops) and never override them.

| # | Decision | Reason |
|---|---|---|
| CS-01 | **External effects pin their command** (`commit/scope.ts` `externalEffect`). Every effect outside the database that a command may run before its first commit-pipeline transaction goes through `externalEffect(label, fn, {idempotent?, refused?})`: a repository origin on disk (`git.origin`), the runner's sign-in steps (`runner.<method>`), the backup service's calls. Before the first commit, a non-idempotent one first checks the request (a request already cancelled or past its deadline never starts it, `CommandStopped`), then **pins** the command: from then on neither a cancel nor the deadline rolls back the commit that records the effect. Idempotent ones (sign-in cancels, a console resize, a usage probe) are only observed. The effect's end is reported: `acted` unless it failed with an error its `refused` predicate recognizes as proof it didn't act (GitHub 4xx or `merged: false`, not connected; a runner request never taken; `createLocalOrigin`'s own failures, which leave nothing), or the caller reverted it (`undoneEffect`). Code that wraps errors lets `CommandStopped` through. | MA-09 says `accepted` means committed and nothing claims exactly-once external effects. But a session that closed, or a deadline, rolled the commit back *after* the handler had merged a PR or made an origin, so the database and the receipt said nothing happened when it had. |
| CS-02 | **An effect before the commit is remembered by the receipt.** Before a pinning effect runs, the receipt row (still `received`) gets `outcome = {kind: 'effect', label, at}`, written on its own (the command's transaction may still roll back). A process that dies after that point leaves a receipt that `status` answers `rejected` + `error{unknown_outcome}` and that a same-id retry replays as `error{unknown_outcome}` (the row is finished that way, `retryable: false`): never `not_found`/`not_executed`, never run again. A command that acted and then failed before any commit ends the same way (its own `unknown_outcome` message kept, others replaced by “This may have happened…”). An acted command that returns a result without committing (no pipeline write) is accepted as it finishes, as before. | Without the mark a crash between the effect and the commit read as `not_found`, and CT-194's resend rule then allowed the very resend that acts twice. |
| CS-03 | **`repos.create` keeps what something needs.** The origin is made as the `git.origin` effect (pinned: a dropped session no longer undoes a made origin, the record commits). When the record is refused, the origin is removed only if nothing needs it: no `repos` row with that `origin_path` and no `repos.create` approval still `pending` or `approved` whose command holds the path. A `202` (asked a person) never removes it: the approval executes the command with that path later. An origin found at the path that nothing needs, and that is exactly what a create leaves (one ref, `main`, at the single `Create <name>` commit), was left by a process that died before recording it: the next request for that name removes it and makes it again. Any other origin (history, other refs, unreadable) is kept and the name refused: the database may have lost track of real work (a restore from an older backup, repairs by hand). Requests for the same path in this process are refused while one runs (one server process, MR-06). | The old cleanup removed the origin a pending approval pointed to, and a crash left an orphan that blocked the name for ever (“already kept on this Whombat”). People never get `ask` for `burrow.manage` today, so the `202` path is latent, but the cleanup must not depend on that. |
| CS-04 | **Receipts across enrollment.** A request's receipt key is `(principal, op, id)` with principal = the account, or `peer:<peerId>` before enrollment. An enrolled session's receipt principals are `[account, peer:<its own peerId>]`: `status{id}` answers the newest receipt of the id among both; a request uses the `peer:` receipt when one exists for the same op and id (in flight here or stored), else the account's. Only the session's own Noise peer (`peerId` is the authenticated static key's) — never another device of the account. | After `enroll.claim`, `recovery.enroll`, an invite or a re-enrollment was accepted, `status` looked under the new account and answered `not_found`, and a same-id retry ran the enrollment again (`claim_used`). |
| CS-04b | **Runner bridge calls without an answer** (`managed/providers/bridge.ts`). The runner runs each request once and never dedupes (every call has a fresh id). The bridge marks a request `taken` when a poll carries it out; a poll whose response didn't go out in full gives its requests back, and one the runner hung up on takes none. No answer (timeout, shutdown, a result that doesn't parse) means: not taken → `unavailable` (“nothing was done”, retryable, receipt `not_executed`); taken, a step that acts → `unknown_outcome` (final, receipt `rejected` + `unknown_outcome`); taken, a read (`list`, `githubToken`) → `unavailable`. The runner's own refusal (`ok: false`) stays `conflict` with its reason. The error is `RunnerBridgeError`, a 409 `conflict` with `details.code: provider.signin_unavailable` outside sessions (usage probes keep reading it as “runner away”). | A timeout answered `conflict` (a final “didn't happen”) though the runner may have signed someone out; a closed bridge answered `internal`, whose receipt read `not_found`. |
| CS-05 | **Failing after the commit while reading back completes redacted.** After a command's first commit, an `internal` or `not_found` error — with no external effect run after the commit — means reading its result back failed: the receipt is `completed` with `REDACTED_COMPLETION` (`{kind: result, resultKind: ok, redacted: true}`), the live answer and a retry are `outcome{state: completed, redacted: true}`, `status` the same. Any other error after the commit (a later step's refusal: `plans.reportBack`'s `bad_request`, `plans.delegate`'s `conflict`, `backup.runNow`'s `backup_busy`), or any error after an external effect that ran after the commit (a backup service call, a runner step), stays `rejected` with its error. A secret op's retry keeps answering `error{unknown_outcome}` (MR-27). | Its writes landed; `rejected` told the client it hadn't. `redacted` is “done, the answer isn't kept” (CT-195). The code rule is a heuristic: about 88 of the ~107 REST handlers that commit read their result back and throw `not_found` when it's gone; the deliberate post-commit refusals use other codes. |
| CS-06 | Superseded by RRB-03 in `refactor-runtime-boundaries.md`: accepted commands with pending external continuations remain uncertain after a crash; other accepted commands complete redacted. | A committed intent is not evidence that its external action finished. |
| CS-07 | **The shared Google token refresh belongs to no caller** (`connectors/tokens.ts`): it runs in `outsideCommandScope` and commits on its own. | It ran in the first caller's command scope: cancelling `connections.check` rolled back the tokens Google had issued (a rotated refresh token lost) and failed the agent tool calls that joined the refresh. |
| CS-08 | **The runtime checks `OPERATION_SAFETY` against what commands do** (`managed/operation-safety.int.test.ts`). `observeExternalEffects` reports every `externalEffect` with its session op and whether it ran before the commit. The suite drives the ops that act (a GitHub merge, a repository origin, the runner's sign-in steps through the real bridge and executor with the fake CLIs, organization removal) and ordinary ones, then asserts: every op seen acting non-idempotently before its commit is `retry: never` or destructive in the vendored contracts' table; the expected effects are still observed (removing a wrapper fails the test); ordinary commands act before their commit not at all. New effect chokepoints go through `externalEffect`; a new op that reaches one before its commit fails this suite unless the contract classifies it `never`/destructive. | A dynamic check at the chokepoints catches a handler change that moves an effect before its commit, which a static table can't. It covers what goes through `externalEffect`: Google revocation/exchange (`connectors/store.ts`, `connect.ts`) and manager calls (`clients.*`, `licence.refresh`) aren't wrapped yet (outside this workstream's files) and stay covered by the contract's hand classification only. |
| CS-09 | **SQLSTATE through drizzle's wrapper.** Where the dispatcher inspects a Postgres error code it reads `sqlState(err)`, which walks the `cause` chain (drizzle's `DrizzleQueryError` wraps the driver's error for statements inside a transaction), as `isReadOnlyViolation` does for REST. Today that is the read-only refusal (`25006` → `unavailable`); the receipts module inspects no codes. | A read-only refusal raised inside a transaction answered `internal`. |
| CS-10 | **Every outside effect, every int test** (extends CS-01, CS-08). Also wrapped: Google revocation (`connectors/store.ts`, pins `connections.remove` and a replaced account's revoke) and code exchange (`connect.ts`, after `finishGoogle`'s state commit); the manager's client install (idempotent) and removal (pins; a 4xx answer or an unreachable socket proves it didn't act) and licence renewal (idempotent); mail sends (`mail/mailer.ts`, both mailers); GitHub PR opening and workflow dispatch. `test/effects-setup.ts`, the int config's setup file, observes every effect in every server int test and fails the file when an op acts non-idempotently before its commit while `OPERATION_SAFETY` lets a client resend it (labels `test.*` are a test's stand-ins). Not wrapped: the self-hosted local sign-in executor (no sessions there), agents' browser and vault probes (not session commands, or read-only). No op the suites drive contradicts contracts 0.29.1. | A check at the chokepoints, run by the whole suite, catches a handler change that moves an effect ahead of its commit wherever a test drives the op. |
| CS-11 | **The automations engine steps down when its lock's session ends** (`automations/engine.ts`). The advisory lock lives on a reserved session; the active engine checks every `lockCheckMs` (500 ms) that the session still holds it (`pg_locks` for its own `pg_backend_pid()`; a dead reservation's query rejects, pg-guard PGG-03). When it doesn't: not active at once (no more ticks, a pass under way starts nothing more), the session given back (a dead one's `release()` does nothing), and it retries like a passive engine. A new holder waits two check intervals, then checks the lock again before it acts, so one whose session just ended has stepped down by then (same `lockCheckMs` on every process). Runs stay fenced by their leases (BP-C10) regardless. | A failover or restart of Postgres ended the session and freed the lock while the engine stayed active: two engines could both run (pg-guard PGG-05). |
| CS-12 | **Reading back is explicit** (refines CS-05). A failure counts as a read-back only while the command reads its result back: `Pipeline.commit` marks the scope when a command commits `ok` (`resultDecided`) and clears the mark when a command's transaction begins (`beforeWrite`); any external effect clears it too. A session-native handler whose last write isn't a pipeline command says so with `readingBack()` (`trust.ts` `enrolledOutput`, the enrollments' read-back; a claim's bookkeeping writes before it keep their own error). `packs.import` spends its staged archive once the import committed (`importArchive`'s `onImported`), so a failed read-back after it no longer gives the archive back for a second import. An account-level commit (`transactAccount`) sets nothing: it may be a preliminary take, not the result. The audit found no handler throwing `internal`/`not_found` on purpose after its result was decided; what the implicit rule misread were `packs.import` (the staged archive taken, then a missing file or a failed store before the import) and two race-only cases (`me.updateProfile`'s later burrows, `guides.act`'s card looked up again). Plain `transactAccount` REST handlers lose the redacted answer on a failed read-back (they answer `rejected` + `internal` as before CS-05) until they call `readingBack()`. | “Committed, then `internal`/`not_found`” also matched a failure after a preliminary commit, where nothing the command is for had happened. |
| CS-13 | **Failures and a second process can't break a receipt** (review of `hp/runtime-safety`). An effect is recorded as started only after its receipt mark was written: a mark that fails leaves nothing started (the effect never runs; the command answers its error, `not_executed`). `#begin` never resets a `received` receipt whose `outcome` is an effect mark (another process marked it meanwhile). `markAccepted` moves only `received`/`accepted` rows and otherwise throws `ReceiptSettled` (the command's transaction rolls back); `#finish` writes only over `received`/`accepted`. So a process that took another's command for dead and settled it `unknown_outcome` is never contradicted by the first one's commit or result. What still assumes one process (MR-06): a `received` receipt without a mark is taken for dead by a second process and run again. Also: `keyFor` looks for a pre-enrollment `peer:` receipt only for ops the enrollment channel allows (no extra SELECT for other commands). The console's keystrokes (`signins.consoleWrite`, `runner.consoleInput`) pin their command and write the effect mark: one more UPDATE on the receipt row per request (insert, mark, finish), kept so a crash mid-keystroke reads unknown rather than `not_found`; the relay's `seq` already dedupes a resend of keystrokes that arrived. | Found in review: a database blip turned “never ran” into a final unknown, and two processes could both run an effect. |
| CS-14 | **A console start that was cancelled or went unanswered isn't a failed console** (`managed/providers/consoles.ts`). The relay rethrows `CommandStopped` (the console ends `cancelled`, nothing was started) and `RunnerBridgeError` `unknown_outcome` (the console stays: the runner may be running it; its output still arrives and its TTL ends it) instead of answering `{ok: false}`. The relay's other catches only keep the write chain alive or stop consoles; the providers service's catches are best-effort cleanup (a demoted owner's key removed) and the usage probe's own result mapping. | A cancelled request was stored as completed with a failed console; an unanswered start as a completed failure while it may run. |

## Protocol limits (no wire change made)

- `status` has no receipt state for “may have happened”. The runtime answers `rejected` with `error.code: unknown_outcome`
  (CS-02, CS-04b); a same-id retry gets `error{unknown_outcome}`, which whombat-app already reads as unknown
  (`OutcomeRedactedError(null)`). A client reading `status` sees state `rejected` and should treat `unknown_outcome` in
  `outcome.error` as unknown (a person checks), not as a refusal. The contracts should document that (no wire change: the
  code exists; `redacted` stays “never with `rejected`”).
- `unknown_outcome` is documented as the secret-op retry code (CT-44); the runtime now also uses it for “an effect may
  have happened and nothing recorded it”.
