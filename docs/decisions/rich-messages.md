# Workstream: rich messages (formatted text, quick replies, digest card)

Asked for by the maintainer on 2026-09-24 after an assistant's inbox triage showed up as raw Markdown
(`**Worth a look**`, backticks, `- ` bullets) in one long paragraph. Not in the mocks; everything here
follows the nearest mocked pattern (B-05).

## Decisions

| # | Decision | Reason |
|---|---|---|
| RM-01 | **Light Markdown, parsed once in core.** `parseMessage()` (`@whombat/core/text/markdown.ts`, pure, no dependency) turns message text into a small block/inline tree that web (`features/messaging/RichText.tsx`) and mobile (`ui/rich.tsx`) render the same way. Supported: paragraphs, `#` headings, `-`/`*`/`+`/`1.` lists (nested by indentation), `>` quotes, fenced code, `---` rules; `**bold**`, `*em*`/`_em_`, `~~strike~~`, `` `code` ``, `[text](https://…)`, bare `https://…` and `@Name`. No HTML, images or tables. Chat rules, not CommonMark: a single newline is a line break, a list may start right under a line of text, an unindented line after a list ends it, `_` only emphasises at word edges (snake_case stays text). Links are `http(s):`/`mailto:` only and open in a new tab. | Models write Markdown whatever the prompt says; rendering it is reliable, fighting it is not. One parser keeps web and mobile identical and is unit-tested. |
| RM-02 | **Everyone's messages are formatted**, people's and agents'. Straight quotes in text become curly (’ “ ”), never inside code or links (the product's copy rule). Headings render as one bold line (a chat message is not a document); `**lead-ins**` are ink/600 against the ink2 body. No extra text measure: the mock's 880px message column already bounds lines (~760px of text), and a cap would re-wrap mocked messages. A one-line message is still one paragraph, so mocked rows render as before. | Maintainer's call (“yes” to formatting for people too). The mocks win on layout. |
| RM-03 | **Plain text where formatting can't show**: notifications (inbox rows and push) and the search index store `plainMessageText()` (“**Heads up** `CI` failed” → “Heads up CI failed”, list items as “• …”). The message itself keeps its Markdown. | Inbox, push and snippets are plain strings; raw `**` there is noise. |
| RM-04 | The persona drops “no headings or bullet lists in chat” and gains a **Formatting** section: what renders, lists only for three or more parallel items, ids and commands in `code`, when to use quick replies and the digest card. Messages the agent reads back show a digest as `[digest card: …]` and its quick replies as `[quick replies: “…”]`. | The agent should write for the renderer, and see what it offered last turn. |
| RM-05 | **Quick replies.** `Message.suggestions` (≤ 3, ≤ 80 chars each; column `messages.suggestions`, migration 0014, idempotent) set by agents through `suggestions` on `post_message`, `reply_in_thread` and `post_card`. A person's are dropped by the server. They show as chips (the DM empty state's suggestion pills; 36dp + hitSlop on mobile) **only under the newest message of a list** (main list or thread) when an agent wrote it, it has no thread replies and the viewer isn't its author (`replySuggestions()`). A tap sends at once, without touching the draft: in the agent's own DM the words as they are, elsewhere `@Name words` so the agent is woken (`suggestionMessage()`). Anything said after the message retires the chips, so they never pile up in history. The runner's fallback reply (an agent that posts nothing) has none; the persona tells agents to post themselves when they offer choices. | Answering “archive the promos or dig into CI?” should be one tap. Retiring them keeps the history honest: old chips would answer questions that have moved on. |
| RM-06 | Quick replies are plain `Message` data, not a card, so a message can have a card **and** quick replies (a digest ending with “Want me to archive the noise?”). | They are about the conversation's next turn, not the card's content. |
| RM-07 | Migration 0014 is `ADD COLUMN IF NOT EXISTS`. | Other workstreams in flight also number their migrations 0014+; whichever order they merge in, re-running this one is harmless. |
| RM-08 | **Digest card** (`kind: 'digest'`, postable): `title` + `summary` → header `INBOX · 7 UNREAD` (`formatDigestLabel`), 1–8 `sections` (`label`, `collapsed`), each with items `{time, title, source, note, url}` (only `title` required). Web: the research card's frame and rhythm, mono time column, the whole row a link when it has a `url` (new tab, external icon, “(opens in a new tab)” for screen readers); a collapsed section folds to one line of titles with “Show N”. Mobile: the same card whole (not a summary), rows open the URL in the browser. The thread pane's title uses the digest's `title` as topic; the search index includes its items. | A triage is structured data; a card makes it scannable and every item one tap from the source. Generic enough for calendars, files and notifications, not only mail. |
| RM-09 | **Mail links.** `mail_search` / `mail_read` results carry `webUrl`: Gmail's `https://mail.google.com/mail/?authuser=<connected email>#all/<threadId>`, so a digest item opens the conversation in the right Google account. Calendar events and Drive files already had `webUrl`. | The agent can't link what it doesn't know; `authuser` picks the right account when several are signed in. |
| RM-10 | **Images (2026-09-27, supersedes “no images” in RM-01; details in `message-polish.md` MPO-01).** `![alt](src)` is an image when `src` is `https://…`, `http://…` or a `data:` PNG/JPEG/GIF/WebP/SVG (`isSafeImageSrc`); an SVG document an agent writes bare or in a ```svg/```xml/```html/``` fence is a `svg` code block that clients show as an image (`svgImageSrc`), with its code at hand. Images render only through `<img>` / an image view, never as DOM; http(s) images are subject to the client's CSP. Plain text shows an image as its alt text or `[image]`. Still no HTML or tables. | The maintainer asked for it: an agent's SVG showed as code. |

## Verification

- Unit: `markdown.test.ts` (parser, including the screenshot's triage), `message.test.ts` (quick-reply rules),
  web `components.test.tsx` (formatted row, chips) and `cards.test.tsx` (digest card), mobile `data.test.ts`
  (digest passes through), persona snapshots.
- Server: `mcp.int.test.ts` (quick replies on posts / thread replies / cards, a person's dropped, more than
  three refused, digest stored with defaults, plain-text notification), `tools-mail.int.test.ts` (Gmail link).
- Visual: the mocked message rows are unchanged (one-paragraph messages); the new pieces were checked in the
  running app in light and dark.
