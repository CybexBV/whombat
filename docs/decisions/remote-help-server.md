# Remote help in the runtime (2026-10-21)

Server side of remote help (`docs/decisions/remote-help.md` RH-01…RH-13; build brief
`docs/implementation/remote-help/assignment.md` §3 S). Code: `apps/server/src/managed/remote-help*.ts`,
`fake-support.ts`, `desk/remote-help.ts`, the step-up in `managed/passkeys.ts`, migration 0134.

| # | Decision | Why |
|---|---|---|
| RH-S01 | **Built against a stand-in, swapped at contracts 0.120.0.** The runtime was built against one local module with the brief's §2 names, swapped for `@whombat/core`, `@whombat/protocol/session` and `@whombat/control-contracts/local` once 0.120.0 was released (vendored on 0.119.0's Chat clearing). The release differed from the brief in: the socket's grant and events carry `duration` (the enum) instead of seconds, every socket body and answer has `v: 1`, the desk's Stop is `/v1/desk/remote-help/stop` with `{v}`, a visit's record may name its `visitId`, the feature is `remote_help`. | Everything but the session ops could be built and tested before the contracts existed, and the swap stayed mechanical. |
| RH-S02 | **The support service is the authority; the runtime is a client** (`remote-help-client.ts`, `WHOMBAT_SUPPORT_SOCKET`, `/run/whombat-support/api.sock`). Calls answer within 3 s, the long poll within its wait + 3 s, JSON answers within `SUPPORT_ANSWER_MAX_BYTES`, a state `supportStateValid` refuses is not the contract, a transcript's headers within 5 s and then 30 s between chunks. Only a refusal's status and code are kept. Refusals: `remote_help_unavailable` and `forever_not_allowed` as `not_allowed` (not retried), `passkey_required` and `passkey_failed` as `forbidden`, `remote_help_busy` as `unavailable` (retryable). A runtime without a support service answers `get` with `available: false` and `visits` with none; one whose socket doesn't answer is `remote_help_busy`. Turning on is an external effect that pins its command unless the service refused (CS-01); Stop is idempotent. | One judge of Forever and the help code (RH-03, RH-05); a client that can't tell which words a service sent never repeats them. |
| RH-S03 | **Names owners read.** Support's `who` goes through core's `remoteHelpWho` again in the runtime (the service already sends the name alone: no operator id in brackets, display text of at most 40, “Someone” when nothing is left). The grantor is the account's name, else its email's local part, as display text (`hostText`, ≤ 120). The help code is passed on only where it is needed (`supportStateValid` already holds the service to that); the wrong-code count never leaves the runtime. | Ids stay out of messages (concise-replies.md); cleaning twice costs nothing. |
| RH-S04 | **The step-up is bound to one choice, one device, one use.** `confirmBegin {level, duration}` keeps a 32-byte nonce in the session with the account, endpoint, level and duration (300 s; a new begin replaces it; the session's close drops it) and answers the request options whose challenge is `passkeyRemoteHelpChallenge({nonce, endpoint: the session's PeerId, level, duration})`. `start` uses the begin up whatever happens and needs an assertion of a live passkey of the caller's own account (PK-05's checks, PK-07's policy, a counter that moves, the last use kept) for that begin's exact choice; an owner with no passkey starts without one, one with a passkey who sends none is `passkey_required`. `verifyAssertion` takes the challenge as a function evaluated inside its checks, so enrollment's checks and answers are unchanged. `confirmBegin` shares `passkey.register.begin`'s path in the dispatcher: no receipt, the ephemeral budget. | A stolen unlocked phone can't turn it on for longer or wider than its owner confirmed, nor replay a confirmation (RH-04). |
| RH-S05 | **The follower records each event once** (migration 0134: `appliance_state.remote_help_seq`, `remote_help_host_key`). Per event, one transaction locks the state row, skips what is behind the cursor, appends the signed appliance event and moves the cursor. `grant` → `remote_help.on {level, duration}` (actor: the grantor when the account exists), `stop` → `remote_help.off {reason: owner\|desk}`, `expired` → `off {expired}`, `locked_out` → `off {wrong_codes}`, `visit_end` → `remote_help.visit {visitId, who, level, startedAt, endedAt, steps}` (its start and level from the service's list when the event lacks them). An event `supportEventValid` refuses, or a record its `RemoteHelp*AuditPayload` refuses, is logged and passed over (the cursor moves past it, nobody is told), so one bad event can't stop the ones after it; `visit_start` is recorded with its end. The endpoint is null: the service doesn't know the device. A new host key or a `next` below the cursor means a new event log: from its start. A failed write keeps the cursor and the event comes again. | Exactly one place records, so a grant isn't signed twice (op and follower) or lost when the op's answer is; a restart neither repeats nor loses one. |
| RH-S06 | **Superseded in part by one-person.md OP-S15, OP-S78**: after the record committed and at most once, the person hears of a visit and of five wrong codes, never of their own grant. **Who hears of it (RH-08)**, after the record committed and at most once: a grant → the other owners in their assistant's DM (the message notifies them); a visit's start → every owner, a `security` push (`remote-help-visit:<id>`) and their assistant's message; five wrong help codes → every owner, a push and a message. Each owner once, in the burrow they were last active in (`recentPlaces`); one without an assistant is skipped and logged. Events more than an hour old when read are recorded but nobody is told (a runtime that was down, a first start on a service with history); a quarantined runtime tells nobody. Expiry and stopping are no messages: the card shows them. | Visibility is the safety net, a stale message is noise; the push wakes devices even when the DM is muted. |
| RH-S07 | **A visit's command line is cleaned on the way out** (`remote-help-transcript.ts`, `remoteHelp.transcript` through an export stream, `text/plain; charset=utf-8`, `whombat-remote-help-<visit>.txt`): escape sequences (CSI, OSC, DCS and the other strings, charset designations, their C1 forms), C0 controls but newline and tab, DEL, C1 and the bidi embeddings, overrides and isolates go, chunk by chunk. A string sequence ends after 4096 characters and a CSI after 64, so output can't hide what follows it from the owner. At most 50 MiB (`transcriptBytesPerVisit`), cut on a character. Reading it is not a signed event. | The owner reads exactly what support saw, without a terminal that could be steered; the record is the box's own, read by its owner. |
| RH-S08 | **The desk** (`desk/remote-help.ts`): `DeskState.remoteHelp {level, until, connected}` from the state the follower keeps (read again after every event and every long poll, so at most 25 s old; an `until` passed hides it at once), paired or not, locked or not; `POST /v1/desk/remote-help/stop {v}` stops it with reason `desk` without unlocking and answers the new state, `503 unavailable` when the service didn't answer, the state as it is without a service. Its own route file, one option and one spread in `DeskService`. | Stopping only ever takes access away (RH-04); kept apart from the desk work happening at the same time (f0). |
| RH-S09 | **The `remote_help` feature is advertised only while the support service answered its last call** (`RemoteHelpService.answering`, read once when the runtime starts, then by every long poll). | Clients show the card only where it can work (§3 S.1). |
| RH-S10 | **The fake** (`WHOMBAT_SUPPORT=fake`: a test Whombat, Forever and no help code; `fake-prod`: a customer's, a help code and no Forever; refused in production like the other fakes): two earlier visits (Look; Look and fix with restarts, a forward and a command line), a grant that expires, “Claude” connecting 3 s after it is turned on and looking until it is stopped or runs out, events as the real service sends them. | Development and the app's e2e see the card, the help code, the connected line, the visits, the messages and the desk line without a box. |
| RH-S11 | **The visits page is read one visit and one step at a time** (`tolerantVisits`): a step that isn't the contract's becomes a refusal with bad arguments (at its own time, else the visit's start), a visit that still isn't is left out. | A security review found that one odd step (support chooses what it types) failed the whole strict parse, hiding a page of an owner's visits for 90 days; the box now also cleans steps before recording them (appliance NX-426). |

## For the appliance

The runtime needs `WHOMBAT_SUPPORT_SOCKET=/run/whombat-support/api.sock` and to be able to connect to it (the
socket's group, uid 951 allowed for everything, §2.3). Nothing else changes for it.
