# A pull request's file, whole

John, 2026-10-02: in a branch room's Files changed, clicking a file opens the whole file, read-only, with the pull
request's changes shown in place as green and red `+`/`−` lines. Contracts CT-241 (0.40.0: `prs.file`, `PrFileView`,
`fileViewLines`, feature `prs.file`); the app side is whombat-app's. This file is the runtime's side.

| ID | Decision | Why |
|---|---|---|
| PF-01 | **`GET /burrows/:burrow/prs/:number/file?repo=&path=` (`prs.file`) is a read, as visible as the PR.** It finds the PR exactly as `prs.get` does (`prByNumber`: `repo` picks among PRs of the same number, else the first repo), so any member of the burrow who can open the branch room's PR can open its files; an agent gets 404 for a PR of a repo that is switched off (as everywhere agents meet repos, `visibility.ts`). Nothing is written and nothing goes through the commit pipeline (`OPERATION_SAFETY` READ). The runtime advertises `prs.file` (`runtime-features.ts`). | Files changed already shows the same PR's files and diff stat to the same people; a file of it is no new secret. |
| PF-02 | **The base version is read at the merge base of the PR's base branch and its recorded head** (`base...head`, what Files changed counts). Once the head is in the base branch — merged with a merge commit, or fast-forwarded — that merge base is the head itself and would show nothing changed, so it is **the first parent of the PR's first recorded commit** (`pr_commits` position 0), the commit the branch started from; when that can't be read (no commits recorded, a root commit, a commit gone), the merge base stands. Null only when the two share no history (every file then reads as added). A squash merge needs no fallback: the head never becomes an ancestor of the base. The head version is the PR's recorded `headSha`, not the branch's current tip. | The file view should show the same change as the Files changed row it is opened from (its `+add −del`), before and after the merge. The recorded head is what that row was counted at. A branch that merged its base in and was then merged with a merge commit shows the base's changes too: rare, and still the branch's whole difference from where it started. |
| PF-03 | **Only the PR's own files are read.** `path` must be one of the PR's `pr_files` rows (exact match) or the answer is 404 “PR #N doesn’t change <path>.” — nothing else of the repository is ever read through this route. Local origins are still read defensively: full object ids only, `git ls-tree -z --full-tree <sha> -- <path>` with `GIT_LITERAL_PATHSPECS=1` and an exact match of the listed entry (no globs, no pathspec magic, a directory is no file), `execFile` with argv, never a shell. On GitHub a path with an empty, `.` or `..` segment is no file (a URL would resolve them). | The PR's file list is the allow-list; the git side doesn't trust it alone. |
| PF-04 | **Reading a version.** Local repos (`source = 'local'`): `localMergeBase`, `localCommitParent`, `localFileAt` in `@whombat/agent-runtime/local-repos` on the bare origin (`git cat-file -s` first; a blob above `PR_FILE_MAX_BYTES` isn't read). GitHub: three adapter calls — `mergeBase` (compare API's `merge_base_commit`), `commitParent` (commits API) and `fileAt` (contents API with `application/vnd.github.raw+json`, 404 → no file, the body streamed and cut off past the limit) — on the host's gh, the managed per-burrow sign-in (in the burrow's `githubScope`) and the fake. A submodule reads as `Subproject commit <sha>`, as git's diff shows it; a directory is no file. GitHub off, a repo of a burrow that isn't connected, gh logged out or a GitHub failure answer 409 with the reason (and the fix when gh isn't connected), as other GitHub reads do. Neither version found (the branch gone) is a 409 too. | The same two questions on both kinds of repo; the raw contents API serves files up to 100 MB, so the cap is ours. |
| PF-05 | **The view**: `binary` when either version has a NUL in its first 8 KiB (`looksBinary`); `too_large` when either version is above `PR_FILE_MAX_BYTES` (1 MiB) or the laid-out lines exceed `PR_FILE_MAX_LINES` (20 000); else `text` with `fileViewLines(base, head)` over the versions decoded as UTF-8 (invalid bytes become U+FFFD, a BOM is dropped). `add`/`del` are counted from the lines (0 unless `text`). `status` is `added` without a base version, `deleted` without a head version, else `modified`. The view is built by one pure function (`buildFileView`), unit-tested. | The contract's rules, applied once; counting from the lines keeps the header and the lines in agreement. |
| PF-06 | **The fake GitHub answers file views too.** In-memory repos keep files per commit and first parents (`simulateFiles`); seeded PRs get versions made up from their `+add −del` with the fixtures' `prFileVersions`, at a made-up merge base, so the seeded world's Files changed opens like the app's fixtures; git-backed repos read git with the local helpers. | Dev and tests exercise the same route and view as a real GitHub. |
| PF-07 | **Renames read as their new path.** Local PRs count files with `--no-renames`; a GitHub rename lists its new path, which has no base version, so it shows as added. | `PrFileView` has no old path; a rename shown whole is still correct, and rare in a file view. |
| PF-08 | **Local PRs list file names as they are**: `localChanges` reads `git diff --numstat -z`, so a name with non-ASCII or special characters (`café menu.md`) is stored as itself rather than git's quoted form (`"caf\303\251 menu.md"`), which matched no file and couldn't be opened. PRs counted before this keep their quoted rows until their next push or merge reads them again. | The file view opens a file by its `pr_files` path; the path has to be the real one. |
