# Safe app updates with automatic rollback (APU)

Part of the “look-after” work of 2026-11-28 for John (stream app-updates). Whombat's helper already said when a Docker
container had a newer image; updating it was the person's chore, done by hand on the server. Now Whombat updates a
Docker Compose app itself, one app at a time (with the services that share its image), watches it come up, and puts
the previous version back by itself when it doesn't — asked through the same approval card as everything else, from
the server's page, a service's page, the assistant or the care plan.

Contracts (additive): `HostGuest.app` (`HostGuestApp`), `HostTask.apps` (`HostAppResult`), the `hosts.manage` op
`app.update` (`HostAppUpdateParams`, with `expect`, what the yes was for) and its answer's `approvalNumber`, the pure rules in `@whombat/core`
(`domain/app-updates.ts`), the Servers tools `app_updates` and `app_update`, the care plan's `apps` automation
(`CareAutomationKind`). Session protocol minor 22 (`APP_UPDATES_MINOR`). No migration. The hosts service: the agent's
`app.update` task and its apps report, the hub's `POST /servers/{id}/apps/update` (hosts `docs/MANAGE.md` 2.11,
`AGENT-PROTOCOL.md`). It changes CPL-03 (marked there).

## What happens

| # | Decision | Why |
|---|---|---|
| APU-01 | **Only apps Docker Compose started are updated.** A container with Compose's labels (its project's folder, its files and its service) is an app; one `docker run` started stays watch-only, and its server's page says “Whombat can update apps started with Docker Compose.” | Compose keeps the app's own files and settings: recreating the one service from them is what the person would do by hand. A `docker run` container's options exist nowhere Whombat could read them back from. |
| APU-02 | **One update is one task on the server: pull exactly what was checked, recreate the service, watch, and go back by itself.** The agent tags the running image `…:whombat-previous-<project>.<service>` and writes down how to go back (`progress.json` in the task's folder: the services, the image they ran, the tag), pulls exactly the newer image the yes was for (`<repo>@<digest>`; the tag only when the registry didn't say which), tags it as the service's image and recreates the service with `docker compose up -d --no-deps --pull never --no-build --remove-orphans=false --scale <service>=<n> -- <services>` from the project's settings as they were written down before the pull (APU-S09), so Compose neither pulls, builds nor removes anything, and each service keeps the number of containers it has. It watches: running, not restarting (counted from before the update), healthy when it has a health check, for 30 seconds (a health check gets up to 5 minutes). When it doesn't come up, it tags the previous image back and recreates the service the same way. Every other service of the same project that runs the same image goes with it, running or not, in the same `up`, the same watch and the same way back; a service that was stopped (the app itself too) is recreated on the new image without starting (`up --no-start`) once the others run well, and stays stopped. An older Compose that doesn't take `--pull never` (it doesn't list `--pull` in `compose up --help`, asked once per task) is used only when no service in the written-down settings has a `pull_policy` that pulls an image it has (anything but `missing`, `if_not_present` and `never`: `always`, `daily`, `weekly`, `every_…`, `build`); otherwise the update is refused before anything changes (`compose_old`: the server needs a newer Docker Compose), and going back after a restart refuses to run it too (`back_failed`, the previous image keeps its tag for a person). An image pulled for an update that ends without running it (held, put back, cut short) is removed when no tag names it and no container was created from it. Up to ten apps in one task, one after another, 30 minutes each and three hours at most; one app task at a time per server. | A failed update must not leave the app down until someone looks: going back is part of the update, not a second request. An older Compose follows `pull_policy: always` and would bring a newer image back over the one the yes was for, or over the previous one while going back; a tag per project keeps two projects that run one image from moving each other's previous image; an image nobody runs shouldn't fill the disk until a prune. Services that share an image must never run two versions side by side, and a stopped one must not start later on an image nobody tried with it. The service's own files decide everything else, so nothing but its image changes; starting what the person stopped, or changing how many copies run, would be a change nobody asked for. |
| APU-03 | **Every update asks through the existing approval card** (*Yes, now · Yes, tonight · No*). Update on a page doesn't run anything: the box commits the assistant's `app_update` for the person, with `ask: true`, in their own Chat; the card goes to the Inbox too and the page opens it. There is no second way to say yes. | One approval path: what the card says is what runs, *Tonight* means the quiet hours for changes, and the yes is in the audit log like every other. |
| APU-04 | **A database's update, a new major version and an update whose versions aren't known always ask, and the card says why.** A database is known by a word of its image's name (postgres, mariadb, mysql, mongo, redis, valkey, a bare `db` word as in `myapp-db`, and the stores that keep data the same way: qdrant, weaviate, chroma, rabbitmq, minio, kafka, nats, redpanda, garage and the like; `vchord-postgres` counts, `postgres-exporter` and `garage-webui` don't); a major jump by the versions the image labels say. The card says that going back can't undo what a database's update did to its data. An image whose running or new version isn't known (`:latest` without a version label) may be a new major version: it asks too, and its card says so; so does an update without the newer image's digest (the registry didn't say which), which takes whatever the tag names by then. On a server set not to ask, the other apps update without a card; these never do: the tool refuses them without a yes whose reasons cover them. | Those are the updates that can break or lose data; going back to the old image doesn't undo a migration, so the person decides knowing that. An unknown version is a major one until shown otherwise. A plain version bump of an ordinary app is what people want done for them. |
| APU-05 | **A snapshot first when the server is a Proxmox guest Whombat watches.** The page's Update takes one by itself (the card says so); the assistant offers it (`snapshotFirst` in `app_updates`, `snapshot: true`). A snapshot that fails stops the update. A server that isn't such a guest updates without one. | A snapshot is the one way back that also undoes a database's change, at no cost to the person; it is offered, never required. |
| APU-06 | **One plain line where the yes came from.** “immich_server is updated to 2.4.”, “immich_server 2.4 didn’t start, so I put 2.3 back.”, one sentence per app (four at most, then how many more). Done recently records it as Whombat's own work, and the server is kept quiet while it runs and 15 minutes after (planned work, monitoring.md). | The person wants to know whether it worked, not the log; a restart Whombat caused itself is no alarm. |
| APU-07 | **The care plan updates apps on Sunday night.** A server with Compose apps gets “Update your apps on Sunday night at 03:00”: an automation Whombat turns on with Go ahead, running at the start of the quiet hours of the night from Sunday to Monday (Sunday itself when they start in the evening). It updates only the apps safe to update by themselves (`hold_major`: an app whose new version turns out to be a major one, or isn't known, stays as it is) and asks about the others in one card. The plan offers it only once the release the box would go back to after a failed update knows it (its schema is `0048_restore_tests` or later, the same release gate as the automations); until then it offers what that release knows, “Tell you when apps have updates”, so a plan it stored is never misread after a rollback. | Apps get updated without becoming a weekly chore, never on the night the system updates may restart the server, and the risky ones wait for a person in the morning. The release before this one would turn the step into a weekly machine backup on Go ahead. |
| APU-08 | **The assistant reads and updates apps with two tools.** `app_updates` lists each server's apps with a newer version, which ask first and why, and how the last update went; `app_update` updates them. Before an update a person asked for, the assistant may read the app's release notes in the turn; Whombat keeps no release-notes crawler. | The same facts and the same path as the page; reading release notes is the assistant's judgement, once, when it matters. |
| APU-09 | **Old and new work together both ways.** An agent from before app updates reports no apps: the page says the server needs Whombat's newer helper, which it gets by itself, and the tools say so. An older hub never sends apps, so a new agent's apps are simply not offered. An app from before minor 22 shows nothing about app updates on a box that doesn't send them. | Agents update themselves on their own schedule; nobody should see a button that can't work or a note that blames the wrong part. |
| APU-10 | **Not now:** Compose apps outside Compose's labels (Portainer stacks without them, Unraid's own templates keep `container_update`), a change log of what changed in an image (another stream), updating several servers' apps in one card, and the fake fleet simulating app updates. | Kept to what is safe and testable today. |

## Server details

| # | Detail | Why |
|---|---|---|
| APU-S01 | The newer image's version is read from its version label (`org.opencontainers.image.version`) once per new digest, with the same registry read as the update check (one more request for the config). A version of 1000 or more is a calendar version: it has no major number. | No extra polling, and a year changing isn't a breaking change. |
| APU-S02 | An image named by digest is `pinned`: it isn't offered (its Compose file says which exact image runs). This Whombat's own containers (`whombat.service`) are never updated by the tool. | Pulling again would change nothing, and Whombat updates its own services itself. |
| APU-S03 | The card's words come from the call's `reasons` (`database`, `major`, `version_unknown`) and `snapshot`, so the card and the run agree; a yes whose reasons no longer cover the apps' refuses and asks again. | A card can't read the server; the call carries what it must say. |
| APU-S04 | The hub's route needs Full control, a recent sign-in and `confirm`, and answers 409 `agent_outdated` when the server reports Compose projects but no apps. The capability is the apps report itself, not a flag. | Same guard as installing system updates; the report already says what the agent knows. |
| APU-S05 | **The yes is bound to what was checked.** The agent reports, per app, the newer image's registry digest and Compose's hash of the service's settings (`com.docker.compose.config-hash`). When the call is asked for (the assistant's `connection_call`, the page's Update), Whombat writes into it, per app and per service of its project that shares its image (running or not, healthy or not), the server's own id (the hosts service's, not the name the call gives it), the service, the image it runs, that hash and that digest (`expect`), and adds the reasons those apps ask first for to the assistant's own, so the card always says them; an `expect` the assistant wrote itself is replaced. No card is made when the apps can't be read, when one of them has no image id or no settings hash, or when they come to more than ten with the services that share their image (the agent says why, naming the app). When it runs, Whombat refuses a yes whose `expect` is missing or doesn't name every app it updates, one read on another server than the one the call's name leads to now (a person can give a name to another server, or remove one and add another under its name), an app that runs another image, another service or other settings by then, or a new service from the same image (“changed since you said yes”), and sends the rest to the hub as `expect`. The agent checks again: the same service, the same image, an expected hash given and equal to the container's hash label and to `docker compose config --hash` of the project's files now, every service sharing the image named, no container of those services on another image; else nothing is pulled (outcome `changed`). A task with `expect` binds every app it names; only a call without any (an older Whombat, the hosts service's own API) runs unbound, and even then the container's hash label must equal the project's files. A newer image found after the yes isn't a change: the yes keeps its own digest. A stopped service isn't checked against the registry itself: it carries the newer digest and version of a running one from the same image, and the agent pulls the digest any app of that image was bound to (two different ones: `changed`). The hosts service gives no identity of a server's agent beyond its id, so a server removed and enrolled again under the same id, running the same app with the same image and settings, counts as the same. | What the card asked about is what runs: an edited Compose file, another service, a newer image pushed since the check or a `build:` service would otherwise be deployed by a yes that never saw them. Compose's own hash is what `up` compares, so it says exactly whether recreating would change more than the image. |
| APU-S06 | **A new major version waits unless the yes said it may be one.** `hold_major` is on for every run except one whose yes said `major` or `version_unknown`; the agent holds an app whose new version is a major jump or whose running or new version isn't known, before anything is retagged, so nothing changes. | A run nobody said yes to for a major version (the care plan's, a server set not to ask) must never take one, known or not. |
| APU-S07 | **An update the server stopped part-way is finished when the agent runs again.** A runner gone without a result whose `progress.json` holds an update being made is started again (its own unit, at most twice): it waits up to five minutes for Docker to answer (it may still be starting), then keeps the update when the services run the new image well (watched again, restart counts from that look; the stopped ones follow), else puts the previous image back; apps it never reached end as `interrupted`, nothing changed, and the outcome names the version it went to. When Docker doesn't answer in time, the runner ends without a result and keeps `progress.json`, so the next try starts from it. After two tries the task ends with what is known and the previous image keeps its tag, so a person can go back by hand. | A server that restarts mid-update must not leave an app on an image nobody checked, or a tag that a later `up` would deploy. |
| APU-S09 | **The settings are written down once, before the pull.** After checking Compose's hash of each service against what runs, the agent writes the project's settings down (`docker compose --profile '*' config`: every service, variables filled in) into the task's folder, checks that the copy gives the same hashes, and recreates the services, and puts them back, from that copy with the project's own name and folder (and its env files). Compose labels a container with the file it was created from, so an updated container names the copy; the agent notes the project's own folder and files (`<state>/apps/projects/<project>-<hash of its folder>.json`, its name and folder checked when read) and reads those again for the next update. The copy is readable only by root and goes with the task's folder a day after the task. | An edit to the project's files while the image downloads, or while going back, must not be deployed by a yes that never saw it, and Compose's hash leaves out the number of copies a service runs. Every profile's services stay in the copy, so Compose never takes one of them for a leftover; the next update still sees the person's own edits. The copy has the variables filled in, secrets from `.env` files included: the same secrets are in the project's own files and in each container's settings on that server, readable by root, so a root-only copy for at most a day adds no reader. Two folders can hold projects of the same name, so each keeps its own note. |
| APU-S08 | **Names from labels are checked before Compose sees them.** A project or service name must be letters, digits, `.`, `_` and `-` and start with a letter or digit (an image's own labels can claim to be Compose's); service names go after `--`, Docker's commands take `--` before references, and every Compose and env file must be an absolute file that is there. | A label like `--build` must never become an option of `compose up`. |
