# Software updates on servers: the server side

Decisions the server stream made building server-updates.md (SWU-01…SWU-15) on contracts 0.98.0 (CT-500…CT-506).
Migration 0121. Code: `apps/server/src/hosts/updates.ts` (the pure parts and the words), `tools-updates.ts` (the two
tools), `routes.ts` (the manage ops), `follow.ts` (the message when a task ends), `testing/fake-packages.ts`.

| Id | Decision | Why |
|---|---|---|
| SWU-S01 | **`hosts.manage` passes `packages.check` and `packages.install` to the hub's two routes** (`POST /servers/{id}/packages/check` with `{}`, `/packages/install` with `{packages?, confirm: true}`), owners only as every change. Install always sends `confirm: true`, whatever the request says: the owner confirmed it on the page, an agent's call was asked where it asks. The tools send the same, Check as operator and Install as admin (SWU-07). | The hub's admin route wants the confirmation; the confirmation itself is Whombat's (the dialog, the approval). |
| SWU-S02 | **Signed and in Done recently as “Checked {server} for updates” and “Installed updates on {server}”**, without Undo. Named packages go in the change's detail (“Only nginx and openssl”), with the tool's `reason`. Kinds: `hosts.manage_packages_check` / `hosts.manage_packages_install` from the page, `hosts.server_update` from the tool. | The build brief's words; an upgrade has no inverse. |
| SWU-S03 | **`server_updates`** answers the server's report (manager, waiting, security, when checked, an error, a restart with why and in words, the running package task, the last result with why it ended early) and the agent's list read now (`inspect/updates` as operator; security first, then by name, at most 500 with `more`). Nothing waiting: the list isn't read. A list that can't be read (no diagnose or console) still answers the report, with `packagesError` in Whombat's words. `canInstall` is the detail's effective manage switch (else the agents row's); `next` tells the agent what it can do. | One read gives the agent what a person sees on the System tab and Look inside → Updates. |
| SWU-S04 | **The approval's words carry the count Whombat last read on that server**, noted in memory by `server_updates` and `server_detail` and used for an hour: “install 23 updates on PVE-02”; unknown or older: “install the waiting updates on PVE-02”; named: “install nginx and openssl on web-01” (more than three: “install updates of 7 packages on web-01”). After a yes: “Installing 23 updates on PVE-02 now.” | `CallWords.ask` is written without a lookup; agents read what waits just before they ask. |
| SWU-S05 | **The server this Whombat runs on always asks** through contracts' `serverAsksApply` (CT-504, which now names `server_update`); `callTier` is unchanged, Check never asks (only `install` is in `SERVERS_SENSITIVE`). The card there adds “This Whombat runs there and may stop for a moment while they install.” and offers no “Don’t ask again” (as SA-03). | SWU-08: an upgrade there can restart Whombat's own database. |
| SWU-S06 | **Both a Check and an Install a Whombat started are followed** (PX-05). Install's one message is written from the task's `packages` and the server's report after it: “PVE-02 is up to date: 23 updates installed.”, “web-01 was already up to date.”, “21 updates installed on PVE-02, 2 updates were held back (a and b).”, named “nginx and openssl on web-01 are up to date: 2 updates installed.”, then the restart (“It needs a restart for the new kernel.” / “… for libc6 and dbus.” / “… to finish.”) and the agent's warning as its own sentence (SWU-06). Check's: “PVE-02 has 23 updates waiting, 4 for security.” or “PVE-02 is up to date.”, with the restart. A warning end is written the same way. | SWU-08's message; a check someone asked for deserves its answer too. |
| SWU-S07 | **The report is “after the task”** when no package task runs and its updates were read after the last package task ended by the agent's own clock (`packageLast`, which must be this task's or later); without `packageLast` (an older hub), after Whombat heard the end. Otherwise it is read once more after 35 s (as IU-07's parity; `startHosts` `followRetryMs` shortens it in tests); still older, the Install message leaves the restart out and the Check message falls back to “The check for updates on PVE-02 is done.”. | Comparing two of the agent's own times needs no clock agreement; the restart sentence must not come from the report before the install. |
| SWU-S08 | **An early end says why**: `task.finished`'s `code` (`busy`: “Another program is installing packages on {server} right now. Try again in a few minutes.”, SWU-04; `timeout`: “Installing updates on {server} didn’t finish within two hours, so it was stopped.” / “Checking {server} for updates didn’t finish within ten minutes, so it was stopped.”). Any other failure: “Installing updates on {server} didn’t work: {the reason}.” | The lock wait is inside the task (the hosts service), so it arrives as the task's code, not as a refusal. |
| SWU-S09 | **The hub's refusals of the two ops in SWU's words**, picked by the op (`hostsErrorText` takes it): `manage_disabled` “Installing updates needs Full control on {server}.” (“Checking for updates needs …” for Check); `busy` at the call “{server} is already checking for or installing updates. Try again when that’s done.” (one about the lock gets SWU-04's); `unsupported` with “unknown operation” (what an older agent answers) or no detail “Update the agent on {server} first.” (SWU-14); any other `unsupported` or `not_allowed` is the agent's own sentence (TrueNAS, NixOS, Unraid, pacman with names). Other ops keep their words. | The hub ships with Whombat, so only the agent can be old; its own refusals are already plain. |
| SWU-S10 | **Waiting updates' hint has its way out on Watch**: `system.updates` → the System tab, “Install them on the System tab.” (SWU-13). The phone's “Install them under Updates.” is the app's (its own Summary hint words). | Watch's body is written by the server for both. |
| SWU-S11 | **`hosts.package_updates` is listed as implemented** like every runtime feature (code-level, the same on every box, as `hosts.asks`); a server's own support is its report and the refusal words. | `runtime-features.ts`' rule; SWU-14's per-server part is the agent's. |
| SWU-S12 | **`server_tasks` and `task_stop` take `pkg:` ids** (platform `host`); `server_tasks` shows a package task's `code` and `packages`. `getTask` maps them (an empty warning is null); the report's `packageTask`/`packageLast` are normalised to the contract (status `ok`/`failed`, an empty message null, a missing code null, an odd one null). | The task view is shared; the hub's shapes are lenient, the contract isn't. |
| SWU-S13 | **The skills ship as Homelab 1.4.0**: proxmox and incus-lxc update a node or host that is in Servers with `server_updates` / `server_update` and keep `apt full-upgrade` over SSH for one that isn't; migration 0121 queues agents' older shipped Homelab pins for the start-up upgrade (as CM-09's 0120). | SWU-09; a skill text change reaches agents only with a new version. |
| SWU-S14 | **The fake hosts service checks and installs** (`testing/fake-packages.ts`): three updates waiting per detailed server (shale's with a Proxmox kernel), `pkg:` tasks whose status carries `packages` and a `code`, the report following them, Unraid refusing, and knobs for what a Check finds, what an Install holds back or warns about, and an agent that refuses. | Tests and the dev world show the whole flow without a real server. |
| SWU-S15 | **A 501 from the hosts service is a refusal before acting** (`refusedBeforeActing`, for every hosts change and undo): the hub answers 501 only for `unsupported`/`unsupported_action`, also an older agent's “unknown operation”. Before, any 5xx counted as “may have acted”, so Install on pve-01 with an old agent (2026-10-20) came back as an unknown outcome (“No answer for hosts.manage …; it may have been applied.”) instead of “Update the agent on pve-01 first.” | Other 5xx (502 agent didn't answer, 504) still may have acted. |
