# Search completeness and pagination

Priority-1 workstream (2026-09-30): `search()` read at most 500 candidates by rank, authorized them in code afterwards,
then paged the survivors by offset (EC-26). Whatever the viewer could open behind 500 better-ranked documents they
couldn't open was never found, `next` said “no more” although there was more, and the chip counts only counted the
first 500. `read/search-pagination.int.test.ts` shows it on the old code: Tom found 0 of the 45 documents of his room
behind 600 of another room, saw `counts.all` 45 instead of 75, and an offset walk duplicated or skipped rows when
membership or the cited answer changed between pages. Supersedes EC-26 (essentials-conversations.md); EC-25's filters,
EC-10, WS-22 / WS-34, BP-C31, FB-F3-03 and security-fixes.md's answer scope are unchanged.

| # | Decision | Why |
|---|----------|-----|
| SRP-01 | **What the viewer may open is part of the query.** `conversation_id is null or conversation_id = any(<visible>)`, where `<visible>` is computed per request by the existing `visibleConversations` (membership; an agent with “Search messages, canvases and runs” also public channels and branch rooms, never private channels, DMs or direct conversations, EC-10; switched-off repos' rooms removed for agents) and intersected with `within` (one principal: their conversations; several: the ones they share), exactly as before. The FB-F3-03 anti-join, the words (`websearch_to_tsquery`, “any term” unless advanced), `from` / `in` / `after` / `before` (EC-25) stay in the same query; the type chip is `type in (…)` derived from core's `searchFilterOf`. Every row a page returns is still checked in code with the same functions as before (conversation gate, `approvalVisible`, `privateApprovalVisibleTo` for everyone in `within`); a row they refuse is skipped. No candidate window any more. | Filtering after a fixed window can't be complete; the window can't be raised far enough without loading everything. The code check stays the authority for what a page shows. |
| SRP-02 | **A DECISION's approval rule is expressed in SQL too**, over a lateral join of the approval and its person condition (the first `person_approves`, `jsonb_path_query_first(…, 'strict $[*] ? (@.kind == "person_approves")', '{}', true)`): the requester; else the private rule (not private, or the requester, or in `approverIds`; `private` truthy as JavaScript reads the JSON value) and (`canDecide`: agents never, an owner unless the approval is private and theirs isn't, a member when there is no person condition or they are an approver; or membership of the approval's conversation); and every principal in `within` passes the private rule. It mirrors core's `privateApprovers` / `canDecide` and the server's `approvalVisible`; the int test holds SQL and code to the same answers (7 viewers × 5 audiences × 9 approval shapes, results and counts). **If they ever disagreed** on a row (the query allows it, the code check refuses it): the row is never returned; it is logged as an error (`search: the query allowed documents the code check refused`, with the viewer's id and the documents' ids and types, never their words); but it is counted in `counts`, and when the page ends on it — the work budget ran out right after it — `next` carries its key: its id, its time (to the microsecond) and its rank for the words, readable by anyone who decodes the cursor. The walk still moves past it and ends (the int test forces such a disagreement). The lateral join is named `search_decision` and its person condition `search_person_condition`, qualified wherever used, so no table column can shadow them. A lateral join, not a correlated `exists`: the subplan cost Postgres its parallel scan and triggered JIT (320 ms → 45 ms for a word in 60 000 of 300 000 documents). | It can be expressed safely, and only then are pages dense and counts exact without reading every match into memory. |
| SRP-03 | **Order and keyset**: `ts_rank(tsv, q)::float8` descending, then `created_at` descending, then `id collate "C"` descending (a unique, bytewise tie-breaker); without words (a filter only) `created_at`, `id`. The next page is every row strictly after the last row read (`(rank, created_at, id) < (…)`). The rank travels as a float8 (exact through JSON and back) — which needs Postgres to print floats exactly: every Whombat pool asks for `extra_float_digits = 3` when it connects (`db/client.ts`; on Postgres 12+ that is the default's shortest exact form, so nothing else the server reads changes), so a database or role set to fewer digits can't round a rank and skip tied rows (the int test walks with the database at 0). The time travels as UTC text with microseconds (a JavaScript `Date` would drop them). Equal sort values (same words, same time) page by id without duplicates. | A stable total order is what makes a walk complete and duplicate-free on unchanged data. |
| SRP-04 | **Cursor**: opaque base64url JSON `{v: 2, s, a, p}` — `s` the first 22 characters of the base64url SHA-256 of (version, burrow, viewer, trimmed words, type chip, `from`, `in`, `after`, `before`, the zone when a day filter is set, the sorted `within`); `a` the pinned answer (SRP-06); `p` the position (`['c', n]` after receipt n, `['r', rank, time, id]` after a ranked row). Checked with a strict schema — the position's id as the index writes ids (`<prefix>_<body>`, `[a-z]{1,8}_[A-Za-z0-9_-]{1,72}`), its time a real instant in the years 0001…9999, `a` core's `AnswerId`, the rank a finite number (null exactly when the search has no words) — and a Postgres data error (SQLSTATE class 22) from a query carrying the cursor's values is taken as the same refusal, so a crafted cursor is a 400, never a 500. A malformed cursor, an offset cursor from an older server (`o:<n>`) or one from another search (another viewer, words, chip, filter or zone) is refused: 400 `validation_failed`, `fields.cursor` “This cursor belongs to another search, or is out of date. Search again without it.” `limit` isn't part of the scope (a client may change it between pages). Not signed: a cursor carries no authority — permissions are read again on every page — and a forged position only moves where the viewer's own results start. ≤ about 330 characters (ids ≤ 80), under `Cursor`'s 512. | Continuing a walk under different rules would silently mix two searches; answering page 1 instead would duplicate rows in a list. |
| SRP-05 | **Work budget**: a request reads at most `SEARCH_SCAN_BUDGET` = 1000 rows, in batches (the first `limit + 1`, one past the page says whether there is more; after refused rows at least 100). When the budget is spent before the end, `next` points after the last row read, so a page may hold fewer than `limit` results — even none — and still have a `next`. `next` is null only when nothing is left (it may also be non-null at the very end when the page filled exactly at the end of a full batch; the next page is then empty with `next: null`). With authorization in SQL, refused rows are rare (the two rule sets disagreeing, or a permission changing during the request), so the budget bounds the worst case rather than shaping normal pages; tests exercise it with a smaller budget (`scanBudget`, not reachable over HTTP: the query schema strips it). | Bounded work per request without ever claiming the end early. |
| SRP-06 | **Cited results first, then by rank, without duplicates.** A walk pins the answer it started with (cursor `a`): the latest answer for the words when it has receipts, else none. Its receipts come first, in receipt order — those that pass the search's filters, chip and authorization — across as many pages as they fill (`['c', n]`), then the ranked rows *without* the cited ids. An answer with receipts never changes (`deliver_answer` refuses a second answer; failures only touch pending ones), so a pinned answer keeps the walk consistent when a newer answer arrives mid-walk; the response's `answer` is still the latest, `citedAs` labels come from the pinned one. A pinned answer that is gone or isn't the viewer's → 400 (SRP-04). Receipts are no longer limited to the old 500-candidate window. | Keyset pages can't re-sort the whole list; excluding the cited ids from the ranked stream is what keeps the two parts disjoint. |
| SRP-07 | **Counts are exact**: one `count(*) … group by type` with the same predicate (SRP-01, SRP-02) over the whole search (every type, not the page or the cursor), so they never count what the viewer can't open. Computed on every page (as of that request; a later page must not answer zeros), once per request, side by side with the page on the pool. Accepted cost: one count scan per page request — about 90 ms for a word in 60 000 of 300 000 documents, a few ms for selective words — and a resync (the socket came back; `search.query` is invalidated) refetches every search page on screen, each with its own count scan (the apps keep only the pages of the current walk observed, SRP-11). Measured on 300 000 documents in 2 000 rooms (a viewer in 100): a word in 20 % of documents 70 → 125 ms median (the old answer said 53 matches, the truth was 6 004), a word in 2 % 23 → 17 ms, a filter-only search 64 → 40 ms. Readers that only want results skip them (`counts: false`, SRP-09). Carrying the first page's counts to later pages (review round 2) was weighed and left: the apps already show the first page's counts (a later page's go unused), but to skip the count scan on a cursor page the server would have to answer something else there — zeros (the contract says `counts` are the chips of the whole search), or counts carried in the cursor (as of the first page, not this request, and a client could put any numbers in a cursor unless it were signed). Either needs a contract change first — a query flag that leaves counts out, or `counts` documented as the walk's first page's — so they stay exact, per request. | Exact is affordable; bounded counts would need their own semantics on every chip. |
| SRP-08 | **When data changes between pages** (keyset semantics, each page authorized as of its own request): a document added above the cursor isn't shown in this walk (search again to see it); one added below appears when the walk reaches it; a deleted one simply isn't there. An edit that changes a document's rank or time moves it: it can show up a second time or be passed in this walk (the web drops repeats by id). Permissions: a room the viewer left is gone from the next page on; a room they joined contributes the rows after the cursor, never the ones before it; a DECISION whose approval became visible or hidden follows the same rule. The counts are those of each page's own request. | What every keyset walk does; nothing is ever shown that the viewer can't open at the time of the request. |
| SRP-09 | **Readers inside Whombat** (the agent `search` tool, the answer-mode dispatch context) take one list: `searchResults` follows `next` (at most 5 pages) until it has `limit` results or the search ends, without counts. The MCP `search` tool keeps its input (no cursor; contracts unchanged). | A sparse page must not read as “nothing found” to an agent either. |
| SRP-10 | **An index for a search in one conversation** (review round 2): `search_documents_conversation_idx` on `(burrow_id, conversation_id, created_at)`, migration `0057_search_conversation` (`expand`, floors `0047_delegation`). With `in` set, the conversation gate is answered in code — is that conversation visible, else the query is `false` — instead of `conversation_id is null or = any(…)`, so the planner sizes the room right (an index for a small room, a parallel scan to count a big one). Measured on 300 000 documents in 2 000 rooms plus one room of 30 000, medians before → after: `in` a small room 25 → 2 ms; `in` the big room 48 → 26 ms; `in` with two weeks of days 31–33 → 2–3 ms; `in` a small room with words 132 → 2 ms; `in` the big room with a word in all of its documents ≈ 120 ms either way (its count reads all 30 000); searches without `in` unchanged. Cost: the build takes 0.3 s per 300 000 documents inside the migration's transaction (writes to `search_documents` wait meanwhile), about 30 MB, 20 000 inserts unchanged within noise, 20 000 text updates 255 → 325 ms. `(…, created_at desc, id collate "C" desc)` measured the same (an incremental sort orders the rare ties by id); a single `(conversation_id)` index sped up small rooms but not the big room's pages. Ranked searches still compute `ts_rank` for every match, as before. | The index turns a whole-table read into a room's read for the Search screen's “In” filter, at a small write cost; the index alone made big rooms slower until the gate stopped hiding the room's size. |

The clients' side — `useSearchPages`, short and empty pages, a refused cursor — is SRP-11…SRP-14 in whombat-app's
`docs/decisions/search-pagination.md`.
