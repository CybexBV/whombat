# A lost Postgres session never crashes the process (postgres.js patch)

Workstream `hp/pg-guard` (2026-09-30). postgres.js 3.4.9, the latest release (2026-04-05), exits the process when the
server ends a session that a transaction or a `sql.reserve()` is using: `pg_terminate_backend`, a Postgres restart or
failover, a network reset, a backend OOM, `idle_in_transaction_session_timeout`. `closed()` nulls the socket and
`nextWrite()` then throws `TypeError: Cannot read properties of null (reading 'write')` from `setImmediate`, an
uncaught exception (porsager/postgres #1208, #1154, #1066). `apps/server/src/db/lost-session.int.test.ts` shows it and
five related defects on the unpatched driver: a hung reservation, a pool stalled for `connect_timeout` (a spent
`nextWriteTimer` blocks the next StartupMessage), the dead backend's `57P01` replayed onto the next pool query, an
unhandled rejection when a session is lost during the array-type fetch (#1223), and — the quiet one — a dead
transaction's INSERT committed in autocommit on the session the pool reconnected for queued work (#1216, #1204). The
same patch and tests are in control (its CL-114).

| # | Decision | Why |
|---|----------|-----|
| PGG-01 | **Patch postgres.js 3.4.9 with pnpm** (`patches/postgres@3.4.9.patch`, `pnpm-workspace.yaml` `patchedDependencies`) until a release has the fixes. The patch backports the open upstream PRs #1209, #1215, #1229 (its `closed()` reset only), #1240 and #1241 (its `fetchArrayTypes().catch` only), to both the ESM (`src/`, what Node's `import`, vitest and the esbuild bundles load) and the CJS (`cjs/src/`) builds; `cf/src` (Cloudflare Workers) is left alone. Every hunk is marked `[whombat patch]` and names its upstream reference. The driver choice itself is the lead's, separately. | The crash is reachable in production by any failover, and a data-integrity hazard comes with it; none of the upstream fixes is released. |
| PGG-02 | **What changes.** `nextWrite()` without a socket settles the pending queries with `CONNECTION_CLOSED` (`error()`: `query`, `initial`, `sent`) instead of throwing. `terminate()` and `closed()` drop `chunk` and set `nextWriteTimer` to null. `closed()` forgets the settled `query`, `results`, `errorResponse`, the partial `result` and the row counter before the pool reconnects the connection. The array-type fetch's promise gets a `.catch` (its error already reaches the waiting query through `errored()`). A transaction whose session closed marks itself dead in `begin()`'s `onclose`: its queued statements and every later one, including the automatic `commit`/`rollback`, reject with the close error and never reach the connection again. A reservation does the same through a `closed` hook `onclose()` calls before it clears `c.reserved`, and its `release()` becomes a no-op (the connection is already back in the pool's closed queue). | Each is the smallest change that removes one observed failure; the tests fail without each. |
| PGG-03 | **What callers see.** `db.transaction` / `sql.begin` reject with the postgres.js error `CONNECTION_CLOSED` (drizzle doesn't wrap it); statements inside a dead transaction reject with drizzle's `DrizzleQueryError` whose `cause.code` is `CONNECTION_CLOSED` (raw `sql`: the error itself). A dead reserved handle's queries reject with `CONNECTION_CLOSED`. The next pool query runs on a fresh session. Nothing retries a transaction: the commit pipeline's callers see the rejection as today's other connection errors. | A lost session is an ordinary, catchable failure; retrying writes is the caller's decision. |
| PGG-04 | **Startup losses fail the waiting query.** A query parked while its connection starts (`initial`) fails with the error that ended that session (`57P01`, `ECONNRESET`) — as on 3.4.9, minus the unhandled rejection. Not taken from #1223/#1241: clearing the stale state on that path to retry the query, because without #1241's `connect_timeout`-bounded backoff a peer that keeps failing (PgBouncer `server_login_retry`) loops forever (#1193). | Fixes the crash without taking on an unbounded reconnect loop. |
| PGG-05 | **Not covered** (open upstream, no crash): a `reserve()` still *waiting* in the pool queue when a connection closes can be handed to the reconnect as `initial` and stranded (#1195, PR #1229's `connect()` change); `sql.reserve()` with `fetch_types: false` can hang (#1220). Whombat reserves in one place — the automations engine's advisory lock (`automations/engine/lock.ts` `takeLock()`), usually from an idle pool. The engine also doesn't notice that the session holding its lock ended (the lock is gone with it); that is an application question for the automations workstream, not a driver one. | Out of the crash's scope; recorded so nobody assumes the patch covers them. |
| PGG-06 | **Regression tests**: `apps/server/src/db/lost-session.int.test.ts`, 13 tests against the dev Postgres (throwaway database): through drizzle's `db.transaction` and `sql.begin`, the backend terminated while the callback goes on querying or returns, `idle_in_transaction_session_timeout`, and the autocommit hazard (the row must not exist); a reserved handle after termination; the next pool query after a backend killed mid-query; a session lost during the array-type fetch (a TCP proxy sends the FATAL, or a reset). Each installs `uncaughtException` / `unhandledRejection` listeners and asserts none fired, and that the pool still answers. All 13 fail on unpatched 3.4.9. | Proves each hunk and tells us when a release makes the patch unnecessary: run them without it. |
| PGG-07 | **Packaging.** `patches/` is tracked and every install runs `pnpm install --frozen-lockfile` on the tree: the dev instance, `pnpm package` / `pnpm bundle:runtime` (esbuild bundles the patched `src/` into `app/server.mjs` and `app/cli.mjs`; checked), and the appliance's Nix build (`fetchPnpmDeps` and `pnpmConfigHook` on the pinned rev, unfiltered). Without the patch file pnpm refuses to install (“Failed to read patch file”), so a build can't ship the driver unpatched. The appliance gets it when its `whombat` pin moves; the lockfile changed, so refresh `pinnedPnpmDepsHash` then (NX-42). | The patch must reach every place the server runs. |
| PGG-08 | **Dropping it.** Bumping `postgres` to another version makes pnpm refuse the unused `postgres@3.4.9` patch, which forces the check: if the release contains the fixes (the tests pass without the patch), delete `patches/` and the `patchedDependencies` entry; otherwise port the patch. | No silent drift between the patch and the driver it patches. |
