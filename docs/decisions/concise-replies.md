# Concise replies: agents answer short, and give the detail when asked

Agents answered like documentation: headings, bullet lists, a recap of the question and a closing offer, for
questions a colleague would answer in two sentences. The runner's system prompt only said “Keep replies short,
plain and specific.” The fix has two layers. The prompt makes short replies the default. An agent that left
something out can offer a “More detail” button, and it offers the button only when there is more to give.

## Maintainer decisions (2026-09-25)

| # | Decision | Why |
|---|---|---|
| CNR-01 | **The system prompt asks for chat-length replies** (`REPLY_STYLE_LINES` in `apps/runner/src/prompt.ts`): lead with the answer or the next step, in one to three short sentences. No headings, bullet lists, recap or closing offers, unless the person asked for a write-up, a plan, a list or steps. | Claude and Codex default to thorough, formatted answers; a half-line didn't change that. The exceptions keep real write-ups possible. |
| CNR-02 | **Detail when asked, and exact content is never cut.** When the person asks for detail (“explain”, “in detail”, “walk me through”, “write it up”) the agent gives all of it at once. Code, commands, links and exact figures are never shortened. | Short replies must not become a second round-trip for someone who already said what they wanted, or a lossy one. |
| CNR-03 | **The agent decides whether there is more.** `post_message` and `reply_in_thread` take an optional `more`: what the short reply left out, in a few words (≤ 200). It is stored on the message as `Message.more {hint, requestedById, requestedAt}` (jsonb `messages.more`) and is dropped on people's messages. Cards and search answers don't offer it. | Only the agent knows whether it held something back; a button under every reply would be odd when the short answer is complete. The hint tells the next turn what to expand without re-deriving it. |
| CNR-04 | **Superseded in part by TC-02 (turn-completion.md)**: a hint without an answer is incomplete and is never posted alone. **A final text can offer more too**: a last line `MORE: what you left out` becomes `more`, and the line is not shown. An empty line offers nothing; a final text that is only that line is posted as it is. | Agents that end a turn without posting have their final text posted by the runner (`postFinal`), which has no other way to pass the field. |
| CNR-05 | **“More detail” is a quick-reply chip under the message**, on web (room and thread pane) and mobile. It shows to people who can wake the agent: any member for a team agent, only the owner for a personal agent (PA-05), never the author (`canAskForMore` in `@whombat/core`). Unlike quick replies it stays on older messages. It goes away once anyone has asked, for everyone, and the agent's “is thinking” takes over. | The same look as quick replies, since it is a reply the reader taps. One ask per message: a second person's tap would only produce a duplicate. |
| CNR-06 | **Asking is a command, not a message**: `POST /messages/:id/more` → `request_more` (commit pipeline). It marks the offer taken (only the first ask; later ones return the message unchanged), signs a hidden `message.more_requested` event, publishes `message.updated`, and queues an `expand` dispatch for the author, where the short reply is: its thread, or the conversation itself. No “tell me more” message is posted for the person. | “More detail” isn't something the person said, so it shouldn't appear in the conversation as their message. The detail lands next to what it expands, and mobile (no thread view) sees top-level detail. |
| CNR-07 | **Superseded in part by HN-T01, HN-T02 (hermes-native.md)**: claims run one turn per agent, conversation and thread at a time, a top-level turn alone in its conversation; an `expand` turn is still its own turn. **An `expand` dispatch is its own turn.** It never coalesces into a queued reply, and a later mention never coalesces into it. Claims still run one turn per agent and conversation at a time. Its prompt quotes the short reply and the hint and asks for the whole detail in one message (lists and headings allowed), without repeating the short reply or offering more again. | Coalescing would lose either the detail or the mention's question. |

## Threads that read like people talking (2026-10-10)

John, on the #reports thread of the Fusebox automation's fix of issue #5: “It posts an enormous thread about the job and
the thread replies are also large. The goal of this project is to keep the agents talk like humans as much as possible,
which means they should be concise and talk in plain English.” Of the thread's 11 KB, the automation's own instructions
to the agents were most: the assessment request 2.6 KB (every rule for Banjo, the raw issue with its HTML comment), the
fix request 2 KB (the issue again), the review request 1 KB (Banjo's reply again). The agents' replies carried commit
hashes, test counts and “strict Clippy”, which the fix step's “what you changed and how you tested it” and the writing
rule's “specific (file names, numbers …)” invited.

| # | Decision | Why |
|---|---|---|
| CNR-08 | **An automation's request to an agent is one line in the conversation**: `@Banjo` and the step's name, and for a run about an issue or pull request which one, linked — “@Banjo Assess it: [#5](…) “Claude Code 2.1.295 is out (Fusebox matches 2.1.293)”” (`requestLine`; a step without a name: “Over to you”). The rendered instructions are kept on the step (`output.instructions`) and are the agent's alone: the server gives them as that message's text wherever the agent's turn sees it — its request, its thread and window (`dispatchInstructions` in `buildDispatchContext`) —, so the runner and the agent work as before. Its other requests in the thread stay one line in its context too. No contract change: the message is an ordinary message, only its text differs for the agent it was for. | Instructions are for the agent, not the people in the channel; a thread should read like people talking. The instructions stay what the automation's steps say (the step editor, Advanced), and each run keeps them on its step; showing them on the run page is the app's to add. |
| CNR-09 | **The writing rule asks for plain English**: “Write like the people here, in plain English anyone on the team understands … specific about what matters to the reader (what changed, what it means, who decided), no jargon … Commit hashes, test counts, file paths, commands and tool output stay out of chat unless someone asks for them or needs them to act: they belong in the pull request, your report’s details or “More detail”.” Replaces “specific (file names, numbers, who decided what and when)”. CNR-02 stands: asked for detail, nothing is cut. | “Specific” read as “technical”; what is specific for a reader is what changed and what it means. |
| CNR-10 | **An automation's turn is reminded that people follow its thread** (`AUTOMATION_REPLY_LINE` after the request): one to three plain sentences, like telling a colleague — what it found or did and what happens next; “how you tested it” in plain words (“the tests pass”), hashes, test counts, file names and logs left to the pull request and the details. Runner only: the recipes' own words (contracts) stay, so no automation needs “Update its wording”. | An automation's instructions ask for reports (“what you changed and how you tested it”); the reminder keeps the answer human without changing every automation. |
| CNR-11 | **A learned skill's message is plain words**: “I wrote down how I did this, so next time goes quicker.” — the card under it names the skill (was “I learned a skill: how-fusebox-claude-code-catch-up-is-verified.”). | A slug isn't a sentence. |

## Short after an investigation, said again at the end of every turn (2026-11-05)

John: “I often get very long replies.” On Home, the agent's Chat replies had a median of 750 characters (192 of 245
over 500) and read like reports: what it checked, bold headings, lists, a closing question. The rules were in the
prompt, but far from where the model reads last (agent-voices.md, 2026-11-05).

| # | Decision | Why |
|---|---|---|
| CNR-12 | **Every turn ends with how long the reply may be** (`replyLengthLines`, the turn prompt's last line): short however long the earlier replies were, the answer or result and what happens next in one to three short sentences under 60 words, no headings, lists or how the agent got there; longer only when the person asked for detail or a write-up, the rest offered with `more`. Not on a “More detail” turn (it gives the detail) or a brief (its card is the reply). | The voice cue at the end of the preface is what made voices stick (AV-08); length had no such reminder. The last line is what the model reads last, and it counters a thread of long replies. |
| CNR-13 | **The reply rule covers investigations**: after a long one too, the reply is what the agent found and what happens next, not how it found it or everything it checked. | The long replies were mostly accounts of the work. |
| CNR-14 | **The limit is a number: under 60 words.** Tried on Claude Opus 5.5 with Home’s real system prompt (Banjo’s and Hazel’s faces, two rounds each, no tools): “one to three sentences” alone still gave four or five long sentences (a heat-pump alarm 726–893 characters); with “under 60 words” 376–509, a disk question 365–405, while “explain in detail” still got 3,300–5,200. | Models read a sentence count loosely and a word count closely. |


## What Whombat posts to wake an agent reads like people talking (2026-11-11)

Whombat's own messages that wake the agent still carried instructions and technical detail in the chat: GitHub's checks
wake (“@Dusty The checks on PR #1 finished on 3d88d8: 3 passed, 1 failed (build).”), the Feedback development handoff
(“@Dusty A development handoff for report … (approval #N). Please investigate and propose a fix on a feature branch …”,
with a 12-character commit on its approval card), the mirrored “Checks finished on 3d88d8.” with a “12/14 passed ·
2 failing” pill, and an automation described in words (“@Dusty please draft an automation for me with draft_automation
(automationId …)”).

| # | Decision | Why |
|---|---|---|
| CW-01 | **A message Whombat posts to wake an agent is one plain line; the details are the agent's brief.** `briefAgent` (`apps/server/src/domain/agent-brief.ts`) records the brief next to the message as a hidden signed event (`message.agent_brief`, no text, about the agent); the turn that message starts reads it as the line followed by the brief, wherever it sees that message (as CNR-08). The checks wake reads “The checks on [PR #1](…) failed (build).” or “… passed.”, the repository, branch, commit and counts in the brief. Mirrored check results read “Checks failed on PR #N.” with a pill naming only the failing checks (“unit and e2e failed”), and their activity line “Checks failed on PR #N (unit).” / “Checks passed on PR #N.”. No contract change: the message is an ordinary message. | Instructions and hashes are for the agent, not the person; the agent still gets everything it got before. |
| CW-02 | **Superseded by CW-05**: **The Feedback development handoff reads “Dusty is working on a fix for FB-….”** (`handoffMessageText`), still posted as the person who asked and shown word for word on the approval card. “Investigate it and propose a fix on a feature branch” is in the agent's prompt next to the report and the assessment (`feedbackHandoffLines`). The card says which code the assessment read (“whombat/billing as its runner exported it”) without the commit's hash; the approval still binds the exact commit and refuses when it changed. | The person approved the handoff; the message tells the thread what happens next. The hash meant nothing to the person deciding. |
| CW-03 | **An automation described in words is asked in the person's words** (`automations.create`, source `describe`): “Please draft an automation for me: …”, mentioning the agent; the draft's id and `draft_automation` are its brief (CW-01). The `describe`, `template` and `import` sources and `automations.templates` stay in the contract although no app calls them now: removing them is a contract change other repositories would have to follow, for no gain to the person. | The tool name and the id are for the agent. |
| CW-04 | **The agent's standing words name what there is now**: the MCP server's instructions say the agent shares the person's “Chat, threads, runs and approvals”, and `post_message` posts “in the person’s Chat or another conversation you are in”, without “channels”, “DMs”, “branch room” or “Mention people with @Name”. | One person and one Chat (one-person.md); words for rooms and people that aren't there make the agent talk about them. |
| CW-05 | **The Feedback development handoff is the person's ask: “Dusty, please work on a fix for FB-….”** (`handoffMessageText`, with the agent's name and the report's reference), still posted as the person who approved it and shown word for word on the approval card; the rest of CW-02 holds (what to do is in the agent's prompt with the report and the assessment; the card names the code without the hash). | Posted under the person's name, “Dusty is working on a fix” read as the person announcing the agent's work; worded as their ask, the way a described automation's line is (CW-03). |
