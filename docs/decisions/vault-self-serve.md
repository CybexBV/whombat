# The assistant runs the Vault for its person (VS)

John, 2026-10-21, in the main checkout: “When we use a vault, we shouldn't have to hand a key to the agent. It should have
access immediately … I also want the agent to be able to store login details and passwords in the vault, so when we share
a login via a chat, it should be able to store the login details in the vault. When we have an SSH key and I tell the agent
to use that SSH key that's already in the vault for a new IP address, I want the agent to be aware that it should add that
IP address to the vault also.” After the recommendation below: “Automatic host key trust is good. For the rest, I
completely agree and I would like you to implement all your recommendations.”

Why now: keys, owner-only server edits and “Trust this server” were built for a crew shared by several people
(vault.md VT-20…VT-23, VT-S04, VT-S05). Since one-whombat.md each person has one assistant that works only for them
(assistant-name.md AN-06, PA-05), so a key to it protects against nothing and every step is a click John must make.

What does **not** change: another person, their assistant and every team agent still never see or use someone's entries
without a key from them (VT-01, VT-21, VT-22); secrets stay sealed and brokered (VT-04, VT-10); every use is in the
owner's RECENT USE (VT-S11).

Spans contracts 0.112.0 (`docs/decisions/contracts.md` CT-780+), this runtime (VS-S01+ below, migration 0129),
whombat-app 0.114.0 (`docs/decisions/vault-self-serve.md` there, AP-4000+). Assignment:
`docs/implementation/vault-self-serve/assignment.md`.

## The assistant saves logins it is sent

| # | Decision | Why |
|---|---|---|
| VS-04 | **Superseded in part by one-person.md OP-S60, OP-S72**: `vault_save` saves into the person's Vault in their own turns, in any of their rooms (every room is theirs); a turn that isn't theirs can't. **`vault_save`** (personal assistants only): saves a website login (`login`, browser sign-in), an API token (`http` + bearer) or a username and password for an API (`http` + basic) into the Vault of the person the turn is for, and gives the assistant its key (VS-01). Refused (`blocked`, plain words) unless the agent is that person's own assistant, the turn is on their behalf and **nobody else reads the room** (`onlyOwnerReads`, VA-01's rule): in a room others read it says to send it in their own chat. | John: “when we share a login via a chat, it should be able to store the login details.” A room others read has already shown the secret to them. |
| VS-05 | **Only what the person wrote.** The secret must appear, exactly, in a message the person wrote in this conversation in the last 7 days (not deleted); else `failed` “That isn’t in a message from {Name} here.” `made: true` (a password the assistant made itself, e.g. for a new database user) skips that check and only ever makes a **new** entry. | A web page, an e-mail or a tool answer the assistant reads can't plant or replace entries; injected text can at most add a new entry the person sees. |
| VS-06 | **New or replaced.** Without `entry`: a new entry (name, address, username as the kind needs), the address checked by the Vault's destination rule exactly as a person's save (VT-11…VT-13, LN), 50 entries per person. With `entry`: one of the person's own entries of the same kind gets the new secret (and username), never a new address: an `address` there is refused (“I can’t change where a saved login points; {Name} can, in the Vault.”). | A changed address with the old secret would send it somewhere else. |
| VS-07 | **The message is blanked.** Right after the save, every message in that conversation that holds the secret — the person's and the assistant's own — has it replaced by `••••••` (`VAULT_BLANKED`), gains `vaultSaved` (“Saved to your Vault · Plex”, linking to the entry) and is sent as `message.updated`; `editedAt` stays. Signed `vault.entry.saved` (new) or `vault.entry.secret_replaced`, by the assistant, owner detail as every Vault event. From then on the value is scrubbed from everything the assistant writes (its scrub list holds entries it saved, `vault_entries.saved_by_id`), and its next turn starts a fresh provider session (the Vault part of the session fingerprint changed). | The chat stops showing it; the next turn's context no longer carries it. |
| VS-08 | **Honest limits**, said once in the Vault's intro, not fixed: the AI provider already received that message; backups made before keep it; a notification shown before stays shown. The Vault's own form remains the fully private way. | Don't promise what blanking can't undo. |

## New servers for an SSH key

| # | Decision | Why |
|---|---|---|
| VS-09 | **`vault_add_server`** (personal assistants, their owner's turn): adds a server to one of the person's SSH keys. `entry` given; else their only SSH key; with none, a new ed25519 key “Servers” is made (as SI-09); with several, refused with their names. `address` is a host name or IP with `:port` (22 by default), checked by VT-S06 (and LN-01/02); `username` given, else the one the key's servers share, else `root`; `name` given, else the server's own `hostname -s` (cleaned to the server-name pattern), else the address with dots as dashes, made unique with `-2`. The same host, port and user already there answers `already`. The assistant's key covers it (All servers, or its list gains it). Signed `vault.entry.changed` by the assistant. | John: “I want the agent to be aware that it should add that IP address to the vault also.” |
| VS-10 | **Superseded in part by one-person.md OP-04**: host keys are still trusted on first contact and a changed one refused; there are no agents' computers. **Host keys are trusted on first contact** (John: “Automatic host key trust is good”), like Sign in once (SI-04): when no entry of the owner pins that host and port, the key the server shows is trusted and pinned; when one does, it must match (else `host_key_changed`, nothing added, nothing sent). This holds for `vault_add_server`, for an agent's first use of a server without a pin, and for the owner's Check. “Trust this server” remains only for a key that **changed**. Agents' computers are unchanged (a server's pin comes from Whombat's first connection). | Nobody compares fingerprints on first contact; a changed key is what matters and is still refused. |
| VS-11 | **The key isn't on the server yet.** With `password` — which must be in the person's own message in a room only they read (VS-04, VS-05) — Whombat signs in with it once, adds the key's public line to that user's `~/.ssh/authorized_keys` (SI-09's command), signs in again with the key to confirm (`key_added`), blanks the password in the messages (`vaultSaved` “Used once, not kept”) and forgets it; it is scrubbed from what the assistant writes for the rest of that turn. A server's password is never stored. Without a password the server is still added (trusted) and the answer is `key_refused` with the public key line, so the assistant can tell the person what to add. | “Use once and forget” beats storing root passwords (recommended, John agreed). |
| VS-12 | **SSH tools are always there for an assistant in its owner's turns** (`ssh_exec`, `ssh_read_file`, `ssh_write_file`, `ssh_upload` with `vault_save` and `vault_add_server`), so a server or key added mid-turn is usable in the same turn. A server name that isn't the key's answers `no_server` with “add it with vault_add_server”. | The tool list is fixed per session (PE-02). |

## What the assistant is told, and what others see

| # | Decision | Why |
|---|---|---|
| VS-13 | **Superseded in part by one-person.md OP-S72, OP-S87**, *and by connect-in-chat.md CIC-10: a secret the agent needs it asks for with `vault_ask`'s write-only card, not in chat; `vault_save` still saves one sent anyway*: the agent is told the person's entries are its to use and to save what they send it with `vault_save` right away; no room is read by anyone else. **Prompt** (contracts' copy, CT-785): a personal assistant is told its person's entries are its to use; to save a login, password or token it's sent in a room only that person reads with `vault_save` right away and say in one line what it saved, never repeating the secret; in a room others read to ask for it in their own chat or the Vault; to add a host it's asked to use with `vault_add_server` first; that a server's password is used once and never kept; that an entry switched Off was switched off by its person (“they can switch “Dusty can use this” back on”). The old “never ask anyone to paste a password into chat” becomes “never in a room other people read”. Team agents keep their wording. | The person's own chat is now a fine place to hand over a login. |
| VS-14 | **Activity**: both tools are Vault tools for the activity row (`isVaultActivityTool`): neutral, no evidence, no input kept (VT-D07). | The input holds the secret. |

## Not now

- Removing the secret from the provider CLI's own transcript files and from earlier backups (VS-08).
- Saving a shared login into a Connection instead of the Vault (connections have their own sign-in, CX-04); the
  assistant may suggest connecting it.
- TOTP codes, SSH passwords kept, per-server tiers (VT-S15 unchanged).
