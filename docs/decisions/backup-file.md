# Backup files

John, 2026-10-11: “We need a way to create a backup which we can simply download and restore via an upload as well.
Perhaps we should be able to check what we want to include in the backup and set a default setting what a user should
backup? For example, I would like connections, memories, automations, etc to be backupped.” After the proposal: “Implement
this fully”.

Whombat already had two whole-box backups, and they stay: the appliance's restic backups (the appliance
`docs/decisions/backup.md` BK-*) and `whombat backup` / `whombat restore` on self-hosted (`docs/backup.md`,
bp-distribution.md BP-F06, BP-F07). A **backup file** is per burrow, made by an owner, of the parts they choose,
downloaded, kept, and uploaded again to restore — on the same Whombat, another box, after a reset, hosted ↔ box.

Contracts 0.79.0 (CT-335): `@whombat/core/backup` (categories, the encrypted container, the tar body, the records, the
restore preview, the words) and `api.backups`; the session's `backup-file` download and upload streams and the feature
`backup.file`. App: whombat-app `docs/decisions/backup-file.md` (AP-1181…), Android `backup-file-android.md`. Migration
0103.

## Decisions

| ID | Decision | Why |
| --- | --- | --- |
| BF-01 | **Superseded in part by one-person.md OP-S79**: making, restoring and setting the defaults are the person's, never an agent's. **Per burrow, owners only.** Making, restoring and setting the defaults are for the burrow's owners who are people. Never agents: no MCP tool, no keys-engine path; every command checks the actor itself. A file, an upload and a restore belong to the owner who made them. | A backup file can hold every sign-in of the burrow; only the people responsible for the burrow decide where that goes. |
| BF-02 | **Superseded by one-person.md OP-S75, OP-S79**: a file holds every conversation of the burrow and the person's things, and nothing of it is held back from the person restoring it. **A file holds only what its maker can see.** Organisation things are in it (agents, automations, shared connections, channels, skills, settings); other people's private things stay out — their Vault entries, their “only you” connections, their profiles, DMs and private channels the maker isn't in — and so do references to them. The panel says so (“Your 8 entries · other people’s stay private”). | A file leaves the box; it must not carry what its maker couldn't open there. |
| BF-03 | **Records, not database rows.** Each category is typed, versioned records (`@whombat/core/backup`); a restore replays them through the commit pipeline (signed events, keys, audit). The audit log is never imported (its chain can't be spliced); each restore is signed (“Restored 9 automations from a backup made on 11 Oct”). | Records survive schema changes and another box's ids; the pipeline keeps every rule and the signed history honest. |
| BF-04 | **A restore only adds or updates; it never deletes.** Things are matched on keys that survive between boxes (agent handle, automation name, connection service and address, memory scope and title, channel slug, person email, Vault kind and name, pack name and version, repository name; messages by the restore map). The preview shows per category New / Already here / Different; for Different one choice for the whole restore: **Keep what’s here** (default) or **Use the backup**. The restore map makes restoring the same file twice add nothing and remaps references. | Restoring into a living burrow must be safe to try; the map makes it idempotent. |
| BF-05 | **Superseded in part by one-person.md OP-S79**: the categories stand, with `people` now `settings` (no person or invite records). **Ten categories** with stable ids, plain labels and meta lines from core: agents, memories, automations, connections, skills, people (channels and settings), vault, messages, files, repositories; the first seven on by default (since 2026-10-21 eleven with `servers`, nine on by default: BF-13, BF-21). Never in a file: the phones and computers people sign in on (push registrations), passkeys, sessions, endpoint enrollments, Claude/Codex/gh logins, provider sessions, run history, dispatches, usage, agent computers, the audit log, caches; and since 2026-10-21 (BF-22) the desk screen and its pairing, Done recently and Undo, followed tasks, what was found on the network and hidden, a device's remembered sign-in token, Email (IMAP) accounts. | What people asked for, in words they know; what is box-bound or rebuilt stays home. |
| BF-06 | **Always encrypted, with a password chosen when the file is made** (at least 10 characters; “You need it to restore. Whombat can’t get it back for you.”). The server unseals sign-ins and writes them inside the encrypted file; a restore seals them again under the target's master key with the new rows' AADs. The password reaches the server in the request and is never stored, logged or kept in a receipt. Every restored connection is checked; one that fails shows under Connections → Needs you with “Sign in again”. | The file must be safe on any disk; sign-ins bound to another box (a Fusebox client key, Google tokens from another OAuth client) must say so instead of failing silently. |
| BF-07 | **Superseded in part by one-person.md OP-S75**: a restore stays safe as it says, except that nobody is invited. **Safe to restore.** Automations come back switched off (published → disabled, drafts stay drafts: “They start switched off, so they don’t run twice.”); agents' schedules and the maker's briefing come back paused; a webhook gets a new URL and secret only when it is switched on; people not in the burrow are invited the normal way; messages keep their original author and time. | Nothing restored acts on its own before a person looks at it. |
| BF-08 | **Superseded in part by one-person.md OP-S74, OP-S75**: making and restoring a file are signed events and the restore's summary is shown; nobody else is told or invited. **People are told.** Making a file is a signed event; when it holds sign-ins (connections or Vault), the other owners hear it in their assistant's DM in one sentence (“Mara made a backup file that includes connection sign-ins.”). A restore is a signed event; its summary is shown (what came back, connections to sign in again, automations to switch on, people invited). | Sign-ins leaving the box is something every owner should know about. |
| BF-09 | **Defaults per burrow.** Owners set the ticks (“Make these the default”); the download panel starts from them (initially the seven); the restore panel starts with every category in the file. | People asked for a default of what to back up. |
| BF-10 | **Transfer.** Making a file is a job with progress; the encrypted file waits in a staging directory under WHOMBAT_HOME (with a `CACHEDIR.TAG` so box backups skip it; `whombat backup` leaves it out) for **24 hours** or until removed. Download: REST bytes with Range; managed: a session `download` stream (`DownloadResource {type: 'backup-file'}`), resumable. Upload: staged (`backups.stage`), then REST chunks (`Content-Range`, resumable) or a session `upload` stream (`UploadTarget {type: 'backup-file'}`); staged uploads go after the restore or 24 hours. Free disk is checked first. A restore is a job with progress. | Files can be gigabytes; every step must resume and never fill the disk. |
| BF-11 | **Not built now:** a scheduled backup file (the box backups already run on their own) and members making a file of “only my things”. | Clean follow-ups; neither was asked for yet. |
| BF-12 | **Feature `backup.file`**: managed runtimes advertise it and the app shows Settings → Backups only then. `whombat backup-file open <file> --out <dir>` decrypts and unpacks a file offline, so nobody's data is locked in. | Old runtimes stay quiet; a file is useful even without a Whombat. |

## Details

| ID | Detail | Why |
| --- | --- | --- |
| BF-D01 | **Migration 0103** (expand): `burrows.backup_defaults` (jsonb, null = the seven) and `backup_defaults_at`; tables `backup_files` (status, categories, progress, size, sha256, staged name, error, maker, ready and expiry times), `backup_uploads` (size, announced or computed sha256, received, status, staged name, expiry), `backup_restores` (upload, file name, made at, source, categories, keep/replace, status, progress, summary, error) and `backup_restore_map` (burrow, source burrow, source id → target id, category). No password, key or secret in any of them. | What the jobs and the views need; old binaries ignore all of it. |
| BF-D02 | **Native crypto, byte for byte.** The server seals and opens chunks with Node's `chacha20-poly1305` under the file's HChaCha20 subkey (`backupChunkSubkey`) and derives keys with `crypto.argon2` (`nativeBackupKdf`); a unit test holds it to core's `BackupFileEncoder` / `BackupFileDecoder`. The CLI uses core's decoder with the native Argon2id. | Gigabytes at native speed; one format everywhere. |
| BF-D03 | **Staging** is `$WHOMBAT_HOME/backup-files` (`WHOMBAT_BACKUP_FILES_DIR` for tests), 0700 with a `CACHEDIR.TAG`, files 0600 under names the server makes (`<id>.wbk`, `<id>.upload`, `<id>.work/`). Room: making needs 1.5 × the estimate, staging 2 × the upload, a restore the upload's size again, each plus 512 MiB kept free. | The appliance's restic honours the tag; refusing early beats a full disk. |
| BF-D04 | **Nothing unencrypted with sign-ins touches the disk.** Records wait in scratch spools encrypted with a one-time AES-256-GCM key held in memory (`Spool`), while a file is made and while a restore reads one. Blobs, canvases and bundles a restore needs wait in its scratch as they are (they are what the file store and the origins hold anyway); a job's scratch goes when it ends, orphans at start. | Sign-ins are the one thing that must never sit in the clear; a crash leaves only unreadable bytes. |
| BF-D05 | **One snapshot.** A file's categories are read in one read-only, repeatable-read transaction into the spools (counts and bytes known), then written: manifest, directory, records, then the blobs (each once by sha256), canvases (Yjs state) and repository bundles (`git bundle create --all`, empty repositories left out). | Records that point at each other agree; the manifest comes first but needs the counts. |
| BF-D06 | **One restorer per category, for the preview and the restore.** `backups.inspect` reads the whole file, spools every category and runs the restorers without writing (stand-in ids keep later records counted as new). A restore runs the chosen categories in dependency order — people, connections, agents, Vault, skills, memories, automations, messages, files, repositories, then the skills agents had switched off — in batches (100 records, 250 for messages and files) through `backup.restore_batch`, each record in its own savepoint: a record this Whombat refuses is skipped and counted, never the restore. The batch command runs only inside the person's own running restore job (an in-process registry), so it can't be called with made-up records. | The preview says exactly what the restore will do; a bad record never blocks the rest. |
| BF-D07 | **Superseded in part by one-person.md OP-S74**: the signed events stand; a file made tells nobody. **Signed events:** `backup.file_made` (“Made a backup file with sign-ins in it”, the DM notice to the other owners once the file is ready), `backup.restored` (core's `backupRestoredText`), `backup.defaults_changed`, and text-less `backup.restore_batch` and `backup.connection_needs_sign_in`. Things brought back through existing commands keep their own events (`agent.hired` “Brought back Toffee from a backup file”, `automation.created`/`published`, `member.invited`, `entry.added`, `repo.created`). Restored messages are not signed again as their authors: their signatures stay in the source's audit log; the restorer's batch events record what was added. | Nobody signs for someone else; the log says who brought what back. |
| BF-D08 | **The estimate is counts and sums** (rows, text lengths, distinct blob sizes, origin folders on disk), never the records themselves. | It runs every time the panel opens. |
| BF-D09 | **Restored history counts as read**: after a restore, members' read markers move (forward only) to each touched conversation's latest message. | An old conversation shouldn't light up as unread because it came back. |
| BF-D10 | **A failed restore keeps its upload** (back to `uploaded`, the restore's `upload` still set) so “Try again” inspects and restores it again — the restore map skips what already came back. A finished restore deletes it. Jobs a stopped server left running are failed at start. | Trying again must not need the upload again. |
| BF-D11 | **`whombat backup-file open`** unpacks into a new or empty folder (0700, files 0600), checks every blob's sha256, and removes what it wrote when the file turns out damaged; the password comes from `--password-file` or a hidden prompt. | Offline, nobody's data is locked in; a half-unpacked damaged file helps nobody. |
| BF-D12 | **`repos.create` lives beside its route** (`github/local-repo-command.ts`) so a restore records a repository without the HTTP layer. A repository comes back under the same rule as creating one (owners; on a self-hosted Whombat owners who are its admins): its origin is made from the bundle (`git init --bare`, `fetch bundle +refs/*:refs/*`); with “Use the backup” a repository that is here takes the bundle's refs on top. | One rule for repositories, wherever they come from. |
| BF-D13 | **Superseded in part by one-person.md OP-S75, OP-S79**: the burrow's settings and channels come back as it says; nobody is invited and no role is restored. **People and settings:** someone not here is invited with `invite_members`; someone here and different gets the file's title, short name and role — never the restorer's own role and never the last owner. Channels by slug, made with their slug, topic, visibility, creator and time, the members who are here and the restorer. The burrow's name and slug never change; time zone, link previews, agents' LAN switch, backup defaults and the AI gateway (when its connection came back) follow keep/replace; home networks are added (never removed) only by an admin. A GitHub repository's settings come back only where GitHub is connected. | The restorer can't lock themselves (or everyone) out; another box's GitHub is its own. |
| BF-D14 | **Superseded in part by one-person.md OP-S79**: an agent record carries no sign-in source. **Agents** come back through `createAgent` (the plan's agents, a free name, a model this Whombat has — else its default —, grants clamped, the managed default sign-in, their signed hire) with their handle when free, channels, keys and the connections they looked after; a host folder only on the same self-hosted Whombat; `trusted` becomes `guarded` on a managed one; an organization sign-in elsewhere becomes each person's own (`org_credential`). | Restoring never grants more than hiring would. |
| BF-D15 | **Automations** come back through their own commands: `automation.create`, the remapped definition as a draft, `automation.publish` with `enable: false` (it checks rooms, agents and connections here); one that doesn't fit stays a draft (`drafts`); keys through `automation.set_keys`. “Use the backup” publishes the file's version, switched off. | The publish checks are the ones a person gets. |
| BF-D16 | **Superseded in part by one-person.md OP-S54**: a restore adds every connection of the file to the burrow, signed, and checks each afterwards. **Connections** come back through `catalog_connection.add` (shared) or as the restorer's own (personal; only their own, never someone else's), an MCP OAuth client by its issuer (made when this Whombat has none); Google/Microsoft accounts only the restorer's; connector apps (this Whombat's OAuth clients) only where none is set up and the restorer is an admin; feedback sources through `feedback.create_integration` with their token. A file never connects GitHub. Afterwards each is checked (`recheckConnection`, the connector check); one that isn't working is set to `needs_reauth` and listed in the summary; tool tiers come back once the check found the tools. | Every sign-in proves itself on the new box or asks for a person. |
| BF-D17 | **Superseded in part by one-person.md OP-S79**: the Vault comes back to the person restoring the file, with its SSH servers, their trusted host keys and the agent's keys. **The Vault** comes back only to the person who made the file (by email): `vault.create`, an SSH key through `vault.create_ssh` with its key read again so its comment names the new entry, its servers with their trusted host keys, the keys agents held. Tools come back with the entry's next check. | Someone else's Vault never lands in another person's hands. |
| BF-D18 | **Skills:** a version is rebuilt from its files and installed through `import_pack` (validation, scan, an admin for host code; its sha256 must match), a shipped pack only from this Whombat's own bundle at exactly that version (`bundled_missing` otherwise); attachments through `attach_pack`, tool approvals only where the tool is unchanged, secret slots bound to the restorer's own entries; learned skills back into the agent's own pack (`approveIntoOwnPack`). Agents' own packs are not written as packs: their learned skills rebuild them. | Installing from a file is installing an upload. |
| BF-D19 | **Superseded in part by one-person.md OP-S75**: messages come back as it says, an author not here kept as a name; nobody is invited. **Messages:** conversations by key (a DM needs its agent and person here) or made; a message's author by email or handle, else kept as a name — a person who left (tied to their account when they have one here, so accepting the invitation makes them themselves again) or a retired agent; a card about something that didn't come back is left out (the text stays); its files when the file holds their bytes; search indexed after the commit. Files saved straight into Files come back saved straight into Files. | History reads as it did, without inventing people. |
| BF-D20 | **Superseded in part by one-person.md OP-S79**: the count stands; another person's things are no longer held back. **The preview's count** is new + already here + different; what can't come back (another person's things, a missing reference) is explained by its notes. | The chips add up to the number shown. |
| BF-D21 | **Jobs tell their maker** with ephemeral `backups.changed` frames on their `me` topic (no outbox row), progress at most once a second, ready/failed/done always. Failed files stay listed with their error for 24 hours; restores are kept 30 days; the sweep runs every 10 minutes. | The apps refetch the view; nothing about the content goes over the wire. |

## Servers, the address and the restore fixes (2026-10-21)

John, 2026-10-21: “I created a back to a file and restored it, but the servers were not exported / imported. Perhaps
there are more issues.” After the review: “can you update the agents to use the new IP address of the dev box … when
we restore a backup and the IP is different than what the previous IP address was, we should ask the user if we should
update the agents with the new IP address … fix the backup procedure, implement all your recommended steps”.

What the review found: servers live in the hosts service (`/persist/hosts`, its own database and certificate
authority) and neither the backup file nor the box's restic backup read it; the DEV box's address changed on a reboot
(10.100.1.160 → .158) and all five agents kept dialling the old one; built-in connections, devices, chat threads,
the assistant's name and more came back wrong. Build brief: `docs/implementation/backup-servers/assignment.md`.

| ID | Decision | Why |
| --- | --- | --- |
| BF-13 | **Servers are a category of their own**, `servers` (“Servers”), offered and on by default only where this Whombat watches servers (the hosts service is there and this is the servers' burrow, ONE-DH02). It holds the hosts service's own backup — its servers, their settings, history and its certificate authority — and Whombat's choices per server (Asks you first). It counts as a file with sign-ins (BF-08): the other owners are told. | Servers are what a box is for; the certificate authority is what lets the servers trust a restored Whombat without anyone visiting them. The file already carries the Vault's SSH keys to the same servers, so it is no new kind of secret. |
| BF-14 | **Servers come back only where they fit.** The same certificate authority as this Whombat's: “Already here” (nothing is imported; the choices per server follow keep/replace). Another one and this Whombat watches no servers yet: the hosts service takes the file's backup and restarts (seconds). Another one and this Whombat already watches servers: they can't come back, and the preview says so (“This Whombat already watches 3 servers, so the 5 in the file stay with the Whombat they report to.”). | A server trusts exactly one Whombat; two fleets can't be merged, and replacing a working fleet from a restore is never what someone meant. |
| BF-15 | **The address question.** When the file's Whombat was at another address than this one, the restore preview asks: “Your servers look for your Whombat at 10.100.1.160. This Whombat is at 10.100.1.158.” — **Point them here** (the default) · Leave them. Point them here signs in to every server the restorer has a Vault SSH key for (Sign in once with a key, SI-02) and updates its agent in place to this address; the others are listed under Needs you with “Point it here”, which opens Add a server filled in (a password once). Leave them changes nothing. | John's ask. The old Whombat may still be running, so moving its servers is the person's choice; while a server can't reach this Whombat, signing in to it is the only way to tell it anything. |
| BF-16 | **An address change on the same Whombat is noticed.** The hosts service remembers its previous address; when servers haven't come back five minutes after it changed, owners see under Needs you: “Your Whombat’s address changed from 10.100.1.160 to 10.100.1.158, and 5 servers haven’t found it yet.” with Point them here (BF-15). It goes away when they are back. | The same question for the case that happened on the DEV box; agents too old to search (BF-17) still get back in one step. |
| BF-17 | **Agents find their Whombat themselves** (hosts HS-170…): the hosts service tells every agent all its addresses; an agent that can't reach its saved address tries those, then looks for a Whombat with the certificate it trusts on its own local networks, and saves the address it found. Nobody is asked. | While a server can't reach the box, the box can't tell it anything; the agent looking is the one fix that always works, and its certificate check keeps a stranger from posing as the Whombat. |
| BF-18 | **The box's own backups hold the servers too** (appliance NX-407…, BK-31…): a consistent copy of the hosts service's data before every snapshot, put back by the console restore. | A dead box lost its servers with either backup. |
| BF-19 | **Restore fixes.** Built-in connections (Servers, devices) are never signed in again: Servers is never added (the server makes it where the hosts service is) and a device comes back with its settings; tool tiers come back with their limits; task chats, the Feedback room, thread subjects and a thread's model stay what they were; the assistant gets its name and face back; agents this Whombat no longer has (the retired crew) aren't hired again; agents' keys pass the same limits as hiring and the apps hear about them; scheduled turns find their thread; what a file couldn't take (a sign-in that didn't open, files without Files ticked) is said in the preview instead of left out quietly. | Each of these was found in the 2026-10-21 review; a restore must give back what was there, and say what it can't. |
| BF-20 | **More in the file**: Dashboard widgets (people), “Always allow” commands (agents), canvas comments (messages), the maker's own preferences and photo (people), a thread's model choice (messages), what a connection runs on (connections). | They are things people made and would miss. |
| BF-21 | **Messages are on by default** (with the servers, nine where servers are offered); Files stay off for their size. Burrows that saved their own defaults keep them. | Chat history is what people expect a backup to keep; without it the default file held no conversation at all. |
| BF-22 | **Never in a file** (adds to BF-05): the desk screen and its pairing, Done recently and Undo, followed tasks, what was found on the network and hidden, a device's remembered sign-in token, Email (IMAP) accounts (CM-M13). | Box-bound, rebuilt, or a second-step code once more; saying so ends the guessing. |
| BF-23 | **Not now**: reaching servers that can't reach the box on the local network through the relay (SI-13), and merging two fleets. | Each is a change of its own; neither blocks restoring or moving a box on the same network. |
| BF-24 | **One restore at a time** (backup-options.md, 2026-11-04): starting one takes its upload only if nobody took it while the file was read (a conditional update), and a partial unique index (`backup_restores_one_running`, migration 0038) refuses a second restore running in the same burrow, which answers `restore_running`; the migration first fails older restores a crash left running. A session upload of a backup file may leave the whole file's sha256 out (CT-1695): the box hashes the file once it is all there and checks it against the one it was staged with, if any. | The running check came before reading the file, which takes minutes, so two restores could replay the same rows at once; the app needn't read a large file twice. |

| ID | Detail | Why |
| --- | --- | --- |
| BF-S01 | **The Servers connection in a file is matched, never added.** Its record is matched to the `whombat_servers` connection of the burrow being restored into (the one `ensureServersConnection` made), remembered in the restore map so keys scoped to it and automations' references follow it, and never checked again. Where there is none (no hosts service, or not the servers' burrow) nothing of it comes back and it isn't counted. | Only the server makes it, and only where the hosts service is; a copy from a file was a second connection to sign in to that could never work (`connect.ts` refuses built-ins). |
| BF-S02 | **Built-in connections' tiers go back without a check.** For Servers (and a device that is here) the file's tiers of the tools this Whombat has by the same name are set in the batch through `catalog_connection.set_tool_tier` (its signed Keys event, then the connection's lifecycle event), with “Use the backup”; “Keep what’s here” keeps them. A device's connection the restore adds is never rechecked: its tiers are set right after the restore. | A built-in connection's tools are there from the start (no check finds them); the tier command keeps the audit trail people see for a change of tier. |
| BF-S03 | **An assistant gets its name and face back.** A name nobody chose here — the assistant has no signed rename by a person (an `agent.updated` event with a `name` that isn't the boot's own naming, AN-07, which has a `reason`) — takes the file's name whatever the choice for what differs; that is what a fresh box has. A name a person chose follows keep/replace. When only the name differs the preview says “Already here” and the restore counts it updated. | The automatic name is nobody's choice, so it can't be what someone wants to keep; on a fresh box the file's name is the one its person chose. |
| BF-S04 | **The rename is a rename**: the same writes as Settings (the assistant's DMs' titles and search `where`s, `renameAgentDms`), its face (the file's look from 0.117, else the character's face for the name in the assistant shell), a signed Keys event by the restorer, “Renamed Neo to Rex”, and `agent.updated` for the apps. That event counts as a chosen name for the next restore. | One way a name changes; a second restore of another file with “Keep what’s here” then keeps it. |
| BF-S05 | **A name this Whombat can't take stays out**: not one capitalised word, reserved (`Whombat`), longer than an assistant's name may be, or used by someone active here. It then doesn't count as a difference. Team agents are never renamed (their names are fixed, FA-03), so their names aren't compared. | The rename's own rules; a difference nothing can apply would make every later restore say “Different”. |
| BF-S06 | **A model this Whombat offers.** The file's model, effort (and from 0.117 fast replies) are checked as a hire checks them (`assertModelChoice`, against the models the runner listed); one that isn't offered falls back, in that order, to without fast replies, without the effort, the tool's own default model. An ACP runtime only where this Whombat runs it (not managed, the runtime listed), else the agent's current tool or this Whombat's default. An agent here is compared with what can be applied, so a missing model isn't “Different” every time. | Restoring never sets a model the runner can't start; the comparison stays idempotent. |
| BF-S07 | **Keys pass hiring's limits and the apps hear them.** A key an agent like it can't hold (`grantFitProblem`, personal or team, the assistant shell's rules) is left out, the rest clamped to what agents may hold (`grantsThatFit`). A hired agent gets them through `createAgent` (its signed hire names them; `principal.created` and `grants.updated` go out); an agent that is here takes them with “Use the backup” through Configure's `writeGrants` (one signed Keys event per change, `grants.updated`), and `agent.updated` goes out after its description, model or channels change. | The restore wrote keys straight into the table: unchecked, unsigned, and invisible to open apps until a reload. |
| BF-S08 | **The retired crew isn't hired again.** In the assistant shell a team agent of the file that isn't an active agent here is skipped with a note, by the rule hiring has there (ONE-02, `noHiring`); one still active here (a crew the boot hasn't retired yet) is matched as before.
