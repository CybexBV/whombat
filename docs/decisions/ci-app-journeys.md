# The app job's browser journeys

The `app` job on the shared CI (`scripts/ci/app.sh`, a disposable VM with 4 CPUs and 12 GiB) runs the managed journeys
(`pnpm e2e:managed`, 4 workers), then the hosted ones, then the real chat smoke test (`pnpm e2e:runtime`).

| Id | Decision | Why |
|----|----------|-----|
| CJ-01 | **The managed journeys run against a bundled build, not the Vite dev server.** The project's web server builds the page (`vite build --mode e2e --outDir dist-managed-e2e`, hosted target, fake world) with `NODE_ENV=development` and serves it with `vite preview`. The development build keeps what the dev server gave the journeys: React's development build, StrictMode's double effects and responses checked against the contracts (`validateResponses`). The build takes a few seconds. | The dev server sends each page load as about 1,200 separate modules. In the VM, with four browsers on four CPUs, every `goto` or `reload` took 3–5 s, and journeys that navigate ten or more times ran out of their 30 s (builds 1, 6 and 11 of `whombat-runtime-app`: every flaky or failed journey ended in “Test timeout of 30000ms exceeded”, mostly inside `fresh()`, `page.goto` or `page.reload`). Locally on four pinned CPUs the dev server gave 14 flaky journeys in one run. The build loads the page as a few dozen chunks. |
| CJ-02 | **Each Playwright run in `app.sh` writes to its own output folder** (`tmp/playwright/web/managed`, `…/hosted`). | A run empties its output folder first, so the hosted run deleted the managed run's traces whenever the managed one passed with retries, and the flakes left nothing to read. |
| CJ-03 | **The `app` job runs the real chat smoke test** (`--project=runtime`, its own output folder) after the fake-world journeys, on a Postgres service of the job's own (`postgres:17`, `DATABASE_URL`), with no retries. The runtime makes a throwaway database next to `DATABASE_URL` and drops it when Playwright stops it. | The fake-world journeys never cross the encrypted session, the server or the runner, so a break between them could reach DEV unnoticed. The one journey takes 10–16 s once its runtime is up; it passed all ten runs (eight on four pinned CPUs, two on a fresh `postgres:17`), so a failure means a real break and needs no retry. |
