# Approved connection calls end as the call did (2026-11-07)

A person's yes to a connection tool call runs the deferred `call_connection_tool` command, whose call to the service
runs after that command's commit. Its outcome is what the approval reports: never a success for a call that didn't get
through. Decisions are `APC-nn`.

| # | Decision | Reason |
|---|---|---|
| APC-01 | **The call is a required continuation of its command, and its result ends the approval.** The command's commit holds `connection.tool_called` (the call's saved intent, its `callId` the deferred input's) with the approval still running; the call then runs as the commit's `complete` hook, not an `after` hook, so what it throws reaches the approvals engine. A call that worked succeeds the approval; one that failed fails it with the call's own plain words; one that broke before the service was called says nothing happened (“Whombat couldn’t start it, so nothing happened. Undo and Approve to try again.”); one the service answered as an error fails it (“The service said it couldn’t do it.”); a timeout is uncertain (“… so it may or may not have happened …”). The agent is still woken with the result; a failure to wake it doesn't change the outcome. | An `after` hook's failure is only logged, so the engine signed “Allowed … to use …” for a call that never ran and left nothing to tell the person or recover. |
| APC-02 | **After a crash, the call's own events settle it, and nothing is sent twice.** The engine's reconciler for `call_connection_tool` reads the agent's `connection.tool_called` and `connection.tool_finished` for the call: no `tool_called` means the command never committed, so the call never ran and runs once now; a `tool_finished` that is `done` completes the approval; anything else is uncertain (`UNCERTAIN_EXECUTION`) and is never sent again. | The command's commit is the point after which the call may have gone out; before it, running it is safe, after it, only a recorded result is known. |
| APC-03 | **A yes is bound to where the call goes, and the call is sent only there.** The `call_connection_tool` command carries `target`, the connection's call target when the agent asked (`connections/call-target.ts`; set by `connection_call` and by the undo paths of connections, devices and servers), and the approval's hash covers it. `executeConnectionCall` compares it with the row it loaded for the request before a call slot is taken, and every request of a call is signed only as that row: each transport checks the stored connection's call target again once its credential is in hand and before it signs, since a refresh, a new sign-in or the MCP transport reads the connection again (`signedConnectionFetch`'s `target`, for `request`, adapters and the MCP pool's requests; a socket's sign-in), a device's skill must be the one, at the address, its connection names, and pooled MCP sessions are kept per call target (`connections/pool.ts`), so one opened as another account is never used and a call that finds the connection changed drops it. When it differs nothing is sent, the call is recorded `refused`, and it fails with “<label> changed since you said yes (its address, account or sign-in), so nothing was sent.” — an approved call's approval fails with it and the agent is woken with it, so it can ask again — or, for a call that didn't ask, “… changed while this call started …, so nothing was sent. Call it again.” A call asked before calls carried a target is sent as before. | Council round 6 asked whether person-approved calls had the gap the mail cards had: they did, since the yes named only the connection id and the tool's hash. Round 7: the MCP transport read the connection again before signing and could reuse a pooled session, so a pasted token replaced on the same server between the check and the request signed the approved write as another account. |
| APC-04 | **An Undo goes only where its change went.** A change made through a connection (`connection.call`), a device (`device.set`), a Servers tool the assistant called (`hosts.*`, undone as a new call of the assistant) or a page's setting (`thing.action`) keeps with its Undo recipe where it went and as whom (`destination`, the connection's call target when it ran; merged settings saves keep the first one's). Undo compares it with the connection as it is now (`undoGoesWhereChangeWent`) and refuses when it differs: “<label> changed since, so this can’t be undone here.”, said in the chat for a device's Undo already under way; the inverse call is bound to that destination (its `target`), so a connection repointed while it starts sends nothing (APC-03). A change recorded before destinations were kept is undone as before. | Round 7 of the council (all three reviewers): Undo worked out where the inverse goes when it was pressed, so after the person pointed a connection at another Home Assistant, Undo sent the inverse there. |
