# Approved connection calls end as the call did (2026-11-07)

A person's yes to a connection tool call runs the deferred `call_connection_tool` command, whose call to the service
runs after that command's commit. Its outcome is what the approval reports: never a success for a call that didn't get
through. Decisions are `APC-nn`.

| # | Decision | Reason |
|---|---|---|
| APC-01 | **The call is a required continuation of its command, and its result ends the approval.** The command's commit holds `connection.tool_called` (the call's saved intent, its `callId` the deferred input's) with the approval still running; the call then runs as the commit's `complete` hook, not an `after` hook, so what it throws reaches the approvals engine. A call that worked succeeds the approval; one that failed fails it with the call's own plain words; one that broke before the service was called says nothing happened (“Whombat couldn’t start it, so nothing happened. Undo and Approve to try again.”); one the service answered as an error fails it (“The service said it couldn’t do it.”); a timeout is uncertain (“… so it may or may not have happened …”). The agent is still woken with the result; a failure to wake it doesn't change the outcome. | An `after` hook's failure is only logged, so the engine signed “Allowed … to use …” for a call that never ran and left nothing to tell the person or recover. |
| APC-02 | **After a crash, the call's own events settle it, and nothing is sent twice.** The engine's reconciler for `call_connection_tool` reads the agent's `connection.tool_called` and `connection.tool_finished` for the call: no `tool_called` means the command never committed, so the call never ran and runs once now; a `tool_finished` that is `done` completes the approval; anything else is uncertain (`UNCERTAIN_EXECUTION`) and is never sent again. | The command's commit is the point after which the call may have gone out; before it, running it is safe, after it, only a recorded result is known. |
| APC-03 | **A yes is bound to where the call goes, and the call is sent only there.** The `call_connection_tool` command carries `target`, the connection's call target when the agent asked (`connections/call-target.ts`; set by `connection_call` and by the undo paths of connections, devices and servers), and `others`, the call target then of each other connection the call acts through, by id (`callReaches`, registered per catalog: a Servers `backup_place_nfs` with `server: connection:<id>` shares on that TrueNAS; set by `connection_call` and by the Servers undo); the approval's hash covers both. The command is saved, and its card asked, only while the connection and each other one are still stored with those targets, read and held (`FOR SHARE`) in the transaction that saves it (`heldChanged`), so the card's words, read from the connection in that transaction, are about what its yes is bound to; otherwise nothing is saved or sent and the agent hears “… changed while this call started …, so nothing was sent. Call it again.” (an Undo: “<label> changed since, so this can’t be undone here.”); an approved call isn't checked there again. `executeConnectionCall` compares them with the rows it loaded for the request before a call slot is taken (another connection the call reaches that wasn't there when it was asked counts as changed), and runs the call bound to them (`connections/bound-targets.ts`): every credential opened for a bound connection, through any transport, is checked before it is opened and again once it is in hand, before anything is signed, on the row it is opened from and on the connection as it is stored then (`resolveCredential`, and the NAS drivers' own Synology and QNAP sign-ins, each before its sign-in). An OAuth refresh, a client secret exchange and a session sign-in read the connection again and check that row before they ask anything (`keepBoundRow`), and one under way is shared only by callers bound alike for that connection (`sharedSignIn`; another waits for it to end and starts its own), so a bound call whose connection changed before its sign-in sends it no sign-in, token request or discovery, and stores no tokens on it or marks it `needs_reauth` (a change that lands while a sign-in is under way meets that write's own condition, the refresh token or the credential's version it used, as before); the background check after a 401 (`confirmRefusedCredential`) is bound to the call's target too. A datagram or a line to the connection's host (a PS5's wake, discovery and reboot, `connectionDatagram`, `connectionLine`) is sent only while the binding, and the call's own target, still match the stored connection, and what a PS5 update keeps on its connection (`keepPs5Fields`) is written only while the bound connection still goes there. Every request of a call is signed only as that row: each transport checks the stored connection's call target again once its credential is in hand and before it signs, since a refresh, a new sign-in or the MCP transport reads the connection again (`signedConnectionFetch`'s `target`, for `request`, adapters and the MCP pool's requests; a socket's sign-in), a device's skill must be the one, at the address, its connection names, and pooled MCP sessions are kept per call target (`connections/pool.ts`), so one opened as another account is never used and a call that finds the connection changed drops it. When any differs nothing is sent, the call is recorded `refused`, and it fails with “<label> changed since you said yes (its address, account or sign-in), so nothing was sent.”, naming the connection that changed (also where a transport turned the refusal into words of its own) — an approved call's approval fails with it and the agent is woken with it, so it can ask again — or, for a call that didn't ask, “… changed while this call started …, so nothing was sent. Call it again.” A call asked before calls carried a target is sent as before; one asked before calls carried `others` signs as each other connection only as it is when the call starts. | Council round 6 asked whether person-approved calls had the gap the mail cards had: they did, since the yes named only the connection id and the tool's hash. Round 7: the MCP transport read the connection again before signing and could reuse a pooled session, so a pasted token replaced on the same server between the check and the request signed the approved write as another account. Round 7's follow-up: a Servers backup place on a TrueNAS checked only the Servers connection, so a key or address replaced on the TrueNAS while the card waited made the approved share run there. Round 8: the credential was opened before the binding was checked, so a refresh, an exchange or a session sign-in (QNAP's too) read the changed connection and signed in at the new server, storing its tokens or marking it `needs_reauth`, before the call refused; a PS5's datagrams and lines had no check; a card could be saved after its connection changed. |
| APC-04 | **An Undo goes only where its change went.** A change made through a connection (`connection.call`), a device (`device.set`), a Servers tool the assistant called (`hosts.*`, undone as a new call of the assistant) or a page's setting (`thing.action`) keeps with its Undo recipe where it went and as whom (`destination`, the connection's call target when it ran; a Servers change also each other connection's it acted through, `otherDestinations`; merged settings saves keep the first one's). Undo compares them with the connections as they are now (`undoGoesWhereChangeWent`) and refuses when any differs: “<label> changed since, so this can’t be undone here.”, said in the chat for a device's Undo already under way; the inverse call is bound to those destinations (its `target` and `others`), and a page setting's Put it back is signed only at its destination (APC-05), so a connection repointed while it starts sends nothing (APC-03); one repointed while the inverse's call is saved is refused there (a connection's and a device's Undo say the same words). A device's Undo reads the device's current value only while the skill it reads is still the device its connection names (`sameDevice`). A change recorded before destinations were kept is undone as before. | Round 7 of the council (all three reviewers): Undo worked out where the inverse goes when it was pressed, so after the person pointed a connection at another Home Assistant, Undo sent the inverse there. Round 8: a device's Undo could read a device given another address between its two reads. |
| APC-05 | **A page's action signs only as the connection it was checked on, and the assistant's yes to one is bound to where it goes.** A page's button or declared setting and its Put it back (`things/actions.ts` `executeThingAction`) load the connection once and run the kind's action bound to that row's call target (Put it back: its change's destination; `connections/bound-targets.ts`), so every request the action signs, through any transport, is signed only while that row and the connection as it is stored then still have it. Otherwise nothing is sent and, whatever words the kind's transport made of it, the person reads “<label> changed just now (its address, account or sign-in), so nothing was sent. Try again.” (Put it back: “<label> changed since, so this can’t be undone here.”). A page action the assistant asks for (`settings_change` of `things.action`) is read from one load of its connection (`askThingAction`): its call target, carried as `targets` in `change_setting`'s input, which the approval's hash covers, and the card's words (the kind's `describe`, a declared setting's old value), read bound to that same target, so a connection that changes while they are read gives no card and the assistant hears “… changed while this call started … Call it again.”. `change_setting` is saved, and its card asked, only while each target is still stored so, read and held (`FOR SHARE`) in the transaction that saves it (the same words otherwise; not checked again for the approved run). After the yes, or at once when the key allows it, the change runs only while the connection still goes there, bound to it from the settings tool through the session dispatcher to the action (the binding follows the call's async chain), and otherwise the assistant hears “<label> changed since you said yes …” (“… changed while this call started … Call it again.” when it didn't ask). An action that reaches `executeThingAction` for the assistant without a binding refuses (“<label> changed just now …”) rather than run on the connection as it is then. A change asked before changes carried targets runs bound to the connection as it is when it runs. A request a page action didn't send because its connection changed counts as not sent for the request's receipt (`actAs`, Home Assistant's restart, UniFi Access, T3 Code's buttons and a PS5 update's requests), so a person's device and the assistant hear that the connection changed, not that it may have happened. | Round 7's follow-up of the council: a page's action, its Put it back and the assistant's approved page settings read the connection once and then signed through transports that read it again (a refresh, a session sign-in), and the assistant's yes named only the thing, so a token, account or address replaced in between made the change run as someone else or somewhere else. Round 8: the card read the old setting from the connection and then loaded it again to bind the yes, so one repointed in between got a card about one server and a yes bound to another; a page action over a session that refused for a changed connection was reported as “may have happened”. |
