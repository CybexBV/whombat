# Email through Whombat Link (LE-01…LE-14)

A box sends email only through a mail server, and almost nobody sets one up. Whombat Link now sends two kinds of email
for the boxes linked to it, each the owner's choice in Settings → Notifications. Control's side (storage, the offline
job, the words of each email) is in whombat-cloud's control decisions; this file is the box's and the contracts' side.
Contracts 4.15.0.

| ID | Decision | Why |
| --- | --- | --- |
| LE-01 | **Two choices, kept on the box.** “Tell me when it goes offline” (`offline`, on unless the owner turns it off) and “Send my emails through Whombat Link” (`notifications`, off unless the owner turns it on). Kept in `appliance_state` (`link_mail_offline`, `link_mail_notifications`, migration 0016, expand) in every Link state; each change is a signed `link.mail_set` appliance event (`LinkMailAuditPayload`: who and both choices). Session op `link.mail.set {offline?, notifications?}` (owners) answers `LinkOutput`; `LinkSummary.mail` carries them (absent from a box before 4.15). | Email through our servers changes who can see what, so the owner decides (John, 2026-11-23). The offline warning carries nothing from the box: control already knows when it stops hearing from it, and it is the one thing a down box can't say itself, so it starts on (watch-defaults.md: Whombat can't reach it any more). |
| LE-02 | **Control is told the choices whenever it knows the box** (any Link state but off): at start, on every Link move, on the owner's change, and every five minutes until it took them (device op `link.mail.set`, manager route `POST /v1/link/mail`). A failed tell is tried again; control's refusal of an email clears what was told, so the next sweep tells again. | Control must never email a box whose owner said no; a box that never reported gets no email from control at all. |
| LE-03 | **The only recipient is the Link account's own email.** `mail.send` names none; control sends to the address of the account the box is linked to (confirmed at sign-up). | A box can't use Link to email anyone else: no relay for spam, no way to mail a stranger. |
| LE-04 | **The notification email is a count.** With `notifications` on, Link on or in grace, and no mail server of the owner's own, the digest (EP-15) sends `mail.send {kind: 'waiting', count, cadence, path}`: how many things wait, hourly or daily as the person chose, and the box's page that shows them. Never who, where, what or a quote. A mail server of the owner's own wins and sends the full email as before. | Control and Mailgun learn how many, not what: the box's content stays on the box. |
| LE-05 | **Notices about the box go by email too**, when `notifications` is on and control knows the box (an ended Link included, as `security` pushes): every `ControlPush.notice` (a new device, a sign-in at the screen, the recovery kit, remote help, a foreign certificate, Link's grace, a restore that is done) sends `mail.send {kind: 'notice', title, body, path}` with the same fixed lines as its push. Not in quarantine, except the notice the restored box may send then. | These are the important ones, in fixed words that hold nothing of the person's. |
| LE-06 | **Only the box's person.** The notification email through Link is sent only for the account that claimed the box (`personAccountId`). | One person a box (one-person.md); anyone else's email would land in the owner's inbox. |
| LE-07 | **One flat `LinkMail` shape** (`kind`, `ref`, then `count` and `cadence`, or `title` and `body`; `path` either way) rather than a union: the manager's Go reads the local route's body with the generated types, which take unions only as registry objects of the same package. `linkMailComplete` says which members a kind needs; control refuses the rest. | One manager route, one schema, cross-language. |
| LE-08 | **A `ref` per email**: an HMAC under a key derived from the master key (`link-mail-ref/1`) of what the email is about and when, 32 base64url characters. Control sends a ref it already sent only once. | No id leaves the box; a retried request is never a second email. |
| LE-09 | **Email through Link is best effort.** A failed `mail.send` is logged by kind and status and not retried; the digest's rows stay claimed. | As with the box's own SMTP: mail never blocks or fails what sent it, and an email late by hours is worse than none. |
| LE-10 | **The manager forwards both ops while control knows the box** (`forwardKnown`): Link's other rules (on or grace for a count, the owner's choice, the day's limit of `LINK_MAIL_PER_DAY` = 40) are control's. | One place decides; a box rolled forward onto an older control just gets a refusal it logs. |
| LE-11 | **The web's WHOMBAT LINK section** in Settings → Notifications shows the two switches while Link isn't off and the box has the choices, after EMAIL; “See an example” unfolds what a count email says. Turning the second on reloads the bootstrap, so EMAIL (the cadence) appears. Not in the mocks: Settings → Profile's rows. | The switches sit where people look for email. |
| LE-12 | **No phone screen for it.** The phone apps have no email settings today; the person changes these on the web or asks their assistant, who may change them only after the person's yes on a card (`link.mail.set` is `ask`). | Email settings live on the web; a phone release for two switches isn't worth it yet. |
| LE-13 | **Offline means two hours** (`LINK_MAIL_OFFLINE_AFTER_S` = 7200) without control hearing from the box. A box with Link running renews its relay tickets every five minutes, so two hours is far past a restart or an update. | Calm: a reboot or an update never sends one. |
| LE-14 | **No “it’s back” email.** One offline email per quiet spell; the box coming back says nothing by email. | The person sees it's back when they open it; two emails for one blip is noise. |
