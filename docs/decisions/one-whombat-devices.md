# One Whombat: devices Whombat doesn't support yet (stream SD, 2026-10-17)

Stream decisions for `docs/implementation/one-whombat/assignment.md` §6.3, under ONE-16…ONE-19
(`docs/decisions/one-whombat.md`). Decided by the implementer (feedback-decide-yourself).

| # | Decision | Why |
|---|---|---|
| ONE-DD01 | **Our own Modbus TCP client** (`devices/modbus.ts`, no dependency): MBAP framing, FC1–4 reads, FC5/6/15/16 writes, one request in flight per connection (a queue), 3 s per request and per connect, late answers (another transaction id) dropped, exception answers in plain words (“The device refused: that address doesn’t exist on it.”). A connection is opened per call and closed after it; calls to one device run one at a time (an in-process lock per address and port). | Many gateways serve one request at a time and few connections; a short-lived connection never leaves a half-open socket on someone’s heat pump. The protocol is small enough that a dependency adds more risk than code. |
| ONE-DD02 | **Values**: `u16`, `s16`, `u32`, `s32`, `f32`, `bool`; 32-bit word order `big` (high word first, the Modbus habit) or `little`; `scale` multiplies the raw value (215 × 0.1 = 21.5). A write that the scale can’t hit exactly (21.25 at 0.1) is refused, never rounded. Readings are read in spans (same table, gaps up to 8 registers, at most 64 words); a span the device refuses is read value by value so one missing register doesn’t hide the rest. | Rounding a setpoint silently changes what the owner asked for; reading in spans keeps a 9-value read to two or three requests. |
| ONE-DD03 | **Devices are reached on the local network only.** The host is resolved once, every address must be private and pass the Vault/Connections rule (`vaultDestinationProblem`: the whole local network when it is open, LN-01, else the home network list with the port), and the driver dials exactly that address. An address on the internet is refused (“Whombat talks to devices on your local network only…”). HTTP/JSON goes through `lib/outbound.ts` under `connectionPolicy` (DNS pinned, no redirects, 10 s, 256 KiB); port 443 means https, every other port http. | Plain Modbus and HTTP must never cross the internet; one rule for every local destination keeps LN-02 (loopback, metadata, this host) closed for devices too. |
| ONE-DD04 | **Limits are generic** (`connections/limits.ts`) and keyed by a JSON pointer into a tool’s arguments: `min`, `max`, `step` (from the minimum) or `choices`. An argument the call leaves out passes; a number limit checks a numeric string as its number (a service may read `"30"` as 30) and refuses anything else. The refusal is one sentence for the agent to pass on: “Room temperature is limited to 16–24 °C, so 30 °C wasn’t sent.” | Works for Home Assistant’s `temperature`, a device’s `value` or any MCP tool alike; refusing non-numbers closes the obvious way around a range. |
| ONE-DD05 | **The profile’s own ranges stay hard bounds** in the driver (`actionValueProblem`), next to the owner’s limits (checked before the keys decide): a device action is refused outside either. | The manual’s range protects the equipment; the owner’s limit is their preference inside it. |
| ONE-DD06 | **A proposal is tested in full before anyone sees it.** `propose_device_skill` checks the profile (unique keys, a register or path for the driver, writes only to holding registers and coils, ranges in order, choices for a choice, a range from the manual for a number) and reads every reading and every Modbus action's current value on the unit; one that doesn't read refuses the proposal with what to fix (“Reading “ghost”: The device refused: that address doesn’t exist on it.”). The card shows the first six tested values (mock 3) and “and N more”. | ONE-19: no half-working card; the owner sees values that were really read. |
| ONE-DD07 | **Superseded in part by one-person.md OP-S50**: a device is a connection of the burrow, and the person decides its card and switches it on. **Devices are the burrow's (shared connections), and owners switch them on** (`burrow.manage`, people only, like any shared connection, CX-03). A member's Whombat may propose; the card and Needs you go to the people who can decide. The choices are checked against the action (a range for a number, choices for a choice or on/off); every action not chosen stays Off (“Everything else stays off.”). `switchOn: true` makes the connection live; `false` keeps the choices without making anything live; a skill already on takes new choices at once either way (tightening must count straight away). `deviceSkills.decline` = Not now. | Equipment in the house is shared; one permission model with the other shared connections. |
| ONE-DD08 | **Rewriting the profile starts again** (ONE-18): a new proposal for the same device (host, port, unit id) replaces the waiting ones (their cards read “Not switched on”) and starts from the defaults, never from the old choices. The live skill keeps running until the new one is switched on; then the same connection takes the new profile's tools, so its page, widgets and Done recently stay. Each device tool's hash includes the profile's hash, so an approval asked under another profile is refused (CX-21). | Choices are bound to exactly the profile they were made for; the connection id is what the rest of Home points at. |
| ONE-DD09 | **Undo for a device action**: before writing, the driver reads the action's current value (the reading of the same key, else its own register); a write that changed it records a change (`device.action`, “Set the heat pump’s room temperature to 21.5 °C”, “20.0 °C → 21.5 °C”) with the recipe `device.set` (old value, value set, profile hash), offered 24 h (`CHANGE_UNDO_WINDOW_S`). Undo answers at once and works in the background: it reads the device again; if someone changed it since, Whombat says so in the chat and leaves it; else the old value goes back as a new `call_connection_tool` by the same Whombat for the person who pressed Undo (keys, tier, limits, approvals again) and its own change marks the original undone. A device that can't say its value takes the write without Undo. | ONE-08; never undo over a change a person made at the unit. |
| ONE-DD10 | **Your things**: a device is `device:<connection id>` once on, `device:<proposal id>` while learning. Learning shows to the person whose Whombat proposed it and to the people who can switch it on; a device that is on shows to everyone in the burrow. Status: `ok` with a reading in the last 15 minutes, `offline` when the last try failed (line “Not answering”), `unknown` before the first; facts are the first four readings, the line the first two (“21.0 °C · 34 °C”). The icon is guessed from the name (`thermometer`, `zap`, `droplet`, `fan`, else `cpu`). | Mock 1's sidebar (“Heat pump · learning”) and Home tiles. |
| ONE-DD11 | **Needs you**: a card waiting for a choice is one item for the people who can switch it on, in the mock's words: “What may I change on the heat pump?” / “I can read it now. Pick what I’m allowed to change before I switch that on.”, button Choose (opens the chat). The card's own message says the same line. | Mock 1, verbatim. |
| ONE-DD12 | **The reader**: every 5 minutes (housekeeping), each switched-on device's readings are read, reads only; the last reading is kept with the skill (not signed: a cache of what the device said) for Home. A device whose last try failed is on Watch (“The heat pump isn’t answering”, the driver's sentence) until a reading works again. The `_read` tool answers `structured {values, text, units, errors?, readAt}` and one line per reading for the agent: a widget plots `/values/<key>`. | Home and widgets stay fresh without the AI (ONE-09). |
| ONE-DD13 | **The prompt** (“A device Whombat doesn’t support yet”, `persona/devices.ts`, personal agents only): what exists first, then the device and its manual, then `device_probe`, then `propose_device_skill`; the plain answer for cloud-only units, extra hardware or no documentation; limits are enforced, refusals are passed on in plain words. The same lines every turn (PE-02). | ONE-17, ONE-19. |
| ONE-DD14 | **Found on your network finds Modbus devices**: port 502 joins the scan; an open one is asked one read (FC3, register 0) and who it is (FC43/14); any Modbus answer, a value or a refusal, lists it as `device` at `modbus://<host>:502` with “Daikin EKRHH” as its version when it says. Hidden like any found service. Never a write. | Finding the device is step 2 of ONE-17; a refusal still proves Modbus is there. |
| ONE-DD15 | **Removing a device connection** (Settings → Connections) turns its skill off (the card reads “Not switched on”) and the reader stops reading it. | Nothing should keep talking to equipment its owner removed. |
| ONE-DD16 | **Names**: the connection's label is the profile's name without its vendor and model words (“Daikin Altherma heat pump” → “Heat pump”, the sidebar's name), its handle from that (`heat-pump`), its tools `<slug>_read` and `<slug>_<action>` (`heat_pump_room_setpoint`). Sentences say “the heat pump” (a brand name keeps its capitals). | Mock 1 and 3; short handles for the agent. |
| ONE-DD17 | **Who uses the device tools**: Whombat only (personal agents, `personal: true`), with its “connected services” read key at Allowed (personal agents hold it by default). `device_probe` is a read: logged, not signed; a proposal is a signed `device_skill.proposed` (Keys), a decision `device_skill.switched_on` / `decided` / `declined` with the choices in words. | Reads of a connection aren't signed either; what changes permissions is. |
| ONE-DD18 | **An action's unit** comes from the reading of the same key, else of the same Modbus register or HTTP path (contracts 0.80 give an action no `unit`); without one, values and limits are shown without a unit. | Contract gap, reported for 0.80.1; the heat pump profile reads its setpoint register anyway. |
| ONE-DD19 | **Words for coded readings** (mode 1 → “Heating”) come from the choices of the action with the same key (contracts 0.80 give a reading no choices). | Contract gap, reported; the mock shows “Mode · Heating”. |
| ONE-DD20 | **Builtins with tools are callable** through `connection_tools` / `connection_call`: `isCallableEntry` (`connections/callable.ts`) lets `device` and `whombat_servers` through where the other builtins (GitHub, Google, Microsoft, Website feedback) stay out. A device connection's tools are never synced from a listing: the decision writes them. | Both new builtins serve tools through the one connection path (CX-30, ONE-12). |
| ONE-DD21 | **Limits on every connection tool**: stored per tool (`connection_tools.limits`), kept when a tool's definition changes on a refresh, shown to agents in `connection_tools`, checked in `connection_call` before anything is signed (a `blocked` answer without an event) and again when an approved call runs (limits narrowed meanwhile refuse it). The server's sentence names the argument and its unit; its rules are the contracts' `checkToolLimits` (a missing argument passes, a numeric string counts as its number, steps from `min`). | One rule for Home Assistant's `temperature`, a device's `value` or any MCP tool. |
| ONE-DD22 | **Superseded in part by one-person.md OP-S50**: the person sets every connection's tool limits, each change a signed `connection.tool_limits_changed`. **`connections.setToolLimits`**: managers of a shared connection, the owner of a personal one; a shared change is a signed `connection.tool_limits_changed` (Keys: “Limited heat_pump_room_setpoint on Heat pump: value: between 18 and 22, in steps of 0.5”), a personal one account-level like its tiers; null or `{args: {}}` removes them. Feature `connections.tool_limits` is advertised. | Same shape as tiers (CX-22, CX-72). |
