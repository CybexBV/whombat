# Workstream: auth-selfhost (S-04, self-hosted phase 4)

Sign-in for a self-hosted Whombat (`docs/decisions/archive/self-hosted.md` S-04): invite-only sign-up, email
optional, invite links, host-issued sign-in links and an optional Tailscale identity. ARCHITECTURE.md,
DECISIONS.md, `production.md` and `security-fixes.md` still apply.

| # | Decision | Reason |
|---|---|---|
| AS-01 | **`WHOMBAT_SIGNUP=invite\|open`, default `invite`.** Invite-only: an email sign-in request (`auth.requestMagicLink`) for an address with no account and no pending invite stores nothing, sends nothing and answers `{sent: true, expiresInSeconds: 900}` like any other; it is even rate-limited the same (5 an hour per address), by an in-memory counter (`IgnoredRequests`, bounded, per service container), so the 6th request cannot tell accounts apart. `verifyLogin` checks the policy again before making an account (an invite may have been removed since the code was sent). The rules are pure functions in `apps/server/src/auth/policy.ts`. | S-04; no account enumeration. |
| AS-02 | **Bootstrap closes sign-up by construction.** With no accounts there can be no invites, so an invite-only instance is closed until the host's `bootstrap` script makes the owner. `open` keeps today's behaviour exactly (anyone who proves an email gets an account, also on an empty instance): the first account has no special rights, and dev, tests and demos rely on it. The test harness (`useTestServer`) defaults to `open`; the invite-only default is tested in `auth/selfhost.int.test.ts` and `auth/host.int.test.ts`. | "Open = today's behaviour". |
| AS-03 | **Superseded in part by AH-05**: an invite link joins only the invite it names. **A new account joins every burrow that invited its email**, whichever way it was made (email code, invite link, Tailscale). An existing account signing in by email still joins only the invite whose token came with the request (unchanged). | An invited person should land in the burrow, not in onboarding for a burrow of their own. |
| AS-04 | **Mail is optional.** `SMTP_URL` has no default in production (no silent fallback to a local Mailpit); outside production it stays `smtp://localhost:51025`; `SMTP_URL=off` disables it anywhere. Without mail: `auth.requestMagicLink` answers 403 `not_allowed` “This Whombat doesn’t send email, so email sign-in is off. Ask the owner for a sign-in link.” (the same for every address), invites are not emailed, and `auth.options.email` is false. | S-04. Our instance keeps `SMTP_URL_FILE` (Mailgun). |
| AS-05 | **`auth.options`** (`GET /auth/options`, public): `{email, tailscale, signup}` (`AuthOptions` in core). `tailscale` is true only for a request that arrived on the Tailscale listener, with the feature on and a `Tailscale-User-Login` header. The web login route loads it before rendering; fixture mode and older servers (404) fall back to `{email: true, tailscale: false, signup: 'invite'}`. | The login screen adapts without guessing. |
| AS-06 | **Invite links are re-derivable, not stored.** An invite's token is `inv_` + HMAC-SHA256(subkey of `WHOMBAT_MASTER_KEY` for `invite-link/v1`, invite id) (`KeyCustody.mac`); the database keeps only its sha256 as before. Owners get `Invite.link` (`{PUBLIC_URL}/login?invite=…&email=…`) in `members.list`, `members.invite`, `onboarding.get/update/complete` and `burrows.create`; members don't (the key is absent). Re-inviting keeps the same link (it no longer rotates). Invites made before this change have a random token: no link until re-invited (re-inviting upgrades them). No migration. Outside production without a master key the public dev key makes tokens derivable by whoever knows an invite id (burrow members only); production requires the key. | "Copy invite link" at any time, without keeping a secret in the database or a schema change that would collide with parallel migrations. |
| AS-07 | **Superseded in part by AH-05**: where the server sends email, a new account confirms its email before the link joins it. **Opening an invite link** (`auth.acceptInvite`, `POST /auth/invite {inviteToken, client}`): for an email without an account it makes the account, signs it in (cookie / bearer) and joins — the link is the credential, as an emailed magic link is. For an email that **has** an account it answers 409 `sign_in_required` (new error code) unless the caller is signed in as that account, which then just joins; signed in as someone else is 403. So an owner holding a copied link cannot take over an existing account. Used or removed links: 400 `invalid_code` “That invite link doesn’t work any more.” Cookie writes follow the origin rule (C-16). | Invites must work as links without email (S-04). |
| AS-08 | **Host-issued sign-in links** (`auth/host.ts`, importable; `src/scripts/bootstrap.ts` and `login-link.ts` are thin): a `login_codes` row whose `code_hash` is the sentinel `link-only` (never a code; left out of code lookups and the email rate limit), token hashed like emailed links, one use, **15 minutes** (`LOGIN_LINK_TTL_S`), landing on `/login/verify?token=`. `bootstrapOwner({email, name, burrowName, timeZone?})` runs migrations, then under an advisory lock makes the account (with the name) when the instance has **no accounts**, and the first burrow when the owner has none (time zone: the host's), and returns `{accountId, email, burrow, created: {account, burrow}, link, expiresAt}`; re-running with the same email makes nothing new and returns a fresh link; a different email once accounts exist is refused (`HostAuthError`, exit 1). The owner's link lands on `/onboarding?burrow=<slug>&step=1` until onboarding is done. `hostLoginLink(email)` is for existing accounts only. Both work with `NODE_ENV=production` and without SMTP; `--json` prints the result for the coming `whombat` CLI. Commands: `pnpm bootstrap --email … --name … --burrow …`, `pnpm login-link <email>`. | S-04, S-06 (`whombat init`, `whombat login-link` wrap these). |
| AS-09 | **Tailscale identity only on its own listener.** `WHOMBAT_AUTH_TAILSCALE=1` needs `WHOMBAT_TAILSCALE_PORT` (≠ `PORT`); the server then also listens on `127.0.0.1:<port>` (`auth/tailscale.ts`), a plain Node server whose requests and upgrades are handed to the same Fastify app, marked in a `WeakSet`. Only requests marked so may use `Tailscale-User-Login` (`auth.tailscale`); the main listener never reads it (a Cloudflare Tunnel, Caddy or the Vite proxy also arrive from loopback). Everything else behaves as on the main listener, except that `/internal/*` is always 404 there. Point `tailscale serve --bg <port>` at it and at nothing else. | S-04's security note. |
| AS-10 | **Who Tailscale lets in:** an existing account, or an email with a pending invite (the account is made, named from `Tailscale-User-Name` when it is a plausible name, and every pending invite is accepted) — whatever `WHOMBAT_SIGNUP` says; everyone else 403 “There’s no Whombat account for … Ask the owner to invite you.” Headers that are not an email (tagged nodes; Funnel traffic carries none) count as absent. A cross-site `Origin` is refused (login CSRF). | A tailnet is not an invitation. |
| AS-11 | **Login screen states** (not mocked; the sign-in frame, B-05): invite link → “Joining the burrow…” then the burrow (or the email / no-mail state with “You already have an account…” when `sign_in_required`, or the error “That invite link doesn’t work any more. Ask the owner for a new one.”); Tailscale → “Signing you in with Tailscale…” then on (refusal: the reason under the fallback state); no email → “Sign in to your burrow” with “This Whombat doesn’t send email. Ask the owner for a sign-in link, or open the invite link they gave you.” and no form; otherwise the email form as before, which now passes the invite token along. `/login?invite=` no longer bounces signed-in people away: they join as themselves. Copy lives in `LOGIN_COPY` (`LoginPage.tsx`). | Behaviour S-04 asks for, in the existing visual language. |
| AS-12 | **“Copy invite link”** (a quiet text button like its “Remove” neighbour, toast “Invite link copied.”; `components/CopyButton`, Clipboard API with a textarea fallback for plain-http origins) on each pending invite in Settings → MEMBERS and onboarding step 4, for owners. Onboarding now **creates each invite when it is added** (`members.invite`) and revokes it on Remove, so its link can be copied at once; “Open {burrow}” only sends the ones the server couldn't take. With mail on, the email therefore goes out at “Add” rather than at “Open”. Without mail step 4's note reads “Your agents are already in. This Whombat sends no email: copy each invite link and send it yourself. It opens {host}.” (`inviteLinkNote`). | S-04: links whether or not mail is configured. |

## Operating notes

- Tailscale: `WHOMBAT_AUTH_TAILSCALE=1 WHOMBAT_TAILSCALE_PORT=4401`, then `tailscale serve --bg 4401`.
  `PUBLIC_URL` must be the `https://<host>.<tailnet>.ts.net` origin people use, because cookie writes,
  `/ws` and `/collab` are only accepted from `PUBLIC_URL`'s origin (C-16). An instance reached through
  two different origins (e.g. a tunnel and Tailscale) needs one of them as `PUBLIC_URL`; the other then
  cannot write with the cookie (follow-up if wanted: a list of allowed origins).
- Any process on the host can connect to the Tailscale listener and send the header. That is inherent to
  `tailscale serve` identity headers; guarded agents' sandboxes (S-13) should not reach loopback ports.
  Leave the feature off on hosts where local processes are not trusted.

## Follow-ups

- Invite links never expire until accepted or removed (as before); an expiry would need a column.
- The mobile app still only knows email sign-in (`auth.options` is there for it; S-16).
- `whombat init` / `whombat login-link` (phase 5) wrap `bootstrapOwner` / `hostLoginLink`; `--json`
  output is the stable interface for that.

# Workstream: auth-admin-hardening (instance admins, review fixes)

The orchestrator's decision to add **admins of this Whombat**, and fixes for independently verified review
findings on sign-in, invites, the Tailscale listener and agent working directories. Where an AH decision
contradicts an AS decision above, AH wins; the operating note above about local processes and the Tailscale
listener is superseded by AH-10. Migration **0009_instance_admins** (`accounts.admin_since`,
`accounts.email_verified_at`).

| # | Decision | Reason |
|---|---|---|
| AH-01 | **Admins of this Whombat** (`accounts.admin_since`, null = not one). Only admins create burrows (AH-03) and connect GitHub through gh (`github.connect`, replacing G-04's “the first burrow claims the connection” rule; `github.status.canConnect` = owner ∧ admin ∧ GitHub not off; picking, adding and syncing repos of a connected burrow stay with its owners). Changing an agent's working directory, checkout or access (`set_agent_runtime`) needs an owner of the burrow (the `burrow.manage` key, members still get the signed Blocked event) **who is also an admin**: otherwise 403 “Only admins of this Whombat change where an agent works.”, nothing written. `Account` gains `isAdmin` and `canCreateBurrows` (optional in the contract for older servers), so session, me, sign-in and profile answers carry them. Web: Configure agent → WORKSPACE, “Connect GitHub” (settings, onboarding step 2) and “Start a new burrow” (burrow menu) are disabled with one line: `ownerAdminLockedReason(action, {owner, admin})` (“Only owners …”, “Only admins of this Whombat …”, “Only owners who are admins of this Whombat …”) and `BURROW_CREATION_LOCKED`. | Owning a burrow cannot guard what reaches the host: anyone who may create a burrow owns it, and trusted access or the host's gh are host-level power. |
| AH-02 | **Who is an admin at first.** `bootstrap` / `whombat init` makes its account an admin (and verified, AH-05). Migration 0009 marks one account of an existing instance: the earliest-created account that owns a burrow (a person principal with role owner), else the earliest-created account, ties by id; nobody on an empty instance, nothing if an admin exists. The seeded world's owners are admins (it stands in for a bootstrapped instance). | Accounts are rows with a `created_at` (set when made) and random ids. On our instance the earliest account is the maintainer's and owns Burrow HQ; preferring an owner avoids crowning a member-only early account (say, an open instance's first sign-up that never made a burrow). |
| AH-03 | **`WHOMBAT_BURROW_CREATION=admins\|anyone`**, default `admins` (`anyone` in development, AH-12). `burrows.create` otherwise answers 403 “Only admins of this Whombat create burrows. Ask someone to invite you to their burrow.” (pure rule `mayCreateBurrow`, policy.ts). An account that may not create burrows gets **Join a burrow** at `/onboarding` instead of step 1 (not mocked, B-05: the sign-in frame of AS-11 — kicker WELCOME, “Only admins of this Whombat create burrows. Ask someone in a burrow to invite you, then open the invite link they send.”, Clover's tip, “← Back to your burrow” when it has one, “Sign out”); resuming a burrow's onboarding (`?burrow=`) is unchanged. The test harness sets `anyone`, as it sets open sign-up. | The orchestrator's decision; joining by invite is the path that already exists. |
| AH-04 | **Admins are granted on the host only**: `grantAdmin` / `revokeAdmin` / `listAdmins` (`auth/admins.ts`, exported by `@whombat/server/host`), `pnpm admin grant\|revoke\|list [email] [--json]`, `whombat admin grant\|revoke\|list [email] [--json]` (Whombat running or stopped). Existing accounts only; never the last admin (“x is the only admin of this Whombat. Grant admin to someone else first.”); one change at a time (advisory lock). **Not a signed event**: a grant belongs to no burrow and nobody acting in one (the host shell is not a principal). The command prints what it did, the process logs an info line (`admin of this Whombat granted` / `revoked`), and the server logs the admins at every start (a warning when there are none). A future in-app grant by an admin would be a signed event in that admin's burrow. | A signed audit event needs a burrow and an actor; a synthetic “host” principal in every burrow for this is out of proportion. |
| AH-05 | **An invite link proves nothing but its one invite.** It accepts only the invite it names, never every pending invite for the email. Signed in as the invited email: joins. An email with an account: `sign_in_required`, `details: {email, account: true}` (AS-07). **A new account on a server that sends email: `sign_in_required`, `details.account: false`** — the login page shows the email form with “Confirm it’s your email first. We’ll send a sign-in link and a 6-digit code, and you’ll join the burrow right after.” (`LOGIN_COPY.emailSubConfirm`) and the code makes the account and joins. Without email the link still makes the account (S-04), but only in that burrow and **unverified** (`email_verified_at` null), and an account made meanwhile (the invitee verifying a code, a second holder of the link) is never handed out. Proving the email later (an emailed code or link, a host login-link, Tailscale) sets `email_verified_at`, **revokes every session and API token the account had** (their sockets close) and joins the burrows that invited it. Tailscale still accepts every pending invite (AS-10): tailscaled vouches for the identity (AH-10). Migration 0009 counts every existing account as verified. | Supersedes AS-03 for links and AS-07's “the link is the credential” where mail exists: a burrow's owners hold its links (AS-06), so opening one must not reach other burrows or keep the account from its owner. |
| AH-06 | **Codes and the sign-in limit don't tell addresses apart.** `auth.verify` by code answers every failure the same — wrong, expired, used up, or never sent because the address has no account: 400 `invalid_code` “That code doesn’t work. Check it, or send a new one.” (`CODE_REFUSED`), and takes an attempt either way (a no-op without a code). `SignInThrottle` (was `IgnoredRequests`) counts every address, real or not, and never forgets one inside its hour: when 100 000 addresses are, new addresses are refused, all alike. The stored-code limit still bounds guessing across restarts. Left: a restart empties the throttle (for every address alike, while stored codes still limit real ones for that hour), and the send path writes one row the ignore path doesn't (the email itself is sent in the background either way). | Six wrong codes told an address with an account or invite from one without (“Too many wrong codes”, “has expired”), and flooding 10 000 addresses evicted an unknown address's count. |
| AH-07 | The request log redacts `invite` (and `invite_token`, `inviteToken`) query values. | Without email a join link signs a new account in; opening one logged it verbatim. |
| AH-08 | **Re-inviting with another role replaces the invite**: the pending one is revoked, a new one (new id, so a new link) is made and signed “Invited x as an owner. The earlier invite link no longer works.” (`member.invited`, payload `replaces`). The same role keeps the invite and its link (AS-06). | A link already shared never gains a role; no change to the link MAC, no column, and the change is in the log. |
| AH-09 | The `/internal/*` 404 (Tailscale listener; tunnel in production) and the cookie-write origin check look at the **route the request matched** (`routedPath`: `req.routeOptions.url`, else the decoded path), not the raw URL. | The router decodes percent-escapes, so `/%69nternal/runner/claim` reached the runner route and `/%61pi/v1/…` skipped the origin check. |
| AH-10 | **Tailscale identity only from tailscaled's connections.** For each connection it accepts, the Tailscale listener finds the owner of the peer's socket in `/proc/net/tcp` and `tcp6` (the row whose local end is the peer's address and port and whose remote end is ours) and honours `Tailscale-User-*` only when that uid is `WHOMBAT_TAILSCALE_PEER_UID` (default 0: tailscaled runs as root) and not the server's own; and not when `X-Forwarded-For` (which `tailscale serve` sets to the client's tailnet address) is one of this machine's own addresses — a local process going out through the tailnet name would carry the machine owner's identity. `/internal` stays 404 there whoever connects. Startup warns when this can't work (no `/proc/net/tcp`, or the server runs as tailscaled's user). Tested with a fake `/proc` reader. | Agents run as the server's user on the same host and could send the header. A Unix socket doesn't help (the same user can connect to it), and Tailscale's whois can't see through a loopback hop; the kernel's socket table can. Linux only (S-01). |
| AH-11 | **No working directory in or above Whombat's secrets** (`resolveWorkdir`, the one check of server and runner): refused when it is or contains `WHOMBAT_HOME`; is in or contains a credential path of the guarded sandbox (`credentialPaths`: gh's config, `~/.ssh`, git credentials, `.netrc`, `~/.config/whombat`); or is or contains the directory of `WHOMBAT_ENV_FILE` or of a `*_FILE` secret (`WHOMBAT_SECRET_DIRS`, which the server's `loadConfig` fills; below such a directory is allowed, as an env file may sit in `~`). A path counts as written and as its realpath. So `~` is refused under the default roots: “~ contains Whombat’s own directory (~/.whombat).” | Rather than allow `~` and lean on the sandbox's deny-list: a guarded Codex agent's writable root is its working directory, and a check that holds whatever sandbox (or none, for trusted agents) runs is simpler to trust. |
| AH-12 | **Development signs up openly.** `WHOMBAT_SIGNUP` defaults to `open` and `WHOMBAT_BURROW_CREATION` to `anyone` when `NODE_ENV=development` (a checkout's `pnpm dev`); tests and production keep `invite` and `admins`. Outside production an ignored sign-in request is logged at info with the reason. | AS-02 said development relies on `open`, but only the test harness set it: `pnpm dev` answered “Check your email” to a new address and nothing came, with nothing in the log. |

### Follow-ups

- Runner: `hostFromEnv` doesn't fill `WHOMBAT_SECRET_DIRS`, so at run time the runner checks `WHOMBAT_HOME` and
  the credential paths but not its env file's directory; `secretDirsOf(env, keys)` is there for it.
- Tailscale Q-encodes non-ASCII names (`=?utf-8?q?…?=`); `tailscaleName` doesn't decode them yet.
- No screen lists or manages admins; granting is host-only (AH-04).
- The mobile app ignores `isAdmin` / `canCreateBurrows` (it has no admin-only controls yet).
