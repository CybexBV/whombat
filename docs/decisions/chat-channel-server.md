# Chat — the server's part (stream S, 2026-10-18)

Stream S of `docs/implementation/chat-channel/assignment.md` under `chat-channel.md` (CHT-01…CHT-11): everything
server-side, in the assistant shell only (`WHOMBAT_SHELL=assistant`); the crew shell is unchanged. Contracts 0.93.0
(CT-440…CT-448), migration 0116.

| # | Decision | Why |
|---|---|---|
| CHT-S01 | **Migration `0116_chat_channel`** (expand): `messages.subject_kind/subject_id/subject_name` (a thread's subject, on its first message), `changes.thread_root_id` (the chat thread a change was made in), `burrows.chat_fresh_start_at` and two partial indexes on `messages` (a room's top level by `coalesce(last_reply_at, created_at)`, and by subject). The fresh-start mark is a new column, not an event lookup: no once-per-burrow marker existed, and `events` has no index by type. Existing burrows read null; the column's default `now()` marks every burrow made since, so a new burrow (or a restored one) never has its first chats emptied. | One expand migration with everything the stream stores; old binaries ignore all of it. |
| CHT-S02 | **The rooms** (`chats/rooms.ts`): a person's **Chat** is their default DM with their own assistant (`task_key IS NULL`, the agent's `owner_id` is the DM's person), **Feedback** the `dm` row with `task_key = 'feedback'` (`FEEDBACK_ROOM_KEY`), titled “Feedback” with `chat_retitled_at` set. `threadedRoom` — a channel, or in the assistant shell one of those two rooms — is the one rule `postMessage` (a person's top-level message opens its thread, CH-01's `opensThread`) and the opening turn's earlier thread (CH-03) read. Task chats, DMs with team agents and the crew shell stay flat. | One predicate for “answers in a thread”; the dispatch's coalescing (CH-02), `turnThread`/`cardThread`, approvals, the Vault and connection asks already follow the dispatch's thread, so nothing else needed a Chat case (a test asks for a key in a Chat thread and finds the card under the person's message). |
| CHT-S03 | **The runner opens a thread wherever the server does**: `prompt.ts` shows the room's recent messages before a thread whose root is the trigger, for any conversation kind (it was channels only). The dispatch context carries no shell; a thread rooted at the trigger is how the server says so. | No contract field for “threaded DM”; the shape already says it. |
| CHT-S04 | **The turn's topic per thread** (`chats/read.ts` `turnTopic`, `title.ts` `roomTopic`): “Chat with Mara: each of their questions is a thread.” and, in a thread about something, core's `chatThreadSubjectLine` (“This thread is about the server pve-02.”) with the thing's id for `pin_widget` (CP-14). Feedback says each report is a thread. A task chat keeps “Task chat “…”.”. For the agent only, in the turn's request (not the cached prefix). | CHT-05 without a chat per task. |
| CHT-S05 | **`chats.start` in the assistant shell** posts the text as a top-level message of the caller's Chat (`ensurePersonalDm`) with the resolved subject on it, signed as the message (`message.posted`, no `chat.started`), idempotent by `clientId`; it wakes the assistant (`dm`) in the new thread. The route answers `{conversation: Chat, message}`; `Conversation.chat` stays absent for Chat. The crew shell still makes a task chat. | CHT-06; an older app's “new chat” lands in Chat. |
| CHT-S06 | **`chats.list`** (assistant shell, `rooms`): the Chat (`default`, `room: 'chat'`) and the Feedback room (`room: 'feedback'`, title “Feedback”) once it exists; task chats only with `archived=true` (`room: 'task'`). The Chat's `title` stays the assistant's name for older apps; Chat's apps name it by its room. | CHT-07; older apps still read a sensible list. |
| CHT-S07 | **`chats.threads`**: the caller's room's top-level messages (deleted ones left out), newest `coalesce(last_reply_at, created_at)` first, then id; `before` is strict (`lastAt < before`) and `next` is the page's last `lastAt` while there are more. `text` is the first line without Markdown marks (≤ 200), “A file”/“n files” for files only. `working`: the room's assistant has a turn queued, claimed or running on that thread. Every top-level message is a thread, the assistant's own posts too. | CT-442/CT-443. Two threads with the same millisecond across a page boundary could be skipped; at one person's pace that doesn't happen. |
| CHT-S08 | **The Feedback room is shared by all of a person's integrations** (`ensureFeedbackRoom`): created by the first save, by the boot move or by an assessing automation, with a signed `chat.started` (`room: feedback`). Each integration that starts posting there (made, or moved by a save) gets the assistant's line naming it (LM-F05's words, “instead of #…” from a channel). The room is never renamed or archived (`isTaskChat` leaves it out, so `rename_chat`/`archive_chat` answer `not_found`), and `retitleFeedbackChat` doesn't touch it. An integration's own chat from before Chat (`fb-…`) still reads as a destination until it moves. | CHT-03: one room for all sites; each report's root names its site. |
| CHT-S09 | **The boot step `moveFeedbackToChats`** moves every integration not posting in a Feedback room — a channel (the shell shows none) or its own `fb-` chat — to its person's Feedback room, as LM-F09 did (same command, person, signed `feedback.integration_moved` with `movedFrom`, the assistant's line). The earlier reports stay where they were. | Reports never land where nobody looks. |
| CHT-S10 | **Automations: the run's room is resolved in `createRun`** (`automations/rooms.ts` `runRoomOf`), for every way a run starts (events, schedules, webhooks, Run now, tests): in the assistant shell, when the given room isn't the publisher's own Chat or Feedback room, the run is in their Feedback room if the recipe assesses (`recipe.job === 'assess'`, made when missing), else in their Chat; a thread it continues stays only when it is in that room, else the item's earlier thread there (`itemThread`). A skipped (blocked) run keeps the given room. The crew shell, a publisher who isn't a person with an active assistant, and published definitions are untouched. | “Resolved when a run posts” at the one place a run's room is set: steps, notices, visibility and later runs about the same issue all read `run.conversationId`, so they agree. |
| CHT-S11 | **The fresh start** (`chats/fresh-start.ts`, CHT-04) runs at boot right after every person got their assistant and before the crew's hand-over, the feedback move and the welcomes, so nothing posted at that start is removed: per burrow with the mark unset, one commit `chat.start_fresh` signed by the first owner removes the messages of every active personal assistant's Chat and task chats (the Feedback rooms and channels untouched) with `removeMessages` — the removal factored out of `clear_conversation` (which still refuses non-channels) — keeping `threadsWithWork` and every feedback report's thread in them, archives the task chats, sets the mark and signs one `chat.fresh_start` (Messages, counts only: chats, removed, kept, archived). Frames as for a clear (`announceRemoval`). Seeded burrows are skipped; a burrow without an owner waits. Runs once: the mark, under the burrow row's lock. | John: “Clear all existing chats so we start fresh”; the channel clear's guarantees for every side table. **Production**: this empties everyone's chats on the box it reaches — John decides before a production deploy. |
| CHT-S12 | **Links to threads** (CHT-08): `chatPlaceHref` (`domain/links.ts`) gives `/chat?thread=<root>` (or `/feedback?thread=`) for a place in a person's room, the room itself at its top, `/chats/<id>` for a task chat. Needs you's questions in a room wait until the person writes **in that thread** (a task chat keeps “any later message”) and Answer opens the thread; a change records the turn's thread (`recordChange` reads `turnThread` when not given) and links to it (the room when made at its top); a device skill's “Choose” and “Open the chat” open the proposal card's thread. Watch's investigate and the things' ask keep their links (the client calls `chats.start`). | Every place that opened a task chat opens its thread. **Working on** keeps `conversationId` only: no screen on the web or the phone shows it any more (only the client's unused `workingOn` model), so a `WorkingTask.href` isn't worth a contracts 0.93.1 (the lead, 2026-10-18). |
| CHT-S13 | **Home still reads task chats that aren't archived** (Needs you, Working on, its chats list): after the fresh start there are none, but one an older app brings back keeps its questions and plans visible. Only `chats.list` hides them (CHT-S06). | The smaller change; nothing is lost if an old chat comes back. |
| CHT-S14 | **The assistant shell's assistant isn't served `set_chat_title`** (`toolFitsTurn`: a personal agent's `teamWork` turn), and its prompt drops the title line: “In Chat each question the person asks is its own thread …” replaces “A chat is about one task … set_chat_title”. The command stays for the crew shell's task chats. “Dashboard” replaces “Home” in its lines and in the widget limit's words (“The Dashboard has 12 widgets already.”). | CHT-11; nothing to name in Chat, and a tool it may never use costs prompt. |
| CHT-S15 | **Chat's unread badge counts top-level messages, as a channel's** (unchanged): the assistant's own posts (an automation's result, a briefing) raise it; its answers are thread replies, which reach the person by the thread's reply notification and the DM's agent updates. Counting replies would need clients to mark a room read by its newest reply, which they don't (their read mark is the newest top-level message), so a badge would never clear. | Left for the apps to show a thread's new replies on its root (the reply row). |
| CHT-S16 | **`chat.channel`** is implemented and advertised only while `WHOMBAT_SHELL=assistant` (with `shell.assistant`); the release manifest (`runtimeFeatures()` without a shell) lists it as code-level support. | CHT-10, ONE-DW17's pattern. |
| CHT-S17 | **Undo's ask in Chat goes into the thread the change was made in** (`ask_to_undo_change`), while that thread is still there, else it starts its own; the assistant is woken in that thread. A task chat stays flat. | HR-03's ask and its answer belong with the change, not loose at the top of Chat. |
