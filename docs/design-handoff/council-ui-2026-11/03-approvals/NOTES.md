## What to review

Open index.html through a repository-root static server. Choose each of the five kinds, card/details/native, theme and phone platform. The left side is an actual shipped web fixture capture, or an explicit native GAP; the right side is an interactive static proposal. “Open the mockup at full size” gives the intended component viewport. Review labels outside the component are editorial, not product UI. Answers in the static document never submit anything.

The PNG set uses desktop 1440×900 and phone 390×844, Chromium, en-GB, Europe/Amsterdam, scale 1. All proposals use packages/tokens/tokens.css, the bundled Bricolage Grotesque / DM Mono, and the production operator avatar selected by the fixture’s face. There are no invented component colours, shadows, fonts or radii. PNG compression is lossless. The code/command and mail/key pairs share contact sheets to avoid separate pictures of every proposal. All five kinds still have separate full-size live mockups. The long email picture is scrolled into the message; the command picture shows its wrapped command. Both keep the answers in view.

The “before” pictures in ../01-groundwork/png/ were read first. The everyday Chat and ApprovalDetails states were recaptured before authoring the proposal. Additional pending kinds are captured here as before-card-* and before-details-*. **Ownership assumption:** the instruction to write only in this step’s folder takes priority over adding files in another task’s groundwork folder. Nothing in 01 is changed. The before viewer links to this folder’s supplemental captures. No existing picture is renamed or replaced.

## Reading order and focus

Before the buttons on the everyday web card, a screen reader reads: Approval: [action title]; the title; {assistant} needs your OK; What will happen and its whole supplied action/restart sentence; Permission used and the catalogue name; Yes, tonight means [full date/time/zone]; Conditions, “A person says yes · not yet”, you. It then reaches Yes, now; Yes, tonight; No; Don’t ask again for pve-02…; Technical details. No hover text is necessary. The action text, permission and time are plain readable text, not accessible-name-only content.

Command: title → reason → permission → exact full command named “The command” → conditions → scope buttons. Deploy: title → exact action → supplied steps → permission → all three named conditions with met/not-yet and notes → its existing CTA(s). Mail: title → From/To/subject in the action → permission → copy state → evening time → conditions → full message on details/native (or Technical details on the web card) → answers. Key: title → key and granted tier in the action → requested permission → condition → grant/decline labels. The actual native header precedes these: avatar named for the helper, status, asker/place/time, question. Content and footer are separate regions, so VoiceOver/TalkBack can traverse everything before entering the answers. A sticky footer does not make it first in accessibility order.

Proposed focus after answering stays on the same approval’s updated result, focused programmatically as a status paragraph with tabindex −1; the result is announced politely, then Undo if allowed. The card does not vanish, fold, reorder or navigate away. On native, the implementation should use the equivalent accessibility-focus call to that result after the query changes; this HTML does not prove VoiceOver behavior. A command’s yes is not offered an Undo that core forbids. Undo returns to pending; implementation should return focus to the first answer. The static Undo reload is only a fixture reset, not a claim of implemented native focus restoration.

Lasting yes: opener → named modal/dialog with its description → Keep asking initially focused → Let {assistant} do it. Focus is trapped by HTML dialog. Cancel/Escape returns to the opener; confirm focuses the updated result and clears the pending choices. Native implementation retains the platform alert (iOS alert / Android Material dialog), not an HTML imitation. Closing approval details returns to the card’s Details opener in the app; Back from native returns to the originating Inbox row or Review and answer door. Static Back/Close go to the gallery, and Settle in the surrounding study is a navigation placeholder; they do not claim to implement the app router or settling.

Technical details uses native HTML details/summary, with expansion state exposed by the browser. Enter/Space opens it; focus stays on the disclosure; Tab can reach the full command/message region. Closing returns no unexpected focus jump. Native implementation keeps its existing accessibilityState.expanded. Long command/email content is selectable/readable without truncation. No accordion contains the approval itself.

All web buttons/disclosures are at least 44 CSS px. Phone footer buttons are at least 48px, meeting both the 44pt iOS and 48dp Android design targets at 1×. Native Back is 44pt iOS, 48dp Android. Large text above 1.3 keeps AP-7409’s one-answer-per-row wrapping; large code/key layout order follows the shipped phone behavior (Approve first at large scale). The HTML stress capture doubles body, title, labels and answer text to 200%; it is **not evidence of either platform’s largest supported accessibility size**. The full native largest-text check remains a GAP. Nothing reorders under a finger; mock data is frozen and no live sort exists. An eventual new quiet-hours value must not silently change the time being reviewed while the person answers.
