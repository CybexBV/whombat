## Screen readers, focus, expansion and touch

The HTML specifies intended native behavior; it is not a VoiceOver/TalkBack certification. Screen-reader order is header and named actions → page/body or combined message → separate named card → status/time → title/reason → choice/current step/selected-work commitment → primary → secondary → Details → reply composer → tabs where present. Tabs expose names, selection and count in their accessible label; the painted badge is decorative, so it does not announce twice. OS status symbols and SVG marks are decorative.

Examples: “Back to Chat” from a card, “Back to Overview” from Home Assistant; “More for Home Assistant”; “Copy the address 10.100.0.131:8123”; “Ceiling light”, switch, checked; “Lower Thermostat” / “Raise Thermostat”; “Select task 2: Show how full the space is”, checked; “AI for every task”; “Change AI for task 2”; “Read Claude Opus 5.5’s answer”; “Open pull request for Taller buttons and switches”; “More for Taller buttons and switches”. Headings and labelled card regions give context to repeated Details/answer controls. Health retains Not working · Needs a look · Learning · Connected. Thread stage still derives from flags in the shipped precedence Waiting for you > {assistant} is working > Handed over > Settled, plus unread New reply; no failed thread flag. “Needs you” is the Inbox group. Settle is not removed by these proposals; these particular excerpts expose the existing Settled door.

Keyboard/switch focus follows DOM reading order. A checkbox’s whole 44/48 square is the target; its 20px glyph is not the target. Each checkbox has its own name and state; no nested action is placed in its label. Per-task AI editors follow the main actions inside Details, but the effective AI is readable **before** Hand over. These facts do not depend on opening Details.

Disclosures open in place and keep focus on their summary. Completed/research/review cards retain step 04’s initial folds; the PNG inventory includes starting and Details-open versions of every state. Council “Read the answers” opens Details and keeps focus on its action. Merged task rows can be expanded independently; PR/branch/More/pictures remain inside the footer Details. Digest heads-ups stay folded. Connection shows “Show 5 heads-ups” folded initially, plus an open rendering with all five entries. Home Assistant’s four problems remain visible above that disclosure.

Preview dialogs use native HTML dialog focus containment, Escape/Close, and return to their exact opener. Change something focuses the same reply field. Stop and the door action retain explicit confirmation. Actual navigation/return-stack behavior and action execution remain the existing app’s responsibility. No new permission, confirmation or commitment fact is removed.

Toggling a task updates its summary and Hand over count only; the task elements retain order and identity. AI editing updates the effective-choice summary without reordering. Switch guesses do not move tiles. No live sort or refresh runs while a finger is down; there is no network in the study. Implementation must retain that behavior.

All **drawn** targets meet the measured minimum in Chromium: iOS 44×44 CSS px representing 44pt, Android 48×48 CSS px representing 48dp, web 44×44. The Home Assistant host row measures **354×44 / 354×48**. Header buttons, short Log/More links, steppers, checkbox labels, AI arrows, disclosures and picture links are included in the census. This is a design requirement for every Android/iOS interaction, not a claim that changing CSS implemented React Native hit boxes across the app.

200% text examples cover council final, editable delegation, Overview and Home Assistant for all three profiles and both themes. Controls become one column; server figures stack; labels, facts and buttons wrap; all content remains reachable vertically with no horizontal page overflow. The commitment continues above Hand over even when several scrolls are needed. These are **200% HTML reflow drawings**, not OS accessibility-size screenshots. Step 08’s actual iOS AX5 / Android largest screenshots remain the before evidence; the shipped native text cap is not repaired by documentation.
