## Accessibility and interaction handoff

- **Reading order:** back → thing identity/status → host/address/check facts → More detail → Ask/Open/menu → tabs → local read problem and recovery → research title/assistant words/step → current notices → heads-up fold → retained content. In the current drawing the local problem precedes tabs visually/DOM, matching ThingPage's existing placement; a built implementation should keep that stable. Usage: Settings groups/back → Usage title/scope → read problem if any → prepared time/timezone → Refresh → three windows → estimate caveat → More. Native Settings: title → five groups → main tabs. Review annotations are named separately, outside product copy.
- **Names:** status pill reads “Needs a look” beside Home Assistant; decorative dot is hidden. Address button: “Copy address 10.100.0.5:8123”; Open: “Open Home Assistant”; ellipsis: “More for Home Assistant”. Notice actions include their notice title in the accessible name, so repeated Ask/Show controls are distinct. Read retry names its scope, e.g. “Try reading usage again”. Each total is an article named by window, tokens, tasks and cost; native implementations should expose it once as one accessible unit. Avatar name comes from the same assistant helper. The screenshot-backed shell/form is illustrative evidence, not an invented keyboard/assistive-technology implementation.
- **Focus and return:** DOM order, visible brand focus rings, real buttons/links/details. Read retry keeps focus and announces Refreshing politely; static prototype does not fake success. In a built version, if the retry disappears after a successful read, focus moves to that section's heading. More detail and heads-up expansion keep focus on their summary; collapsing returns nothing to the page top. Ask opens the existing thread/Chat with its origin retained; Back returns to the initiating control and scroll position. Native iOS edge back and Android predictive back remain as shipped, closing an open sheet before the screen. Mock review dialogs trap focus, Escape/Close dismisses them and focus returns to the opener; all eight platform/theme journeys were exercised.
- **Touch sizes:** native iOS 44pt minimum, Android 48dp minimum (represented as CSS px in drawings), including header back/address, tabs, Ask/Open, notices, folds and retry. Targets grow for wrapped text; no compressed invisible action beside a full row. Desktop controls keep their established size. Gallery selects/links styled as buttons are at least 44px. Native hit slop and system metrics are still native-verification GAPs.
- **Expanded behavior:** all six heads-ups unfold **in place** after the three current lines, with their own original Show/Ask destinations; no action is executed by expanding. The keep version opens its four remaining lines. Technical facts, diagnostics and number explanations each have their own named fold. Read failures do not clear old values, replace them with skeletons or move rows. No-copy is distinct from a legitimately empty result. Live values keep the same order. Quiet/ignored rows would be last with Undo; none are fabricated here.
- **Largest text:** 390px drawings exercised at 200% root text in both themes for all three screens and both native phone platforms, plus phone-width web: no page-wide horizontal overflow; actions stack, prose wraps and Usage tiles become rows. Tabs scroll within their own line rather than reorder. This is a drawing-layout check, **not** proof of the largest iOS/Android accessibility size, VoiceOver/TalkBack, keyboard or safe-area behavior. Those remain GAPs.
- **No reorder under the finger:** sidebar pixels retain order. Notices retain shipped worst-first current order and fixture order within heads-ups. Expanding adds rows below the opener; refreshing never sorts/moves them. Usage windows remain Today → 7 days → 30 days and never rearrange on new values.

## Measured WCAG text contrast

WCAG sRGB relative luminance, `(lighter + .05)/(darker + .05)`, threshold **4.5:1 for every pictured text size**. `before.json` records actual composited pairs; `verification.json` records new DOM pairs and explicit gradient measurements. Solid scan is the groundwork's scanner. Gradient coverage samples **257 positions** between the computed opaque CSS endpoints (9%/3% warn mixed with sf); the darkest/least favorable point is retained per text foreground. The primary button is a separate opaque btn/btnfg pair. The scanner otherwise excludes gradients, images and SVG text; these explicit measurements close the research-text gap, not a whole-image accessibility audit.
