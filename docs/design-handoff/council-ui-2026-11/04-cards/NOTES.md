# Shared chat card layout

## Scope, entry points and assumptions

Design mockups only, for **web, native iOS and native Android**. No app code, tests, tokens, decision documents or TODO changed. Approvals belong to 03. This folder covers the card families explicitly listed in the brief; it does not redesign the Chat shell, Inbox, service pages, settings or automation screens owned by the other steps.

- Open `index.html`: choose any card, web/iOS/Android, starting/expanded state and light/dark. Shipped evidence and the proposal sit side by side. Open directly from disk; no server is needed.
- `mockup.html`: every starting state, then an expanded example of every folding card, the council’s answers/plan, digest heads-ups and delegation’s finished rows. Add `?platform=ios` or `?platform=android`; `&theme=dark`; `&large=1` for the text-size study. `?card=plan` opens one card.
- `mockup.html?decisions=1`: labelled alternatives beside shipped evidence. The first agreement round with two agreements and one request for changes is explicitly historical, not the final verdict.
- `png/after-{web,ios,android}-{light,dark}.png`: six compressed overview pictures at exactly 1440×900 or 390×844. `png/decisions-…`: full-height contact strips so each decision alternative is reviewable. Every starting/expanded state is in the HTML, rather than 100 separate committed PNGs. Individual card viewport PNGs are retained locally under `.whombat/shots/`.

The brief asks to add missing before pictures to `../01-groundwork/png/`, and also says to write **only** in this step’s folder. I kept that folder boundary: the four `png/before-…` atlases here supplement, and link back to, groundwork. Nothing in 01 is edited. The before/after selector uses exact card crops without resizing; `before.json` records the viewport, route, text and crop coordinates for every image.

The only assumption about new copy is that plain summaries may paraphrase existing facts. No new capability, consequence, measured duration, recommendation, severity or freshness is claimed. Unknown card times display `—`, read as “No time recorded”; they are not filled from the capture clock.

## Shared anatomy and decision boundaries

Each proposal has: mark + status word + card family + time; a plain title; one sentence saying what happens and why; any information needed before acting; a fixed footer containing the main action, at most one secondary action and Details. Hand over’s AI arrow is part of its split main action. On phone that split action takes the first footer row; Not now and Details stay together below. The footer is in document flow, never fixed over the conversation.

Branches, file paths, pull request numbers, merge machinery, code, checks’ technical names and score grids go in Details. **Retained-decision exception:** the main handed-over delegation keeps the shipped per-task Pull request link and More menu, with pictures under their own disclosure (AP-7701, AP-7731). The labelled delegation alternative moves those rows into Details. Effective AI and dependencies stay visible before Hand over in both versions. Exact care-plan steps remain visible because those are the commitment, including servers, backup destination, times and retention.

Plans name the current step, or the step waiting for the person, before the footer. The count alone is never the explanation. Failed checks, paused work, unanswered members and unselected tasks retain readable words; there is no group opacity or disabled-text fade. A check failure uses neutral words: it is a card result, not a red thread flag. Red is reserved for a thing that is not working; there is no new red frame or second loud cue on these cards.

No thread stage is inferred from a card’s tone, elapsed time or local failure. A surrounding thread uses only its shipped flags, in order: `waiting` → **Waiting for you**; working → **{assistant} is working**; `handedOver` → **Handed over**; otherwise **Settled**, with unread adding **New reply**. “Needs you” remains an Inbox group. These card-only documents introduce neither a `failed` flag nor new thread badges. Settle stays in the existing thread/navigation surfaces, subject to the shipped restriction while work is handed over (DLG-31, AP-7706, AP-7735).

Read and preserved: `ui-refresh-*.md`, `quiet-notices.md`, `needs-you-list.md`, `handle-it.md`, `command-safety.md`, `phone-refresh-*.md`, the design-handoff README, `card-settle.md`, council web/phone, delegation web/phone and `delegate.md`. The full council stays a card in both states (AP-7620, AP-7640); the retained final version keeps its score table and last answers (AP-7626, AP-7718). On phone the table keeps member names fixed, scrolls rounds independently, and starts on the latest round (AP-7644). The main editable checklist keeps its AI chips and global split action (DLG-32…34, AP-7738…40).

## Access, focus and touch

Reading order: card status and time → title → reason → current step or full choice/commitment → main action → secondary action → Details and its contents. Native message author/time/body remains its own accessible element; the card is a separate named region (AP-7410). Marks are decorative because the adjacent word carries the status. In implementation a live change announces its short state politely once; it must not re-read a whole score table or every row.

Specific accessible names: “Plan: Invoice PDF export”; “Run: Address review”; “Select task 2: Show how full the space is” with checked state; “AI for task 2: Claude Opus 5.5 · Extra high”; “AI for every task”; “More for [task title]”; “Council scores by round” with row/column headers; “Read its answer” in the named member row; “UniFi username” / “UniFi password”; “Open source” in its numbered source row. Native labels should include the enclosing member/source in those repeated controls. Unknown time reads “No time recorded”, not “dash”. Score-table member names remain fixed while rounds scroll.

Keyboard focus follows the same DOM order. Editable checklist focus visits task 1’s tick and AI, then task 2’s tick/AI, and so on, **before** Hand over, the global AI arrow, Not now and Details. On handed-over cards, a row’s Pull request, pictures and More follow its state. Native screen-reader order is the same; AI chips are siblings of checkboxes, never nested inside them. Footer order stays main → secondary → Details even when it wraps.

Details is a real disclosure; opening does not navigate, reorder or move focus. A main action explicitly named Read… can open that content in place and retains focus. Navigation actions retain their existing destinations (Open plan, Open run, Vault, connections, search, PR/T3 Code); this static file does not execute them. Closing a dialog/menu returns focus to its exact opener; Escape cancels it. Change something focuses the existing thread reply field and returns to the action if cancelled. After a real guide answer replaces an input/action, focus goes to its answer row, as shipped. Stop keeps the shipped confirmation. The preview’s extra check-the-work dialog is only a demonstration; it is **not a proposed new app confirmation** before Hand over.

Minimum targets: **44×44 CSS px/web and 44×44pt/iOS; 48×48dp/Android**, including the checkbox label, More, disclosure and the split AI arrow. The checkbox glyph is 20px inside that target. Choice/service rows include their whole label. Buttons wrap, rather than reducing type or clipping text. The primary footer button is always reachable; no sticky footer covers the last selected task.

The text-size study (`large=1`) uses 200% body text at 390px, increases titles to 34px, stacks actions and lets text wrap. All card boundaries remain inside the viewport; only the score grid may scroll horizontally, with names fixed. This is **HTML reflow evidence**, not proof at iOS’s largest Dynamic Type or Android’s largest font/display scale. Those native measurements, VoiceOver/TalkBack journeys and keyboard avoidance remain GAPs.

No order changes under the finger. Ticking changes only that checkbox, selected-work summary and count; AI changes update the chip and effective-AI summary immediately, with no reorder. Updates retain the existing row order. Completed rows fold on the next explicit load/refresh or the person’s disclosure; do not collapse a row or move Hand over beneath an ongoing press. No new list severity sort runs during interaction.

## Gaps, delivery and baselines

None was opened or repurposed. `apps/mobile/preview-runtime.cjs` exports HTML-runtime bytes, not a React Native screen renderer. The groundwork’s native capture gaps therefore remain.
