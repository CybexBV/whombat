# Release workstream decisions (RL)

Decisions of the release-package workstream (`release` branch of the appliance). They refine the MA
decisions (`docs/implementation/architecture.md`) and never override them. **RL-01…RL-04 are proposals that need
John's decision** (they concern live hosts, blocker X-06); the others are settled for this workstream.

| # | Decision | Reason |
|---|---|---|
| RL-01 | **Pilot UI host `pilot.whombat.com` in the prod environment (proposal).** Before `app.whombat.com` switches, the hosted UI for internal and pilot orgs is published on `pilot.whombat.com`; control's CORS origins and the relays' `allowed-origins` include it; sign-in there is by magic link only (a WebAuthn RP id `app.whombat.com` can't serve another origin); after the switch it redirects to `app.whombat.com` for 30 days and is removed. | MA-14 gives the hosted UI `app.whombat.com`, which serves the monolith until cutover; a pilot on the dev environment would pin pilot appliances to dev TUF roots and dev keys, forcing a re-provisioning later. |
| RL-02 | **Dev environment first, as the rehearsal (proposal).** The dev stack is deployed and `dev.whombat.com` switched before anything in prod; the dev monolith moves to `legacy-dev.whombat.com`. | Every step of the prod cutover runs once where a mistake costs little. It changes where John's current dev instance lives, hence his decision. |
| RL-03 | **Legacy monolith read-only on `legacy.whombat.com` for 90 days after the prod switch (proposal)**, then decommissioned with a final encrypted backup under the retention policy. | People need a way back to their pre-cutover data and exports; bounded so the monolith doesn't become a second product to secure. |
| RL-04 | **No import until the import tool and the re-enrollment ceremony for device-less accounts exist (proposal).** Pilots start fresh; existing users stay on the monolith until their org's import window. | Only the dry run exists (MR-18); MR-23 names the missing ceremony. Importing by hand would bypass the commit pipeline and the signed audit. |
| RL-05 | **SBOMs are CycloneDX 1.6 JSON from each ecosystem's own maintained generator** (`pnpm sbom`, `cyclonedx-gomod`, the CycloneDX Gradle plugin, `sbomnix`), tools pinned to the appliance's nixpkgs where nixpkgs has them, versions and store paths recorded. SPDX only where the generator emits it (sbomnix). | One format for all components; generators that read the real installed dependency data. syft, osv-scanner's lockfile reader and cdxgen mis-read pnpm 12 lockfiles (measured). |
| RL-06 | **Vulnerability scans use two databases per non-Nix SBOM (grype + osv-scanner), govulncheck for Go reachability, vulnxscan for Nix**; results are reports, triage decisions are data (`release/policy/triage.json`, first match wins, owner named), and a scan never changes code. | Cross-checking scanners reduces misses; decisions next to the data make every re-scan reviewable. |
| RL-07 | **License classification is policy as data** (`release/policy/licenses.json`): SPDX `OR` takes the best option, `AND` and multiple entries the worst; manual annotations for missing metadata say why; first-party and generated files are their own categories. The output is an engineering inventory that flags items for qualified review, never a compliance claim. | Conservative by default and reviewable; assignment §15 forbids claiming compliance from tooling. |
| RL-08 | **Release output is committed per product version** (`release/out/<productVersion>/`, 7 MB for 0.5.2) with `SHA256SUMS`; raw scanner output stays in the work directory (`~/.cache/whombat-mgd/release-sbom/<run>/`). | The inventory must be reviewable with the release; raw scanner JSON is large and reproducible from the SBOMs. |
