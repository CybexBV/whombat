# Claiming with a console code (MA-22) — decisions CC-nn

Decided with John on 2026-09-26. The old claim ceremony was too hard: people had to type a 26-character card secret
and compare a fingerprint group by group. It also needed a factory-printed card, and a downloadable ISO (planned
next) has none. In the new ceremony the appliance shows a short code on its console (`KX-4821-QM`). When someone
opens the claim page on the same network, the page already knows which box they mean (“We found a Whombat on your
network”), so they only type the four letters. When the box and the browser are on different networks, they type the
whole code instead. Once the claim succeeds, the console clears.

This decision supersedes MA-04 §1–3 (claim ceremony) and the fingerprint comparison of whombat-app AP-21. It keeps
MA-04's other properties unchanged: the appliance is the authority on who owns it, control can find and admit a
claimer but never grant ownership, and the recovery kit, pairing, invites and revocation work as before.

Component decisions refine this file: contracts CT-58+, control CL-30+, runtime MR-49+, app AP-47+, manager
MG-28+, NixOS/provisioning NX-32+, harness IN-33+.

| # | Decision | Reason |
|---|---|---|
| CC-01 | **The claim code is `LL-NNNN-LL`.** `NNNN` is the **lookup number**, 4 decimal digits leased by control (CC-03); the contract admits 4–6 digits so the pool can grow. `LLLL` are the **secret letters**, 4 characters from the 20-letter alphabet `ABCDEFGHJKMNPQRTVWXY` (no I L O S U Z, which read as 1 1 0 5 V 2), 20⁴ = 160,000 codes (≈ 17.3 bits). The appliance draws them from a CSPRNG and holds them only in memory and on its console. They never go to control, the relay or a log. The display form is `L1L2-NNNN-L3L4`, and the PAKE password (CC-06) is the four letters in order. **Normalization** (`normalizeClaimCode`): ASCII upper-case; drop Unicode White_Space, U+FEFF and `-`; the result is either 4 letters (letters-only entry) or 2 letters + 4–6 digits + 2 letters. Nothing is repaired: a letter outside the alphabet is invalid, never mapped. | Short enough to read off a screen and type; digits and letters in separate groups can't be confused; the lookup number carries no secret. |
| CC-02 | **Two claim methods share one protocol:** `code` (console letters, this file) and `card` (the factory card's 26-character secret, for boxes without a screen). Both authenticate the appliance to the client through the PAKE (CC-06), so **no one compares fingerprints any more**. The card still prints the secret and its QR code; it no longer prints a fingerprint to compare. A card claim keeps control's `claimProof` gate (CT-43). A code claim can't have one, because control never learns the letters. | One ceremony to build, test and explain; the fingerprint step was the hard part. |
| CC-03 | **Lookup leases.** An unclaimed device asks control for a lookup number with the device op `claim.lookup {}` → `{lookup, expiresAt, renewAfterS}` (signed like every device op), and renews it every `renewAfterS` (300 s). Control hands out the lowest free 4-digit number (5 digits once more than 5,000 leases are live), keeps it for the same device on every renewal, releases it when the device is claimed, retired, or has not renewed for 24 h, and refuses the op with `already_claimed` for a claimed device. The manager leases the number and hands it to the runtime over the admin socket (`POST /claim-lookup {v, lookup, expiresAt}` or `{v, lookup: null}`), as it already does with the claim window. | The number must be unique among boxes waiting to be claimed and stable while a person reads it; control is the only party that sees all boxes. |
| CC-04 | **Discovery by public network.** On every signed device op from an **unclaimed** device, control records `networkTag = HMAC-SHA256(discoveryKey, prefix)` with `lastNetworkAt`. `prefix` is the IPv4 address or the IPv6 /64, taken from the request's client address after the configured proxy hops (`TRUST_PROXY_HOPS`). Only the tag is stored, never the address, and control erases it when the device is claimed or retired. `claims.nearby` (`GET /v1/orgs/:org/claims/nearby`, session auth, `claim` right) computes the caller's tag and lists unclaimed devices with the same tag, `lastNetworkAt` within 15 min and a live lookup lease: `{devices: [{device, model, registeredAt, lastSeenAt}]}`. The lookup number is not in the response. It's rate-limited per account and per IP. The box reports on both address families (the manager renews its lease over IPv4 and IPv6, MG-32), and control keeps one tag per family and matches the caller's tag against its own family's (CL-36), so a dual-stack network works whichever family each side picks. | Hue/Plex-style “we found your box”. The match only finds a box and never grants anything, so a lying control or a shared NAT (CGNAT, offices) can at worst show a box that isn't yours, and the letters then fail. |
| CC-05 | **`claims.start` takes one of three bodies** (a discriminated union on `method`): `{method:'card', device, claimProof}` (unchanged gate); `{method:'code', device}` (only for a device `claims.nearby` would list for this caller: `device_not_nearby` 403 otherwise); `{method:'code', lookup}` (a live lease, `lookup_not_found` 404 otherwise). The code forms spend a per-account (10/h), per-org (20/h), per-IP (20/h) and per-device (30/h) budget. The response is unchanged: `{claim, ticket}` for the enrollment channel. A newer pending claim supersedes an older one, as with a card claim. That's harmless because the appliance completes whichever claim id the winning PAKE presented (CT-27). | Knowing a lookup number or sharing a network admits you to a guess, never to the box; the budgets bound how fast anyone can guess. |
| CC-06 | **PAKE: CPace, suite `CPACE-RISTR255-SHA512`, initiator–responder, draft-irtf-cfrg-cpace-21**, implemented in `@whombat/protocol` (TS on `@noble/curves` ristretto255) and Go `protocol` (on `github.com/gtank/ristretto255`), checked against the draft's Appendix B.3 vectors plus our own cross-language vectors. Inputs: `PRS` = UTF-8 password (the 4 letters, or for a card `claimCardPassword(deviceId, secret)` = the `claim.json` `secretHash`, since the appliance never stores the secret — contracts 0.7.1, CT-66); `CI` = `lv_cat("whombat-claim/1", method, deviceId, appliancePeerId, clientPeerId)`, both PeerIds as each side sees them in the Noise handshake it is running; `sid` = the control claim id's UTF-8 bytes; `ADa` = `ADb` = empty. `ISK` as in the draft. **Key confirmation**: `k = HKDF-SHA512(ISK, info "whombat-claim-confirm/1")`, `tagClient = HMAC-SHA512(k, "client" ‖ transcript)`, `tagAppliance = HMAC-SHA512(k, "appliance" ‖ transcript)`, both truncated to 32 bytes and base64url-encoded. Because the static keys are in `CI`, a relay or control that man-in-the-middles the Noise session (two different static keys) gets mismatching keys even when it forwards CPace unchanged. An active attacker gets exactly one password guess per exchange, and a confirmation tag reveals nothing beyond that guess. | A 17-bit code is safe only under a PAKE: offline guessing is impossible, and online guessing is bounded by CC-07. Channel binding through the static keys replaces the fingerprint check. |
| CC-07 | **Session ops** (channel `enroll`): `enroll.claim.begin {claimId, method, share}` → `{share}`. The appliance runs the responder, keeps `{ISK, transcript, claimId, method}` for this session for at most 120 s, and reveals nothing about the password. Then `enroll.claim {claimId, confirm: tagClient, account, endpoint}` → `EnrolledOutput + {recoveryKitRequired, confirm: tagAppliance}`. The appliance checks `tagClient` in constant time before anything else; only then does it create the owner, exactly as today. The client checks `tagAppliance` before it trusts the result (pins the PeerId, creates the kit). A mismatch there means it was talking to something else: it stops with “This isn’t the Whombat on your screen”. `claimSecret` leaves `EnrollClaimInput`. **Attempts**: a failed `tagClient` is one wrong guess. Under `code` the letters then rotate at once (new letters on the console) and the failure counts toward a backoff: the first 3 failures in a rolling 24 h are free, then the appliance refuses `begin` for 1, 2, 4 … min, capped at 60 min (`claim_backoff`, with `retryAt`). Under `card` the same backoff applies without rotation. A `begin` without a following `enroll.claim` costs nothing: it learns nothing. The existing per-peer and total attempt limits (MR-26) still apply to `begin`, and the physical claim window still exempts the total limit. Success clears the counters. | Rotation after every wrong guess stops any code from being eliminated one guess at a time; the backoff caps a determined guesser at ~24 guesses a day, so a box left unclaimed for a month has < 0.5 % odds of being guessed, and only by someone who can reach its lookup. |
| CC-08 | **The console.** The runtime is the authority on the letters, rotation, backoff and claim state, and writes an atomic JSON file (`WHOMBAT_CONSOLE_FILE`, `/run/whombat/console.json`, mode 0640, group `whombat-console`): `{v:1, state:'starting'|'waiting'|'claimable'|'backoff'|'claimed', code?, url, retryAt?}`. `waiting` means there's no lookup lease yet (control unreachable); `code` is present only in `claimable`. The whole code is on the console, never in the journal. A new Go program `whombat-console` (the appliance) runs as its own unprivileged unit on tty1 (getty@tty1 is disabled; the other VTs keep the banner), redraws when the file changes (1 s poll), and shows the words below. Rendering is plain text, so a crafted file can't rewrite the console (escape sequences stripped, like the recovery menu, N-3). **Words**: `claimable` — “Claim this Whombat” / “Open {url} and enter” / the code / “The code changes after a wrong try.” `waiting` — “Connecting to Whombat…” / “Check the network cable. The claim code appears once this Whombat is online.” `backoff` — “Too many wrong codes. Try again in {n} min.” `claimed` — “This Whombat is set up.” / “Open {url} to use it.” `url` is `WHOMBAT_APP_URL` + `/claim`, shown without the scheme. | The runtime already owns the claim and the attempt limits; a file keeps the console process free of any socket or credential, and the dev environment reads the same file. |
| CC-09 | **The app.** `/claim` (web and Android): sign in → organization → the claim page calls `claims.nearby`. **One box found**: “We found a Whombat on your network” with its model and id, and a 4-letter field (“Enter the 4 letters from its screen”). **Several found**: pick one first. **None found**, or “Not this one?”: “Enter the code on your Whombat’s screen” (the full code). A secondary link “Claim with a card instead” leads to the card secret or QR (which uses `method:'card'`). Then `claims.start` → session → `begin` → `enroll.claim` → the `tagAppliance` check → recovery kit, as before. The fingerprint screen is removed. Refusals: `claim_invalid` → “That code isn’t right. Your Whombat now shows a new one.” (code) / “That claim code isn’t right.” (card); `claim_backoff` → “Too many wrong codes. Try again in {n} min.”; `lookup_not_found` → “No Whombat is showing that code. Check the digits.”; `device_not_nearby` → back to the full-code field. | The fewest steps that keep the letters as the proof. |
| CC-10 | **Self-registration (for the ISO).** `POST /v1/devices/self-register` (no credential) takes the same `DeviceRegistration` with both key proofs and `model: 'self-installed'`; control accepts it only when `SELF_REGISTRATION=1`, limits it per IP (5/h, 20/day), marks the device `origin: 'self'`, and retires self-registered devices that stay unclaimed and unseen for 7 days. `whombat-provision self` generates the identity on the device, registers through that endpoint and writes the identity files with a `claim.json` that has no card secret (`secretHash: null`), so only `method:'code'` can claim it. It writes no cards. The NixOS unit `whombat-self-provision` runs it at boot while unprovisioned, behind `whombat.provisioning.selfRegister` (default off). **Out of scope, deferred to the ISO work**: the disk recovery key for self-installed boxes (today it is on the factory card) and hardware qualification for arbitrary machines. | The claim flow works for a box without a factory; the ISO pieces unrelated to claiming are named, not half-built. |
| CC-11 | **Development.** `dev/up` still provisions the dev appliance factory-style (card too), and additionally prints the console code. `dev/console` renders the console file in the terminal (`--watch` redraws). On the public dev instance control trusts one proxy hop (cloudflared), and the dev appliance's manager talks to control through the public API origin, so a browser on the same network as the host sees the dev box as nearby. A browser elsewhere uses the full code from `dev/console`. | The real flow runs end to end on dev.whombat.com, including discovery when it can. |
| CC-12 | **Versions.** Contracts 0.7.1 (0.7.0 + CT-66; breaking: `EnrollClaimInput`, `claims.start`, new ops and admin/IPC paths); every consumer moves to 0.7.1 together, as with 0.6.0 (CT-57). No appliance was ever claimed against a live control, so nothing needs migrating. The candidate pin set `manifest/candidates/0.7.1.json` is validated before the dev instance runs it. | Same procedure as every contracts release. |
| CC-13 | **Same network only; the console shows the four letters (John, 2026-09-26; amends CC-01, CC-03, CC-05, CC-08, CC-09, CC-11).** A code claim works only from a device on the box's own network (`claims.nearby`). The console shows only the letters, e.g. `KXQM`, with “On a computer or phone on this network, open {url} and enter”; it never shows the lookup number. `claims.start` has no lookup form any more (contracts 0.8.0, CT-67). The lookup lease stays as the box's internal “waiting to be claimed” presence: `claims.nearby` requires it, and the runtime shows `waiting` without it. App: when nothing is found, “We couldn’t find your Whombat” explains that this device must be on the same network and offers “Look again”; the card stays as the fallback for boxes without a screen. Contracts 0.8.0 replaces 0.7.1 for every consumer. | A short code that is only the secret; guessing now also needs a foothold on the box's network. |
| CC-14 | **A self-installed box shows its disk recovery key before the claim code (2026-09-27; PI-04; amends CC-08, CC-10).** Before any claim state the console shows “Write down this recovery key. It is shown only once.” with the key's eight groups and a QR code, and asks for its last group; until the right group is typed it shows no claim code, whatever the runtime's state file says. The runtime's states and `ConsoleState` are unchanged: the screen comes from a file only provisioning, the console and a root unit share (NX-53, NX-54), not from the runtime, so no contract changes. The key is never sent anywhere (it gates the recovery menu and factory reset, stored as a hash). CC-10's deferral of the recovery key is closed. | The key must be written down before anyone can claim the box; shown once and confirmed, it can't be skipped past or lost unshown. |

## Threats and residual risks

- **Guessing** (T4'): bounded by CC-05 budgets at control and CC-07 rotation/backoff on the box; a lying control or
  relay gets the same one guess per exchange as anyone else.
- **Griefing**: someone who can reach the lookup (same network, or who read the digits) can burn wrong guesses and
  push the box into backoff (≤ 60 min at a time). Accepted: the claim window (hardware button, where present)
  exempts the total limit, and the owner can always wait it out; the guesser still can't claim.
- **Shoulder surfing** the console before the owner claims = physical access, the same trust as holding the card.
- **Remote consoles** (IPMI/KVM, VM consoles on the ISO): whoever sees the console can claim, and, while it is still
  pending, write down the disk recovery key (CC-14). Documented for the ISO (`docs/runbooks/install.md` §2).
- **Discovery privacy**: the network tag is keyed (a control DB leak doesn't reveal addresses), exists only while
  the device is unclaimed, and `nearby` answers only signed-in org members with the `claim` right.
- **Self-registration abuse**: per-IP limits and 7-day expiry; self-registered devices get no rights beyond
  waiting to be claimed.
