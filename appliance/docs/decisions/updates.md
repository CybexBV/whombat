## The pipeline in one table

| Stage | Command (appliance repo) | Needs | Writes (next to the release, `~/.cache/whombat-releases/<id>/`) |
|---|---|---|---|
| build | `release/ship build <prod id> [--reuse-host <prod id>]` | clean tree, pins checked, newer than published (UP-A3) | the PROD release and its DEV twin (`pve-dev-…`, same commit), ISOs, `build.json`, `notes.md`/`notes.json` (UP-C3) |
| validate | `release/ship validate <prod id>` | `build.json` | `gates.json` (gates, scenarios, demo) and `upgrade-gates.json` (UP-C2 VM gates) |
| publish dev | `release/ship publish-dev <prod id>` | both records | the DEV twin on the DEV TUF repository, rolled out to the DEV box (UP-D1); `dev-soak.json` when the soak passes (UP-D2) |
| promote prod | `release/ship promote-prod <prod id> [--waves default\|all-at-once\|<file>]` | `dev-soak.json`, John's yes (assignment §9) | the PROD publish through `deploy.sh release … --waves`, `promote.json`, `manifest/pins.json` promoted (UP-C4) |
| status | `release/ship status` | — | one screen: hosted components, fleet by release, open rollouts, alerts (UP-G3) |

Every record names the release id and the sha256 of the record before it (`build.json` → `gates.json` →
`upgrade-gates.json` → `dev-soak.json` → `promote.json`); a stage refuses to run when the previous record is missing,
names another release or another build, or failed (UP-C1).

## U-A Versions that only move forward

| # | Decision | Reason |
|---|---|---|
| UP-A1 | **One totally ordered version per component.** Runtime: `<Whombat package.json semver>-<commit time UTC YYYYMMDDHHMMSS>.<shortrev>` (then `.p<digest>` for patched bundles, `.<label>` for dev labels), the commit time being the flake input's `lastModifiedDate`; Whombat's package.json moves to `0.2.0` (MD-13). Host: the release id (`pve-YYYYMMDD.N`, `pve-dev-YYYYMMDD.N`), ordered by `CompareVersions` as it is (day, then `N` numerically). Manager (and the helper, one build): `<appliance semver>-<appliance commit time>.<shortrev>` (appliance semver `0.2.0`, in `flake.nix`), set for release builds only (`proxmoxRelease`), so VM tests and dev builds don't rebuild on every commit; dev/test builds keep `0.2.0-dev`. App, embed, admin: their package semver. | A commit time is fixed by the pinned source, so the Nix build stays pure and a rebuild gives the same version; the pipeline needs no counter to keep. Commit times on `main` move forward with every merge; UP-A3 catches the exception (a pin moved back, clock skew) before signing. |
| UP-A2 | **The transition.** Every version in the field (`0.1.0-<hex>[.p…]`, manager `0.1.0`) has core `0.1.0`; every new one has core `0.2.0`, which `CompareVersions` orders after it whatever follows the `-`. Proven by tests over every published tuple (`~/.cache/whombat-releases/*/tuple.json`, the fixtures' and the TUF repositories' targets) in Go (helper `forward_test.go`) and in the contracts' shared vectors (`compareVersions`, CT-135). No `allowDowngradeFrom` is needed for the transition. | The pre-release part of `0.1.0-<hex>` is compared as text (`e847497` > `195421a`), so about every other runtime-only release would have been refused; raising the core ends that for every old version at once. |
| UP-A3 | **Nothing older is signed.** `tufrepo publish-release` refuses a release whose host, runtime or manager version is lower than the newest published release's (by `CompareVersions`, over the `releases/*` targets' tuples), or whose id isn't newer, unless `--allow-downgrade-from <id,…>` is given (custody rollback, which also writes the TUF-signed `allowDowngradeFrom`). `release/ship build` runs the same check early against the public repository (`tufrepo check-newer --metadata-url …`). Messages name the component, both versions and the release that published the newer one. | The signing step is the one place every release passes, dev and prod; checking again at build saves a 20-minute build. |

## U-B Compatibility across versions

### UP-B1 The compatibility model

| Pair | Declared by | Checked by | Rule |
|---|---|---|---|
| runtime ↔ database schema | the runtime's `compat.json` (per-migration class and reader/writer floors, recorded in `whombat_meta.schema_versions`), and the tuple's `schemaReads {min,max}` / `schemaWrites` | the candidate's own `whombat schema-check --json` on the live database (MD-10, MD-12), then the manager: exit 0 → `checkCompatibleActivation` (UP-B2), exit 10 → `checkMigratingActivation` (CT-134), 11/12 → refused | `schemaWrites`: the schema the runtime migrates to and writes (its newest migration). `schemaReads`: what the tuple promises it reads (`min` = `runtime.readsFrom`, `max` = `schemaWrites`). Both are versions: the chain's `schemaBase` (absent: 0) plus a migration's position (`release/schema-numbers`, and the harness's `schemaRange` for its manifests and dev releases), so a Whombat chain that starts again with a new baseline keeps numbering after the one it replaced (Whombat report-trackers.md). The **floors decide** where they are reported: a binary of schema `s` reads a database whose readers floor ≤ `s` and writes it when writers ≤ `s`, whatever the tuples say. |
| runtime ↔ host | tuple `runtime.hostAbi {min,max}`, `host.abi` | the helper (`CheckCompat` inside a tuple), the manager, `release/build-proxmox` (`--reuse-host` refuses another ABI) | `hostAbi` contains `host.abi`. The ABI is raised only when the host stops providing something a runtime uses. |
| runtime ↔ session protocol | tuple `runtime.protocol {min,max}` (`major*1000+minor`) | the manager (`ProtocolOverlap` with the installed runtime: no update strands every client), the runtime on `hello` | a candidate shares a major with the installed runtime. |
| runtime ↔ clients | the runtime's API level and feature list (`welcome.runtime`, UP-B3), the tuple's `clientFloor` (CT-53) | clients on `welcome`; the runtime on `hello` (floor); the pipeline and `deploy.sh` (UP-B3, UP-B4) | a client serves runtimes whose API level is within its window; a runtime refuses clients below its floor. |
| release ↔ installed release | tuple versions | control (`notOlder`, now by versions, UP-X03), the manager and the helper (`CheckForward`) | forward only; back only with TUF-signed `allowDowngradeFrom`. |
| release ↔ manager | the device's reported `managerVersion` | control (UP-E6) | a release that migrates the database goes only to managers ≥ `0.2.0-0` (built by this pipeline: MG-43 and later, reporting a real version). |

`checkActivation` (exit 0 without floors, runtimes before MD-12), `checkCompatibleActivation` (exit 0 with the live
schema's floors, UP-B2), `checkMigratingActivation` (exit 10, CT-134): the three contract functions; the manager picks one
from the exit code and whether the runtime reported floors, never from the tuple alone.

| # | Decision | Reason |
|---|---|---|
| UP-B2 | **Exit 0 uses the floors too.** When the candidate's schema check answers exit 0 and reports the live schema's floors (`target` = the database, verdicts `current` and `newer_compatible`), the manager calls `checkCompatibleActivation(current, candidate, dbSchema, {readers, writers})` (CT-135): the candidate is accepted when its own schema (`schemaWrites`) is at or above the writers floor (`newer_compatible`: it reads and writes the newer database, as its own check said), refused `candidate_read_only` between the floors and `candidate_cannot_read_schema` below the readers floor; `schema_downgrade` no longer applies to it (nothing is migrated down: the newer schema stays, written compatibly). Rollback access is the installed runtime's own schema against the same floors. Without floors: `checkActivation`, as before. A custody rollback still needs the TUF-signed `allowDowngradeFrom` (the forward check is unchanged). Tests in Go and TS (vectors), the manager (testworld), and the VM case `custody-rollback` in `update-migration` (UP-C2 5). | After an `expand` the older runtime's own check says it reads and writes the migrated database; the tuple-only rule refused it (known issue 6), so custody could never step back after a migration. |

### UP-B3 Clients tolerate skew

| # | Decision | Reason |
|---|---|---|
| UP-B3a | **Window: a client serves runtimes whose API level is from its own − 2 to its own + 1.** The API level is an integer in `@whombat/protocol` (`SESSION_API_LEVEL`, 22 at contracts 0.22.0; bumped by every contracts minor that changes a session op, output, frame or union — the contracts release checklist says so). A runtime advertises it in `welcome.runtime` (UP-B3c); runtimes before it count as 21. Hosted web, Android and the embed apply the same window. | Levels, not release ids: a client can't know release order, and contracts minors are exactly the points where the session API changes. N−2 covers a box that skipped a release; N+1 covers the hosted web deployed after a box updated. |
| UP-B3b | **Tolerant decoding in contracts** (`decodeTolerant(schema, value)` in `@whombat/protocol`): on a parse failure caused only by unknown enum members or union discriminators, the element that carries it is replaced by an `unknown` placeholder where the schema allows one (cards, work items, events, activity rows) or dropped from its list, and the rest decodes; the result lists what was skipped. Clients use it at every session output and frame parse point; a screen shows “This needs a newer version of the app.” for a skipped item, never a failed screen. CT-130's “older apps refuse answers carrying a new member” is replaced (CT-136). Tests feed a 0.20-era schema 0.22 data and vice versa. | The closed-union policy made every contracts minor a lockstep deploy of runtime, web and Android (HZ-28's rollback of the web). |
| UP-B3c | **The runtime says what it can do**: `welcome.runtime = {version, apiLevel, features[]}` (optional member of `Welcome`, a tolerant message). `features` are names from `RUNTIME_FEATURES` in `@whombat/protocol` (`spend`, `browser`, `skills`, `roles`, `delegation`, `vault.login`, …, one per feature added since 0.19); unknown names are ignored. The web hides or explains a feature the box lacks (“Update your Whombat to use Spend.”) instead of calling its ops; a runtime whose level is below the window gets a banner “This Whombat needs an update for this version of the app.” and above it “Reload to get the newest version of the app.” (web) / the store link (Android). | Newer clients called endpoints older runtimes lack (HZ-28); feature names are what the UI actually needs to know. |
| UP-B3d | **Floors**: a runtime release that needs a newer client sets the tuple's `clientFloor` (CT-53; `release/ship build --client-floor web=N,android=M`), clients below it get the existing “update the app” path (`client_below_security_floor`). `promote-prod` refuses a runtime whose web floor the deployed hosted web doesn't meet (the hosted web's build number from `https://app.whombat.com/version.json`).<br>Superseded by IN-413 (HE-52). | The floor exists since CT-53 but nothing checked it against what is deployed. |
| UP-B4 | **Hosted deploys check the fleet.** `deploy.sh web\|embed\|admin\|control\|relay` read control's fleet summary (`GET /v1/operator/fleet`: devices by release with each release's API level, from control's release records) and refuse, unless `--force`, when the new build's window (web, embed: its API level −2…+1; control, relay: the device API and relay protocol they serve) leaves out a release some live device runs; the refusal prints the order to use (e.g. “update the boxes first: …” or “deploy web first”). | The order was a thing to remember (HZ-28). |

## U-C Release pipeline and gates

| # | Decision | Reason |
|---|---|---|
| UP-C1 | **`release/ship`** (bash entry, TypeScript in `harness/src/ship/`) with the stages and records of the table above. A PROD candidate is built as a pair: the PROD release and its DEV twin (`pve-dev-<same day>.<N>`), from the same commit; runtime and manager store paths are identical (they don't depend on the environment), the hosts differ only by the environment profile. Everything that needs a real update chain runs on the twin; what is published to PROD is the PROD build. Records are hashed and chained, not signed (the operator's machine is trusted; no new keys, PI-05). | One command per stage, no order to remember; the twin is what makes a DEV proof of a PROD build possible without PROD keys. |
| UP-C2 | **Upgrade gates in VMs, with the real previous releases.** New NixOS tests in `vm-tests/upgrade-gates/` build the previous releases from their recorded sources (`build.json` `source.rev` → `builtins.getFlake` of that appliance commit, its `proxmoxRelease` for `dev`, then `extendModules` with a gate module that points it at the test's fake control and TUF repository) — the same code and the same runtime store paths as published — and update them to the candidate through the real manager, helper, TUF (signed by the fixture keys) and the fake control: (1) PROD N−1 → candidate with a populated database; (2) N−2 → candidate; (3) fresh install from the candidate's ISO, self-registration, claim, healthy; (4) a candidate that fails verification → automatic rollback to N−1, healthy, rows intact; (5) migration classes: expand without a checkpoint, contract with a destination (checkpoint, migrate), contract without one (waits, nothing changed), custody rollback after an expand (UP-B2); (6) a runtime-only release on the previous host and a host release keeping the runtime. Required for `validate` of a PROD candidate; images and closures are shared between the gates (one build per release). | The missing gate of 2026-09-28: nothing installed a candidate as an update of the release boxes run. |
| UP-C3 | **Release notes** (`notes.json` + `notes.md`, generated by `release/ship build`): per component the commits since the previous release of the environment (appliance, Whombat pin, contracts, app), the migrations with class and floors, the client floor, the API level and features, known issues (from `--known-issue`). Control stores them with the release (`POST /v1/operator/releases` `record`, UP-X02) and the admin panel and the owner's “what changed” show them. | Nobody could say what a release contained or which migrations it ran. |
| UP-C4 | **`promote-prod` promotes `manifest/pins.json`** to the candidate it published (and commits it on the appliance's `main`), so the pins always name what PROD runs. | Stale since `2026.09.26-rc.1`. |

## U-E PROD rollouts with safety

| # | Decision | Reason |
|---|---|---|
| UP-E1 | **Staged waves by default**: `internal` 100 % (observe 1 h), `pilot` 100 % (6 h), `canary` 100 % (12 h), `general` 10 % (24 h), `general` 100 %; failure threshold 0 and minimum sample 1 in every wave (any failure pauses). Control promotes a wave automatically when its window passed with every activated device healthy (as it does today); an empty wave promotes at once. `deploy.sh release … --waves default\|all-at-once\|<file>` (all-at-once: one wave, threshold 0), `promote-prod` uses `default` and waits, printing progress. The operator can pause, resume, promote or stop at any time. | Automatic promotion keeps a clean release moving without someone awake; a threshold of 0 is right while the fleet is small (one box). Revisit when a wave has hundreds of boxes. |
| UP-E2 | **Automatic stop**: control pauses the rollout when a device of the current wave reports `Failed`, `RolledBack`, `Quarantined` or `ForwardRepairRequired`, or a health regression (runtime or database `down` in two consecutive status reports within the observation window) — `pauseReason` `device_failed` / `health_regression` with the device and the failure detail; an alert goes out (UP-G2). `promote-prod` reports it and exits non-zero. Emergency stop (`PUT /v1/operator/emergency-stop`) is documented in `shipping.md` and tested (`rollout.int.test.ts`). | The one-wave rollout could never pause (`failureThresholdBp 10000`). |
| UP-E3 | **Failure detail reaches control as structured fields**, not text: `update.failureDetail {stage, code, reasons[], dbSchema?, targetSchema?, candidateSchema?, failedChecks[], release}` in `status.report` and `update.progress` (codes, ids and counters: the §12 allowlist holds). Contracts render the message (`describeUpdateFailure`, CT-137) for the admin panel, `promote-prod` and the owner's app. The box keeps its full local message (journal, `whombat-manager status`). | Operators have no shell on a box; free text from a box could carry paths or content. The incident's message is exactly reconstructible from these fields. |
| UP-E4 | **Owners are told** (*since Whombat one-person.md OP-03, 2026-10-25: the box's one person*) in Settings → This Whombat: an update waiting (safe boundary with what runs, checkpoint “needs a backup destination”, maintenance window, hold) or failed (the rendered detail, “Your Whombat is still on …; nothing changed”), and after a successful update “Updated to … on …” with the notes' summary. The manager adds `waiting {reason, since, blockers}` and `lastUpdate {release, at, summary}` to `UpdateFacts` (CT-138). An optional maintenance window per org (`notBefore` in assignments from the org's window, control). | The owner saw nothing of the incident. |
| UP-E5 | **Reinstall and replacement**: a self-registration refused because a live record holds the same hardware serial is recorded as a pending re-registration; the admin panel shows it with “Reinstalled — retire the old record” (retire, then the box's next attempt registers); unclaimed registrations older than 14 days are deleted by retention. `factory-reset.md` / `replacement.md` describe it. | HZ-29 needed a manual retire. |
| UP-E6 | *Superseded (HE-52): control's `manager_too_old` hold is gone (IN-420).* **Old managers don't get migrating releases.** Control holds (reason `manager_too_old`) a device whose `managerVersion` compares below `0.2.0-0` (core below 0.2.0: every manager before this workstream reports `0.1.0`; every new one is a pre-release of 0.2.0, `0.2.0-<time>.<rev>` or `0.2.0-dev`, so the floor is `0.2.0-0`, not `0.2.0`) from a release whose `schemaWrites` is above the device's current release's; the rollout view lists those devices with “give it a host release without a migration first, or reinstall”. `promote-prod` prints them. | Managers before MG-43 fail every migrating release; `0.1.0` is also reported by the one MG-43 manager (`pve-20260928.6`) — conservative: its next release is a host release without a migration (UP-X04). |
