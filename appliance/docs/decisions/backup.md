# Backups, restore, replacement and recovery (workstream W3-BK)

Branch `backup` of the appliance, 2026-09-25. Implements MA-13 (and the backup parts of MA-03, MA-11, MA-12)
and assignment §4 (backup gaps), §9 (checkpoint before an incompatible migration), §11 and §14 item 13.
Decisions are `BK-nn`; they refine the MA decisions and never override them. Code: `backup/` and `recovery/`
(packages of the root Go module `github.com/CybexBV/whombat/appliance`). Runbooks:
`docs/runbooks/backup.md`, `restore.md`, `replacement.md`, `recovery-export.md`.

| # | Decision | Reason |
|---|---|---|
| BK-01 | **Packages of the one root Go module** (`github.com/CybexBV/whombat/appliance`, merged from `main` at `3a89c33`), using its vendored `third_party/whombat-contracts-go` (0.4.0, MA-02). Shared, cloud-free code is in `backup/pkg/*` (coverage, manifest, kit, restic, pgtool, gitinv, restore, fsutil); service-only code in `backup/internal/*`; the recovery tool (`recovery/`) imports only `backup/pkg/*`. restic is driven as a CLI (`--json`), never linked. The integration harness is `backup/itest` (not internal, so the recovery tests reuse it). | One module per repository (orchestrator); the recovery tool stays small and has no service code; restic's CLI is its supported interface. |
| BK-02 | **Coverage is code** (`backup/pkg/coverage`): 15 classes, the first 9 covered (`database`, `memory`, `attachments`, `packs`, `home`, `workspaces`, `configuration`, `provider-sessions`, `recovery-references`), 6 deliberately not (`identity`, `recovery-secrets`, `manager`, `postgres-datadir`, `backup-state`, `caches`). The ids are the contract's `BackupScope`. `docs/runbooks/backup.md` carries the rendered table, and a test fails when they differ. Every checkpoint manifest records the coverage and the excluded paths. Runtime directories outside the sources are a coverage gap (`coverage.CheckRoots`): agent workdir roots must be under `/persist/whombat/workspaces`. | One inventory for the service, the manifest, the client and the docs; the old self-hosted backup silently left out workspaces and `codex-home` (assignment §4). |
| BK-03 | **Cache rule.** Left out only when regenerable and not authored: a directory with `CACHEDIR.TAG` (restic `--exclude-caches`); inside a git repository, a directory git *ignores* whose name is a cache name (`node_modules`, `.venv` with `pyvenv.cfg`, `target` next to `Cargo.toml`, …); in-flight uploads (`home/files/.staging`), per-turn scratch and transient push repos (`workspaces/.scratch`, `.push`); WHOMBAT_HOME transients (logs, locks, pid). Everything else is kept, including git-ignored non-cache files (`.env`) and untracked directories named like caches. | Excluding by name alone would lose authored work (a tracked or untracked `build/` or `node_modules` that isn't regenerable); ignoring + a known name is a safe signal. |
| BK-04 | **File consistency: a snapshot inside the quiesce, upload from the snapshot.** `whombat-backup-snapd` (root, socket-activated, one peer uid, typed `take`/`release` by checkpoint id; sources and destinations from its own config) puts each source (`home`, `workspaces`, `credentials`, `secrets`) at `/persist/backup/staging/current/files/<name>`. Drivers: `btrfs` (read-only subvolume snapshots: every source a subvolume on the filesystem of `/persist/backup`), `zfs` (dataset snapshot bind-mounted read-only), `copy` (fallback: a full copy taken while writes **and** new turns stay paused, scope `all`; FICLONE when the filesystem supports it, byte copy otherwise; an up-front space estimate plus ENOSPC handling; the manifest says `quiesced-copy`). LVM snapshots are not implemented. **The current NixOS layout (NX-07: ext4 `/persist`) only allows `copy`**: the pause then grows with the data. Requirement for the NixOS side: btrfs subvolumes for the four sources (preferred), or XFS with reflink (fast copies without snapshots). | A live copy plus an independent dump is not a checkpoint (§11). A btrfs snapshot takes milliseconds, so the write pause is short. The fallback still makes a correct checkpoint and says what it cost. |
| BK-05 | **Quiesce = the runtime admin socket's drain** (contract CT-23): `POST /drain {reason: backup, scope: writes\|all, leaseMs}` until `safe`, renewing the lease every lease/3 while inside, `POST /resume` afterwards (always, from a fresh context). Scope `writes` is the write barrier: new write transactions wait at the commit pipeline, in-flight ones finish, file-moving workers pause, and running turns continue. The runner's direct workspace writes then land crash-consistently in the snapshot. The wait is bounded (`quiesceTimeoutMs`, default 120 s). On timeout, busy (409) or cancel the drain is released, nothing is killed or cancelled, and the reason names the blockers. A crashed backup can't leave writes paused, because the lease expires. `Restart=on-failure` retries in 15 minutes. **Order inside the quiesce: database snapshot first, then files**, so the files are a superset of what the database references. | The contract's shapes. A write barrier instead of a full drain keeps backups from waiting on long agent turns. The file-superset order means a checkpoint never references a blob it lacks. |
| BK-06 | **Database: `pg_dump --snapshot` from a snapshot exported inside the quiesce.** A `REPEATABLE READ READ ONLY` transaction runs `pg_export_snapshot()` inside the quiesce and stays open. `pg_dump -Fc -Z0 --snapshot=<id>` runs **after resume** and still sees the checkpoint instant. Row counts, schema version (`whombat_meta.schema_versions`, drizzle count) and the referenced blob set are read in the same snapshot. Custom format uncompressed: restic's chunking dedups it across days and restic compresses. Restores use `pg_restore --no-owner --no-acl --single-transaction --exit-on-error` into an empty database. The service role is `whombat_backup` (`pg_read_all_data`, `BYPASSRLS`, peer auth); exporting a snapshot needs no privilege. Rejected: a physical base backup (`pg_basebackup`/`pg_backup_start`), which needs WAL handling, a replication role and the same PostgreSQL major, and can't be exported as open data without a server. | The write pause is only snapshot export plus file snapshot, not the dump. The logical dump restores into a newer major (MD-09) and converts to SQL without a server (recovery). It includes `whombat_meta`, so restored databases describe their own schema (MD-02). Verified against the real runtime schema (82 tables, schema 29). |
| BK-07 | **Identity keys are never backed up; the master key is.** A replacement gets fresh management and content identities (MA-03). The manifest records only public references: management key fingerprint, content PeerId and recovery authority fingerprint, from provisioning's `management.pub` and `content.peerid`. `/persist/secrets` (the master key that seals signing keys and connector tokens in the database) is covered, so a backup's confidentiality is the repository password's. | Two appliances with one content identity would defeat pinning. A backup without the master key restores a database whose secrets can't be opened. |
| BK-08 | **Signed checkpoint manifest** (`whombat.checkpoint/1`, in the snapshot at `manifest/checkpoint.json` + `.sig`): Ed25519 over a domain-separated hash, with a manifest key generated on the appliance (`/persist/backup/keys`, separate from the management key; public half in the kit and in each manifest). The snapshot is tagged `whombat-checkpoint`, `ck:<id>` and `mf:<manifest sha256>`. Verification requires the kit's key, the `mf:` tag equal to the content hash and `ck:` equal to the manifest id. Then dump hash, row counts, blob digest and every repository's inventory are compared with the restored data. Manifests form a hash chain (`seq`, `previous{id, seq, manifestSha256}`), so gaps, withheld snapshots and duplicate manifests are reported. What it adds over restic's own MAC: restic authenticates with the (shared) repository password, while the manifest key tells "made by this appliance" from "made by someone holding the kit". It can't beat a compromised appliance, which holds the key; append-only retention covers that case. | Tests: forged newer checkpoint (other key), replayed genuine manifest with other data, tag/content mismatch, tampered snapshot file. |
| BK-09 | **First qualified destination: restic REST server `--append-only`** (rest-server 0.14.0 tested). The appliance credential can read and add, and nothing else. Tested: DELETE of data/snapshots/keys/index → 403; overwrite (POST to an existing name, config) → 403; a mismatched upload → 400; `restic forget --prune` and `key remove` fail; lock files stay deletable (restic needs it). **Prune/delete authority** is a second rest-server instance on the same data directory, without `--append-only`, with its own htpasswd user, run and reachable only on the customer's side. The appliance never holds that credential; the appliance credential is refused there. **Retention policy: `forget --keep-within <d> --prune` only**, never `--keep-last`/`--keep-daily`. Tested: an attacker's future-dated snapshot would make `--keep-last 1` drop every real checkpoint, while `--keep-within 30d` keeps them all (restic's append-only guidance). Object locking (S3 Object Lock) is **not** prescribed: not tested with restic maintenance. The appliance probes append-only enforcement by deleting a random non-existent key file: 403 = `verified`, success = `not-enforced`, shown in the status. | Deletion resistance enforced outside the appliance (§11). A probe proves the property with the appliance's own credential and deletes nothing. |
| BK-10 | **Repositories are untrusted input.** Git runs hardened: no system/global config, `HOME=/nonexistent`, `core.fsmonitor=false`, `core.hooksPath=/dev/null`, `core.attributesFile=/dev/null`, `GIT_ATTR_SOURCE`=empty tree, every filter driver named in the repository's config neutralized on the command line, `protocol.allow=never`, `GIT_OPTIONAL_LOCKS=0`, `safe.directory=*`, a ceiling at the snapshot root. Only plumbing that runs nothing is used (`rev-list`, `for-each-ref`, `ls-files`, `diff-index --cached`, `fsck`, `bundle`). Worktrees are read with `GIT_DIR`/`GIT_WORK_TREE` mapped into the snapshot, never through their absolute `gitdir:` to the live repository. Restores relocate `gitdir`, `worktrees/*/gitdir` and `objects/info/alternates`, and report (never follow) any path left outside the restore. | A test repository with an fsmonitor, filter drivers (incl. `info/attributes`) and hooks pointing at a marker script: the inventory, cache scan and fsck run none of them. A control shows plain `git status` does run them. |
| BK-11 | **Status for the client** is `whombat.backup-status/1`, the contract's `local.BackupServiceStatus` (contracts 0.4.0). It is validated against the schema before every write. States: `unprotected` (no destination; never "enabled"), `pending`, `protected`, `stale` (older than 36 h), `failing` (with the previous success still shown). It also carries last success (age, method, write pause, bytes), last failure (`{id, at, stage, reason}`, stage from the contract enum, reason one line in any script ≤ 500 characters, BK-75), coverage with `relogin`, recoverability (last drill: ok, RTO and backup age as integer seconds, failed/skipped checks) and the kit generation. It is served at `GET /v1/status` on `/run/whombat-backup/api.sock` (runtime and manager uids) and written to `/persist/backup/status.json` (0644). The manager forwards it to the runtime in `/facts` and the runtime summarizes it (`summarizeBackup`). | One document, one schema, no protocol gap for reading status. |
| BK-12 | **Superseded in part by BK-67** (a check reads through a cache made for it, never the box's). **Drills restore into quarantine and verify everything; skipped ≠ passed.** Quarantine means a fresh directory under `/persist/backup/drill/<id>` and a fresh database: a private throwaway PostgreSQL cluster (unix socket only) by default, or a named database on a server. The database is made `default_transaction_read_only = on`. Nothing is started from it, so no schedule or outbound effect can run. The repository is read without the appliance's restic cache, so the drill sees what a recovery would. Checks: `restic-check` (structure or `--read-data[-subset]`), `manifest` (authentic + chain), `restore` (`restic restore --verify`), `dump-hash`, `database` (pg_restore + read-only), `row-counts` (+ schema version), `attachments` (every blob's sha256 against its name; the referenced set equals the manifest's digest and is present), `audit-chain` (the runtime's own `audit:verify` against the quarantine; **skipped and reported** when not configured), `git` (fsck + every repository's HEAD, refs digest, unpushed commits, staged/modified/untracked lists equal to the manifest). **RTO** = wall time from drill start to the end of verification (restic check, restore, database load, all checks). **Backup age** = drill start − checkpoint instant. No SLA is derived. | §11: measured, not invented. A drill that hides a skipped check would claim recoverability it didn't prove. |
| BK-13 | **Replacement** (`docs/runbooks/replacement.md`): fresh provisioning (new identities). `destination adopt` joins the old repository with the kit's password and never re-initializes. `quarantine apply` verifies the checkpoint like a drill, then restores into the empty layout and database and leaves a marker `/persist/backup/quarantine.json`. The runner units don't start while it exists, and the runtime must run no schedules, automations or outbound effects (runtime requirement). The database stays read-only. `quarantine release` needs every required item resolved: `old-appliance` (decommissioned \| credentials-rotated \| lease-expired), `revocations` (re-applied from the owner's knowledge and control's revocation metadata), `endpoints` reviewed, `provider-logins` re-verified, `external-outcomes` (runs/pushes `uncertain` or newer than the checkpoint reconciled; nothing replayed), `identity-repin`. **Old-appliance policy:** relay revocation can't stop an old machine's direct provider or Git calls. Confirmed decommission (factory reset or secure erase, NX) is strongest but needs the old device. Credential rotation works without it and is required when the old device is lost or stolen. An execution lease (effects only while a control-signed lease is fresh) stops only honest stale devices, costs offline execution after the lease TTL and a cloud dependency, and is **not relied on** (future manager/runtime feature). No exactly-once claims anywhere. | §11 replacement requirements, and the offline-versus-revocation tradeoff made explicit. |
| BK-14 | **Recovery/export tool** (`whombat-recovery`): a static CLI authorized by the kit's backup section, needing no Whombat cloud and no appliance. `list`, `verify` and `export` work over REST or a local copy of the repository; `export-disk` works from an unlocked `/persist`, copies the data directory and never starts it in place. It never writes to a repository. Open formats: custom and plain SQL dump, file trees, working trees with relocated git metadata, one `git bundle` per repository, the signed manifest, `verification.json` and `README.txt`. Credentials and the master key only with `-include-secrets`. It ships in the signed recovery UKI (`nix/profiles/recovery.nix`, the `whombat-export` slot of NX-13) and runs on any Linux machine. It is not a hosted or local UI. | §11: customer-controlled recovery and service exit. |
| BK-15 | **Kit and password custody.** The repository password is 256-bit random, generated on the appliance by `destination set`. It is stored 0600 under `/persist/backup/secrets` (LUKS, NX-07) and sealed with `systemd-creds` (TPM2 + host key) by the NixOS unit's `ExecStartPre=+`; the service reads `$CREDENTIALS_DIRECTORY/restic-password`. **Kit backup section** (`whombat.backup-recovery-material/1`): `applianceId`, `generation`, `createdAt`, `repository` (no credentials in the URL), `restUser`/`restPassword` (the append-only credential: with it the kit alone reaches the backups, and it can't delete), `repositoryPassword`, `repositoryId`, `manifestKey`. The client fetches it over the E2E session (owner-only; `GET /v1/recovery-material` answers only the runtime uid) and merges it with the client-generated recovery key into `whombat.recovery-kit/1` with a transcription checksum. `generation` bumps on every destination or password change, and the client must then issue a new kit. Rotation: `restic key add` works append-only, but `key remove` needs the maintenance side. A leaked old key file plus password still opens the repository until it's removed, and the master encryption key only changes with a new repository. | MA-03/MA-04 custody table, with the limits stated. |
| BK-16 | **Billing boundary.** Suspension of the subscription never wipes data, never stops a running checkpoint or drill, and never blocks export or recovery. The backup service has no control-plane dependency at all: it talks only to the local runtime, local PostgreSQL and the customer's destination, and the recovery tool works offline with the kit. Any future entitlement policy (e.g. no new off-device checkpoints after a long suspension) must be decided and documented separately, and may not affect existing backups, drills, export or recovery. | §11. |
| BK-17 | **Pre-migration checkpoint** (§9, MD-06, the manager's MG-18 proposal accepted as is): the manager, holding its own drain (scope `all`), calls `POST /v1/checkpoints {reason: "migration", releaseId, migrations[], underDrain?}` on `/run/whombat-backup/api.sock`. Only the manager uid may ask. It gets `200 {ref, verified: true, id, seq, snapshotId, manifestSha256, createdAt, schemaVersion}`, or `409` busy, `412` unprotected, or `502 {stage, reason}`, and then defers. The service doesn't drain again, since a second caller would be refused as busy; it confirms `RuntimeHealth.draining` before and after. The manifest records `reason: pre-migration`, the release, the migrations and the drain id. **Verified** means re-read from the destination without the local cache: `restic check`, the manifest authenticated and bound to the snapshot, and the dump streamed back and hashed. `ref` is the checkpoint id the manager passes to `whombat migrate --checkpoint`. Without a configured destination it fails (`412`): a local pre-migration repository is an open item. Suggested addition for the manager: send its drain `requestId` as `underDrain`, so the manifest names it (otherwise `manager` is recorded). | MD-06 steps 1–3 with one migration authority. |

## Destinations beyond the REST server, restore onto a fresh box (robust updates UP-F1, UP-F2; 2026-09-28)

Branch `ru-backup`. The owner chooses the destination in the app after the claim (UP-F1); the session op
`backup.configureDestination` passes the contract's input (contracts 0.22.0, CT-142) unchanged to
`PUT /v1/destination`. Runbooks: `docs/runbooks/backup.md` (a section per kind), `restore.md` (onto a fresh box).
VM test: `vm-tests/backup-destinations.nix`.

| # | Decision | Reason |

| BK-18 | **S3-compatible destinations**: `s3:https://host[:port]/bucket[/path]` (`http:` accepted for a NAS on the home network; the data is restic-encrypted either way, and SigV4 never sends the secret), with `s3AccessKeyId`, `s3SecretAccessKey` and an optional `s3Region` (`AWS_DEFAULT_REGION`). The credentials reach restic **only in its environment** (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, plus `AWS_SHARED_CREDENTIALS_FILE=AWS_CONFIG_FILE=/dev/null` so no other credential source is ever consulted); `/proc/<pid>/environ` is readable only by the backup user and root. The key id is in `destination.json` (0600, never in the status), the secret is a sealed secret (BK-23). `allowInit` lets restic create the bucket. **Append-only: `not-enforced`**, always (answer and status): with the key, anyone can delete or overwrite every object, i.e. every backup, and the kit holds the key. The runbook recommends bucket versioning with a lifecycle rule (or Object Lock in governance mode) so a deletion only hides versions for the retention time; not prescribed or probed, since restic's maintenance with Object Lock is untested here (BK-09). | The cheapest off-site destination for most owners. Being explicit that the key can delete is the honest status; a probe could not tell a versioned bucket from a plain one. |
| BK-19 | **SFTP/NAS destinations**: `sftp:host:/path` or `sftp://host[:port]//path` (restic's forms), the user in `sftpUser`, never in the URL. **The box's own Ed25519 key**, made on the first `GET /v1/ssh-public-key` (`backup.sshPublicKey`) or destination set, is a sealed secret like the repository password; only `{publicKey, fingerprint}` leaves the box (`publicKey` ends `whombat-backup@<applianceId>`). **The host key is pinned**: a known_hosts-style line as given, or a `SHA256:` fingerprint the scanned key must match, or trust on first use (`ssh-keyscan`, the best type: ed25519 > ecdsa > rsa), and the fingerprint is answered (`hostKeyFingerprint`) for the owner to compare with the NAS's. A changed host key is refused until the owner sets the destination again (no silent re-pin). restic runs `-o sftp.command=` with **ssh hardened**: `-F none`, `BatchMode`, `IdentitiesOnly`, `IdentityAgent=none`, only the box's key, `StrictHostKeyChecking=yes` against a one-line `UserKnownHostsFile` (`GlobalKnownHostsFile=none`, `UpdateHostKeys=no`, `CheckHostIP=no`, `VerifyHostKeyDNS=no`), `HostKeyAlgorithms` = the pinned key's type (RSA only with SHA-2), no forwarding, no `ControlMaster`/`ProxyCommand`/`ProxyJump`/`PermitLocalCommand`, `ConnectTimeout` and keep-alives; user, host and every path are checked to contain nothing the command-line split could read differently, and the environment is empty of the caller's (no `SSH_AUTH_SOCK`). The OpenSSH formats are written in Go (`backup/pkg/sshkey`, checked against `ssh-keygen`), not `x/crypto/ssh`, which would change the module's vendor hash. The kit carries `sftpUser`, `sftpPrivateKey` (OpenSSH PEM) and `sftpHostKey`. Append-only `not-enforced`: the key can delete what it wrote; the runbook recommends an SFTP-only account and the NAS's own snapshots. | The key never leaves the box except in the owner's kit; pinning is what makes an SFTP destination on a home network safe against a spoofed NAS; TOFU plus a shown fingerprint is what an owner can actually do. |
| BK-20 | **The backup disk** (`disk:`, exactly): a filesystem labelled `WHOMBAT-BACKUP` (ext4 or btrfs), made by the owner or, with `allowInit`, by the root helper `whombat-backup disk-init` behind a path unit. The service can only *ask* (`/persist/backup/disk-init/request.json`); the helper takes no device name and formats only when **exactly one** whole disk is empty and unused: not read-only, ≥ 1 GiB, no partitions, no holders, not mounted, no signature (`blkid -p`), its first MiB all zeros; more than one or none is refused with a sentence for the owner. `mkfs.ext4 -L WHOMBAT-BACKUP -m 0 -E root_owner=<backup uid>`. The NixOS module **mounts it whenever it is attached** (udev asks for `persist-backup-disk.mount` when the label appears, at boot or later; block-device mounts stop when the device goes; `nodev,nosuid,noexec,noatime`; never needed for boot), not only while backups run: the API is long-running and takes pre-migration checkpoints, the status must say at any time whether the disk is there, and mounting on demand would need a root helper to mount into the services' namespaces. The repository is at the fixed `<mount>/whombat/repository` (a replacement or `whombat-recovery -repo-dir <mount>` finds it). **The status says when the disk is missing** as soon as it is read (`lastFailure` "The backup disk (labelled WHOMBAT-BACKUP) isn't attached…", state `failing`), and stops when it is back; a checkpoint fails its preflight with the same sentence. It is not off-site: on Proxmox the disk should live on other storage than the VM's. | The one destination that needs no account anywhere; on the Proxmox platform “attach a disk” is a two-click act, formatting it is not, so the box does it — but only for a disk that is provably blank and unambiguous. |
| BK-21 | **Owner-facing failures and no 15-minute waits.** Every failure to reach or open a destination is a sentence the owner can act on, in the status (`lastFailure.reason`) and the API answer (`destination_failed`): wrong REST user/password, the bucket refused the key, the bucket doesn't exist, another region, the server refused this Whombat's key (add it to `authorized_keys`), the host key doesn't match (compare fingerprints; maybe interception), the folder doesn't exist, the certificate isn't trusted, unreachable, full, the disk isn't attached, the password doesn't open the repository; the technical cause follows in parentheses, **redacted** of every secret the restic wrapper knows. restic retries every backend error for up to 15 minutes: opening a repository (`cat config`, `init`) now stops at the first retry, and any run stops at a retry no retry heals (bad signature/key, missing bucket, access denied, 401/403, host key failure, `Permission denied (publickey)`); a real upload keeps restic's retries for transient errors. | Found by the S3 tests: a wrong secret answered after 15 minutes with “context canceled”. |
| BK-22 | **Sockets of the backup group may open TCP connections to any port** (`meta skgid <whombat-backup gid> meta l4proto tcp accept` in the egress chain, from `backup.nix`): the backup user's processes (their primary group) and a root restore at the console, which keeps uid 0 and takes that gid (BK-24); nothing else runs with it (no other user has it as primary group, and taking it needs root). Destinations are the owner's servers on their own ports (SFTP 22, rest-server 8000, MinIO 9000), on the internet or the home network; the allowlist (443) refused them all. The backup user reads all data anyway, so a wider egress adds no reach to data it doesn't already have; the runner, the browser and the server keep their rules. | Without it no SFTP or LAN destination could work on a real box, nor a restore at the console. |
| BK-23 | **Destination secrets** (repository password, REST password, S3 secret, the SSH key): written by the service as plain 0600 files under `/persist/backup/secrets` (encrypted `/persist`), sealed by `whombat-backup-seal` (systemd-creds, TPM2 + host key) into `<name>.cred` (in the root-only `/persist/backup-root` since BK-26) and shredded; every backup unit loads all four (`restic-password`, `rest-password`, `s3-secret`, `ssh-key`). Read **plain first** (a value written since the last seal is the newest), else the credential, **an empty credential is absent** (the seal unit's placeholder for a secret never set). This fixes a bug: the API read the empty `restic-password` placeholder as the password and wrote to the read-only credentials directory, so no destination could be set through the app. **A new destination is verified before it replaces anything**: its secrets are staged, restic opens or creates the repository with them, and only then are they moved into place and `destination.json` written; a failed attempt leaves the working destination and its secrets untouched. `caCert` is the contract's PEM (it was treated as a path), kept as `/persist/backup/ca.pem`. | The seal lifecycle BK-15 designed for the password, applied to every secret; an owner mistyping a key must not break the backups that work. |
| BK-24 | **Restore onto a fresh box** (UP-F2; `restore.md`), the documented commands, as root at the console: stop the runtime; `destination adopt -kit` (the kit's repository, password, REST/S3 credentials or SFTP key and host key, and the old manifest key, kept as `keys/adopted-manifest.pub`); `quarantine prepare -admin-dsn …` (the fresh install's files moved to `/persist/whombat-set-aside-<time>/`, its database renamed to `<db>_set_aside_<time>` and an empty one created owned by `whombat`: nothing deleted until the release, BK-40, BK-44); `quarantine apply -dsn … -admin-dsn … [-kit]` (trusts the adopted key, or the kit's with its newest-checkpoint check; `pg_restore --role whombat` so the runtime's role owns what a superuser restores); resolve; `release`. Fixed on the way: `apply` renamed each restored tree over its live directory, which fails across btrfs subvolumes (`EXDEV`) and would have replaced the subvolumes; it now fills the existing directory (renames, else extent-clone copies). ## Security review part 2 fixes (MA-21; 2026-09-25)
- **Quarantine first (M-1, MA-21e).** `quarantine apply` writes and fsyncs `quarantine.json` (`phase:
  "restoring"`) before any data is restored; the runtime units get `WHOMBAT_QUARANTINE_FILE` and the runner
  doesn't start while it exists. The database is made read-only and every other session is terminated before and
  after `pg_restore` (which writes with a session override). A restore that stops part-way leaves the marker
  (with the error); it cannot be released, and is undone from its set-aside journal (BK-40, BK-43).
- **Manifest paths (M-4, MA-21f).** Manifest verification accepts only the layout's sources (`home`, `workspaces`,
  `credentials`, `hermes`, `agent`, `secrets`, and `hosts` where the hosts service runs) at `files/<name>` and
  repositories at clean relative paths below `files/`. The export additionally
  checks every output path (no `..`, not absolute, no symlinked component below `-out`).
- **Least privilege (M-5, MA-21f).** Every backup unit sees a read-only tmpfs over `/persist/identity` (only
  `device.json`, `management.pub`, `content.peerid` bound in) and over `/var/lib` (Secure Boot keys, disk-policy
  key, helper state, systemd's credential host key); the runtime's credential directories and `/boot` are
  inaccessible. The API and checkpoint job keep `CAP_DAC_READ_SEARCH` (pre-migration checkpoints read staged
  snapshots of other owners); making staging readable to the backup user instead is a later option. The API
  returns only the kit's backup material (no identity material exists in its namespace).
- **Withheld checkpoints (I-2).** The kit material records the newest checkpoint (`head`: seq, manifest sha256,
  time). `restore.Run{ExpectHead}` adds `newest-checkpoint`, failing when the destination's newest authentic
  checkpoint is older or differs at that sequence; `whombat-recovery verify|export` use the kit's head
  (`-ignore-kit-head` exports what the destination has). Limit: a kit only knows the head at the time it was
  fetched; newer checkpoints made after that are covered only by the appliance's own record (a live appliance)
  or a newer kit.
- **Export in the recovery environment.** `export-disk` replaces the copied cluster's configuration (the
  appliance's `postgresql.conf` is a store symlink, `pg_hba` peer-based) and runs PostgreSQL as `-pg-user`.
