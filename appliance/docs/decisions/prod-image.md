# The first production image: a self-installed Whombat on a Proxmox VM — decisions PI-nn

Decided with John on 2026-09-27. John wants to run a production Whombat at home, installed from an ISO onto a
Proxmox VM (x86_64), claimed against app.whombat.com. Nothing in the repo can build that today: a prod build refuses
the stand-in runtime (NX-20, `nix/modules/runtime.nix`), needs a pinned prod licence key set (NX-38), refuses
self-registration because a self-installed box has no disk recovery key (CC-10, `nix/modules/provisioning.nix`), and
has no production TUF root to pin (X-05, HZ-12). This record says how each gap is closed for this first box and
what must change before anyone else installs one.

Component decisions refine this file: NixOS NX-41+, manager MG-35+ (if any), control CL-54+ / HZ-15+, runtime
MR-72+ (if any), harness IN-67+.

**Scope: a home pilot for one organization.** Two of John's choices (plain disks in the VM, update keys online on
the prod host) are deliberately weaker than the hardware design. They are acceptable because John owns both the
Proxmox host and the Hetzner host. PI-12 lists what must change before a second organization installs an image.

## Choices John made

| # | Decision | Reason |
|---|---|---|
| PI-01 | **Delivery is the installer ISO** (`installer-iso`), written to the Proxmox ISO store and booted once; `whombat-install` writes the virtual disk. No prebuilt qcow2. | Keeps the one install path the VM tests already cover (identity, seeds and machine-id are made on the device, `checks.image-no-secrets`). |
| PI-02 | **A new platform profile `proxmox-vm` with no guest encryption.** `whombat.platform = "proxmox-vm"` sets a new storage mode `host-encrypted`: the same GPT layout and btrfs `/persist` subvolumes and quotas as NX-07, without LUKS and without TPM enrolment. Secure Boot is not required (`requireSecureBoot = false` for self-provisioning, `whombat-tpm-seal` absent). Lanzaboote stays the boot loader because boot counting and fallback depend on it (NX-04); its keys are generated but not enrolled. `host-encrypted` is allowed in prod **only** together with `proxmox-vm`; the dev mode `plain` stays refused in prod. | Host updates reboot unattended (`activate-host-on-reboot`, MG verify window); a passphrase at every boot would stall or roll back every host update. Encryption at rest becomes the Proxmox host's job. |
| PI-03 | **What `host-encrypted` means for the operator** (written into the install runbook, shown on the console at first boot): put the VM disk on encrypted storage (ZFS native encryption or LUKS on the host), encrypt backups (`vzdump` to Proxmox Backup Server with client-side encryption), and **never restore a Proxmox snapshot or backup of a running Whombat** — it rolls back the licence high-water mark, TUF rollback protection, session and receipt state. Recovery uses Whombat's own backups (W3-BK, `docs/runbooks/restore.md`). | Every key the box holds (master key, device and content identity) is plaintext inside the VM disk; the host is the protection. |
| PI-04 | **Disk recovery key: shown once on the console.** A self-installed box generates the 256-bit modhex key at self-provisioning (as `whombat-provision` does for factory boxes) and the console shows it once, with a QR code, before the claim code: “Write down this recovery key. It is shown only once.” The operator types its last group to continue; only then does the console move to the claim state. It is never sent anywhere or logged. With `host-encrypted` there is no LUKS slot for it: it gates the recovery menu's data-touching actions and factory reset (NX-10, NX-25) and is stored as a hash (Argon2id) in `/persist/secrets`. | Closes the CC-10 deferral for self-installed boxes; one path whether or not the disk is encrypted, so a later encrypted profile adds a keyslot without a new ceremony. |
| PI-05 | **Update keys online on the Hetzner host (“online-pilot” custody).** TUF root, targets, snapshot, timestamp and clients keys are generated **on the prod host** into `/etc/whombat/secrets/tuf/` (0600, next to the other host secrets) with threshold 1 each. `release-tools` gains an explicit prod mode that refuses to run unless `--custody online-pilot` is given and the key directory is on the host; it still refuses dev keys in prod and prod keys in dev (MA-14). Root expiry **120 days**, so the pilot root must be rotated (PI-12) or re-signed within four months. `updates-release-signing.md` stays the target design. | John's choice: fastest start. Consequence written here: whoever controls the Hetzner host can sign a release that runs on John's box. Root rotation onto offline keys later is the tested path (three consecutive rotations over 200 days offline, V-15/V-21). |
| PI-06 | **Private download link.** The ISO and its `SHA256SUMS` go to the prod host under `updates.whombat.com/install/<version>/`, served only with an expiring HMAC link (`?exp=…&sig=…`, key in `/etc/whombat/secrets/install-link`, default 7 days). `infra/hetzner/deploy.sh iso <version>` uploads it; `deploy.sh iso-link <version> [--days N]` prints a link. Anything else under `/install/` answers 404. The ISO is generic (no identity, no org), so a leaked link lets someone install a box that still needs an org with `selfInstall` and a subscription to claim (LC-15). No in-app download yet. | John chose a private link over “just me” and over public distribution; D-06 (public distribution) stays open. |

| PI-26 | **The installer's files are compared by digest** (2026-11-19, R1 #14; amends PI-24, PI-25). `release/upload-iso` asks the public site for each file's ETag (the MD5 of a one-PUT object or a copy of one; with a query of its own, so no cache answers) and compares it with the local file's, never the size: a release's ISO and `.sha256` are checked before either is sent; the same digest is left, a missing one is sent, another digest under the same release id stops the run with nothing sent (a release id never names two installers), and a site that says no ETag can't be compared and is not written over. After the upload it checks the release's two files, and then both `installer/latest/` files, as the site serves them; only then does `installer/latest.json` go up (and is checked too). The fixed `installer/latest/` pair only moves forward (R2 B2): when the site's `latest.json` names a newer release, the run leaves the fixed links and `latest.json` as they are, says so and exits 3 (`promote` takes that as done: a runtime-only release keeps its host's installer, a newer host's stays); a failed upload of either fixed file is tried twice more, and failing still stops the run before `latest.json`, which a run again puts right; before `latest.json` the served checksum file must name the ISO's sha256. The two fixed links never name different ISOs (R3 B2): the swap puts the checksum first, checks it as served, then the ISO, checks it, then the pair, and only then `latest.json`; a step that fails puts the previous release's pair back from its own files (`installer/<previous id>/`, copied on the bucket, a file left that was never swapped), or removes the fixed files when there was none, and leaves `latest.json`. A `latest.json` the site can't give (a status other than 200 or 404, an unreadable body, no release id) stops the run before anything changes; only a 404 is no `latest.json`. | A checksum file is the same length for every ISO, so sizes said nothing; the website's links must never name a checksum of another ISO. |
