# Agent ↔ hub protocol

Message schemas: `internal/proto`. Framing: `internal/wire`. Interfaces on
the agent side: `internal/agent/agent.go`.

## Listener

The hub has a dedicated **agent listener** (default `:8443`), always TLS 1.3,
with a server certificate issued by the hub's own CA (created on first start
in the data dir; ECDSA P-256; CA valid 10 years). The TLS chain the hub
presents includes the CA certificate. Client certificates are requested but
only required on `/agent/v1/connect`.

Agents trust the hub by **pinning the CA**: `ca_sha256` = lowercase hex
SHA-256 of the CA certificate's DER. On first contact the agent accepts the
chain only if its root hashes to the pin, then stores the CA in
`/etc/whombat-agent/ca.crt` and verifies the chain against it from then on
(hostname is not checked: the CA is private and pinned).

## Enrollment

1. An admin creates an enrollment (in Whombat: Add a server) → token
   (single use, 1 h) and an install command. Headless it fetches from the
   agent listener with the listener's key pinned:
   `curl -fsSL --insecure --pinnedpubkey 'sha256//<key>' https://<agent host>:<port>/install.sh | sudo sh -s -- --token <token>`;
   with the UI, from the UI origin:
   `curl -fsSL <ui-origin>/install.sh | sudo sh -s -- --token <token>`.
   `install.sh` is generated by the hub with the agent URL and CA pin baked
   in; it downloads `/download/whombat-agent-linux-<arch>` from where the
   script came from (pinned like the script on the agent listener; the
   SHA-256 is checked either way), installs `/usr/local/bin/whombat-agent`,
   the service, and runs `whombat-agent enroll --hub <wss url> --ca-sha256
   <pin> --token <token>`.
2. `whombat-agent enroll` generates an ECDSA P-256 key
   (`/etc/whombat-agent/agent.key`, 0600) and sends:

   `POST /agent/v1/enroll` (no client cert), JSON
   ```json
   {"token": "...", "csr": "<PEM CSR>", "hostname": "thetitan", "machine_id": "...",
    "os": "Debian GNU/Linux 13 (trixie)", "address": "10.100.0.7", "agent_version": "0.1.0"}
   ```
   → `202 {"enrollment_id": "en_…", "poll_secret": "…", "state": "pending"}`; `401 {"code":"invalid_token"}`.
   A **pre-approved** token (Whombat's Add a server, `POST /enrollments
   {"approve": true}`) is approved in this request: `202 {…, "state":
   "approved", "server_id": "pve-03"}`, and the first poll returns the
   certificate. Hubs before this send no `state`.
3. The agent polls at once and then every 5 s (up to the token lifetime):
   `GET /agent/v1/enroll/{id}` with `Authorization: Bearer <poll_secret>`
   → `202 {"state":"pending"}` | `200 {"state":"approved","server_id":"thetitan","certificate":"<PEM>","ca":"<PEM>"}` | `403 {"state":"rejected"}`.
4. On approval the agent writes `agent.crt`, `ca.crt`, `agent.toml`
   (hub URL, pin, remote control **off**), and exits 0; systemd then starts
   `whombat-agent run`.

Client certificates: CN = server id, URI SAN `whombat:server:<id>` (the hub
also accepts Rackoon's `rackoon:server:<id>`), lifetime 30 days. The agent sends a CSR in `Hello` when less than 10 days
remain; the hub returns the new certificate in `HelloAck`. Revocation =
deleting the server (the hub refuses certificates whose serial is not the
server's current one).

## Connection

`GET /agent/v1/connect` — WebSocket upgrade, subprotocol
`whombat.agent.v1` (the agent also offers Rackoon's `rackoon.agent.v1`, and
the hub accepts either: the protocol is the same), client certificate
required. The WebSocket carries
binary messages; both sides wrap it as a `net.Conn`
(`websocket.NetConn`) and run yamux on it with `wire.YamuxConfig()`. The
**agent is the yamux client**, the hub the yamux server; both may open
streams.

Streams (first frame: `proto.StreamHeader`, then length-prefixed CBOR
messages via `wire.WriteMsg` / `wire.ReadMsg`):

| Kind | Opened by | Flow |
|---|---|---|
| `control` | agent, once | agent: `Envelope{hello}` → hub: `Envelope{hello_ack}` → agent: `report` every 10 s (+ early report after an event), `backfill` batches (≤ 500 samples each, oldest first, after a reconnect), `event`; hub: `checks`, `hub_addrs`, `hub_move`; either side: `ping`/`pong` |
| `action` | hub | hub: `ActionRequest` → agent: `ActionResponse`; close |
| `thumbnail` | hub | hub: `ThumbnailRequest` → agent: `ThumbnailResponse`; close |
| `console` | hub | hub: `ConsoleRequest` → agent: `ConsoleResponse`; if OK, both sides switch to console frames (`wire.FrameWriter`/`FrameReader`) until either side closes the stream |

Heartbeat: any frame on the control stream. The hub marks the server
offline after 60 s without one. Reconnect backoff 1 s → 60 s with jitter.

Unknown message types on the control stream are ignored by both sides
(every agent since the first one), and unknown CBOR keys too: new messages
and fields are additive.

## The hub's addresses and finding the hub (HS-170…HS-176)

`HelloAck.Addrs` (`addrs`, wss URLs, omitted when empty) lists every
address of the agent listener an agent may reach: the agents' URL first
(`--agent-url`, auto's LAN address), then the hub machine's own interface
addresses on the listener's port — IPv4, then global IPv6; not loopback,
link-local, or container, VM and VPN interfaces (`wbc*`, `incusbr*`,
`lxcbr*`, `lxdbr*`, `docker*`, `br-*`, `veth*`, `virbr*`, `cni*`,
`flannel*`, `cali*`, `vxlan*`, `tailscale*`, `wg*`, `zt*`, `tun*`, `tap*`,
`kube*`, `podman*`; `internal/netaddrs`) — and last the addresses of the
Tailscale interface (`tailscale*`) in Tailscale's ranges (100.64.0.0/10,
`fd7a:115c:a1e0::/48`): the way in for servers that reach the hub only over
the tailnet, a fallback for the others; at most 16, the tailnet's kept. A listener bound to
one address names only that one. The hub looks every 30 s and sends
`hub_addrs` (`HubAddrs{addrs}`, the same list) to every connected agent
that was told another list.

The agent keeps the list in `<state_dir>/hub-addresses.json` (0600,
atomic; `{"addrs": […], "updated_at": "…"}`). When dialling its saved
`hub` fails with a network or TLS error — no HTTP answer over a verified
connection; an HTTP 401/403 or `HelloAck.Rejected` is a rejection and
never starts a search — three times in a row over at least 60 s, it
searches: first the remembered addresses (not the saved one), then its own
networks: every up, non-loopback interface that is not a container, VM or
VPN interface (the list above; `vmbr*` and `br0` count) with a private
IPv4 address, its subnet when the prefix is /22 or longer, else the /22
around the address, on the ports of the saved and remembered URLs (8443
when there are none), without its own and the saved address. A probe is a
TCP connect (300 ms, 64 at a time) and a TLS handshake verified against
the stored CA (the connection's check; no client certificate is sent). The
first that passes wins: the agent rewrites only the `hub = …` line of
`agent.toml` (atomically, mode and owner as they were, every other byte
kept; on Unraid the flash copy), logs “found the hub at …” and connects.
While it stays unconnected it searches again after 2, 4 and 8 minutes,
then every 15. A connection, or any answer from the hub, ends the streak.

## Moving to another of the hub's addresses (HS-221, HS-222)

`hub_move` (`HubMove{url}`, hub → agent) asks the agent to connect to the
hub at `url` (one of its addresses, a wss URL) before the one it uses goes
away; the hub sends it on `POST /hub/agents/move` to every connected agent
not already there. The agent ignores it when `url` is the address it uses
or a move is under way. Otherwise it dials `url` with its usual TLS (the
pinned CA, not the host name; its client certificate) and says hello,
within 10 s. Once the hub accepted that hello, the agent saves `url` as
its hub (the `hub = …` line of `agent.toml`, as a found address,
HS-176), carries on with the new connection and closes the old one (log
“moved to the hub at <url>”); the hub, on the new hello, closes the old
connection too. Any failure (no answer, TLS, a rejected hello) is logged,
and the old connection and the saved address stay. Agents older than
`hub_move` ignore it and find the hub by searching once the old address
stops answering.

## Local enforcement on the agent

Before calling the broker, the runtime checks `agent.toml`:
`[remote_control] console = true` for console and thumbnail streams,
`power = true` for action streams (except `ctrl_alt_del`, which needs
console). The host's own screen (a Mac's: its `vnc` console and its
thumbnail) needs `host_shell` instead, like the host's root shell.
Otherwise it answers with code `remote_control_disabled`. The policy is
reported in every `Report.Policy`.

Limits on the agent: at most 20 concurrent console sessions; console frames
≤ 1 MiB.

## Backfill

The agent keeps samples (`Report.Series()` + timestamp) for up to 24 hours
(8640 samples, newest kept) in memory and in `state_dir/buffer.cbor`
(format version 2 with shared series names, rewritten every minute, so an
agent restart keeps them; version 1 files are still read, unreadable ones
are renamed `*.corrupt`) while the hub is unreachable. On Unraid the
buffer stays in RAM. After reconnect it sends
them as `backfill`, oldest first. The hub ignores samples whose
(series, timestamp) already exists.

## Hub behavior (as implemented; additive)

- `POST /agent/v1/enroll`: 400 `{"code":"invalid_csr"}` when the CSR is not
  ECDSA P-256/P-384 or Ed25519 or its signature is wrong; 429
  `{"code":"rate_limited"}` after repeated bad tokens from one address.
- `GET /agent/v1/enroll/{id}`: 404 for an unknown id or a wrong poll secret;
  410 `{"state":"expired"}` when nobody approved within 1 h of the request.
- `/agent/v1/connect`: 401 without a verified client certificate; 403 when
  the server is unknown (deleted) or the serial is not the current one.
  The hub closes an older connection of the same server when a new one
  arrives.
- **After a restore** (HS-180): for 14 days after the database was
  restored (`restored_at`), a certificate of a server the database knows,
  signed by the CA, unexpired, with a later expiry than the stored one (the
  agent renewed after the backup was made), is accepted when `Hello`'s
  machine id is the server's; it becomes the server's certificate (audit
  `agent.certificate_adopted`, outcome `ok`; another machine id: `denied`,
  code `machine_id_mismatch`, and `HelloAck.Rejected`). Afterwards the
  normal rule.
- `HelloAck.Rejected` is set for a `ProtocolVersion` other than
  `proto.Version` (and "certificate revoked" when the server was deleted
  while connecting). After a renewal the certificate the agent connected
  with stays valid until the agent connects with the renewed one (a lost
  `HelloAck` does not lock it out); from then on only the renewed serial is
  accepted.
- Clock skew = `Hello.Clock` − hub time. Beyond ±30 s the hub shifts sample
  timestamps by the skew. Samples older than ~23.5 h (raw retention) or more
  than 2 min in the future are dropped; a report with an unusable `At` is
  stored at the hub's receive time.
- Reports are ingested at most 5 in a burst, then one per 2 s; extra reports
  still count as heartbeats. Backfill messages may carry up to 5000 samples
  (500 recommended); `(series, timestamp)` pairs already stored are ignored.
- The hub sends `ping` every 30 s (body: CBOR int, hub time in unix ns) and
  answers the agent's `ping` with `pong` carrying the same body.
- Untrusted input: strings are truncated, non-finite numbers dropped, list
  lengths bounded (5000 guests per platform), duplicate guest ids ignored.
- Console streams: the hub sends its own `status` control frame to the
  browser after a successful `ConsoleResponse` (the agent may send its own
  too), forwards `resize`, `open`, `close` and `ping` controls (normalized
  JSON; `activity` is consumed by the hub) and forwards from the agent only
  `status`, `opened`, `closed`, `pong` and `error` controls. Closing the
  browser side closes the stream (FIN); the hub closes the stream when it
  ends a session.

## Agent behavior (as implemented; additive)

- **Enroll**: `whombat-agent enroll --hub wss://… --ca-sha256 … --token …`
  (`--token -` reads it from stdin). Refuses `ws://`; refuses to run when
  `agent.crt` exists (`--force`). Writes `agent.key` (0600), `agent.crt`,
  `ca.crt` (both checked: CA hash = pin, certificate = our key and issued by
  the CA) and `agent.toml` (0600, remote control off). Polls at once, then
  every 5 s; 404, 410 and 401 on the poll end the enrollment with an error.
  When the hub answers `state: "pending"` (or nothing) it prints `whombat-agent:
  waiting <enrollment id>` on stdout (install.sh's result line).
- **Identity** (`whombat-agent whoami [--check [--hub URL]]`): prints
  `<server id> <CA SHA-256>`; `--check` adds `known`, `removed` or
  `unreachable`: a plain mTLS `GET /agent/v1/connect` is 403 for a deleted
  server or revoked certificate (`removed`; an expired certificate too),
  400/426 for a known one (no WebSocket handshake), anything else
  `unreachable`.
- **Reports**: every 10 s; a collector event is forwarded at once and
  triggers an extra report 2 s later (debounced). Right after `hello_ack`
  the agent backfills, then collects a fresh report. Samples are buffered
  when the connection is down or the report queue is stuck. Pings from the
  hub are answered with the same body.
- **Renewal**: a certificate in `HelloAck` is used immediately (also when
  writing `agent.crt` fails, which is logged as an error).
- **Codes** (`Code` in the RPC responses, `error.code` in console
  controls): runtime `remote_control_disabled`, `too_many_sessions`,
  `timeout`, `open_failed`, `unsupported`; broker `invalid_request`,
  `inventory_unavailable` (no report yet), `unknown_guest`,
  `unsupported_action`, `unsupported_protocol`, `protocol_unavailable`
  (message = reason), `guest_not_running`, `no_screen`, `platform_error`,
  `capture_failed`, `busy`.
- **Validation**: the guest must be in the latest report, the protocol in
  its `Console.Protocols` (not in `Unavailable`), and running (checked live).
- **Actions**: VMs `start|shutdown|reboot|force_stop|ctrl_alt_del`,
  containers `start|restart|stop` (`shutdown`→`stop`, `reboot`→`restart`
  for containers and vice versa for VMs). One action per guest at a time;
  the state is polled until it matches, at most 60 s (`timeout` with the
  observed `State` otherwise). Container `stop` is graceful with a 30 s
  timeout, then forced. Incus has no send-key: `ctrl_alt_del` →
  `unsupported_action` (send it through the console).
- **Thumbnails**: `max_w` 0 = full size; `fmt` `jpeg` (quality 75) or
  `png`. Containers → `no_screen`. Incus 6.0 LTS cannot take VM screenshots
  (its screendump file is not writable for QEMU); the agent then renders
  the screen over a short SPICE connection (raw and LZ images; QUIC/GLZ →
  `capture_failed`) and answers `busy` while any SPICE client is connected,
  because a new SPICE client disconnects the existing one.
- **Consoles**: the agent sends `status` (`connected`, protocol, resolution
  when known) first. Terminals (`shell`, `tty`, `serial`): data on channel
  0; `resize` applies to `shell`/`tty`; the stream ends when the shell exits
  or the console detaches. `vnc`: the agent completes the RFB handshake with
  the guest (None, VNC auth with the password from the platform, VeNCrypt
  x509) as a shared client and presents RFB 3.8 with security type None to
  the browser. `spice`: channel 0 is the main channel; `{"type":"open",
  "channel":N}` opens another SPICE connection (`opened`, or `error`
  `open_failed` + `closed`), at most 16 per session; `close` closes one;
  the agent sends `closed` when the guest side ends a channel and ends the
  session when the main channel ends. In every channel's link phase the
  agent replaces the browser's encrypted ticket with its own encryption of
  the real one, so the browser never sees SPICE passwords. A further
  `status` with `resolution` is sent when the display channel reports the
  primary surface size.

| Platform / protocol | Agent attaches to |
|---|---|
| Incus container shell | `POST /1.0/instances/<n>/exec` (PTY, `/bin/bash -l` or `/bin/sh -l`, TERM=xterm-256color), `window-resize` on the control websocket |
| Incus container tty, VM serial | `POST /1.0/instances/<n>/console` type `console` |
| Incus VM spice | `POST /1.0/instances/<n>/console` type `vga`, one websocket per SPICE channel |
| libvirt vnc / spice | endpoint from the live domain XML (Unix socket, or loopback port whose listener must belong to the domain's QEMU); password from the secure XML; TLS-only SPICE is `Unavailable` |
| libvirt serial | the domain's serial PTY (or bound Unix socket) |
| PVE vnc | QMP `set_password` (random, 30 s) on `<vmid>.qmp`, RFB on `<vmid>.vnc` |
| PVE spice | QMP `query-spice` + `set_password`; TLS to 127.0.0.1:tls-port verified against `/etc/pve/pve-root-ca.pem` |
| PVE serial | `/var/run/qemu-server/<vmid>.serialN` |
| PVE LXC shell / tty | `lxc-attach --clear-env` login shell / `lxc-console -e -1` on a PTY, via `systemd-run --pty` when sandboxed |
| PVE actions | `qm`/`pct` start, shutdown, reboot, stop, sendkey; via `systemd-run` when sandboxed (guests must not inherit the agent's sandbox) |

**Policies**: `Policy` adds `host_shell`, `host_power` (both off unless

**Actions** (`action` stream): `pause`, `resume` (power), snapshot
`snapshot_create` / `snapshot_restore` / `snapshot_delete` with `Args`
`snapshot`, `description`, `memory` (power), and with `Platform: "host"`
`host_reboot` / `host_shutdown` (host power).

**Consoles**: protocol `logs` (read-only): Docker container logs (last 500
lines, then followed; also for stopped containers) or, with `Platform:
"host"`, the systemd journal (console permission). `shell` on Docker
containers (`docker exec`, console permission) and with `Platform: "host"`
a root login shell (host shell permission).

**Inspect** (`inspect` stream, console permission): `InspectRequest{kind}`
→ `InspectResponse` with `processes` (top by CPU, with the guest a process
belongs to), `ports` (listening sockets with their process), `services`
(systemd units or OpenRC services), `updates` (pending packages, security
flagged) or, for a guest, `snapshots`. Nothing of it is stored by the hub.

**Self-update** (`update` stream, hub → agent): `UpdateRequest` (version,
arch, size, SHA-256, Ed25519 signature of the digest) followed by
`UpdateChunk`s of at most 1 MiB, answered by `UpdateResponse` after the
agent verified the signature with the public key built into its binary
(`-X rackoon/internal/agent.UpdatePublicKey=`), checked that the new
executable reports the version (`whombat-agent <v>` or Rackoon's
`rackoon-agent <v>`), refused same-version (`same_version`), older
(`older_version`: never back, HS-140; versions ordered by the build time
of `0.0.0-<UTC YYYYMMDDHHMMSS>.<rev>`, else semver, and refused when the
order is unknown) and wrong-arch updates, and installed the executable (systemd / OpenRC / SysV
in place; Unraid also on the boot flash). It then restarts. A marker
(`update-pending.json`) rolls back to the previous executable (`<exe>.prev`,
and the flash copy on Unraid) when the new version does not connect to the
hub within 5 minutes or starts more than 3 times without connecting.
Signing: `cmd/rackoon-sign` (key outside the repo,
`~/.config/rackoon/update-signing.key`), `make hub` writes
`dist/agent/manifest.json`.

**Whombat Helper** on a Mac follows the same stream: `UpdateRequest.Component`
`helper` (absent: the agent itself), `Arch` `universal`, `Version` the
helper's, the zip's size, SHA-256 and signature (the same key), and `Team`,
the Apple team the hub's build names. The hub sends it only to an agent
whose `AgentInfo.Caps` has `helper_update` (a Mac's agent with its screen
part). The agent answers `unsupported` without a helper, `update_disabled`
without its key, with `[update] allow = false` or without the host shell,
refuses the same or an older version than the installed app
(`same_version`, `older_version`; none installed takes any), any `Arch`
but `universal` (`wrong_arch`) and a bad signature, receives the zip into
`<state dir>/helper-update.zip` (0600) and installs it without restarting
itself (below, "Additions (2026-11-17): Whombat Helper updates"). Another
code: `no_answer`, the new helper didn't answer at the screen and the
previous one is back.

**Checks** (`checks` message, hub → agent on the control stream, after
`hello_ack` and on every change): `CheckSpecs` with HTTP / TCP / ping / DNS
checks for this agent to run from its network (at most 200, 8 at a time,
interval 30 to 3600 s with jitter). The latest result of each is in
`Report.Checks`; the hub ignores results for checks the agent does not own.

**Self-metrics** in `Report.Agent`: CPU including helper processes
(getrusage), consoles open, reconnects, dropped events, install method,
architecture and update key fingerprint.

## Additions (2026-10-17): managing guests

Additive like the above; `proto.Version` is unchanged. `docs/MANAGE.md`
is the design.

**Policy**: `Policy.Manage` (`manage`, off unless `[remote_control] manage
= true`; it implies neither power nor console). The runtime answers the
`manage` stream with `remote_control_disabled` without it.

**Manage** (`manage` stream, hub → agent): `ManageRequest` →
`ManageResponse` (`internal/proto/manage.go`), one operation per stream.
The request names an operation (`config.get`, `config.set`,
`disk.resize`, `guest.create`, `backup.restore`, `task.status`, …), a
platform (`pve`, `incus`), a guest (its platform id, as in the report) and
typed values, never an API path, a command or a host file path; the agent
checks every key and value against its own allowlist and, on Proxmox VE,
uses its own limited API token. The answer is `OK` with the operation's
part (`Config`, `Choices`, `Backups`, `Content`, `Appliances`, `Tasks`,
`TaskStatus`, `Firewall`, `Changes`, `NewID`), or a `Code` with `Message`
and, for values that failed validation, `FieldErrors`. `OK` with `Task`
means the platform still works on it: the hub asks `task.status`
(`LogStart` -1: no log) every 2 s until it ends. The hub's timeout is
100 s; the agent answers long operations with their task at once. Codes
besides the broker's (`invalid_request`, `unknown_guest`, `unsupported`,
`platform_error`, `timeout`, `busy`, `inventory_unavailable`):
`digest_mismatch`, `locked`, `not_allowed`, `invalid_value`, `not_found`,
`guest_running`, `protected`, `exists`. The hub refuses obviously invalid
values before opening the stream, checks role, its own Manage switch and
`Policy.Manage`, and runs one change per guest at a time (shared with
power actions); the agent keeps its own guest lock.

**Report**: `Guest` adds (Proxmox, `omitempty`) `tags` (strings),
`pending` (configuration changes waiting for a restart), `qga`
(`running` | `not_running`: the QEMU guest agent of a running VM with the
agent enabled), `snap_oldest` (time), `backup_job` (bool pointer: an
enabled backup job covers the guest; absent = unknown) and `ha` (the HA
manager's state). `PVE` adds `templates` (`TemplateGuest`: guest templates
of this node, which stay out of `guests`); `PVEStorage` adds `prov` (the
configured size of this node's guest disks on it) and `thin`. The hub
bounds them like the other report strings and lists (32 tags per guest,

## Additions (2026-10-17): the assistant

Additive like the above; `proto.Version` is unchanged. `docs/ASSIST.md` is
the design (§3, the catalog in §3.1); `internal/proto/assist.go` the types;
`internal/agent/diagnose` the agent's side.

**Policy**: `Policy.Diagnose` (`diagnose`), unlike the other switches **on
unless** `[remote_control] diagnose = false` (absent counts as true; new
`agent.toml` files list it as `true`). It allows the read-only checks only;
the assistant's shell commands need `host_shell`, and console, power or
manage imply neither. The agent logs `diagnose` with the other switches at
start.

**Diagnose** (`diagnose` stream, hub → agent): `DiagnoseRequest{check,
args}` → `DiagnoseResponse`, one check per stream; `remote_control_disabled`
without the policy. `check: "list"` answers `Checks`: the catalog of the
checks this host can run (name, description, arguments, which are
required); a check whose tool or file is missing (no `smartctl`, no Docker
socket, not Unraid, no `pveversion`, …) is left out and answers
`unsupported`. The hub names a check and its arguments, never a command:
the agent validates every argument (unknown arguments, unit, container,
instance, domain, pool and VMID names, disks resolved to a block device
under `/dev` or `/dev/disk/by-id`, `lines` and `limit` lowered to their
maximum, `since` parsed into a time, `grep` at most 200 characters, a
`priority` name) and answers `invalid_request` with the reason. Checks run
fixed argv (no shell) with a clean environment (`PATH` with sbin,
`LANG=C.UTF-8`, `HOME=/root`, `SYSTEMD_COLORS=0`), stdin closed, in `/`,
30 s per command and 50 s per check (the stream allows 60 s), stdout and
stderr together. A check of several commands answers sections headed `$
<command>`, a failing one shows its error in its section; a check of one
command that fails answers `failed` (or `timeout`) with what it printed.
`Commands` lists what ran. Output is UTF-8 without escape sequences, at
most 256 KiB (`Truncated`; logs keep their end, the rest their start).
Configuration output (Unraid's `var.ini` and `disks.ini`, `qm` / `pct
config`) has the values of keys that look like passwords, tokens or keys
(`csrf_token`, `cipassword`) replaced with `<redacted>`, as have
`KEY=value` pairs, URL passwords and the argument after a secret flag in
process command lines and `docker inspect`; containers' `Config.Env` is
never returned. `pvesm` and `ha-manager` run outside the agent's sandbox
(`systemd-run --pipe`), like the broker's. `logs` reads the journal
(`journalctl -o short-iso -n N`, `--unit`, `--since`, `--grep`,
`--priority`); kernel messages come from the journal too
(`_TRANSPORT=kernel`, all boots) because the sandbox's
`ProtectKernelLogs=yes` blocks `dmesg`. Without journald (Unraid, SysV,
OpenRC) the agent reads the last 32 MiB of `/var/log/syslog` or
`/var/log/messages` itself and filters by program, `kernel:`, the `grep`
regular expression and the lines' timestamps (syslog files have no
priority; the answer says so). `smart` uses `smartctl -x -n standby`: a
disk in standby is not woken up.

**Disk usage** (`disk_usage` stream, hub → agent): `DiskUsageRequest{mount,
max_depth, timeout_s}` → `DiskUsageResponse`, controlled by `Policy.Diagnose`
(same read-only switch as `diagnose`). Runs only on request (never scheduled),
one scan at a time (`busy` otherwise). Validates that `mount` is a local
mounted filesystem (rejecting remote and virtual mounts, except Unraid's
`/var/log` tmpfs). Before touching the mount, resolves every backing physical
disk from RAM/metadata (Unraid's `/var/local/emhttp/disks.ini`, macOS
inventory/`diskutil` plist for APFS containers and slices, Linux
`/sys/fs/btrfs/<fsid>/devices/`, `/sys/fs/bcachefs/<uuid>/dev-*/block`,
`dm-*`/`md*` `slaves/`, ZFS pool inventory) and checks spin state for
rotational physical disks via cached `Standby` state, Linux kernel sysfs
(`device/power/runtime_status` and `device/state`), and — only for confirmed
ATA/SAT disks (direct `libata`, SAS HBA SATL with vendor `ATA`, or legacy
IDE) — `hdparm -C` or `smartctl -d <sat|ata> -n standby,3,5 -i` (treating an
unsupported `CHECK POWER MODE` as unknown; USB bridges, native SCSI/SAS,
hardware RAID volumes, and macOS rotational drives are never probed and return
`standby_unknown`; hypervisor virtual guest disks such as `vd*`, `xvd*` and
QEMU/VMware/VBOX/Hyper-V disks and non-rotational NVMe/SSD/MMC devices cannot
spin down, while passed-through physical HDDs in a VM are still checked). If any backing disk
is confirmed asleep it returns `code: "spun_down"` with `skipped_spun_down`; if
the backing disks, disk type or spin state cannot be confirmed (for example
LXC `loop*` mounts, ZFS without visible pool disks, missing Btrfs/bcachefs
sysfs, ZFS zvols or union/pooled FUSE mounts such as mergerfs) it returns
`code: "standby_unknown"` without doing I/O on the mount. Walks on a
low-priority thread (Linux nice 19 + `IOPRIO_CLASS_IDLE`; macOS
`PRIO_DARWIN_BG`), anchors the scan to one open directory descriptor of the
target mount root (on Linux resolved strictly from kernel cache via
`openat2(O_PATH, RESOLVE_CACHED | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS)`
so neither intermediate nor final components can trigger an automount or wake a
disk, verified via `/proc/self/fdinfo/<fd>` mount ID before `statx`, `fstatfs`,
or readable open; on macOS verified via `fgetattrlist(ATTR_CMN_FSID)` before
`fstat`), and resolves every subsequent step relative to its open parent
descriptor: on Linux via `openat2` with
`RESOLVE_NO_XDEV | RESOLVE_NO_SYMLINKS | RESOLVE_NO_MAGICLINKS` (pinning entries
with `O_PATH` and verifying `/proc/self/fdinfo/<fd>` before `statx`, refusing
newly mounted filesystems and bind mounts with `EXDEV`, rejecting automount
triggers before any readable open, and reading raw `getdents64` entries so
`DT_UNKNOWN` entries on XFS without `ftype=1` or FUSE never trigger a hidden
`lstatat`); Linux kernels lacking `openat2` or `RESOLVE_CACHED` (`ENOSYS` /
`EINVAL`), seccomp profiles blocking `openat2`/`statx`, unsupported macOS
volumes lacking `ATTR_DIR_MOUNTSTATUS`, and other OSes refuse cleanly with
`code: "unsupported"`; on macOS via batched `getattrlistbulk(2)` (skipping
mount points, automount triggers, and APFS firmlinks before `openat`). Never
follows symlinks, deduplicates hardlinks,
and bounds depth (default 6, max 12), entries (250,000) and time (default 20 s,
max 45 s; sets `partial: true` when cut short). Reports recognised categories on
that mount (container images, build cache, volumes and logs, systemd journal,
package caches, VM disks and snapshots where known) and up to 15 largest
non-overlapping folders.

**Exec** (`exec` stream, hub → agent): `ExecRequest{cmd, timeout}` →
`ExecResponse`, needs `Policy.HostShell`. The command (at most 16 KiB, no
NUL) runs with `/bin/sh -c` as root, stdin `/dev/null`, a clean environment
(`PATH`, `HOME=/root`, `LANG=C.UTF-8`, `USER`, `LOGNAME`, `TERM=dumb`,
`DEBIAN_FRONTEND=noninteractive`), 120 s by default and 1800 s at most.
Under systemd it leaves the agent's sandbox (a read-only file system and no
`/root`): `systemd-run --quiet --wait --collect --pipe
--service-type=exec --property=KillMode=mixed --property=TimeoutStopSec=5s
--property=RuntimeMaxSec=<timeout>s --working-directory=/root --setenv=…
-- /bin/sh -c <cmd>`, so systemd stops the unit, and everything the command
started, when the time is up (`TimedOut`: the run lasted its timeout and
failed, as `systemd-run` exits 1 then). Elsewhere (Unraid, OpenRC, SysV)
it runs directly in `/root` (or `/`) in its own process group, which is
killed when the time is up or the shell exits. `ExitCode` is the shell's
status (128 + signal when killed), `Output` stdout and stderr as they
interleaved (the last 256 KiB), `DurationMs` the run time; `failed` means
the command could not be started. The agent logs every command (its first
200 characters) when it starts and when it ends, with exit code, duration
and `timed_out`; the stream allows the timeout plus 30 s.

and app names match with case and white space ignored (exact, then the
start, then a part; an ordinary app before an accessory or an extension
matched alike); it takes `{"op": "action", "app", "name", "role",
"index", "action"}` (Accessibility, unlocked: the element as `press`
finds it, then the accessibility action named `action`: an app's own,
listed as `Name:Play\nTarget:0x0\nSelector:(null)` and named by the words
after `Name:`, or an `AX…` one; exact, then the only one that starts with
it; `not_found` with the element's action names), `{"op": "quit", "app"}`
(an ordinary app, `terminate()`, up to 3 s, `message` "It is still
closing." when it hasn't ended), `{"op": "geocode", "queries"}` (1 to 8,
each at most 300 characters; `places` in order, `{lat, lon, accuracy_m}`
or null; one search at a time, answers kept an hour) and `{"op": "map",
"w", "h", "scale", "dark", "format", "pins", "lat", "lon", "span_m"}`
(MapKit; `image` base64, `format`, `w`, `h` in pixels, `points` in the
requested points from the top-left or null, `lat`, `lon`, `span_m` the
region drawn); `quit`, `geocode` and `map` work while locked and without
Accessibility, and `geocode` and `map` get 20 s. `status` adds `idle_s`:
whole seconds since the last keyboard or mouse input at the Mac
(`CGEventSource` of the HID system state, so Screen Sharing's input
counts too), null when unknown.

## Additions (2026-10-18): out of memory, the machine or a limit

`proto.Version` is unchanged; both fields are additive (Whombat
`less-is-more.md` LM-04, decisions HS-111…HS-118).

- **Report**: `SystemInfo.OOMLimitKills` (`oom_limit`): of `OOMKills`, the
  kills the kernel made because a cgroup reached its own memory limit
  (`CONSTRAINT_MEMCG`), as far as the agent saw them in the kernel log;
  never more than `OOMKills`; nil when the agent cannot read the kernel log
  (or is older). `SystemInfo.OOMLimited` (`oom_limited`): those kills of the
  last hour, newest last, at most 16, each `{at, proc, cgroup, platform,
  guest}`: the killed process's name, the cgroup at its limit (the kernel's
  `oom_memcg`, `""` when its summary line was rate-limited) and, when that
  cgroup is a guest's, the guest (`platform` and `Guest.ID`).
- **The agent** reads `/dev/kmsg` where it may, else (systemd, the unit's
  `ProtectKernelLogs=yes`) the journal with `journalctl -k`, every 60 s
  after `/proc/vmstat`. A kill it does not see counts as the machine's.
- **The hub**: `host.oom` counts `ΔOOMKills − ΔOOMLimitKills` when this and
  the last report carry the split, else every kill as before; kills at a
  limit are the `memory.limit` hint (`docs/CONTRACT.md`). An old hub ignores
  the fields and warns on every kill.

## Additions (2026-11-17): Whombat Helper updates

`proto.Version` is unchanged; both fields are additive (decisions
HS-360…HS-372).

- **AgentInfo.Caps** (`caps`): what the agent can do beyond the base
  protocol. `helper_update`: it installs Whombat Helper sent on the update
  stream. A Mac's agent reports it; older agents and Linux agents don't,
  and are never sent a helper.
- **UpdateRequest.Component** (`component`): `helper` for Whombat Helper's
  zip; `Team` (`team`) the Apple team id the hub's build names (from
  `whombat-helper-macos.json`, or absent). An older agent would refuse a
  helper as an agent update anyway (`universal` is no agent's
  architecture).
- **The install** (`internal/agent/screen/helperinstall.go`): the zip is
  unpacked with `ditto -x -k` into `.update` beside the app
  (`/Library/Application Support/Whombat`, made root's 0755 when missing;
  a link there is refused). The bundle must be `Whombat Helper.app` with
  `Contents/MacOS/WhombatHelper`, its `Info.plist` must name
  `com.whombat.helper` and the version told, `codesign --verify --deep
  --strict` must pass, and when the new app is signed by a team (not ad
  hoc) that team must be the installed app's or the one the request names.
  The app becomes root:wheel, `u+rwX,go+rX,go-w`; the installed one is kept
  as `Whombat Helper.app.prev` and the new one renamed into place. When the
  new build's designated requirement (`codesign -d -r-`) differs from the
  installed one's and it is signed ad hoc or by another team, the helper's
  Accessibility permission is reset (`tccutil reset Accessibility
  com.whombat.helper`) before it restarts: macOS remembers the permission
  by the build it saw, and would list the new one as switched on without
  access; reset, it shows up switched off (install.sh does the same, and
  its uninstall resets it). The LaunchAgent
  `/Library/LaunchAgents/com.whombat.helper.plist` is written when missing
  (install.sh's file). The helper restarts in every desktop
  session (`launchctl kickstart -k gui/<uid>/com.whombat.helper`, or
  `bootstrap gui/<uid>` where it isn't loaded, three tries); the agent asks
  the helper of the user at the screen for `status` every 2 s until it
  answers with the new version, at most 2 minutes. Then `.prev` goes and the
  answer is OK (its message says when the new helper runs without
  Accessibility, as an ad hoc build or a new signer does; the report's
  `macos.helper.ax` says it too). No answer: the new app goes, the previous
  one comes back and restarts (a first install takes out the app and the
  LaunchAgent it wrote), `no_answer`. Nobody at the screen: installed, OK,
  “it starts when someone logs in”.
