# Hosts service decisions (One Whombat, stream H, 2026-10-17)

Rackoon's hub becomes Whombat's headless hosts service (ONE-11…ONE-15 in
Whombat's `docs/decisions/one-whombat.md`; the assignment is Whombat's
`docs/implementation/one-whombat/assignment.md` §4). The contract Whombat
uses is `docs/WHOMBAT.md`. Decisions taken in this stream:

| # | Decision | Why |
|---|---|---|
| HS-01 | **Headless is a mode of the same binary** (`serve --headless`). The route table is split into `authRoutes` (sign-in, passkeys, single sign-on, kiosk, API tokens, users) and `dataRoutes`; headless registers only the data routes, and neither notification channels nor the assistant. Without `--headless` everything works as before (Rackoon's own UI). | One code base; the non-headless tests keep covering the shared paths. |
| HS-02 | **Headless, the service token is the only credential**: session cookies and `rk_` API tokens are not even looked at, also when a data directory with Rackoon users is reused. | One permission model, Whombat's (ONE-12). |
| HS-03 | The service token is `wbh_` + 43 base64url characters (256 bits), created with `O_EXCL` and mode 0640 when the file is missing; the hub keeps only its SHA-256. The file is re-read when its size, time or inode change (checked every 2 s); a missing or malformed file refuses every request (logged once) and is not recreated while the hub runs. Consoles and event streams opened with an old token end. | Rotation without a restart, fail closed, and "re-authorisation checks the token still matches" means something. |
| HS-04 | `X-Whombat-Actor: <id>\|<name>`: the id is 1–128 of `A–Z a–z 0–9 . _ : @ -` (else 400 `bad_actor`), the name printable, ≤ 128 bytes, whitespace collapsed; absent = `whombat\|Whombat`. The hub's user name for the actor is **`<name> (<id>)`** (audit log, `acknowledged.by`, `created_by`); per-person limits key on the id, through a stable negative user id (FNV-1a of the id). | Several people's assistants are all called "Whombat" (ONE-01): the id is what tells them apart; real user ids are positive, so no clash. |
| HS-05 | `X-Whombat-Role` only lowers (default admin); an unknown value is 400 `bad_role`, not ignored. | A typo must not grant admin. |
| HS-06 | The service principal skips CSRF, the Origin check (also on the console WebSocket) and re-authentication. | A bearer token is not ambient; Whombat checks its browsers' origins and asks people itself (approvals). |
| HS-07 | Requests over the Unix socket count as a secure transport (consoles, no `insecure_transport`). `X-Whombat-Client-IP` becomes the request's address for service requests and `X-Forwarded-*` are dropped. | The socket is local; the browser's TLS is Whombat's job. The audit log shows the person's address. |
| HS-08 | `--listen unix:/path`: a socket file left by an earlier run is replaced unless something still answers on it; the hub chmods it to `--socket-mode` (0660) right after binding. `--tls-cert` with a socket is refused. A headless TCP listener that is not loopback logs a warning. | Restarts after a crash must not need cleanup; two hubs on one socket must not happen. |
| HS-09 | **`install.sh`, `/download/*` and `/ping/*` are also served on the agent listener**, in both modes. Headless, `POST /enrollments` returns ` curl -fsSL --insecure --pinnedpubkey 'sha256//<listener key>' https://<agents address>:<port>/install.sh \| sudo sh -s -- --token …`, and the script pins the same key for the binary (wget cannot pin; the SHA-256 from the pinned script checks the binary). Not headless, the command keeps the UI origin. The response adds `install_url`, `tls_pin`, `agent_url`, `ca_sha256`. | curl cannot pin a CA without a file on disk; pinning the listener's key plus the checksum gives the same guarantee in one line (ONE-15). |
| HS-10 | `--agent-url auto`: the IPv4 of the interface with the default route of lowest metric (`/proc/self/net/route`, visible in a `ProcSubset=pid` sandbox, else `/proc/net/route`; private addresses first), else the source address of a UDP "connect" to 192.0.2.1 (no packet). Looked up when used, cached 30 s, the last good answer kept on errors; also included in the listener certificate at start. | DHCP changes show up within a minute; no outbound traffic. Agents do not check host names (pinned CA), so the certificate need not follow. |
| HS-11 | Without `--agent-url`, the agents' URL falls back to the agent listener's own host when it names one; when nothing is known, headless enrollment answers 503 `no_agent_url`. | An install command that cannot work is worse than a clear refusal. |
| HS-12 | Headless, a heartbeat check's `ping_url` is on the agent listener. | It is the only port hosts can reach. |
| HS-13 | **Diagnose and exec as REST routes**: `GET/POST /servers/{id}/diagnose` (operator, the diagnose switches, each run audited as `diagnose.ran`; a check that ran and failed or timed out is 200 with `ok: false`), `POST /servers/{id}/exec` (admin, both host shell switches, re-authentication — the service token passes —, audited before it runs and refused if that fails, `exec.finished` after; it runs to its end when the caller leaves). Output as the agent bounds it (256 KiB). | The same rules the assistant and the host shell had; Whombat's own keys and approvals sit in front (ONE-12). |
| HS-14 | **`guest.migrate`** (`POST …/guests/{guestId}/migrate {target, storage, digest, confirm}`): admin, `confirm: true`, Proxmox VE clusters only. Running VMs: `online=1` and `with-local-disks=1`; running containers: `restart=1`, `timeout=180`; stopped guests offline; `targetstorage` / `target-storage` from `storage`. PVE's migrate API has no digest, so the agent compares it with the current configuration first. Templates are refused. `VM.Migrate` is listed in `WhombatManage`'s extra privileges (PVEVMAdmin has it already). | Migrating always asks in Whombat (ONE-12); `with-local-disks` is harmless for shared storage and needed for local disks. |
| HS-15 | **Names** (ONE-14): binaries `whombat-hosts` and `whombat-agent`; agent paths `/usr/local/bin/whombat-agent`, `/etc/whombat-agent`, `/var/lib/whombat-agent`, unit / init script `whombat-agent`, `/run/whombat-agent.pid`, Unraid `/boot/config/plugins/whombat-agent` and `rc.whombat-agent`; Proxmox `whombat@pve`, `whombat-manage@pve`, `WhombatManage`, `WhombatNetwork`; settings `WHOMBAT_HOSTS_*` (`RACKOON_*` still read); data default `/var/lib/whombat-hosts`; snapshot default name `whombat-<time>`; texts the service passes on say Whombat. | User-visible names say Whombat; nothing is shared with a Rackoon agent, so both run side by side. |
| HS-16 | **Kept as they were**: the Go module path `rackoon` (import paths, `-X rackoon/internal/agent.UpdatePublicKey`), the developer tools `rackoon-sim`, `rackoon-sign`, `rackoon-collectdebug`, the console subprotocols `rackoon.console.v1` / `rackoon.token.`, Prometheus metric names `rackoon_*`, problem type URLs, cookie names, the webhook format name, and the non-headless UI's texts (setup banner, passkey name, notifications), since the web UI is not changed. The agent offers `whombat.agent.v1` and `rackoon.agent.v1`; the hub accepts both and Rackoon's `rackoon:server:` certificate URIs (new certificates say `whombat:server:`); the updater accepts `whombat-agent` and `rackoon-agent` version output. | Wire compatibility and less churn; the web clients ported into whombat-app speak the console protocol unchanged. |
| HS-17 | A Rackoon agent is **not** turned into a Whombat agent by a pushed update: its updater wants `rackoon-agent` output, and its paths would stay Rackoon's. Moving John's servers is a reinstall with the Whombat installer (and `install.sh --uninstall` of the Rackoon one), a follow-up with importing a hub (ONE-22). | No silent changes on John's servers during the build. |
| HS-18 | **`make deploy-dev` is retired** and AGENTS.md says so: the Rackoon dev hub (`rackoon` container) and the LAN agents stay on the last Rackoon build until John moves them. | Deploying this tree there would rename the agent and its paths under running hosts. |
| HS-19 | `go 1.27.1` in go.mod (mise keeps 1.27.2 as the toolchain). | nixpkgs' `buildGo127Module`. |
| HS-20 | Build targets for the appliance: `make headless` (hub without the UI) and `make agents-unsigned` (agents without an update key: self-update off on DEV); `make lint-go` is gofmt without the web toolchain. | The appliance packages exactly these; the web UI is not built (stream WT ports it). |
| HS-21 | `rackoon-sim --ui unix:/path --service-token-file F` drives a headless hub (enrollments, approvals, switches through the service token; the agents' URL and pin from `GET /hub`). `GET /hub` adds `headless`, `ca_sha256`, `tls_pin`, `agents_url`. `GET /metrics` accepts the service token. | Smoke tests against the real binary with the fake fleet (stream SH), and `hosts.status`. |
| HS-22 | Two diagnose tests skip `/dev` symlinks (`/dev/cdrom` resolved to `/dev/sr0` and failed on machines with an optical drive), and the Incus manage tests set their fast watcher retry once instead of restoring it (a race under `-race`). | Keep the suite green; the code was right. |

## Full Proxmox support (stream H, 2026-10-17)

Whombat's `docs/decisions/proxmox.md` (PX-01…PX-11) and
`docs/implementation/proxmox/assignment.md` §2.1 and §2.3.

| # | Decision | Why |
|---|---|---|
| HS-23 | **Backup jobs** (PX-03): `backupjob.list` reads `GET /cluster/backup` with the manage token (`Sys.Audit`); `backupjob.create`, `update` and `delete` run `pvesh create\|set\|delete /cluster/backup[/<id>]` as root with `--key=value` arguments, after every value was checked; `backupjob.run` posts `/nodes/{node}/vzdump` with the token like Back up now. `pvesh` joins `pvesm` and `ha-manager` outside the agent's sandbox (systemd-run). | PVE wants `Sys.Modify` on `/` for jobs, which would let the token change the node; a new job writes its state file in `/var/lib/pve-manager/jobs`, read-only for the sandboxed agent. |
| HS-24 | The agent makes the job id (`backup-<8 hex>-<4 hex>`, like PVE's dialog). The digest is SHA-256 of the job's JSON as listed without `next-run` (keys sorted, numbers as PVE wrote them); update compares it first. pvesh errors: "400 Parameter verification failed." with its `field: message` lines → `invalid_value` with the request's field names, "already exists" → `exists`, no such job → `not_found`, a cluster lock → `locked`. Failed commands keep their error output (`cmdError`) for this. | `pvesh create` answers nothing and PVE's own default id is a bare UUID; PVE's job API has no digest, and `next-run` moves with the clock. |
| HS-25 | **Run** backs up the job's guests on this node only. A job restricted to another node, or a guests job none of whose guests are on this node, is `unsupported` ("run it from that server"); one without a storage (a `dumpdir` job) is `not_allowed`. A job with its own retention runs with `remove=0`; without one vzdump prunes by the storage's retention, as the scheduled run does. | The task of another node cannot be followed through this agent; `prune-backups` through the API needs `Datastore.Allocate`, which would let the token change storage definitions. The next scheduled run prunes. |
| HS-26 | Values: `keep` with every count 0 is `keep-all=1` (and reads back so); `keep: null` is the storage's own retention. `compress` is `zstd`, `lzo`, `gzip` or `"0"` (none); `null` is Proxmox's default, PVE's old `"1"` reads as `lzo`. A new job defaults to `mode` snapshot and `compress` zstd, none on a Proxmox Backup Server. `comment` and `notes_template` are one line up to 1024 characters (PVE itself allows 512 for `comment` and says so). | The shape of §2.1 has no `keep_all`; the defaults are what Proxmox's own dialog sets (no compression wastes space). |
| HS-27 | Updates send only what changes; `null`, `""` or `[]` removes `node`, `compress`, `keep`, `notes_template`, `comment` or `exclude`; other fields cannot be removed. Changing `selection` needs the new one's `guests` or `pool` (PVE drops the old one's keys). Guest ids a job already has pass even when their guest is gone; new ones must be in `/cluster/resources`. The hub reads job bodies itself (hub ids → vmids, `Clear`), not as `ManageRequest` JSON; create answers `{ok, id, audit_id}`, update always has `changes`; a server without Proxmox VE is 501 `unsupported`. | John's real job on pve-01 excludes deleted guests: refusing them would make it uneditable. |
| HS-28 | After a backupjob create, update or delete through the agent, the runtime asks the collector to read the jobs again (`RefreshBackupJobs`, the slow PVE sub marked dirty) and reports at once, so `Guest.BackupJob` and the `guest.no_backup_job` hint follow within about 10 seconds. Jobs changed in Proxmox's own UI show at the next slow read (5 minutes). | “Add to a backup job” that leaves the hint for five minutes looks broken. |
| HS-29 | **Snapshot lists need power or manage** (PX-08); a switch counts when it is on in the hub and in the agent's `agent.toml`. Checked in the hub (`needSnapshots`, 403 `power_disabled` with "Listing snapshots needs power actions or managing guests turned on for this server" or the agent's version), in the agent and in the simulator. Agents built before this still want the console switch. | Snapshots are taken and restored under power; managing guests lists them too. |
| HS-30 | **`whombat-agent allow`, `deny` and `policy`** (PX-04): `[remote_control]` is edited line by line (values replaced in place with their indent and trailing comment, a commented-out `# key =` line takes the value, a missing key goes after the table's last key, a missing table at the end); the result must parse with the asked values, else nothing is written. Dotted or inline `remote_control`, or the table twice, are refused ("change it by hand"). `all` includes `diagnose`; `host-shell` is accepted for `host_shell`. Reload: `systemctl reload whombat-agent` when the unit is active and the directory is `/etc/whombat-agent`; else SIGHUP to the supervisor in `/run/whombat-agent.pid` or to the `whombat-agent run` processes of that directory (from `/proc`: OpenRC's supervise-daemon, a hand-started agent); else the sentence says it applies when the agent starts. The agent's own directory (default, or the Unraid flash when that is where `agent.toml` is) needs root; an explicit `--config-dir` relies on that file's permissions. | Re-serializing the TOML would drop the template's comments; reloading only agents of that directory keeps a test or second agent from signalling the real one; OpenRC keeps no PID file of ours. |
| HS-31 | Rackoon names left in the docs are Whombat's (MANAGE.md: the service, the manage user's comment, `VM.Migrate` listed in `WhombatManage`; REST-API.md: the snapshot default `whombat-YYYYMMDD-HHMMSS`, the example task's `whombat-manage@pve`, "Whombat's allowlist"); the simulator's seeded snapshot is `whombat-…`. HS-16's kept names stay. | PX-08. |
| HS-32 | `TestHubNudgesRenewalOnLongConnection` waits for the hub to register the redialled agent before it looks at the connection. | The hub answers the hello before it attaches the connection, so under a loaded full run the test read nil (a test race; the code was right). |

## Full Incus and the self guest (stream HI, 2026-10-17)

Whombat's `docs/decisions/incus-unraid.md` (IU-01…IU-12) and
`docs/implementation/incus-unraid/assignment.md` §2.1, §2.2, §2.4, §3 HI.

| # | Decision | Why |
|---|---|---|
| HS-33 | **The self guest is marked by the hub at ingest**: `proto.Guest.Self` (`cbor:"-"`, never sent) is set right after `sanitizeReport` (new reports and the ones loaded at start) when one of the guest's MACs is one of the hub machine's. Those come from `/sys/class/net/*/address` (every interface but `lo`, all-zero ones dropped; containers' veths count, a VM's card is what Incus calls `volatile.eth0.hwaddr`), read at start and every 10 minutes; `--self-macs` / `WHOMBAT_HOSTS_SELF_MACS` replaces them. Stored reports are not re-marked: the next report (10 s) follows a changed MAC. | The model stays pure (`BuildGuest` copies the flag, `hosts_this_whombat` is any guest's flag); reports stay immutable once stored. |
| HS-34 | **The refusal is contracts 0.83.0's allow list**, not a deny list: actions `start`, `resume`, `snapshot_create`, `snapshot_delete`; manage changes `backup.create`, `backup.update`, `backup.delete`, `guest.clone`, `replication.add`, `replication.delete`, `task.stop`; `backup.restore` as a new guest; reads and consoles. Everything else changing the self guest (also `ctrl_alt_del`, firewall, HA, a restore over it) is 409 `self_guest` “That’s this Whombat itself.”, audited as denied; the assistant's guest tool refuses too. Host power on its server is not refused. | Hub, server and apps agree (coordinator, 2026-10-17); Ctrl+Alt+Del reboots most guests. |
| HS-35 | `detail_view`: `proxmox` > `unraid` > `incus` > `standard` (a future `libvirt` comes after `incus`). unRAID is HU's `model.IsUnraid` (HS-61). An Incus host is any whose report has `incus`, also when its collector failed. | Both new values fit one function. |
| HS-36 | **The Incus host view rides on `Platform.Incus`** (`proto.IncusDetail`), read on the slow path (5 minutes) and after lifecycle events (`instance-backup-*`, `storage-pool-*`, `storage-volume-*`, `image-*`, `profile-*`, `network-*`, `project-*`, instance created/deleted/renamed/updated); project instance counts follow every run. Networks are the managed ones and host bridges, not Docker's (`docker0`, `br-<12 hex>`) nor physical cards; the create form's bridges leave Docker's out too. Volumes are custom ones of every project, each with its `…/state` use. A part Incus cannot answer is left out, the rest is kept. | One request per volume and pool every 5 minutes is cheap; Docker's 25 bridges on The Titan were noise. |
| HS-37 | **Incus hints**: `incus.no_snapshots` needs `created` (an agent that reports schedules), skips instances younger than a day (CI jobs) and lists all such instances in one hint per host with the new optional `hints[].guests` (hub ids) for the way out; `incus.pool_full` is info from 85 %, a warning from 95 %; `incus.warning` replaces `platform.warnings` for Incus (link `#system`). | Five running instances on The Titan would otherwise be five rows; the guest list lets Whombat open the right guest. |
| HS-38 | **Restore streams in the agent** (`GET …/backups/<b>/export` piped into `POST /1.0/instances` with `X-Incus-name` / `X-Incus-pool`), always as a new instance (`guest` names the source; default name `<name>-restored`), answered at once with an agent task `incus:<random uuid>` whose messages say "Copying the backup: 45% (…)", "Unpacking the backup" and whose status gets `new_id`. The hub needs no `confirm` for an Incus restore. | The copy can take minutes (the 90 s manage call cannot wait); a backup never leaves the host and never overwrites. |
| HS-39 | **Backups**: default name `whombat-YYYYMMDD-HHMM` (minutes, Incus backup names are per instance), expiry 7 days, compression `zstd` / `gzip` / `none` (`compress` read when `compression` is empty), `notes` = `expires <RFC 3339>`, `format` `optimized` / `tar`, size from `/var/lib/incus/backups/instances/<project>_<name>/<backup>` when readable (none with `storage.backups_volume`). | The shapes of §2.2; Incus' API has no size. |
| HS-40 | **Publish and image downloads answer a task**; the fingerprint is known when it ends: `TaskStatus.new_id` and `task.finished.new_id` (the hub's watcher keeps it; the audit's `manage.finished` has it). A download names the image locally with its alias only when that alias is free; `auto_update` defaults to true. | Incus computes the fingerprint at the end; aliases are unique per project whatever the type. |
| HS-41 | **Tasks**: `task.list` merges Incus' operations of class `task` (exec and console sessions are not tasks and carry secrets), the agent's own (kept 48 h, at most 200) and the failed ones the collector reports; `task.stop` cancels only operations that say `may_cancel` (`not_allowed` otherwise; a finished one is OK). | "Running ones and the last 48 h" (§2.2) although Incus forgets an operation after 5 s. |
| HS-42 | **Leases of every project**: Incus lists only the asking project's leases, so `network.leases` without a project also asks each project using the default project's networks (`features.networks` not true) and merges them; the guest is the instance whose `volatile.*.hwaddr` holds the address. | Checked on The Titan: `cishared0` showed only its gateway from the default project. |
| HS-43 | **Profiles**: the instance allowlist applies, container-only keys included (a profile serves both kinds); `copy_from` copies config and devices as they are (applying the original is allowed, so a copy adds nothing); `default` cannot be deleted (`not_allowed`), a used profile is `in_use`. `config.set` takes `profiles`: a non-empty ordered list replaces the instance's (each must exist in its project); emptying them stays in Incus. | IU-04 "plus profiles"; an empty list cannot be told from "unchanged" once CBOR drops it. |
| HS-44 | `devices` (`{name: {options} | null}`) in `config.set` and `profile.update` becomes `device.<name>` keys of Set/Delete before the allowlist; naming a device in both is refused. | One allowlist and one change list for both spellings. |
| HS-45 | **Create shorthands**: `pool` → the root disk (`device.root` with that pool, the size kept when `device.root` is also set), `network` → `eth0` (a host bridge becomes `nictype=bridged`), `cloud_init` → `cloud-init.user-data` (allowlisted, at most 64 KiB, newlines allowed). The audit records `cloud_init: set`, never the text. | User data may hold passwords. |
| HS-46 | **Move** is Incus' local move (`POST /1.0/instances/<n> {migration: true, pool, project}`), stopped instances only, `confirm: true` in the hub; **rename** takes `^[A-Za-z][A-Za-z0-9-]{0,62}$` without a trailing `-`, stopped only. | §2.2; Incus copies and deletes the original on a move. |
| HS-47 | **Volumes**: create needs an absolute size of at least 1 MiB and `filesystem` or `block` (ISO volumes come from an import, not here); resize only grows and refuses a volume without a size limit; delete refuses an attached volume (`in_use`). | §2.2. |
| HS-48 | **Hub routes by `init`**: `manage_incus.go` appends the Incus routes to `manageRoutes` and adds the Incus fields to the shared routes at start; `manage.go` gained one call per hook (parse, validate, confirm, answer, details, the restore's source guest, the self refusal). Incus-only ops on a host or guest that is not Incus are 501. | Keeps edits of the shared file small for stream HU. |
| HS-49 | **The real-Incus test** (`TestIncusReal`, `WHOMBAT_TEST_INCUS=1`) creates `whombat-test` with its own images, profiles and volumes (`features.images=true`, not the brief's `false`), so the image it caches stays in the project; its cleanup deletes only what the project keeps itself (it checks the features first) and then the project. Ran on The Titan: passes in about 45 s. | With `features.images=false` the cached image would land in the default project's store, outside the throwaway project. |
| HS-50 | **Fake fleet**: every non-Docker guest has a stable MAC; basalt has the complete Incus view, schedules (ci-runner has none), a backup on nixbuild and the Incus VM `whombat` (`fakefleet.SelfMAC` = `10:66:6a:77:68:01`), all left out of the exact fixture. The simulator answers every Incus op on basalt from memory. | The hub's tests and the simulator show the self guest and the Incus pages without touching fixtures. |
| HS-51 | Rackoon's own web UI is not changed (its DEV-only response check lists `standard` / `proxmox`; production skips it). | Whombat reads the hosts service through its server; the Rackoon UI is frozen. |
| HS-52 | After an Incus change the agent relies on Incus' lifecycle events to read the host view again (no extra hook in the manage stream). | Every change Whombat makes raises one; changes made in Incus itself are covered the same way. |

## Full unRAID support (stream HU, 2026-10-17)

Whombat's `docs/decisions/incus-unraid.md` (IU-01…IU-12) and

| # | Decision | Why |

Running checks would write `/tmp/plugins` and send unRAID notifications nobody asked for. |
| HS-54 | **The page's own commands, with the 7.3.1 words** (read from BlackBox's scripts): array `emcmd cmdStart=Start` / `cmdStop=Stop`; parity `emcmd cmdCheck=Check[&optionCorrect=correct]`, `cmdCheckPause=`, `cmdCheckResume=`, `cmdCheckCancel=` (what the Main page's buttons post to emhttpd; pause and resume first append to `/var/tmp/stamps.ini` like `ParityControl.php`); spinning `emcmd cmdSpinupAll=Apply` / `cmdSpindownAll=Apply` / `cmdSpinup=<disk>` / `cmdSpindown=<disk>` (`ToggleState.php`); `mover start` (the cron's); `plugin checkall` / `plugin update <file>`; `dockerupdate check nonotify` (the Docker page's button); `update_container <name>`; `notify archive <id>.notify`. | HS-55 | **Every unRAID command is an agent task** `unraid:<16 hex>` (`broker/unraid_tasks.go`): the command in its own session writing to `<state_dir>/tasks/<id>.log` (an agent restart does not kill it; the task is then unknown), log lines masked and stripped of escapes and dockerMan's HTML, kept a day. Array start and stop wait until `var.ini` says so (15 min), pause/resume/cancel until md does (1 min), and **parity.start follows the check to its end** with a progress line every 5 minutes, ending “No errors.” / “3 errors found.” (cancelled or an error code fails it). `task.status` takes `unraid:` ids on any platform; `task.stop` is `unsupported` (use `parity.cancel`). One array or parity command, one plugin command, one mover run, one container check and one update per container at a time (`busy`). The Titan got “Out of memory · 1 process killed in the last hour” while
98 GB were free; a test's python3 had been killed inside its own memory
cgroup (`constraint=CONSTRAINT_MEMCG`, `oom_memcg=/user.slice/…/wbtest159958.slice`).
`/proc/vmstat`'s `oom_kill` counts such kills too.

| # | Decision | Why |
|---|---|---|
| HS-111 | **The kernel log tells the machine's kills from kills at a cgroup's own limit.** Every kill prints “<why>: Killed process <pid> (<name>) …”, never rate-limited and once per vmstat `oom_kill`: “Memory cgroup out of memory” is a cgroup at its limit (`CONSTRAINT_MEMCG`); “Out of memory” (also `oom_kill_allocating_task`, and the cpuset and mempolicy constraints, where the machine's or a NUMA node's memory ran out) is the machine's. The rate-limited `oom-kill:` summary just before it (same pid, within 10 s) names `oom_memcg`, the cgroup at its limit; `memory.oom.group` kills take the cgroup of “Tasks in <cgroup> are going to be killed”. Older kernels (“Kill process … or sacrifice child”, then a bare “Killed process”) are read from those two lines. Not chosen: comparing vmstat with the cgroups' `memory.events` (its `oom_kill` also counts a machine-wide kill of a process inside a container) or their `oom` events (no link to a kill; one OOM may kill none or a whole group). | Exact per kill, cgroup v1 and v2, no extra permission. |
| HS-112 | **The agent reads `/dev/kmsg` where it may, else the journal**: `/dev/kmsg` without blocking from the oldest record the ring buffer still holds, kernel facility only, the kernel's `\xNN` escapes undone (OpenRC, SysV, Unraid, an agent started by hand); on systemd `journalctl -k -o json`, the first read `--since=-1h`, then `--after-cursor` (after a quiet hour, the newest kernel message's cursor). **The unit is unchanged**: its `ProtectKernelLogs=yes` hides `/dev/kmsg` (and drops `CAP_SYSLOG`) but not the journal, and agents updated by the hub keep the unit they were installed with. The system collector reads the log every 60 s, right after `/proc/vmstat`; a source that cannot be opened is tried again after 10 minutes. | Works after a pushed update, no reinstall, no wider sandbox. |
| HS-113 | **A kill the agent did not see counts as the machine's.** `OOMLimitKills` counts the limit kills read (including what the log still held when the agent started), clamped to `OOMKills`; vmstat is read first, so a kill logged between the two reads counts once vmstat has it. When vmstat counted kills since the last run the log does not show, the agent reads again up to three times a second apart (journald may lag); a kill never logged is not waited for again. A failed read sends `OOMLimitKills` nil. | Every way of missing a line errs towards today's warning; only counting too many could hide a real one. |
| HS-114 | **Protocol, additive**: `SystemInfo.OOMLimitKills` (`oom_limit`, a pointer: nil unknown, 0 none) and `OOMLimited` (`oom_limited`: the limit kills of the last hour, newest last, at most 16, `{at, proc, cgroup, platform, guest}`). `OOMKills` is unchanged. The hub bounds the list and its strings and clamps `OOMLimitKills` to `OOMKills`. | CBOR ignores unknown keys both ways (`TestOOMSplitIsAdditive`). |
| HS-115 | **Cgroup to guest, in the agent, the processes view's way** (`inspect.ContainerOf`, which now also knows libvirt's cgroupfs `qemu-<n>-<name>.libvirt-qemu`, Unraid's): `docker-<64 hex>.scope` or `docker/<64 hex>` (named from the Docker collector's id → name map, kept two hours after a container is gone), `lxc.payload.<name>` / `lxc.payload.<project>_<name>` → Incus `name` / `project/name` (split at the last `_`: instance names have none), `lxc/<vmid>` and `qemu.slice/<vmid>.scope` → Proxmox VE, `machine-qemu\x2d<n>\x2d<name>.scope` → the libvirt domain with the same letters and digits (a long name by its start: libvirt cuts machine names at 64; two candidates are none). Incus, Proxmox and libvirt guests must be in the same report. Resolved when the report is built and retried until known; otherwise only the cgroup goes. Docker inside an Incus or Proxmox container is the inner container's, which the host does not know: a note without a guest rather than a limit put on the outer one. Incus VMs run in `incus.service`, without a cgroup of their own. | One mapping for both views; only the Docker collector knows container ids; guest ids are the report's. |
| HS-116 | **`host.oom` counts the machine's kills only**: per report `ΔOOMKills − min(ΔOOMLimitKills, ΔOOMKills)` when this and the last report carry the split; a limit count that went down (the agent restarted and read less of the log) takes nothing off; without the split every kill as before. Title, detail and banner are unchanged (“Out of memory”, “1 process killed in the last hour”, warning). | The Titan's 10:39 warning becomes a note; a real shortage still warns. |
| HS-117 | **A kill at a limit is a quiet `memory.limit` hint** (info, the report's `OOMLimited` of the last hour), not an alert: one per guest, entity and `guests` its hub guest id, link `#guests`: “A process in web hit its memory limit” / “php-fpm was stopped 12 min ago. No guest field or guest alert: a guest's `oom_killed` means its last exit was an OOM kill (Docker's inspect), the only guest-level alert (`guest.restart_loop`) is a warning, and Whombat already shows hints on Watch with the server's Guests or System tab as the way there. | No change in Whombat's contracts, server or app; plain words, ids and paths only in the detail. |

## On-request disk usage breakdown (2026-11-21)

| # | Decision | Why |
|---|---|---|
| HS-484 | **On-request disk breakdown (`disk_usage` stream, `internal/agent/diskusage`)**: additive stream within `proto.Version = 1`, controlled by `Policy.Diagnose` (on by default on both sides, operator role). Never runs on a schedule; at most one scan runs at a time per agent (`busy` otherwise). For one validated local mount point it reports container images and build cache (Docker/Podman socket `/info` + `/system/df?type=image&type=build-cache`), container volumes and logs (measured locally with the agent's own low-priority bounded walk inside the mount scope), the systemd journal, package caches, VM disks and snapshots where known (including `zfs list` on ZFS), and up to 15 largest non-overlapping folders. | Lets the assistant and the person see what fills a disk when it fills up without running background scans, letting dockerd run unbounded volume walks, or widening permissions beyond read-only diagnostics. |
| HS-485 | **Safe, bounded, non-waking walk** *(skip-reason code, platform/multi-device backing and standby-probe rules refined by HS-487 and HS-488)*: before touching the target mount (`statfs` or `lstat`), the agent checks Unraid's `/var/local/emhttp/disks.ini` (in RAM), the latest report's `Standby`/Unraid spin state, and — falling back to deriving backing disks from the mount's source (partition → disk, LVM/dm/mdraid → member disks via sysfs) — probes rotational backing disks with `smartctl -i -n standby` (falling back to `hdparm -C`); if no backing disks can be identified (such as a ZFS mount without usable pool inventory), any backing disk's rotational state cannot be checked, any backing disk is spun down, or a rotational backing disk's spin state cannot be determined, it answers `spun_down` explaining why (with any known skipped disks) and does no I/O on the mount. The walk runs on a dedicated OS thread locked at low CPU and I/O priority (Linux nice 19 + `IOPRIO_CLASS_IDLE` / lowest best-effort; macOS `PRIO_DARWIN_BG`), verifies every category probe and walked path against the mount table (mountinfo mount IDs, not only `st_dev`) before any stat or read so it never crosses into nested mounts or same-device bind mounts, never follows symlinks, deduplicates hardlinks, uses allocated disk blocks, and stops cleanly with `partial = true` at its depth limit (default 6, max 12), entry cap (250,000) or time limit (default 20 s, max 45 s). | A disk inspection on a busy server or Unraid array must never wake sleeping drives, stall on a child NFS mount, cross bind mounts, hang on deep trees, or starve workloads. |
| HS-486 | **Hub persistence and 24-hour recency (`server_disk_usage`, schema 14)** *(refined by HS-487 for `standby_unknown`)*: `POST /api/v1/servers/{id}/disk-usage` (operator, diagnose switch, audited as `disk_usage.ran`) defaults an omitted mount to the fullest writable local filesystem, persists successful measurements per `(server_id, mount)` in SQLite, broadcasts `server.disk_usage`, and returns `spun_down` cleanly (`ok: false`) without overwriting a prior measurement. `GET /api/v1/servers/{id}` includes `disk_usage` entries measured within 24 hours (newest first) so the server page shows them in place of “Everything else” while recent and falls back automatically once stale. | Keeps the server page and the assistant in sync without making the page trigger scans on load or showing week-old figures. |
| HS-487 | **Truthful skip codes, macOS/VM disk detection, and complete multi-device resolution**: (1) `disk_usage` returns `code: "spun_down"` (with `skipped_spun_down`) only when at least one backing disk is confirmed asleep; unknown backing disks, partial backing resolution, unknown disk type, or unreadable spin state (for example LXC `loop*` roots or invisible ZFS pools) return `code: "standby_unknown"` with an empty `skipped_spun_down` and plain wording that never claims a disk is spun down. The hub handles both codes identically (HTTP 200 `ok: false`, preserving stored measurements). (2) On macOS, `macos.FilesystemsWithDisks` populates `Filesystem.Disks` from physical whole disks (resolving synthesized APFS containers through `DiskList.Containers`), and `diskusage` resolves `diskNsMsK` slices via inventory and `diskutil info`/`list -plist` without ever reading Linux `/sys`; internal/external SSDs scan cleanly, external HDDs probe standby, and disks with unknown `SolidState`, virtual disk images, AppleRAID or CoreStorage skip as `standby_unknown`. (3) On Linux VMs, hypervisor virtual disks are detected **per disk** (`vd*`, `xvd*`, virtio/Xen/Hyper-V/VMware sysfs drivers/buses and hypervisor vendor/model identity) rather than per host, so VM mounts scan without skipping even when the guest kernel reports `rotational=1`, while PCI-passed-through physical HDDs in the same VM still verify standby state and LXC containers are never misclassified as VMs. (4) For multi-device filesystems outside Unraid, Btrfs reads the full member list from `/sys/fs/btrfs/<fsid>/devices/`, bcachefs reads `/sys/fs/bcachefs/<uuid>/dev-*/block`, mdraid checks `slaves/` and `md/dev-*`, LVM/dm walks `slaves/` transitively, and ZFS matches dataset and snapshot sources (`pool/ds`, `pool@snap`) against pool inventory; any missing member list, unresolved stacked/virtual leaf (`loop*`, `dm-*`, `md*`, `zd*`, `rbd*`, `drbd*`, `ublkb*`) or union/pooled FUSE/overlay filesystem (`mergerfs`, `unionfs`, `mhddfs`, `overlay`, `aufs`) skips as `standby_unknown` even if partial inventory lists one disk. | Keeps the non-waking guarantee airtight on multi-device pools while making “What fills this disk?” work out of the box on Macs and VMs and giving people and the assistant honest skip reasons. |
| HS-488 | **Verified non-waking standby probes only** *(2026-11-22; refines HS-485 and HS-487)*: before running any external probe on a rotational physical disk, Linux checks kernel sysfs RAM state (`/sys/block/<dev>/device/power/runtime_status` `"suspended"`/`"suspending"` → asleep without opening `/dev/<dev>`; `device/state` other than `"running"` → unknown). Only confirmed ATA/SAT disks (direct Linux `libata` under `/ata<N>/`, SATA behind a SAS HBA SATL with T10 SAT vendor `"ATA"` and not native SAS `ssp`, or legacy IDE `ide-disk`) are probed, using `hdparm -C /dev/<dev>` (ATA `CHECK POWER MODE` `0xE5` only) when present and otherwise `smartctl --json=c -d <sat|ata> -n standby,3,5 -i /dev/<dev>` (explicit `-d` disables autodetection and `STATUS2=5` exits immediately without running `-i` when `CHECK POWER MODE` is unsupported or unknown). Non-rotational devices (`nvme*`, `mmcblk*`, `pmem*`, SSDs, `queue/rotational == 0`, virtual guest disks) need no probe; USB bridges, native SCSI/SAS disks, hardware RAID volumes, devices without confirmed ATA sysfs metadata, and macOS/non-Linux rotational drives are never probed and return `standby_unknown`. | `smartctl` autodetection can spin a drive up before checking power mode, and an unsupported power check is ignored by default unless `STATUS2` is set; probing only confirmed ATA/SAT paths guarantees the probe itself never wakes a sleeping disk. |
